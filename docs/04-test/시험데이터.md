# 시험데이터 (샘플)

> 실제 대량 시험데이터는 `seed/`(Auto QA 컨벤션 참고)에 별도 관리하고, 여기서는 형식과 대표 샘플만 정의한다. **실 고객 대화 원문/PII는 절대 이 문서나 저장소에 포함하지 않는다.**

## 1. 의도(Intent) 샘플

```json
{
  "intentName": "배송조회",
  "examples": [
    "제 주문 어디까지 왔어요?",
    "배송 조회하고 싶어요",
    "택배 언제 도착하나요",
    "주문번호 12345 배송상태 알려줘"
  ]
}
```

## 8. 챗봇 운영관리(No.1~4) 시드 데이터 — `apps/api/prisma/seed.ts`

> `docs/requirements/chatbot-operations.md` D-5(빈 상태 검증용 로그 0건 챗봇 포함) 권고를 반영해 **3트랙**으로 구성한다. 그룹/챗봇은 name·slug 기준 upsert(재실행해도 중복 생성되지 않음), 대화로그는 매 실행마다 재생성된다(`pnpm --filter @chat-bot/api prisma:seed`).

| 트랙 | 챗봇 | slug | 상태 | 소속 그룹 | 대화로그 | 검증 대상 |
|---|---|---|---|---|---|---|
| A | 샘플 고객지원 챗봇 | `sample-support-bot` | `ACTIVE` | 고객지원 그룹 | 100건(응답 90 / 미응답 10, sessionId 40종, "배송 조회" 12건·"환불 절차" 7건·공백정규화 1건·빈 문자열 1건 포함) | AC-2-1~2-4(응답률/미응답률/인기질문 정규화), D-1(A안, sessionId 기반 visitCount) |
| B | 빈 대시보드 챗봇 | `empty-dashboard-bot` | `DRAFT` | 고객지원 그룹 | 0건 | AC-2-5/AC-2-6(빈 상태), AC-4-10(DRAFT 임베드 주의문구) |
| C | 레거시 보관 챗봇 | `archived-legacy-bot` | `ARCHIVED` | 보관 그룹 | 20건(30일 이전, 응답률 75%, sessionId 일부 null) | AC-1-11(영구삭제 409), AC-1-12(편집 409), AC-2-10(보관본 대시보드 조회) |

추가로 "테스트 그룹"(챗봇 0개 유지)을 별도로 시드해 EX-1-4(빈 그룹 삭제 정상), AC-1-5(잔여 챗봇 그룹 삭제 거부)와 구분되는 "그룹 자체는 항상 삭제 가능한 빈 상태"를 상시 제공한다.

### 8.1 apps/web 컴포넌트/통합 테스트 픽스처

자동화된 컴포넌트 시험(`apps/web/src/**/*.spec.tsx`)은 위 시드를 그대로 DB에서 읽지 않고 `apps/web/src/test/fixtures.ts`의 순수 함수 픽스처(`makeGroup`/`makeChatbot`/`makeChatbotListItem`/`makeDashboardSummary`/`makeEmptyDashboardSummary`)를 사용한다. 수치는 위 표(트랙 A/B)와 정렬해 두었다 — 예: `makeDashboardSummary()`는 트랙 A의 "배송 조회 12건/환불 절차 7건" 상위질문을, `makeEmptyDashboardSummary()`는 트랙 B(로그 0건)를 그대로 재현한다. 시드 수치를 변경하면 이 픽스처도 함께 갱신해야 한다.

### 8.2 API 통합 테스트 데이터

`apps/api/src/integration/chatbot-operations.integration.spec.ts`는 seed에 의존하지 않고 매 케이스마다 임시 SQLite DB(`prisma db push`)에 그룹/챗봇을 직접 생성한다(`createGroup`/`createChatbot` 헬퍼). `ConversationLog`가 필요한 케이스(AC-1-11, AC-2-10)는 `PrismaService`를 통해 직접 1건 삽입한다. slug는 매번 `Date.now()` + 랜덤 접미사로 유일성을 보장한다.

## 9. 대화 설계(No.5~9) 시험 데이터

### 9.1 `apps/api/prisma/seed.ts`(NFR-M5) — 알려진 공백

`sample-support-bot`에 의도 5건(예문 포함, "빈예문의도" 1건은 EX-D-5용 예문 0개)/키워드 3건/동음이의어 1건("배")/컨텍스트 1건("커피주문")/노드 4건(START·NORMAL 2·FALLBACK)/FAQ 4종(카테고리별 1건 이상)이 있다. **단, 동음이의어 의미(`meanings[].intentId`)와 컨텍스트 슬롯(`slots[].keywordId`)이 실제 의도/키워드를 참조하는 조합은 시드에 없다** — frontend-implementer가 H2 수정 후 자체 보고한 미검증 지점과 동일 공백이다. 수동 확인이나 seed 확장이 필요하면 이 절을 갱신할 것.

### 9.2 API 통합 테스트(H2 검증) — 인라인 fixture로 공백 재현

위 공백은 seed를 건드리지 않고 `apps/api/src/integration/dialogue-design.integration.spec.ts`가 매 케이스마다 직접 만드는 조합으로 재현했다:

- `EX-R-2 / H2`: 의도를 생성 → `intentId`를 연결한 동음이의어(의미 2개, 그중 하나가 그 의도를 참조) 생성 → 의도 삭제 시도 → `409` 메시지에 "동음이의어" 포함 확인.
- `EX-R-3 / H2`: 키워드를 생성 → `type=KEYWORD` 슬롯(`keywordId`가 그 키워드를 참조)을 가진 컨텍스트 생성 → 키워드 삭제 시도 → `409` 메시지에 "컨텍스트" 포함 확인.

`apps/web/src/pages/dialogue/IntentsKeywordsPage.spec.tsx`는 서버 메시지를 그대로 `ApiError` mock으로 주입해 `resolveBlockedRefKind` 매핑과 배너 렌더링·링크 이동까지 프런트 측에서 재검증한다(`DeleteBlockedBanner.spec.tsx`는 순수 컴포넌트 단위로 3가지 kind를 전수 검증).

### 9.3 `packages/dialogue-engine` 성능 시험 규모(M4)

`resolver.performance.spec.ts`는 ADR-0008/FR-E-10이 명시한 설계 규모를 그대로 합성 생성한다 — 의도 1,000건×예문 20건(합 20,000예문), 키워드 50건, 노드 500건(전 의도 구간에 고르게 분산 참조 + FALLBACK 1건), FAQ 2,000건. 노드 매칭 히트/FAQ 매칭 히트/완전 폴백 3가지 경로를 섞은 100회 호출의 P95를 측정한다(2026-09-20 측정치: 인덱스 재사용 시 P95 수 ms대, 200ms 기준 대비 여유 큼).

### 9.4 `apps/web` 대화설계 화면 컴포넌트 시험 픽스처

의도/키워드/노드 목록 아이템은 각 스펙 파일 내부에 `IntentListItem`/`KeywordListItem`/`DialogNodeListItem` 최소 픽스처를 인라인으로 정의한다(`chatbot-operations` 그룹의 `test/fixtures.ts` 패턴과 달리 대화설계 쪽 리소스는 스펙별로 필요한 필드 조합이 크게 달라 공용 팩토리보다 지역 정의가 더 읽기 쉽다고 판단). 공용으로 재사용하는 것은 `makeChatbot`(`test/fixtures.ts`)뿐이다.

## 10. 품질/채널(No.10~11) 시험 데이터

### 10.1 `apps/api/prisma/seed.ts` 수정 — 컨텍스트 슬롯명 정규식 위반 결함 수정

`sample-support-bot`의 `커피주문` 컨텍스트 슬롯명이 한글("메뉴"/"사이즈"/"수량")로 되어 있어 `ContextSlotSchema.name`
정규식(`^[A-Za-z0-9_]{1,50}$`)을 위반하는 결함을 이번 품질/채널 시험 중 발견했다(대화설계 No.5~9 그룹 seed의 기존
결함, 이번 그룹의 결함은 아님). **seed를 직접 수정**했다 — `slots[].name`을 `menu`/`size`/`quantity`(영문)로 바꾸고
`label`(화면 표시용, "메뉴"/"사이즈"/"수량")은 그대로 유지, `completionMessage`의 치환자도 `{menu} {size} {quantity}`로
함께 수정했다. 다른 seed 데이터는 변경하지 않았다. 상세 근거는 `자동시험_전략.md` §3.5.5 참고.

### 10.2 `apps/api` 통합 테스트 — 오버레이/공개 API 픽스처

`apps/api/src/integration/quality-channel.integration.spec.ts`는 seed에 의존하지 않고(§8.2/§9.2와 동일 원칙) 매
케이스마다 `createChatbot()`으로 챗봇을 직접 생성한다. 이번에 추가한 오버레이 크기 경계값 테스트는 슬롯/의도 데이터가
아니라 **의도 예문 배열**(항목당 최대 200자, 의도당 최대 500개)을 ASCII 문자로 채워 정밀하게 크기를 제어한다 —
한글을 섞으면 문자 수(zod 검증 기준)와 UTF-8 바이트 수(실제 HTTP 페이로드 기준)가 벌어져 목표 크기를 벗어나기 쉽다.

| 목표 구간 | 구성 | 실측 크기 |
|---|---|---|
| 100KB 초과 ~ 1MB 미만 | 의도 2건 × 예문 500개 × (필러 185자 + 접두 13자) | 약 200KB |
| 1MB 초과 ~ 2MB 미만 | 의도 11건 × 예문 500개 × 동일 필러 | 약 1.08MB |

### 10.3 `apps/web` 컴포넌트 테스트 픽스처

`SimulatorPanel.spec.tsx`/`CompareView.spec.tsx`는 `packages/shared-types`의 `SimulateResponse`/`CompareResponse`
타입에 맞춘 인라인 팩토리(`makeState`/`makeResponse`/`makeCompareResponse`)를 스펙 파일 내부에 정의한다(대화설계
그룹의 "리소스별 조합이 크게 달라 공용 팩토리보다 지역 정의가 낫다"는 §9.4 판단을 그대로 따른다). 동음이의어 되묻기
시나리오는 `state.pendingClarify`(`homonymId`/`word`/`askedAt`)를 직접 구성해 실제 seed의 "배"(과일/선박) 사전과
동일한 형태를 재현한다.

`ChannelCard.spec.tsx`의 `makeWebItem`/`makeKakaoItem`은 `ChannelListItemSchema`(`packages/shared-types/src/channel.ts`)
구조를 그대로 따르며, `WEB`(`IMPLEMENTED`)과 `KAKAOTALK`(`CONFIG_ONLY`) 두 구현등급을 대표값으로 삼는다.

### 10.4 `apps/widget` DOM 테스트 픽스처

`ui/app.spec.ts`는 `PublicChatbotConfig`/`PublicMessageResponse` 스키마에 맞춘 `makeConfig()` 팩토리와 URL 패턴
기반 `fetch` 목(mock)을 사용한다(`/config`·`/messages` 요청을 각각 가로채 실제 백엔드 계약과 동일한 형태의 응답을
반환). `sessionId`/`state`는 `apps/widget/src/core/session.ts`가 `crypto.randomUUID()`(jsdom·Node 전역 Web Crypto)로
자체 발급하므로 별도 픽스처가 필요 없다.

## 11. 보안/이력(No.12~13) 시험 데이터

### 11.1 `apps/api` 통합 테스트 — 역할별 테스트 계정 헬퍼

`apps/api/src/integration/helpers/auth.helper.ts`(선행 세션에서 구축)는 `seedTestUsers()`로 ADMIN/EDITOR/VIEWER 3계정(`integration-test-{role}@chat-bot.local`, 공통 비밀번호 `Test-Password#1`)을 생성하고, `loginAs()`가 실제 `POST /auth/login`을 호출해 `cb_session` 쿠키 문자열을 반환한다. **세션을 DB에 직접 INSERT하는 우회는 쓰지 않는다** — 인증 경로 자체의 회귀도 함께 검증하기 위함이다. 이번 시험(AC-12D-5, 전수 스캔 보강)은 이 헬퍼를 그대로 재사용했다.

### 11.2 `apps/api` 통합 테스트 — AC-12D-5(시뮬레이션 금지어 미적용) 픽스처

`security-audit.integration.spec.ts`에 추가한 케이스는 전용 금지어(`시뮬금지어검증용`, BLOCK)를 등록한 뒤 신규 그룹/챗봇을 생성하고, `POST /chatbots/:id/simulate`로 그 단어가 포함된 문장을 보낸다. 공개 대화(`/public/chatbots/:slug/messages`)였다면 반환되었을 고정 안내문("바람직하지 않은 표현이 포함되어 있습니다...")과 **다른** 응답(엔진의 원본 미매칭 폴백)이 나오는지로 "필터가 아예 적용되지 않았다"를 검증한다. 채널 활성화 등 시뮬레이션에 불필요한 사전 조건(FR-10-2, `assertReadable`만 요구)은 생략했다.

### 11.3 `apps/api` — `@Public()` 전수 스캔 컨트롤러 목록

`apps/api/src/common/auth/public-decorator-count.spec.ts`의 전수 스캔 테스트는 `find apps/api/src -iname "*.controller.ts"`로 확인한 **17개 컨트롤러 전부**(`AuditLogsController`/`AuthController`/`BannedWordsController`/`ChannelsController`/`ChatbotGroupsController`/`ChatbotsController`/`ContextsController`/`DialogNodesController`/`FaqsController`/`HealthController`/`HomonymsController`/`IntentsController`/`KeywordsController`/`PublicConversationController`/`RolesController`/`SimulationController`/`StatsController`/`UsersController`)를 직접 import해 등록한다. 라우트 핸들러 판별은 `@nestjs/common/constants`의 `PATH_METADATA`(`'path'`)로 "실제 HTTP 메서드 데코레이터가 붙은 메서드"만 골라내고, 그중 `IS_PUBLIC_KEY` 메타데이터가 `true`인 것만 센다. **새 컨트롤러 파일이 추가되면 이 목록에도 import를 함께 추가해야** 전수 스캔이 유지된다(가드 역할을 하는 목록이므로 `docs/04-test/자동시험_전략.md` §4.5에 유지보수 규칙으로 명시).

### 11.4 `apps/web` 공용 테스트 픽스처(`test/fixtures.ts`) — 보안/이력 도메인 추가분

기존 챗봇/대시보드 픽스처에 이어 다음을 추가했다(챗봇 운영관리 그룹의 "공용 팩토리" 패턴을 그대로 재사용 — 대화설계/품질채널 그룹이 "리소스별 조합이 달라 지역 정의가 낫다"고 판단한 것과 달리, 사용자/금지어/이력은 스펙 간 형태가 안정적이라 공용 팩토리가 더 적합하다고 판단):

| 팩토리 | 용도 |
|---|---|
| `makeUser(overrides)` | `User`(EDITOR 기본값) — 회원 목록/카드 렌더링 |
| `makeCurrentUser`/`makeAdminUser`/`makeViewerUser(overrides)` | `CurrentUser`(권한 배열 포함) — `AuthContext`/`RequirePermission`/각 페이지의 `useAuth()` mock에 사용. 역할별 `permissions[]`는 `packages/shared-types`의 `ROLE_PERMISSIONS` 값을 그대로 반영 |
| `makeBannedWord(overrides)` | `BannedWord`(CONTAINS/BLOCK 기본값) |
| `makeAuditLogListItem`/`makeAuditLogDetail(overrides)` | `AuditLogListItem`/`AuditLogDetail` — 요구사항 S-13 예시("2026-09-19 14:22 / 김편집(EDITOR) / 삭제 / 의도 '주문_배송조회'")를 기본값으로 사용해 시험데이터-요구사항 문서 간 대조가 쉽도록 함 |

### 11.5 `apps/web` — 401 세션만료 통합 시험(AC-U-4) 픽스처

`AuthContext.session-expiry.spec.tsx`는 실제 `AuthProvider` + `apiClient`를 함께 동작시키고(내부 모듈만 mock, `useAuth` 자체는 mock하지 않음), 편집 폼을 흉내 낸 최소 컴포넌트(`DirtyNodeForm` — 텍스트 입력 1개 + 저장 버튼)를 인라인으로 정의한다. `global.fetch`를 `vi.stubGlobal`로 목해 1차 호출은 401(SESSION_EXPIRED), 재인증 후 재시도는 200을 반환하도록 구성했다 — `authApi.me`/`authApi.login`은 별도 모듈 mock이라 이 `fetch` 카운트에 잡히지 않는다(1차 저장 401 + 재시도 200 = 2회).
