# 시험데이터 (샘플)

> 실제 대량 시험데이터는 `seed/`(Auto QA 컨벤션 참고)에 별도 관리하고, 여기서는 형식과 대표 샘플만 정의한다. **실 고객 대화 원문/PII는 절대 이 문서나 저장소에 포함하지 않는다.**

## 1. 의도(Intent) 샘플

```json
{
  "intentName": "배송조회",
  "examples": [
    "제 주문 어디까지 왔어요?",
    "배송 조회하고 싶어요",
    "택배 언제 도착하나요",
    "주문번호 12345 배송상태 알려줘"
  ]
}
```

## 6. 미응답 질문(학습현황) 샘플

> ⚠ 2026-09-22 갱신(`docs/requirements/stats-learning.md` §10 정정 제안 반영) — `UnansweredQuestion` 스키마가 DD-49로 전면 보강되면서 `suggestedIntent`(저장 컬럼)는 **제거**되고 조회 시점 계산으로 바뀌었다(J-5). 아래는 DD-49 확장 필드(변형 3종·상태 3종·재발생)를 반영한 최신 샘플이다.

```json
{
  "questionText": "해외배송도 되나요?",
  "questionNormalized": "해외배송도되나요",
  "variants": ["해외배송 되나요", "해외배송도 되나요?", "해외 배송 가능한가요"],
  "occurredCount": 12,
  "status": "PENDING",
  "lastOccurredAt": "2026-09-22T06:00:00.000Z",
  "recurredCount": 0,
  "source": "UNANSWERED",
  "channelType": "WEB"
}
```

**상태 3종 + 재발생 케이스 샘플**(FR-15-5, S-9 — 목록 화면의 "반영 후 재발생 N회" 배지 검증용):

```json
[
  { "questionText": "포장 선물 되나요?", "status": "RESOLVED", "resolvedIntentId": "<선물포장문의 intentId>", "recurredCount": 0 },
  { "questionText": "ㅋㅋㅋ", "status": "IGNORED", "recurredCount": 0 },
  { "questionText": "환불 얼마나 걸리나요", "status": "RESOLVED", "resolvedIntentId": "<환불문의 intentId>", "recurredCount": 4, "recurredAfterAt": "2026-09-15T00:00:00.000Z" }
]
```

추천 의도 후보 형식(J-5, 조회 시점 계산 — 저장하지 않음):

```json
{ "intentId": "...", "intentName": "배송문의", "score": 0.62, "matchedExample": "배송 얼마나 걸리나요" }
```

## 8. 챗봇 운영관리(No.1~4) 시드 데이터 — `apps/api/prisma/seed.ts`

> `docs/requirements/chatbot-operations.md` D-5(빈 상태 검증용 로그 0건 챗봇 포함) 권고를 반영해 **3트랙**으로 구성한다. 그룹/챗봇은 name·slug 기준 upsert(재실행해도 중복 생성되지 않음), 대화로그는 매 실행마다 재생성된다(`pnpm --filter @chat-bot/api prisma:seed`).

| 트랙 | 챗봇 | slug | 상태 | 소속 그룹 | 대화로그 | 검증 대상 |
|---|---|---|---|---|---|---|
| A | 샘플 고객지원 챗봇 | `sample-support-bot` | `ACTIVE` | 고객지원 그룹 | 100건(응답 90 / 미응답 10, sessionId 40종, "배송 조회" 12건·"환불 절차" 7건·공백정규화 1건·빈 문자열 1건 포함) | AC-2-1~2-4(응답률/미응답률/인기질문 정규화), D-1(A안, sessionId 기반 visitCount) |
| B | 빈 대시보드 챗봇 | `empty-dashboard-bot` | `DRAFT` | 고객지원 그룹 | 0건 | AC-2-5/AC-2-6(빈 상태), AC-4-10(DRAFT 임베드 주의문구) |
| C | 레거시 보관 챗봇 | `archived-legacy-bot` | `ARCHIVED` | 보관 그룹 | 20건(30일 이전, 응답률 75%, sessionId 일부 null) | AC-1-11(영구삭제 409), AC-1-12(편집 409), AC-2-10(보관본 대시보드 조회) |

추가로 "테스트 그룹"(챗봇 0개 유지)을 별도로 시드해 EX-1-4(빈 그룹 삭제 정상), AC-1-5(잔여 챗봇 그룹 삭제 거부)와 구분되는 "그룹 자체는 항상 삭제 가능한 빈 상태"를 상시 제공한다.

### 8.1 apps/web 컴포넌트/통합 테스트 픽스처

자동화된 컴포넌트 시험(`apps/web/src/**/*.spec.tsx`)은 위 시드를 그대로 DB에서 읽지 않고 `apps/web/src/test/fixtures.ts`의 순수 함수 픽스처(`makeGroup`/`makeChatbot`/`makeChatbotListItem`/`makeDashboardSummary`/`makeEmptyDashboardSummary`)를 사용한다. 수치는 위 표(트랙 A/B)와 정렬해 두었다 — 예: `makeDashboardSummary()`는 트랙 A의 "배송 조회 12건/환불 절차 7건" 상위질문을, `makeEmptyDashboardSummary()`는 트랙 B(로그 0건)를 그대로 재현한다. 시드 수치를 변경하면 이 픽스처도 함께 갱신해야 한다.

### 8.2 API 통합 테스트 데이터

`apps/api/src/integration/chatbot-operations.integration.spec.ts`는 seed에 의존하지 않고 매 케이스마다 임시 SQLite DB(`prisma db push`)에 그룹/챗봇을 직접 생성한다(`createGroup`/`createChatbot` 헬퍼). `ConversationLog`가 필요한 케이스(AC-1-11, AC-2-10)는 `PrismaService`를 통해 직접 1건 삽입한다. slug는 매번 `Date.now()` + 랜덤 접미사로 유일성을 보장한다.

## 9. 대화 설계(No.5~9) 시험 데이터

### 9.1 `apps/api/prisma/seed.ts`(NFR-M5) — 알려진 공백

`sample-support-bot`에 의도 5건(예문 포함, "빈예문의도" 1건은 EX-D-5용 예문 0개)/키워드 3건/동음이의어 1건("배")/컨텍스트 1건("커피주문")/노드 4건(START·NORMAL 2·FALLBACK)/FAQ 4종(카테고리별 1건 이상)이 있다. **단, 동음이의어 의미(`meanings[].intentId`)와 컨텍스트 슬롯(`slots[].keywordId`)이 실제 의도/키워드를 참조하는 조합은 시드에 없다** — frontend-implementer가 H2 수정 후 자체 보고한 미검증 지점과 동일 공백이다. 수동 확인이나 seed 확장이 필요하면 이 절을 갱신할 것.

### 9.2 API 통합 테스트(H2 검증) — 인라인 fixture로 공백 재현

위 공백은 seed를 건드리지 않고 `apps/api/src/integration/dialogue-design.integration.spec.ts`가 매 케이스마다 직접 만드는 조합으로 재현했다:

- `EX-R-2 / H2`: 의도를 생성 → `intentId`를 연결한 동음이의어(의미 2개, 그중 하나가 그 의도를 참조) 생성 → 의도 삭제 시도 → `409` 메시지에 "동음이의어" 포함 확인.
- `EX-R-3 / H2`: 키워드를 생성 → `type=KEYWORD` 슬롯(`keywordId`가 그 키워드를 참조)을 가진 컨텍스트 생성 → 키워드 삭제 시도 → `409` 메시지에 "컨텍스트" 포함 확인.

`apps/web/src/pages/dialogue/IntentsKeywordsPage.spec.tsx`는 서버 메시지를 그대로 `ApiError` mock으로 주입해 `resolveBlockedRefKind` 매핑과 배너 렌더링·링크 이동까지 프런트 측에서 재검증한다(`DeleteBlockedBanner.spec.tsx`는 순수 컴포넌트 단위로 3가지 kind를 전수 검증).

### 9.3 `packages/dialogue-engine` 성능 시험 규모(M4)

`resolver.performance.spec.ts`는 ADR-0008/FR-E-10이 명시한 설계 규모를 그대로 합성 생성한다 — 의도 1,000건×예문 20건(합 20,000예문), 키워드 50건, 노드 500건(전 의도 구간에 고르게 분산 참조 + FALLBACK 1건), FAQ 2,000건. 노드 매칭 히트/FAQ 매칭 히트/완전 폴백 3가지 경로를 섞은 100회 호출의 P95를 측정한다(2026-09-20 측정치: 인덱스 재사용 시 P95 수 ms대, 200ms 기준 대비 여유 큼).

### 9.4 `apps/web` 대화설계 화면 컴포넌트 시험 픽스처

의도/키워드/노드 목록 아이템은 각 스펙 파일 내부에 `IntentListItem`/`KeywordListItem`/`DialogNodeListItem` 최소 픽스처를 인라인으로 정의한다(`chatbot-operations` 그룹의 `test/fixtures.ts` 패턴과 달리 대화설계 쪽 리소스는 스펙별로 필요한 필드 조합이 크게 달라 공용 팩토리보다 지역 정의가 더 읽기 쉽다고 판단). 공용으로 재사용하는 것은 `makeChatbot`(`test/fixtures.ts`)뿐이다.

## 10. 품질/채널(No.10~11) 시험 데이터

### 10.1 `apps/api/prisma/seed.ts` 수정 — 컨텍스트 슬롯명 정규식 위반 결함 수정

`sample-support-bot`의 `커피주문` 컨텍스트 슬롯명이 한글("메뉴"/"사이즈"/"수량")로 되어 있어 `ContextSlotSchema.name`
정규식(`^[A-Za-z0-9_]{1,50}$`)을 위반하는 결함을 이번 품질/채널 시험 중 발견했다(대화설계 No.5~9 그룹 seed의 기존
결함, 이번 그룹의 결함은 아님). **seed를 직접 수정**했다 — `slots[].name`을 `menu`/`size`/`quantity`(영문)로 바꾸고
`label`(화면 표시용, "메뉴"/"사이즈"/"수량")은 그대로 유지, `completionMessage`의 치환자도 `{menu} {size} {quantity}`로
함께 수정했다. 다른 seed 데이터는 변경하지 않았다. 상세 근거는 `자동시험_전략.md` §3.5.5 참고.

### 10.2 `apps/api` 통합 테스트 — 오버레이/공개 API 픽스처

`apps/api/src/integration/quality-channel.integration.spec.ts`는 seed에 의존하지 않고(§8.2/§9.2와 동일 원칙) 매
케이스마다 `createChatbot()`으로 챗봇을 직접 생성한다. 이번에 추가한 오버레이 크기 경계값 테스트는 슬롯/의도 데이터가
아니라 **의도 예문 배열**(항목당 최대 200자, 의도당 최대 500개)을 ASCII 문자로 채워 정밀하게 크기를 제어한다 —
한글을 섞으면 문자 수(zod 검증 기준)와 UTF-8 바이트 수(실제 HTTP 페이로드 기준)가 벌어져 목표 크기를 벗어나기 쉽다.

| 목표 구간 | 구성 | 실측 크기 |
|---|---|---|
| 100KB 초과 ~ 1MB 미만 | 의도 2건 × 예문 500개 × (필러 185자 + 접두 13자) | 약 200KB |
| 1MB 초과 ~ 2MB 미만 | 의도 11건 × 예문 500개 × 동일 필러 | 약 1.08MB |

### 10.3 `apps/web` 컴포넌트 테스트 픽스처

`SimulatorPanel.spec.tsx`/`CompareView.spec.tsx`는 `packages/shared-types`의 `SimulateResponse`/`CompareResponse`
타입에 맞춘 인라인 팩토리(`makeState`/`makeResponse`/`makeCompareResponse`)를 스펙 파일 내부에 정의한다(대화설계
그룹의 "리소스별 조합이 크게 달라 공용 팩토리보다 지역 정의가 낫다"는 §9.4 판단을 그대로 따른다). 동음이의어 되묻기
시나리오는 `state.pendingClarify`(`homonymId`/`word`/`askedAt`)를 직접 구성해 실제 seed의 "배"(과일/선박) 사전과
동일한 형태를 재현한다.

`ChannelCard.spec.tsx`의 `makeWebItem`/`makeKakaoItem`은 `ChannelListItemSchema`(`packages/shared-types/src/channel.ts`)
구조를 그대로 따르며, `WEB`(`IMPLEMENTED`)과 `KAKAOTALK`(`CONFIG_ONLY`) 두 구현등급을 대표값으로 삼는다.

### 10.4 `apps/widget` DOM 테스트 픽스처

`ui/app.spec.ts`는 `PublicChatbotConfig`/`PublicMessageResponse` 스키마에 맞춘 `makeConfig()` 팩토리와 URL 패턴
기반 `fetch` 목(mock)을 사용한다(`/config`·`/messages` 요청을 각각 가로채 실제 백엔드 계약과 동일한 형태의 응답을
반환). `sessionId`/`state`는 `apps/widget/src/core/session.ts`가 `crypto.randomUUID()`(jsdom·Node 전역 Web Crypto)로
자체 발급하므로 별도 픽스처가 필요 없다.

## 11. 보안/이력(No.12~13) 시험 데이터

### 11.1 `apps/api` 통합 테스트 — 역할별 테스트 계정 헬퍼

`apps/api/src/integration/helpers/auth.helper.ts`(선행 세션에서 구축)는 `seedTestUsers()`로 ADMIN/EDITOR/VIEWER 3계정(`integration-test-{role}@chat-bot.local`, 공통 비밀번호 `Test-Password#1`)을 생성하고, `loginAs()`가 실제 `POST /auth/login`을 호출해 `cb_session` 쿠키 문자열을 반환한다. **세션을 DB에 직접 INSERT하는 우회는 쓰지 않는다** — 인증 경로 자체의 회귀도 함께 검증하기 위함이다. 이번 시험(AC-12D-5, 전수 스캔 보강)은 이 헬퍼를 그대로 재사용했다.

### 11.2 `apps/api` 통합 테스트 — AC-12D-5(시뮬레이션 금지어 미적용) 픽스처

`security-audit.integration.spec.ts`에 추가한 케이스는 전용 금지어(`시뮬금지어검증용`, BLOCK)를 등록한 뒤 신규 그룹/챗봇을 생성하고, `POST /chatbots/:id/simulate`로 그 단어가 포함된 문장을 보낸다. 공개 대화(`/public/chatbots/:slug/messages`)였다면 반환되었을 고정 안내문("바람직하지 않은 표현이 포함되어 있습니다...")과 **다른** 응답(엔진의 원본 미매칭 폴백)이 나오는지로 "필터가 아예 적용되지 않았다"를 검증한다. 채널 활성화 등 시뮬레이션에 불필요한 사전 조건(FR-10-2, `assertReadable`만 요구)은 생략했다.

### 11.3 `apps/api` — `@Public()` 전수 스캔 컨트롤러 목록

### 14.1 `apps/api` 단위 테스트 — 증강 검증(`validateCandidates`) 경계값 픽스처

`apps/api/src/augmentation/lib/validate-candidates.boundary.spec.ts`(신규)는 5종 검증(의미보존/신규성/타의도충돌/금지어/형식) 각각의 임계값 안팎을 다룬다. `cosineSimilarity`(`../../embedding/lib/cosine.ts`)가 사전 정규화를 전제한 단순 내적이라는 점을 이용해, ①②③(코사인 기반) 검사는 `jest.mock`(`jest.requireActual` 폴백 포함)으로 `cosineSimilarity`의 반환값을 직접 주입한다 — 0.97·0.95·0.8은 2진 부동소수점으로 정확히 표현되지 않아 실제 벡터로 "정확히 그 값"을 재현하면 `Float32Array` 저장 시 반올림 오차가 threshold 판정에 섞이기 때문이다(§14.1.1 참고). ④⑤(문자열 기반) 검사는 실제 `cosineSimilarity`를 그대로 쓴다.

| 검사 | 경계 | 픽스처 | 기대 |
|---|---|---|---|
| ① 의미 보존 | `keepMin=0.75`(하한 포함) | `similarityToSeed=0.75` / `0.749999` | accepted / `SEMANTIC_DRIFT` |
| ① 의미 보존 | `keepMax=0.97`(상한 포함) | `similarityToSeed=0.97` / `0.970001` | accepted / `NEAR_DUPLICATE` |
| ② 신규성 | `noveltyMax=0.95`(하한 **포함** — `>=`) | `novelty=0.95` / `0.949999` | `DUPLICATE_OF_EXISTING` / accepted |
| ③ 타 의도 충돌 | `acceptThreshold=0.8`(하한 포함, 차단 아님) | `conflict=0.8` / `0.799999` | 배지 표시 / 배지 없음 |
| ④ 금지어 | falsy 가드 | `bannedWords: ['', '실제금지어']` vs `['   ']`(공백만) | 전자는 무시, 후자는 **결함**(아래 §14.1.1) |
| ⑤ 형식 | 길이 `[1,200]`(기본) 양끝 포함 + 커스텀 `[5,5]` | 정확히 200자/1자/커스텀 5자 | 통과, 201자/0자/4·6자는 `INVALID_FORMAT` |

#### 14.1.1 발견된 결함 — 공백 전용 금지어 항목의 전수 오탐

`containsBannedWord()`가 `bannedWords.some((w) => w && normalized.includes(normalizeText(w)))`로 구현되어 있어, 금지어 목록에 공백만 있는 항목(`"   "`)이 있으면 `normalizeText()`가 이를 빈 문자열로 정규화하고 `"".includes()`가 항상 `true`가 되어 **모든 증강 후보가 오탐 차단**된다. `validate-candidates.boundary.spec.ts`가 이 현재(결함) 동작을 회귀 센서로 고정해 두었다(수정 시 기댓값 반전 필요). 등급·라우팅은 `docs/04-test/시험항목.md`의 "학습 고도화(No.16/23)" 절 하단 기록 참고(Medium, `backend-implementer` 인계, 코드 미수정).

### 15.2 `apps/api` 통합 테스트 — `version-history-reindex.integration.spec.ts` mock 임베딩 서버(★신규)

AC-H3-7(증분 재색인) 전용으로 `learning-augmentation.integration.spec.ts`의 mock 임베딩 서버 패턴을 재사용하되, **요청받은 텍스트 수를 누적 계측하는 레코더**(`totalTextsSinceReset()`/`reset()`)를 추가로 둔다 — `EmbeddingProviderFactory`가 실제로 호출하는 `POST /embed`의 `texts[]` 길이를 합산해, "재색인이 몇 문장을 임베딩했는가"를 직접 계측한다.

- **규모**: 예문 30건(의도 1개) 기준으로 시작해 5건만 텍스트를 바꾼다 — 설계서 §17이 예시로 든 "1,000건 중 20건"과 같은 비율 관계(바뀐 비율 ≪ 전체)를 유지하면서 시험 시간을 단축했다. 결론("전체가 아니라 바뀐 문장 수만큼만 재임베딩된다")은 규모에 무관하게 동일하다.
- **측정 절차**: ① 의도 생성(예문 30건) → 초기 재색인(이름 1 + 예문 30 = 31건) 완료까지 `ReindexQueueService.isRunning()`을 폴링 대기 → 레코더 리셋 ② 예문 5건 텍스트 변경(PATCH) → 재색인 완료 대기 → 레코더가 정확히 5건임을 사전 확인(재색인 자체의 증분 규칙 검증) ③ 별도 의도(intentId2)로 "원본 버전 저장 → 편집 → 복원" 흐름을 구성해, 복원 직후의 재색인 호출만 측정 구간으로 분리 ④ 복원 완료 대기 후 레코더가 정확히 5건(`CHANGED_COUNT`)임을 `toBe()`로 단언.
- **왜 별도 앱 인스턴스인가**: `version-history.integration.spec.ts`(공유 앱)는 `EMBEDDING_BASE_URL`을 의도적으로 비워 둔다("이 그룹은 임베딩을 쓰지 않는다"는 전제를 공유 스위트 전체에 강제하기 위해). AC-H3-7만 실제 임베딩 호출 계측이 필요하므로 전용 NestJS 앱을 새로 띄운다(`learning-augmentation.integration.spec.ts`와 동일한 패턴).

### 15.3 `apps/api` 단위 테스트 — `ReindexQueueService` 재실행 예약 플래그 픽스처(★신규)

### 16.1 `apps/api` 통합 테스트 — FakeClock + 단일 앱 하네스(기존, 재확인)

### 16.2 `apps/api` 통합 테스트 — 트랜잭션 중간 실패 주입(원자성, AC-D2-4)

`channels/lib/channel-enable-rule.ts`의 `assertChannelEnableAllowed`를 모듈 네임스페이스째 import(`import * as channelEnableRule from '../channels/lib/channel-enable-rule'`)해 `jest.spyOn(channelEnableRule, 'assertChannelEnableAllowed').mockImplementationOnce(...)`으로 1회성 예외를 주입한다. `ChatbotPublicationService.publish()`가 상태 갱신 → 채널 활성화 순으로 같은 `$transaction` 콜백 안에서 실행되므로, 채널 단계에서 던진 예외가 상태 갱신까지 롤백시키는지(원자성)를 실제 SQLite로 검증한다(No.25 AC-H3-8 "apply() 완료 직후 예외 주입" 기법과 같은 원리 — 실제 쓰기를 전부 수행한 뒤 실패를 주입하는 편이 블랙박스 통합 시험에서 재현 가능한 가장 충실한 "중간 실패" 시뮬레이션이다).

### 16.3 `apps/api` 통합 테스트 — 진행 중 작업(ACTIVE_JOB) 재시도 픽스처(AC-D3-5/6)

`TestCaseSet`을 실제 API(`POST /chatbots/:id/test-sets`)로 만든 뒤, `TestRun` 행은 실행 없이 `prisma.testRun.create({ data: { chatbotId, setId, status: 'RUNNING' } })`로 직접 시딩한다 — `VersionRestoreService.restore()`의 진행 중 작업 검사(`trainingJob`/`testRun` count where status IN QUEUED,RUNNING)를 실제 실행 없이 저비용으로 유발한다. 재시도 창(15분) 경계는 `clock.advance(16 * 60_000)`으로 넘긴다.

### 16.4 `apps/api` 통합 테스트 — 임대 만료 회수(RECOVERED/INTERRUPTED) 시딩(AC-D3-11/12)

"선점 후 프로세스 사망"은 실제 크래시를 일으킬 수 없으므로 `DeploySchedule` 행을 `status:'RUNNING', claimToken:'sim-token-N', claimedAt:<과거>`로 직접 갱신해 재현한다.

- **RECOVERED(커밋된 실행)**: 이 예약이 원인이라는 것을 증명하는 `ChatbotVersion(trigger:'BEFORE_RESTORE', triggerContext: JSON.stringify({ deployScheduleId }))` 행을 `claimedAt` 이후 시각으로 직접 생성한다(§7.8 "백업 존재 = 커밋 증명" 판정 근거를 그대로 이용).
- **INTERRUPTED(커밋 전 중단)**: 백업 행을 만들지 않는다 — `judgeRecovery`가 흔적 없음 + 현재 해시 ≠ 대상 해시로 판정해야 한다.
- **AC-D3-12(임대 유효)**: `clock.advance(2 * 60_000)`(임대 기본 5분 미만)로만 전진시켜 `RECOVER` 결정 자체가 나오지 않아야 함을 확인한다.

### 16.5 `apps/api` 통합 테스트 — 보존 보호(AC-D5-1) 대량 시딩

`VERSION_RETENTION_AUTO`(기본 30)는 `ConfigModule`이 앱 인스턴스화 시점에 고정해 공유 앱 안에서 동적으로 바꿀 수 없다(No.25 시험 문서에 이미 기록된 제약과 동일 — §15.6 "환경변수 고정 시점 제약"). 전용 앱을 새로 띄우는 대신, `chatbotVersion.create()`를 35회 반복 호출해 자동 한도를 실제로 초과시키고 `VersionRetentionService.pruneBestEffort(chatbotId, lastSeedId)`를 서비스 메서드로 직접 호출해 배선(활성 예약 참조 조회 → `selectVersionsToPrune`에 보호 집합 전달)을 검증한다.

### 16.6 `apps/api` 다중 인스턴스 통합 테스트 — 2앱 동시 tick 하네스(AC-D2-1, ★신규 파일)

`scheduled-deploy-multi-instance.integration.spec.ts`(신규)는 같은 `DATABASE_URL`(임시 SQLite 파일)을 보는 완전히 분리된 Nest DI 컨테이너 2개(`app1`이 HTTP로 챗봇·버전·예약을 만들고, `app2`는 포트를 열지 않고 `engine.tick()`만 호출)를 각자의 `FakeClock` 인스턴스와 함께 띄운다. 두 시계를 정확히 같은 "도래" 시각으로 맞춘 뒤 `Promise.all([engine1.tick(), engine2.tick()])`로 실제 동시성을 재현하고, `attemptCount:1`·`BEFORE_RESTORE` 백업 1건·감사 `RESTORE` 1건 세 지표를 교차 확인해 "결과가 우연히 1회로 보이는 것"이 아니라 "실제로 1회만 실행됐음"을 증명한다.

### 18.1 체인 실행 순서 픽스처 — 복원+공개 2단계 tick(AC-D2-6)

같은 챗봇에 `RESTORE_VERSION`(scheduledAt = "08:55" 대응)과 `PUBLISH`(scheduledAt = "08:55"+5분, "09:00" 대응)를 순서대로 만든 뒤, 클록을 두 예정 시각을 모두 지나치도록 한 번에 전진시켜 "서버 다운 후 기동"을 재현한다. `tick-planner.ts`가 챗봇당 1건만 결정하므로 `engine.tick()`을 **정확히 2회** 호출해야 한다 — 1차 호출 직후 복원만 SUCCEEDED이고 공개는 여전히 PENDING임을 먼저 확인(1차 증거), 다음 폴링 주기를 흉내 낸 소폭 전진(`clock.advance(30_000)`) 후 2차 호출로 공개도 SUCCEEDED가 됨을 확인한다(2차 증거). 복원 예약이 `acknowledgeActive` 없이도 성공한다는 사실 자체가 "복원이 공개보다 먼저 실행됐다"의 행위 기반 증거다(순서가 뒤집혔다면 ACTIVE 챗봇에서 STATE_CHANGED로 실패했을 것 — `restore-version.executor.ts`의 §5.3 사전 확인).

**주의(교차 시험 오염 회피)**: 이 시험은 자신이 만든 두 예약을 반드시 종결 상태(SUCCEEDED)로 남겨야 한다 — 파일 전체가 단일 공유 DB + 단조 증가 `FakeClock`을 쓰므로, PENDING 상태로 남은 예약은 이후 테스트의 `engine.tick()` 호출에 섞여 들어가 예기치 않은 부작용(§18.2)을 일으킬 수 있다(자동시험_전략 §10.3에 실제 발생 사례 기록).

### 18.2 BUSY 경합 주입 픽스처(AC-D3-7)

`jest.spyOn(prisma, '$transaction').mockImplementationOnce(() => { throw new Error('SQLITE_BUSY: database is locked'); })`로 복원 트랜잭션(`version-restore.service.ts`)의 `$transaction` 호출 1회만 실패시킨다. `isBusyError()`가 메시지 패턴(`/SQLITE_BUSY|database is locked/i`)으로 판별하므로 실제 SQLite 잠금을 재현할 필요가 없다 — 이 메시지 형태의 `Error`만 던지면 충분하다. `mockImplementationOnce`는 설치 후 **가장 먼저** 도달하는 `$transaction` 호출을 가로채므로, 같은 tick에 다른 due 행이 섞여 있으면 엉뚱한 호출을 가로챌 수 있다(§18.1 "주의" 참고 — 이번 회차에서 실제로 이 방식으로 실패를 경험했고, 원인 제거 후 정상화했다).

### 18.3 유휴 tick 격리 하네스 — 완전히 빈 전용 DB(AC-D2-9, ★신규 파일)

`scheduled-deploy-idle-tick.integration.spec.ts`(신규)는 `scheduled-deploy-multi-instance.integration.spec.ts`(AC-D2-1)와 같은 이유로 별도 파일·별도 임시 SQLite DB·별도 Nest 앱 인스턴스를 쓴다 — "예약이 전혀 없는 상태"라는 전제가 다른 테스트가 남긴 잔여 PENDING/RUNNING 행에 의해 깨지지 않게 하기 위함이다. ### 18.8 EX-I-6 — 감사 이력이 실존해도 소급 재구성하지 않음을 증명하는 픽스처

그룹A 생성 → 챗봇 생성(그룹A 소속) → `groupId:''`(백필 미완 센티넬) 로그를 `prisma.conversationLog.create()`로 직접 시딩(챗봇이 실제로 그룹A 소속이던 시점을 흉내) → `PATCH /chatbots/:id/group`으로 그룹B로 실제 이동(감사로그에 `summary:'소속 그룹 이동'` 레코드가 실제로 남는다 — 이 감사 기록이 "소급 재구성에 쓸 수 있었던 재료"다) → 백필 스크립트 실행. 백필 후 그 로그의 `groupId`가 감사 이력상 원래 그룹(A)이 아니라 **현재 그룹(B)**으로 채워짐을 확인한다 — `backfill-conversation-group.ts`가 "현재 groupId로만 채운다"는 단순 규칙(EX-I-6, FR-I2-8)이 감사 이력의 존재 여부와 무관하게 지켜짐을 행위 기반으로 증명한다. `execSync`로 스크립트를 기동하므로 `it(..., 30_000)`으로 개별 타임아웃을 명시했다(모노레포 병렬 실행 시 기본 5초를 넘길 수 있다 — AC-I3-3/AC-I3-4 선례와 동일한 이유). **배치 순서 주의**: 이 케이스도 전역 센티넬(`groupId=''`)과 백필 스크립트를 다루므로, 반드시 `AC-I3-3/AC-I3-4`(파일 맨 마지막) **이전**에 두어 잔여 센티넬 없이 스스로 정리하고 끝나야 한다(§17.6의 "맨 마지막" 격리 원칙과 대칭).

### 18.9 `apps/web` — ScheduleDeployDialog axe 스캔 픽스처(AC-D6-3)

    "retryCount": 0,
    "startedAt": "2026-09-24T10:00:00.000Z",
    "lastInteractedAt": "2026-09-24T10:00:00.000Z"
  }
}
```

정상 진행 중인 세션의 상태(`t0.body.state.surveySession`)를 그대로 얻어 필드 일부만 조작(`{ ...session, questionIndex: 99 }` 등)하는 방식으로 위변조를 재현한다 — 값을 완전히 새로 만들면 구조 자체가 스키마를 통과하지 못해 "폐기" 경로와 "무시" 경로를 구분하기 어렵다.

| 조작 필드 | 조작 값 | 기대 결과 |
|---|---|---|
| `surveyId` | 다른 챗봇의 다른 설문 id | sanitize 폐기(`UNKNOWN_SURVEY`, `stateReset:true`), 그 설문에 응답 행 0건 |
| `questionIndex` | 문항 수 이상(예: `99`) | sanitize 폐기(`SURVEY_STATE_INVALID`), 응답 행 `lastQuestionIndex` 불변 |
| `questionIndex` | 범위 안이지만 실제 진행보다 앞선 값 | 클라이언트 관점에서는 진행되는 것처럼 보여도, 쓰기 키(`chatbotId,sessionId,surveyId,startedAt`)에 해당하는 서버 행이 없으면 조용히 무시(가장 핵심적인 위변조 방어 — 노출되지 않은 `startedAt`을 지어내는 조합과 함께 시험) |
| `startedAt`/`lastInteractedAt` | `Date.now() + 10분` | sanitize 폐기(`SURVEY_SESSION_EXPIRED`, 5분 허용오차 초과) |

### 20.6 기간·상태 시험 — `OffsetDateTimeSchema` 분 단위 내림 주의

`activeFrom`/`activeTo`는 오프셋 포함 ISO 문자열을 받아 **분 단위로 내림 정규화**한다(`packages/shared-types/src/deploy-schedule.ts`의 `truncateToMinute`, 예약 배포 그룹의 `OffsetDateTimeSchema` 재사용). 초 단위로 가까운 미래(`+8초` 등)를 넣으면 "현재 분의 시작"으로 내림돼 이미 지난 시각이 될 수 있다 — 기간 관련 픽스처는 **분 단위 이상 여유**(`+1시간` 등)를 두거나, "진행 중 마감" 시나리오처럼 정밀한 타이밍이 필요하면 시각 자체를 조작하지 말고 `PATCH { status: 'CLOSED' }`(캐시 무효화까지 보장되는 실제 쓰기 경로)로 대체한다(§자동시험_전략 §12.3).

await prisma.$executeRawUnsafe(

```

(`hybrid-cs-hardening.integration.spec.ts`의 "3. 배정 경합" · `hybrid-cs-hardening-multi-instance.integration.spec.ts` 둘 다 적용한다.)

### 21.3 원문(P-9) 전수 누출 검사 — 같은 describe 안에서 전화번호를 공유하지 않는다

### 21.5 버전 캡처·복원 응답 형태 — `version.id`이지 `id`가 아니다

`POST /chatbots/:id/versions`는 판별 유니온 `{ unchanged:false, version:{...} }` / `{ unchanged:true, latestVersionId, latestVersionNo }`를 반환한다(버전 id는 `captureRes.body.version.id`). 복원(`POST .../restore`)은 `expectedCurrentHash`(64자 hex, `restore/preview` 응답의 `currentContentHash`)가 필수이고, **운영 중(ACTIVE) 챗봇은 `acknowledgeActive: true`도 함께 보내야 한다**(없으면 `400 VALIDATION_FAILED`, `details[0].field === 'acknowledgeActive'`). 스냅샷 캡처 이후 실제 콘텐츠(FAQ·노드 등) 변경이 전혀 없으면 diff가 `identical:true`(`blockers:[{code:'NO_CHANGES'}]`, `restorable:false`)라 복원 자체가 `409 RESTORE_NO_CHANGES`로 거부된다 — "상담 설정만 바꾸고 복원해서 되돌아오는지" 같은 시험은 상담 설정 변경**만으로는 diff가 생기지 않는다는 것 자체가 "상담 설정이 스냅샷 대상이 아니다"의 직접 증거이므로, 실제 복원 실행까지 보려면 FAQ 등 진짜 콘텐츠 변경을 하나 더 곁들여야 한다.

### 21.6 `/stats/questions` 응답 필드는 `topQuestions`다

`items`가 아니라 `topQuestions`/`topUnansweredQuestions`(`packages/shared-types/src/stats.ts` 182행)다. 쿼리는 `chatbotId`(uuid 필수)만 있으면 되고 `from`/`to`는 선택이다.

### 21.7 이력 요약 조회는 KST `dayBucket`을 그대로 써야 한다(§21.8과 같은 함정)

`GET .../handoffs/summary?from=&to=`는 `HandoffSession.dayBucket`(KST 날짜 문자열)로 범위를 거른다. 테스트에서 "오늘"을 `new Date().toISOString().slice(0, 10)`(UTC 기준)로 계산하면 UTC 15:00~23:59(KST 00:00~08:59)에 실행되는 CI에서 실제 `dayBucket`(이미 다음 날)과 어긋나 요약이 0건으로 나온다. 생성된 행을 `prisma.handoffSession.findUniqueOrThrow()`로 다시 읽어 그 행의 `dayBucket` 필드를 그대로 쿼리 범위로 쓴다.

§21.7과 동일한 `new Date().toISOString().slice(0, 10)` 패턴이 `survey-management.integration.spec.ts`에 9곳(338·365·545·584·622·631·1007행 등) 있다. 이번 회차 3회 반복 실행에서 실제 UTC 야간 시간대(KST 00:15경)에 2건이 결정적으로(매회 동일하게) 실패하는 것을 확인했다 — No.27 담당 범위라 여기서는 고치지 않고 `자동시험_전략.md` §No.24 "발견된 결함"에 보고만 한다.

## 22. 토픽 시스템(No.22) 시험 데이터(2026-09-25)

`topic-system.integration.spec.ts`가 매 케이스마다 임시 SQLite DB(`prisma migrate deploy`)에 그룹/챗봇/토픽을 직접 생성한다(seed 비의존). 이번 회차에서 실제로 걸려 넘어진 픽스처 함정을 기록한다(전부 시험 코드 쪽 문제였고 제품 코드 결함은 아니었다).

### 22.1 표준 토픽 3개 + 교차 참조 픽스처

topic-system-설계.md §21.1이 요구한 "토픽 3개 + 교차 참조 표준 픽스처"를 코드로 고정했다(`setupInsuranceScenario()`류 헬퍼):

- **배송**(활성) · **환불**(활성) · **보험청구**(비활성) — 각 토픽에 의도 1개 이상 + 그 의도를 조건으로 쓰는 노드 1개를 기본으로 둔다.
- FALLBACK 노드는 항상 공통(`topicId` 미지정)으로 먼저 만든다 — START/FALLBACK가 없으면 노드 저장 자체는 되지만(`NORMAL` 조건 규칙과 무관), 공개 대화 폴백 문구를 확정적으로 비교하려면 FALLBACK 노드가 필수다.

### 22.2 ★ 토픽 관리 엔드포인트는 대부분 `201`을 반환한다(`200`이 아니다)

`TopicsController`·`TopicAssignmentsController`의 `move`·`enable`·`disable`·`split/preview`·일괄 지정(`topic-assignments`) 핸들러는 `@HttpCode` 오버라이드가 없어 Nest 기본값(POST → `201 Created`)을 그대로 쓴다. "미리보기라서 200일 것"·"토글이라서 200일 것"이라는 직관과 다르다 — 실제 상태 코드는 컨트롤러 코드가 유일한 근거다(`topics.controller.ts`·`topic-assignments.controller.ts`). `split`(실행)만 `@HttpCode(HttpStatus.CREATED)`로 명시돼 있어 어차피 201이고, `PATCH`(수정)·`DELETE`(`204`)·`GET`(`200`)류만 REST 관례대로다.

### 22.3 시작·폴백 노드 트림 시험은 "빈 결과 보정"(TRIM_WOULD_EMPTY)을 피해야 한다

`system-node-trim.ts`는 트림 후 아웃풋이 0개가 되면 **자르지 않고 대신 따라간다**(§9.3, "잘라내면 출력이 없어짐" 보정). 시작 노드의 아웃풋이 "범위 밖 노드로 가는 버튼 1개"뿐이면, 그 버튼을 자르는 순간 아웃풋이 0개가 되어 `trimmedLinks`가 아니라 `followedLinks`(`reason: 'TRIM_WOULD_EMPTY'`)로 잡힌다 — 일반 TRIM 경로(`trimmedLinks.total >= 1`)를 보려면 시작 노드에 **살아남을 다른 아웃풋**(예: 고정 TEXT)을 하나 더 둬야 한다.

### 22.4 분리(split) 폐포 대상 노드는 자기 자신의 선택 토픽에 있으면 트림 대상이 아니다

"시작 노드가 분리 대상 토픽의 노드로 가는 버튼"은 **범위 안**(선택 자체)이라 트림되지 않는다. TRIM/FOLLOW 시험은 반드시 **선택하지 않은 토픽·폐포에도 들어오지 않는 별도 노드**를 목표로 삼아야 한다.

### 22.5 답변 설정 미리보기(`/answer-settings/preview`)는 번들에 후보가 0건이면 항상 `503 EMBEDDING_UNAVAILABLE`이다

`assembleSemanticInput()`은 `getCached()` 번들에 있는 의도·FAQ만 후보로 삼는다. 챗봇에 **비활성 토픽 의도 1개뿐**이면 번들의 후보가 0건이 되어 `semanticMatch.score()`가 항상 `null`을 반환하고 `EMBEDDING_UNAVAILABLE`(503)로 거부된다 — "비활성 토픽 의도가 후보에서 빠진다"(AC-TP3-2)를 보려면 **활성(또는 공통) 후보를 최소 1개** 같이 만들어야 실제로 `top3`가 채워진 응답을 받을 수 있다. 또한 배경 재색인(`ReindexQueueService`)은 토픽 활성 여부와 무관하게 `textHash` 기준으로 색인하므로(비활성 토픽 의도도 벡터 행이 생길 수 있다), "벡터 행 존재 여부"가 아니라 **매칭 시점 `top3` 결과**로 제외를 확인해야 한다(색인 단계가 아니라 후보 조립 단계에서 제외된다).

### 22.6 버전 복원 전 "참조 중인 자산" 삭제 순서

`DELETE /intents/:id`는 노드가 참조 중이면 `409 INTENT_IN_USE`로 막는다(기존 규칙 불변). K-1 회귀(§21.3)처럼 "의도를 지웠다 복원으로 되살아나는지" 보려면 **먼저 그 의도를 참조하는 노드를 지우고, 그다음 의도를 지워야** DELETE가 실제로 성공한다 — 순서를 건너뛰면 DELETE가 조용히 409로 실패해(테스트가 상태 코드를 확인하지 않으면) "현재 상태가 실은 바뀌지 않아 복원이 `RESTORE_NO_CHANGES`(409)로 거부되는" 오탐을 만든다.

### 22.7 슬러그 등 픽스처 이름에 영문 "topic"을 literal로 쓰지 않는다

"공개 응답에 topic 노출 0"(AC-TP4-4) 시험처럼 응답 본문 전체를 `toLowerCase().includes('topic')`으로 검사하는 시험이 있으면, 챗봇 slug나 다른 필드 기본값에 시험 편의상 넣은 영문 `topic-...` 접두어가 그대로 응답(`PublicChatbotConfig.slug`)에 실려 **자기 자신의 픽스처 이름 때문에 오탐**한다(1차 작성 시 실제로 재현). 이런 검사가 있는 스위트는 슬러그 접두어를 `ts-itest-`처럼 영문 "topic"을 포함하지 않는 문자열로 둔다.

### 22.8 TOCTOU(§11.2) 재현 — 실제 동시 HTTP로도 재현 가능했다

`version-restore.service.ts`의 노출 게이트는 **두 번** 계산된다: ① `preview`~`restore` 진입 전(트랜잭션 밖, `exposureForGate`) ② 트랜잭션 안에서 최신 토픽 상태로 재계산(`exposureInTx`). 두 값이 다르면 `RESTORE_PREVIEW_STALE`(409)이다. 실제 HTTP로 재현하려면: 토픽을 **활성** 상태로 둬 사전 게이트(①)를 통과시킨 뒤, `POST .../restore`와 `POST .../topics/:id/disable`을 `Promise.all`로 **동시에** 보낸다 — restore의 사전 준비 단계(버전 조회·무결성 검사·스냅샷 캡처 등 순차 DB 라운드트립 ~6회)가 disable(~2~3회)보다 길어, 같은 이벤트 루프 안에서도 disable이 먼저 끝나 트랜잭션 안 재계산에 반영될 확률이 높다. 다만 타이밍 의존이라 이 시험은 **최대 5회 재시도**하며, 재현되지 않으면 테스트를 실패시켜(조용히 통과 처리하지 않음) 원인 가설과 함께 보고하도록 만들었다(3회 반복 실행 결과는 자동시험_전략.md §14 참고 — 모두 재현 성공).

## 23. 환경 분리 / 버전 관리(No.40) 시험 데이터(2026-09-25)

`environment-separation.integration.spec.ts`(A~T, 81 tests) · `environment-query-count.integration.spec.ts`(1 test — Prisma 쿼리 계측) · `environment-separation-multi-instance.integration.spec.ts`(1 test — 앱 2개)가 매 케이스마다 임시 SQLite DB(`prisma migrate deploy`)에 그룹/챗봇을 직접 생성한다(seed 비의존). 구현·코드 리뷰(2라운드) 완료 이후 이번 회차(test-automation)에서 실제로 걸려 넘어진 픽스처 함정을 기록한다(전부 시험 코드 쪽 문제였고 제품 코드 결함은 아니었다).

### 23.1 ★ 쿼리 수 계측은 프로세스 전역 캐시 2종의 "첫 턴만 콜드" 함정을 피해야 한다

공개 대화 경로의 Prisma 쿼리 수(AC-EN1-1)를 실측하려고 챗봇 A(환경 분리 미사용)·B(켜기→끄기)의 공개 턴을 비교하면, 처음에는 A=17~18, B=17로 어긋난다. 원인은 이 그룹과 무관한 기존 캐시 2종이다.

- **금지어 사전 캐시**(`InMemoryBannedWordCache`, No.12D · TTL 60초 · 전역 단일 슬롯): 프로세스에서 가장 먼저 도착한 공개 턴만 `banned_words` SELECT 1건이 더 붙는다.
- **대화 번들 캐시**(`DialogueBundleService.getCached()`, TTL 60초 · 챗봇별): **같은 챗봇**에 두 번째 턴을 보내면 번들 SELECT 약 12개가 통째로 빠져 쿼리 수가 17~18 → 5로 뚝 떨어진다.

해법: (a) 계측 전에 별도의 "예열용" 챗봇으로 한 번 요청해 금지어 캐시를 데운다 (b) A·B·대조군(A′, A와 같은 모양의 "또 다른 미사용" 챗봇)을 **각각 처음 한 번만** 재서 비교한다(같은 챗봇에 두 번째 요청을 보내 반복 안정성을 확인하려 하면 번들 캐시 때문에 다른 것을 재게 된다). 계측 자체는 제품 코드(`PrismaService`)를 건드리지 않고, `log:[{emit:'event',level:'query'}]`로 생성한 테스트 전용 `PrismaClient` 서브클래스를 `.overrideProvider(PrismaService)`로 주입해 만든다(`environment-query-count.integration.spec.ts`).

### 23.2 fire-and-forget 로그 적재 확인은 "쿼리 이벤트 배열 자체"를 스캔해야 계측 창을 오염시키지 않는다

로그 적재(`ConversationLogService.record()`)는 공개 응답을 먼저 보낸 뒤 백그라운드에서 끝난다(CLAUDE.md 기존 규약 — 폴링 확인). 계측 중인 쿼리 배열을 정확히 세려면, 확인 폴링 자체가 `conversationLog.findFirst` 같은 새 SELECT를 발사해 계측 창에 노이즈를 더하면 안 된다 — `prismaCounter.queries`(이미 잡고 있는 이벤트 로그) 안에서 `INSERT INTO ... conversation_logs`가 나타났는지를 **추가 쿼리 없이** 메모리에서만 찾는 `waitForLogInsert()`로 대체했다. SQLite 드라이버가 실제로 내는 식별자 인용은 큰따옴표가 아니라 백틱(`` `main`.`conversation_logs` ``)이다 — `/insert into "conversation_logs"/i` 같은 더블쿼트 정규식은 항상 매치 실패한다.

### 23.3 `evaluateProdSwitchGate`의 ROLLBACK 하향은 미리보기 응답 자체에 이미 반영돼 있다

§10 "kind=ROLLBACK이면 BLOCK을 WARN으로 낮춘다"는 `evaluateProdSwitchGate()` **내부에서** 일어난다 — `ProdSwitchService.preview({kind:'ROLLBACK', ...})`가 돌려주는 `gate.verdict`는 이미 `'WARN'`이며, "미리보기는 BLOCK 그대로 보여주고 확정 시점에만 낮춘다"처럼 2단으로 나뉘어 있지 않다. 롤백 게이트 시험은 `preview` 응답에서부터 `WARN`을 기대해야 한다.

### 23.4 게이트가 이미 BLOCK이면 `SWITCH_PROD_VERSION` 예약은 **생성 자체**가 막힌다

설계서 §11.2의 "GATE_BLOCKED는 생성 시점 blocker가 아니다"는 "예약을 만든 **뒤에** 게이트가 BLOCK으로 바뀌는" 흐름을 가리킨다. `ProdSwitchService.preview()`는 게이트를 항상 평가하고, `verdict==='BLOCK' && kind==='SWITCH'`면 `blockers`에 `GATE_BLOCKED`를 넣는다 — 이 `blockers`가 비어있지 않으면 `SwitchProdVersionExecutor.preview()`가 `preconditionFailures=[{code:'SWITCH_BLOCKED'}]`를 채우고, `deploy-schedule.service.ts#create()`는 `preconditionFailures.length>0`이면 예약 생성 자체를 `409 DEPLOY_SCHEDULE_PRECONDITION_FAILED`로 거부한다. "실행 시점 재평가에서 BLOCK → `FAILED(GATE_NOT_PASSED)`"(AC-EN5-3)를 실제로 보려면 **① 게이트가 통과(또는 미설정)인 상태에서 예약을 먼저 만들고 → ② 그다음 게이트를 BLOCK으로 바꾼 뒤 → ③ 예약 시각에 도달**시키는 순서여야 한다.

### 23.5 `ChatbotVersion.createdAt`은 예약 엔진의 `CLOCK`이 아니라 실제 벽시계(`new Date()`)다

`EnvironmentModeService#enable()`/`#disable()`, `ProdSwitchService#switch()`는 전부 `new Date()`를 직접 쓴다(주입된 `CLOCK`을 쓰지 않는다) — `DeploySchedulesEngine.tick()`류(§11)만 `CLOCK`을 경유한다. 학습 큐 "운영 미반영" 판정(`judgeProdReflection`, §15.1)처럼 **버전 `capturedAt`과 반영 시각(`resolvedAt`)을 같은 시간축에서 비교**해야 하는 시험은, 같은 통합 스위트 안에서 `FakeClock`을 다른 절(F·P 블록)이 이미 앞으로 돌려놨더라도(초기값 2026-03-01 + 누적 advance) 영향받지 않는다 — `resolvedAt`도 `clock.now()`가 아니라 **실제 `new Date()`** 로 찍어야 `ChatbotVersion.createdAt`과 같은 축이 된다(1차 작성 시 `clock.now()`를 썼다가 FakeClock이 실제 벽시계보다 한참 과거라 판정이 뒤집히는 것을 실제로 재현).

### 23.6 실제 동시성(`Promise.all`) 시험은 "같은 대상"과 "다른 대상" 경합을 구분해 설계해야 한다

운영 전환 CAS(`chatbot.updateMany(where:{id, prodVersionId: expected})`)는 대상이 같으면 늦게 도착한 쪽이 **먼저 `dto.targetVersionId === chatbot.prodVersionId`인지 보는 조기 반환(NOOP)** 에 걸릴 수 있어, 항상 "승자 1 · 패자 1(409)"로 갈리는 것이 아니라 "승자 1 · 패자 1(NOOP, 200번대)"도 정상 결과다. **서로 다른 대상**으로 동시 전환을 걸면(예: 스테이징 vs 운영 이력) 이 조기 반환 경로로 새지 않고 CAS 승자만 남아 결과가 결정적이 된다(P-1). 반대로 **같은 대상**을 노리는 경합(예약 실행 vs 즉시 전환, P-4)은 의도적으로 "APPLIED 또는 NOOP 또는 STATE_CHANGED/ENV_POINTER_STALE" 중 하나로만 수렴함을 확인하고, 최종 포인터·이력 건수(중복 적용 없음)로 정합성을 검증한다.

### 23.7 다중 인스턴스 시험은 예약 엔진(`tick()`)이 아니라 공개 대화 HTTP 자체를 양쪽에 태워야 한다

No.28(`scheduled-deploy-multi-instance.integration.spec.ts`)은 인스턴스 2가 `tick()`만 직접 호출하면 됐지만(예약 실행은 엔진이 하는 일), No.40의 AC-EN2-5(포인터 무캐시·TTL 대기 없음)는 **공개 대화 응답 자체**가 인스턴스별로 즉시 반영되는지가 요구사항이다 — 인스턴스 2도 `app.listen(0)`으로 실제 HTTP 포트를 열어 `/public/chatbots/:slug/messages`를 받게 해야 한다(관리자 라우트는 인스턴스 1에만 필요).

## 24. 데이터 거버넌스(No.45) 시험 데이터(2026-09-26)

### 24.1 파기 잡(`RetentionJob`)은 같은 KST 날짜에 두 번째 `tick()`을 조용히 건너뛴다

`RetentionJob.tick()`은 `GovernanceJobState('RETENTION').lastCompletedDay === kstToday`이면 즉시 반환한다(§9.1). 한 시험 파일 안에서 여러 `it()`이 각자 `retentionJob.tick()`을 호출해야 하면, 앞선 `it()`에서 `!partial`로 완료된 순간 `lastCompletedDay`가 오늘 날짜로 박혀 이후 `tick()`은 전부 무동작이 된다(실제로 `data-governance-purge-effects.integration.spec.ts` 작성 중 2~4번째 `it()`의 파기가 전부 조용히 no-op으로 끝나는 것을 관측했다). 해결: 첫 `tick()` 이후의 모든 `it()`에서 호출 직전에 `prisma.governanceJobState.updateMany({ where:{jobName:'RETENTION'}, data:{lastCompletedDay:null} })`로 재설정한다. 다른 No.45 잡(`FieldCryptoJob`)은 이런 하루 1완료 제약이 없다(I-2 — `DATA_REENCRYPT_JOB_ENABLED`는 자동 루프 시작 여부만 결정, `tick()` 자체는 게이트 없음).

### 24.2 `AccessViewInterceptor.recordView()`는 fire-and-forget — 연속 호출로 dedupe를 시험하려면 폴링이 필수다

`access-view.interceptor.ts`는 `void this.auditLog.recordView(...)`로 기록해 **HTTP 응답이 감사 기록보다 먼저 끝난다**. `data-governance-view-export-audit.integration.spec.ts` 초안에서 같은 핸들러를 `await` 순차 호출 3번만 했더니 `VIEW` 행이 1건이 아니라 2건 생기는 것을 실제로 관측했다 — 첫 호출의 dedupe 조회(`findFirst`)와 삽입이 끝나기 전에 두 번째 호출의 dedupe 조회가 먼저 실행되는 레이스였다. CLAUDE.md 규약대로 각 호출 뒤 실제 행 수를 폴링해 확인한 다음에야 다음 호출을 보내도록 고쳤다(`waitForViewCountAtLeast`). 이때 V-4/V-5(설문 응답 목록·자유 텍스트)처럼 **의도적으로 같은 (열람자·targetType·targetId·chatbotId·일) 키를 공유하는 두 핸들러**는 두 번째 핸들러 호출 전 "기존 카운트"가 이미 1이므로 `대기 목표 = before+1`로 걸면 영원히 타임아웃한다 — `대기 목표 = max(1, before)`로 완화해야 한다.

### 24.3 ★ 공개 대화 경로 쿼리 수 계측 — "두 번째 턴(캐시 적중)" 측정은 전체 스위트 반복에서 불안정했다

No.40의 `environment-query-count.integration.spec.ts` 선례를 따라 처음에는 "예열 턴 → 대상 챗봇 첫 턴(콜드) → 대상 챗봇 두 번째 턴(캐시 적중, 측정 대상)"으로 설계했다. 파일 단독 실행 3회는 항상 통과했지만, **`apps/api` 전체 스위트(212개 파일) 반복 실행에서만** 8 → 7로 흔들리는 것을 발견했다(2회차 전체 실행에서 재현). 원인 추정: 첫 턴의 fire-and-forget 후처리(대화 로그 적재 이후의 부수 작업)가 `waitForLogInsert()`가 반환한 시점에는 끝나지 않은 채로 남아 있다가, 전체 스위트 부하로 이벤트 루프가 밀리면 그 잔여 쿼리가 "두 번째 턴" 측정 창(`prismaCounter.queries.length = 0` 이후)으로 새어 들어간다 — 단독 실행처럼 여유 있는 스케줄링에서는 재현되지 않았다. 대응: No.40 방법론 그대로 "신규 챗봇의 첫 턴"(콜드 스타트) 1회만 측정하도록 되돌렸다 — 측정 대상 앞뒤에 다른 측정 창이 없어 레이스 여지가 없다. 이 값은 우연히 No.40의 예열 후 첫 턴 값(17)과 같았다(같은 키워드 매칭 경로를 공유하기 때문으로 추정 — 의도적으로 맞춘 것은 아니다).

### 24.4 `dayBucket`은 `SurveyResponse`·`HandoffSession`에도 필수 컬럼이다(선례: `ConversationLog`)

`SurveyResponse.create()`·`HandoffSession.create()`를 Prisma로 직접 시드할 때 `dayBucket`(KST 일자 문자열)을 빠뜨리면 컴파일 타임에 `Property 'dayBucket' is missing`으로 막힌다(`@@map` 스키마가 요구) — `toKstDayBucket(date)`(shared-types)로 채워야 한다. `ConversationLog`는 이미 알려진 함정이었지만(§21.7 참고) `SurveyResponse`·`HandoffSession`도 같은 규약이라는 점은 이번 회차에 처음 마주쳤다.

### 24.5 `ConfigModule.forRoot({validate})`의 "파일당 1회 import" 제약은 실패→성공 재현 통합 시험도 막는다

AC-DG2-1/2-2를 "실제 `AppModule` 기동이 환경변수에 따라 실패/성공한다"는 통합 시험(`data-governance-boot.integration.spec.ts` 시도)으로 만들려 했으나, 같은 Jest 파일 안에서 `process.env`를 바꾼 뒤 두 번째 `await import('../app.module')`을 호출해도 **첫 import 시점에 고정된 `ConfigModule` DynamicModule을 그대로 재사용**해 두 번째 시도가 첫 번째 환경변수로 기동하는 것을 발견했다(CLAUDE.md의 "정적 import spec" 경고가 사실은 "그 파일에서의 첫 동적 import"에도 그대로 적용된다는 재확인). 이 접근은 폐기하고, `governance-bootstrap.service.spec.ts`의 기존 M-2 패턴(가짜 `ConfigService` + private 메서드 직접 호출)으로 같은 서비스 인스턴스에서 실패→성공을 자유롭게 반복하는 방식으로 바꿨다 — 실제 파일시스템(임시 디렉터리)까지 동원해 `checkResidencyOrThrow()`의 심볼릭 링크 우회 케이스도 이 패턴으로 재현했다.

### 24.6 `SurveyExportQuerySchema`·`SurveyTextAnswerListQuerySchema`의 `from`/`to`는 선택이 아니라 필수(`KstDayString`)다

`StatsQuerySchema`(No.14, `chatbotId`+옵션 `from`/`to`)와 달리 설문 쪽 조회 스키마는 `from`/`to`가 필수다 — 생략하면 `400`. `toKstDayBucket(new Date())`로 항상 채워야 한다.
