# 오류검출 및 내용보완 프로세스 v1.0

## 1. 결함 분류 기준

| 등급 | 정의 | 예시 |
|---|---|---|
| Critical | 서비스 전체 장애, 데이터 유실/손상, 보안 취약점 | 대화 엔진 응답 불가, 권한 우회로 타 챗봇 데이터 접근 |
| High | 핵심 기능 불가, 우회 방법 없음 | 대화그래프 저장 실패, 채널 Webhook 수신 불가 |
| Medium | 기능은 동작하나 일부 시나리오에서 오류/부정확 | 특정 슬롯필링 조합에서 컨텍스트 유실 |
| Low | UI/UX 사소한 문제, 문구 오류 | 색상 대비 기준 미달, 오탈자 |

## 2. 검출 채널

1. 자동시험 실패(CI) — `자동시험_전략.md` 파이프라인에서 자동 수집
2. 수동 시험(`시험항목.md` 체크리스트 수행 중 발견)
3. 대화 품질 모니터링(운영 중 미응답률/오응답 급증 알림 — No.2 대시보드, No.24 하이브리드CS 연계)
4. 사용자/상담원 피드백(운영 단계)

## 3. 처리 절차

```
검출 → 등급 분류(위 기준) → 재현 확인 → 원인 분석 → 수정 → 회귀시험(관련 시험항목 재실행) → 종료
```

- Critical/High는 발견 즉시 담당 에이전트/개발자에게 할당, 수정 전까지 관련 배포 보류(`docs/05-ops/자동배포.md` 게이트 연계)
- Medium/Low는 스프린트 단위로 backlog화하여 우선순위 조정

## 4. 내용보완(문서 갱신) 원칙

- 시험 중 발견된 요구사항 누락/오해는 `docs/01-requirements/기능요구사항.md`을 직접 갱신하고, 변경 이력을 해당 문서 내 "교차검증 메모" 섹션에 이어서 기록한다.
- 설계 변경이 필요한 결함은 `docs/02-spec/개발명세서.md`를 갱신한다.
- 문서 갱신 없이 코드만 수정하는 것을 금지 — 요구사항/설계와 실제 구현의 괴리를 방지한다.

## 5. 책임

`bug-triage` 에이전트가 결함 등급 분류와 라우팅을 담당하고, 각 기능 담당 에이전트(system-architect, ui-designer, backend-implementer, ml-engineer, frontend-implementer 등)가 원인 영역에 따라 문서/코드를 보완한다.
