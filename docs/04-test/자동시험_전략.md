## 2. CI/CD 연계

- PR 생성 시: 단위/통합 시험 + 정적분석 자동 실행 (`docs/05-ops/자동배포.md`의 파이프라인 1단계와 연계)
- main 병합 전: 대화 품질 회귀 시험 + E2E 핵심 플로우 실행, 실패 시 병합 차단
- 배포(스테이징) 후: 부하 시험 + 접근성 자동 검사 실행, 결과를 `오류검출_프로세스.md` 기준으로 트리아지
- **현재 상태(2026-09-19)**: CI 워크플로 자체는 아직 미구성(`docs/05-ops/자동배포.md` §1에 따라 사용자가 플랫폼/자격증명을 명시하기 전까지 착수하지 않음). 아래 §3에 실제 구현된 로컬 실행 스크립트만 존재한다.

### 3.2 `apps/web` — Vitest + Testing Library + jest-axe

- 2026-09-19 기준 신규 도입. `package.json`에 `@testing-library/react`, `@testing-library/jest-dom`, `@testing-library/user-event`, `jsdom`, `jest-axe`, `@types/jest-axe`를 devDependency로 추가했다(`pnpm --filter @chat-bot/web add -D ...`).
- 설정: `apps/web/vite.config.ts`의 `test` 필드(`environment: 'jsdom'`, `setupFiles: ['./src/test/setup.ts']`, `globals: false`). `globals: false`를 유지하므로 각 스펙 파일은 `vitest`에서 `describe/it/expect/vi`를 명시적으로 import한다(프로젝트의 명시적 import 컨벤션 유지).
- `src/test/setup.ts`: `@testing-library/jest-dom` matcher 등록, 각 테스트 후 `cleanup()` 명시 호출(globals=false라 testing-library 자동 cleanup 훅이 등록되지 않아 수동 등록 필요), jsdom `offsetParent` 폴리필(jsdom은 레이아웃 엔진이 없어 모든 요소의 `offsetParent`가 항상 `null`이다 — `components/Modal.tsx`의 포커스 트랩이 `offsetParent !== null`로 "보이는 요소"를 판별하므로 이 폴리필이 없으면 Tab 트랩 시험이 실패한다. **앱 코드 버그 아님, 테스트 환경 한계에 대한 테스트 전용 보정**).
- **주의**: `vitest.config`의 `restoreMocks`/`clearMocks` 옵션은 켜지 않는다. 이 저장소의 spec 파일들은 대부분 모듈 스코프에서 한 번 `vi.fn().mockResolvedValue(...)`를 설정하는 패턴을 쓰므로, 저 옵션을 켜면 매 테스트 전에 mock 구현이 초기화되어 `Cannot read properties of undefined (reading 'then')`류 오류가 발생한다. 각 spec이 필요하면 `beforeEach`에서 명시적으로 `mockReset()`/재설정한다.
- 실행: `pnpm --filter @chat-bot/web test`(= `vitest run`), 타입체크는 `pnpm --filter @chat-bot/web typecheck`.

### 3.3 axe-core(jest-axe) 관련 알려진 한계

jsdom에는 실제 CSS 레이아웃/렌더링 엔진이 없어 `color-contrast` 규칙이 배경색 합성을 계산하지 못하고 "incomplete"만 반환한다. 따라서 `ChatbotListPage.a11y.spec.tsx`에서는 이 룰만 비활성화하고, 나머지 axe 규칙(레이블 누락, ARIA 속성, 랜드마크, 중복 id 등)은 그대로 적용한다. **실 브라우저 렌더링 기반 대비 자동 스캔은 Playwright + `@axe-core/playwright` 등 E2E 인프라 도입 시점에 보완이 필요하다** — 우선순위는 §4 "다음 자동화 대상"에 기록.

**code-reviewer 지적사항 보강 — 오버레이 요청 본문 크기(FR-10-21)**: 기존에는 100KB~2MB 구간의 실제 HTTP 페이로드 크기 테스트가 없어 수동 curl로만 검증되어 있었다. 이번에 다음 2건을 신규로 추가했다.

1. 약 200KB(과거 Express 기본 body-parser 상한인 100KB는 넘지만 오버레이 1MB 상한(`OVERLAY_LIMITS.bodyBytes`)보다는 작은 크기) → `200` 정상 처리.
2. 약 1.08MB(1MB 상한은 넘지만 부트스트랩에 설정한 2MB 하드 캡보다는 작은 크기) → `400 LIMIT_EXCEEDED`(Express의 생 `413`이 아니라 우리 오류 봉투).

이 두 테스트가 의미를 가지려면 **테스트용 Nest 앱도 `main.ts`와 동일하게 body-parser 상한을 2MB로 올려야 한다** — 기존 `Test.createTestingModule(...).compile()` → `createNestApplication()` 흐름은 Express 기본값(약 100KB)을 그대로 썼기 때문에, 고치지 않으면 정상 크기 오버레이 요청도 생 `413`으로 실패해 버그를 오히려 은폐하는 테스트가 됐을 것이다. `quality-channel.integration.spec.ts`의 `beforeAll`에 `app.useBodyParser('json', { limit: '2mb' })` 등을 `main.ts`와 동일하게 추가해 이 문제를 막았다. 크기 제어는 examples 배열(항목당 최대 200자, 의도당 최대 500개)을 ASCII로만 채워 문자 수(zod `.length` 기준)와 바이트 수(`Buffer.byteLength`, 실제 HTTP 크기)가 사실상 같아지도록 설계했다.

**추가로 발견해 보강한 커버리지 공백**:

- **AC-P-12(공개 API 레이트리밋 429)**: 기존에는 `rate-limiter.spec.ts`의 `consume()` 순수 함수만 테스트되어 있었고, `PublicRateLimitGuard`가 실제 컨트롤러에 배선되어 `429`+`Retry-After`를 반환하는지의 통합 테스트는 없었다. 같은 `sessionId`로 31회 연속 HTTP 요청을 보내 31번째가 `429 RATE_LIMITED`+`Retry-After` 헤더를 반환함을 확인하는 테스트를 추가했다.
- **AC-C-1(응답 스키마 계약)**: 이 그룹의 통합 테스트는 다른 두 그룹과 달리 성공 응답에 대한 zod 파싱 검증이 전혀 없었다(오류 응답의 `ApiErrorSchema.parse`만 있었음). 대표 성공 케이스 5건(AC-10-1/AC-11-1/FR-10-25~30/AC-P-1/AC-P-6)에 `SimulateResponseSchema`/`ChannelListItemSchema`/`CompareResponseSchema`/`PublicChatbotConfigSchema`/`PublicMessageResponseSchema.parse()`를 추가해 계약 검증 공백을 메웠다. 단, 이 스키마들은 `.strict()`가 아니라서 **여분 필드 추가**(AC-C-5, NFR-S1 회귀)는 zod가 조용히 strip하므로 런타임 계약 테스트로는 못 잡는다는 한계를 `시험항목.md`에 명시했다 — `.strict()` 전환 여부는 `system-architect` 판단 필요.

#### 3.5.5 seed 데이터 결함 발견 및 처리 — 컨텍스트 슬롯명 정규식 위반

시험 진행 중 `apps/api/prisma/seed.ts`의 `커피주문` 컨텍스트 슬롯명이 한글("메뉴"/"사이즈"/"수량")로 되어 있어 `ContextSlotSchema.name`의 정규식(`^[A-Za-z0-9_]{1,50}$`)을 위반하는 것을 발견했다(대화설계 그룹 seed의 기존 결함, 이번 품질/채널 그룹의 결함은 아님 — 세션 재개 시 frontend-implementer가 이미 보고했던 지점과 동일 계열). PATCH 저장은 물론 오버레이 시뮬레이션도 이 슬롯 정의를 그대로 오버레이에 실으면 `400`이 난다.

**처리: seed를 직접 수정했다**(fixture 우회가 아니라 근본 수정을 선택). `slots[].name`을 `menu`/`size`/`quantity`(영문 식별자)로 바꾸고, 화면 표시는 기존 `label`("메뉴"/"사이즈"/"수량")을 그대로 유지했다. `completionMessage`의 치환자도 `{메뉴} {사이즈} {수량}` → `{menu} {size} {quantity}`로 함께 수정했다(치환 로직이 `slot.name`을 키로 쓰기 때문, `packages/dialogue-engine/src/context-session.ts`의 `renderCompletionMessage`). 다른 seed 데이터는 건드리지 않았다. 이 seed는 자동화된 통합/컴포넌트 테스트가 직접 로드하지 않으므로(각 그룹 테스트는 seed와 무관하게 자체 fixture를 생성) 기존 테스트 스위트에는 영향이 없다 — 실 서버 기동 시 수동 검증(`pnpm --filter @chat-bot/api prisma:seed`)과 위젯 수동 검증(NFR-M5)에서만 차이가 드러난다.

#### 3.8.4 공개 위젯 통합 시나리오(질문 전송 → PENDING → 폴링 → 완료) — 3계층 조합 검증 판단

과제에서 요구한 "공개 위젯 통합 시나리오"는 실제 외부 RAG 서버·실제 공개 대화 API HTTP 왕복까지 포함한 **단일 종단 통합 테스트로는 구현하지 않았다**. 이유:

- `nlu-rag-answering.integration.spec.ts`는 `RAG_BASE_URL` 미설정을 전제로 부팅된다 — 이는 우연이 아니라 그 스위트 자체의 존재 이유(AC-N4-1: "신규 환경변수를 하나도 설정하지 않아도 정상 기동")이므로, 같은 스위트 안에서 RAG를 활성화하면 오히려 AC-N4-1의 회귀 방지력이 약해진다.
- RAG 활성 상태의 **별도** Nest 앱을 추가로 부팅(`prisma db push` + `app.listen()`)하는 비용은 크고, `global.fetch`를 이중으로 모킹(공개 API 왕복 + 외부 RAG 왕복)해야 해 테스트 자체의 신뢰도도 오히려 떨어진다.

대신 **3개 레이어를 조합**해 같은 경로를 각 경계에서 정밀하게 검증했다(§3.8.1/§3.8.3):

1. 위젯 DOM 레벨(`app.pending.spec.ts`) — 위젯이 실제로 소비하는 계약(`pendingAnswer` → 폴링 → `READY`/`FAILED`/`EXPIRED`).
2. 백엔드 오케스트레이션 레벨(`rag-answer.service.spec.ts`) — `PendingAnswerStore.complete()`/`ConversationLogPort.record()`가 올바른 인자로 호출되는지.
3. 외부 HTTP 클라이언트 레벨(`rag-http.client.spec.ts`) — 실제로 나가는 요청의 모양.

3개 프로세스를 모두 살려 실제 네트워크 스택까지 왕복하는 단일 E2E 테스트는 여전히 없다 — Playwright 등 E2E 인프라 도입 시 1순위로 추가할 것(§4.7 참고). 외부 RAG 서버를 실제로 호출하는 테스트는 어떤 레이어에서도 CI에 넣지 않는다(전부 모킹 — `nlu-rag-answering.md` §11 인계 메모 "test-automation ⑩" 원칙 준수).

### 11.2 ★ 핵심 발견 — `ConfigModule.forRoot()`는 호출 즉시(동기) `process.env`를 스냅샷한다

`@nestjs/config`(v3.3.0) `ConfigModule.forRoot()`(`config.module.js`)는 `await` 이전에 `config = {...config, ...process.env}` 후 `options.validate(config)`를 **동기로 즉시** 실행한다. 이 호출은 `app.module.ts`의 `@Module({imports:[ConfigModule.forRoot(...)]})` 데코레이터 인자가 평가되는 시점 — 즉 테스트 파일이 `import { AppModule } from '../app.module'`을 **정적으로** 선언하는 순간(테스트 파일이 로드될 때, `beforeAll`보다 먼저) 실행된다.

이 때문에 초기 작성 버전에서는 `beforeAll` 안에서 `process.env.LEGACY_API_PRIVATE_ALLOWLIST`·`LEGACY_API_CIRCUIT_FAILURE_THRESHOLD`·`LEGACY_API_CIRCUIT_OPEN_MS`·`LEGACY_API_ENABLED` 등을 설정해도 **전혀 반영되지 않는** 현상을 겪었다(항상 zod 기본값으로 동작 — allowlist 시험이 "허용" 케이스에서도 차단되고, 회로차단 임계치가 항상 5로 동작하며, `LEGACY_API_ENABLED=false`가 무시됨). `moduleRef.get(ConfigService).get('LEGACY_API_PRIVATE_ALLOWLIST')`를 직접 찍어 `""`(zod 기본값)임을 확인해 원인을 특정했다.

**이것은 제품 결함이 아니다** — 실제 운영에서는 프로세스 기동 전에 환경변수를 설정하므로 "부팅 후 env 불변"이 정상 동작이다. 시험 방식이 잘못이었다. **해결**: `app.module.ts`를 정적 import하지 않고, `beforeAll` 안에서 환경변수를 먼저 설정한 뒤 `const { AppModule } = await import('../app.module')`로 **동적 import**한다. 단, 같은 파일 안에서 **서로 다른 env 값으로 앱을 두 번** 띄워야 하는 경우(`LEGACY_API_ENABLED=true` vs `false`) `jest.resetModules()`로 두 번째 동적 import 전 모듈 캐시를 비우면 `@nestjs/core`의 데코레이터 메타데이터(Reflector 등)까지 같이 리셋되어 `Nest can't resolve dependencies of the PermissionGuard(?, ...)` 식으로 깨진다(직접 확인). 그래서 `LEGACY_API_ENABLED=false` 케이스는 **별도 파일**(`legacy-api-integration-disabled.integration.spec.ts`)로 분리해, 파일 단위로 격리된 jest 모듈 레지스트리를 그대로 활용했다(`resetModules()` 불필요).

**향후 그룹에 대한 권고**: `beforeAll`에서 `LEGACY_API_*`류(zod 스키마에 등록된) 환경변수를 설정해 동작을 바꿔야 하는 통합 스펙은, 이 파일을 선례로 삼아 `AppModule`을 **동적 import**로 읽을 것. 기존 그룹들(No.16/23·No.28 등)이 `DEPLOY_SCHEDULE_ENABLED`/`EMBEDDING_BASE_URL`을 `beforeAll`에서 설정해도 문제없이 동작해 온 이유는 그 값들의 소비처가 `ConfigService.get()`이 아니라 **요청 시점에 `process.env`를 직접 읽거나**(`EMBEDDING_BASE_URL`은 zod 스키마에 아예 없음) **폴링 루프 시작 전에** 참조되기 때문으로 보인다(각각 개별 확인은 하지 않았음 — 이번 그룹만의 재현·해결이며, 일반화된 결론은 아니다).

### 11.3 SSRF 시험 기법 — 루프백 절대 차단과 로컬 목 서버 검증을 양립시킨 방법

지시서가 확인을 요구한 항목: "시험용 로컬 서버를 쓰려면 정상 경로로만 열 수 있어야 한다"는 설계 의도(§17 NFR-LM2 "시험 대체 지점")와 실제 구현이 일치하는지.

- `LegacyApiModule`은 `LEGACY_DNS_RESOLVER`/`LEGACY_TRANSPORT`를 DI 토큰으로 두고(`legacy-transport.port.ts` 주석 "시험에서 가짜 리졸버·가짜 전송으로 교체하는 지점") `NodeDnsResolver`/`NodeHttpTransport`로 바인딩한다. 이 두 토큰은 `LegacyApiModule.exports`에는 없다(L-4 봉인 대상).
- `Test.createTestingModule({imports:[AppModule]}).overrideProvider(LEGACY_DNS_RESOLVER).useValue(fakeDns).overrideProvider(LEGACY_TRANSPORT).useValue(fakeTransport)`로 **테스트 전용 파일에서만** 교체했다 — 운영 코드는 한 줄도 바꾸지 않았다. `overrideProvider`는 토큰 문자열로 전역 치환하므로 `exports` 미포함과 무관하게 동작한다.
- 가짜 DNS는 시험용 도메인(`legacy.example.invalid` 등)을 **공인/사설 주소로 위장**해 반환한다 — 이 시점에서 `classifyAddress()`(운영 코드, 무수정)가 정상적으로 PUBLIC/PRIVATE를 분류한다. 가짜 전송은 그 **뒤에만** 개입해 실제 소켓 연결을 로컬 목 서버(127.0.0.1)로 돌린다.
- **루프백 자체 차단 확인**: `baseUrl`을 IP 리터럴(`http://127.0.0.1:1`)로 등록한 연결은 `LegacyApiHttpClient.send()`가 `isIP(hostname)!==0`이면 리졸버를 아예 호출하지 않고 곧장 `classifyAddress()`로 넘어간다 — 즉 가짜 리졸버가 있어도 IP 리터럴 루프백은 **운영 코드 그대로** 차단된다. 실제로 이 케이스에서는 가짜 전송(`transportCounter.calls`)조차 호출되지 않음을 확인했다(`legacy-api-integration.integration.spec.ts`, "6. SSRF — 루프백 baseUrl은 절대 차단되며…").

**결론**: 설계 의도(NFR-LM2)와 정확히 일치한다. 운영 코드 파일에는 테스트 전용 분기·환경변수·토큰이 전혀 추가되지 않았고, SSRF 방어 로직(`ip-policy.ts`·`build-request.ts`)은 이 시험 전 구간에서 무수정·무우회로 실행됐다.
