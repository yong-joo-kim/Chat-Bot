# 시험계획

> 기반 문서: `docs/01-requirements/기능요구사항.md`, `docs/02-spec/개발명세서.md`

## 1. 시험 목적 및 범위

`기능요구사항.md`의 39개 기능(기본 15 / 확장 14 / 옵션 10)에 대해 기능·비기능(성능/보안/접근성) 검증을 수행한다. 범위는 `02-spec` §6에서 확정되는 1차 개발 범위를 따른다.

## 2. 시험 단계

| 단계 | 대상 | 수행 시점 | 담당 |
|---|---|---|---|
| 단위 시험 | `packages/dialogue-engine`, `packages/llm-provider` 로직 단위 | 구현 직후 | `test-automation` 서브에이전트 |
| 통합 시험 | `apps/api` 엔드포인트, DB 연동 | 기능 단위 완료 시 | `test-automation` |
| 회귀 시험 | 대화검증시스템(TC테스트, 19번), 학습영향도 TEST(20번) 재사용 | 매 재학습/배포 전 | `test-automation` + ml-worker |
| UI/접근성 시험 | `docs/03-design/UIUX_준수기준.md` 10개 카테고리 | 화면 구현 완료 시 | `frontend-implementer` + `code-reviewer` |
| 사용자 인수 시험(UAT) | 관리자 시나리오(챗봇 제작→배포→모니터링) | 1차 개발 범위 완료 시 | 사용자 승인 |

## 3. 시험 환경

- 로컬: `docker-compose`(API+DB+Redis+ml-worker mock) — `docs/05-ops/자동배포.md` 참고
- LLM/STT/TTS 등 외부 연동은 기본적으로 `mock` Provider 사용(Auto QA 컨벤션과 동일), 실 연동 시험은 별도 스테이징에서만 수행

## 4. 완료 기준(Exit Criteria)

- 해당 기능의 시험항목(`시험항목.md`) 전 항목 Pass
- `code-reviewer` 이슈 재발생 0건(최대 3회 반복 내 해결)
- 접근성 시험: 색상대비 4.5:1, 키보드 전체 탐색 가능 — 100% 충족
- 회귀 시험: 기존 통과 케이스 중 신규 실패(regression) 0건

## 5. 리스크 및 대응

| 리스크 | 대응 |
|---|---|
| GPU 인프라 부재로 확장기능(16~21) 시험 불가 | ml-worker mock 모드로 로직만 검증, 실제 GPU 성능시험은 별도 일정 |
| 옵션기능(30~39)은 아직 설계 미확정 | 시험항목은 설계 확정 후 추가 |
| 외부 채널(카카오톡 등) API 정책 변경 | Webhook 어댑터 계층에 계약테스트(contract test) 우선 적용 |
