**근거 2 — 국내 규제 관행(⚠ 법무 확인 전 가정)**: 개인정보처리시스템의 **접속기록**(처리자 식별·일시·접속지·처리한 정보주체 정보·수행 업무 — **조회 포함**)을 최소 1년(대규모·고유식별정보 처리 시 2년) 보관하고 정기 점검하는 관행, 보유기간 경과 개인정보의 **지체 없는 파기와 파기 기록**, 전송·저장 구간 암호화. → 이 그룹의 "열람 감사(FR-DG8)"·"감사 보존 하한(FR-DG5-6)"·"파기 이력(FR-DG6)"의 근거이며 **수치는 환경변수 기본값일 뿐 법적 판단이 아니다.**

**근거 3 — No.36과의 경계**(카탈로그 비고):

### 1.3 이미 있는 것과 없는 것 (코드 확인)

#### 1.3.1 ★ 저장소 — "SQLite 단일 파일, 암호화 계층 없음"

| 사실 (파일:행) | 결과 |
|---|---|
| `datasource db { provider = "sqlite"; url = env("DATABASE_URL") }`(`apps/api/prisma/schema.prisma` 17~19행) · `DATABASE_URL`은 필수 문자열 1개뿐(`config/env.validation.ts` 10행) — 경로·호스트 검증 없음 | 저장 위치 = **`DATABASE_URL`이 가리키는 파일 1개**. 레지던시 (a)는 "이 경로가 허용 디렉터리 안인가"를 **기동 시 검사**하는 것으로 구현 가능(FR-DG2) |
| DB 계층 암호화 없음 — Prisma의 SQLite 엔진은 SQLCipher를 지원하지 않는다(프로젝트 전체에 `PRAGMA key`·`cipher` 0건 — 원시 SQL은 `handoff-secure-delete.query.ts` 9행의 `PRAGMA secure_delete = ON` 등 4파일뿐) | ★ **C-1**: DB 계층 암호화는 **드라이버 교체**(libSQL 등)가 필요해 범위 밖. 현실적 계층 = **인프라(디스크·볼륨 암호화)** + **애플리케이션(필드 AES-GCM)** 2가지뿐(J-5) |
| 상담 원문 소거 트랜잭션만 `PRAGMA secure_delete = ON`을 켠다(`handoff/handoff-secure-delete.query.ts` 4~9행) · 설계서가 "저널·백업·파일시스템 잔존은 애플리케이션이 보증하지 않는다 → 디스크 암호화·백업 정책 = No.45"로 넘김(`hybrid-cs-설계.md` 708·1169행) | 파기 잡의 소거도 같은 장치를 써야 하며, **물리 잔존 0은 애플리케이션이 약속할 수 없다** → 디스크 암호화를 **거버넌스 모드의 운영 전제**로 명문화(C-8) |
| Postgres 전환은 예정(개발명세서 §6-4, 377행 "SQLite/Postgres 공통 문법만") | 레지던시 검증·파기 SQL은 **양쪽 공통**이어야 한다(원격 DB면 "호스트 허용 목록" 검사로 대체 — FR-DG2-2) |

#### 1.5.3 방식 (J-6 · P-7)

- **알고리즘**: AES-256-GCM, 필드마다 무작위 96비트 IV, 인증 태그 포함. **AAD = (테이블, 컬럼, 행 id)** — 암호문을 다른 행·컬럼에 복사해 붙이는 공격을 막는다.
- **저장 형식**: 문자열 컬럼 그대로(`String`) — 접두 봉투 `enc:v1:<keyId>:<base64(iv‖ct‖tag)>`. 접두가 없으면 평문(기존 행 호환 — 이행 기간 읽기 지원).
- **키 관리(1차)**: 환경변수 키링 `DATA_ENCRYPTION_KEYS`(예: `k2:<base64 32B>,k1:<base64 32B>` — 첫 키 = 쓰기 키, 나머지 = 읽기 전용). **KMS·HSM·Vault는 2차** — `KeyProvider` 포트 1개로 두어 교체 지점을 1곳으로(ADR-0026 3포트 선례).
- **키 교체**: 새 키를 앞에 추가하고 재기동 → 신규 쓰기는 새 키 → **재암호화 잡**(파기 잡과 같은 `PollingLoop` · 배치)이 옛 키 행을 새 키로 바꾼다 → 데이터 지도에 "옛 키 사용 행 0"이 되면 운영자가 옛 키를 제거. 옛 키가 필요한 행이 남았는데 키를 빼면 **기동 실패**(FR-DG4-9).
- **키 분실 = 데이터 영구 손실**이다. 이를 막는 것은 운영(키 백업 절차)이며 콘솔·문서에 명시한다.

#### 1.5.5 기존 데이터 이행 (P-8)

- 켜기 = 신규 쓰기부터 암호화 + **백필 잡**이 기존 평문 행을 배치(예: 500행/트랜잭션)로 암호화. 진행률 = 데이터 지도 "평문 잔존 N행". 읽기는 접두로 판별해 평문·암호문 모두 지원.
- 끄기 = **콘솔에서 끌 수 없다**(완화는 서버 설정만 — J-3). 운영자가 `DATA_ENCRYPTION_ENABLED=false`로 바꾸면 신규 쓰기는 평문, 기존 암호문은 **키가 있는 한 계속 읽힌다**. 전량 복호화는 운영 스크립트(2차 · 필요 시).
- 백필 중 암호문·평문 혼재는 정상 상태다(읽기 경로가 둘 다 처리).

| `ConversationLog` | 대화 원천(통계 원천) | ★ R-4/R-9/R-10 | **텍스트 소거**: `userMessage`·`botResponse` → 빈 값 + 소거 시각 표식(행·수치 컬럼·`sessionId` 보존) | `createdAt` |
| `UnansweredQuestion` | 학습 큐 | 봉인(`integrated-stats-patches.md` 95행) | **종결 항목(RESOLVED·IGNORED)만** 텍스트 소거(또는 architect가 롤업 후 삭제 판단) · PENDING은 대상 아님 | `lastOccurredAt` |

**왜 "텍스트 소거"인가 (P-3 권고 근거)**: ADR-0033 §3은 행 삭제 시 **같은 트랜잭션에 수치 롤업 선적재**를 의무화했다. 롤업을 만들면 통합 통계·질문 순위·설문 분포·상담 통계가 **"원천 ∪ 롤업" 두 원천**이 되고(정의 드리프트), 주/월 세션 수는 일 롤업으로 재현되지 않는다(DD-61). 반면 **텍스트만 소거**하면 개인정보(발화 본문)는 사라지고 **모든 수치 통계가 바이트 단위로 불변**이며 롤업 테이블이 필요 없다. 상담 원문 소거가 이미 같은 방식으로 봉인과 공존한다(ADR-0033 No.24 갱신 3항). 대가: 행과 `sessionId`(가명 난수)는 남는다 — 규제 해석상 "행 자체의 삭제"가 요구되면 2차에 "소거 후 더 긴 기한의 행 삭제(롤업 선적재)"를 얹는다(P-3 (c)).

**소거 후 화면**: 질문 순위·큐·대화 보기·설문 목록은 소거된 행을 "보존기간 경과로 파기됨"으로 표시하거나 순위 집계에서 제외한다(빈 문자열이 순위 1위로 뭉치지 않게 — FR-DG6-6).

#### 1.6.2 정책 범위 (P-5)

- **전역 기본**(콘솔 — `security:write`) + **챗봇별 재정의**(대화 원천 4종만 — 같은 서버에 금융 상담 봇과 일반 안내 봇이 공존하는 경우). 감사로그·호출 로그는 **전역만**(챗봇 무관 행 존재).
- 값 = 일(日) 단위 정수 또는 "무기한". **서버 하한·상한**(환경변수)이 콘솔 입력 범위를 제한한다: 대화 원천 하한 기본 **7일**, 감사로그 하한 기본 **365일**(⚠ 법무 확인 — §1.2 근거 2).
- **기본값 = 전부 무기한**(현행과 동일 — FR-0-161).

#### 1.6.3 안전장치

- **단축 유예**: 보존기간을 줄이면 **새 기준의 첫 파기는 유예기간(기본 7일) 뒤**다. 저장 시 "영향 행 수 미리보기(대상·건수)" + **챗봇 이름(전역이면 "보존기간 단축") 재입력 확인** + 감사.
- **파기 이력**(`RetentionRun` 가칭): 실행 id · 대상 테이블 · 챗봇 · 적용 정책(일수) · 기준 시각(cutoff) · 처리 건수 · 시작/종료 · 결과(성공/부분/실패) · 실행 인스턴스. **본문·id 목록 없음**. 이력 자체는 감사로그와 같은 보존 하한을 따른다.
- **1회 처리량 상한**·배치 간 양보(SQLite 단일 작성자 — 공개 대화 로그 적재를 막지 않게 — NFR-DGP3).
- **파기 잡은 끌 수 있다**(`DATA_RETENTION_JOB_ENABLED` — 기본 `true`이지만 정책이 전부 무기한이면 할 일이 없다 · 시험 격리 규약상 `jest.isolate-env.js`가 `false`로 고정).

### 1.7 ★ 선결 쟁점 4 — 감사 강화: 무결성 · 열람 감사 · 내보내기 (P-6)

#### 1.7.1 무결성 (J-11)

| 선택지 | 내용 | 막는 것 | 판정 |
|---|---|---|---|
| 없음 | append-only + 삭제 API 부재(현행) | 애플리케이션 경유 변조 | 원문 "감사 강화" 미충족 |
| **해시 체인 + 체인 앵커** ★ | 각 행에 `seq`(전역 순번)·`prevHash`·`rowHash = SHA-256(prevHash ‖ 정규 직렬화(행))` · 선택적으로 **HMAC 키**(`AUDIT_CHAIN_KEY`)가 있으면 HMAC-SHA256 · 검증 API가 구간을 재계산 · **체인 머리(최신 seq·해시)**를 파기 이력·내보내기 파일·서버 로그에 주기적으로 남겨 외부 대조 가능 | DB 직접 수정·중간 행 삭제·순서 변경의 **탐지** | **권고** — 키가 없으면 "DB 쓰기 권한자가 체인 전체를 재계산"하는 공격은 앵커 대조로만 탐지됨(정직 표기) |
| 외부 봉인(WORM 저장소·타임스탬프 기관) | 체인 머리를 외부로 전송 | 서버 장악자 변조 | **2차** — 새 외부 출구(출구 통제와 충돌) |

- 체인은 **기록된 행의 무변조**만 증명한다. 기록 실패(C-4)로 인한 **누락**은 증명하지 못한다(FR-DG7-6).
- 기존 행(도입 전)은 체인 밖 — 도입 시점에 **제네시스 앵커 1건**(직전까지 행 수·최대 `createdAt`)을 남긴다.
- 보존 파기로 앞부분이 지워지면 **마지막 파기 행의 해시가 새 앵커**가 된다(검증은 앵커부터).

#### 1.7.2 열람 감사 (J-12)

현재 열람 감사는 상담 원문 `RAW_VIEW` 1종뿐이다. 규제 관행상 "누가 어떤 개인정보를 조회했는가"(§1.2 근거 2)가 필요하다. 모든 GET을 기록하면 볼륨이 수십 배다(ADR-0016 대안표 — 조회 75개 중 32개).

| 선택지 | 대상 | 판정 |
|---|---|---|
| 없음 | — | 미충족 |
| 내보내기만 | CSV·파일 다운로드 5종 | 최소 |
| **내보내기 + 개인정보 원천 열람 화면(닫힌 목록)** ★ | 내보내기: 감사로그·설문 응답·TC 결과·FAQ/의도/키워드(자산 — 제외 검토) · 열람: 대화 보기(`live-sessions/:sessionRef/transcript` — `live-sessions.controller.ts` 41행)·상담 이력 상세·설문 응답 목록·미응답/부정 평가 항목 상세·**감사로그 조회 자체** | **권고** — 거버넌스 모드 켜짐일 때만. 단위 = (열람자, 대상 리소스, KST 일)당 1건(폴링·새로고침 중복 억제 — `RAW_VIEW` 선례의 "원문이 실제로 응답에 실린 건당 1건"을 일 단위로 완화) |
| 모든 조회 | 전 GET | 기각(볼륨·신호 소실) |

- 기록 위치 = **`AuditLog`**(새 액션 `VIEW`·`EXPORT` — 같은 조회 화면·같은 체인·같은 보존). 본문·검색어 원문 없음(대상 id·건수·기간 파라미터만).
- 대상 자산 내보내기(FAQ·의도·키워드 — 관리자 작성 데이터)는 개인정보 원천이 아니어서 **제외**(단 학습 반영 예문에 마스킹된 사용자 발화가 섞일 수 있다는 점은 architect가 최종 판단).

#### 1.7.3 감사로그 내보내기 (J-13)

- 기존 `GET /audit-logs/export`(CSV · 10,000행 · 기간 90일)를 유지하고 **① 내보내기 자체를 `EXPORT`로 감사** ② 열 추가 `seq`·`rowHash` ③ 파일 끝(또는 응답 헤더)에 **구간 체인 검증 결과·체인 머리**를 동봉한다.
- 10,000행 상한을 넘는 장기 보관용 대량 내보내기(월 단위 분할·서명 파일)·SIEM(syslog) 실시간 전송은 **2차**(SIEM은 새 외부 출구 — 출구 허용 목록에 등록돼야 한다).

### 1.9 ★ 선결 쟁점 6 — 기본값 · 하위 호환 · 성능 (FR-0-161 · NFR-DGP)

- **거버넌스 모드 = 서버 단위 스위치**(`DATA_GOVERNANCE_MODE=OFF|ON`, 기본 `OFF`). 꺼져 있으면: 출구 검사 0 · 열람 감사 0 · 암호화 0 · 파기 대상 정책 0(전부 무기한) · 데이터 지도 화면은 **읽기로 제공**(현재 상태를 보여 주는 것 자체는 무해 — P-12).
- **감사 체인은 모드와 별개로 항상 켤지**가 쟁점이다(P-6): 체인은 기존 행을 바꾸지 않고 새 컬럼만 채우며 비용이 작다 → 권고 = **모드와 무관하게 항상**(감사 무결성은 규제 고객만의 가치가 아니다). 단 기존 감사 API 응답 모양은 불변(체인 필드는 상세·내보내기에만 추가).
- **성능 영향 요약**: 공개 대화 경로 = 출구 검사(메모리 호스트 비교 ≤0.1ms) + 암호화 1차 대상은 공개 대화 턴에 없음(상담 메시지·설문 자유 텍스트 적재 시 AES 1회 ≤0.1ms) · 감사 기록 = 직전 행 해시 조회 1회 + SHA-256 1회(NFR-DGP2) · 파기 잡 = 야간 창·배치·양보(NFR-DGP3).

### 1.10 목적

1. 규제 고객이 "우리 데이터는 **허용된 저장 위치**에만 있고 **허용된 곳으로만** 나간다"를 **콘솔 화면과 기동 검증**으로 증명할 수 있다.
2. 유일한 원문 저장소와 자유 텍스트 저장소가 **필드 단위로 암호화**되고, 키를 **교체**할 수 있다.
3. 대화·상담·설문 텍스트와 호출·감사 로그가 **정책화된 보존기간**이 지나면 자동으로 파기되고, 파기 사실이 **이력**으로 남으며, **수치 통계는 변하지 않는다.**
4. 감사로그가 **변조 탐지 가능**하고, 개인정보 화면 **열람·내보내기가 기록**된다.
5. 거버넌스 모드를 켜지 않은 설치는 **모든 동작이 바이트 단위로 동일**하고, 대화 엔진·위젯·ml-worker는 **수정하지 않는다.**

### 1.12 전체 흐름 (이 문서가 만드는 것)

```
■ 기동 (서버 설정 — DATA_GOVERNANCE_MODE=ON)
  DATABASE_URL 경로/호스트 ∈ DATA_RESIDENCY_ALLOWED_* ?     아니면 기동 실패
  EMBEDDING/RAG/AUGMENTATION 기본 URL 호스트 ∈ DATA_EGRESS_ALLOWED_HOSTS ?   아니면 기동 실패
  DATA_ENCRYPTION_ENABLED → 키링 파싱 · 옛 키 필요 행 존재 확인           키 누락이면 기동 실패

■ 데이터 지도 (security:read — 설정 > 데이터 거버넌스)
  저장 위치 · 디스크 암호화(운영 자기 신고) · 출구 5종(호스트·송신 데이터·마스킹·허용/차단)
  암호화 상태(대상 필드·평문 잔존·키별 행 수) · 보존 정책 · 최근 파기 · 체인 상태 · 평문 토큰 잔존(v1)

■ 공개 대화 · 관리자 동작 (모드 ON)
  외부 호출 직전 → EgressGuard.check(host)  → 차단이면 기존 실패 분기 + EGRESS_BLOCKED 메타 기록
  상담 메시지·설문 자유 텍스트 적재 → 금지어 → PII(모드별 강도) → AES-GCM → 저장
  개인정보 원천 화면 조회·내보내기 → AuditLog VIEW/EXPORT (열람자·리소스·일 1건)

■ 감사 기록 (항상)
  AuditLogService.record() → seq·prevHash·rowHash 계산 → 저장        (본문 규약 불변)

■ 보존 정책 (security:write · 재입력 확인 · 단축은 유예 7일)
  전역 기본 [대화 원천 4종 · 호출 로그 · 감사(≥하한)] + 챗봇별 재정의 → 감사 1건

■ 파기 잡 (PollingLoop · 임대 선점 · 야간 창 · 배치)
  대화 원천  → 텍스트 소거 + purgedAt   (행·수치 보존, secure_delete)
  호출 로그  → 행 삭제
  감사로그   → 하한 경과 행 삭제 → 체인 앵커 갱신
  → RetentionRun(대상·cutoff·건수·결과) + 감사 요약 1건

■ 재암호화 잡 (키 교체 · 백필)
  옛 키/평문 행 → 쓰기 키로 배치 재암호화 → 데이터 지도 잔존 0

■ 봉인 (CI 정적 검사)
  외부 HTTP 출구 5클래스 전부 EgressGuard 경유 · 대화 원천 소거는 1파일 · 로그 행 삭제 0 유지
  암호화 대상 컬럼 쓰기 파일 = 기존 쓰기 주체 그대로(암호화 함수 경유) · 키 값 로그·응답 0
  엔진·위젯·ml-worker 변경 0 · @Public() 8 유지
```

## 2. 사용자 역할 및 시나리오

### 2.1 역할

| 역할 | 이 그룹에서의 활동 | 권한(권고안 기준) |
|---|---|---|
| **운영자(서버 관리자)** | 환경변수로 모드·저장 경로·출구 허용 목록·키링·감사 하한 설정 · 디스크 암호화·키 백업 | 서버 접근(콘솔 권한 아님) |
| **ADMIN** | 데이터 지도 조회 · 보존 정책 설정 · 파기 이력 조회 · 감사 체인 검증 · 감사 내보내기 · 열람 감사 조회 | `security:read/write` · `audit:read`(기존) |
| **EDITOR · VIEWER · AGENT** | 변경 없음 — 거버넌스 모드에서 자신이 개인정보 화면을 열면 열람 감사가 남는다 · 소거된 행은 "파기됨"으로 보인다 | 기존 |
| 최종 사용자 | 변경 없음(위젯 동작 동일) | — |

### 2.2 사용자 시나리오

**S-1. 규제 모드 설치 (운영자 · ★)** 금융사 전산실 서버에 설치하며 `DATA_GOVERNANCE_MODE=ON`, `DATA_RESIDENCY_ALLOWED_DIRS=/secure/chatbot`, `DATA_EGRESS_ALLOWED_HOSTS=127.0.0.1,ml-worker.internal,legacy.bank.internal`을 설정한다. 실수로 `AUGMENTATION_PROVIDER=gemini`를 남겨 두자 서버가 "외부 전송 허용 목록에 없는 호스트(generativelanguage.googleapis.com) — 증강 생성기"를 이유로 **기동하지 않는다.**

**S-2. 데이터 지도로 심사 대응 (ADMIN · ★)** 감독기관 점검 전에 `설정 > 데이터 거버넌스`를 연다. "저장 위치: /secure/chatbot/prod.db(허용 경로)", "외부 전송: 임베딩(ml-worker.internal · 질의 원문 · 허용), 외부 RAG(미설정), 증강(규칙 기반 · 외부 전송 없음), 레거시 API 연결 3개(허용 3 · 차단 0)", "필드 암호화: 3개 필드 · 평문 잔존 0행 · 키 k2", "보존: 대화 180일 · 감사 5년", "감사 체인: 정상(마지막 검증 09-26 02:00)"을 캡처해 제출한다.

**S-3. 보존기간 설정 (ADMIN · ★)** 전역 대화 보존을 "무기한 → 180일"로 바꾼다. 미리보기에 "대화 로그 1,204,331행 · 설문 자유 텍스트 8,112건 · 상담 메시지 20,431건의 텍스트가 **10-03(유예 7일 후)부터** 파기됩니다. 통계 수치는 변하지 않습니다"가 나오고, "보존기간 단축"을 재입력해 저장한다. 감사 1건이 남는다.

**S-4. 챗봇별 재정의 (ADMIN)** "대출 상담봇"만 대화 보존 90일로 더 줄인다. 일반 안내봇은 전역 180일을 따른다.

**S-5. 자동 파기와 이력 (ADMIN)** 10-03 새벽 파기 잡이 돈다. `파기 이력`에 "10-03 02:00 · 대화 로그 · 전 챗봇 · 기준 04-06 이전 · 1,190,002행 소거 · 성공"이 남고, 통계 화면의 3월 대화 수는 그대로이며 질문 순위의 3월 항목은 집계에서 빠진다(파기됨).

**S-6. 감사 체인 검증 (ADMIN · ★)** `감사로그 > 무결성 검증`에서 지난 30일을 검증하면 "412,003행 · 정상 · 체인 머리 seq 1,882,410 / 해시 9f3a…"가 나온다. DB를 직접 수정한 행이 있으면 "seq 1,880,122에서 불일치 — 이후 행 신뢰 불가"로 표시된다.

**S-7. 열람 감사 (ADMIN)** 상담 이력 상세를 연 EDITOR의 기록이 `감사로그`에 "열람 · 상담 #a1b2 · EDITOR 박○○"로 하루 1건 남는다. 설문 응답 CSV 내보내기는 "내보내기 · 설문 '만족도' · 기간 09-01~09-25 · 3,204행"으로 남는다.

**S-8. 키 교체 (운영자)** 연 1회 정책에 따라 `DATA_ENCRYPTION_KEYS=k3:…,k2:…`로 바꾸고 재기동한다. 데이터 지도의 "k2 사용 행"이 재암호화 잡으로 줄어 0이 되면 k2를 제거하고 재기동한다. k2를 먼저 지웠다면 서버가 "k2가 필요한 행 12,033개"로 기동을 거부한다.

**S-9. 레거시 연결 차단 (ADMIN)** 허용 목록에 없는 `api.partner.com`으로 새 연결을 저장하려 하자 "외부 전송 허용 목록에 없는 호스트입니다(서버 설정 필요)"로 거부된다. 기존 연결이 목록에서 빠진 경우 호출은 실패 분기로 가고 호출 로그에 `EGRESS_BLOCKED`가 남는다.

**S-10. 모드 꺼진 일반 고객 (★)** 거버넌스 모드를 켜지 않은 구독형 고객은 모든 화면·API·통계가 이전과 같다. 데이터 지도는 "거버넌스 모드 꺼짐 — 외부 전송 통제·필드 암호화·열람 감사가 적용되지 않습니다"와 현재 상태를 읽기로 보여 준다.

### 4.13 이 그룹이 **하지 않는** 것 (범위 요약)

대화로그·미응답 큐 본문 암호화(2차) · KMS/HSM/Vault(2차) · 정보주체 파기 요청(2차) · SIEM·외부 봉인(2차) · 감사 전용 역할(2차) · 2인 승인(No.36) · 멀티테넌시(별도) · DB 계층 암호화 · 물리 리전 보증 · 백업 자동화 · 로그 포함 챗봇 영구삭제 · 질의 임베딩 마스킹 · 작은 표본 비공개 · 운영 테이블 정리.

## 7. 수용기준 (AC)

### AC-DG1. 범위 · 회귀 · 모드

- **AC-DG1-1** ★ Given 모드 OFF(기본) · 보존 정책 없음, When 전 시험 세트(공개 대화·설정·통계·상담·설문·평가·버전·환경·예약·감사)를 실행, Then 결과·응답 바이트·공개 경로 DB 조회 수가 도입 전과 같고 신규 컬럼(`textPurgedAt`)은 null이다. (감사 체인 컬럼은 채워지나 기존 목록 API 응답 모양은 같다.)
- **AC-DG1-2** Given 모드 OFF, Then 데이터 지도는 읽기로 열리고 "거버넌스 모드 꺼짐"이 표시된다.
- **AC-DG1-3** Given 저장소 전체, When `governance-sealing.spec.ts`, Then FR-DG9-4 단언 전부 통과(역검증 포함) · `@Public()` 8 · 엔진·위젯·ml-worker 변경 0.

### AC-DG2. 저장 위치 · 외부 전송

- **AC-DG2-1** ★ Given 모드 ON · `DATA_RESIDENCY_ALLOWED_DIRS=/a`, When `DATABASE_URL=file:/b/x.db`로 기동, Then 기동 실패(경로·허용 목록 표시 · 비밀 없음). `/a/x.db`는 성공. 심볼릭 링크로 `/a` 밖을 가리키면 실패.
- **AC-DG2-2** ★ Given 모드 ON · 허용 목록에 Gemini 호스트 없음, When `AUGMENTATION_PROVIDER=gemini`로 기동, Then 기동 실패. 목록에 추가하면 성공.
- **AC-DG2-3** ★ Given 모드 ON, When 목록 밖 호스트로 레거시 연결 저장, Then `400 EGRESS_HOST_NOT_ALLOWED`. 저장된 연결의 호스트를 목록에서 뺀 뒤 대화에서 호출, Then 송신 0(전송 목 확인) · 실패 분기 응답 · `ApiCallLog.outcome = EGRESS_BLOCKED`.
- **AC-DG2-4** Given 모드 ON · 임베딩 URL 허용, Then 의미 매칭이 도입 전과 같은 결과다. 데이터 지도에 "질의 원문 송신 · 허용"이 표시된다.
- **AC-DG2-5** Given 모드 OFF, Then `EgressGuard`가 호출돼도 조회·비교 없이 통과한다(단위 시험).

### AC-DG3. 필드 암호화

- **AC-DG3-1** ★ Given 암호화 ON, When 상담 사용자 메시지·설문 자유 텍스트 적재, Then DB 원시 값이 `enc:v1:` 접두 봉투이고 평문 부분 문자열이 없으며, 상담 스레드·원문 열람·설문 결과·CSV 응답은 **암호화 전과 같은 값**이다.
- **AC-DG3-2** Given 암호문을 다른 행의 같은 컬럼에 복사, When 조회, Then "[복호화 실패]" 표시 · 경고 로그(행 id·키 id만) · 요청 성공(AAD 검증).
- **AC-DG3-3** ★ Given 평문 1만 행 · 암호화 켜기, When 백필 잡 `tick()` 반복, Then 평문 잔존 0 · 데이터 지도 진행률 일치 · 그동안 공개 대화 로그 유실 0.
- **AC-DG3-4** ★ Given 키링 `k1`, When `k2:…,k1:…`로 재기동 후 재암호화 완료, Then 모든 행이 `k2` · 이후 `k1` 제거 재기동 성공. **재암호화 전에 `k1`을 제거하면 기동 실패**(필요 행 수 표시).
- **AC-DG3-5** Given 암호화 OFF로 전환, Then 신규 쓰기 평문 · 기존 암호문 정상 조회 · 데이터 지도 잔존 경고.
- **AC-DG3-6** Given 상담 종료, Then `rawText` 소거가 암호화 여부와 무관하게 동작한다(ADR-0036 시험 불변).
- **AC-DG3-7** Given 어떤 경로의 로그·오류·응답, Then 키 값 문자열 0(정적·동적 검사).

### AC-DG4. 보존 정책

- **AC-DG4-1** ★ Given 전역 대화 무기한, When 180일로 단축 저장(확인 문자열 일치), Then 정책 = 적용 예정(지금+7일) · 미리보기 건수 = 실제 대상 수 · 감사 1건. 확인 불일치는 `400`.
- **AC-DG4-2** Given 감사 보존 하한 365, When 콘솔에서 300일 저장, Then `400 RETENTION_BELOW_MINIMUM`.
- **AC-DG4-3** Given 유예 중, When 취소, Then 정책 원복 · 감사 1건 · 파기 없음.
- **AC-DG4-4** Given 챗봇 A 재정의 90일 · 전역 180일, Then A는 90일, B는 180일 기준으로 계산된다(순수 함수 시험 — 시각 주입).
- **AC-DG4-5** Given 챗봇 복사·토픽 분리, Then 새 챗봇에 재정의가 없다.

### AC-DG5. 파기 잡 · 이력

- **AC-DG5-1** ★ Given 기준 시각 이전 대화 로그 N행, When 파기 `tick()`, Then 해당 행 `userMessage`·`botResponse` = 빈 값 · `textPurgedAt` 설정 · **행 수·`dayBucket`·`sessionId`·`groupId`·매칭 id 불변** · 행 삭제 0.
- **AC-DG5-2** ★ Given 소거 전후, When 대시보드·기간 통계·통합 통계(턴·세션·응답률·출처·시간대)·설문 분포·상담 건수 조회, Then **수치가 동일**하다. 질문 순위에서는 소거 행이 빠지고 빈 문자열 항목이 나타나지 않는다.
- **AC-DG5-3** Given 호출 로그·감사로그 기준 이전 행, When 파기, Then 행 삭제 · 감사 앵커 갱신(같은 트랜잭션) · 이후 체인 검증 정상.
- **AC-DG5-4** Given 2인스턴스, When 동시에 `tick()`, Then 파기는 1인스턴스만 실행(임대).
- **AC-DG5-5** Given 1회 상한 초과 대상, Then `PARTIAL` 이력 · 다음 창에서 이어서 처리.
- **AC-DG5-6** Given 파기 실행, Then 이력 1행(대상·cutoff·건수·결과) · 감사 요약 1건 · 이력·감사에 본문·행 id 목록 0.
- **AC-DG5-7** Given 실행 창 밖, Then `tick()`이 아무것도 하지 않는다.
- **AC-DG5-8** Given 파기 중 공개 대화 부하, Then NFR-DGP3(P95 < 20% · 로그 유실 0) 측정 기록.
- **AC-DG5-9** Given 봉인 spec, Then 소거 서비스 1파일만 허용 목록에 있고, 다른 파일에 로그 `update`를 넣은 임시 사본은 실패한다(역검증).

### AC-DG6. 감사 무결성

- **AC-DG6-1** ★ Given 체인 도입 후 기록 1,000건, When 검증, Then 정상. 임의 행의 `summary`를 DB에서 직접 수정, Then "불일치(첫 seq)". 중간 행 삭제, Then "순번 결손".
- **AC-DG6-2** Given `AUDIT_CHAIN_KEY` 설정, Then 키 없이 재계산한 해시와 달라 "키 없는 재계산"으로는 정상 판정을 만들 수 없다(단위 시험).
- **AC-DG6-3** Given 동시 감사 기록 50건(병렬 요청), Then `seq` 중복·결손 0 · 체인 정상.
- **AC-DG6-4** Given 도입 전 행, Then 검증 결과에 "체인 이전 N행" · 제네시스 앵커 1건.
- **AC-DG6-5** Given 기존 감사 목록 API, Then 응답 모양 불변(체인 필드는 상세·내보내기만).

### AC-DG7. 열람 · 내보내기 감사

- **AC-DG7-1** ★ Given 모드 무관, When 설문 응답 CSV·감사로그 CSV·TC 결과 내보내기, Then 각 `EXPORT` 감사 1건(대상·기간·행 수 · 검색어 원문 없음). FAQ 내보내기는 기록 없음.
- **AC-DG7-2** ★ Given 모드 ON, When EDITOR가 같은 상담 이력 상세를 하루에 10번 열고 대화 보기 폴링이 100회, Then `VIEW`는 (열람자·리소스·일)당 1건.
- **AC-DG7-3** Given 모드 OFF, Then `VIEW`는 기록되지 않는다(`EXPORT`는 기록).
- **AC-DG7-4** Given 감사로그 내보내기, Then 파일에 `seq`·`rowHash` 열과 구간 검증 결과·체인 머리가 있다.

### AC-DG8. 권한 · 마스킹 강도

- **AC-DG8-1** ★ Given EDITOR, When 데이터 지도·보존 정책·파기 이력·체인 검증, Then `403` · 감사 `PERMISSION_DENIED`(기존 규약).
- **AC-DG8-2** Given ADMIN, Then 콘솔에 모드·출구 목록·암호화·키·하한을 **바꾸는 컨트롤이 없다**(읽기 표시만).
- **AC-DG8-3** Given `PII_MASK_MODE=FULL`, When `010-1234-5678`·`a@b.com` 포함 발화 적재, Then 로그·설문·상담 저장값이 `[전화번호]`·`[이메일]` · 과거 행은 불변. `PARTIAL`(기본)은 도입 전과 바이트 동일.
