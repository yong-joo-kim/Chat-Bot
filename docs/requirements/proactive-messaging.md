## 0. 쉬운 말 요약 — 왜 필요한가, 무엇이 달라지나, 안 해도 되는 경우

### 0.1 지금은 사용자가 먼저 말을 걸어야만 대화가 시작된다 (코드 근거)

| 사실 | 근거 (파일:행) |
|---|---|
| 웹 위젯은 **사용자가 런처(말풍선 버튼)를 눌러야** 서버에서 챗봇 설정을 받아 오고, 그때 인사말과 빠른 선택 버튼을 보여 준다. 누르기 전에는 서버에 아무 요청도 보내지 않는다 | `apps/widget/src/ui/app.ts` 413~434행(`handleOpen` — 426행 `client.getConfig()` · 431행 `renderGreeting`) · 256행(런처 클릭 → `handleOpen`) |
| 예외는 전체 화면 모드(`data-fullscreen="true"`)뿐이다 — 처음부터 창이 열린 상태로 시작한다. 이것도 "봇이 먼저 말 거는" 것이 아니라 **창이 이미 열려 있는** 것이다 | `apps/widget/src/loader.ts` 36·45행 · `app.ts` 642~644행 |
| 인사말(`greetingMessage` ≤200자)과 빠른 선택(`quickReplies` ≤5개)은 이미 있다. 단 **창을 연 뒤에만** 보이고 서버 대화 기록에는 남지 않는다(위젯이 화면에만 그림) | `packages/shared-types/src/channel.ts` 67~68행 · `apps/widget/src/core/store.ts` 64~78행 · `app.ts` 397~411행 |
| 서버의 대화 요청은 **사용자 입력(글자) 또는 버튼 선택 중 정확히 하나**가 있어야 받아들인다. "봇이 먼저 말하기" 요청 형식은 없다 | `packages/shared-types/src/conversation.ts` 258~278행(`PublicMessageRequestSchema` — 269~276행 "정확히 하나") |
| 대화 엔진도 입력이 "글자" 또는 "특정 대화 노드로 가는 버튼" 중 하나일 때만 턴을 만든다 | `packages/dialogue-engine/src/turn.ts` 55~89행(`resolveTurn`) |
| 서버는 대화 상태를 저장하지 않는다(브라우저가 들고 다님). 서버가 위젯 쪽으로 먼저 보내는 통로는 **상담원 연결 중 짧은 폴링**과 **보류 답변 폴링**뿐이다 | `docs/02-spec/decisions/ADR-0009-client-held-conversation-state.md` 20~22행 · `apps/api/src/conversation/public-conversation.controller.ts` 74~109행 |
| 카카오톡·네이버 톡톡 등 외부 채널은 **설정만 저장**할 수 있고, 메시지를 주고받는 구현은 웹(`WEB`)뿐이다. 다른 채널로 대화를 처리하려 하면 `409 CHANNEL_NOT_IMPLEMENTED` | `packages/shared-types/src/channel.ts` 24~33행 · `apps/api/src/conversation/adapters/channel-adapter.factory.ts` 15~21행 |

→ 즉 **지금 "봇이 먼저 말 걸기"가 기술적으로 가능한 곳은 사용자가 보고 있는 웹 페이지 안(웹 위젯)뿐**이다. 카카오 알림톡·문자처럼 사용자가 사이트에 없을 때 먼저 보내는 것은 채널 연동 자체가 없어 불가능하다.

### 0.2 있으면 누가 무엇을 얻나 (수치 주장 없음)

| 누가 | 지금 | 규모 A 이후 |
|---|---|---|
| **최종 사용자(방문자)** | 도움이 필요해도 챗봇이 있는지 모르거나, 런처를 눌러야 한다는 것을 모르면 그냥 떠난다 | 오래 머무는 페이지·결제 실패 페이지 등에서 "배송 조회를 도와드릴까요?" 같은 **짧은 제안**을 보고 한 번 눌러 바로 해당 안내로 들어간다. 원치 않으면 닫으면 다시 안 뜬다 |
| **최종 사용자(대화 중)** | 챗봇이 연속으로 답을 못 해도 계속 같은 "이해하지 못했어요"를 본다 | 연속 N회 못 알아들으면 "자주 묻는 메뉴 보기 / 상담 안내" 같은 **탈출구 제안**이 한 번 붙는다 |
| **챗봇 운영자(편집자)** | 방문자가 문의를 포기하기 전에 개입할 방법이 없다 | 규칙(어느 페이지 · 몇 초 · 어떤 문구 · 누르면 어느 대화로)을 콘솔에서 만들고 켜고 끈다. **표시·클릭·닫기 수**로 "도움이 되는지, 성가신지"를 본다 |
| **상담 부서** | — | 제안 버튼을 상담 안내 노드로 연결하면 문의 유입 경로가 하나 늘어난다(실제 상담 연결은 기존 No.24 방식 그대로 — 사용자 요청형 상담 연결은 여전히 없음) |
| **서버 운영자** | — | 변화 거의 없음(새 환경변수는 전부 선택 · 기본값에서 동작 불변) |

**몇 %가 전환되는지, 이탈이 줄어드는지는 실측 전 모른다.** 그래서 1차에 **측정(표시·클릭·닫기)** 을 함께 넣는 것을 권고한다(P-4).

### 0.4 이 기능 없이 충분한 경우 (정직하게)

- **고객이 스스로 문의하러 오는 사이트**(고객센터 전용 페이지 · 사내 헬프데스크 · 민원 안내처럼 방문 목적이 곧 문의인 곳) — 런처가 잘 보이면 선제 안내의 이득이 작다.
- **"챗봇이 여기 있어요"를 알리는 것만 필요한 경우** — 이미 있는 인사말·빠른 선택 버튼(`channel.ts` 67~68행)과 런처 위치 설정으로 충분할 수 있다. 사이트 쪽에서 런처 근처에 "궁금한 점은 챗봇에게" 같은 문구를 직접 두는 방법도 있다(우리 쪽 개발 0).
- **외부 메시지 채널(카카오톡 등)로 먼저 보내는 것이 진짜 목적인 경우** — 규모 A는 이 목적을 **전혀** 채우지 못한다. 채널 실연동(No.42 2차 — ADR-0042 144행)이 먼저다. 이 경우엔 **지금은 하지 않음**이 맞다.
- **"이탈을 예측해서 막는다"를 기대하는 경우** — 규모 A는 규칙 기반 추정일 뿐 예측이 아니다(§0.5). 기대치를 맞추지 못하면 만들어도 실망이 크다.
- **방문자 수가 적은 사이트** — 표시·클릭 수가 너무 적어 효과를 판단하기 어렵다.

→ 그래서 §11 P-1에 **"지금은 하지 않음"** 선택지를 둔다. 반대로 **특정 페이지(결제·신청서·오류 화면 등)에서 사용자가 막혀 떠나는 일이 알려져 있고, 그 페이지에 챗봇이 도울 수 있는 대화가 준비돼 있다면** 규모 A의 가치가 분명하다.

| 대화 로그 1행 = 사용자 턴 1건 · 입력 유형 `TEXT·BUTTON_MESSAGE·BUTTON_NODE`(`apps/api/prisma/schema.prisma` 472~540행 — `inputKind` 534행) | 말풍선 **표시만으로는** 로그가 생기지 않게 한다(FR-0-240) — 방문·턴·미응답 통계 불변 |
| 응답의 선택 키 선례: `pendingAnswer`·`handoff`·`feedback`는 해당 턴에만 존재하고 없으면 바이트 동일(`conversation.ts` 315~339행) | "대화 중 연속 미응답" 제안은 같은 방식의 **선택 키 1개**로 싣는다(FR-PA2-6) — 구버전 위젯은 키를 모르므로 무시 |
| 연속 미응답 계산 1벌이 이미 있다(`session-alert.ts` 25행 `evaluateSessionAlert` — No.24 경고 · No.41 `streak.ts` 8~12행이 재사용) | 같은 계산식을 쓴다(화면·웹훅·선제 제안의 수치 일치 — FR-PA2-5) |

**결론**: "사용자가 아무것도 하지 않았는데 **서버가 봇 턴을 만들어 기록**하는 것"은 새 엔진 진입점·로그 의미 변경이 필요해 비용이 크다. 규모 A는 **"말풍선은 화면 표시일 뿐, 사용자가 누를 때 평범한 턴이 시작된다"**로 설계해 이 비용을 피한다(J-3).

| 선택지 | 동작 | 개인정보·원칙 | 판정 |
|---|---|---|---|
| **(a) 탭 세션 동안만 기억(`sessionStorage`)** ★ | 닫거나 "이번 방문 동안 안내 끄기"를 누르면 **그 탭을 닫을 때까지** 다시 안 뜬다. 새 탭·재방문이면 다시 뜰 수 있다(세션당 상한은 다시 적용) | 현행 원칙 유지(`session.ts` 3~6행 — localStorage·쿠키 0) · 브라우저에 오래 남는 기록 0 · 추가 고지 불필요로 보임(법무 확인 권장) | **권고** — 원칙을 바꾸지 않는다. 대신 버튼 문구를 **"이번 방문 동안 안내 끄기"**로 정직하게 쓴다("다시 보지 않기" 금지 — 지키지 못할 약속이 된다) |
| (b) 며칠 동안 기억(`localStorage`에 "닫음 기록"만 — 규칙 id·만료 시각 · 식별자 0) | 닫으면 N일(예: 7일) 동안 같은 브라우저에서 안 뜬다 | ★ 위젯 원칙(NFR-S8) **변경** · 단말기에 정보를 저장하는 것에 대한 고지·동의 필요 여부 **법무 확인 필요** · 사이트가 끌 수 있어야 함 | 대안 — 재방문 반복 노출 불만이 확인되면(재검토 트리거) |
| (c) 서버가 방문자를 알아보고 기억(쿠키·지문) | 서버에 방문자별 닫음 기록 | 방문자 추적이 된다 — 개인정보 부담 큼 | 비권고 |

### 1.7 ★ 선결 쟁점 4 — 효과를 어떻게 잴까 (통계, P-4)

| 선택지 | 무엇을 셈 | 새 공개 주소 | 판정 |
|---|---|---|---|
| **(a) 표시·클릭·닫기·"안내 끄기" 수를 규칙별·일별 숫자로만** ★ | 브라우저가 보고한 사건을 서버가 검증 후 **카운터만 증가**(세션 id·주소·IP·시각 원본 저장 0) · 클릭률·닫기율 계산 | +1(`@Public()` 8 → 9) — 전용 버킷·결합 검증·중복 억제 | **권고** — "도움이 되는지, 성가신지"를 **닫기율**로만 알 수 있다. 측정 없이 켜 두면 R-1을 모른 채 방치하게 된다 |
| (b) 클릭(대화 시작)만 | 클릭 시 보내는 대화 요청에 규칙 표식을 실어 서버가 셈 | 0 | 대안 — 표시 수를 몰라 클릭률·닫기율을 계산할 수 없다 |
| (c) 측정 안 함 | — | 0 | 비권고 — 효과·성가심 판단 근거 없음 |

### 1.8 ★ 선결 쟁점 5 — 어떻게 띄울까 (표시 방식, P-5)

| 선택지 | 동작 | 판정 |
|---|---|---|
| **(a) 런처 옆 작은 말풍선만 · 대화 창 자동 열기 없음 · 휴대폰은 규칙별 선택(기본 끔)** ★ | 말풍선(문구 + 버튼 ≤3 + 닫기). 포커스·스크롤을 건드리지 않는다. 버튼을 누르면 그때 창이 열리고 대화가 시작된다 | **권고** — 사용자가 하던 일을 끊지 않는다(UIUX 준수기준 §3·§7 48행 "포커스 이동만으로 팝업 금지" 취지) |
| (b) 조건이 맞으면 대화 창을 자동으로 연다 | 창이 열리고 봇 문구가 창 안에 보임 | 비권고 — 포커스를 빼앗거나 화면을 가린다. 휴대폰에서는 창이 화면 전체를 덮는다(`app.ts` 37~38행 — `mobile` 모드는 뷰포트 전체) |
| (c) (a)와 같되 휴대폰도 기본 켬 | — | 대안 — 휴대폰 화면에서 본문을 가리는 문제를 감수 |

### 1.10 목적

1. 운영자가 **특정 페이지·사건·대화 실패** 순간에 챗봇이 먼저 짧게 도움을 제안하게 할 수 있다.
2. 사용자는 제안을 **무시·닫기·끄기**를 한 번에 할 수 있고, 하던 일(읽기·입력·화면 낭독)을 방해받지 않는다.
3. 제안은 **아무것도 기록하지 않는다** — 사용자가 누를 때 평범한 대화가 시작되고, 그때부터 기존 규칙(로그·마스킹·통계)이 적용된다.
4. 운영자는 규칙별 **표시·클릭·닫기** 수로 도움이 되는지 성가신지 판단한다.
5. 기능을 쓰지 않으면(챗봇 스위치 꺼짐 · 규칙 0 · 사이트 삽입 코드에 사용 표시 없음) 시스템 동작이 **바이트 단위로 동일**하다.

| FR-PA3-9 | 휴대폰 표시(규칙에서 허용한 경우)에서 말풍선은 화면 아래 영역의 일부만 차지하며(최대 높이는 ui-designer) 본문 입력 필드를 가리지 않도록 가상 키보드가 열려 있으면 표시를 미룬다 |

### 4.4 빈도 · 재노출 억제 · 기간 · 시간대 — J-5

| ID | 요구사항 |
|---|---|
| FR-PA4-1 | **세션당 최대 표시 수**(FR-PA1-1)와 **안내 사이 최소 간격**을 넘지 않는다. 세션 = 위젯 대화 세션(`cb.sid.{slug}` — 탭 단위 `sessionStorage`) |
| FR-PA4-2 | 사용자가 닫은 규칙은 **같은 세션에서 다시 표시하지 않는다**. "이번 방문 동안 안내 끄기"를 누르면 그 세션에서 **모든** 체류·신호 안내를 표시하지 않고, 연속 미응답 제안도 붙이지 않는다(위젯이 기능 선언에서 `proactive-v1`을 빼거나 동등한 방식 — architect) |
| FR-PA4-3 | 노출·닫음·끄기 기록은 P-3 결과의 저장소에만 둔다((a) = `sessionStorage` · 저장 불가 환경은 메모리 폴백 — `session.ts` 선례) |
| FR-PA4-4 | **게시 기간**: 시작 전·종료 후 규칙은 서버가 내려보내지 않는다. **표시 시간대**(선택 — 요일 + 시작·종료 시각, KST): 서버가 조회 시점 기준으로 판정해 시간대 밖이면 내려보내지 않고, 위젯은 받은 규칙의 **표시 가능 종료 시각**이 지나면 표시하지 않는다(탭을 오래 열어 둔 경우) |
| FR-PA4-5 | **대화 창이 열려 있거나**, 이 세션에서 사용자가 이미 메시지를 보냈고 마지막 전송 후 N분(기본 5분) 이내면 체류·신호 말풍선을 표시하지 않는다(대화를 끊지 않음) |
| FR-PA4-6 | **상담원이 연결된 동안**(서버: 이 세션의 활성 상담 · 위젯: `handoff` 모드 `CONNECTED` — `store.ts` 34행)에는 모든 선제 안내와 연속 미응답 제안을 억제한다. 연결 전 관찰 상태(`WATCHING`)는 억제 대상이 아니다(EX-PA-19) |
| FR-PA4-7 | 위젯이 비활성(`DISABLED`)·챗봇 공개 중지·WEB 채널 꺼짐이면 규칙 조회 결과가 비고 아무것도 표시하지 않는다 |

### 4.5 서버 판정 · 위젯 ↔ 서버 프로토콜 · 남용 방지 — J-9 · J-10

| ID | 요구사항 |
|---|---|
| FR-PA5-1 | 위젯은 **삽입 코드에 선제 안내 사용 표시가 있을 때만**(속성 이름은 architect — 예: `data-proactive="on"`) 페이지 로드 시 규칙을 1회 조회한다. 표시가 없으면 현행처럼 런처 클릭 전 요청 0 |
| FR-PA5-2 | 규칙 조회 응답에는 위젯이 판정에 필요한 것만 담는다: 규칙 id · 트리거 종류와 조건(경로 패턴·초·신호 이름) · 문구 · 버튼(동작·라벨·노드 id·문장·주소) · 기기 · 표시 가능 종료 시각 · 챗봇 단위 상한·간격. **규칙 이름·게시 기간 원본·수정자·통계·연속 미응답 규칙은 싣지 않는다**(연속 미응답은 서버 전용) |
| FR-PA5-3 | 수집 사건(P-4 (a))은 `{ sessionId(uuid), ruleId(uuid), kind: SHOWN｜CLICKED｜DISMISSED｜OPTED_OUT }`만 받는다. 페이지 주소·체류 시간·신호 이름·사용자 문자열·리퍼러를 **받는 필드 자체가 없다**(zod `strict`) |
| FR-PA5-4 | 서버는 수집 사건을 **슬러그의 챗봇 · 켜진 규칙 · 지금 유효한 규칙**과 결합 검증하고, 맞지 않으면 조용히 무시(응답은 성공과 같은 형태 — 존재 여부 탐지 방지)한다. Origin 가드는 현행 규칙 그대로 적용 |
| FR-PA5-5 | 규칙 조회와 수집 사건은 대화 전송의 `ip`·`session` 버킷을 **소비하지 않고** 각자 전용 버킷을 쓴다(No.44 `FEEDBACK` 선례 — `public-rate-limit.guard.ts` 25~28행). 한도 기본값·환경변수 이름은 architect |
| FR-PA5-6 | 같은 `(sessionId, ruleId, kind)`는 **1회만** 센다(메모리 중복 억제 · TTL = 세션 상한 시간 — 인스턴스별 근사). `CLICKED`·`DISMISSED`·`OPTED_OUT`은 `SHOWN` 없이 와도 세되 통계 화면의 비율 계산에서 분자가 분모를 넘지 않게 상한 처리한다 |
| FR-PA5-7 | 수집 경로는 응답 본문이 없거나 고정이며, 실패해도 위젯 동작(표시·대화)에 영향이 없다(보내고 잊기 · 재시도 없음) |
| FR-PA5-8 | 규칙 조회 응답은 짧게 캐시할 수 있게 한다(예: `Cache-Control: max-age` 수십 초 — 값은 architect). 규칙을 끄거나 고친 뒤 반영까지 걸리는 최대 시간을 콘솔에 안내한다 |

### 5.2 출력 — 공개 규칙 조회(개요)

### 5.3 출력 — 공개 메시지 응답 선택 키(연속 미응답 제안)

### AC-PA3. 트리거 · 표시(위젯)

- **AC-PA3-1** Given 규칙(경로 `/order/**` · 30초 · 데스크톱), When `/order/123`에서 탭이 보이는 상태로 29초가 지나면, Then 말풍선이 없다. When 30초가 되면, Then 말풍선이 1개 보이고 `SHOWN` 수집 요청이 1건 나간다.

- **AC-PA3-4** Given `HOST_SIGNAL` 규칙(`payment_failed`), When 호스트가 `signal('payment_failed')`를 호출하면, Then 말풍선이 표시된다. When `signal('Payment Failed!')` 또는 `signal('payment_failed', {card: '1234'})`를 호출하면, Then 앞의 것은 무시되고 뒤의 것은 인자를 버리고 이름만 처리한다(수집 요청 본문에 신호 이름·인자가 없다).

- **AC-PA3-10** Given 기기 = 데스크톱만인 규칙, When `data-mode="mobile"`에서 조건이 맞으면, Then 표시되지 않는다.

### AC-PA4. 빈도 · 억제 · 기간 · 시간대

- **AC-PA4-1** Given 세션당 최대 1 · 규칙 2개가 모두 조건 충족, When 두 번째 조건이 맞으면, Then 두 번째는 표시되지 않는다.
- **AC-PA4-2** Given 규칙 A를 닫은 세션, When 같은 탭에서 A 조건이 다시 맞으면(다른 페이지 이동 후), Then 표시되지 않는다. Given 새 탭(새 `sessionStorage`), Then 표시될 수 있다(P-3 (a)).
- **AC-PA4-3** Given "이번 방문 동안 안내 끄기"를 누른 세션, When 다른 규칙 조건이 맞거나 대화 중 연속 미응답 임계에 도달하면, Then 말풍선도 제안도 없다.
- **AC-PA4-4** Given 패널이 열린 상태, When 조건이 맞으면, Then 표시되지 않는다. Given 사용자가 2분 전 메시지를 보낸 뒤 패널을 닫음(억제 5분), Then 표시되지 않는다.
- **AC-PA4-5** Given 상담 연결 중(`handoff` 모드 `CONNECTED`), When 조건이 맞으면, Then 표시되지 않고 연속 미응답 제안도 붙지 않는다.
- **AC-PA4-6** Given 게시 종료 시각이 지난 규칙, When 규칙을 조회하면, Then 그 규칙이 응답에 없다. Given 표시 시간대(평일 09~18시 KST)와 서버 시각 토요일 10시, Then 없다.
- **AC-PA4-7** Given 조회 시 받은 규칙의 `showUntil`이 지난 뒤 조건 충족, When 판정하면, Then 표시되지 않는다.
- **AC-PA4-8** Given 상담(No.24)이 켜진 챗봇 · 연속 미응답 임계 3 규칙 · 상담원 미연결, When 세 번째 미응답 턴 응답을 받으면, Then 응답에 상담 관찰 키(`handoff`)와 선제 제안 키가 **함께** 있고 위젯은 둘 다 처리한다.

### AC-PA5. 서버 판정 · 프로토콜 · 남용 방지

- **AC-PA5-1** Given 선제 안내 요청 표시가 있는 조회, When 응답을 스키마 검사하면, Then 규칙 이름·게시 기간 원본·수정자·연속 미응답 규칙 키가 없다.
- **AC-PA5-2** Given 수집 요청 본문에 `url` 필드 추가, When 전송하면, Then `400`이다(`strict`).
- **AC-PA5-3** Given 다른 챗봇의 규칙 id · 꺼진 규칙 id · 없는 id, When 수집을 보내면, Then 응답은 정상과 같은 형태이고 카운터가 변하지 않는다.
- **AC-PA5-4** Given 같은 `(sessionId, ruleId, SHOWN)`, When 5번 보내면, Then 카운터는 1 증가한다.
- **AC-PA5-5** Given 수집 전용 버킷 한도 초과, When 같은 IP에서 대화 메시지를 보내면, Then 대화는 429가 아니다(버킷 분리).
- **AC-PA5-6** Given `PROACTIVE_ENABLED=false`(동적 import로 로드), When 조회·메시지·수집을 호출하면, Then 조회 결과에 규칙이 없고 제안이 0이며 카운터가 변하지 않는다.
- **AC-PA5-7** Given 연속 미응답 임계 3 규칙, When 한 세션에서 미응답 3회 → 4회 → 5회, Then 제안은 3회째 응답에만 있다. When 이후 답변 성공 1회 뒤 다시 미응답 3회, Then 그 3회째에 다시 1번 있다.
- **AC-PA5-8** Given 연속 미응답 제안이 붙은 턴, When 대화 로그를 조회하면, Then `botResponse`·`isAnswered`·매칭 필드가 제안이 없는 경우와 같다.

### AC-PA6. 통계

- **AC-PA6-1** Given 규칙 A의 오늘 표시 10 · 클릭 3 · 닫기 5, When 통계를 조회하면, Then 클릭률 30% · 닫기율 50%와 일별 표가 반환된다.
- **AC-PA6-2** Given 표시 120 · 닫기 70, When 규칙 목록을 보면, Then "사용자가 자주 닫는 안내" 안내가 있고 규칙은 켜진 상태 그대로다.
- **AC-PA6-3** Given 규칙 삭제, When 통계를 조회하면, Then 삭제 전 카운터가 이름 스냅샷과 함께 남는다.
- **AC-PA6-4** Given 카운터 저장 테이블, When 스키마를 검사하면, Then 세션 id·IP·주소 컬럼이 없다.
- **AC-PA6-5** Given 선제 안내 사용 전후 같은 대화, When No.14 대시보드·No.29 통합 통계를 조회하면, Then 수치가 같다(버튼 클릭으로 시작된 대화만 현행 규칙대로 산입).

### AC-PA7. 거버넌스 · 보안

- **AC-PA7-1** Given 거버넌스 모드 ON, When S-1을 수행하면, Then 동작이 같고 외부 송신이 0건이다.
- **AC-PA7-2** Given 데이터 지도 조회, When 선제 안내 규칙이 있으면, Then FR-PA7-4의 세 행이 있다.
- **AC-PA7-3** Given 문구에 `<img src=x onerror=alert(1)>`, When 위젯이 표시하면, Then 텍스트로 보이고 요소가 생성되지 않는다.
- **AC-PA7-4** Given 전역 금지어가 포함된 문구, When 저장하면, Then `400`이다.
- **AC-PA7-5** Given 1만 자 길이의 경로 패턴과 악의적 반복 문자열 주소, When 매칭을 1,000회 수행하면, Then 선형 시간 안에 끝난다(시간 상한 시험).

### AC-PA8. 콘솔 · 접근성

- **AC-PA8-1** Given 말풍선, When 키보드 Tab만으로 이동하면, Then 버튼·닫기·끄기에 순서대로 도달하고 Esc로 닫으면 포커스가 런처로 간다.
- **AC-PA8-2** Given 말풍선 표시, When 접근성 트리를 검사하면, Then 패널 밖 상태 알림 영역에 안내 문구가 1회 기록되고, 이후 조작 없이 다시 기록되지 않는다.
- **AC-PA8-3** Given 콘솔 규칙 편집, When 키보드만으로 규칙을 만들고 우선순위를 위/아래 버튼으로 바꾸면, Then 성공하고 오류 시 인라인 오류가 읽힌다.
- **AC-PA8-4** Given 미리보기, When 표시하면, Then 수집 요청이 0건이다.
- **AC-PA8-5** Given `channel:read` 사용자, When 선제 안내 탭을 열면, Then 편집 컨트롤이 비활성이다.

### AC-PA9. 배포 관계

- **AC-PA9-1** Given `NODE` 버튼이 가리키는 노드를 삭제, When 규칙을 조회하면, Then 그 규칙 전체가 응답에 없고 콘솔 목록에 "연결 대상 없음" 경고가 있다.
- **AC-PA9-2** Given 환경 모드 챗봇 · 노드가 초안에만 있고 운영 버전에는 없음, When 공개 조회, Then 그 규칙이 없다. When 운영 전환 후, Then 있다.
- **AC-PA9-3** Given 버전 복원(No.25) 실행, When 규칙 목록을 조회하면, Then 규칙이 복원 전과 같다.

### 11.1 AskUserQuestion용 쉬운 문구(핵심 6건)

**Q1. 챗봇이 먼저 말을 거는 기능을 이번에 만들까요? 만든다면 어디까지 할까요?** (지금은 방문자가 챗봇 버튼을 눌러야만 대화가 시작됩니다. 챗봇이 먼저 말을 걸 수 있는 곳은 현재 사이트 화면 안뿐이고, 카카오톡·문자로 먼저 보내는 연결은 아직 없습니다)
- ① **작게: 사이트 화면 안에서만. 관리자가 정한 조건(이 페이지에 30초 머묾 · 사이트가 "결제 실패" 같은 순간을 알려 줌 · 대화 중 챗봇이 연달아 못 알아들음)에 맞으면 챗봇 버튼 옆에 짧은 안내를 띄우고, 누르면 그 대화로 시작. 사이트 삽입 코드에 한 줄 추가가 필요 (추천)**
- ② 크게: ①에 더해 회사 시스템에서 일이 생기면(예: 결재 승인) 지금 보고 있는 사람에게 먼저 알려 주기, 로그인한 고객만 골라 말 걸기 — 서버 구조를 크게 바꿔야 함
- ③ 아주 크게: ②에 더해 카카오톡·문자로 먼저 보내기 — 채널 연결, 수신 동의 관리, 법무 검토가 먼저 필요
- ④ 지금은 하지 않기 — 고객이 스스로 문의하러 오는 사이트라면 지금의 인사말·빠른 버튼으로 충분

**Q2. 어떤 순간에 챗봇이 먼저 말을 걸게 할까요?**
- ① **세 가지: 특정 페이지에 일정 시간 머물 때, 사이트가 알려 주는 순간(결제 실패 등), 대화 중 챗봇이 연달아 답을 못 했을 때 (추천)**
- ② ①에 더해 화면을 많이 내렸을 때, 마우스가 창 밖으로 나가 떠나려 할 때 — 탭을 바꾸려고 마우스를 올리기만 해도 반응해 엉뚱한 때 뜨기 쉬움, 휴대폰에서는 안 됨
- ③ 특정 페이지에 일정 시간 머물 때만

**Q3. 방문자가 안내를 닫으면, 언제까지 다시 안 보이게 할까요?**
- ① **그 브라우저 탭을 닫을 때까지. 다시 방문하면 다시 보일 수 있음. 방문자 브라우저에 오래 남는 기록을 두지 않는 지금 원칙 유지. 버튼 이름도 "이번 방문 동안 안내 끄기"로 정직하게 (추천)**
- ② 며칠 동안 — 방문자 브라우저에 "닫음" 기록을 며칠 남김. 지금 원칙을 바꾸는 것이라 법무 확인 필요
- ③ 서버가 방문자를 알아보고 기억 — 방문자를 추적하는 셈이라 추천하지 않음

**Q4. 안내가 도움이 되는지, 성가신지 어떻게 확인할까요?**
- ① **안내별로 하루에 몇 번 보였고, 몇 번 눌렸고, 몇 번 닫혔는지 숫자만 셈. 누가 봤는지는 기록하지 않음. 이를 위해 인증 없이 받는 창구가 하나 늘어남 (추천)**
- ② 눌러서 대화를 시작한 횟수만 셈 — 창구는 안 늘지만 몇 번 보였는지 몰라 "성가신지"는 알 수 없음
- ③ 재지 않음

**Q5. 안내를 어떻게 띄울까요?**
- ① **챗봇 버튼 옆에 작은 말풍선만. 대화창을 저절로 열지 않고, 보고 있던 화면이나 입력 칸을 건드리지 않음. 휴대폰은 안내마다 켤지 정하고 기본은 끔 (추천)**
- ② 조건이 맞으면 대화창을 저절로 열기 — 하던 일을 끊고, 휴대폰에서는 화면 전체를 가림
- ③ ①과 같되 휴대폰도 기본으로 켬 — 작은 화면에서 본문을 가릴 수 있음

**Q6. 안내 문구에 할인·이벤트 같은 홍보 내용을 넣어도 될까요?** (홍보성 안내는 광고 관련 법 적용 여부를 법무에 확인해야 합니다)
- ① **이번에는 "이용 도움" 안내로만 쓰기. 저장할 때 "광고 목적 아님"을 확인하는 체크를 두고 기록. 홍보 문구는 법무 확인 뒤 다시 결정 (추천)**
- ② 제한 없이 쓰기 — 법무 확인 전이라 위험
