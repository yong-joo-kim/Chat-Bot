## 0. 쉬운 말 요약 — 왜 필요한가, 무엇이 달라지나, 안 해도 되는 경우

### 0.1 한 줄 요약

**"콜센터 상담 녹취를 글로 옮긴 수천 줄짜리 엑셀을 올리면, 비슷한 말끼리 자동으로 묶어 '이런 질문 묶음이 있고, 이 중 우리 챗봇이 못 알아듣는 게 이것들'이라고 보여 주고, 관리자가 고른 문장만 챗봇 학습 예문으로 넣는 기능"** 이다. 원본 ROCHA에 실제로 있는 화면이고, 핵심 계산은 우리가 이미 쓰는 문장 벡터 모델로 된다. 생성형 AI(LLM)는 필요 없다(묶음 이름 짓기 보조로만 선택).

### 0.4 치르는 비용과 위험

| # | 비용·위험 | 설명 | 통제 |
|---|---|---|---|
| R-1 | ★ **개인정보 밀도** | 상담 녹취 전사본은 이름·전화번호·주소·계좌·주민번호가 섞이기 쉽다. 정규식 마스킹은 **사람 이름 같은 비정형 개인정보를 놓칠 수 있다** | 업로드 즉시 금지어 → PII 마스킹 후 **마스킹본만 저장** · 원본 파일 저장 0 · 화면에 "마스킹이 완전하지 않을 수 있음" 안내 · 보존기간 자동 삭제(FR-DC9) · 거버넌스 `PII_MASK_MODE=FULL` 연동 |

| R-3 | **CPU 부하** | 5,000문장 임베딩은 ml-worker 호출 약 80회다. 같은 ml-worker가 대화 경로 임베딩도 처리하므로 대량 작업이 **대화 응답을 느리게 할 수 있다** | 동시 실행 상한 · 배치 사이 양보 · 대화 우선(NFR-DCP2) · 대량은 별도 ml-worker 프로세스 권고(architect) |

| R-6 | **원본과 범위 차이** | 원본 딥러닝 군집분석은 다운로드로 끝나고, 반영은 통계 > 군집분석 쪽에 있다. 우리가 "반영"까지 넣으면 원본보다 넓다 | P-3으로 확인 — 권고는 반영 포함(기존 경로 재사용이라 비용 작음) |

### 0.5 이 기능 없이 충분한 경우 (정직하게)

- **고객사가 상담 녹취 전사본 같은 외부 발화 데이터를 갖고 있지 않거나, 넘겨줄 수 없는 경우** — 입력이 없으면 기능이 놀게 된다. 챗봇 자체의 미응답·👎은 이미 학습현황 큐(No.15·44)로 모인다.
- **발화 데이터가 수백 줄 이하인 경우** — 사람이 엑셀로 읽는 편이 빠르다. 기존 No.15 추천 의도·No.23 요소분해로 충분하다.
- **"자동으로 의도까지 만들어 주는 AI"를 기대하는 경우** — 이 문서의 권고 범위는 그것을 하지 않는다(R-2).

→ 그래서 §11 Q2에 **"지금은 하지 않음(카탈로그 비고만 정리)"** 선택지를 둔다. 반대로 **콜센터·VOC 데이터를 가진 구축형 고객(금융·공공)에게 원본 ROCHA와 같은 "녹취 전사본 → 학습 후보 정제" 도구를 보여 줘야 한다면** 규모 A의 가치가 분명하다.

### 1.5 ★ 판정 — 신규 개발량: **"중"**

- **"대"가 아닌 이유**: 새 모델·모델 학습·새 인프라(Redis·GPU 서버)가 없다. 무거운 부품(임베딩 · 엑셀 · 형태소 · 대량 대조 · 작업 큐 · 반영 경로 · 마스킹 · 거버넌스 틀)이 전부 커밋돼 있다. LLM은 필수가 아니다.
- **"소"가 아닌 이유**: 군집 연산 본체와 묶음별 키워드 계산은 **처음 만드는 알고리즘 코드**이고, **테이블 2~3개 + 마이그레이션**, **화면 3개**, 반영 경로, 보존 종류 추가, 품질 측정 도구가 필요하다. No.16(증강 — 신규 테이블 1 · 화면 1 · 작업 1)보다 약간 크고 No.43(크롤링 — 테이블 5 · 출구 1)보다 작다.
- **대화 경로·위젯·대화 엔진·`@Public()`·채널 어댑터 변경 0**, No.22 `Topic`·No.15 큐·No.29 통계·No.44 원장에 쓰기 0(규모 A).

### 1.6 ★ 판정 — 개발 PC(3050) 결과를 어디까지 믿을 수 있나 (ADR-0046 방침의 적용 범위)

| 구성 요소 | 개발 PC와 운영 서버 | 품질 판정을 개발 PC에서 해도 되나 |
|---|---|---|
| 임베딩(KURE-v1) | **같은 모델·같은 리비전·같은 정규화** — 기본값이 CPU라 운영도 같은 계산 | ✅ **된다**(벡터가 같으면 묶음도 같다 — 재현성 FR-DC3-5 전제) |

| 대표 키워드 | 형태소 분석기(API 쪽) — 장비 무관 | ✅ 된다 |

### 1.8 목적

1. 외부 발화 파일을 **안전하게(마스킹)** 받아 비슷한 말끼리 묶고, 묶음마다 대표 키워드와 **"챗봇이 이미 답하는가"** 를 보여 준다.
2. 관리자가 고른 발화만 **기존 반영 경로로** 의도 예문에 넣는다(승인 없는 자산 변경 0).
3. LLM 없이 성립하고, LLM은 이름 제안 보조로만 선택해 켠다(모델·백엔드는 설정).
4. 대화 경로·위젯·엔진·다른 기능의 데이터를 **바꾸지 않는다.**

## 2. 사용자 역할 및 시나리오

### 2.1 역할

| 역할 | 이 그룹에서 하는 일 |
|---|---|
| **챗봇 운영 담당**(EDITOR·ADMIN) | 발화 파일 준비 → 분석 요청 → 결과 검토 → 엑셀 다운로드 · 발화 선택 반영 · 분석 삭제 |

| **ML 담당(ml-engineer)** | 군집 연산 · 품질 측정 도구 · 조건 기본값 제안 |
| **최종 사용자** | 변화 없음 |

### 2.2 사용자 시나리오

**S-1 (기본 흐름)**: 운영 담당이 "발화 묶음 분석" 화면에서 **양식 받기** → 콜센터 전사본 3,000줄을 양식(1열 = 발화, 선택 열 = 발생 횟수·출처 메모)에 붙여 넣음 → 대상 챗봇 선택 · 조건(목표 묶음 수 10 · 묶음 최소 발화 수 5 · 대표 키워드 수 10 · 명사만 · 대조 점수 기준)을 기본값 그대로 → 요청. 화면은 "처리 중(진행률)"을 보여 주고, 담당자는 다른 일을 해도 된다.

**S-2 (결과 검토)**: 완료 뒤 결과 상세에서 **묶음 목록**(묶음 번호 · 대표 키워드 · 발화 수 · **챗봇 미응답 비율**)을 본다. "미분류" 묶음은 목록 맨 끝. "해지·환급·위약금" 묶음이 380건인데 미응답 72%인 것을 확인 → 그 묶음의 **발화 목록**(마스킹된 발화 · 챗봇 대조 결과: 매칭 의도/미응답 · 점수 · 추천 의도)을 연다.

**S-3 (선택 반영)**: 발화 12개를 골라 **"의도에 예문으로 넣기"** → 기존 의도 "해지문의"를 고르거나 새 의도 이름 입력 → 확인 대화상자(몇 개가 들어가는지 · 중복·200자 초과로 빠지는 것) → 반영. 기존 반영 경로로 **즉시 대화에 적용**되고 감사 기록이 남는다. 분석 결과의 해당 발화에는 "반영됨(의도명)" 표시.

**S-4 (엑셀로만 쓰기 — 원본 방식)**: 반영하지 않고 **결과 엑셀 다운로드**(묶음 시트 + 발화 시트) → 사내 검토 회의 자료로 쓴다. 다운로드는 감사 기록 대상이다(마스킹본이지만 대량 반출).

**S-5 (LLM 이름 제안 — 선택)**: 서버에서 이름 제안이 켜져 있으면 요청 화면에 "묶음 이름 제안 받기" 확인란이 보인다. 켜면 묶음마다 "해지 및 환급 문의" 같은 이름 후보가 **키워드 옆에 참고용**으로 붙는다(표시 "AI 제안 — 확인 필요"). 이름 제안이 실패·지연돼도 분석은 완료되고 키워드만 보인다.

**S-6 (실패·예외)**: 파일에 빈 줄·너무 긴 줄·중복이 섞여 있으면 **검증 미리보기**에서 "유효 2,870 · 중복 합침 110 · 제외 20(사유별)"을 먼저 보여 준다. ml-worker가 도중에 죽으면 작업은 "오류(임베딩 서비스 응답 없음)"로 끝나고 **부분 결과를 저장하지 않는다**. 다시 요청하면 된다.

**S-7 (세션 만료)**: 요청 뒤 관리자 로그인이 만료돼도 작업은 서버에서 계속된다. 재로그인 후 목록에서 결과를 본다.

**S-8 (보존)**: 90일(설정값)이 지난 분석은 자동 삭제되고, 거버넌스 파기 이력에 건수만 남는다. 담당자는 그 전에 직접 삭제할 수도 있다.

| FR-DC1-2 | 양식: **1열 "발화"(필수)** · 선택 열 "발생 횟수"(정수 · 없으면 1) · "출처 메모"(자유 텍스트 — 저장 시 마스킹, 길이 상한). **양식 받기** 버튼(원본 p.100 "업로드 샘플 다운로드")을 둔다 |
| FR-DC1-3 | 한도: 파일 5MB · **유효 발화 5,000행**(`IMPORT_LIMITS` 재사용 — 상향은 설정, 운영 실측 후 · J-10). 초과 시 요청 거부(부분 처리 안 함) |
| FR-DC1-4 | 행 정리: 앞뒤 공백 제거 · 빈 행 제외 · **정규화 문자열(`normalizeText`)이 같은 행은 1행으로 합치고 발생 횟수를 더한다** · 발화 길이 상한(권고 기본 300자 — 설정) 초과 행은 **제외**하고 사유 기록 · 한 글자 발화·숫자·기호만 있는 행 제외 |
| FR-DC1-5 | **검증 미리보기**(요청 전): 전체 행 · 유효 · 합침 · 제외(사유별 건수) · 마스킹 적용 건수를 보여 준다. 미리보기는 저장하지 않는다(요청 시 다시 계산 — 방식 architect) |
| FR-DC1-6 | 수식·셀 서식·병합 셀·숨은 시트는 값만 읽고 실행·해석하지 않는다(기존 파서 규약) |

### 4.3 벡터화 · 묶기 (FR-DC3)

| ID | 요구사항 |
|---|---|
| FR-DC3-1 | 벡터화는 **ml-worker `/embed`(기존 계약 불변)** 를 배치 상한(현 64) 단위로 호출해 수행한다. 임베딩 모델을 이 기능 전용으로 바꾸거나 추가하지 않는다(현재 챗봇 매칭과 **같은 모델**) |
| FR-DC3-2 | 묶기 조건(원본 p.100 대응): **목표 묶음 수**(기본 10 · 범위 2~50) · **묶음 최소 발화 수**(기본 5 · 이보다 작은 묶음의 발화는 "미분류"로) · **대표 키워드 수**(기본 10 · 1~20) · **키워드 명사만**(기본 켬). "실제 묶음 수는 데이터에 따라 목표와 다를 수 있음"을 화면에 적는다 |
| FR-DC3-3 | 어떤 묶음에도 속하지 않는 발화는 **"미분류" 묶음**(원본 토픽번호 -1 대응)으로 모은다. 미분류도 결과·다운로드·반영 대상이다 |
| FR-DC3-4 | 알고리즘(예: 코사인 기반 k-means · 계층 군집 · 밀도 기반)과 **실행 위치**(API 프로세스 vs ml-worker 신규 경로)는 **architect가 ADR로 정한다**(ADR-0024 114행 · ADR-0027 148행의 재판정 요구). 판정 기준: ① 대화 경로 임베딩 지연에 주는 영향 ② 새 의존성(파이썬 쪽 `scikit-learn`이 이미 설치되는지 **확인 필요**) ③ 5,000건 메모리 ④ 시험 용이성 ⑤ ml-worker "추론 전용" 원칙과의 정합 |
| FR-DC3-5 | **재현성**: 같은 파일·같은 조건·같은 임베딩 모델이면 **같은 묶음**이 나온다(난수 사용 시 고정 시드). 결과에 임베딩 `modelId`·조건·알고리즘 버전을 기록한다 |
| FR-DC3-6 | 묶음 번호는 **발화 수 많은 순**으로 매긴다(1, 2, …, 마지막 = 미분류). 묶음마다 발화 수(발생 횟수 합 포함) · 대표 발화 3개(중심에 가까운 순) 를 계산한다 |
| FR-DC3-7 | **품질 측정 도구**(ml-engineer): 기존 챗봇의 의도 예문(정답 라벨 있음)을 입력으로 넣어 묶음 결과와 의도 라벨의 일치도(예: 순도·조정 랜드 지수 — 지표는 ml-engineer)를 보고서로 남긴다. `apps/ml-worker/eval/report/` 형식 재사용. 합격 기준은 P-5 |
| FR-DC3-8 | 분석용 벡터는 **작업 안에서만** 쓰고 저장하지 않는다(권고 — 저장이 필요하면 architect가 근거와 보존을 함께 정한다). `EmbeddingVector`(대화 색인)에 쓰지 않는다 |

### 4.10 GPU 재확인

| 구성 | 실제 연산 | 기준표 구간 | 비고 |
|---|---|---|---|
| 기본(규모 A · LLM 끔) | 임베딩 **추론** 배치(CPU) + 수치 군집(CPU) + 형태소 빈도 | 4~5 | 모델 학습 없음. 5,000건 처리 시간은 **실측 필요** |
| 대량(수만 건 이상 — 상한 상향 시) | 같은 연산, 건수만 큼 | 5~6 | GPU 임베딩 권장(ADR-0024 "GPU는 권장이지 필수 아님") |
| LLM 이름 제안 켬 | 묶음 수(≤50)만큼 짧은 생성 | No.37 등급표 | 경량 = 동작 확인 · 운영 = No.17 소관 |

→ **권고: 카탈로그 7 → 5 하향 + 각주**("기본 구성은 CPU로 성립 — 임베딩 추론 + 수치 군집, 모델 학습 없음 · 수만 건 이상은 GPU 권장 · LLM 이름 제안은 선택(No.37 등급표)"). GPU 필요 사유 "비지도 클러스터링 대량 배치, GPU 권장" → "임베딩 배치 추론 + CPU 군집, 대량 시 GPU 권장". 구축형 ○ 유지 · 구독형 △ 유지 + 각주("상담 전사본의 개인정보 밀도 — 벤더 클라우드 업로드 부담").

### 11.1 AskUserQuestion용 쉬운 문구(핵심 6건)

**Q1. 원래 목록의 "STT/TA 발화 데이터"를 무엇으로 볼까요?** (원본 매뉴얼은 "상담 녹취를 글로 옮긴 것 같은 발화 데이터를 엑셀로 올린다"고 설명합니다)
- ① **이미 글자로 된 발화 목록 파일(엑셀/CSV)을 올리는 것 (추천)**
- ② ①에 더해, 우리 챗봇의 대화 기록(못 알아들은 질문 등)도 같이 분석하는 것
- ③ 녹음 파일(음성)을 올리면 글자로 바꾸는 것까지 — 음성 인식은 별도 기능(No.32) 영역이라 훨씬 큼
- ④ 콜센터·VOC 시스템에서 자동으로 가져오는 것 — 고객사마다 연결 작업이 필요함

**Q2. 이번에 어디까지 할까요?**
- ① 지금은 하지 않기 — 목록에 "이렇게 해석한다"는 메모만 남김
- ② **파일을 올리면 비슷한 말끼리 묶고, 묶음마다 대표 단어와 "챗봇이 이미 답하는지"를 보여 주고, 관리자가 고른 문장만 학습 예문으로 넣기. 생성형 AI 없이 동작 (추천)**
- ③ ②에 더해 우리 챗봇 대화 기록도 분석 대상으로
- ④ ③에 더해 묶음마다 의도를 자동으로 만들고, 외부 시스템 연동·음성까지 — 가장 크고 위험함

**Q3. 분석 결과를 어떻게 쓰게 할까요?**
- ① 화면에서 보고 엑셀로 내려받기만(원본과 똑같이)
- ② **①에 더해, 관리자가 고른 문장을 바로 의도 예문으로 넣을 수 있게 (추천)** — 넣기 전에 확인 화면이 나오고, 이미 있는 학습 반영 방식을 그대로 씀
- ③ 묶음마다 의도를 자동으로 만들어 넣기 — 사람 확인 없이 챗봇이 바뀌어 권하지 않음

**Q4. 생성형 AI(LLM)는 어떻게 쓸까요?**
- ① 쓰지 않음 — 묶음 이름은 대표 단어로 표시
- ② **서버에서 켤 수 있는 "묶음 이름 제안" 보조 기능으로만. 기본은 꺼짐, 꺼져도 기능은 그대로 (추천)**
- ③ 반드시 사용(요약·설명까지) — 운영 AI 서버가 있어야만 기능이 동작함

**Q5. "잘 묶인다"는 합격 판단은 어떻게 할까요?** (묶는 데 쓰는 문장 분석 모델은 개발 PC와 운영 서버가 같아서, 결과도 같습니다. 속도와 생성형 AI 부분만 장비에 따라 다릅니다)
- ① **묶음 품질은 지금 개발 PC에서, 이미 만들어 둔 의도 예문을 정답으로 삼아 측정해 판정. 속도·생성형 AI는 운영 서버에서 따로 확인 (추천)**
- ② 모든 판단을 운영 서버에서 잰 뒤로 미룸 — 운영 서버 담당자가 생길 때까지 대기
- ③ 기준 없이 결과를 보고 판단

**Q6. 올린 발화 데이터는 얼마나 보관할까요?** (상담 녹취 전사본에는 이름·전화번호 같은 개인정보가 많을 수 있어, 자동으로 가린 뒤 저장합니다)
- ① **가린 문장만 저장하고, 원본 파일은 저장하지 않으며, 90일이 지나면 자동 삭제(기간은 설정 가능) (추천)**
- ② 가린 문장을 저장하고, 사람이 지울 때까지 보관
- ③ 묶음 요약만 남기고 문장은 분석 직후 삭제 — 이 경우 "골라서 예문으로 넣기"는 할 수 없음
