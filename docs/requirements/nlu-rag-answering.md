## 1. 배경 / 목적

### 1.1 배경 — 매칭기가 "문자열 포함"에서 멈춰 있다

현행 매칭은 `packages/dialogue-engine`의 **정규화 후 정확일치 / 부분 문자열 포함** 두 가지뿐이다(`matcher.ts` 38~44행, `faq.ts` 22~27행, ADR-0008). 여기서 세 가지 문제가 발생한다.

| # | 현재 상태 | 결과 |
|---|---|---|
| ① | **표현이 다르면 못 찾는다.** `"배송 언제 오나요"` 예문이 있어도 `"물건 며칠 걸려요"` 는 매칭되지 않는다 | 관리자가 예문을 수십 개씩 손으로 채워야 하고(No.15 운영 루프의 근본 원인), 그래도 빠진 표현은 계속 미응답이 된다 |
| ② | **부분 문자열 포함이 오탐을 만든다.** `normalizedInput.includes(norm) \|\| norm.includes(normalizedInput)` 은 짧은 예문일수록 위험하다 — 예문 `"취소"` 는 `"취소하면 위약금 있나요"` 를 잡아 엉뚱한 의도로 확정한다 | 정확한 질문일수록 오답이 나오는 역설. 점수는 `Math.min(길이)` 라 **짧은 쪽이 이길 수도 있다** |
| ③ | **답을 만들 수단이 하나뿐이다.** 관리자가 미리 적어 둔 FAQ/노드 아웃풋을 **찾는 것**만 가능하고, 이미 존재하는 사내 문서(PDF/엑셀)로 답을 **만드는 것**은 불가능하다 | 매칭에 실패하면 무조건 `"죄송해요, 잘 이해하지 못했어요"`(`DEFAULT_FALLBACK_RESPONSE`)다. 문서에 답이 있어도 쓰지 못한다 |

동시에 **외부 RAG 서버가 이미 운영 중**이고 연동 명세(`docs/00-source/API_RAG.md`)가 확보됐다. 즉 ③의 해법은 새로 만드는 것이 아니라 **안전하게 연결하는 것**이다. 다만 그 서버는 **인증이 전혀 없고**, 전체 문서 DB를 복구 불가하게 지우는 `POST /api/documents/reset` 이 그대로 열려 있으며, 시스템 프롬프트를 바꾸면 **다른 모든 이용자의 답변까지 바뀐다**(API_RAG §7 경고, §8 경고). 연결 방식 자체가 이 기능의 최대 리스크다.

### 1.2 목적

1. 1단계에서 **의미 유사도**로 FAQ/의도를 찾는다 — 예문에 없는 표현도 매칭한다(①).
2. **부분 문자열 포함 매칭을 제거**해 짧은 예문발 오탐을 없앤다(②). 정확일치는 유지한다.
3. 1단계 실패 시 **외부 RAG 서버로 문서 근거 답변**을 생성한다(③).
4. 외부 서버와의 접촉면을 **`apps/api` 안의 단일 클라이언트 + 경로 allowlist**로 봉인해, 파괴적 무인증 엔드포인트가 우리 코드에서 **호출 불가능한 상태**가 되게 한다.
5. 위 셋을 **`packages/dialogue-engine`의 순수성·동기성·결정론을 깨지 않고** 붙인다(ADR-0008 유지).
6. RAG가 답한 턴이 통계·미응답 큐에서 **정확히 구분**되게 한다(No.14/No.15 정합성).

### 1.4 외부 API 근거 인용 (`docs/00-source/API_RAG.md`)

**근거 1 — HTTP 200이 성공이 아니다.** §0-3:
> "문서 인입/삭제/초기화 **실패** → `{"result": "RAG Vector DB 추가 실패."}` / RAG 질의에서 **근거 문서를 못 찾음** → `retrieval_success: 0` / 요약에서 **LLM을 못 씀** → `degraded: true` … **연동 코드는 HTTP 상태 코드와 본문을 둘 다 봐야 한다.**"

→ **FR-N2-14(성패 판정 규칙)** 의 직접 근거.

**근거 2 — `source_info`로 실패를 판별하면 안 된다.** §6-4:
> "3. 청크는 찾았지만 LLM이 '모르겠다'는 취지의 답을 냈다 → `source_info`: **채워진 객체 그대로** … ⚠ **`source_info === null` 로 실패를 판별하면 안 된다.** … 반드시 `retrieval_success` 를 볼 것."

**근거 3 — LLM 오류도 200으로 온다.** §6-5 말미:
> "**LLM 호출 자체가 실패한 경우**는 400/500이 아니라 200으로 온다 — `result`가 `"답변 생성 중 오류가 발생했습니다: …"`로 시작하고 `retrieval_success`는 `1`이다. **답변 본문을 사용자에게 그대로 노출한다면 이 접두어를 확인하는 편이 좋다.**"

→ **FR-N2-15**(내부 오류 문자열 노출 금지)의 근거.

**근거 4 — 설정 변경은 전역이다.** §7 서두:
> "⚠ **이 설정은 서버 전역이다.** 특정 호출자나 세션에만 적용되는 값이 아니라, 이후 모든 `/api/rag/query` 와 챗봇 응답에 영향을 준다. … **요청 단위로만 임계값을 바꾸고 싶다면 이 API 대신 질의의 `similarity_threshold` 필드를 쓸 것.**"

→ **J-5**(설정 API 미사용) + **FR-N2-8**(요청 단위 임계값만 사용)의 근거.

**근거 5 — 파괴적 엔드포인트에 안전장치가 없다.** §4:
> "**Neo4j의 RAG 데이터를 전부 지운다. 되돌릴 수 없다.** 요청 파라미터는 없다. … ⚠ 운영 중인 서버에 이 API를 노출하지 말 것. **확인 절차도, 취소도, 복구도 없다.**"

**근거 6 — 두 종류의 503은 본문 모양이 다르다.** §0-4:
> "두 종류의 503은 **본문 모양이 다르다**(`code` 키 유무). **재시도 전략을 나누려면 이걸로 구분한다.**"

→ **FR-N2-19**(재시도 정책 분기)의 근거.

**근거 7 — `company` 오타는 오류가 아니라 침묵이다.** 부록 B-6:
> "**`company` 오타.** 검색은 오류 없이 `retrieval_success: 0`만 돌려준다. `GET /api/documents/metadata`의 이름과 대조할 것."

→ **FR-N3-6**(연결 점검 기능)의 근거이자, §4.4에서 `metadata`만 읽기 허용한 이유다.

**근거 8 — 응답 필드가 비어 있을 수 있다.** §6-3 경고:
> "실제 응답에서는 `total_pages`·`processed_at`·`processing_model`·`chunk_index` 가 근거 5건 **전부 `"N/A"`** 였다. … 이 필드들을 화면에 그대로 쓰려면 `"N/A"` 처리가 반드시 필요하다."

### 2.1 역할

`security-audit.md` §2.1의 역할 3종을 상속한다.

| 역할 | 이 그룹에서의 활동 |
|---|---|
| **ADMIN** | EDITOR의 모든 활동 + **RAG 연동 설정(연결 대상·테넌트 스코프)**, 연결 점검, 재색인 실행 |
| **EDITOR** | 임계값 조정, 재색인 실행, 시뮬레이터에서 매칭 근거·RAG 사용 여부 확인 |

| 최종 사용자 | 위젯에서 질문한다. 1단계/2단계의 구분을 **알 필요가 없어야 한다**(FR-N2-24) |

### 2.2 사용자 시나리오

**S-1. 예문에 없는 표현도 답한다 (최종 사용자)**
FAQ에 `"배송 언제 오나요?"` 만 등록돼 있다. 사용자가 `"물건 며칠이나 걸리죠"` 라고 묻는다. 현행 엔진은 폴백이지만, 이제 유사도 0.84로 같은 FAQ가 매칭되어 정상 답변이 나간다.

**S-2. 애매하면 되묻는다 (최종 사용자)**
`"카드 문제요"` 라는 입력에 `결제카드 등록` 0.71 / `포인트카드 조회` 0.68 두 후보가 잡힌다. 둘 다 `τ_accept` 미만이고 격차도 0.03이라, 봇이 **"이 중에 해당하는 게 있을까요?"** 와 함께 두 후보 질문을 버튼으로 제시한다. 사용자가 버튼을 누르면 그 문장이 그대로 재입력되어 **정확일치**로 확정된다.

**S-3. 짧은 예문의 오탐이 사라진다 (EDITOR)**
편집자가 예전에 `"취소"` 예문 때문에 `"취소하면 위약금 있나요?"` 가 엉뚱하게 매칭되던 것을 기억하고 다시 시험한다. 이제는 부분 문자열 포함 규칙이 없어져 위약금 FAQ가 정상 매칭된다.

**S-4. 문서에서 답을 만든다 (최종 사용자)**
`"산재 요양급여 신청 서류가 뭔가요?"` — FAQ에도 노드에도 없다. 봇이 **"문서에서 찾아보고 있어요. 잠시만요"** 를 먼저 보여주고, 7초 뒤 문서 근거 답변으로 교체된다. 답변 아래에 `출처: 산재보험안내.pdf · 요양급여 신청 · 12쪽` 이 표시된다.

**S-5. 문서에도 없다 (최종 사용자)**
`"사장님 생일 언제예요?"` — RAG가 `retrieval_success: 0`을 돌려준다. 봇은 **RAG의 문구를 그대로 쓰지 않고** 기존 폴백 문구로 답하며, 이 질문은 미응답 큐(No.15)에 적재된다.

**S-6. RAG 서버가 죽어 있다 (최종 사용자 / ADMIN)**
vLLM이 내려가 `503`이 반복된다. 회로차단기가 열려 **이후 60초 동안은 2단계를 아예 건너뛰고** 즉시 폴백한다. 사용자 체감 지연이 생기지 않는다. 관리자 콘솔의 RAG 설정 화면에는 `연결 상태: 사용 불가(vLLM 미준비) · 최근 확인 12:40` 배지가 뜬다.

**S-7. 회사명 오타 (ADMIN)**
관리자가 `company`에 `"국민연금공단"`을 넣었는데 적재된 이름은 `"국민연금"`이다. `연결 점검`을 누르면 **"적재된 문서가 0건입니다. 등록된 이름과 일치하지 않습니다"** 라고 즉시 알려준다(오타를 침묵으로 넘기지 않는다 — §1.4 근거 7).

**S-8. FAQ를 고치면 색인도 따라온다 (EDITOR)**
FAQ 답변만 수정하면 재색인이 일어나지 않지만, 질문·대체질문을 수정하면 **저장 직후** 그 항목만 재색인된다. 화면은 `색인 최신` 배지를 유지한다.

**S-9. 색인이 밀렸다 (EDITOR)**
엑셀로 예문 3,000건을 대량 등록했다. 화면에 `색인 대기 2,840건 · 진행 중` 이 표시되고, 그 사이 들어온 질문은 **이미 색인된 항목 범위에서** 매칭된다(대화가 멈추지 않는다).

**S-10. 임베딩 서비스가 죽었다 (최종 사용자)**
ml-worker가 내려갔다. 1단계는 **저하 모드**로 전환되어 기존 규칙 매칭(정확일치 + 부분일치)으로 동작하고, 대화는 계속된다. 관리자 화면에만 `의미 매칭 일시 중지` 경고가 뜬다.

**S-11. 개인정보가 섞인 질문 (최종 사용자)**
`"제 번호 010-1234-5678로 결과 알려주세요"` 가 2단계로 넘어간다. 외부 서버에 **실제로 전송되는 문장은 `제 번호 010-****-5678로 결과 알려주세요`** 다(J-9).

**S-12. 위험한 버튼은 존재하지 않는다 (ADMIN)**
관리자가 RAG 설정 화면을 뒤져도 **문서 삭제·초기화·프롬프트 변경 버튼이 없다.** 개발자 도구로 우리 API에 해당 동작을 요청할 경로도 없다(J-5).

**S-13. 시뮬레이터에서 근거를 본다 (EDITOR)**
No.10 시뮬레이터에서 문장을 넣으면 `매칭: FAQ #12(의미 유사도 0.84, 2위 0.61)` 와 같이 **점수와 2위 격차**가 표시된다. 2단계를 탔다면 `2단계 RAG 사용 · 근거 3건 · 4.2초` 가 함께 보인다.

**S-14. 임계값을 조정한다 (EDITOR)**
오탐이 잦아 `τ_accept`를 0.80 → 0.85로 올린다. 저장 즉시 다음 턴부터 적용되고, **이 변경은 해당 챗봇에만** 영향을 준다(외부 서버 전역 설정은 건드리지 않는다).

**S-15. 위젯이 기다리다 포기한다 (최종 사용자)**
RAG가 90초를 넘겨도 답이 없다. 위젯은 **"지금은 답변을 준비하지 못했어요"** 로 정리하고 입력을 다시 받는다. 백그라운드 작업은 계속되다 완료되면 로그에만 남는다.

## 4. 기능별 요구사항

### 4.1 1단계 — NLU 의미 유사도 매칭 (FR-N1-*)

#### 4.1.1 임베딩 조달 방식 — J-1 결정

**결정: 자체 구축한다. `apps/ml-worker`를 신설하되 학습 기능 없이 추론 전용으로 시작하고, `EmbeddingProvider` 포트로 추상화해 구독형에서는 외부 임베딩 API로 교체 가능하게 한다.**

외부 RAG 서버 재사용을 기각한 근거:

| # | 근거 |
|---|---|
| ① | **임베딩 엔드포인트가 없다.** API_RAG가 다루는 7기능(§0 범위표)에 임베딩이 없고, "그 밖의 기능이 필요하면 담당자에게 문의"라고만 적혀 있다 — **계약이 존재하지 않는 것에 대화 경로를 의존시킬 수 없다** |
| ② | **`/api/rag/query`로 대체할 수 없다.** 이 엔드포인트는 검색+**LLM 생성**이라 한 번에 수 초~수십 초가 걸린다(§6-6). FAQ 매칭에 쓰면 **모든 턴이 LLM 호출**이 되어 200ms(P95) 목표가 100배 초과된다 |
| ③ | **유사도 점수를 주지 않는다.** 응답 최상위 필드는 `result`/`keywords`/`source_info`/`retrieval_success` 4개뿐이며(§6-3) 후보별 점수가 없다 — 임계값 기반 판정이 불가능하다 |
| ④ | **vLLM 게이트에 묶인다.** 이 문서 범위에서 vLLM이 죽으면 막히는 유일한 엔드포인트다(§0-5). **1단계까지 외부 LLM 가용성에 묶이면 FAQ 응답조차 멈춘다** |
| ⑤ | **레이트리밋을 공유한다.** A 부류는 IP당 분당 200회(§0-4). 매 턴 임베딩을 외부에서 받으면 2단계 몫까지 잠식한다 |

| ID | 요구사항 |
|---|---|
| FR-N1-1 | 임베딩은 **`EmbeddingProvider` 인터페이스**(`embed(texts: string[]): Promise<Float32Array[]>` + `modelId`/`dimension`/`healthy()`)로 추상화하고, 소비자는 이 포트만 안다. 구현체 교체 지점은 **DI 바인딩 1곳**이다. |

#### 4.1.2 엔진 통합 방식 — J-2 · J-3 결정

**결정: 엔진 시그니처는 `ResolveOptions.semantic` 선택 필드 1개만 늘린다. `apps/api`가 점수 맵을 계산해 주입하고, 엔진은 그 맵을 동기적으로 소비한다. 부분 문자열 포함 매칭은 제거하고 정확일치는 유지한다.**

```ts
// packages/shared-types — 계약 개요(최종 형태는 system-architect가 확정)
interface SemanticMatchInput {
  modelId: string;
  /** FAQ id → 최고 유사도(질문·대체질문 중 최댓값) */
  faqScores: ReadonlyMap<string, number>;
  /** 의도 id → 최고 유사도(의도명·예문 중 최댓값) */
  intentScores: ReadonlyMap<string, number>;
  /** 되묻기 후보 구성을 위한 상위 N(점수 내림차순, 결정론적 타이브레이크 포함) */
  ranked: ReadonlyArray<{ kind: 'FAQ' | 'INTENT'; id: string; score: number; matchedText: string }>;
  thresholds: { accept: number; low: number; margin: number };
}
```

| ID | 요구사항 |
|---|---|
| FR-N1-8 | `resolveResponse`/`resolveByNodeId`/`resolveTurn`의 **기존 인자 순서와 반환 타입을 바꾸지 않는다.** `ResolveOptions.semantic`은 **선택 필드**이며 미지정 시 **현행 동작과 완전히 동일**하다(저하 모드가 곧 현행 동작이다). |
| FR-N1-9 | **점수 합성 규칙(고정)**: ① 정규화 후 **정확일치** → 확정(기존 `norm.length + 1000` 계열 우선순위 유지) ② 정확일치가 없으면 **의미 유사도 점수** ③ `semantic` 미주입 시에만 **부분 문자열 포함**을 사용한다. 즉 **의미 매칭이 살아 있는 동안 부분일치는 동작하지 않는다**(J-3). |
| FR-N1-10 | 동점 처리는 **결정론적**이어야 한다. 점수 동률 시 `FAQ` → `INTENT` 순, 같은 종류 내에서는 `id asc`로 고정한다(ADR-0008 §2 보강 2와 같은 원칙). |

#### 4.1.4 임계값과 1단계 실패 판정 — J-4 결정

**결정: 3구간 + 격차 조건. 챗봇별 설정값이며 기본값은 잠정값이다.**

| 구간 | 조건(코사인 유사도 `s` = top1 점수) | 동작 | 기본값 |
|---|---|---|---|
| **확정** | `s ≥ τ_accept` **그리고** `s − s₂ ≥ τ_margin` | 그 FAQ/의도로 매칭 확정 | `τ_accept = 0.80` |
| **모호** | `τ_low ≤ s < τ_accept`, **또는** `s ≥ τ_accept`이나 `s − s₂ < τ_margin` | **후보 되묻기**(최대 3건, FR-N1-12) | `τ_margin = 0.05` |
| **실패** | `s < τ_low` (후보 0건 포함) | **2단계로 이관**. 2단계 비활성이면 기존 폴백 | `τ_low = 0.60` |

| ID | 요구사항 |
|---|---|
| FR-N1-25 | 세 임계값은 **챗봇별 설정값**이며 `0.0 ≤ τ_low < τ_accept ≤ 1.0`, `0 ≤ τ_margin ≤ 0.5`를 서버가 검증한다. 위반 시 `400 INVALID_THRESHOLD`. |
| FR-N1-26 | 기본값은 **모델 종속 잠정값**이다. 모델이 바뀌면 기본값도 함께 바뀌어야 하므로, **`modelId` → 기본 임계값 매핑을 코드 상수 1곳**에 둔다. |
| FR-N1-27 | **보정 절차를 산출물로 남긴다.** 골든셋(정답 라벨이 붙은 질문 **최소 100문항**: 매칭 성공 60 / 되묻기 20 / 미매칭 20)으로 `τ` 스윕을 돌려 **정밀도·재현율·오탐률 표**를 만들고, 최종 기본값을 그 표로 정당화한다(AC-N1-12). |
| FR-N1-28 | 임계값 변경은 **해당 챗봇에만** 영향을 준다. **외부 RAG 서버의 전역 설정(`POST /api/rag/settings`)은 절대 호출하지 않는다**(§1.4 근거 4). |
| FR-N1-29 | 임계값 변경은 **감사 대상**이다(`Chatbot` 대상 `UPDATE` 1건, No.13 재사용). 변경 전/후 값을 스냅샷에 남긴다. |
| FR-N1-30 | 임계값은 **저장 즉시 다음 턴부터 적용**된다(번들·설정 캐시 무효화). "적용 중" 상태를 만들지 않는다. |

#### 4.2.6 느린 응답의 전달 방식 — J-7 결정

**결정: 공개 대화 API는 즉시 `PENDING`을 반환하고, 위젯이 폴링해 최종 답변을 받는다.**

| ID | 요구사항 |
|---|---|
| FR-N2-33 | `POST /public/chatbots/:slug/messages` 응답에 **선택 필드 `pendingAnswer?: { id, pollAfterMs, expiresAt }`** 를 추가한다. 기존 필드(`messageId`/`outputs`/`state`/`stateReset`)는 **형태·의미 모두 불변**이며, 2단계를 타지 않는 턴의 응답은 **바이트 단위로 현행과 동일**하다(AC-N2-16). |
| FR-N2-34 | `PENDING` 턴의 `outputs`에는 **대기 안내 텍스트 1건**이 담긴다. `state`는 **요청에 실려온 상태를 그대로 보존**한다(금지어 BLOCK 턴의 처리와 동일 — EX-12-26 패턴). |
| FR-N2-35 | **신규 공개 엔드포인트** `GET /public/chatbots/:slug/messages/:messageId` — `{ status: 'PENDING'|'READY'|'FAILED'|'EXPIRED', outputs?, sources? }`. ⚠ **`@Public()` 핸들러가 5개 → 6개가 된다. AC-C-4/AC-X-3을 "정확히 6개"로 갱신해야 한다**(회귀 방지 장치를 무력화하지 않고 **의도적으로 갱신**한다). |
| FR-N2-36 | 이 엔드포인트는 **공개 API 규약을 전부 상속**한다 — 레이트리밋(세션 30/분·IP 120/분), Origin 가드, 내부 식별자·`trace` 미노출(ADR-0011). **`messageId`(UUID v4) 추측 공격**에 대비해 ① 조회 성공은 **최초 1회 + 유예 30초** ② TTL 만료(기본 5분) 후 `404 PENDING_ANSWER_NOT_FOUND` ③ 해당 슬러그의 대화에서 발급된 id가 아니면 `404`. |
| FR-N2-37 | 보류 답변 저장소는 **TTL 기반 서버 상태**다. 단일 인스턴스 전제이므로 **인터페이스로 추상화**해 다중 인스턴스 전환 시 교체 지점이 1곳이게 한다(명세서 §5 확장성 규약). |
| FR-N2-38 | **위젯 폴링 규격**: 최초 대기 `pollAfterMs`(기본 1,200ms) 후 시작, 간격 1.5초, **최대 대기 90초**. 초과 시 정리 문구로 마감하고 입력을 다시 활성화한다(S-15). 폴링 중에는 입력이 잠기지 않고, 사용자가 새 질문을 보내면 **이전 폴링을 중단**한다. |
| FR-N2-39 | 위젯은 **대기 중임을 시각·보조기술 양쪽에 알린다** — 진행 표시 + `aria-live="polite"` 안내. 애니메이션만으로 상태를 전달하지 않는다(UIUX 준수기준). |
| FR-N2-40 | **대화 로그는 최종 결과로 1건만 남긴다.** `PENDING` 시점에 적재하지 않고, RAG 완료(또는 실패) 시점에 `record()`를 1회 호출한다. `messageId`는 최초 턴의 값을 유지해 **중복 로그를 만들지 않는다**. |

### 4.4 문서 인입의 분리 — J-8 결정

**결정: 문서 업로드/삭제/비동기 task 관리는 이번 범위에서 제외하고, `기능요구사항.md`에 신규 항목(No.48 제안)으로 등록한다. 이번엔 `GET /api/documents/metadata` 읽기만 연결 점검에 쓴다.**

분리 근거는 §1.3 J-8에 정리했다. 추가로, 이번 범위에 넣지 않아도 **기능이 성립한다**는 점이 결정적이다 — 외부 서버에는 이미 문서가 적재돼 있고(§2-2 예시의 1,842청크), 2단계는 그 문서만으로 동작한다.

**신규 항목 제안(§10에서 정식 제안)**

| No | 기능 그룹 | 기능명 | 설명 | GPU | 구축형 | 구독형 |
|---|---|---|---|---|---|---|
| **48(제안)** | 생성형 AI | **RAG 지식베이스 관리** | 문서 업로드(비동기 인입·task 폴링)·적재 현황 조회·범위 삭제. **파괴적 초기화는 제공하지 않는다** | 1(자체 GPU 없음, 외부 위임) | △ | ○ |

**No.48 착수 시 반드시 먼저 풀어야 할 문제**(이번 문서가 남기는 인계):

1. **되돌릴 수 없는 삭제에 어떤 승인 흐름을 붙일 것인가** — `DELETE /api/documents`는 `company`만 주면 그 회사 문서 전부를 지우며 **몇 건이 지워졌는지도 응답에 없다**(§3-3).
2. **`"삭제 실패"`가 "지울 게 없었다"와 구분되지 않는 문제**(§3-3 경고) — 재시도·알람 설계 전에 `metadata` 대조가 선행돼야 한다.
3. **진행률 UI를 만들 수 없다**(`progress`가 항상 0, §5-1) — "진행 중/완료/실패" 3상태로만 표현해야 한다.
4. **서버 재시작 시 task 기록이 사라진다**(§5-1) — `not_found`를 "실패"로 오판하지 않는 정책이 필요하다.
5. **파일명이 겹치면 경고 없이 덮어쓴다**(§1-1) — 업로드 파일명 유일화 규칙이 필요하다.
6. **`.hwp`/`.hwpx`는 리눅스 서버에서 사실상 동작하지 않는다**(§1-1) — 업로드 화면이 사전에 거부하고 PDF 변환을 안내해야 한다.
7. **재인입 시 청크 수가 줄면 옛 청크가 남는다**(§1-5) — "삭제 후 인입"을 기본 동작으로 할지 결정해야 한다.

### 4.5 GPU 필요도 재산정 — J-1·J-5의 귀결

기준표의 구간 정의(`기능요구사항.md` §1): `1~2` CPU 전용 · `3~4` 경량 ML(CPU 가능) · `5~6` 중간 딥러닝(GPU 권장) · `7~8` LLM/비전(GPU 필수).

| 구성요소 | 카탈로그 | **재산정** | 근거 |
|---|---|---|---|
| **1단계 임베딩(No.18 부분)** | **5** | **4** | 카탈로그의 5는 **"임베딩 학습·추론"**(§3 표 GPU 필요 사유)을 함께 가정한 값이다. 이번 범위는 **① 학습·파인튜닝 없음 ② 추론 전용 ③ 소형 문장 인코더 ④ 코퍼스가 챗봇당 수백~수천 문장 ⑤ 벡터 인덱스 없이 메모리 내적**이다. 실시간 1문장 인코딩은 CPU에서 수십~수백 ms이고, 전체 재색인만 배치로 시간이 걸린다(GPU 있으면 빨라지는 정도). **"경량 ML(CPU 가능)" 구간의 정의에 정확히 부합**한다. GPU는 **권장이지 필수가 아니다** |
| **2단계 RAG(No.30 부분)** | **8** | **1** | 카탈로그의 8은 비고에 **"자체 서빙은 고사양 GPU 필요"** 라고 명시돼 있다. 이번 범위에서 LLM 추론·벡터 검색(Neo4j)·문서 파싱·임베딩이 **전부 외부 서버(vLLM, `Qwen3.6-35B-A3B-AWQ-4bit`)에서 수행**되고, 우리 몫은 **HTTP 프록시 + 응답 판정 + 유량 제어**뿐이다. 이는 CPU 전용 구간의 정의 그 자체다 |
| **No.6 / No.9** | 2 | **2(변동 없음)** | 관리 CRUD는 그대로다. 매칭 엔진 교체는 No.18의 몫으로 계상한다 |
| **이 기능그룹 종합** | — | **4** | 1단계가 지배한다. **2단계를 추가해도 자체 GPU 요구는 올라가지 않는다** |

| 구성요소 | 구축형 | 구독형 | 단서 |
|---|---|---|---|
| 1단계 임베딩 | **○** | **○** | 소형 모델이라 온프레미스 CPU/저사양 GPU로 충분. 구독형은 외부 임베딩 API로 교체(`EmbeddingProvider` 포트) |
| 2단계 RAG | **△** | **○** | ⚠ **"엔진까지 사내 설치"라는 구축형 세일즈 포인트**(`기능요구사항.md` §5)와 충돌한다. 현재 제공된 서버는 **공인 IP·무인증**이라 구축형 고객사의 보안 요건을 충족하지 못한다. **RAG 서버가 고객사 내부망에 설치되고 인증이 도입되면 ○** |

## 5. 데이터 요구사항

### 5.1 신규 엔터티 — `EmbeddingVector`(명세서 §3에 예고된 항목의 1차 구체화)

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | string(uuid) | PK |
| `chatbotId` | string | 챗봇 스코프(FK **있음** — 파생 데이터라 챗봇과 생사를 같이한다) |
| `ownerType` | string | `FAQ_QUESTION` \| `FAQ_ALT` \| `INTENT_NAME` \| `INTENT_EXAMPLE`(zod enum 단일 소스) |
| `ownerId` | string | 원본 `FaqEntry.id` / `Intent.id`. **FK를 걸지 않는다**(로그·파생 규약 준수, 정리는 서비스가 책임) |
| `slotIndex` | int | 배열 내 위치(`altQuestions`/`examples`). 단일 필드는 `0` |
| `textHash` | string | 정규화 텍스트의 sha256. **재임베딩 회피 키**(FR-N1-19) |
| `modelId` | string | 모델 식별자 + 버전 |
| `dimension` | int | 차원 수 |
| `vector` | string | L2 정규화된 float 배열의 직렬화(SQLite: JSON 또는 base64 BLOB). **Postgres 전환 시 `vector` 타입으로 승격 가능** |
| `status` | string | `READY` \| `PENDING` \| `FAILED` |
| `createdAt`/`updatedAt` | datetime | — |

- **유일 제약**: `@@unique([chatbotId, ownerType, ownerId, slotIndex, modelId])`
- **인덱스**: `(chatbotId, modelId, status)`, `(chatbotId, ownerType, ownerId)`
- **원문 텍스트는 저장하지 않는다** — `ownerId`/`slotIndex`로 역참조 가능하고, 중복 저장은 수정 시 정합성 부담만 늘린다.
- ⚠ **로딩 전략 결정 필요(아키텍트)**: 턴마다 DB에서 벡터를 읽으면 예산을 넘는다. **번들 캐시(`DialogueBundleService`)와 같은 수명주기의 메모리 캐시**에 동거시키는 것을 권고한다(무효화 지점도 공유).

### 5.3 기존 엔터티 변경 — `ConversationLog` (J-10)

|---|---|
| **추가** | `answeredByRag` `boolean` 기본 `false`. 쓰기 주체는 `ConversationLogService.record()` 1곳(파라미터 전달) |

### 5.5 외부 API 계약(수신 스키마 개요)

```jsonc
// 요청 (우리가 조립 — provider는 DTO에 없고 상수 주입)
{ "question": "<PII 마스킹된 문장, ≤200자>", "company": "<설정값>",
  "category": "<설정값|생략>", "subcategory": "<설정값|생략>", "provider": "pdf" }

// 응답 (zod 파싱 대상 — 최상위 정확히 4필드)
{ "result": string, "keywords": string[], 
  "source_info": { "total_sources": number,
                   "common_metadata": { company, category, subcategory },
                   "sources": Array<{ file_path, page: number|"N/A", section_title, 
                                      paragraph_id, highlight_text, ... }> } | null,
  "retrieval_success": 0 | 1 }
```

- 모든 `sources[]` 필드는 **`"N/A"` 허용**으로 스키마를 작성한다(FR-N2-22).
- 알려지지 않은 필드는 **strip**한다. 스키마 파싱 실패 = 호출 실패(`SCHEMA_INVALID`).

| **NFR-S19** | ⚠ **잔존 리스크(R-1)**: 외부 RAG 서버는 무인증·공인 IP이며 우리 통제 밖이다. **사내 문서 질의가 제3자에게 관측될 수 있다**는 점을 설계서에 리스크로 명시하고, 고객 배포 전 ① 내부망 이전 ② 인증 도입 ③ 전송 구간 TLS 중 최소 1개를 **전제 조건**으로 건다. 현재 Base URL은 `http://`(평문)다. |

## 7. 수용기준 (AC)

### AC-N1. 1단계 의미 유사도 매칭

- **AC-N1-1** Given FAQ 질문 `"배송 언제 오나요?"` 만 등록, When `"물건 며칠이나 걸리죠"` 로 대화하면, Then **그 FAQ가 매칭**되고 `trace`에 `SEMANTIC_MATCHED`가 있다.
- **AC-N1-2** Given 의도 예문에 `"취소"` 가 있고 별도 FAQ `"취소하면 위약금 있나요?"` 가 있음, When `"취소하면 위약금 있나요?"` 를 입력하면, Then **위약금 FAQ가 매칭**된다(부분 문자열 포함 오탐 제거 검증 — J-3).
- **AC-N1-3** Given `semantic` 옵션을 주입하지 않음(저하 모드), When 기존 엔진 테스트 전체를 실행하면, Then **현행과 동일한 결과**이며 부분일치가 다시 동작한다.
- **AC-N1-4** Given top1 = 0.71 / top2 = 0.68(둘 다 `τ_accept` 미만), When 대화하면, Then **후보 2건이 `MESSAGE` 버튼**으로 제시되고 `trace`에 `SEMANTIC_AMBIGUOUS`가 있으며 `isAnswered = true`다.
- **AC-N1-5** Given 되묻기 후보 버튼을 클릭, When 그 텍스트가 재입력되면, Then **정확일치로 확정**되며 대화 상태 봉투 스키마가 **변경되지 않았다**.
- **AC-N1-6** Given 의도 `A`를 조건으로 갖는 노드가 있고 입력이 예문과 표현만 다름, When 대화하면, Then **그 노드가 매칭**된다(의미 매칭이 노드 트리거에 전파됨 — FR-N1-11의 명시 고정).
- **AC-N1-7** Given top1 = 0.86 / top2 = 0.84(`τ_margin` 미달), When 대화하면, Then **확정하지 않고 되묻는다**.
- **AC-N1-8** Given 동일 입력·번들·점수 맵·`now`, When 100회 실행하면, Then **결과가 100회 모두 동일**하다(결정론 — FR-0-40).
- **AC-N1-9** Given 임베딩 서비스 응답 지연 1초(타임아웃 300ms), When 대화하면, Then **300ms 안에 저하 모드로 전환**되어 응답이 나가고 사용자에게 오류가 보이지 않는다.
- **AC-N1-10** Given 임베딩 서비스 연속 5회 실패, When 6번째 턴을 보내면, Then **임베딩을 호출하지 않고**(회로 open) 즉시 저하 모드로 응답한다.
- **AC-N1-11** Given `modelId`가 바뀐 채 기존 벡터가 남아 있음, When 대화하면, Then **옛 모델 벡터를 매칭에 쓰지 않고** 상태 API가 `staleModel: true`를 보고한다.
- **AC-N1-12** Given 골든셋 100문항, When `τ` 스윕 보고서를 확인하면, Then **정밀도·재현율·오탐률 표가 존재**하고 최종 기본값이 그 표로 정당화돼 있다(FR-N1-27).
- **AC-N1-13** Given FAQ **답변만** 수정, When 색인 상태를 확인하면, Then **재임베딩이 0건**이다(FR-N1-19).
- **AC-N1-14** Given FAQ **질문**을 수정, When 저장 직후 대화하면, Then **수정된 질문 기준으로 매칭**된다(캐시 TTL을 기다리지 않는다).
- **AC-N1-15** Given 예문 3,000건 임포트 직후(색인 진행 중), When 대화하면, Then **응답이 정상**이고 이미 색인된 범위에서 매칭되며 `pending` 건수가 상태 API에 보고된다.
- **AC-N1-16** Given `enabled=false` FAQ, When 그 질문과 의미가 같은 입력을 하면, Then **매칭되지 않는다**.
- **AC-N1-17** Given 재색인 진행 중, When 같은 챗봇에 재색인을 다시 요청하면, Then `409 REINDEX_IN_PROGRESS`다.
- **AC-N1-18** Given `acceptThreshold ≤ lowThreshold` 로 저장 시도, When 호출하면, Then `400 INVALID_THRESHOLD`이며 저장되지 않는다.
- **AC-N1-19** Given 임계값 변경, When 이력(No.13)을 조회하면, Then `Chatbot` `UPDATE` 1건이 있고 **대화 문장이 포함돼 있지 않다**.
- **AC-N1-20** Given 챗봇 영구 삭제, When 벡터 테이블을 조회하면, Then **해당 챗봇 벡터가 0건**이다.

### AC-N2. 2단계 RAG 폴백

- **AC-N2-1** Given 저장소 전체, When `documents/reset`·`rag_prompts`·`rag/settings`·`DELETE /api/documents` 문자열을 검색하면, Then **코드에서 0건**이다(문서 파일 제외 — NFR-S11).
- **AC-N2-2** Given RAG 설정이 켜진 챗봇, When 1단계가 실패하는 질문을 보내면, Then 외부로 나간 요청의 **`provider`가 `"pdf"`** 이고 `Content-Type: application/json`이다.
- **AC-N2-3** Given 공개 대화 요청 본문에 `company: "타사"` 를 임의로 추가, When 전송하면, Then **그 값은 무시되고** 서버 설정의 `company`가 사용된다(NFR-S14).
- **AC-N2-4** Given 사용자 질문에 전화번호 포함, When 외부 호출을 관찰하면, Then **전송 문장이 마스킹돼 있다**(J-9).
- **AC-N2-5** Given 외부 응답 `retrieval_success: 0`, When 결과를 확인하면, Then **우리 폴백 문구**가 나가고 `isAnswered=false`이며 **미응답 큐에 적재**된다.
- **AC-N2-6** Given 외부 응답 `retrieval_success: 1` **이지만** `source_info`가 채워진 채 `result`가 `"답변 생성 중 오류가 발생했습니다: …"` 로 시작, When 결과를 확인하면, Then **그 문자열이 사용자에게 노출되지 않고** 폴백 처리된다(§1.4 근거 3).
- **AC-N2-7** Given 외부 응답 `retrieval_success: 1` + `source_info: null`, When 결과를 확인하면, Then **성공으로 처리**된다(`source_info`로 판별하지 않음 — §1.4 근거 2).
- **AC-N2-8** Given 성공 응답의 `sources[0].file_path = "/home/doota/.../연금안내서.pdf"`, When 화면 출력을 확인하면, Then **`연금안내서.pdf` 만** 보이고 경로가 노출되지 않는다.
- **AC-N2-9** Given `page`·`section_title`·`total_pages`가 전부 `"N/A"`, When 출처를 표시하면, Then **오류 없이 파일명만** 표시된다.
- **AC-N2-10** Given 외부 서버가 `503` + `code` **없음**(vLLM 미준비), When 호출하면, Then **재시도하지 않고** 즉시 폴백하며 회로차단 카운트가 증가한다.
- **AC-N2-11** Given 외부 서버가 `503` + `code: "SERVER_OVERLOAD"`, When 호출하면, Then **1회 재시도**가 발생한다(§1.4 근거 6).
- **AC-N2-12** Given 연속 5회 실패 후, When 다음 질문이 1단계 실패로 오면, Then **외부 호출이 발생하지 않고**(회로 open) 즉시 폴백한다.
- **AC-N2-13** Given 동시 호출 상한 5, When 6번째 요청이 들어오면, Then **대기하지 않고 즉시 폴백**한다.
- **AC-N2-14** Given `RAG_TIMEOUT_MS=30000`(하한 미만)으로 설정, When 기동하면, Then **120,000으로 보정**되고 경고 로그가 남는다(FR-N2-26).
- **AC-N2-15** Given 1단계 실패 턴, When 공개 대화 API를 호출하면, Then **200ms(P95) 안에 `PENDING` 응답**이 오고 `state`가 요청 상태 그대로다.
- **AC-N2-16** Given 2단계를 타지 않는 일반 턴, When 응답을 확인하면, Then **`pendingAnswer` 키가 없고** 기존 응답 스키마와 완전히 동일하다(하위호환).
- **AC-N2-17** Given `PENDING` 응답의 `messageId`, When 폴링하면, Then `PENDING` → `READY` 로 전이하고 **최종 답변과 출처**가 반환된다.
- **AC-N2-18** Given 다른 슬러그로 같은 `messageId`를 폴링, When 호출하면, Then `404`다.
- **AC-N2-19** Given TTL 경과 후 폴링, When 호출하면, Then `404 PENDING_ANSWER_NOT_FOUND`이며 보류 답변이 메모리에서 제거돼 있다.
- **AC-N2-20** Given 2단계가 성공한 턴, When `ConversationLog`를 조회하면, Then **행이 1건**이고 `isAnswered=true`, `answeredByRag=true`이며 **미응답 큐에 없다**.
- **AC-N2-21** Given 2단계가 성공한 턴, When No.14 응답 출처 분포를 조회하면, Then **`RAG` 조각에 집계**된다.
- **AC-N2-22** Given 컨텍스트 세션(슬롯필링) 진행 중 인식 실패 턴, When 확인하면, Then **2단계가 실행되지 않는다**(FR-N2-1 ⑥).
- **AC-N2-23** Given `NODE` 버튼 클릭 턴이 폴백으로 끝남, When 확인하면, Then **2단계가 실행되지 않는다**.
- **AC-N2-24** Given 금지어 `BLOCK` 턴, When 확인하면, Then **엔진도 RAG도 호출되지 않는다**(기존 동작 유지).
- **AC-N2-25** Given 관리자 시뮬레이션 기본 호출, When 1단계 실패 문장을 넣으면, Then **외부 호출이 0건**이다. `useRag: true`일 때만 호출되며 그때도 `ConversationLog`는 적재되지 않는다.
- **AC-N2-26** Given `/simulate/compare` 실행, When 확인하면, Then **외부 호출이 0건**이다.
- **AC-N2-27** Given `RAG_BASE_URL` 미설정, When 1단계 실패 턴을 보내면, Then **기존 폴백 문구**가 즉시 나가고 `PENDING`이 발생하지 않는다.
- **AC-N2-28** Given 외부 응답이 스키마와 다름(예: `retrieval_success`가 문자열), When 처리하면, Then **예외가 사용자에게 전파되지 않고** `SCHEMA_INVALID`로 폴백된다.
- **AC-N2-29** Given `RagCallLog` 전체, When 검사하면, Then **질문·답변 원문이 어디에도 없다**(NFR-S8/FR-0-48).
- **AC-N2-30** Given 영어 질문으로 RAG가 영어 폴백 문구를 반환, When 사용자 화면을 확인하면, Then **한국어 폴백 문구**가 표시된다(FR-N2-19).

### AC-N3. 관리자 콘솔

- **AC-N3-1** Given ADMIN 로그인, When AI 답변 설정 화면을 열면, Then 1단계·2단계 설정과 색인 상태·연결 상태가 보인다.

- **AC-N3-4** Given `연결 점검` 실행, When 외부 호출을 관찰하면, Then **`/api/rag/query`가 호출되지 않는다**(FR-N3-7).

- **AC-N3-8** Given 공개 대화 API 응답, When 확인하면, Then **점수·`trace`·내부 식별자가 포함돼 있지 않다**(NFR-S1 유지).
- **AC-N3-9** Given 임계값 미리보기에 시험 문장 입력, When 실행하면, Then **저장 없이** 판정 결과가 표시되고 엔진과 **동일한 함수**가 사용된다(NFR-M2 — 값이 어긋나지 않는다).
- **AC-N3-10** Given 신규 화면, When axe 스캔하면, Then 대비 위반 **0건**이고 슬라이더에 수치 입력 대체 수단이 있다.

### AC-N4. 공통 / 회귀

- **AC-N4-1** Given 신규 환경변수를 **하나도 설정하지 않음**, When API를 기동하고 대화하면, Then **정상 기동**하고 현행 규칙 매칭으로 동작한다(두 단계 모두 비활성).
- **AC-N4-2** Given 기존 통합·단위 테스트 전체, When 실행하면, Then **부분일치 의존 테스트(설계서에 목록화된 것)를 제외**하고 전부 통과한다.
- **AC-N4-3** Given `@Public()` 핸들러, When 개수를 세면, Then **정확히 6개**다(AC-C-4/AC-X-3의 의도적 갱신 — NFR-S17).
- **AC-N4-4** Given `packages/dialogue-engine`, When 의존성을 검사하면, Then **HTTP 클라이언트·Prisma·환경변수 접근이 0건**이다(FR-0-39).
- **AC-N4-5** Given 엔진 공개 API, When 기존 호출부 3종(시뮬레이션·비교·공개대화)을 컴파일하면, Then **인자 순서·반환 타입 변경으로 인한 수정이 0건**이다.
- **AC-N4-6** Given 전체 저장소, When 외부 RAG 호스트로 나가는 HTTP 호출부를 검색하면, Then **`RagHttpClient` 1곳**뿐이다(FR-0-41).
- **AC-N4-7** Given PII 마스킹, When 구현 위치를 검사하면, Then **함수가 1벌**이며 저장 경로와 송신 경로가 같은 함수를 쓴다(NFR-S13).
- **AC-N4-8** Given 신규 엔드포인트 전체, When 계약 테스트를 실행하면, Then 모든 응답이 대응 zod 스키마 파싱을 통과한다.
- **AC-N4-9** Given 신규 원시 SQL, When 검사하면, Then **0건**이다(NFR-M5).
- **AC-N4-10** Given 기존 No.14 대시보드/통계 AC, When 실행하면, Then **수치가 변하지 않는다**(`answeredByRag` 추가가 기존 집계를 바꾸지 않음을 증명).
