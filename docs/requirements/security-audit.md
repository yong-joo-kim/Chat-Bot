## 1. 배경 / 목적

### 1.1 배경 — 이 그룹은 "새로 만드는" 것이 아니라 "미뤄둔 빚을 갚는" 그룹이다

1차 개발 범위(기본기능 No.1~15) 중 **세 그룹(No.1~11)이 `main`에 병합**되었다. 그 과정에서 인증·인가·감사는 매 그룹마다 **"No.12에서"** 로 일관되게 유보되었고, 그 결과 현재 시스템은 아래 네 가지 미완 상태에 있다.

| # | 현재 상태 | 위험 |
|---|---|---|
| ① | **관리자 API 75개 핸들러 전부가 인증 없이 호출 가능**하다. `PermissionGuard`는 11개 컨트롤러에 부착돼 있으나 `canActivate()`가 무조건 `true`를 반환한다 | 네트워크에 닿는 누구나 챗봇을 영구 삭제(`POST /chatbots/:id/permanent-delete`)하거나 대화 자산을 대량 삭제할 수 있다 |
| ② | `@RequirePermission('...')` 데코레이터가 **75곳에 부착돼 있으나 문자열 9종이 어디에도 정의돼 있지 않다**(시그니처가 `permission: string`) | 오타가 타입 검사에 걸리지 않는다. 가드를 켜는 순간 오타 1건 = 해당 API 영구 403 |
| ③ | `AuditLog` 테이블은 존재하지만 **쓰기 코드가 0줄**이다(`apps/api/src` 전체에 `AuditLog` 문자열이 단 1회도 없다). 지금까지 만든 9개 도메인 모듈(`chatbot-groups`/`chatbots`/`intents`/`keywords`/`homonyms`/`contexts`/`dialog-nodes`/`faqs`/`channels`)의 등록·수정·삭제가 **한 건도 기록되지 않았다** | 감사로그는 **소급 백필이 불가능**하다. 도입을 미루는 기간만큼 이력이 영구 결손된다 |
| ④ | `apps/web`에 로그인 화면이 없고(`App.tsx` 라우트 10종에 `/login` 없음), `apps/web/src/api/client.ts`의 401 분기는 주석만 있는 빈 블록이다 | 인증을 켜면 관리자 콘솔이 **즉시 전면 사용 불가**가 된다. 프런트 작업이 이 그룹의 필수 구성요소다 |

즉 이 그룹은 **새 화면 몇 개를 추가하는 그룹이 아니라, 이미 배포된 11개 컨트롤러·9개 도메인 모듈·1개 프런트 앱 전체에 걸쳐 횡단 관심사를 채워 넣는 그룹**이다. 범위 산정과 회귀 위험 관리가 이 문서의 핵심 과제다.

### 1.2 목적

1. 이메일+비밀번호 기반 **실제 인증**을 도입하고, 인증되지 않은 요청이 관리자 API에 도달하지 못하게 한다(No.12).
2. `PermissionGuard`를 **실제 동작하는 RBAC 가드**로 채우고, 이미 부착된 75개 데코레이터와 호환되는 권한 체계를 확정한다(No.12).
3. 회원(사용자) 등록·수정·비활성화와 역할 부여를 관리자 콘솔에서 수행하게 한다(No.12).
4. **금지어/비속어 필터**를 최종 사용자 대화 파이프라인에 적용한다(No.12).
5. **전 메뉴의 등록/수정/삭제 이력을 기록**하고 조회·추적할 수 있게 한다(No.13).

## 2. 사용자 역할 및 시나리오

### 2.1 역할

이 그룹에서 **역할이 처음으로 실제 의미를 갖는다**(지금까지는 문서상 개념일 뿐 코드가 구분하지 않았다).

| 역할 | 정의 | 대표 활동 |
|---|---|---|
| **ADMIN**(시스템 관리자) | 시스템 전체 관리자 | 회원 등록/역할 부여/비활성화, 금지어 사전 관리, 이력 조회, 챗봇 영구 삭제 |
| **EDITOR**(챗봇 편집자) | 챗봇·대화 자산 편집자 | 챗봇 생성/설정/보관, 대화 설계 전반, 채널 설정, 시뮬레이션 |
| **VIEWER**(운영 모니터) | 조회 전용 | 챗봇·대화 자산·채널·대시보드 조회, 시뮬레이션 실행(읽기 성격) |
| 최종 사용자(End User) | 위젯 이용자 | **인증 대상이 아니다.** 공개 대화 API는 레이트리밋·Origin 가드로만 보호된다(ADR-0011) |

### 2.2 사용자 시나리오

**S-1. 최초 기동과 부트스트랩 (ADMIN)**
새로 구축한 서버에 접속하면 `/login`으로 리다이렉트된다. 설치 담당자는 seed가 생성한 초기 ADMIN 계정(`BOOTSTRAP_ADMIN_EMAIL`)과 초기 비밀번호로 로그인한다. 최초 로그인이므로 **비밀번호 변경 화면이 강제로 뜨고**, 변경 전에는 다른 화면으로 이동할 수 없다. 변경 후 대시보드가 열린다.

**S-2. 로그인과 세션 유지 (전 역할)**
편집자가 아침에 콘솔을 연다. 이메일·비밀번호를 입력하고 로그인하면 상단 바 오른쪽에 이름과 `편집자` 배지가 나타난다. 브라우저를 닫았다가 2시간 안에 다시 열면 **재로그인 없이** 이어서 작업한다(유휴 만료 전).

**S-3. 잘못된 로그인 (전 역할)**
비밀번호를 세 번 틀리면 "이메일 또는 비밀번호가 올바르지 않습니다"라는 **동일한 문구**가 계속 표시된다(계정 존재 여부를 알려주지 않는다). 5회째에 "로그인 시도가 너무 많습니다. 15분 후 다시 시도해 주세요"로 바뀐다.

**S-4. 권한별 화면 접근 제한 (VIEWER)**
모니터 역할 사용자가 챗봇 상세를 연다. 대시보드·설정·스킨·응답테스트·채널·대화설계 탭은 모두 보이지만 **저장/삭제/추가 버튼이 화면에 없다**. 상단 바에도 `시스템 설정` 메뉴가 보이지 않는다. 주소창에 `/settings/users`를 직접 입력하면 **"이 페이지에 접근할 권한이 없습니다"** 안내 화면이 뜨고 홈으로 돌아가는 링크가 제공된다.

**S-5. 권한 없는 API 직접 호출 (VIEWER)**
같은 사용자가 개발자 도구로 `DELETE /api/v1/chatbots/:id`를 직접 호출한다. 서버는 **`403`(`FORBIDDEN`)** 을 반환하고 챗봇은 그대로다. 이 시도는 이력에 `PERMISSION_DENIED`로 기록된다.

**S-6. 세션 만료 (EDITOR)**
편집자가 노드 편집 폼을 절반쯤 채운 채 회의에 다녀왔다. 저장을 누르자 서버가 `401`을 반환한다. 화면은 **입력한 내용을 그대로 유지한 채** "로그인이 만료되었습니다. 다시 로그인해 주세요" 모달을 띄운다. 모달에서 비밀번호를 입력해 재인증하면 **모달이 닫히고 작성 중이던 폼이 그대로** 남아 있어 저장을 다시 누르면 성공한다.

**S-7. 회원 등록과 역할 부여 (ADMIN)**
관리자가 `시스템 설정 > 회원 관리`에서 `회원 추가`를 누른다. 이메일·이름·역할(편집자)을 입력하면 **임시 비밀번호가 1회만 화면에 표시**되고 "이 값은 다시 볼 수 없습니다"라는 안내와 복사 버튼이 함께 나온다. 관리자는 이를 당사자에게 전달한다. 당사자는 첫 로그인 시 비밀번호 변경을 강제당한다.

**S-8. 권한 즉시 회수 (ADMIN)**
퇴사자가 생겨 관리자가 해당 계정을 `비활성`으로 바꾼다. 그 사람이 열어둔 탭에서 저장을 누르면 **즉시 `401`** 이 반환되고 재로그인도 실패한다("비활성화된 계정입니다"). 역할을 EDITOR→VIEWER로 낮춘 경우에도 **다음 요청부터 바로** 쓰기가 `403`이 된다(재로그인 불필요).

**S-9. 마지막 관리자 보호 (ADMIN)**
관리자가 실수로 자기 자신을 VIEWER로 바꾸려 한다. 시스템에 ADMIN이 자기 하나뿐이므로 `409`(`LAST_ADMIN`)와 함께 "마지막 관리자의 역할은 변경할 수 없습니다"가 표시되고 변경되지 않는다.

**S-10. 금지어 사전 등록 (ADMIN)**
관리자가 `시스템 설정 > 금지어 관리`에서 비속어 목록을 등록한다. 각 단어에 정책(`차단` / `경고만`)을 지정한다. 화면 하단의 **`문장으로 시험하기`** 입력창에 "이런 XX 서비스가 다 있나"를 넣고 실행하면 탐지된 단어와 적용될 정책이 즉시 표시된다.

**S-11. 최종 사용자의 금지어 발화 (End User)**
방문자가 위젯에 욕설이 섞인 질문을 보낸다. `차단` 정책 단어이므로 대화 엔진은 **해석 자체를 하지 않고** "바람직하지 않은 표현이 포함되어 있습니다. 다시 입력해 주세요"라는 안내만 반환한다. 대화 로그에는 마스킹된 문장이 `isAnswered=false`, `blockedByFilter=true`로 남는다.

**S-12. 봇 응답의 금지어 차단 (End User)**
관리자가 실수로 FAQ 답변에 금지어를 넣어 저장했다. 저장은 막히지 않지만, 최종 사용자에게 응답이 나갈 때 해당 부분이 `***`로 **마스킹되어 전달**된다.

**S-13. "누가 이걸 지웠지?" (ADMIN)**
어제까지 있던 의도 `주문_배송조회`가 사라졌다. 관리자가 `시스템 설정 > 이력 관리`에서 대상 유형 `의도`, 기간 `최근 7일`로 필터링한다. 목록에 `2026-09-19 14:22 / 김편집(EDITOR) / 삭제 / 의도 "주문_배송조회"` 행이 보인다. 행을 펼치면 삭제 직전 값(예문 12건 포함)이 표시되어 무엇을 복구해야 하는지 알 수 있다.

**S-14. 대량 작업 이력 (ADMIN)**
같은 날 의도 엑셀 업로드가 있었다. 이력에는 **5,000행이 5,000건으로 쌓이지 않고** `대량 등록 / 의도 / 신규 4,812건·갱신 188건` **한 건의 요약**으로 기록돼 있다. 상세를 펼치면 업로드 파일명과 건수 내역이 보인다.

**S-15. 이력 대량 조회 (ADMIN)**
이력이 수십만 건 쌓인 상태에서 관리자가 필터 없이 이력 화면을 연다. 화면은 **기본 최근 30일**로 자동 제한되어 1초 안에 표시되고, "조회 기간은 최대 90일까지 지정할 수 있습니다"라는 안내가 필터 옆에 붙어 있다.

**S-16. 이력은 고칠 수 없다 (ADMIN)**
관리자가 자신의 삭제 기록을 지우고 싶어도 **이력 화면에는 수정/삭제 기능이 없고 API도 존재하지 않는다**.

## 4. 기능별 요구사항

### 4.1 No.12 — 회원·권한·보안 관리

기준 목록의 기능 설명은 4요소다: **(a) 회원(그룹)관리 · (b) 권한관리 · (c) 로그인 정책 · (d) 금지어/비속어 필터.** 이번 Phase의 대응은 (a) **역할 기반으로 구현, 조직 그룹은 제외**(J-7) / (b) **전면 구현** / (c) **전면 구현, MFA 제외**(J-1, J-2) / (d) **대화 파이프라인 2지점에 구현**(J-3)이다.

#### 4.1.1 인증 / 로그인 정책 (c) — J-1 결정

**결정: 이메일+비밀번호 인증 + 서버가 보관하는 불투명 세션 토큰(`Session` 테이블) + httpOnly 쿠키 전달. JWT는 채택하지 않는다.** 근거:

1. **즉시 회수가 이 그룹의 수용기준이다.** S-8(계정 비활성화·역할 강등의 즉시 반영)은 감사·보안 기능의 기본 기대치이며 AC-12B-8/AC-12C-9로 검증한다. 무상태 JWT는 만료 전까지 회수할 수 없어 이 AC를 통과하려면 결국 **서버 측 무효화 목록(=세션 테이블)** 을 같이 두어야 한다. 그러면 JWT의 유일한 장점(무상태)이 사라진다.
2. **확장성 원칙과 충돌하지 않는다.** `개발명세서.md` §5는 "단일 인스턴스 전제의 서버 상태는 인터페이스로 추상화"를 요구하는데, 세션을 **DB 테이블**에 두면 애초에 프로세스 로컬 상태가 아니므로 다중 인스턴스 전환 시 손댈 곳이 없다(레이트리밋 카운터·번들 캐시와 다른 점).
3. **토큰을 JS가 읽지 못해야 한다.** `localStorage` 보관은 XSS 1건으로 전 계정 탈취가 되고, 메모리 보관은 새로고침마다 로그아웃되어 실사용이 불가능하다. httpOnly 쿠키가 두 문제를 동시에 푼다.
4. **CSRF는 구조로 막는다.** `SameSite=Lax` 쿠키는 크로스사이트 **POST/PATCH/DELETE에 전송되지 않으므로** 상태 변경 API가 전부 비-GET인 현재 구조(파괴적 동작의 GET 노출 금지 — `개발명세서.md` §4.1)에서 CSRF 토큰 없이도 방어된다.
5. **개발 환경 구성**: `apps/web`(5173)과 `apps/api`(3000)가 다른 출처이므로, dev는 **Vite 프록시로 `/api`를 동일 출처화**하는 것을 권고한다(`VITE_API_BASE_URL`이 이미 환경변수라 값만 `/api/v1`로 바꾸면 된다). 이 경우 CORS 자격증명 설정이 불필요해지고 운영(리버스 프록시 동일 출처)과 구성이 일치한다. 최종 방식은 `system-architect`가 확정한다.

#### 4.1.2 권한 관리(RBAC) (b) — J-6 결정 + 기존 데코레이터 감사

**결정: 역할 3종을 고정하고, 역할→권한 매핑을 코드 상수로 둔다. `Role`/`Permission` 테이블은 만들지 않는다.** 근거:

1. **권한은 이미 코드에 하드코딩돼 있다.** `@RequirePermission('chatbot:purge')`는 소스에 박힌 문자열이다. 권한 목록을 DB로 옮겨도 "새 권한 추가"는 여전히 코드 수정이 필요하므로, 테이블은 **유연성의 착시**만 만들고 정합성 검증 부담(DB의 권한 ↔ 코드의 데코레이터 동기화)을 새로 만든다.
2. **소비하는 수용기준이 없다.** "관리자가 커스텀 역할을 만든다"는 시나리오는 기준 목록 No.12의 설명("회원(그룹)관리, 권한관리")에서 도출되지 않으며, 쓰기 주체·수용기준 없는 구조를 만들지 않는 선례가 있다(ADR-0004, DD-20).
3. **이미 단일 소스가 있다.** `packages/shared-types/src/security.ts`의 `RoleName`(ADMIN/EDITOR/VIEWER) zod enum과 Prisma `User.role String`은 §3.1 "enum은 DB String + zod 단일 소스" 규약을 이미 따르고 있다.
4. **되돌리기 쉽다.** 매핑이 상수 1곳이므로, 커스텀 역할이 필요해지는 시점(No.45 규제산업 거버넌스)에 테이블로 승격하는 비용은 크지 않다.

**기존 데코레이터 감사 결과**(전수 조사는 **부록 A**): 11개 컨트롤러·**75개 핸들러**에 **9종**의 권한 문자열이 부착돼 있다. 아래 표가 확정 권한 체계이며 **기존 데코레이터 값은 한 글자도 바꾸지 않는다**(변경 시 75곳 재검토가 필요하고 회귀 위험이 이득보다 크다).

#### 4.1.4 금지어/비속어 필터 (d) — J-3 결정

**결정: 필터는 최종 사용자 대화 파이프라인의 2지점에만 적용한다 — ① 입력 수신 직후(해석 전) ② 응답 반환 직전. 관리자 콘솔의 텍스트 입력(의도 예문·FAQ 질문/답변·노드 아웃풋 등)에는 적용하지 않는다.** 근거:

1. **선행 문서 2건이 이미 이 2지점을 지정했다.** `개발명세서.md` §5 보안("금지어/비속어 필터(사전 매칭, No.12 — 적용 지점은 *입력 수신 직후*와 *응답 반환 직전* 2곳)")과 `quality-channel.md` NFR-S11·EX-P-11이 동일하게 명시했다. 이번에 다른 해석을 채택하면 확정된 설계 규약 2건을 뒤집게 된다.
2. **관리자 입력 검열은 "응답 반환 직전" 필터가 자동으로 커버한다.** FAQ 답변·노드 텍스트가 금지어를 포함해도 그것이 문제가 되는 순간은 **최종 사용자에게 도달할 때**이며, 출구 필터가 그 지점을 이미 막는다(S-12). 입구를 한 번 더 막는 것은 **같은 위험에 대한 이중 방어**이고, 9개 도메인 모듈 전부의 저장 경로에 검증을 추가하는 비용을 새로 만든다.
3. **오탐 비용이 비대칭이다.** 관리자 입력을 차단하면 정상 업무 용어(지역명·상품명·의학 용어 등)가 사전에 걸릴 때 **업무가 멈춘다**. 반면 대화 파이프라인의 오탐은 한 턴의 안내 메시지로 끝난다.
4. **관리자 입력은 이미 추적된다.** 이번 그룹이 감사로그를 도입하므로 "누가 이 문구를 넣었는지"가 남는다 — 사전 차단이 아니라 사후 추적으로 통제하는 것이 내부 사용자에 대한 적절한 수준이다.

### 4.2 No.13 — 이력관리(감사추적)

기준 목록의 기능 설명은 2요소다: **(a) 전 메뉴 등록/수정/삭제 이력 기록 · (b) 레거시 API 연동 상세 로그.** 이번 Phase의 대응은 (a) **전면 구현 + 기존 3개 그룹 소급 적용**(J-4) / (b) **Out of scope**(J-5)이다.

#### 4.2.1 감사로그 기록 — J-4 결정(소급 적용)

**결정: 지금까지 만들어진 9개 도메인 모듈 전체에 소급 적용한다. 다만 "기록 단위"와 "기록 필드"를 통제해 범위·용량 폭증을 막는다.** 근거:

1. **감사로그는 백필이 불가능하다.** 과거 변경 내역은 DB 어디에도 남아 있지 않다. 소급을 다음 Phase로 미루면 **그 기간의 이력이 영구히 존재하지 않는다**. 이는 "나중에 추가하면 되는" 다른 기능들과 성격이 근본적으로 다르다.
2. **설계 원칙이 이미 그렇게 세워져 있다.** `개발명세서.md` §2.1은 서비스 계층의 책임을 "비즈니스 규칙의 단일 진입점(**향후 `AuditLog` 기록 지점**)"으로 명시했고, `quality-channel.md` FR-11-13도 채널 서비스를 "향후 `AuditLog` 기록 지점"으로 설계했다. 소급을 안 하면 이 설계 의도가 실현되지 않은 채 남는다.
3. **지금이 가장 싸다.** 모듈은 앞으로만 늘어난다(No.14/15 + 확장기능 14종). 9개 모듈일 때 하는 것과 20개 모듈일 때 하는 것의 비용 차이는 크다.
4. **실제 작업량은 보이는 것보다 작다.** 쓰기 서비스 메서드는 대부분 이미 "존재 확인용 `findUnique`"를 수행하고 있어 `beforeValue`를 얻기 위한 추가 조회가 거의 필요 없다. 메서드당 기록 호출 1~2줄 수준이다.
5. **"기본기능 13번"의 문구 자체가 "전 메뉴"다.** 이번 그룹에서 만든 3개 메뉴(회원/금지어/이력)만 기록하면, 관리자가 이력 화면을 열었을 때 **정작 궁금한 챗봇·대화 자산 변경이 하나도 없는** 빈 껍데기 기능이 된다.

> **범위 통제 장치**(이것이 없으면 소급은 위험한 결정이다):
> - 기록 대상은 **쓰기 API만**이다. 조회·시뮬레이션·비교·공개 대화는 기록하지 않는다.
> - **대량 작업은 행당 1건이 아니라 배치 1건 + 요약**으로 기록한다(FR-13-5).
> - `beforeValue`/`afterValue`는 **전체 엔터티 덤프가 아니라 허용 필드 화이트리스트 스냅샷**이며 크기 상한을 둔다(FR-13-11).
> - 기록 실패가 **본 동작을 실패시키지 않는다**(FR-13-13) — 소급 적용이 기존 75개 API의 가용성을 떨어뜨리지 않게 하는 안전장치.

| ID | 요구사항 |
|---|---|
| FR-13-1 | 공통 `AuditLogService.record()`를 도입하고, **모든 쓰기 서비스가 이 단일 진입점을 통해 기록**한다(FR-0-27). 컨트롤러·매퍼·`lib/`는 감사로그를 알지 못한다. |
| FR-13-2 | **소급 대상(필수)**: `chatbot-groups`, `chatbots`, `intents`, `keywords`, `homonyms`, `contexts`, `dialog-nodes`, `faqs`, `channels` — 9개 모듈의 생성/수정/삭제 경로 전부. |
| FR-13-3 | **신규 대상**: `users`(등록/수정/역할변경/상태변경/비밀번호초기화), `banned-words`(등록/수정/삭제), `auth`(로그인 성공/실패/로그아웃). |
| FR-13-4 | `action` 값 집합을 확장한다: `CREATE`, `UPDATE`, `DELETE`, **`PURGE`**(영구삭제), **`STATUS_CHANGE`**(챗봇 상태전이·계정 상태전이), **`BULK_DELETE`**, **`IMPORT`**(대량 업로드 커밋), **`COPY`**, **`LOGIN`**, **`LOGIN_FAILED`**, **`LOGOUT`**, **`PERMISSION_DENIED`**. 기존 3종만으로는 "보관"과 "영구삭제"를 구분할 수 없다(ADR-0002가 굳이 권한까지 나눈 동작인데 이력에서 같아지면 안 된다). |
| FR-13-5 | **대량 작업 기록 단위**: `POST /intents/bulk-delete`(N건), `POST /intents/import/commit`(수천 행)은 **배치 1건**으로 기록하고 `afterValue`에 `{ created: n, updated: m, deleted: k, fileName?, targetIds: [...최대 50건] }` 요약을 담는다. 50건 초과 시 ID 목록은 절단하고 `truncated: true`를 표기한다. |
| FR-13-6 | **챗봇 컨텍스트 추적**: 대화 자산(의도/키워드/노드/FAQ/컨텍스트/동음이의어/채널) 변경은 `chatbotId`를 함께 기록한다. 없으면 "이 챗봇에 무슨 일이 있었나"를 조회할 수 없다(`targetId`는 의도 ID라 챗봇으로 역추적이 불가능하다). |
| FR-13-7 | **표시용 스냅샷 기록**: `actorEmail`, `actorRole`, `targetName`(챗봇명·의도명 등)을 기록 시점 값으로 함께 저장한다. 근거: 대상이 삭제되거나 이름이 바뀌면 이력 목록이 **UUID 나열**이 되어 사용 불가능해진다. 로그는 "그 시점의 사실 기록"이라는 기존 판단과 일치한다(§3.1 `ConversationLog` 예외 조항). |
| FR-13-8 | **인증 이력**: `LOGIN`/`LOGIN_FAILED`/`LOGOUT`은 `targetType='SESSION'`으로 기록하고 **IP·User-Agent**를 담는다. `LOGIN_FAILED`에는 시도된 이메일만 기록하고 **비밀번호 문자열은 어떤 형태로도 기록하지 않는다**. |
| FR-13-9 | **권한 거부 이력**: `403`이 발생하면 `PERMISSION_DENIED`로 기록한다(요청 경로·요구 권한·사용자). 단 **단일 사용자의 반복 실패가 로그를 폭증시키지 않도록**, 동일 사용자·동일 경로 조합은 60초 내 1건으로 합친다. |
| FR-13-10 | `actorId`가 없는 기록(시스템 동작·부트스트랩 seed)은 `actorId=null` + `actorEmail='system'`으로 남긴다. |
| FR-13-11 | **민감정보 금지**: `beforeValue`/`afterValue`에 비밀번호·해시·세션 토큰·**대화 원문**·PII를 담지 않는다. 기록 대상 필드는 도메인별 **화이트리스트**로 정의하고, 직렬화 결과가 상한(기본 8KB)을 넘으면 절단 후 `truncated: true`를 표기한다. |
| FR-13-12 | 기록은 **본 동작과 같은 트랜잭션에서 수행**하는 것을 권고한다(본 동작이 롤백되면 이력도 남지 않아야 한다). 트랜잭션 경계가 없는 경로는 동작 성공 직후 기록한다. 최종 방식은 `system-architect`. |
| FR-13-13 | **감사로그 기록 실패가 본 동작을 실패시켜서는 안 된다**(트랜잭션 내 기록을 택하더라도 기록 실패는 경고 로그 후 무시). 소급 적용이 기존 API의 가용성을 떨어뜨리지 않게 하는 안전장치다(`ConversationLog` 적재 실패 정책과 동일 — FR-11-24). |
| FR-13-14 | **`AuditLog`는 append-only다.** 수정·삭제 API를 제공하지 않으며 ADMIN도 예외가 아니다(FR-13-20). |

## 7. 수용기준 (Acceptance Criteria)

### AC-12A. 인증 / 로그인 정책

- **AC-12A-1** Given 유효한 이메일·비밀번호, When `POST /auth/login`을 호출하면, Then `200`과 `{ user }`가 반환되고 httpOnly 쿠키가 설정되며 `Session` 1행이 생성된다.
- **AC-12A-2** Given 존재하지 않는 이메일, When 로그인하면, Then `401`(`INVALID_CREDENTIALS`)이며 **존재하는 이메일 + 틀린 비밀번호와 응답 본문·상태코드가 동일**하다.
- **AC-12A-3** Given 로그인 응답, When 본문을 검사하면, Then `passwordHash`·세션 토큰 원문이 **포함되어 있지 않다**.
- **AC-12A-4** Given 5회 연속 실패한 계정, When 6회째(올바른 비밀번호로) 시도하면, Then `401`(`ACCOUNT_LOCKED`)이며 잠금 해제 시간이 안내된다.
- **AC-12A-5** Given 잠긴 계정, When 잠금 시간이 지난 뒤 올바른 비밀번호로 로그인하면, Then 성공하고 실패 카운터가 0이 된다.
- **AC-12A-6** Given 로그인된 세션, When `POST /auth/logout` 후 같은 쿠키로 API를 호출하면, Then `401`이다.
- **AC-12A-7** Given 절대 만료 시간이 지난 세션, When API를 호출하면, Then `401`(`SESSION_EXPIRED`)이고 슬라이딩 갱신으로 되살아나지 않는다.
- **AC-12A-8** Given 유휴 만료 직전 세션, When API를 호출하면, Then 성공하고 `lastSeenAt`이 갱신된다.
- **AC-12A-9** Given 본인 비밀번호를 변경, When 변경 전 발급된 **다른 세션**으로 API를 호출하면, Then `401`이다.
- **AC-12A-10** Given 비밀번호 정책 위반(9자), When 변경을 시도하면, Then `400`(`PASSWORD_POLICY`)이며 `details`에 위반 규칙이 담긴다.
- **AC-12A-11** Given `mustChangePassword=true` 사용자, When `/chatbots`를 호출하면, Then `403`(`PASSWORD_CHANGE_REQUIRED`)이고 `/auth/me`·`/auth/password`는 정상 동작한다.
- **AC-12A-12** Given DB에 사용자가 0명, When API를 기동하면, Then 기동에 성공하고 경고 로그가 남는다(기동 실패 아님).
- **AC-12A-13** Given seed 실행 직후, When 부트스트랩 ADMIN으로 로그인하면, Then 성공하며 `mustChangePassword=true`다.
- **AC-12A-14** Given 로그인 성공·실패·로그아웃, When 이력을 조회하면, Then 각각 `LOGIN`/`LOGIN_FAILED`/`LOGOUT`으로 기록되고 **어떤 레코드에도 비밀번호 문자열이 없다**.

### AC-12B. 권한(RBAC)

- **AC-12B-1** Given 미인증 요청, When `GET /chatbots`를 호출하면, Then `401`(`UNAUTHENTICATED`)이다.
- **AC-12B-2** Given 미인증 요청, When `GET /api/health`, `GET /public/chatbots/:slug/config`, `POST /public/chatbots/:slug/messages`를 호출하면, Then **전부 기존과 동일하게 동작**한다(FR-0-29).
- **AC-12B-3** Given VIEWER 세션, When `GET /chatbots`를 호출하면 `200`, When `POST /chatbots`를 호출하면 **`403`(`FORBIDDEN`)** 이다.
- **AC-12B-4** Given EDITOR 세션, When `DELETE /chatbots/:id`(보관)는 `204`, When `POST /chatbots/:id/permanent-delete`는 **`403`** 이다.
- **AC-12B-5** Given VIEWER 세션으로 프런트에서 버튼이 보이지 않는 상태, When 개발자 도구로 해당 API를 직접 호출하면, Then `403`이고 **DB가 변경되지 않는다**.
- **AC-12B-6** Given 어떤 역할이든, When `GET /audit-logs`를 호출하면, Then ADMIN만 `200`, 나머지는 `403`이다.
- **AC-12B-7** Given 권한 부족 응답(`403`), When 본문을 검사하면, Then **요구 권한 문자열이 포함되어 있지 않다**(FR-12-23).
- **AC-12B-8** Given EDITOR 세션이 열려 있는 상태에서 ADMIN이 그 사용자를 VIEWER로 강등, When **재로그인 없이** 쓰기 API를 호출하면, Then 즉시 `403`이다.
- **AC-12B-9** Given 소스 전체, When `@RequirePermission`에 유니온에 없는 문자열을 넣으면, Then **타입 검사가 실패한다**(FR-12-18).
- **AC-12B-10** Given 가드를 부착하지 않은 신규 컨트롤러를 추가, When 미인증으로 호출하면, Then `401`이다(fail-closed, FR-0-24).
- **AC-12B-11** Given ADMIN 세션, When `GET /roles`를 호출하면, Then 역할 3종과 역할별 권한 목록이 반환되고 프런트가 이를 그대로 사용한다.
- **AC-12B-12** Given `403` 발생, When 이력을 조회하면, Then `PERMISSION_DENIED` 기록이 존재하고 동일 조합 반복 실패가 60초 내 1건으로 합쳐진다.
- **AC-12B-13** Given 권한 없는 사용자가 존재하지 않는 리소스 ID로 쓰기 요청, When 호출하면, Then `404`가 아니라 **`403`** 이다(FR-12-22).

### AC-12C. 회원 관리

- **AC-12C-1** Given ADMIN, When 회원을 등록하면, Then `201`과 함께 **임시 비밀번호가 1회 반환**되고 이후 어떤 API로도 재조회할 수 없다.
- **AC-12C-2** Given 이미 존재하는 이메일(대소문자만 다름), When 등록하면, Then `409`(`DUPLICATE_EMAIL`)다.
- **AC-12C-3** Given 등록된 회원, When 임시 비밀번호로 첫 로그인하면, Then 비밀번호 변경이 강제된다.
- **AC-12C-4** Given ADMIN 본인, When 자기 역할을 변경하거나 자기를 비활성화하면, Then `409`(`SELF_MODIFICATION`)다.
- **AC-12C-5** Given ACTIVE ADMIN이 1명뿐, When 그 계정을 강등/비활성화하면, Then `409`(`LAST_ADMIN`)다.
- **AC-12C-6** Given ACTIVE ADMIN이 2명, When 한 명을 강등하면, Then `200`으로 성공한다.
- **AC-12C-7** Given 회원 목록 응답, When 본문을 검사하면, Then `passwordHash` 필드가 **존재하지 않는다**.
- **AC-12C-8** Given 회원 삭제 API, When 경로를 탐색하면, Then **존재하지 않는다**(비활성화로 대체, FR-12-30).
- **AC-12C-9** Given 로그인 중인 사용자를 ADMIN이 비활성화, When 그 사용자가 API를 호출하면, Then 즉시 `401`(`ACCOUNT_DISABLED`)이고 재로그인도 실패한다.
- **AC-12C-10** Given 비밀번호 초기화 실행, When 기존 세션으로 API를 호출하면, Then `401`이다.
- **AC-12C-11** Given 회원 등록/수정/상태변경, When 이력을 조회하면, Then 각 동작이 기록되고 `beforeValue`/`afterValue`에 **비밀번호 관련 값이 없다**.

### AC-12D. 금지어/비속어 필터

- **AC-12D-1** Given `BLOCK` 정책 금지어를 포함한 사용자 발화, When 공개 대화 API로 전송하면, Then 고정 안내 아웃풋이 반환되고 **대화 엔진이 호출되지 않는다**(매칭 결과가 없다).
- **AC-12D-2** Given 위 요청 후, When `ConversationLog`를 조회하면, Then 1행이 `isAnswered=false`로 적재되고 저장된 문장에 **금지어 원문이 없다**.
- **AC-12D-3** Given `WARN` 정책 금지어를 포함한 발화, When 전송하면, Then **정상 해석되어 평소와 같은 응답**이 나온다.
- **AC-12D-4** Given 봇 응답 텍스트에 금지어가 포함된 FAQ, When 최종 사용자가 그 FAQ를 매칭시키면, Then 응답에서 해당 부분이 `***`로 마스킹되어 전달된다.
- **AC-12D-5** Given 같은 입력, When **관리자 시뮬레이션 API**로 호출하면, Then 필터가 적용되지 않고 원본 동작이 그대로 확인된다(FR-12-42).
- **AC-12D-6** Given 금지어 사전이 0건, When 대화를 요청하면, Then 응답 시간이 필터 도입 전과 유의미하게 다르지 않다.
- **AC-12D-7** Given `POST /banned-words/test`에 문장을 보내면, Then 탐지 단어·정책·마스킹 미리보기가 반환된다.
- **AC-12D-8** Given 금지어를 추가/수정/삭제, When 즉시 대화를 요청하면, Then **캐시 TTL을 기다리지 않고** 새 사전이 적용된다.
- **AC-12D-9** Given 정규식 문자열(`.*`)을 단어로 등록 시도, When 저장하면, Then 리터럴 문자열로 취급되며 **정규식으로 해석되지 않는다**.
- **AC-12D-10** Given 대소문자·공백이 다른 변형(`X X`, `xx`), When 정규화 규칙에 해당하면, Then 동일하게 탐지된다.
- **AC-12D-11** Given 금지어 사전 API, When VIEWER/EDITOR가 호출하면, Then `403`이다.

### AC-13. 이력관리

- **AC-13-1** Given EDITOR가 의도를 생성, When 이력을 조회하면, Then `CREATE`/`targetType='Intent'`/`targetName`/`chatbotId`/`actorEmail`이 채워진 1행이 존재한다.
- **AC-13-2** Given 의도를 수정, When 상세를 조회하면, Then `beforeValue`/`afterValue`가 있고 **변경된 필드만** 대비 표시할 수 있다.
- **AC-13-3** Given 의도를 삭제, When 이력을 조회하면, Then `DELETE`와 함께 삭제 직전 값이 `beforeValue`에 남아 있다.
- **AC-13-4** Given 챗봇 **보관**과 **영구삭제**를 각각 수행, When 이력을 조회하면, Then `DELETE`와 `PURGE`로 **구분되어** 기록된다.
- **AC-13-5** Given 5,000행 엑셀 임포트 커밋, When 이력을 조회하면, Then **1행**이 `IMPORT`로 기록되고 건수 요약이 담긴다(5,000행이 아니다).
- **AC-13-6** Given 의도 20건 대량 삭제, When 이력을 조회하면, Then `BULK_DELETE` 1행 + 대상 ID 요약(최대 50건)이 기록된다.
- **AC-13-7** Given 9개 도메인 모듈 각각의 생성/수정/삭제, When 이력을 조회하면, Then **모든 모듈의 기록이 존재한다**(소급 적용 완료 증명 — 모듈별 최소 1케이스).
- **AC-13-8** Given 챗봇 하위 자산 변경, When `chatbotId` 필터로 조회하면, Then 해당 챗봇의 자산 변경 이력이 모두 조회된다.
- **AC-13-9** Given 기간을 지정하지 않고 조회, When 응답을 검사하면, Then 최근 30일로 제한되며 그 사실이 응답 또는 화면에 명시된다.
- **AC-13-10** Given 120일 기간을 요청, When 호출하면, Then `400`(`AUDIT_RANGE_TOO_WIDE`)이다.
- **AC-13-11** Given 이력 10만 건, When 목록 1페이지를 조회하면, Then P95 1초 이내에 응답한다.
- **AC-13-12** Given 이력 API 전체, When 수정·삭제 메서드를 탐색하면, Then **존재하지 않는다**.
- **AC-13-13** Given 감사로그 기록이 실패하도록 강제, When 챗봇을 수정하면, Then **수정은 성공**하고 경고 로그만 남는다.
- **AC-13-14** Given 본 동작이 실패(유효성 오류)한 요청, When 이력을 조회하면, Then **기록이 남지 않는다**(성공한 변경만 기록).
- **AC-13-15** Given 삭제된 챗봇의 과거 이력, When 조회하면, Then `targetName` 덕분에 **이름이 표시**되고 링크 대신 "삭제됨" 표기가 나온다.
- **AC-13-16** Given 기존 성능 기준(목록 300ms/임포트 커밋 20초), When 감사로그 소급 적용 후 측정하면, Then 기준을 여전히 만족한다(NFR-P3).
- **AC-13-17** Given 어떤 이력 레코드든, When `beforeValue`/`afterValue`를 검사하면, Then 대화 원문·PII·비밀번호가 포함되어 있지 않다.

### AC-U. 관리자 콘솔

- **AC-U-1** Given 미인증 상태, When `/chatbots`에 직접 접근하면, Then `/login`으로 이동하고 로그인 후 **`/chatbots`로 복귀**한다.
- **AC-U-2** Given 로그인 화면, When 키보드만으로 이메일·비밀번호 입력·제출을 수행하면, Then 전 과정이 완료된다.
- **AC-U-3** Given 잘못된 비밀번호, When 제출하면, Then 인라인 오류가 표시되고 포커스가 이동하며 스크린리더로 전달된다.
- **AC-U-4** Given 노드 편집 폼에 미저장 내용이 있는 상태에서 세션이 만료, When 저장을 누르면, Then **입력 내용이 유지된 채** 재로그인 모달이 뜨고, 재인증 후 저장이 성공한다.
- **AC-U-5** Given VIEWER 로그인, When 챗봇 상세를 열면, Then 저장/삭제/추가 버튼이 **렌더되지 않는다**.
- **AC-U-6** Given VIEWER 로그인, When `/settings/users`에 직접 접근하면, Then 403 안내 화면이 표시된다(빈 화면·무한 로딩 아님).
- **AC-U-7** Given ADMIN 로그인, When 상단 바를 보면, Then `시스템 설정` 메뉴가 보이고 VIEWER에게는 보이지 않는다.
- **AC-U-8** Given 로그아웃, When 버튼을 누르면, Then 세션이 무효화되고 `/login`으로 이동하며 뒤로가기로 이전 화면 데이터가 보이지 않는다.
- **AC-U-9** Given 대량 업로드(multipart) 요청, When 인증 상태로 호출하면, Then **`postForm` 경로도 인증이 정상 동작한다**(FR-U-9).
- **AC-U-10** Given 위젯(`apps/widget`), When 인증 도입 후 임베드 페이지를 열면, Then **동작이 이전과 동일**하다(FR-U-10).
- **AC-U-11** Given 신규 화면 3종, When axe 스캔을 수행하면, Then 대비 위반 0건이다.

### AC-C. 공통/횡단

- **AC-C-1** 모든 신규 엔드포인트 응답이 대응 zod 스키마 파싱을 통과한다(계약 테스트).
- **AC-C-2** 기존 통합 테스트 2종이 인증 헬퍼 적용 후 **전부 통과**한다(회귀 0건).
- **AC-C-3** 기존 단위 테스트(엔진·lib 순수함수)는 **수정 없이** 통과한다(인증은 엔진에 침투하지 않는다).
- **AC-C-4** `@Public()`이 부착된 핸들러는 정확히 **5개**다(테스트로 개수 고정 — 우회 경로 회귀 방지). 대상은 아래 5곳이며, 5번 `POST /auth/logout`은 설계서 `security-audit-설계.md` **DD-45**(§8.2)가 FR-12-20의 4곳에서 1곳 늘려 공개 경로로 확정한 것이다 — 근거: FR-12-8이 "이미 만료된 세션으로 호출해도 `204`(멱등)"를 요구하는데 인증을 요구하면 만료 세션 로그아웃이 `401`이 되어 요구사항을 만족할 수 없고, 로그아웃은 세션을 파괴만 하므로 인증 없이 호출해도 공격자가 얻는 것이 없다.

  | # | 경로 | 핸들러 |
  |---|---|---|
  | 1 | `GET /api/health` | `HealthController#check` |
  | 2 | `GET /api/v1/public/chatbots/:slug/config` | `PublicConversationController#getConfig` |
  | 3 | `POST /api/v1/public/chatbots/:slug/messages` | `PublicConversationController#sendMessage` |
  | 4 | `POST /api/v1/auth/login` | `AuthController#login` |
  | **5** | **`POST /api/v1/auth/logout`** | `AuthController#logout` (DD-45로 추가) |

  `@Public()`은 클래스가 아니라 **핸들러**에 부착한다(부착 단위가 섞이면 개수 고정 테스트가 의미를 잃는다).

  > **갱신(2026-09-22 · FAQ/의도 매칭 고도화)**: `@Public()` 핸들러는 **정확히 6개**가 된다. 6번은 `GET /api/v1/public/chatbots/:slug/messages/:messageId`(`PublicConversationController#pollMessage`, 보류 답변 폴링)이며, 근거는 `decisions/ADR-0023-async-pending-answer-delivery.md` §2와 `nlu-rag-answering-설계.md` §11.1이다. 개수 고정 테스트는 무력화하지 않고 **6으로 갱신**한다(위 5개 표는 이력으로 보존).
- **AC-C-5** 신규 환경변수를 하나도 설정하지 않아도 API가 기동한다(FR-0-30).
- **AC-C-6** 공개 대화 API의 기존 AC(AC-P-1~15)가 전부 그대로 통과한다.

| # | 관찰 | 판단 |
|---|---|---|
| **A-1** | 권한 문자열 9종이 **어디에도 정의돼 있지 않다**(`RequirePermission(permission: string)`). 오타가 타입 검사에 걸리지 않는다 | **수정 대상**(FR-0-25, FR-12-18) — 유니온 타입화. 이 조치 없이 가드를 켜면 오타 1건이 영구 403을 만든다 |
