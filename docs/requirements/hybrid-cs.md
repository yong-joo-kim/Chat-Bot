### 1.2 이미 있는 것과 없는 것 (코드 확인)

| 사실 (파일:행) | 결과 |
|---|---|
| 공개 대화는 **요청/응답 HTTP 1턴**이다: `POST /public/chatbots/:slug/messages`(`public-conversation.controller.ts` 33~42행). 위젯은 **전송 버튼·버튼 클릭 때만** `client.sendMessage()`를 부른다(`apps/widget/src/ui/app.ts` 234~248행 `handleSend`) | ★ 서버가 위젯에게 **먼저 말할 경로가 없다.** 상담원 메시지를 받으려면 위젯이 어떤 형태로든 **스스로 요청을 반복**하거나 **연결을 유지**해야 한다 |
| **유일한 "서버 → 위젯 지연 전달" 선례 = 보류 답변 폴링**: 응답에 `pendingAnswer`가 있으면 위젯이 `GET …/messages/:messageId`를 최초 1.2초 → 1.5초 간격 → 90초 상한으로 폴링(`app.ts` 174~232행 · `core/pending-poll.ts` 15~16행 · 서버 `public-conversation.service.ts` 233~239행) | ★ **폴링 방식은 이미 검증된 패턴**이다(순수 로직 `core/` + 부수효과 `ui/` 분리, 세대 카운터로 이전 폴링 폐기 `app.ts` 45~46·186행). 단 이 경로는 **사용자 질문 1건 ↔ 답 1건**에 묶여 있어 상담원이 **먼저** 보내는 메시지를 표현할 수 없다 |

#### 1.3.2 "관찰 창" — 위젯이 조용할 때 상담원이 먼저 말을 거는 문제

카탈로그 원문은 "**모니터링 중** 미응답 누적 시 … 상담원 개입"이다 → 개입은 **상담원이 먼저** 시작한다. 그런데 위젯은 상담 중이 아닐 때 서버에 묻지 않는다(§1.2.1). 대안:

| 방식 | 설명 | 트래픽 | 판정 |
|---|---|---|---|
| 모든 열린 위젯이 상시 폴링 | 방문자 전원이 10초마다 조회 | **방문자 수에 비례** — 상담이 없는 챗봇에도 부하 | 기각 |
| **다음 발화 편승만** | 개입 사실을 사용자의 다음 메시지 응답에 실음 | 0 | 단독으로는 부족 — 미응답에 지친 사용자는 **말을 멈춘 뒤**일 가능성이 크다 |
| **관찰 창** ★ | 상담 기능이 켜진 챗봇에서 **이번 턴이 미응답(`isAnswered=false`, BLOCK 제외)이면** 응답에 `handoff.watch`(관찰 시간·간격)를 싣고, 위젯은 그 시간(기본 3분) 동안 **5초** 간격으로 상담 경로를 조회한다. 새 미응답이 오면 창이 연장된다 | **미응답을 겪은 세션만**, 창 1개당 최대 36회 | **채택 권고** — 경고 대상(= 개입 후보)이 정확히 "미응답을 겪은 세션"이다. 그 밖의 세션에 대한 개입은 **다음 발화 편승**으로 전달된다(한계 고지 — EX-CS-3) |

> 주: 외부 RAG로 넘어간 턴은 응답 시점에 결과를 모른다(`PENDING`). 이 턴은 관찰 창을 발급하지 않고, 보류 답변이 `FAILED`로 끝나면 위젯이 그 시점에 관찰 창을 연다(폴링 응답에 같은 필드 — architect 확정).

### 1.4 ★ 선결 쟁점 2 — "세션 단위 서버 상태가 필요한가, `sessionId`를 믿을 수 있는가"

#### 1.4.1 서버 상태의 모양 — 세션 테이블이 아니라 **상담 스레드**

| 후보 | 구조 | 판정 |
|---|---|---|
| X. 봉투에 "상담 중" 플래그 | 클라이언트가 보관 | **기각** — ADR-0009 §3 위반(상태전이·신원 값). 사용자가 플래그를 지우면 상담원 모르게 봇으로 돌아가고, 넣으면 상담원 큐를 오염시킨다 |
| Y. **모든 세션**을 서버 세션 테이블로(ADR-0009 전면 대체) | 방문 세션마다 행 1개 + 턴마다 갱신 | **기각** — 턴마다 쓰기 1회(SQLite 단일 작성자 — 개발명세서 305행 ⚠)·만료 정리 배치(ADR-0009 근거 60행)·봇 상태 봉투까지 옮기면 엔진·시뮬레이터·TC 전면 수정. 얻는 것(모니터링)은 **`ConversationLog` 읽기만으로 이미 얻을 수 있다**(§1.2.3) |
| **Z. 상담 스레드**(개입이 일어난 세션만) ★ | `HandoffSession`(세션 1개의 상담 1건: 상태·담당자·토큰 해시·시각) + `HandoffMessage`(상담 구간 메시지 순서열). **봇 대화 상태는 계속 봉투**, 모니터링은 **`ConversationLog` 최근 창 조회** | **채택 권고** — ADR-0009 근거 61행이 예고한 바로 그 모델("메시지 시퀀스 + 담당자 + 상태"). 행은 **개입이 일어난 세션에만** 생기므로 만료 배치가 필요 없고, 상담 이력 그 자체가 되어 **지울 대상이 아니다**(봉인 — J-12) |

→ ADR-0009는 **부분 갱신**: 결정 1(봇 대화 상태 세션 테이블 미도입)·2·3은 **유지**, 재검토 트리거 ①(No.24)은 "**상담 스레드 도입으로 해소**"로 기록. 트리거 ②(No.42 통합 인박스)·③(이력 복원)은 남는다.

**핫 경로 비용**: 상담 기능이 꺼진 챗봇 = 추가 조회 **0**(설정은 이미 턴마다 읽는 답변 설정 캐시에 동거 — §1.2.4). 켜진 챗봇 = **턴마다 `(chatbotId, sessionId)` 활성 상담 유일 조회 1회**(인덱스, ≤5ms). 턴마다 쓰기는 **0**(상담 구간 턴만 스레드에 적재).

#### 1.4.2 `sessionId` 신뢰 — 위협과 대응 (권고안 기준)

`sessionId`는 인증 수단이 아니다(`session.ts` 39행). 상담 스레드는 **세션별 서버 데이터를 공개 경로로 돌려주는 첫 사례**이므로 `sessionId`만으로 접근을 허용하면 안 된다.

| 위협 | 공격 방법 | 방어 | 남는 위험(수용) |
|---|---|---|---|
| **엿보기** — 남의 상담원 메시지 조회 | 피해자 `sessionId`를 알고 폴링 | ① **상담 토큰**(서버 발급 256비트 난수, **DB에는 해시만**, 상담 1건 한정·종료 시 무효)이 없으면 메시지 0건 ② 토큰은 **봉투 밖**(응답의 `handoff.token` → 위젯 별도 저장 키) — ADR-0009 §3 준수 | 토큰 발급 **이전**에 공격자가 먼저 가져가는 경쟁(아래 "선점") |
| **가장** — 사용자인 척 상담원에게 발화 | 피해자 `sessionId`로 `POST messages` | 상담 구간에서 **토큰 없는 발화는 상담원에게 전달하지 않는다**(사용자에게는 중립 안내 — EX-CS-10) | 없음 |
| **선점** — 개입 직후 토큰을 먼저 받음 | 피해자 `sessionId`를 **미리 알고**, 개입 순간에 먼저 폴링 | 토큰은 **1회만 발급**(재발급 없음). 두 번째 요청자는 토큰을 못 받고 "보낼 수 없음" 안내 → **정상 사용자가 즉시 알아채고**, 콘솔에 "확인되지 않은 연결 시도" 신호. 상담원이 **재개입**하면 새 스레드·새 토큰 | `sessionId`를 사전에 알아야 한다 — UUID v4는 추측 불가하고 **공개 경로·콘솔·CSV 어디에도 노출하지 않는다**(FR-CS3-2). DB 직접 접근자는 이미 모든 원천에 접근 가능 |

### 1.6 목적

1. 운영자가 **지금 진행 중인 대화**를 챗봇별로 한눈에 보고, **연속으로 답하지 못한 세션**을 색상 + 텍스트 경고로 즉시 알아챈다(카탈로그 "실시간 대화 모니터링 중 미응답 누적 시 색상 경고").
2. 상담원이 경고 세션(또는 임의의 진행 중 세션)에 **개입**하면 봇이 멈추고, 상담원과 사용자가 **같은 위젯 창에서** 대화한 뒤 종료하면 봇이 다시 응답한다(카탈로그 "상담원 개입").
3. 상담원 화면에 **사용자 마지막 질문과 가까운 FAQ/의도 답변**과 **자주 쓰는 문장**이 자동으로 제시되고, 한 번에 **복사하거나 입력창에 넣을** 수 있다(카탈로그 "응답힌트/자주쓰는문장 자동 제시, 복사 기능").
4. **대화 엔진·시뮬레이터·TC·버전·예약 배포의 동작이 바이트 단위로 동일**하다 — 개입 분기는 API 계층에서 엔진 **이전**에 끝난다.
5. **영구 원문 저장소를 만들지 않고**(원문은 상담 중에만 임시 보관 후 확실히 파기 — P-9), 상담 기록은 **조용히 사라지지 않는다**(영구 저장은 마스킹본만 · 삭제 경로 0).
6. 신규 의존성·인프라 0으로 **다중 인스턴스에서도** 동작한다(DB 원천 + CAS 잠금).

## 2. 사용자 역할 및 시나리오

### 2.1 역할

`security-audit.md` §2.1의 역할 3종에 **`AGENT`(상담원)을 더한다**(⚠ J-7 · P-7).

| 역할 | 이 그룹에서의 활동 | 권한(권고안) |
|---|---|---|
| **ADMIN** | 전부 + 강제 인수 | 기존 15종 + `cs:read` + `cs:write` |
| **EDITOR** | 상담 설정·자주 쓰는 문장 관리 · 모니터링·대화 보기·이력(개입 불가) | 기존 9종 + `cs:read` |
| **AGENT(신설)** | 모니터링 · 대화 보기 · 힌트 · 개입·전송·종료 · 이력 | `chatbot:read` + `cs:read` + `cs:write` |

### 2.2 사용자 시나리오

**S-1. 경고 발견 (AGENT · ★ 핵심)**
상담원이 `모니터링` 메뉴에서 챗봇 "쇼핑몰 도우미"를 고른다. 진행 중 세션 14개 중 1개가 **빨간 배경 + "경고 · 연속 미응답 3"** 텍스트로 맨 위에 있다. 행에는 세션 별칭 `#a3f9c1`·채널 WEB·마지막 발화 "환불 계좌를 바꾸고 싶어요"·마지막 활동 "20초 전"·누적 미응답 4 / 전체 7턴이 보인다. 화면 상단 알림 영역(스크린리더 `polite`)에 "경고 세션 1건"이 읽힌다.

**S-2. 대화 보기 + 응답힌트 (AGENT)**
행을 열면 왼쪽에 대화 전문(마스킹본)이 턴별로 보이고, 미응답 턴에는 "답변 못함" 배지, 답한 턴에는 노드 이름이 붙는다. 오른쪽 **응답힌트** 패널에 "가까운 답변" 3건(FAQ "환불 계좌 변경 방법" 0.82 · 의도 `환불_문의` 연결 노드의 텍스트 · FAQ "환불 소요 기간")과 "자주 쓰는 문장" 3건(환불 계좌 변경 안내 · 본인 확인 요청 · 인사)이 있다. 각 항목에 `복사`·`입력창에 넣기` 버튼이 있다.

**S-3. 개입 (AGENT · ★)**
`개입하기`를 누르면 "이 대화를 맡습니다. 챗봇 응답이 멈춥니다." 확인 후 상태가 **"상담 중 · 나"**로 바뀐다. 다른 상담원 화면에는 "상담 중 · 김상담"이 보이고 `개입하기`가 비활성(사유 텍스트)이다. 상담원이 자주 쓰는 문장 "안녕하세요, 상담원 김OO입니다…"를 `입력창에 넣기`로 가져와 고친 뒤 보낸다.

**S-4. 사용자 화면 (최종 사용자 · ★)**
사용자의 위젯은 방금 미응답을 받았으므로 관찰 창 폴링 중이다. 5초 안에 "**상담원이 연결되었어요. 잠시만 기다려 주세요.**"(시스템 안내) 다음에 **"상담원"** 라벨이 붙은 말풍선으로 상담원 메시지가 나타난다. 사용자가 "계좌를 국민은행으로 바꾸고 싶어요"를 보내면 챗봇 응답 없이 말풍선만 남고, 3초 안에 상담원 답이 온다.

**S-5. 개인정보 (AGENT · 최종 사용자)**
사용자가 "제 번호 010-1234-5678이에요"를 보내면 상담원 화면에는 "제 번호 010-****-5678이에요"로 보인다 **[P-9 갱신] — 담당 상담원이 `원문 보기`를 켜면 상담 중에 한해 원문 "010-1234-5678"이 함께 보이고(열람 기록), 상담이 끝나면 원문은 파기된다**. 상담원이 "010-1234-5678로 연락드릴게요"를 입력하면 입력창 아래 미리보기가 "010-****-5678로 연락드릴게요 — **개인정보는 가려져 전송됩니다**"를 보여 주고, 사용자도 가려진 문장을 받는다.

**S-6. 종료 (AGENT · 최종 사용자)**
상담원이 `상담 종료`를 누르면 사용자 위젯에 "상담이 종료되었어요. 이제 챗봇이 도와드릴게요." + 버튼 `상담 만족도 남기기`가 나온다. 버튼을 누르면 설문 노드가 일반 대화로 실행된다(No.27). 이후 "배송 조회"를 입력하면 다시 챗봇이 답한다.

**S-7. 사용자가 떠남 (자동 종료)**
상담 중 사용자가 탭을 닫았다. 상담원 화면에 "사용자 응답 없음 6분"이 보이고, 10분이 지나면 다음 콘솔 조회 시점에 상태가 **"종료 · 사용자 무응답"**이 된다(배치 없음). 상담원 전송 버튼은 비활성(사유 텍스트)이다.

**S-8. 새로고침 (최종 사용자)**
상담 중 사용자가 새로고침한다. 위젯이 저장된 상담 토큰으로 상담 모드를 복구하고, **상담 구간 메시지**(연결 안내 이후)를 다시 보여 준다. 봇 구간 대화는 복원되지 않는다(기존 한계 — 안내 1줄).

**S-9. 강제 인수 (ADMIN)**
담당 상담원이 자리를 비웠다. ADMIN이 `강제 인수`를 누르고 사유 "담당자 부재"를 입력한다. 담당자가 ADMIN으로 바뀌고 감사로그에 `HandoffSession UPDATE (강제 인수: 담당자 부재)`가 남는다. 사용자 화면에는 변화가 없다.

**S-10. 설정 · 자주 쓰는 문장 (EDITOR)**
챗봇 상세 > 답변 설정 > `상담 연계`에서 사용 여부·주의/경고 임계값·안내 문구·종료 후 버튼 노드를 저장한다. `자주 쓰는 문장` 탭에서 분류별 문장을 추가하고 위/아래 버튼으로 순서를 바꾼다.

**S-11. 이력 (EDITOR/AGENT)**
`모니터링 > 상담 이력`에서 지난주 상담 23건 · 평균 첫 응답 42초 · 평균 상담 6분 12초를 보고, "종료 · 상담원 무응답" 필터로 연결에 실패한 3건을 열어 대화 전문을 확인한다.

**S-12. 접근성 (AGENT · 최종 사용자)**
경고는 색상만이 아니라 "경고"·"주의" 텍스트와 아이콘으로 구분된다. 스크린리더 사용자는 목록 표를 행 단위로 읽고, 새 경고는 `aria-live="polite"`로 한 번만 안내된다. 위젯에서 상담원 말풍선은 "상담원:"으로 시작해 읽힌다.

| ID | 요구사항 |
|---|---|
| FR-CS4-1 | `POST /chatbots/:chatbotId/live-sessions/:alias/handoff`(`cs:write`) — **CAS 선점**으로 `HandoffSession`(`CONNECTING`, 담당자 = 요청자)을 만든다. 같은 `(chatbotId, sessionId)`에 활성(`CONNECTING`/`CONNECTED`) 상담은 **부분 유니크 인덱스로 최대 1건**. 이미 있으면 `409 HANDOFF_ALREADY_ASSIGNED`(담당자 이름 포함). 활성 창 밖·WEB 채널 닫힘·챗봇 비공개/보관 = `409 HANDOFF_SESSION_NOT_LIVE`. 감사 `HandoffSession CREATE`. |
| FR-CS4-2 | 공개 대화 파이프라인: **입구 금지어 판정 뒤, 번들·엔진 이전**에 상담 기능이 켜진 챗봇이면 `(chatbotId, sessionId)` 활성 상담을 조회한다. 활성 상담이 있으면 **엔진·의미 점수·레거시 API·설문 적재·RAG를 전부 호출하지 않는다**. |
| FR-CS4-3 | 활성 상담 + **유효한 상담 토큰**이 요청에 있으면: 사용자 메시지(버튼 `MESSAGE`는 텍스트, `NODE` 버튼은 라벨 텍스트 "[선택] 라벨")를 스레드에 **`USER` 메시지로 await 적재**(금지어 마스킹 → PII 마스킹 — **[P-9] 마스킹본과 다르면 원문을 `rawText`에 임시 보관**) → 응답 `{ outputs: [], state: 진행 상태를 비운 요청 봉투(멱등 — 설계서 §5.4), stateReset: false, handoff: { status, pollAfterMs } }`. |
| FR-CS4-4 | 스레드 적재가 실패하면 사용자에게 **재시도 가능한 오류**를 돌려준다(`503` — 기존 위젯 재시도 UI 사용). 상담 구간 메시지를 조용히 버리지 않는다(`record()`의 실패 흡수와 다른 규칙 — J-4). |
| FR-CS4-5 | 같은 턴을 `ConversationLog`에도 기존대로 fire-and-forget 적재하되 `handoffTurn=true`, `isAnswered=true`, 봇 응답 = 빈 문자열, `matched*` = null. |
| FR-CS4-6 | 활성 상담이 있으나 **토큰이 없거나 틀린** 요청: 상담원에게 전달하지 않고 스레드 적재 0, 응답 `outputs` = 중립 안내 1줄("지금은 메시지를 보낼 수 없어요. 잠시 후 다시 시도해 주세요.") + `handoff` 키 없음. 콘솔에 "확인되지 않은 연결 시도 n회" 표시(선점 탐지 — §1.4.2). 단 FR-CS4-7의 **토큰 미발급 첫 접촉**은 예외다. |
| FR-CS4-7 | **개입 전달 규칙**: `CONNECTING` 상담이 있고 이 상담에 **토큰이 아직 발급되지 않았으면**, 그 세션의 첫 요청(이번 턴 `POST messages` 응답 또는 상담 폴링 — 먼저 온 쪽)에 **토큰을 1회 발급**하고 `CONNECTED`로 전이한다. 이 첫 응답은 봉투의 `contextSession`·`pendingClarify`·`surveySession`을 **비운 봉투**를 돌려준다(J-16 — `completedSurveyIds`는 유지). |
| FR-CS4-8 | `CONNECTING`/`CONNECTED`에서 **상담원 무응답 한도**(첫 상담원 메시지 없이 기본 5분)가 지나면 조회·요청 시점에 `ENDED(AGENT_NO_REPLY)`로 판정, 사용자가 연결된 상태였다면 연결 실패 안내 후 봇 복귀. |
| FR-CS4-9 | 상담원이 개입했지만 사용자가 **돌아오지 않은**(토큰 미발급) 채 사용자 무응답 한도가 지나면 `ENDED(NOT_DELIVERED)` — 사용자 화면 변화 없음. |
| FR-CS4-10 | **ADMIN 강제 인수** `POST …/handoff/takeover`(`cs:write` + ADMIN 역할 확인, 사유 1~200자 필수) — 담당자만 교체, 토큰·스레드 유지, 사용자 화면 변화 없음, 감사 `HandoffSession UPDATE`(사유 포함, 본문 없음). |

| FR-CS5-7 | 챗봇 보관·WEB 채널 닫힘·챗봇 비공개 전환 시 활성 상담은 다음 판정 시점에 `ENDED(CHANNEL_CLOSED)`. 위젯은 기존 `DISABLED` 처리(403)를 따른다. |
| FR-CS5-8 | 종료된 상담은 **재개하지 않는다** — 다시 개입하면 **새 `HandoffSession`**(새 토큰)이다. |

| FR-CS9-6 | 종료 후 버튼은 기존 `NODE` 버튼 렌더러·전송 경로를 그대로 쓴다(새 버튼 종류 0). |
| FR-CS9-7 | **새로고침 복구**: 로드 시 상담 키가 있으면 커서 0부터 한 번 조회해 **상담 구간 메시지**(`AGENT`·`SYSTEM`)를 다시 그리고 폴링을 재개한다. 사용자 자신의 상담 구간 발화 복원 여부(폴링 응답에 `USER` 포함)는 architect. 봇 구간은 복원하지 않는다. |
| FR-CS9-8 | 상담 중 봇 시절 `NODE` 버튼 클릭은 **서버가** 라벨 텍스트로 상담원에게 전달한다(FR-CS4-3) — 위젯은 기존대로 전송만 한다. |
| FR-CS9-9 | vanilla TS 유지 · 런타임 의존성 0 · **gzip 100KB 게이트 통과**. 증가분을 빌드 로그로 보고한다. |

## 7. 수용기준 (AC)

### AC-CS1. 범위 · 회귀 · 설정

- **AC-CS1-1** ★ Given 상담 연계가 꺼진 챗봇, When 기존 엔진·대화·통계·검증·버전·예약 스위트를 돌리면, Then FR-0-126 목록 외에는 **수정 없이 전부 통과**하고 공개 응답에 `handoff` 키가 없으며 DB 조회 수가 도입 전과 같다(설정 캐시 적중 상태에서 측정).

- **AC-CS4-8** Given 관찰 창이 발급되지 않은 세션(모든 턴 응답), When 상담원이 개입, Then 위젯은 폴링하지 않고 **다음 사용자 발화 응답**에서 개입이 전달된다.

- **AC-CS7-7** Given 위젯 빌드, Then gzip 100KB 이내다.

### AC-CS8. 원문 — 상담 중 한정 (PM 결정 P-9, 2026-09-25 신설)

- **AC-CS8-1** ★ Given 담당 AGENT · 활성 상담 · 사용자 "제 번호 010-1234-5678", When `includeRaw=true`로 대화 보기, Then 해당 항목에 마스킹본과 원문이 함께 있고 `RAW_VIEW` 감사 1건이 남는다. 같은 요청 10회 반복에도 감사는 1건이다.
- **AC-CS8-2** Given 비담당 AGENT · EDITOR · `includeRaw` 없는 담당자, When 대화 보기, Then 원문 키가 없고 감사 0건이다. 비담당 ADMIN은 원문 ○ · 감사 1건(관리자)이다.
- **AC-CS8-3** ★ Given 상담원 종료, When DB를 직접 조회하면, Then 그 상담의 `rawText`가 전부 `NULL`이고(종료와 같은 트랜잭션) 대화 보기는 `rawVisible=false`다.
- **AC-CS8-4** ★ Given 사용자 무응답 11분 · 콘솔·위젯 요청 0건, When 정리 루프 1회 실행, Then 상담이 종료되고 원문이 소거된다(조회 없이도 파기).
- **AC-CS8-5** Given 적재 후 60분이 지난 원문, Then 읽기는 즉시 비노출이고 다음 정리 루프 후 `NULL`이다. 강제 인수 후 이전 담당자는 다음 조회에서 `rawVisible=false`다.
- **AC-CS8-6** ★ Given 고유 표식 원문을 상담 중 전송 후 종료·정리 루프, When 서버 로그·감사·오류 응답·이력·폴링·힌트 응답·`ConversationLog`·**SQLite DB 파일 바이트**를 전수 검사하면, Then 원문 문자열이 0건이다.
- **AC-CS8-7** Given 공개 폴링 `restore=true`, Then 사용자 메시지는 마스킹본이며 원문 키가 존재하지 않는다. PII가 없는 발화는 원문을 저장하지 않는다(`rawText=NULL`).
