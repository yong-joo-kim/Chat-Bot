### 1.2 원본 근거 — "토픽"은 무엇인가 (★ 원문 해석)

**근거 1 — 카탈로그 원문**(`기능요구사항.md` 59행):
> "토픽 시스템(멀티 온톨로지) | **부서·주제별 토픽 분리 구축 후 개별 챗봇화 또는 병합/확장** | GPU 1 | 사유: **구조적 데이터 분리 관리** | ○ | ○"

→ 요구는 셋이다. ① 부서·주제별로 **나누어 구축**한다. ② 나눈 토픽을 **개별 챗봇으로 만든다**. ③ 토픽을 **병합하거나 확장**한다. GPU 사유 "구조적 데이터 **분리 관리**"는 새 모델이 없다는 뜻이다. 인식 모델을 토픽별로 따로 학습한다는 뜻이 아니다.

**근거 2 — 제품소개서 p.18 "1. 토픽 시스템 제공(세계최초)"** (전문):
> "관리가 어렵고 복잡한 **1개의 온톨로지**를, 토픽 시스템을 활용하여 관리 가능합니다.
> **토픽을 만든 후 별도의 챗봇으로 만들고, 추가, 수정이 가능합니다.**
> 과거 하나의 인식률 문제, 온톨로지로 복잡했던 문제를 해결한 시스템입니다"
>
> [좌] **단일 온톨로지 구축** — "1개의 전체 온톨로지는 인식률 문제가 발생될 수 있으며, 추가 확장 시에도 매번 새롭게 구축을 해야하는 문제가 있음"
> [우] **전문적인 토픽 구축 통한 확장성 용이** — "**담당 부서별로 토픽을 만들 수 있고** 이를 추가, 수정할 수 있어 업데이트와 인식률에 용이하며, **따로 특정 토픽을 떼내어 챗봇을 만들거나 병합도 가능함**"

도식: 좌측은 `인사 → {기타, 위치 문의 → {지하철, 버스, 자동차 → {강변북로, 올림픽대로}}}` 한 그래프다. 우측은 같은 그래프의 `위치 문의`·`자동차` 가지를 **별도 상자(토픽)** 로 떼어 낸다. 상자 `위치 문의`에는 `위치문의 → {지하철, 버스, 자동차}`가 들어 있다. 상자 `자동차`에는 `자동차 → {강변북로, 올림픽대로}`가 들어 있다. 본 그래프는 두 상자로 **위임**한다. **`자동차`는 두 토픽에 모두 등장한다.**

→ 해석:
- ⓐ 토픽 = **대화 그래프의 한 가지와 그 가지가 쓰는 의도·키워드를 묶은 모듈**이다(= "온톨로지 조각").
- ⓑ 토픽은 **부서가 담당**한다("담당 부서별로").
- ⓒ 토픽을 **떼어 내 챗봇으로 만든다**. 원본에서 옮기는지 복사하는지는 문장만으로 정할 수 없다. "떼내어"는 옮기기, "만든 후 별도의 챗봇으로 만들고"는 복사에 가깝다.
- ⓓ **병합**도 가능하다.
- ⓔ "인식률에 용이"는 **토픽 단위로 좁혀서 매칭한다(계층 라우팅)**는 뜻일 수 있다. 다만 원문은 방식을 설명하지 않는다.
- ⓕ 같은 개념(`자동차`)이 여러 토픽에 **중복 존재**한다. 즉 ROCHA의 토픽은 **독립 사본**에 가깝다.

**근거 3 — 제품소개서 p.17 FEATURE 목록 첫 항목** "**토픽 시스템**" · 둘째 항목 "그룹관리 및 통합 통계" → 토픽과 그룹은 **별개 기능**이다(T-1).

**근거 4 — ROCHA 콘솔 상단 내비게이션**(`로차_간단학습매뉴얼.pdf` p.5~23 모든 화면, 제품소개서 p.19): `챗봇 | **토픽** | 운영중인 챗봇 | TC테스트 | 통계 | 관리` → **토픽은 챗봇과 같은 층위의 최상위 메뉴**다. 해석 (b)(토픽이 챗봇 밖의 독립 자원)를 **지지하는 가장 강한 증거**다. 반면 좌측 챗봇 메뉴(`챗봇설정·챗봇제작(대화그래프·의도관리·키워드관리·동음이의어/다의어·테스트)·채널설정·통계/분석·모니터링·설문관리·이력관리`)에는 토픽 항목이 **없다**.

**근거 5 — 대화그래프 화면의 탭 줄**(간단매뉴얼 p.5~9): 캔버스 위에 `⊕ | 기본` 탭이 있다 → **한 챗봇의 대화그래프를 여러 탭으로 나눌 수 있다**는 흔적이다. 탭이 토픽인지, 단순한 레이어인지는 **확인하지 못했다**(조사 한계). 해석 (a)를 **약하게** 지지한다.

**근거 6 — 제품소개서 p.15 플랫폼 구성도**: AI PLATFORM > Learning Management System에 "**Ontology learning**"이 있고 Data collection에 `INTENT SET / ENTITY SET / CONTEXT SET / DIALOG SET`이 있다 → ROCHA의 "온톨로지" = **의도·엔티티·컨텍스트·대화상자 묶음**이다. 우리 시스템의 **대화 자산 6종**(의도·키워드·동음이의어·컨텍스트·노드·FAQ — 스냅샷 대상과 같다, `version.ts` 114~121행)에 해당한다.

**근거 7 — 제품소개서 p.28 통계 카드** "**총 토픽수 320**" · "고객 별, **대화 주제 별** 통계" → 한 설치본에 토픽이 **수백 개**다. "부서 단위의 큰 묶음"보다 **훨씬 잘게 쪼갠 주제 단위**일 가능성이 있다(또는 대화상자 수를 "토픽"이라 부른 마케팅 표기일 수도 있다 — 판단 보류). → 토픽 상한을 너무 작게 잡지 않는다(J-2: 챗봇당 50 → P-2에서 조정 가능).

**근거 8 — 원본 재학습 절차**(간단매뉴얼 p.4): `운영중 챗봇 복사`(6p 챗봇 리스트) → `복사한 챗봇 학습` → … → `운영 챗봇 교체`(88p) → ROCHA의 챗봇 복사는 **자산까지 복사한다**. 우리 `copy()`는 **프로필만** 복사한다(`chatbots.service.ts` 236~277행, `chatbot-operations.md` FR-1-14). "토픽 → 새 챗봇"은 이 격차를 메우는 **같은 부품**(깊은 복사)을 요구한다(T-6·T-9).

### 1.3 이미 있는 것과 없는 것 (코드 확인)

#### 1.3.1 대화 자산 모델 — "모든 것이 `chatbotId` 하나로 잘려 있다"

| 사실 (파일:행) | 결과 |
|---|---|
| 대화 자산 6종 `Intent`·`Keyword`·`HomonymDictionary`·`DialogNode`·`ContextVariable`·`FaqEntry`는 전부 `chatbotId`(FK `Restrict`)로 스코프된다(`schema.prisma` 89~256행) | 토픽을 **챗봇 안에 두면** 기존 스코프 규약·교차 챗봇 404·인덱스를 그대로 쓴다. 토픽을 **챗봇 밖에 두면**(해석 b) 6개 테이블의 소유 관계가 바뀐다 |
| **정규화 이름 유일성이 챗봇 단위**: `(chatbotId, nameNormalized)` — Intent 106행 · Keyword 125행 · DialogNode 182행 · ContextVariable 231행 · Homonym `(chatbotId, wordNormalized)` 148행 · FAQ `(chatbotId, questionNormalized)` 252행 · Survey 1085행 (ADR-0006) | ★ 해석 (a)에서는 **토픽이 달라도 같은 챗봇 안에서 이름이 겹칠 수 없다.** 두 부서가 각자 의도 "문의"를 만들 수 없다 → 이름 규칙(접두어)이 운영 지침으로 필요하다(EX-TP-3). 유일성을 `(chatbotId, topicId, nameNormalized)`로 바꾸면 **엔진·편집기·가져오기·동음이의어가 "이름 → 자산" 해석을 전부 다시 해야** 하므로 채택하지 않는다(J-2) |
| 자산 중 **활성 플래그가 있는 것은 노드(`enabled` 164행)와 FAQ(`enabled` 248행)뿐**이다. **의도·키워드·컨텍스트·동음이의어에는 없다**. 인덱스 구축 시 의도는 전부 색인되고(`dialogue-index.ts` 44~51행) FAQ만 `enabled=false`를 건너뛴다(56행) | 토픽 비활성을 "자산마다 `enabled` 끄기"로 구현하면 의도에 새 컬럼이 필요하고 사용자 설정값과 섞인다 → **번들 조립 단계의 필터**가 맞다(§1.6) |
| 노드↔의도·키워드는 **조인 테이블**(`DialogNodeIntent`·`DialogNodeKeyword`, FK `Restrict`, `schema.prisma` 189~209행, ADR-0005). 노드→컨텍스트는 FK(`contextVariableId` 168~170행). 나머지 참조는 **JSON 안**에 있다(`outputs` 172~174행, 동음이의어 `meanings[].intentId` 137~139행, 컨텍스트 `slots[].keywordId` 218~220행) | 참조 엣지 목록은 §1.3.2 |
| `Survey`는 챗봇 스코프·**스냅샷 밖**(ADR-0035 · `survey-management.md` J-9 185행) · `CannedResponse`는 **대화 번들·스냅샷·엔진 밖**(`개발명세서.md` 217행) | 두 자산은 **토픽 소속 대상에서 뺀다**(J-2) |
| `ApiConnection`은 **전역 자원**이다(챗봇 스코프 아님, `schema.prisma` 981~1012행, ADR-0034). 삭제 사전검사가 **전 챗봇 노드**를 훑는다(`reference-check.service.ts` 205~229행) | ★ **해석 (b)의 유일한 선례**다. 단 연결은 ADMIN만 쓰는 설정 자원이고, 대화 자산처럼 매칭·편집·스냅샷·임베딩에 엮이지 않는다. 같은 방식을 대화 자산에 적용하는 비용은 비교가 안 된다(§1.4) |

**참조 무결성 4곳**(요청 확인 항목):
1. **삭제 사전검사** `ReferenceCheckService`(위 표) — 챗봇 스코프 쿼리이므로 **토픽을 몰라도 올바르다**. 토픽 도입으로 바꿀 것이 없다.
2. **설계 점검** `validateDesign`/`getOutgoingNodeRefs`(`packages/dialogue-engine/src/design-validator.ts` — 코드 `BROKEN_REFERENCE`·`ORPHAN_NODE`·`MOVE_CYCLE`·`DUPLICATE_CONDITION`·`EMPTY_EXAMPLE_INTENT` 등) — **엔진 패키지 안에 있다.** 토픽 규칙을 여기에 넣으면 "엔진 수정 0"이 깨진다 → 토픽 규칙은 **API 계층의 별도 순수 함수**로 추가하고 결과를 기존 점검 결과에 합친다(J-3 · FR-TP4-1). `getOutgoingNodeRefs()`는 **호출만** 한다.
3. **스냅샷 무결성** `checkSnapshotIntegrity`(`versions/lib/snapshot-integrity.ts` 47행) + `findCrossChatbotIdConflicts`(`versions/restore/cross-chatbot-check.ts` 15~55행) — `topicId`를 스냅샷에 넣으면 "없는 토픽 참조" 규칙을 **경고(차단 아님)**로 추가한다(J-9). 분리(1차-B)의 **재매핑 전 캡처 검증**으로도 재사용한다.
4. **저장 검증** `dialog-nodes.service.ts` 130~183행 — "같은 챗봇의 자산인가"만 본다(`INVALID_REFERENCE` 404, 181행). **토픽 경계를 넘는 참조는 차단하지 않는다**(J-3). 이 검증은 **바꾸지 않는다**.

> 관찰: 노드→노드 참조 목록이 **두 벌**이다 — `getOutgoingNodeRefs()`(설계 점검·삭제 사전검사)와 `dialog-nodes.service.ts` 130~161행(저장 검증, 버튼·카드 `NODE`를 직접 순회). 이 그룹은 **세 번째 벌을 만들지 않고** `getOutgoingNodeRefs()`를 쓴다(NFR-TPM1). 두 벌을 합치는 일은 범위 밖이다(K-2).

**권고 근거 3가지**:
1. **(a)가 나머지의 바탕이다.** (c1)의 "토픽을 떼어 낸다"와 (c2)의 "새 토픽으로 넣는다"에는 **먼저 토픽이라는 단위**가 있어야 한다.
2. **(c1)은 대상이 비어 있어 충돌이 없다.** 원문의 "개별 챗봇화"를 가장 싸게 충족한다. 같은 부품으로 **No.1 깊은 복사**(T-6)와 **ROCHA 재학습 절차의 `운영중 챗봇 복사`**(T-9)도 풀린다.
3. **(c2)는 운영 중인 챗봇을 바꾼다.** 충돌 규칙을 PM이 먼저 정하고(P-9), (c1)의 재매핑 적재기가 검증된 뒤 착수하는 편이 안전하다. (b)는 "챗봇 = 버전·배포·검증 단위"라는 선행 13개 그룹의 전제를 바꾸므로 별도 판단이 필요하다.

### 1.5 ★ 선결 쟁점 2 — 토픽 경계를 넘는 참조

**원칙**: 토픽은 **분류**다. 격리 경계가 아니다. 토픽 경계를 넘는 참조를 **허용**하고 대신 **보이게** 한다.

| 방식 | 설명 | 판정 |
|---|---|---|
| 차단 | 노드는 같은 토픽(또는 미분류)의 의도·키워드·노드만 참조 | **기각** — 공용 키워드(`@시스템-날짜`, 간단매뉴얼 p.12)와 공용 의도("인사")를 토픽마다 복제해야 한다. ROCHA 도식(근거 2)의 **본 그래프 → 토픽 상자 위임**도 경계를 넘는 이동이다. 기존 자산을 토픽으로 나누는 순간 저장이 막힌 노드가 대량으로 생긴다 |
| **허용 + 가시화** ★ | 저장 검증은 그대로(같은 챗봇이면 통과). 설계 점검에 **교차 토픽 참조(정보)** · **비활성 토픽 참조(경고)** 추가. **비활성화 전 영향 미리보기**(무엇이 끊기는가) 필수 | **채택** |
| 허용 + 자동 동반 | 참조 대상이 비활성 토픽이면 참조한 쪽도 자동 비활성 | 기각 — 연쇄 비활성화가 예측 불가. 관리자가 모르는 사이 공용 노드가 꺼진다 |

**"미분류"의 의미**: `topicId = null`인 자산은 **"공통"**(화면 표기 — P-2에서 이름 확정)이다. **항상 활성**이고 삭제·비활성화할 수 없다. START·FALLBACK 노드는 **공통에 고정**한다(토픽 지정 불가). 이 둘이 비활성 토픽에 들어가면 챗봇 전체가 인사·폴백을 잃기 때문이다(`resolver.ts` 164행). 여러 토픽이 공유하는 키워드·의도는 **공통에 두는 것이 운영 권장**이다 — ROCHA 도식에서 `자동차`가 두 토픽에 중복되는 문제를 **복제 대신 공유**로 푼다.

### 1.6 ★ 선결 쟁점 3 — 엔진 영향 (비활성 토픽을 어디서 걸러내는가)

| 위치 | 설명 | 엔진 수정 | 의미 매칭 일관성 | 판정 |
|---|---|---|---|---|
| 엔진 안(`resolveTurn`에 비활성 토픽 목록 인자) | 매칭 단계마다 토픽 검사 | **필요** | 엔진이 따로 챙겨야 함 | 기각 — 선행 그룹 전부 "엔진 수정 0"을 지켰다(FR-0-118 등) |
| 인덱스 구축(`buildDialogueIndex`) | 색인에서만 제외 | **필요**(엔진 패키지 파일) | 번들 원본에는 남아 `bundle.intents`로 도는 경로(색인 미주입 시 `matcher.ts` 66~70행)와 어긋남 | 기각 |
| 자산별 `enabled` 일괄 끄기 | 토픽 비활성 = 소속 노드·FAQ `enabled=false` | 0 | ○ | 기각 — 의도·키워드에는 `enabled`가 없고, 사용자 개별 설정값을 덮어써 **되켤 때 원래 값을 잃는다** |
| **번들 조립(API 계층 `DialogueBundleService.build`)** ★ | 비활성 토픽에 속한 **노드·의도·FAQ**를 번들에서 뺀다 | **0** | **자동**(§1.3.3 — `assembleSemanticInput`이 번들 기준으로 거른다) | **채택** |

**무엇을 빼는가 — "응답 진입점"만**:
- **빼는 것: 노드·의도·FAQ.** 사용자 발화가 답에 도달하는 **진입점**이다. 이것을 빼야 "그 토픽이 답하지 않는다"가 성립한다.
- **남기는 것: 키워드·컨텍스트·동음이의어.** **사전형 자산**이다. 스스로 답하지 않고, 노드를 거쳐야만 효과가 난다. 이것까지 빼면 **활성 토픽의 노드가 공용 키워드를 잃는** 교차 파손이 커진다. 남겨도 비활성 토픽을 되살리지 않는다.
- 결과: 비활성 토픽의 노드로 **이동하던** 활성 노드의 아웃풋은 `BROKEN_REFERENCE`로 건너뛴다(`outputs.ts` 188~191행). 비활성 토픽의 **의도를 조건으로 쓰던** 활성 노드는 그 조건으로 매칭되지 않는다. **둘 다 비활성화 전에 영향 미리보기로 보여 준다**(FR-TP3-3).

**버전 캡처는 필터하지 않는다**: 캡처(`build(chatbotId, tx)`)는 **전체 자산**을 담아야 한다. 비활성 토픽 자산이 스냅샷에서 사라지면 복원이 그것을 지운다. 따라서 필터는 `build()`의 **선택 인자**(기본 = 필터 없음)로 두고, **`getCached()` 경로만 필터를 켠다**(FR-TP3-6 · architect 확정). 같은 이유로 설계 점검·흐름 트리·삭제 사전검사도 **전체 자산**을 본다.

### 1.7 ★ 선결 쟁점 4 — 분리·병합의 ID와 이름 충돌

#### 1.7.1 분리(1차-B) — 새 챗봇으로 복사

| 결정 | 내용 | 근거 |
|---|---|---|
| **복사다(원본 불변)** | "떼어 낸다"를 **옮기기**로 구현하면 원본 운영 챗봇에서 자산이 사라진다 → 운영 사고. 복사 후 원본 토픽을 **비활성화하거나 지우는 것은 관리자가 별도로** 한다(두 단계, 각각 감사) | 근거 2 "토픽을 만든 후 별도의 챗봇으로 만들고" · 근거 8 "운영중 챗봇 **복사**" |
| **모든 ID를 새로 발급** | 두 챗봇은 같은 ID를 가질 수 없다(PK). 참조(E-1~E-8)는 **재매핑 표**로 옮긴다 | ADR-0031 §8 77행 · `version-history.md` J-12 |
| **의존 자산 자동 포함** | 선택 토픽 자산이 참조하는 **토픽 밖 자산**(의도·키워드·컨텍스트·노드·동음이의어 의미의 의도)을 **폐포(닫힌 집합)로 함께 복사**한다. 새 챗봇에서 이것들은 "공통"이 된다. 미리보기에 "함께 복사되는 자산 n건"을 보여 준다 | 끊어서 복사하면 저장 검증(`INVALID_REFERENCE`)을 통과하지 못하는 노드가 생기거나, 아웃풋을 몰래 지워야 한다 |
| **START·FALLBACK 노드 항상 포함** | 새 챗봇이 인사·폴백 없이 시작하지 않게 | `resolver.ts` 164행 · 설계 점검 `NO_FALLBACK_NODE` |
| **설문은 정의만 복제** | 참조된 설문을 새 챗봇에 복제(응답 0, 상태 `DRAFT`, 이름 유지) → 노드의 `surveyId`를 재매핑 | FR-SV2-6 복제 규칙 · 설문은 챗봇 스코프(E-5) |
| **API 연결은 그대로** | `connectionId`는 전역 자원 → 재매핑 없음 | ADR-0034 |
| **복사하지 않는 것** | 채널·답변 설정·상담 설정·자주 쓰는 문장·TC·미응답 큐·증강 제안·분류기·대화로그·버전 이력·임베딩 벡터(재색인으로 새로 생성) | 기존 `copy()`가 프로필만 복사하는 규칙의 연장 · 원천 기록은 복사 대상이 아니다 |
| **새 챗봇은 `DRAFT`** | 운영 노출 0. 채널은 관리자가 따로 연다 | `chatbots.service.ts` 271행 |
| **토픽 정의도 복사** | 선택한 토픽들은 새 챗봇에 **같은 이름의 토픽**으로 생성(활성 상태는 원본 값 유지 — 비활성 토픽을 분리하면 새 챗봇에서도 비활성) | 부서 단위 챗봇을 만든 뒤에도 토픽 구분이 남는다 |
| **이름 충돌 없음** | 대상이 빈 챗봇이다. 원본 안에서 이름이 이미 유일하므로 새 챗봇에서도 유일하다 | ADR-0006 |

#### 1.7.2 병합(2차) — 이름 충돌 기본 규칙 (★ 지금 정할 것은 기본값뿐)

병합 = "원본 챗봇 S의 토픽(들)을 대상 챗봇 T에 **새 토픽**으로 가져온다". T의 유일성 제약(§1.3.1) 때문에 **정규화 이름 충돌**이 생긴다.

| 자산 | 충돌 판정 키 | 권고 기본값 | 대안 | 근거 |
|---|---|---|---|---|
| 의도 | `nameNormalized` | **합치기** — T의 기존 의도를 쓰고 S의 예문을 추가(중복 예문 무시). 기존 의도의 토픽 소속은 **바꾸지 않는다** | 이름 바꿔 추가(접미사) · 건너뛰기 | 대량 가져오기 선례(`import-planner.ts` 36~76행) — 같은 이름 = 같은 의미로 본다 |
| 키워드 | `nameNormalized` | **합치기**(동의어 추가). 단 합친 결과가 **다른 키워드의 동의어와 겹치면 병합 전체 거부**(차단) | — | 동의어 교차 충돌은 이미 **차단 규칙**(FR-6-16, `import-planner.ts` 79~106행) |
| 노드 | `nameNormalized` | **이름 바꿔 추가**(`이름 (가져옴)`, 다시 겹치면 번호) | 건너뛰기 | 노드는 아웃풋·우선순위가 달라 합칠 수 없다. 합치면 T의 운영 응답이 바뀐다 |
| 컨텍스트 | `nameNormalized` | **이름 바꿔 추가** | 합치기(슬롯 정의가 같을 때만) | 슬롯 구조가 다르면 진행 중 세션이 깨진다(`SESSION_DEFINITION_CHANGED`) |
| 동음이의어 | `wordNormalized` | **건너뛰기 + 리포트**(T 유지) | 의미 합치기 | 한 단어의 해석 정책은 챗봇당 하나여야 한다 |
| FAQ | `questionNormalized` | **건너뛰기 + 리포트**(T 유지, 답변이 다르면 "충돌"로 표시) | S로 덮어쓰기 | 운영 중 답변을 조용히 바꾸지 않는다 |
| START·FALLBACK | 종류 | **가져오지 않는다**(T 유지) | — | 챗봇당 1개(FR-5-4) |

**병합 공통 규칙(2차에서 확정)**: dry-run 미리보기 필수(자산별 신규/합침/이름 변경/건너뜀/거부 건수 + 행 단위 리포트) · **`BEFORE_MERGE` 자동 스냅샷**(트리거 7번째) · 원본 S 불변 · 병합 뒤 T 설계 점검 자동 실행 · 교차 예문 중복 경고(TC-22 "병합 후 의도/키워드 충돌 시 경고"의 실체).

#### 1.7.3 No.40(환경 분리)과 겹치는가

| 축 | No.22 분리(1차-B) | No.40 환경 분리 |
|---|---|---|
| 목적 | 다른 **서비스**(새 챗봇)를 만든다 | **같은 서비스**의 준비본을 운영본으로 승격한다 |
| 결과물 | 독립 챗봇(이후 따로 진화) | 두 환경이 **같은 챗봇의 두 상태**로 묶임(승격·태깅·트래픽 전환) |
| ID | 새로 발급(재매핑) | 새로 발급(재매핑) — **같은 부품** |
| 반복 | 1회성 | 반복 승격(차이 적용) |

→ **기능은 겹치지 않고 부품(캡처 + ID 재매핑 적재기)을 공유한다.** 이 그룹이 적재기를 **"대상 챗봇 + 자산 부분집합 + 재매핑 표 → 적재"** 인터페이스로 만든다. No.40은 여기에 "기존 대상과의 차이 적용"을 더하면 된다(NFR-TPM2).

#### 1.7.4 감사 · 자동 스냅샷 대상 여부

| 동작 | 감사(ADR-0016) | 자동 스냅샷(`BEFORE_*`) | 근거 |
|---|---|---|---|
| 토픽 생성·이름 변경·삭제(빈 토픽) | `Topic` CREATE/UPDATE/DELETE | 아니오 | 자산 내용 불변 |
| 토픽 활성/비활성 | `Topic` STATUS_CHANGE | **아니오** | 되돌리기 쉽고(토글) 자산 내용이 바뀌지 않는다. 대신 **영향 미리보기 + 확인**(FR-TP3-3) |
| 자산 1건 토픽 변경 | 해당 자산 UPDATE(before/after `topicId`) | 아니오 | 기존 자산 감사 경로 |
| 일괄 토픽 지정(n건) | `Topic` UPDATE **요약 1건**(건수·자산 종류별 수, 원문 0) | 아니오 | 행마다 감사하면 수천 건 — `BULK_DELETE` 요약 선례 |
| 분리(새 챗봇) | 새 `Chatbot` **COPY 1건**(summary: 원본 챗봇·토픽 수·자산 수) | 원본: 아니오(불변) · 대상: 아니오(새 챗봇) | 기존 `COPY` 동작 재사용 |
| 병합(2차) | 대상 `Chatbot` IMPORT 요약 1건 | **예 — `BEFORE_MERGE`** | 운영 챗봇 대량 변경 |

### 1.8 목적

1. 한 챗봇의 대화 자산을 **부서·주제별 토픽**으로 나누어 편집·검토할 수 있게 한다(원문 요소 ①).
2. 토픽 단위로 **운영 노출을 켜고 끌 수 있게** 한다. 준비 중인 부서 토픽을 비활성 상태로 만들고 시뮬레이터로 시험한 뒤 켠다(원문 "업데이트에 용이").
3. 토픽 경계를 넘는 참조를 **보이게** 하여 비활성화·분리의 영향을 미리 안다.
4. 선택한 토픽을 **새 챗봇으로 분리**한다(원문 요소 ② — 1차-B). 같은 부품으로 챗봇 깊은 복사를 제공한다.
5. **병합**(원문 요소 ③)의 충돌 규칙을 지금 정해 2차 착수를 막힘없이 준비한다.
6. 위의 모든 것을 **엔진 수정 0 · 신규 권한 0 · 신규 공개 경로 0**으로 한다.

## 2. 사용자 역할 및 시나리오

### 2.1 역할

| 역할 | 이 그룹에서의 활동 | 권한 |
|---|---|---|
| **ADMIN** | 전부 | 기존 17종 그대로 |
| **EDITOR**(부서 담당 포함) | 토픽 생성·편집·삭제 · 소속 지정 · 활성/비활성 · 분리 · 토픽 필터 내보내기/가져오기 | `dialogue:write`(+분리 시 `chatbot:write`) — 기존 보유 |
| **VIEWER** | 토픽 목록·필터·설계 점검 결과 조회 | `dialogue:read` — 기존 보유 |
| **AGENT** | 변화 없음(대화설계 화면 접근 권한 없음 — `security.ts` 69행) | — |
| 최종 사용자 | 활성 토픽의 답변만 받는다 | — |

> 부서 담당자가 **자기 토픽만** 편집하도록 제한하는 기능은 **없다**(J-7 · P-10). 모든 EDITOR가 모든 토픽을 편집한다.

### 2.2 사용자 시나리오

**S-1. 기존 챗봇을 토픽으로 정리 (EDITOR · ★)**
"고객센터 봇"에는 의도 180개, 노드 120개, FAQ 400개가 한 덩어리로 있다. 담당자가 `토픽`에서 "배송"·"환불"·"회원"을 만든다. `의도·키워드` 목록 상단 필터를 "공통"으로 두고 검색어 "배송"으로 42건을 추린 뒤 전체 선택 → `토픽 지정: 배송`을 누른다. 목록의 "토픽" 열이 바뀌고, 토픽 화면에 "배송 — 의도 42 · 노드 0 · FAQ 0"이 보인다. 같은 방법으로 노드와 FAQ도 정리한다.

**S-2. 교차 토픽 참조 확인 (EDITOR)**
`설계 점검`을 누르면 기존 항목 아래에 "**다른 토픽 참조 17건**(정보)"이 나온다. 펼치면 "노드 `환불접수`(환불) → 조건 의도 `주문조회`(배송)"처럼 출발·도착 토픽이 보인다. 담당자는 `주문조회`를 공통으로 옮긴다.

**S-3. 준비 중 토픽 (EDITOR · ★)**
보험청구 부서가 새 토픽 "보험청구"를 **비활성**으로 만들고 의도·노드·FAQ를 채운다. 운영 위젯에서 "보험금 청구"를 입력해도 기존처럼 폴백이 나온다. 시뮬레이터에서 `비활성 토픽 포함`을 켜고 같은 문장을 입력하면 새 노드가 답한다. trace에 "토픽: 보험청구(비활성)"가 표시된다.

**S-4. 토픽 켜기 (EDITOR · ★)**
준비가 끝나 `활성화`를 누른다. 확인 대화상자가 "이 토픽을 켜면 노드 12 · 의도 9 · FAQ 30이 운영 응답에 포함됩니다. 다른 토픽과 겹치는 예문 3건이 있습니다(보기)."를 보여 준다. 확인하면 1분 안에 모든 서버에서 운영 위젯이 새 답을 준다.

**S-5. 토픽 끄기 — 영향 미리보기 (EDITOR · ★)**
"이벤트" 토픽을 끄려 하자 미리보기가 "**끊기는 참조**: 활성 노드 `메인메뉴`의 버튼 '이벤트 보기' → 이 토픽 노드 `이벤트안내`(1건)"를 보여 준다. 담당자는 먼저 `메인메뉴` 버튼을 정리하거나, 그대로 끄고 설계 점검 경고를 받아들인다.

**S-6. 부서 챗봇 분리 (ADMIN · ★ 1차-B)**
보험청구 부서가 자체 챗봇을 원한다. `토픽` 화면에서 "보험청구"를 선택하고 `새 챗봇으로 분리`를 누른다. 마법사가 "토픽 자산 51건 + **함께 복사되는 공통 자산 7건**(의도 `인사`, 키워드 `@시스템-날짜` 등) + 시작·폴백 노드 + 설문 1건(정의만)"을 보여 준다. 새 챗봇 이름 "보험청구 봇", 그룹 "상담센터"를 정하고 실행한다. "보험청구 봇(초안)"이 생기고 원본은 그대로다. 담당자는 원본의 "보험청구" 토픽을 따로 비활성화한다.

**S-7. 챗봇 통째 복사 (EDITOR)**
재학습용 사본이 필요하다(ROCHA 재학습 절차 `운영중 챗봇 복사`). `새 챗봇으로 분리`에서 **토픽 전체 + 공통**을 선택하면 자산 전체가 새 챗봇으로 복사된다.

**S-8. 토픽 단위 내보내기 (EDITOR)**
`의도·키워드`에서 토픽 필터 "환불"을 두고 `내보내기`를 누르면 환불 토픽의 의도만 CSV로 받는다. `가져오기`에서 "신규 항목의 토픽: 환불"을 고르면 새로 생기는 의도는 환불 토픽에 들어간다. 이미 있는 의도는 토픽을 바꾸지 않고 예문만 합친다.

**S-9. 토픽 삭제 (EDITOR)**
빈 토픽은 바로 삭제된다. 자산이 남아 있으면 "소속 자산 23건이 있습니다. 먼저 공통으로 옮기시겠어요?"가 나오고, `공통으로 옮기고 삭제`를 누르면 한 번에 처리된다(감사 2건).

**S-10. 버전 복원 (ADMIN)**
어제 버전으로 복원했다. 복원된 자산은 **그 버전 당시의 토픽**에 다시 들어간다. 그 사이 삭제된 토픽을 가리키던 자산은 공통으로 들어가고, 복원 결과에 "토픽 없음 → 공통 3건" 경고가 나온다. 토픽의 활성/비활성은 복원으로 바뀌지 않는다.

**S-11. 접근성 (모든 관리자)**
토픽은 **색만이 아니라 이름 텍스트**로 표시된다(선택적 색 점은 보조). 비활성 토픽은 "비활성" 텍스트 배지로 구분한다. 일괄 지정·필터·마법사는 키보드만으로 조작할 수 있다.

### 5.2 신규 데이터 모델 제안 (`system-architect` 확정 사항)

| 모델 | 주요 필드(개요) | 제약 |
|---|---|---|
| **`Topic`** | id · chatbotId(FK `Restrict`) · name · nameNormalized · description? · sortOrder · enabled(기본 true) · createdAt · updatedAt | 유일 `(chatbotId, nameNormalized)` · 인덱스 `(chatbotId, sortOrder)` · 챗봇당 50 · 스냅샷 밖 |

**FK 여부**(architect): 복원이 "없는 토픽 → null"로 적재하므로 FK를 걸어도 복원은 깨지지 않는다. FK를 걸지 않으면 토픽 삭제 후 잔여 `topicId`가 생길 수 있다 → **FK `Restrict` 권고**.

**미도입 결정(개발명세서 §3에 기록 제안)**: 토픽 계층 · 자산 다대다 소속 · 토픽 단위 권한 · 챗봇 밖 공유 토픽 · 토픽 우선순위 · 토픽별 임베딩 색인 · 토픽 활성화 예약 · 토픽 스냅샷.

## 7. 수용기준 (AC)

### AC-TP1. 범위 · 회귀 · 토픽 정의

- **AC-TP1-1** ★ Given 토픽이 없는 챗봇, When 기존 엔진·대화·시뮬레이터·TC·통계·버전·예약 스위트를 돌리면, Then FR-0-136 목록 외에는 **수정 없이 전부 통과**하고 공개 응답·버전 `contentHash`가 도입 전과 같다.
- **AC-TP1-2** Given `packages/dialogue-engine`, When 이 그룹 전후를 비교하면, Then 변경 파일 0이다.
- **AC-TP1-3** Given 토픽 "배송"이 있음, When 이름 " 배송 "(정규화 동일)으로 생성하면, Then `409 DUPLICATE_NAME`이다(~~`DUPLICATE_TOPIC_NAME`~~ — 기존 코드 재사용, FR-0-134 확정). 51번째 토픽 생성은 `409 LIMIT_EXCEEDED`다(~~`TOPIC_LIMIT_EXCEEDED`~~).
- **AC-TP1-4** Given 자산 23건이 있는 토픽, When 삭제하면 `409 TOPIC_NOT_EMPTY`(종류별 건수)이고, `moveToCommon=true`로 삭제하면 23건이 공통이 되고 토픽이 사라지며 감사가 2건(요약 UPDATE·DELETE) 남는다.
- **AC-TP1-5** Given 다른 챗봇의 토픽 id, When 자산 `topicId`로 지정하면 `404 INVALID_REFERENCE`다. START 노드에 토픽을 지정하면 `400 TOPIC_SYSTEM_NODE_LOCKED`다.

### AC-TP2. 소속 지정 · 목록

- **AC-TP2-1** Given 의도 42건 선택, When 일괄 지정으로 "배송"에 넣으면, Then 42건의 `topicId`만 바뀌고 이름·예문·조인 테이블은 바이트 동일이며 감사 요약 1건(건수 42, 원문 0)이 남는다.
- **AC-TP2-2** Given 1,001건, When 일괄 지정하면 `400`이다. 중간에 실패하면 0건 반영이다(부분 성공 없음).
- **AC-TP2-3** Given 토픽 필터 "배송,공통", When 의도 목록을 조회하면, Then 배송 소속 + 공통 의도만 나오고 쿼리 수가 필터 없을 때와 같다.
- **AC-TP2-4** Given 가져오기 파일에 기존 의도 "주문조회"(환불 소속)와 신규 의도 "반품접수", When "신규 항목의 토픽: 배송"으로 커밋하면, Then "반품접수"는 배송, "주문조회"는 **환불 유지** + 예문만 합쳐진다.

### AC-TP3. 활성 / 비활성 · 엔진 영향

- **AC-TP3-1** ★ Given 비활성 토픽 "보험청구"에 노드 N(의도 I 조건)·FAQ F, When 공개 대화로 I의 예문과 F의 질문을 입력하면, Then 둘 다 **폴백**(또는 다른 활성 자산)으로 응답하고 공개 응답 어디에도 N·I·F가 없다.
- **AC-TP3-2** ★ Given AC-TP3-1 상태 + 임베딩 켜짐, When I의 예문과 의미가 가까운 문장을 입력하면, Then 의미 되묻기 후보에 I·F가 **나오지 않는다**(재색인 없이).
- **AC-TP3-3** Given 비활성 토픽 소속 **키워드** K를 활성 노드 M이 조건으로 씀, When M의 조건을 만족하는 문장을 입력하면, Then M이 **정상 응답**한다(사전형 자산은 제외하지 않음).
- **AC-TP3-4** ★ Given 활성 노드 A의 `DIALOG_MOVE` → 토픽 T의 노드 B, When T 비활성화 영향 미리보기를 요청하면, Then "끊기는 참조" 목록에 A→B가 있다. 비활성화 후 A가 답하면 A의 나머지 아웃풋은 나가고 이동은 건너뛴다(trace `BROKEN_REFERENCE`).
- **AC-TP3-5** Given 토픽 T 비활성, When 버전을 수동 캡처하면, Then 스냅샷에 T의 노드·의도·FAQ가 **모두 있다**(캡처는 필터 미사용).
- **AC-TP3-6** Given 토픽 T 비활성, When 시뮬레이터에서 `비활성 토픽 포함`을 켜고 I의 예문을 입력하면 N이 답하고 결과에 "토픽: 보험청구(비활성)"가 보인다. 토글을 끄면 폴백이다. 이 요청 뒤 공개 대화는 여전히 폴백이다(운영 캐시 오염 0).
- **AC-TP3-7** Given 같은 인스턴스, When 토픽을 활성화하면, Then 다음 공개 요청부터 반영된다(`invalidate()` 호출 확인).
- **AC-TP3-8** Given 상담 켜진 챗봇, When 비활성 토픽 FAQ와 같은 질문으로 상담 힌트를 요청하면, Then 그 FAQ가 힌트에 나오지 않는다.

### AC-TP4. 교차 참조 점검 · 충돌

- **AC-TP4-1** Given 공통 노드 → 비활성 토픽 노드 이동 1건 · 배송 노드 → 환불 의도 조건 1건, When 설계 점검을 하면, Then `INACTIVE_TOPIC_REFERENCE` 경고 1건 · `CROSS_TOPIC_REFERENCE` 정보 1건이 출발·도착 토픽 이름과 함께 나온다.
- **AC-TP4-2** Given 배송 의도 "택배 언제 와"와 환불 의도 "택배 언제 와", When 두 번째 의도를 저장하면, Then 저장은 성공하고 경고에 상대 의도 이름과 **토픽 "배송"**이 있다. 설계 점검에 `CROSS_TOPIC_DUPLICATE_EXAMPLE` 1건이 나온다.
- **AC-TP4-3** (TC-22 1차 구체화) Given 토픽 A 키워드의 동의어 "반품"을 토픽 B 키워드에 추가, When 저장하면, Then 기존 규칙대로 **차단**되고 오류에 상대 키워드와 토픽 이름이 있다.
- **AC-TP4-4** Given 토픽 규칙 추가 전후, When 토픽이 없는 챗봇의 설계 점검을 하면, Then 결과가 동일하다.

### AC-TP5. 분리 (1차-B)

- **AC-TP5-6** Given 모든 토픽 + 공통 선택, When 분리하면, Then 새 챗봇의 자산 수·예문 수가 원본과 같고, 같은 입력 100문장에 대한 두 챗봇의 해석 결과(답한 자산 **이름** 기준)가 같다(임베딩 꺼진 상태 — 재색인 전).
- **AC-TP5-7** Given 동기 상한 초과 자산, When 분리하면 `TOPIC_SPLIT_TOO_LARGE`이고 아무것도 생기지 않는다.
- **AC-TP5-8** Given VIEWER, When 분리하면 `403`이다. 다른 챗봇 id로 요청하면 `404`다.
- **AC-TP5-9** Given 분리 완료, Then 감사에 새 챗봇 `COPY` 1건(summary에 건수만)이 있고 원본에는 감사가 없다. 채널·답변 설정·TC·대화로그가 새 챗봇에 0건이다.

### AC-TP6. 버전 · 감사 · 통계

- **AC-TP6-1** ★ Given 토픽이 없는 챗봇, When 도입 전후에 같은 자산으로 캡처하면, Then `contentHash`가 같다.
- **AC-TP6-2** Given 의도 I가 토픽 T였던 버전 v, 이후 T 삭제(공통으로 옮김), When v로 복원하면, Then I는 **공통**으로 복원되고 복원 경고 `TOPIC_MISSING` 1건이 있다. 토픽 활성 상태는 바뀌지 않는다.
- **AC-TP6-3** Given 토픽 활성 전환, Then 감사 `Topic STATUS_CHANGE` 1건이 있고 버전 자동 스냅샷은 생기지 않는다.
- **AC-TP6-4** (P-12 채택 시) Given 토픽 "배송" 노드가 답한 턴, When 로그를 보면 `topicId = 배송`이다. 이후 노드를 "환불"로 옮겨도 과거 행은 "배송"이다(`update` 0).

### AC-TP7. 권한 · 봉인 · 접근성

- **AC-TP7-1** Given VIEWER, When 토픽 생성·지정·전환하면 `403`, 목록·점검·미리보기(읽기)는 `200`이다. AGENT는 전부 `403`이다.
