## 1. 배경 / 목적

### 1.1 배경 — 직전 그룹이 만든 회귀 리스크에 대한 안전망이다

직전 **학습 고도화(No.16/23)** 그룹이 예문 자동 증강(DLE)을 도입해, `Intent.examples`가 **관리자 승인 한 번에 대량으로 늘어날 수 있게** 됐다. 그런데 예문은 저장 즉시 매칭에 반영된다(`appliedImmediately === true`, ADR-0018 보론). 즉 **승인 버튼 하나가 대화 동작을 즉시 바꾼다.**

`learning-augmentation.md`는 이 위험을 **제안 단위 안전장치**로 막았다 — 의미 보존 밴드·신규성·타 의도 충돌 경고·금지어·형식(§4.1.4의 검증 6종). 그러나 그 장치들은 **문장 1건이 타당한가**만 본다. 막지 못하는 것이 남아 있다.

| 남은 구멍 | 왜 기존 장치로 못 막는가 |
|---|---|
| **① 개별 제안은 전부 타당한데 전체 동작이 나빠진다** | 충돌 검사(③)는 `max cos(후보, 타 의도 예문) ≥ τ_accept`일 때 **경고만** 하고 차단하지 않는다(FR-L1-15 — 의도적 결정). 경고를 무시하고 10건을 승인하면 **경계에 있던 다른 의도들의 1위/2위가 뒤집힌다.** 뒤집혔다는 사실을 알 방법이 현재 없다 |
| **② 격차 조건(`τ_margin`)은 후보 1건만 봐서는 판정 불가** | ADR-0021은 `top1 − top2 < 0.05`면 확정이 아니라 **되묻기**로 보낸다. 예문이 늘면 top2가 올라가 **확정이던 질문이 되묻기로 강등**될 수 있다. 이것은 **제안 검증이 아니라 질의 집합 전체로만** 드러난다 |
| **③ 검증 화면이 "이 의도 안"만 본다** | 승인 화면은 대상 의도 1개의 맥락이다. 영향은 **챗봇 전체**에 퍼진다 |
| **④ 사후에 발견해도 무엇 때문인지 모른다** | 감사로그는 `"증강 예문 반영 (2건)"`(FR-L1-24)만 남는다. 어제와 오늘의 **동작 차이**를 재현할 수단이 없다 |

**PM 결정**: 예문이 대량으로 늘어나는 시점에 맞춰 이 그룹을 **바로 이어서** 진행한다(`개발명세서.md` §6 결정 30 맥락). 따라서 이 그룹의 설계 목표는 "테스트 도구를 만든다"가 아니라 **"직전 그룹이 만든 회귀 경로를 실제로 막는다"** 이다.

### 1.2 이미 있는 것과 없는 것 (경계를 먼저 긋는다)

**있다 — No.10 응답 테스트/시뮬레이션(구현 완료).** 코드 확인(`apps/api/src/simulation/`):

| 자산 | 실제 구현 | 이 그룹의 재사용 |
|---|---|---|
| `POST /chatbots/:id/simulate` | 단건 실행. `matchTrace`(1단계 top3·구간 판정)·`assetCounts`·`elapsedMs` 반환. **`ConversationLogService`를 주입하지 않는다**(AC-10-14 — 규약이 아니라 의존성 그래프로 로그 불가를 보장) | 실행 엔진 호출 방식을 **그대로 따른다** |
| `POST /chatbots/:id/simulate/compare` | **A = 저장본 / B = 저장본+오버레이** 로 같은 문장 배열을 각각 처음부터 재생, 턴별 `diff` 반환. `messages` **1~20건** 상한(FR-10-25) | **비교의 개념·판정 함수를 그대로 계승**한다 |
| `compareDiff()`(`lib/compare-diff.ts`) | 순수 함수. `outputsChanged`(정규화 직렬화 비교) + `matchChanged`(`matchedNodeId`/`matchedFaqId`/`matchedIntentId`) → `SAME`/`DIFFERENT`. **`trace`는 판정에 쓰지 않는다**(경유 경로 차이가 노이즈가 되므로) | **복제하지 않고 재사용**한다(FR-V4-3) |
| `mergeOverlay()`(엔진 순수 함수) | 저장본 번들 + 오버레이 → 새 번들. `draft-` 임시 id 지원, 원본 불변 | 사전 비교(M2)의 **B 계열 생성 수단** |
| `SheetReader`·`ImportStagingStore`(ADR-0007) | `.csv` 자체 구현 + `.xlsx` `exceljs` 스트리밍, 2단계(dry-run → commit), TTL 10분 메모리 스테이징, `importToken` 1회용 소비, `escapeCsvCell` | **대량 업로드 인프라 100% 재사용**(FR-V1-9) |
| `TrainingJobQueue`(ADR-0027) | in-process fire-and-forget. **`task` 콜백만 받고 `kind`를 모른다** — 코드 확인 결과 완전히 kind-agnostic | 대량 실행의 **실행기**로 재사용(J-6) |

**없다.** 대량 입력(엑셀), 기대값(TC) 저장소, 실행 결과 영속화, 실행 간 비교, 판정(통과/실패) 개념.

> **원본 문서가 이미 이 경계를 그어 두었다** — `quality-channel.md` **FR-10-29**:
> "입력 문장은 줄바꿈 구분 다건 입력을 허용한다(붙여넣기 지원). **엑셀 업로드 기반 대량 회귀 검증은 No.19(대화검증시스템/TC 테스트) 범위**이므로 이번에는 제공하지 않으며, 화면에 그 사실을 안내한다."
> 같은 문서 §Out of scope: "이번 비교는 **최대 20문장 직접 입력**까지다."
>
> **이 그룹은 그 예고를 그대로 이행한다.** 새 축은 **딱 3개**다 — ① **대량**(20 → 2,000) ② **기대값과 판정**(눈으로 보는 비교 → PASS/FAIL) ③ **영속화와 실행 간 비교**(일회성 → 시점 간 회귀 추적).

### 1.3 목적

1. 챗봇별 **회귀 테스트 자산(TC 세트)** 을 엑셀로 대량 등록·관리한다(No.19).
2. 수백~수천 건을 **비동기로 일괄 실행**하고 **기계적으로 PASS/FAIL 판정**한다(No.19).
3. **승인하기 전에** "이 증강 제안들을 반영하면 무엇이 깨지는가"를 본다(No.20 — 사전 회귀).
4. **과거 실행 결과와 비교**해 "어제는 통과하던 것이 오늘 깨졌다"를 찾아낸다(No.20 — 사후 회귀).
5. 위 전부를 **`packages/dialogue-engine` 수정 0건**, **대화 로그·통계·미응답 큐 오염 0건**으로 달성한다.
6. 대량 실행이 **운영 대화의 성능을 밀지 않게** 한다(이 그룹 고유의 최대 리스크 — §4.5).

| **J-4** | **판정 기준을 무엇으로 두는가** | **매칭 대상 ID 일치**(`matchedIntentId`/`matchedFaqId`/`matchedNodeId`)를 **유일한 PASS/FAIL 축**으로 한다. **응답 텍스트는 판정하지 않고** 정규화 해시로 **변화만 감지**한다. 결과는 4값: `PASS` / `FAIL` / `NOT_JUDGED` / `UNRESOLVED` | 바이트 일치는 **원리적으로 불가능**하다 — ① RAG/생성형 응답은 매번 다르다(ADR-0023: 외부 LLM, 비결정론) ② `SCENARIO`/`SURVEY`/`API_CONDITION` 3종은 **실행되지 않고 `unsupportedOutputs`로 보고된다**(ADR-0008) ③ 컨텍스트 폼의 `completionMessage`는 슬롯 치환으로 매번 달라진다. 반면 **매칭 ID는 결정론적**이며(엔진은 순수 함수, 타이브레이크까지 고정 — FR-N1-10) **이것이 바로 "인텐트·응답 매칭"의 검증 대상**이다. 응답 해시는 **`compareDiff()`의 `serializeOutputsForDiff()`를 재사용**하므로 신규 규칙이 0건이다. §4.1.5 |
| **J-5** | ⚠ **"엔티티(키워드) 매칭"을 어떻게 검증하는가** | **1차는 "기대 노드 ID 일치"로 간접 검증한다.** 키워드 단위 직접 판정은 **범위 밖**으로 두고 재검토 트리거를 남긴다 | **코드 확인**: `DialogueTurnResult`에 `matchedKeywordIds`가 **존재하지 않는다**. `TraceStep`도 `NODE_MATCHED`/`NODE_CONDITION_FAILED`의 `targetId`(노드 id)까지만 준다. 즉 **엔진을 고치지 않으면 키워드 판정이 불가능**하다. 그런데 FR-0-49(엔진 무수정)는 직전 그룹의 핵심 규약이다. **대안**: 노드 조건은 `의도 + 키워드` 조합이므로(ADR-0005) **그 노드가 매칭됐다 = 키워드 조건이 충족됐다**가 성립한다 — 간접 검증으로 원문의 의도를 대부분 달성한다. ⚠ **카탈로그 원문이 "인텐트·엔티티·응답 매칭"을 명시**하므로 **PM 확인 항목(P-2)**: 직접 판정이 필요하면 `DialogueTurnResult`에 **선택 필드 `matchedKeywordIds?`를 추가만** 하는 비파괴 확장이 가능하다(ADR-0020이 `ResolveOptions.semantic`을 선택 필드로 넣은 것과 대칭) — **ADR 사안**. §4.1.6 |
| **J-6** | ⚠ **대량 실행을 어떤 작업 인프라로 돌리는가** — `TrainingJob` 재사용? 새 큐? | **큐(`TrainingJobQueue`)는 재사용하고, 상태는 `TrainingJob`이 아니라 `TestRun` 자신이 갖는다.** `TrainingJob`에 `TC_RUN` kind를 추가하지 **않는다** | **코드 확인**: `TrainingJobQueue.enqueue(jobId, task)`는 **`task` 콜백만 받고 `kind`를 알지 못한다** — 완전히 kind-agnostic한 실행기다. 재사용 비용이 0이다. 반면 **`TrainingJob` 행은 중복이 된다**: ① `TestRun`은 **영속 자산**(비교 축이므로 남아야 한다)이고 `TrainingJob`은 **로그성 작업 상태**라 보존 정책이 다르다 ② `TrainingJob.resultSummary`는 **문장 원문 미포함**이 규약인데(NFR-LS4) TC 결과는 질문 문장을 담아야 화면이 성립한다 ③ `TestRun`이 이미 `status`·`progress`·`startedAt`/`finishedAt`을 가져야 하므로 `TrainingJob` 행은 **같은 값을 두 벌** 쓰게 된다. **이름 문제도 사라진다** — "Training"이 아닌 작업이 `TrainingJob`에 들어가지 않는다. ⚠ 큐 클래스를 `AsyncTaskQueue`로 **개명**할지(의미 정합) 그대로 둘지는 **`system-architect` 확정 사안**. §4.1.7 |
| **J-7** | **GPU 필요도 2가 여전히 맞는가** — 직전 그룹이 임베딩 매칭을 도입했다 | **맞다. 단 "자체 GPU를 쓰지 않는다"는 뜻이며 "GPU 부하를 만들지 않는다"는 뜻은 아니다.** 완화 3종을 **요구사항으로 못 박는다** | 이 그룹은 **새 모델을 적재하지 않는다** — 임베딩 추론은 전부 기존 ml-worker(No.18, GPU 4)에 위임된다. ADR-0024가 No.30을 8 → 1로 재산정한 것과 **같은 논리**(위임처의 등급이 이미 매겨져 있다). **결정적 관찰 3가지**: ① **A/B 비교는 임베딩 호출을 늘리지 않는다** — 같은 질문 문장·같은 `modelId`이므로 **벡터 1개를 두 계열이 공유**한다(코사인 계산만 2배, 그것은 CPU 메모리 연산이다) ② `EmbeddingProvider.embed(texts[], 'QUERY')`가 **배열을 받는다** — 색인기가 이미 `BATCH_SIZE=64`로 쓰고 있다. TC 2,000건 = **32회 호출**이지 2,000회가 아니다 ③ 벡터 캐시(`VectorCacheService`)는 **실행당 1회 로드**로 공유한다. §4.5 |
| **J-8** | ⚠ **대량 실행이 운영 대화의 임베딩 캐시를 파괴한다** (이 그룹 고유의 최대 위험) | **대량 실행은 전역 질의 임베딩 캐시를 오염시키지 않는다.** 실행 로컬 벡터 맵을 쓰거나 캐시 쓰기를 우회하는 경로를 **반드시** 둔다 | **코드 근거**: `QueryEmbeddingService`의 질의 캐시는 **LRU 1,000건 · TTL 10분**이며 `storeInCache()`가 초과분을 **가장 오래된 것부터 축출**한다. TC 2,000건을 실행하면 **운영 대화가 데워 놓은 1,000건이 전부 밀려난다** — 실행 직후 실사용자들의 임베딩 캐시 적중률이 **0으로 붕괴**하고, 모든 턴이 ml-worker를 다시 때린다. 이것은 **테스트 도구가 운영 품질을 떨어뜨리는** 정확히 그 유형의 사고다. 증상이 "실행 중"이 아니라 "**실행 후**"에 나타나 원인 추적이 어렵다. **요구사항 수준에서 금지**한다(FR-V1-20, NFR-VP4) |
| **J-9** | **대량 실행이 통계·미응답 큐를 오염시키는가** | **오염시키지 않는다. 의존성 그래프로 보장한다** — 실행 서비스는 `ConversationLogService`를 **주입하지 않는다** | `SimulationService`가 이미 이 방식이다(주석에 명시: "**읽기 전용** — `ConversationLogService`를 주입하지 않는다(FR-0-21, AC-10-14 — **규약이 아니라 의존성 그래프로** 로그 불가를 보장한다)"). 미응답 큐 적재 지점이 `ConversationLogService.record()` **내부**이므로(ADR-0019) 로그를 안 남기면 **큐·응답률·접속수·시간대 분포가 자동으로 안전**하다. 2,000건 실행이 미응답 큐에 2,000건을 꽂으면 No.15가 즉시 무너진다 — **안 하기로 약속하는 대신 할 수 없게 만든다**(ADR-0022의 봉인 방식) |
| **J-10** | **TC 실행에서 2단계(외부 RAG)를 호출하는가** | **기본 `false`. 명시적 옵션이며 실행당 별도 상한(기본 50건)을 둔다** | ① 2,000건 × RAG(목표 5초 P95, ADR-0023)는 **외부 서버를 사실상 DoS** 한다 — 그 서버는 **인증이 없고**(ADR-0022) 다른 이용자와 공유된다 ② `RagGateService`의 동시 게이트를 대량 실행이 독점하면 **운영 대화의 2단계가 굶는다** ③ 무엇보다 **RAG 응답은 비결정론적이라 판정에 쓸 수 없다**(J-4). 대신 `band === 'FAILED'`인 TC에 **"2단계로 갔을 것"** 을 **표시만** 한다(`ThresholdPreviewResponse.wouldUseRag` 선례) |
| **J-11** | **TC 세트와 실행 결과는 감사 대상인가** | **TC 세트 CRUD·임포트는 감사 대상이다. 실행·실행 결과는 감사 대상이 아니다** | TC 세트는 **관리자가 만든 자산**이고 다수 인원이 공유하며 "누가 기대값을 바꿨나"가 통제 대상이다 → `AuditTargetType`에 `TestCaseSet` **1종 추가**. 반면 실행은 **읽기 연산**이고 자산을 바꾸지 않으며, 기록하면 실행 1회당 감사 1건이 쌓인다(FR-15-35·FR-L2-25와 **같은 판단**). 또한 실행 결과에는 **사용자 발화가 아닌 관리자 작성 문장**만 들어가므로 NFR-S8(감사로그에 사용자 발화 유입 금지) 문제와는 무관하다 |
| **J-12** | ⚠ **신규 권한 문자열을 만드는가** | **만들지 않는 안을 권고한다** — 읽기 `simulation:read`, 쓰기 `dialogue:write`. ⚠ 최종 확정은 `system-architect` | **코드 확인**: `Permission` 유니온 **14종**에 `simulation:read`는 있으나 **`simulation:write`가 없다**. `ROLE_PERMISSIONS`상 VIEWER는 `simulation:read`를 갖고 `dialogue:write`는 갖지 않는다 → **읽기=`simulation:read` / 쓰기=`dialogue:write`** 조합이 "VIEWER는 보기만, EDITOR 이상이 작성·실행"이라는 요구를 **신규 문자열 0건으로** 정확히 만족한다(stats-learning J-7·learning-augmentation §2.1과 동일 원칙 — "동작이 바꾸는 자원을 기준으로 정한다"). **다만 두 도메인이 섞이는 어색함**이 있어 `simulation:write` 신설(15종)이 더 깔끔하다는 반론이 성립한다 — ADR-0015 갱신 사안이므로 **ADR로 확정**한다. ⚠ **실행(run) 권한**은 쓰기로 본다: 실행은 DB를 바꾸지 않지만 **ml-worker 자원을 대량 소비**하므로 조회 권한자에게 열면 안 된다 |

→ **J-3**의 근거. 한 줄에 **두 개의 요구**가 들어 있다 — "응답 비교"(=M2 사전)와 "회귀 리스크 관리"(=M1 사후). 둘을 분리해야 각각이 실현 가능해진다.

**근거 3 — No.10이 이 그룹에 남긴 문장**(`quality-channel.md` FR-10-29 / Out of scope):
> "**엑셀 업로드 기반 대량 회귀 검증은 No.19(대화검증시스템/TC 테스트) 범위**이므로 이번에는 제공하지 않으며, 화면에 그 사실을 안내한다." / "이번 비교는 **최대 20문장 직접 입력**까지다."

→ **§1.2 경계**의 근거. 화면에 이미 "이건 No.19 범위입니다" 안내가 떠 있으므로, 이 그룹은 **그 안내를 실제 링크로 바꾸는 일**을 포함한다(FR-V3-2).

**근거 4 — No.10이 이미 A/B 비교를 한다**(`quality-channel.md` FR-10-26/27):
> "A는 **저장본 번들**, B는 **저장본 + 오버레이 번들**이다. 두 계열은 **독립된 대화 상태**를 유지해 멀티턴 비교가 가능해야 한다." / "차이 판정 `diff`: ① `outputsChanged` ② `matchChanged` ③ 종합 `status`: `SAME`/`DIFFERENT`. 판정 로직은 **순수 함수로 분리**한다."

**근거 5 — GPU 구간 정의**(`기능요구사항.md` §1):
> "| 1~2 | **CPU 전용** — CRUD/설정/통계조회/**규칙매칭** |"

→ **J-7**. 이 그룹의 자체 연산은 전부 CPU다(CRUD·엑셀 파싱·코사인 계산·diff·집계). 임베딩만 위임 호출이며, 그 위임처는 이미 No.18로 등급이 매겨져 있다.

**근거 6 — 직전 그룹이 남긴 회귀 표면**(`learning-augmentation.md` FR-L1-15):
> "**충돌 경고(③)는 차단이 아니다.** 관리자가 보고 판단한다 — 의도 설계상 의도적으로 가까운 두 의도가 존재할 수 있다."

→ **§1.1 ①**의 근거. 차단하지 않기로 한 것이 옳은 결정이었다면, **차단 대신 관찰할 수단**이 있어야 한다. 그것이 이 그룹이다.

  "통과→실패" 회귀 N건                      "승인하면 M건이 달라진다"
  "실패→통과" 개선 M건                      ★ 승인 전에 본다 = 회귀 예방

## 2. 사용자 역할 및 시나리오

### 2.1 역할

`security-audit.md` §2.1의 역할 3종을 상속한다. **신규 권한 문자열을 만들지 않는 안을 권고**한다(J-12).

| 역할 | 이 그룹에서의 활동 | 권한(권고안) |
|---|---|---|
| **ADMIN** | EDITOR의 모든 활동 + 보존 정책 관련 설정 | `simulation:read` + `dialogue:write` |
| **EDITOR** | TC 세트 생성·편집·업로드·실행·비교(**이 그룹의 주 사용자**) | `simulation:read` + `dialogue:write` |
| **VIEWER** | TC 세트·실행 결과·비교 결과 **조회만**. 생성·업로드·실행·삭제 버튼이 **렌더되지 않는다** | `simulation:read` |
| 최종 사용자 | **직접 사용하지 않으며, 이 기능의 존재를 알 수 없다.** 다만 이 기능이 막아 주는 회귀의 피해자가 이 사람이다 | — |

### 2.2 사용자 시나리오

**S-1. 증강 승인 전에 영향을 본다 (EDITOR · No.20 M2 · ★ 이 그룹의 핵심 시나리오)**
`환불규정문의` 의도에 증강 제안 9건이 떠 있다. 편집자가 6건을 선택하고 `승인` 대신 **`선택 항목 영향도 검사`** 를 누른다. 세트 `전체 회귀 480건`을 고르자 실행이 시작되고 40초 뒤 결과가 뜬다 — **`통과 471 → 468 (▼3)`**. 달라진 3건을 열어 보니 전부 `반품문의` 의도로 가던 질문이 `환불규정문의`로 넘어왔다. 편집자는 **승인 화면으로 돌아가 충돌 배지가 붙었던 2건을 선택 해제**하고 다시 검사한다 — 이번에는 `통과 471 → 471 (변화 없음)`. 그제서야 승인한다. **자산은 이 과정에서 1바이트도 바뀌지 않았다.**

**S-2. 엑셀 500건을 올린다 (EDITOR · No.19)**
운영팀이 실제 상담 이력에서 뽑은 500문장 엑셀을 받았다. `TC 업로드`에 끌어다 놓으면 검증 리포트가 뜬다 — `총 500행 / 신규 487 / 중복 8 / 오류 5`. 오류 5건은 전부 **`기대 대상명 '배송문의2'를 찾을 수 없습니다`(3행, 17행, …)** 다. 편집자가 `오류 행만 CSV로 내려받기`로 5건을 받아 이름을 고친 뒤 다시 올린다. 확정하면 487건이 세트에 들어간다.

**S-3. 어제는 통과했는데 오늘 깨졌다 (EDITOR · No.20 M1)**
아침에 `전체 회귀` 세트를 실행한다. `통과 462 / 실패 18 / 판정없음 0`. 어제 실행(`통과 471`)과 비교하니 **`통과 → 실패` 9건**이 목록에 뜬다. 각 행에 어제의 매칭 대상과 오늘의 매칭 대상이 나란히 보인다 — 9건 모두 `주문조회` → `배송문의`. 실행 헤더의 **환경 지문**을 비교하니 어제와 오늘 사이에 **의도 예문이 +46건** 늘어 있다. 편집자는 이력관리(No.13)에서 `"증강 예문 반영 (46건)"` 레코드를 찾아 경위를 확정한다.

**S-4. 기대값이 사라졌다 (EDITOR)**
`배송문의` 의도를 삭제한 뒤 세트를 실행했다. 그 의도를 기대하던 TC 32건이 **`UNRESOLVED — 기대 대상이 더 이상 존재하지 않습니다`** 로 표시되고, **실패(FAIL)로 집계되지 않는다.** 요약 줄에 `판정 불가 32건 — TC 정리가 필요합니다`가 뜨고 `일괄 비활성` 액션이 제시된다. **삭제가 회귀로 오인되지 않는다.**

**S-5. 실행이 오래 걸린다 (EDITOR)**
2,000건 실행을 걸고 편집자가 다른 화면으로 이동했다. 10분 뒤 돌아오니 실행 목록에 `완료 · 2,000건 · 4분 12초`가 남아 있고 결과를 그대로 볼 수 있다. **상태가 서버에 있다.**

**S-6. 실행을 중단한다 (EDITOR)**
세트를 잘못 골라 실행했다. `취소`를 누르면 다음 TC 경계에서 멈추고 `CANCELLED · 340/2000 처리됨`으로 남는다. **거기까지의 결과는 조회할 수 있지만 비교의 기준선으로는 쓸 수 없다**(부분 실행끼리 비교하면 "사라진 TC"가 회귀로 보인다).

**S-7. 임베딩이 꺼져 있다 (EDITOR)**
ml-worker가 내려간 상태에서 실행했다. 결과 헤더에 **`⚠ 의미 매칭 저하 모드로 실행됨 — 규칙 매칭만 적용`** 배지가 뜨고, 모든 TC의 `band`가 `SKIPPED`다. 이 실행은 **저하 모드가 아닌 실행과 비교할 때 경고를 띄운다** — 환경이 다르면 차이는 회귀가 아니다.

**S-8. 대량 실행이 끝났는데 서비스가 느려지지 않는다 (운영자 · J-8)**
2,000건 실행 직후에도 실제 사용자 대화의 응답 시간이 평소와 같다. 대량 실행은 **전역 질의 임베딩 캐시를 건드리지 않았다.**

**S-9. 금지어가 섞인 TC (EDITOR)**
업로드 파일에 금지어가 포함된 질문 문장이 있다. TC는 **관리자가 작성한 검증 입력**이므로 등록 자체는 막지 않되, 실행 결과에 **`금지어 필터로 차단된 응답`** 임이 표시된다(실제 대화에서 차단되는 동작을 그대로 재현하는 것이 검증의 목적이다). **단 TC 세트 내보내기 CSV에는 수식 인젝션 방어가 적용된다**(`escapeCsvCell` 재사용).

**S-10. 다국어/이모지 문장 (EDITOR)**
영문·일문·이모지가 섞인 질문이 있다. 정규화는 `normalizeText`(NFKC → trim → 소문자 → 공백 축약) **한 벌**을 그대로 쓰며, 별도 언어 분기를 두지 않는다. 임베딩이 2자 미만으로 정규화되는 문장은 의미 매칭을 시도하지 않고(`EX-N1-6` 상속) `band: SKIPPED`로 표시된다.

**S-11. 멀티턴 TC (EDITOR)**
`커피주문` 컨텍스트 폼을 검증하려면 3턴이 필요하다. TC 1건에 **문장 배열**(최대 5턴)을 담고, **마지막 턴의 매칭 결과로 판정**한다. 중간 턴의 결과는 참고로 함께 보인다. 상태는 TC 내부에서만 이어지고 **TC 간에는 절대 이어지지 않는다**(각 TC는 독립 세션).

**S-12. 세션 만료 (EDITOR)**
멀티턴 TC 실행 중 `sessionTimeoutMinutes`를 넘기는 상황은 발생하지 않는다 — 실행은 **고정된 `now` 한 시각**으로 전 TC를 처리한다(`SimulationService`가 `const now = new Date()`를 1회만 잡는 것과 동일). 이로써 실행 결과가 **실행 소요 시간에 영향받지 않는다**(재현성).

**S-13. VIEWER 접근 (VIEWER)**
운영 모니터는 지난 실행 결과와 비교 화면을 볼 수 있지만 `실행`·`업로드`·`TC 추가`·`삭제` 버튼이 **렌더되지 않는다**. API를 직접 호출해도 `403`이며 DB·ml-worker 호출이 발생하지 않는다.

**S-14. 접근성 (EDITOR)**
결과 표의 PASS/FAIL은 **색상만이 아니라 아이콘 + 텍스트 라벨**로 표시된다. 비교 화면의 `개선/회귀` 구분도 마찬가지다. 진행률은 `aria-live="polite"`로 안내되며, 좁은 화면에서 A/B는 세로 스택으로 접힌다(FR-10-28과 동일 규칙).

## 4. 기능별 요구사항

### 4.1 No.19 — 대화검증시스템 & TC 테스트

#### 4.1.1 범위 확정 — No.10과의 경계

| 축 | **No.10**(구현 완료) | **No.19**(이번) |
|---|---|---|
| 입력 규모 | 문장 **1~20건**(직접 입력·붙여넣기) | **1~2,000건**(엑셀/CSV 업로드) |
| 입력 보관 | **보관하지 않는다**(일회성) | **`TestCase`로 영속화**(재사용 자산) |
| 기대값 | **없다**(사람이 눈으로 본다) | **있다**(`expectedKind` + `expectedTargetId`) |
| 판정 | 없다(A/B `SAME`/`DIFFERENT`만) | **`PASS`/`FAIL`/`NOT_JUDGED`/`UNRESOLVED`** |
| 실행 방식 | **동기**(요청 안에서 완료) | **비동기 Job**(202 + 폴링, 취소 가능) |
| 결과 보관 | 없다 | **`TestRun` + `TestRunCase`로 영속화** |
| 비교 축 | 저장본 vs 오버레이(1회성) | 저장본 vs 오버레이 **+ 실행 vs 실행** |

> **핵심**: No.19는 No.10을 대체하지 않는다. **단건 탐색은 여전히 시뮬레이터**이고, No.19는 **반복 가능한 회귀 자산**이다. 화면에서도 서로를 링크로 안내한다(FR-V3-2).

#### 4.1.2 TC 데이터 모델 — J-1 결정

**결정: TC는 `질문(1~5턴) + 기대 유형 + 기대 대상 ID`를 저장한다. 기대 응답 텍스트는 메모로만 저장하고 판정에 쓰지 않는다.**

| ID | 요구사항 |
|---|---|
| FR-V1-1 | TC는 **세트(`TestCaseSet`)** 에 속한다. 세트는 `{ name, description?, isDefault }`를 가지며 **챗봇당 최대 20개**다. 세트 이름은 챗봇 내에서 **정규화 기준 유일**하다(ADR-0006 규약 재사용). |
| FR-V1-2 | TC 1건의 구성: `{ seq, messages: string[](1~5, 각 1~1000자), expectedKind, expectedTargetId?, expectedAnswerNote?, tags?, enabled }`. **`messages`가 2건 이상이면 멀티턴 TC**이며 **마지막 턴으로 판정**한다(S-11). |
| FR-V1-3 | **`expectedKind` 5종**: `INTENT` · `FAQ` · `NODE` · `FALLBACK`(어떤 것도 매칭되지 않아야 함) · `ANY`(판정하지 않음 — 회귀 비교 전용). `INTENT`/`FAQ`/`NODE`는 `expectedTargetId` 필수, `FALLBACK`/`ANY`는 금지. |
| FR-V1-4 | **기대 대상은 ID로 저장한다.** 표시용 이름(`expectedTargetName`)은 **조회 시점에 현재 자산에서 읽어 채운다** — 저장하지 않는다. 근거: 이름을 저장하면 이름 변경이 **TC의 거짓 실패**로 나타나고, 이름만으로 저장하면 이름 변경이 **TC 전체를 깨뜨린다**. |
| FR-V1-5 | `expectedAnswerNote`는 **자유 서술 메모**(최대 500자)이며 **판정에 일절 사용되지 않는다.** 화면은 이 필드 옆에 "**참고용 — 판정에 사용되지 않습니다**"를 상시 표기한다(오해 방지). |
| FR-V1-6 | **TC 상한**: 세트당 **2,000건**, 챗봇당 총 **5,000건**(기존 `IMPORT_LIMITS.maxRows = 5000`과 정합). 초과 시 `TEST_CASE_LIMIT_EXCEEDED`. |
| FR-V1-7 | 같은 세트 안에서 `messages`의 **정규화 결합 문자열이 동일한 TC는 중복**으로 본다. 업로드 시 중복 행은 **오류가 아니라 `duplicatedRows`로 집계**되고 건너뛴다(기존 임포트 리포트 규약 재사용). |
| FR-V1-8 | TC·세트는 **감사 대상**이다. `AuditTargetType`에 **`TestCaseSet` 1종 추가**, 대량 임포트는 **배치 1건 + 요약**(ADR-0016 규약 그대로). 개별 TC 편집은 소속 세트의 `UPDATE`로 기록한다. |

#### 4.1.3 엑셀 대량 업로드 — ADR-0007 인프라 100% 재사용

| `ChatbotAnswerSetting` | 임계값 3종(환경 지문) |
| `AugmentationSuggestion` | M2의 `AUGMENTATION_SUGGESTIONS` 오버레이 소스(**읽기 전용**) |

### 5.2 신규 데이터 모델 제안 (`system-architect` 확정 사항)

| 테이블 | 목적 | 핵심 컬럼(개요) | 판단 근거 |
|---|---|---|---|
| **`TestCaseSet`** | TC 묶음 | `chatbotId`, `name`, `nameNormalized`, `description?`, `isDefault`, `caseCount`(파생 or 계산), `createdAt`/`updatedAt` · `@@unique([chatbotId, nameNormalized])` | 쓰기 주체 = 세트 CRUD·임포트. ADR-0006 유일성 규약 재사용 |
| **`TestCase`** | 기대값을 가진 검증 입력 | `setId`, `chatbotId`, `seq`, `messages`(JSON string[]), `messagesNormalized`(중복 판정 키), `expectedKind`, `expectedTargetId?`, `expectedAnswerNote?`, `tags?`(JSON), `enabled` · `@@unique([setId, messagesNormalized])` | `expectedTargetId`에 **FK를 걸지 않는다** — 걸면 TC가 있는 의도를 삭제할 수 없고, 삭제는 정당한 동작이다(`AugmentationSuggestion.intentId`·`EmbeddingVector.ownerId`와 **동일한 의도적 예외**). 대신 조회 시 `UNRESOLVED` 판정 |
| **`TestRun`** | 실행 스냅샷 = **버전 축**(J-2) | `chatbotId`, `setId`, `mode`(SINGLE\|OVERLAY_COMPARE), `overlaySource`, `status`(QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELLED), `progress`, `totalCount`/`processedCount`, `summary`(JSON: pass/fail/notJudged/unresolved, A/B 각각), `envFingerprint`(JSON), `degradedMode`, `failureReason?`, `startedAt`/`finishedAt`, `createdAt` | **쓰기 주체 = 실행 작업**이고 `FAILED`·`CANCELLED`가 실제로 발생한다 → ADR-0004 기준 통과. `TrainingJob`과 **합치지 않는 이유는 J-6** |
| **`TestRunCase`** | TC 1건의 실행 결과 | `runId`, `caseId`, `seq`, `resultA`(PASS/FAIL/NOT_JUDGED/UNRESOLVED), `matchedIntentIdA?`/`matchedFaqIdA?`/`matchedNodeIdA?`, `bandA`, `top1ScoreA?`, `outputsHashA`, `outputsPreviewA`, (B 계열 동일 필드, `mode=OVERLAY_COMPARE`일 때만), `diffStatus?`, `elapsedMsA`, `unsupportedCountA` · `@@index([runId, resultA])` | 비교의 **원자 단위**. `trace` 전문은 담지 않는다(용량 — FR-V1-29) |

**만들지 않는 것**: 자산 스냅샷 테이블(J-2) · TC 세트 버전 이력 · `TrainingJob`의 `TC_RUN` kind(J-6) · 비교 결과 저장 테이블(FR-V2-5) · 새 큐 클래스(J-6 C안) · Redis/BullMQ · `ImportBatch`(ADR-0007 유지).

**보존 정책**: `TestRun`은 **세트당 최근 20건 + 고정(pin) 최대 5건**을 유지하고 초과분은 **오래된 것부터 실행 결과와 함께 정리**한다. 근거: 2,000 TC × 20 run = 40,000행/세트이며 무한 누적은 SQLite에 부담이다. ⚠ 정리 시점은 **새 실행 완료 직후**(스케줄러 인프라가 없으므로 — 선행 그룹과 동일 판단).

## 7. 수용기준 (AC)

### AC-V1. TC 세트와 대량 업로드 (No.19)

- **AC-V1-1** Given 500행 CSV, When dry-run을 실행하면, Then `{ totalRows, newItems, duplicatedRows, errors[] }` 리포트가 오고 **DB는 변경되지 않았다**.
- **AC-V1-2** Given 기대 대상명이 존재하지 않는 행, When dry-run을 보면, Then 그 행이 `TARGET_NOT_FOUND` 오류로 **행 번호와 함께** 보고된다.
- **AC-V1-3** Given 정규화 기준 동명 의도가 2개인 상태에서 그 이름을 쓴 행, When dry-run을 보면, Then `AMBIGUOUS_TARGET`으로 보고되고 **커밋되지 않는다**.
- **AC-V1-4** Given dry-run 후 11분 경과, When 커밋하면, Then `400 IMPORT_TOKEN_EXPIRED` + 재검증 안내다(기존 규약 재사용).
- **AC-V1-5** Given 같은 `importToken`으로 2회 커밋, When 두 번째를 시도하면, Then 실패한다(1회용 소비).
- **AC-V1-6** Given `.xlsx` 파일, When 업로드하면, Then `.csv`와 **동일한 리포트 구조**가 온다(`SheetReader` 인터페이스 재사용).
- **AC-V1-7** Given 세트에 TC 2,000건, When 1건 더 추가하면, Then `TEST_CASE_LIMIT_EXCEEDED`다.
- **AC-V1-8** Given TC 세트 내보내기, When CSV를 열면, Then **업로드와 같은 컬럼 규격**이며 `=`로 시작하는 셀에 `'`가 붙어 있다.
- **AC-V1-9** Given 의도 이름을 변경, When TC 목록을 조회하면, Then **표시 이름이 새 이름으로 바뀌어 보이고 TC는 여전히 유효**하다(ID 저장 — FR-V1-4).

### AC-V2. 대량 실행과 판정 (No.19)

- **AC-V2-1** Given TC 480건인 세트, When 실행을 요청하면, Then **`202 { runId }`** 가 즉시(500ms 이내) 오고 상태가 `QUEUED`/`RUNNING`이다.
- **AC-V2-2** Given 실행 진행 중, When 다시 실행을 요청하면, Then `409 TEST_RUN_IN_PROGRESS`다.
- **AC-V2-3** Given 실행 완료, When 결과를 조회하면, Then 요약 `{ pass, fail, notJudged, unresolved }`의 **합이 실행 대상 TC 수와 정확히 일치**한다.
- **AC-V2-4** Given `expectedKind: 'INTENT'`이고 실제 `matchedIntentId`가 일치, When 판정을 보면, Then `PASS`다.
- **AC-V2-5** Given `expectedKind: 'FALLBACK'`이고 세 매칭 ID가 모두 없음, When 판정을 보면, Then `PASS`다.
- **AC-V2-6** Given 기대 대상 의도를 삭제한 뒤 실행, When 결과를 보면, Then 해당 TC가 **`UNRESOLVED`** 이고 **`fail` 집계에 들어가지 않는다**(FR-V1-27).
- **AC-V2-7** Given `expectedKind: 'ANY'`, When 판정을 보면, Then `NOT_JUDGED`이며 **응답 해시는 기록돼 있다**(비교에는 쓰인다).
- **AC-V2-8** Given 실행 중 취소, When 상태를 보면, Then `CANCELLED`이고 `processedCount`가 전체보다 작으며, **비교 기준선으로 선택하면 `TEST_RUN_NOT_COMPARABLE`** 이다.
- **AC-V2-9** Given 2,000건 실행, When 임베딩 호출 횟수를 계측하면, Then **`ceil(고유문장수 / 64)` 회**이며 TC 수만큼 호출되지 않는다(NFR-VP3).
- **AC-V2-10** Given 실행 완료, When `ConversationLog`·`UnansweredQuestion`·`RagCallLog` 행 수를 실행 전후로 비교하면, Then **모두 0건 증가**다(**J-9**).
- **AC-V2-11** Given 실행 완료, When `Intent`·`Keyword`·`FaqEntry`·`DialogNode`의 `updatedAt`을 확인하면, Then **어느 것도 변경되지 않았다**.
- **AC-V2-12** Given 같은 자산·같은 TC로 2회 연속 실행(RAG 미사용), When 두 결과를 비교하면, Then **모든 TC의 판정과 매칭 ID와 응답 해시가 동일**하다(NFR-VM6).
- **AC-V2-13** Given ml-worker 중지 상태, When 실행하면, Then 실행이 **성공하고** 모든 `band`가 `SKIPPED`이며 `degradedMode: true`가 기록된다(기능이 멈추지 않는다).
- **AC-V2-14** Given 서버를 실행 중 재시작, When 기동 후 상태를 보면, Then 그 실행이 `FAILED(SERVER_RESTART)`로 정리돼 있다.

### AC-V3. 비교 (No.20)

- **AC-V3-1** Given 같은 세트의 실행 2건, When 비교를 조회하면, Then 각 TC가 `REGRESSED`/`IMPROVED`/`CHANGED`/`UNCHANGED`/`ONLY_IN_ONE` 중 하나로 분류된다.
- **AC-V3-2** Given 어제 PASS·오늘 FAIL인 TC, When 비교를 보면, Then `REGRESSED`이고 **양쪽의 매칭 대상이 나란히** 보인다.
- **AC-V3-3** Given 두 실행 사이에 TC 5건을 추가, When 비교를 보면, Then 그 5건이 **`ONLY_IN_ONE`으로 분리**되고 통과 수 증가가 **개선으로 집계되지 않는다**(FR-V2-18).
- **AC-V3-4** Given 세트가 서로 다른 두 실행, When 비교를 요청하면, Then `400 TEST_RUN_NOT_COMPARABLE`이다.
- **AC-V3-5** Given `embeddingModelId`가 다른 두 실행, When 비교를 보면, Then **강한 경고 배지**가 표시된다(FR-V2-19).
- **AC-V3-6** Given `overlaySource: 'AUGMENTATION_SUGGESTIONS'` + 제안 6건, When 실행이 끝나면, Then A/B 요약이 각각 나오고 **`AugmentationSuggestion`의 `status`·`updatedAt`이 전혀 변하지 않았다**(**NFR-VS3**).
- **AC-V3-7** Given 증강 제안 6건을 오버레이로 적용, When 그 제안과 표현이 유사한 질문 TC의 B 계열 `top1Score`를 보면, Then **A보다 높다**(FR-V2-13이 실제로 동작함을 증명 — 오버레이 예문이 임베딩됐다).
- **AC-V3-8** Given `stale`인 제안 id가 섞인 요청, When 결과 헤더를 보면, Then **제외 건수가 표시**되고 요청 전체는 성공한다(FR-V2-12).
- **AC-V3-9** Given `overlaySource: 'INLINE'`, When 요청 본문을 보면, Then **No.10과 동일한 `DialogueOverlay` 스키마**를 쓴다(새 DTO를 만들지 않았다).
- **AC-V3-10** Given `useRag: false`(기본값), When 실행하면, Then **외부 RAG로 나가는 HTTP가 0건**이다.
- **AC-V3-11** Given `useRag: true`이고 `band=FAILED`인 TC가 200건, When 실행하면, Then RAG 호출은 **최대 50건**이고 나머지는 `wouldUseRag: true` 표시만 된다(FR-V2-20).

### AC-V4. 봉인·성능·권한 (공통)

- **AC-V4-1** Given 저장소 전체, When 실행 모듈의 import 그래프를 검사하면, Then `ConversationLogService`·`IntentsService`·`KeywordsService`가 **0건** 참조된다(정적 검사 — FR-0-60/61).
- **AC-V4-2** Given 저장소 전체, When `packages/dialogue-engine`의 git diff를 확인하면, Then **변경 0건**이다(NFR-VM3).
- **AC-V4-3** ⚠ Given 전역 질의 캐시를 900건까지 채운 상태, When TC 2,000건을 실행하고 다시 확인하면, Then **원래 캐시 항목이 여전히 남아 있다**(축출되지 않았다 — **J-8**, NFR-VP4).
- **AC-V4-4** Given 실행 중, When 다른 관리자 API를 호출하면, Then P95 지연 증가가 **20% 미만**이다(NFR-VP5).

- **AC-V4-6** Given 공개 API 라우트 목록, When `@Public()` 핸들러 수를 세면, Then **정확히 6개**다(FR-0-66).

- **AC-V4-10** Given 환경변수를 하나도 설정하지 않은 환경, When 서버를 기동하고 실행하면, Then **정상 동작**한다(FR-0-64).

## 8. 예외 케이스 (EX)

| ID | 상황 | 기대 동작 |
|---|---|---|
| EX-V-1 | 실행 중 ml-worker가 내려감 | 남은 TC는 **저하 모드로 계속 실행**되고, `degradedMode: true` + **"실행 도중 저하 모드로 전환됨"** 을 결과에 기록한다. 실행을 실패시키지 않는다 |
| EX-V-2 | 실행 중 임계값(`ChatbotAnswerSetting`)이 변경됨 | 실행은 **시작 시점에 읽은 값**을 끝까지 쓴다(환경 지문에 그 값이 남는다). 실행 중간에 기준이 바뀌면 결과 해석이 불가능해진다 |
| EX-V-3 | 실행 중 의도·노드가 삭제됨 | 번들은 **실행 시작 시 1회 로드**한 것을 쓰므로 실행 자체는 일관된다. 삭제는 **다음 실행부터** `UNRESOLVED`로 나타난다 |
| EX-V-4 | 질문 문장이 정규화 후 2자 미만 | 의미 매칭을 시도하지 않고 `band: SKIPPED`(EX-N1-6 상속). 규칙 매칭 판정은 정상 수행 |
| EX-V-5 | 질문 문장에 **금지어** 포함 | TC 등록은 허용. 실행 결과에 **차단 사실을 표시**(S-9). 실제 대화 동작의 재현이 목적이다 |
| EX-V-6 | 질문 문장이 **다국어·이모지** | `normalizeText` 한 벌을 그대로 적용. 언어별 분기를 두지 않는다(S-10) |
| EX-V-7 | 멀티턴 TC에서 **컨텍스트 세션이 만료** | 실행은 **고정된 단일 `now`** 를 쓰므로 실행 소요 시간에 의한 만료가 발생하지 않는다(S-12). TC가 의도적으로 만료를 검증하려면 `ANY` 기대값 + 응답 해시 비교로 한다 |
| EX-V-8 | 멀티턴 TC 중간 턴에서 **되묻기(AMBIGUOUS)** 발생 | 그대로 진행하고 **마지막 턴으로 판정**한다. 중간 턴의 `band`는 참고 지표로 보인다 |
| EX-V-9 | 기대값이 `FALLBACK`인데 **폴백 노드가 응답** | `matchedNodeId`가 채워지므로 **FAIL**이다. ⚠ 이 동작은 직관과 다를 수 있어 화면이 "폴백 노드가 응답한 경우도 매칭으로 봅니다"를 명시한다 |
| EX-V-10 | 엑셀에 **빈 행·헤더 행**이 섞임 | 빈 행은 건너뛰고, 헤더 행은 자동 판별한다(기존 파서 규약). 판별 실패 시 첫 행이 오류로 보고될 뿐 전체가 실패하지 않는다 |
| EX-V-11 | 업로드 파일이 **EUC-KR 인코딩** | 기존 CSV 리더의 동작을 그대로 따른다(ADR-0007이 `.xlsx` 지원을 유지한 이유가 바로 이것이다). 깨진 문자는 `TARGET_NOT_FOUND` 등으로 드러나며 **템플릿 링크를 함께 안내**한다 |
| EX-V-12 | 두 실행의 `degradedMode`가 서로 다름 | 비교는 허용하되 **강한 경고**를 띄운다(FR-V2-19). 저하 모드끼리, 정상끼리 비교하는 것이 올바른 사용법임을 안내한다 |
| EX-V-13 | 세트의 모든 TC가 `enabled: false` | `400 TEST_SET_EMPTY`(FR-V1-25) |
| EX-V-14 | 보존 한도를 넘겨 오래된 실행이 정리됨 | 비교 화면에서 참조하던 실행이 사라지면 **"기준 실행이 정리되었습니다"** 안내 + 다른 실행 선택을 제시한다. `pin`한 실행은 정리되지 않는다 |

| **P-1** | **실행 규모 전제** — 챗봇 수 × TC 수 × 실행 빈도. "야간 전체 회귀"를 운영할 계획이 있는가? | 단일 프로세스 전제(§4.5)가 유지되는지, **실행 전용 워커 분리**가 1차에 필요한지가 갈린다. 자동 스케줄 요구가 있으면 **스케줄러 인프라 부재(§9)** 가 즉시 제약이 된다 | 단일 프로세스 · 수동 실행 · 챗봇당 동시 1건 |
| **P-2** | ⚠ **엔티티(키워드) 직접 판정이 필요한가** | 카탈로그 원문이 "인텐트·**엔티티**·응답 매칭"이다. 필요하면 **엔진에 선택 필드 `matchedKeywordIds?` 추가**(FR-0-59 예외, ADR 필요)가 선행한다. 불필요하면 노드 기대값 간접 검증으로 충분하다(J-5) | **간접 검증**(엔진 무수정) |
| **P-3** | **미응답 큐 → TC 승격 경로를 1차에 넣는가** | 회귀 세트를 빠르게 키우는 가장 현실적인 경로이지만, No.15 화면에 액션이 하나 늘고 **마스킹된 문장이 TC가 된다**(NFR-VS6) | **1차 범위 포함**(단방향·1건 단위만) |
| **P-4** | **실행 결과 보존 정책** — 세트당 20건 + 고정 5건이 적절한가 | 2,000 TC × 20 run = 40,000행/세트다. 감사·품질 보고 요구가 있으면 더 길게, 용량이 제약이면 더 짧게 | **20 + pin 5** |
| **P-5** | **`simulation:write` 권한을 신설하는가**(J-12) | 권한 유니온이 14 → 15가 되고 `ROLE_PERMISSIONS`가 바뀐다. ADR-0015 갱신 사안 | **신설하지 않음**(읽기 `simulation:read` / 쓰기 `dialogue:write`) |
| **P-6** | **TC 실행에서 외부 RAG를 호출할 수 있게 하는가**(J-10) | 외부 RAG 서버는 **인증이 없고 공유**된다. 대량 호출은 다른 이용자에게 영향을 준다. 호출하지 않으면 2단계 품질은 검증 대상에서 빠진다 | **기본 비활성 · 옵션 시 실행당 50건 상한** |
| **P-7** | **화면 정보 구조** — 최상위 탭 신설(7 → 8탭) vs 기존 탭의 서브내비 | 탭 8개는 이미 많다. `ui-designer` 판단 사항이지만 제품 방향(검증을 1급 기능으로 노출할 것인가)은 PM 사안 | `ui-designer` 판단에 위임 |
