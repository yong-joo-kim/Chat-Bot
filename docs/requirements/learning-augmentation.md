## 1. 배경 / 목적

### 1.1 배경 — 세 개의 선행 결정이 이 그룹을 정확히 겨냥하고 있다

이 그룹은 새로 시작하는 기능이 아니라, 앞선 두 그룹이 **명시적으로 미뤄 둔 자리**다.

| 선행 결정 | 미뤄 둔 내용 | 이번 그룹의 인계 지점 |
|---|---|---|
| **ADR-0018**(No.15) | "경량 분류기 재학습은 **No.23의 정의 그 자체**", "딥러닝 증강학습은 **No.16**" — 둘 다 미구현. 대신 `LearningApplyService.applyLearning()` **단일 메서드**를 인계 지점으로 남김 | §4.4에서 그 계약을 **실제로 검증**하고, **교체할지 말지**를 결정한다(⚠ 결론은 "교체하지 않는다" — J-6) |
| **ADR-0024**(No.18/30) | `apps/ml-worker`를 **추론 전용**으로 확정. "학습·파인튜닝은 포함하지 않는다. 그것은 No.16(DLE 증강학습)·No.18의 학습 부분" + 재검토 트리거에 **"No.16·No.23 착수 → 학습 기능 추가, Job Queue·`TrainingJob` 도입, GPU 5 복귀"** 를 명시 | §4.5에서 이 트리거를 **부분적으로만 발동**시키는 안을 제시한다(⚠ J-7) |
| **개발명세서 §3** | `TrainingJob` 테이블을 "쓰기 주체가 생길 때 만든다"며 2회 연속 보류 | §5.2에서 **쓰기 주체가 드디어 생겼는지** 판정한다(⚠ J-8) |

동시에 **직전 그룹이 만들어 놓은 자산**이 이 그룹의 전제를 바꿨다.

- `EmbeddingVector` 테이블에 챗봇별 **L2 정규화 문장 벡터**가 이미 쌓인다(FAQ 질문·대체질문·의도명·예문 4종, base64 float32, `modelId` 태깅).
- `judgeBand()`(`packages/dialogue-engine/src/semantic.ts`)가 **의미 유사도 3구간 판정**을 순수 함수 1곳으로 제공한다.
- 즉 **"두 문장이 의미가 같은가"를 수치로 판정할 도구가 이미 시스템 안에 있다.** 이번 그룹은 그 도구를 새로 만들 필요가 없고, **소비**하면 된다.

### 1.2 이번 그룹이 풀어야 하는 실제 문제 3가지

| # | 문제 | 현재 상태 | 누가 막혀 있는가 |
|---|---|---|---|
| ① | **예문이 1~2개뿐인 의도는 의미 매칭도 못 살린다** | 1단계 의미 유사도는 `질의 ↔ 등록 예문`의 **최대 코사인**이다. 등록 예문이 격식체 `"배송 조회 방법 안내"` 하나뿐이면 구어체 `"언제 와요?"` 와의 코사인이 `τ_accept`(0.80)에 못 미친다. 임베딩 모델이 좋아도 **비교 대상이 빈약하면 매칭은 실패**한다 | 신규 챗봇을 만드는 EDITOR(콜드스타트), 의도를 새로 추가한 직후의 운영자 |
| ② | **No.15는 키워드(엔티티)를 만들 수 없다** | 미응답 반영은 `Intent.examples`에 문장을 통째로 1건 추가하는 것이 전부다(FR-15-22). 그런데 대화 노드의 인풋 조건은 의도 **+ 키워드** 조합이다(`DialogNodeKeyword`, ADR-0005). 질문에 등장한 `"해외"`·`"반품"` 같은 **엔티티를 등록할 경로가 학습 루프에 없다** | 노드 조건에 키워드를 쓰는 EDITOR — 의도는 맞는데 키워드가 없어 계속 폴백을 본다 |
| ③ | **추천 의도가 문자 bigram 자카드다** | FR-15-16의 추천은 사전·모델 없이 문자 2-gram 자카드로 계산한다(J-5의 의도적 선택). 어휘가 겹치지 않는 패러프레이즈(`"물건 며칠 걸려요"` ↔ `"배송문의"`)에는 **거의 0점**이 나와 "추천할 의도가 없습니다"가 뜬다 | 미응답 큐를 매일 도는 EDITOR — 매번 의도명을 손으로 찾아 입력한다 |

### 1.3 목적

1. **의도별 예문 풀을 의미 보존 범위 안에서 자동 확장**하고, 편입 전에 **관리자가 반드시 확인**하게 한다(①, No.16).
2. 미응답 질문을 **낱개 요소로 분해**해 인텐트 신호 / 엔티티 후보 / 불용 요소로 나누고, 엔티티 후보를 **`Keyword` 등록 경로로 연결**한다(②, No.23).
3. 챗봇별 **경량 의도 분류기**를 재학습해 **추천 의도의 품질을 bigram 자카드 이상으로** 끌어올린다(③, No.23).
4. 위 셋을 **대화 경로(`packages/dialogue-engine`)를 건드리지 않고** 붙인다 — ADR-0008/0020/0021의 회귀 표면을 0으로 유지한다.
5. 자체 GPU 학습을 요구하지 않는 **1차 구현 경로**를 확보하고, GPU가 있을 때 성능이 올라가는 **교체 지점만** 남긴다.

### 1.4 이 문서의 핵심 판단 12건 (⚠ = PM 확인 필요)

| # | 쟁점 | 결정 | 근거 요약 |
|---|---|---|---|
| **J-1** | **No.16 DLE가 정확히 무엇을 만들어내는가** — (a) 데이터 증강 파이프라인 vs (b) 분류기·임베딩 파인튜닝 | **(a) 데이터 증강 파이프라인으로 확정한다.** 산출물은 **모델이 아니라 예문 데이터**이며, 최종 형태는 기존 `Intent.examples` 항목이다. **파인튜닝은 이번 범위에서 제외**한다 | 카탈로그 원문이 "문장·의도 **데이터**를 유사 의미로 증강학습"이다 — 산출물을 **데이터**라고 스스로 말한다. 산출물을 데이터로 두면 ① 기존 색인·임계값·매칭·감사 경로를 **그대로 재사용**하고 ② 모델 산출물 버전·롤백·배포라는 별도 설계가 이번 범위로 끌려 들어오지 않으며 ③ 자체 GPU 없이도 1차 구현이 성립한다. §4.1.1 |
| **J-2** | **증강이 1단계 임베딩 유사도(직전 그룹)와 중복인가** | **중복이 아니다. 단, 겹치는 부분이 있으므로 범위를 축소한다.** 임베딩이 푸는 것은 "**질의 쪽** 표현 다양성"이고, 증강이 푸는 것은 "**등록 쪽** 표현 빈약(콜드스타트)"이다. 다만 예문이 이미 충분한 의도(기본 10건 이상)에는 증강을 **권하지 않는다**(수확 체감 + 오염 위험) | 1단계 점수는 `max(질의, 예문ᵢ)` 코사인이다. 예문 집합이 한 표현군에 몰려 있으면 max가 구조적으로 낮게 형성되고, `τ_accept` 미달 → 되묻기 또는 2단계 이관이 된다. **임베딩 모델을 아무리 좋게 바꿔도 비교 대상이 1개면 해결되지 않는다.** 반대로 예문이 다양하면 같은 모델로 max가 올라간다 — 증강의 가치는 모델이 아니라 **데이터 분포**에 있다. §4.1.2 |
| **J-3** | **증강 문장을 무엇으로 만드는가** | **`AugmentationProvider` 포트 1개 + 구현체 3종.** 기본값은 **G1 규칙·사전 기반**(GPU 0, 의존성 0, 항상 동작), 선택 구현은 **G2 외부 LLM API**·**G3 로컬 생성모델**. 교체 지점은 **DI 바인딩 1곳**이다 | 프로젝트의 확립된 패턴(ADR-0007/0011/0016/0018/0024 — "인터페이스 1곳 + 구현 교체")의 여섯 번째 적용이다. **G1만으로도 기능이 성립해야** 개발·데모·CI가 외부 자원에 묶이지 않는다(`MockEmbeddingProvider`로 Python 없이 전 테스트가 통과하는 것과 같은 논리, ADR-0024 §3). ⚠ **G2/G3 사용 여부는 PM 확인 항목(P-1/P-2)** |
| **J-4** | **생성된 문장을 어떻게 걸러내는가** | **기존 임베딩으로 자기 검증한다.** ① **의미 보존 밴드**(원문과의 코사인 `0.75 ≤ s ≤ 0.97`) ② **신규성**(기존 예문 전체와의 max 코사인 `< 0.95`) ③ **타 의도 충돌**(다른 의도 예문과의 max 코사인 `≥ τ_accept`이면 경고) ④ **금지어 필터 통과** ⑤ **길이 1~200자**. 다섯을 모두 통과한 것만 **제안**되며, 제안이 곧 편입은 아니다 | 생성 모델은 반드시 쓰레기를 만든다. 검증 없이 편입하면 **오학습이 즉시 대화 품질을 떨어뜨린다**(ADR-0018이 자동 반영을 기각한 바로 그 이유 — 반영이 즉시이기 때문이다). 우리는 **의미 동일성을 수치로 판정할 도구를 이미 갖고 있다**(§1.1) — 안 쓸 이유가 없다. 상한 0.97은 "사실상 같은 문장"을 걸러 예문 상한 500을 낭비하지 않기 위함이다. §4.1.4 |
| **J-5** | **No.23의 "경량 분류기"는 정확히 무엇을 분류하는 모델인가** | **챗봇별 의도 분류기**다. 입력 = 문장 임베딩 벡터(이미 저장된 것), 출력 = `의도 id → 확률`. 구현은 **저장된 벡터 위의 선형 분류기**(다항 로지스틱 회귀). **엔티티 추출기는 학습 모델을 만들지 않고** 사전(gazetteer) 기반 스팬 탐지로 한다 | ① 학습 데이터가 이미 라벨링돼 있다 — `Intent.examples`의 (예문, 의도) 쌍이 곧 지도학습 데이터셋이다. ② 입력 벡터가 이미 DB에 있다(`EmbeddingVector`, base64 float32) — **재임베딩이 필요 없다**. ③ 클래스 수 수십~수백, 샘플 수 수백~수천 규모에서 선형 분류기는 CPU로 수 초에 학습된다 → 카탈로그 GPU 4("경량 ML(CPU 가능) — 소규모 분류/배치학습")의 정의와 정확히 일치한다. ④ 엔티티 NER은 **스팬 라벨 데이터가 0건**이라 애초에 학습이 불가능하다. §4.2.3 |
| **J-6** | ⚠ **분류기를 대화 매칭에 쓰는가** | **쓰지 않는다. 소비자는 "관리자 보조 라벨 제안" 1곳뿐이다**(미응답 큐의 추천 의도 — FR-15-15~19를 대체·보강). 대화 경로(`resolveTurn`)는 **한 줄도 바뀌지 않는다** | **매칭과 추천은 다른 문제다**(stats-learning J-5가 이미 확립한 원칙) — 매칭은 오탐 비용이 높고, 추천은 관리자가 거르므로 낮다. 분류기를 대화 경로에 넣으면 ADR-0020(점수 주입)·ADR-0021(3구간 임계값)·저하 모드·되묻기를 **전부 재설계**해야 하고, 그 회귀 표면은 이 그룹이 주는 가치보다 크다. 또한 1단계 의미 매칭은 사실상 **1-NN 분류기**라 선형 분류기와 기능이 겹친다 — 겹치는 쪽을 대화에서 떼고 **겹치지 않는 쪽(확률 캘리브레이션된 라벨 제안)** 만 쓴다. **재검토 트리거**: 골든셋에서 분류기 top-1이 1단계 kNN을 유의미하게(예: +5%p) 상회할 때. §4.2.4 |
| **J-7** | ⚠ **ADR-0024(ml-worker 추론 전용)를 뒤집는가** | **전면적으로 뒤집지 않는다. "한 줄 수정"을 제안한다.** ① **분류기 학습은 `apps/api` 안에서 CPU로 수행**한다(입력이 이미 DB의 float32 벡터이고, 선형 학습은 외부 의존성 0) ② ml-worker의 역할 정의만 "**임베딩 추론 서비스**" → "**ML 추론 서비스**"로 넓혀 **생성 추론(`POST /augment`)을 선택적으로** 수용한다 ③ **모델 파라미터를 갱신하는 파인튜닝은 여전히 도입하지 않는다** | ADR-0024의 재검토 트리거는 "No.16/23 착수 → 학습 기능 추가, Job Queue·`TrainingJob` 도입, GPU 5 복귀"였다. 그런데 **실제로 착수해 보니 셋 중 GPU 복귀는 근거가 없다** — 증강 생성은 추론이고(학습이 아니다), 분류기 학습은 CPU 수 초다. 트리거를 **기계적으로 전부 발동시키는 것이 아니라 항목별로 판정**하는 것이 옳다. §4.5에 3개 대안과 트레이드오프를 정리했다 — **최종 확정은 `system-architect`의 ADR 사안** |
| **J-8** | ⚠ **`TrainingJob` 테이블을 드디어 만드는가** | **만든다(조건부).** 증강 생성은 외부 LLM 사용 시 수 초~수 분이 걸리고 실패·부분성공·재시도가 존재하며, 관리자가 화면을 떠났다 돌아와도 결과를 봐야 한다 — **ADR-0004의 "쓰기 주체가 있는가" 기준을 통과한다.** 단 **Redis/BullMQ는 도입하지 않는다**(단일 인스턴스 in-process 큐 — `ReindexQueueService` 선례) | ADR-0018/0024가 두 번 보류한 이유는 "상태가 항상 `SUCCEEDED`인 가짜 Job 행만 쌓인다"였다. 이번에는 **`FAILED`·`PARTIAL`이 실제로 발생**하고 진행률이 실제로 변한다. 다만 **G1(규칙 기반)만 쓰는 구성에서는 생성이 동기 수백 ms**라 Job이 과하다 → **Job 적재 여부를 Provider 특성으로 분기**할지, 항상 Job으로 통일할지는 `system-architect` 판단(§5.2) |
| **J-9** | **ADR-0018의 인계 지점 `applyLearning()`을 교체하는가** | ⚠ **교체하지 않는다.** 이 그룹이 추가하는 학습 연산은 **대화 매칭 반영 경로에 있지 않다** — 증강은 "예문 편입 → 기존 즉시 반영"이고, 분류기는 "대화에 관여하지 않는 추천 제안기"다. 따라서 **`appliedImmediately`는 여전히 `true`가 사실**이며, `mode: 'QUEUED'` 분기는 **이번에도 켜지지 않는다** | ADR-0018 §2와 개발명세서 §6 결정 23이 "No.16/23 착수 시 이 1곳만 Job 큐 적재로 교체"라고 예고했으나, **실제 착수해 보니 그 전제(=학습이 대화 반영을 지연시킨다)가 성립하지 않는다.** 화면에 "학습 대기열에 추가되었습니다"를 띄우면 **거짓말이 된다** — 예문은 저장 즉시 매칭에 반영되기 때문이다. K-4(하드코딩 금지)가 이 판단을 가능하게 했다: 분기 코드는 이미 있고, 반환값이 계속 `true`일 뿐이다. **상위 문서 3곳의 예고를 정정 제안**한다(§10) |
| **J-10** | **요소분해에 형태소 분석기를 도입하는가** | ⚠ **1차는 도입하지 않는다.** 공백 토큰 + **기존 `Keyword`/`synonyms`/`HomonymDictionary` 최장일치**(gazetteer) + 조사 절단 휴리스틱으로 시작한다. 형태소 분석기(mecab-ko 등) 도입은 **PM 확인 항목(P-4)** | 형태소 분석기는 ① 네이티브 빌드·사전 파일 배포가 구축형 설치 절차를 무겁게 하고 ② 모노레포에 Python 프로세스를 하나 더 늘리거나 Node 바인딩 의존성을 추가하며 ③ **분해 결과의 소비자가 "관리자가 칩을 보고 고르는 화면" 1곳**이라 정밀도 요구가 높지 않다. 관리자가 칩 경계를 **직접 수정할 수 있게** 하면(FR-L2-8) 분석기 정밀도 부족이 치명적이지 않다. §4.2.2 |
| **J-11** | **전면 자동화하지 않는다는 요구를 어떻게 구조로 강제하는가** | **"제안"과 "자산"을 서로 다른 저장소에 둔다.** 증강 제안·분해 결과·엔티티 후보는 **제안 테이블**에만 존재하고, `Intent.examples`/`Keyword.synonyms`로 넘어가는 경로는 **관리자의 명시적 승인 액션 1곳**뿐이다. 자동 승격 코드 경로를 **만들지 않는다** | 카탈로그 원문이 "**관리자 확인 후** … 전면 자동 아님"이라고 명시했고, `기능요구사항.md` §5 교차검증 메모가 **"답변 못한 질문 자동학습" → "관리자 보조 재학습"으로 명칭까지 정정**한 항목이다. "자동으로 하지 않기로 한다"는 약속은 회귀에 약하다 — **할 수 없게** 만든다(ADR-0022의 allowlist 봉인과 같은 방식). 승인 없이 자산을 바꾸는 코드 경로가 0건임을 **정적 검사로 강제**한다(AC-L4-3) |
| **J-12** | ⚠ **GPU 없는 개발 환경에서 이 그룹이 성립하는가** | **성립한다.** G1 증강(규칙 기반) GPU 0 · 분류기 학습(선형, CPU) GPU 0 · 임베딩 검증은 **이미 돌고 있는 추론 경로 재사용**. **카탈로그의 No.16 GPU 6은 "자체 생성모델을 학습·서빙한다"는 전제의 값**이며 이번 1차 범위에는 해당하지 않는다 → **GPU 2~3으로 재산정 제안** | ADR-0024가 No.18을 5→4, No.30을 8→1로 재산정한 것과 **동일한 논리**다 — 카탈로그 값은 "그 기능을 최대로 구현했을 때"의 값이고, 실제 착수 범위가 좁으면 재산정하고 그 근거를 남긴다. **⚠ 자체 GPU 학습 인프라 보유 여부는 PM 확인 항목(P-2)** |

### 1.5 원본 근거 인용

**근거 1 — 카탈로그 No.16 원문**(`기능요구사항.md` §3):
> "딥러닝 학습엔진(DLE) | **최소 데이터로 문장·의도 데이터를 유사 의미로 증강학습** | GPU 6 | 사유: 딥러닝 배치학습, GPU 권장 | 구축형 ○ 구독형 △ | **구축형 핵심 차별점(엔진까지 사내 설치)**"

→ **J-1**(산출물은 데이터)·**J-2**("최소 데이터"= 콜드스타트가 표적임이 원문에 있다)·**J-3**(구독형 △는 외부 LLM 의존이 아니라 사내 엔진 전제에서 온 값)의 근거.

**근거 2 — 카탈로그 No.23 원문**(같은 문서):
> "답변 못한 질문 관리자 보조 재학습 | 미응답 질문을 **낱개 요소로 분리해 인텐트·엔티티 부여**, **관리자 확인 후** 경량 분류기 재학습(**전면 자동 아님**) | GPU 4 | 사유: **경량 분류기 재학습(소규모 배치)**"

→ **J-5**(경량·소규모 배치 = 선형 분류기)·**J-11**(전면 자동 금지가 요구사항 본문)의 근거.

**근거 3 — GPU 구간 정의**(`기능요구사항.md` §1):
> "| 3~4 | **경량 ML(CPU 가능)** — 소규모 분류/배치학습 | 의도 학습, FAQ 자동완성 | / | 5~6 | 중간 딥러닝(GPU 권장) — 임베딩/증강학습 | Text Embedding, **DLE 증강학습** |"

→ **No.23(GPU 4)은 기준표가 스스로 "CPU 가능"이라고 정의한 구간**이다. 반면 No.16(GPU 6)은 "GPU 권장"이므로, 자체 생성모델을 쓰지 않는 1차 범위에서는 재산정 대상이 된다(**J-12**).

**근거 4 — ADR-0018이 이 그룹에 넘긴 문장**:
> "경량 분류기(TF-IDF 등)를 이번에 도입 → **기각: No.23의 정의 그 자체**(GPU 4, 경량 배치). 선점하면 그 항목이 빈 껍데기가 되고, **모델 산출물 보관·버전·롤백이라는 별도 설계가 이번 범위로 끌려 들어온다**"

→ 그 "별도 설계"를 이제 이 그룹이 한다(§5.2). 다만 **증강(No.16)은 산출물이 데이터라 그 부담을 지지 않는다**(J-1)는 것이 이번의 핵심 설계 이득이다.

**근거 5 — ADR-0024가 남긴 재검토 트리거**:
> "**No.16(DLE 증강학습)·No.21(군집분석)·No.23(경량 재학습) 착수** → 학습 기능 추가, Job Queue·`TrainingJob` 도입, GPU 필요도 5 복귀."

→ **J-7**이 항목별로 재판정한다. 결론: 학습 기능은 `apps/api`에 추가(ml-worker 아님) · `TrainingJob`은 조건부 도입 · **GPU 5 복귀는 근거 없음**.

**근거 6 — 미응답 반영의 구조적 한계**(`stats-learning.md` FR-15-22 + ADR-0018 §5):
> "추가되는 예문은 기본적으로 `questionText`(마스킹된 원문)다." / "반영해도 답하지 못하는 경우를 화면이 먼저 알린다 — `linkedNodeCount`가 `0`이면 … 원본 매뉴얼 p.4가 오답 유형을 **'의도 미파악 / 키워드 미파악 / 둘 다'로 3분기**한 바로 그 함정"

→ **No.15는 3분기 중 "의도 미파악"만 다룬다.** "키워드 미파악"을 다룰 경로가 없다는 것이 §1.2 ②의 근거이며, No.23의 "엔티티 부여"가 정확히 그 빈칸이다.

## 2. 사용자 역할 및 시나리오

### 2.1 역할

`security-audit.md` §2.1의 역할 3종을 상속한다. **신규 권한 문자열을 만들지 않는다**(ADR-0015, stats-learning J-7과 동일 원칙 — 동작이 바꾸는 자원을 기준으로 정한다).

| 역할 | 이 그룹에서의 활동 | 권한 |
|---|---|---|
| **ADMIN** | EDITOR의 모든 활동 + 증강 Provider 설정(활성화·모델 선택) | `dialogue:write` + `chatbot:write` |
| **EDITOR** | 증강 요청·제안 검토·승인, 요소분해 확인·엔티티 등록, 분류기 재학습 실행(**이 그룹의 주 사용자**) | `dialogue:write` |
| **VIEWER** | 제안 목록·분해 결과·분류기 상태 **조회만**. 생성·승인·재학습 버튼이 **렌더되지 않는다** | `dialogue:read` |
| 최종 사용자 | **직접 사용하지 않는다.** 다만 이 사람의 미응답 발화가 (A)의 유일한 입력원이며, 승인된 증강 예문이 이 사람의 매칭 성공률을 올린다 | — |

### 2.2 사용자 시나리오

**S-1. 예문 1개짜리 의도를 살린다 (EDITOR · No.16)**
`환불규정문의` 의도에 예문이 `"환불 규정 안내"` 하나뿐이다. 편집자가 의도 상세에서 `예문 늘리기`를 누른다. 12초 뒤 제안 9건이 뜬다 — `"환불 어떻게 해요?"`(유사도 0.86) · `"돈 돌려받을 수 있나요"`(0.81) · `"반품하면 환불되나요"`(0.79, **⚠ `반품문의` 의도와 충돌 가능** 배지) 등. 편집자는 앞의 두 건에 체크하고 충돌 배지가 붙은 것은 건너뛴 뒤 `선택 2건 예문으로 추가`를 누른다. 토스트: **"반영 완료 — 다음 대화부터 적용됩니다."**

**S-2. 제안을 하나도 받지 않는다 (EDITOR · No.16)**
`배송문의` 의도에는 이미 예문이 34건 있다. `예문 늘리기`를 누르면 제안 12건 중 10건이 **"기존 예문과 거의 같음(신규성 미달)"** 으로 자동 제외되고 2건만 남는다. 화면은 **"이 의도는 예문이 충분합니다 — 증강 이득이 작습니다"** 안내를 함께 보여준다(J-2).

**S-3. 생성기가 헛소리를 했다 (EDITOR · No.16)**
외부 LLM이 `"환불 규정 안내"` 에서 `"오늘 날씨가 좋네요"` 를 만들었다. 의미 보존 검증에서 코사인 0.11 → **제안 목록에 아예 나타나지 않는다.** 화면 하단에 "생성 12건 중 검증 통과 7건(의미 이탈 3 · 중복 2)"이라는 요약만 보인다.

**S-4. 증강 제공자가 없다 (EDITOR · No.16)**
환경변수를 아무것도 설정하지 않은 환경이다. `예문 늘리기` 버튼을 눌러도 외부 호출 없이 **규칙 기반(G1)** 이 동작해 어미·조사·동의어 치환 제안 5건을 만든다. 품질은 LLM보다 낮지만 **기능이 멈추지 않는다**(FR-0-46 상속).

**S-5. 미응답 질문을 요소로 뜯어본다 (EDITOR · No.23)**
`통계 > 학습현황`에서 `"해외로 반품 보낼 수 있나요"`(7회) 행을 연다. 새로 생긴 `요소 분해` 패널에 칩 4개가 보인다 — `[해외]`(엔티티 후보·기존 키워드 `국가` 와 일치) · `[반품]`(엔티티 후보·**미등록**) · `[보낼 수 있나요]`(의도 신호) · `[로]`(불용). 편집자가 `[반품]` 칩에서 `새 키워드로 등록`을 고르고, `[해외]` 는 기존 `국가` 키워드의 동의어로 추가한다.

**S-6. 칩 경계가 틀렸다 (EDITOR · No.23)**
`"해외배송비"` 가 통째로 한 칩이다. 편집자가 칩을 클릭해 **분리 지점을 직접 지정**한다 → `[해외배송]` `[비]`. 시스템은 편집자의 수정을 그대로 받아들인다(형태소 분석기 정밀도에 의존하지 않는다 — J-10).

**S-7. 추천 의도가 똑똑해졌다 (EDITOR · No.23)**
`"물건 며칠이나 걸리죠"` 에 대해 기존 bigram 추천은 **후보 0건**이었다. 분류기를 재학습한 뒤 같은 행을 열면 **`배송문의` 87% · `주문조회` 6%** 가 뜬다. 각 후보 옆에 **`분류기`** 출처 배지가 붙어, 이 값이 문자 유사도가 아니라 학습된 모델에서 나왔음을 알 수 있다.

**S-8. 분류기를 학습할 수 없다 (EDITOR · No.23)**
갓 만든 챗봇은 의도가 1개이고 예문이 2건뿐이다. `분류기 재학습`을 누르면 **"학습에 필요한 최소 데이터가 부족합니다(의도 2개 이상 · 의도당 예문 3건 이상 · 총 20건 이상)"** 안내가 뜨고, 추천은 **기존 bigram 방식으로 계속 동작**한다(기능 정지 없음).

**S-9. 모델이 낡았다 (EDITOR · No.23)**
지난주 학습 이후 예문이 180건 추가됐다. 학습현황 화면에 **`분류기 낡음 — 재학습 권장(학습 후 예문 +180건)`** 배지가 뜬다. 추천은 계속 나오되 각 후보에 `학습 시점: 7일 전` 이 병기된다.

**S-10. 임베딩 모델이 바뀌었다 (ADMIN · No.23)**
`modelId`가 바뀌어 기존 벡터가 무효가 됐다(AC-N1-11). 분류기는 **옛 모델 벡터로 학습된 것**이므로 즉시 **사용 중지**되고 추천이 bigram으로 자동 복귀한다. 배지: `분류기 사용 불가 — 임베딩 모델 변경(재색인 후 재학습 필요)`.

**S-11. 승인하지 않은 것은 반영되지 않는다 (EDITOR · 공통)**
편집자가 제안 20건을 받아 놓고 화면을 떠났다. 다음 날 다시 오니 제안이 그대로 `미검토` 상태로 남아 있고, **대화 동작은 전날과 완전히 동일**하다. 제안은 `Intent.examples`에 들어가지 않았다(J-11).

**S-12. 증강이 만든 예문임을 나중에도 안다 (EDITOR)**
`배송문의` 의도의 예문 목록에서 어떤 문장이 사람이 쓴 것이고 어떤 것이 증강 승인분인지 구분이 안 된다. 이력관리(No.13)에서 `예문 추가` 감사 레코드의 `summary`가 **"증강 예문 반영 (2건)"** 으로 남아 있어 경위를 추적할 수 있다.

**S-13. 외부로 문장이 나가는 것을 막는다 (ADMIN)**
구축형 고객사다. 관리자가 증강 설정 화면에서 Provider를 **`규칙 기반`** 으로 고정한다. 이후 증강 요청에서 **외부로 나가는 HTTP가 0건**임이 보장된다(AC-L1-14).

**S-14. 접근성 (EDITOR)**
제안 목록은 표이며 각 행이 체크박스 + 문장 + 유사도 + 충돌 배지로 구성된다. 유사도는 색상만이 아니라 **수치와 텍스트 라벨**을 병기한다. 요소분해 칩은 **키보드만으로 순회·역할 변경**이 가능하다.

## 4. 기능별 요구사항

### 4.1 No.16 — 예문 증강(DLE)

#### 4.1.1 범위 확정 — J-1 결정

**결정: No.16의 1차 범위는 "의미 보존 문장 증강 파이프라인"이며, 산출물은 모델이 아니라 `Intent.examples`에 편입될 후보 문장이다. 임베딩 모델·분류기의 파인튜닝은 이번 범위에서 제외한다.**

후보 2안 비교:

| 안 | 산출물 | 이번 판정 | 근거 |
|---|---|---|---|
| **(a) 데이터 증강 파이프라인** | **예문 문장**(기존 `Intent.examples`) | **채택** | 카탈로그 원문이 "문장·의도 **데이터**를 증강"이라고 적었다. 산출물이 기존 자산이므로 색인(FR-N1-18)·매칭·감사·권한·롤백(예문 삭제)이 **전부 이미 존재**한다. 새로 설계할 것이 **제안 저장소 1개**뿐이다 |
| **(b) 임베딩/분류기 파인튜닝** | **모델 가중치 파일** | **제외(Out of scope, §9)** | ① `modelId` 규약이 **전역 1개**를 전제한다(ADR-0024 §4) — 챗봇별 파인튜닝은 이 규약을 깨고 **임계값 기본값 매핑**(ADR-0021)까지 챗봇별로 갈라놓는다 ② 챗봇당 수백~수천 문장으로 문장 인코더를 파인튜닝하면 **과적합**이 지배적이다 ③ 모델 산출물 보관·버전·롤백·배포 설계가 통째로 필요하다(ADR-0018이 우려한 바로 그 부담) ④ 실제 GPU가 필요해진다(J-12) |

> ⚠ **PM 확인(P-3)**: 카탈로그의 "**구축형 핵심 차별점(엔진까지 사내 설치)**" 라는 세일즈 문구는 **(b)를 암시**한다. (a)만 구현하면 "우리 엔진을 고객 데이터로 학습시킨다"는 주장은 **하지 못한다**(대신 "고객 데이터로 예문을 자동 확장한다"는 주장은 가능하다). 세일즈 메시지와의 정합성을 PM이 확인해야 한다. 기술적으로는 (a) → (b)가 **선행 관계**다 — (a)가 만든 데이터가 (b)의 학습 데이터가 되므로 순서상 손해가 없다.

#### 4.1.2 임베딩 유사도와의 관계 — J-2 결정 (중복 여부 판정)

**결정: 중복이 아니다. 단 "예문이 이미 충분한 의도"에는 증강을 권하지 않는 것으로 범위를 좁힌다.**

| 축 | 1단계 의미 유사도(직전 그룹, 구현 완료) | No.16 증강(이번) |
|---|---|---|
| 푸는 문제 | **질의 쪽** 표현이 예문과 달라도 찾는다 | **등록 쪽** 표현이 빈약해서 못 찾는 것을 메운다 |
| 작동 시점 | 매 턴(추론) | 관리자 편집 시점(오프라인) |
| 바꾸는 것 | 점수 계산 방식 | **비교 대상 집합** |
| 한계 | 예문이 1건이면 `max` 자체가 낮다 | 생성 품질에 의존한다 |

**왜 임베딩만으로 부족한가(수치 예시)** — 1단계 점수는 `s = max_i cos(q, eᵢ)` 다.

- 예문이 `{"배송 조회 방법 안내"}` 1건일 때 `q = "물건 언제 와요?"` → `s ≈ 0.62` → `τ_low(0.60) ≤ s < τ_accept(0.80)` = **모호 구간 → 되묻기**.
- 예문이 `{"배송 조회 방법 안내", "언제 와요?", "물건 며칠 걸려요", "배송 얼마나 걸리나요"}` 로 늘면 같은 `q`에 대해 `s ≈ 0.93` → **확정**.
- **모델은 그대로다.** 바뀐 것은 데이터뿐이다.

| ID | 요구사항 |
|---|---|
| FR-L1-1 | 증강의 목적은 **`Intent.examples`의 표현 다양성 확대**다. FAQ 질문·대체질문(`FaqEntry`)은 **1차 범위에서 제외**한다(§9) — 경로가 둘이 되면 승인 화면·감사·상한 규칙이 두 벌이 된다. |
| FR-L1-2 | 대상 의도의 현재 예문 수가 **충분 임계(기본 10건)** 이상이면 화면이 **"증강 이득이 작습니다"** 를 안내한다. 요청 자체는 막지 않는다(관리자 판단 존중). |
| FR-L1-3 | 증강은 **의도 단위 요청**이다. 챗봇 전체 일괄 증강은 1차 범위 밖이다(§9) — 수백 개 제안을 한 화면에서 검토하는 것은 **승인 절차를 형식화**시킨다(J-11의 취지를 무너뜨린다). |
| FR-L1-4 | 1회 요청의 **제안 상한은 기본 20건**이며, 생성 요청 수는 상한의 최대 3배까지 시도할 수 있다(검증 탈락을 감안). 예문 상한 500(기존 규약)을 넘길 수 있는 요청은 **생성 전에 거부**한다. |

#### 4.1.3 증강 생성기 — J-3 결정

**결정: `AugmentationProvider` 포트 1개 + 구현체 3종. 기본값은 G1(규칙·사전 기반)이며 교체 지점은 DI 바인딩 1곳이다.**

```ts
// 계약 개요(최종 형태는 system-architect 확정)
interface AugmentationProvider {
  readonly providerId: string;              // 감사·제안 레코드에 기록된다
  readonly requiresNetwork: boolean;        // true면 PII 마스킹·금지어·타임아웃 경로가 강제된다
  generate(input: {
    seeds: readonly string[];               // 기존 예문 + 의도명
    targetCount: number;
    locale: 'ko';
  }): Promise<readonly string[]>;           // 검증 전 원시 후보. 실패 시 빈 배열(예외 전파 금지)
  healthy(): Promise<boolean>;
}
```

| 구현체 | 방식 | GPU | 외부 호출 | 구축형 | 판정 |
|---|---|:---:|:---:|:---:|---|
| **G1 `RuleBasedAugmentationProvider`**(기본값) | 어미·종결형 변형(`~인가요/~되나요/~돼요?`), 조사 교체, **기존 `Keyword.synonyms`·`HomonymDictionary` 동의어 치환**, 띄어쓰기 변형, 어순 교체, 경어/구어 변환 | **0** | **없음** | ○ | **1차 필수 구현.** 한국어 교착어 특성상 어미·조사 변형만으로도 표현 다양성이 실질적으로 늘고, **사내 사전을 재활용**하므로 도메인 적합도가 높다 |

#### 4.1.4 자기 검증 — J-4 결정 (⚠ 이 기능의 안전장치)

**결정: 생성 문장은 이미 운영 중인 임베딩 추론 경로로 스스로 검증한다. 신규 추론 인프라를 만들지 않는다.**

| 검사 | 규칙 | 기본값 | 실패 시 |
|---|---|---|---|
| ① **의미 보존** | `τ_keep_low ≤ cos(후보, 시드) ≤ τ_keep_high` | `0.75` / `0.97` | **제외**(사유 `SEMANTIC_DRIFT` / `NEAR_DUPLICATE`) |
| ② **신규성** | `max cos(후보, 기존 예문 전체) < τ_novel` | `0.95` | **제외**(사유 `DUPLICATE_OF_EXISTING`) |
| ③ **타 의도 충돌** | `max cos(후보, 같은 챗봇의 다른 의도 예문) ≥ τ_accept` | 챗봇 설정값 | **경고 표시**(제외하지 않음) |
| ④ **금지어** | `BannedWord` 필터 통과 | — | **제외**(사유 `BANNED_WORD`) |
| ⑤ **형식** | 길이 1~200자, 정규화 후 비어있지 않음, 제어문자 없음 | — | **제외**(사유 `INVALID_FORMAT`) |
| ⑥ **자기 중복** | 같은 요청 내 후보 간 정규화 동일·`cos ≥ 0.97` | — | **1건만 유지** |

|---|---|
| FR-L1-10 | 검증에 쓰는 임베딩은 **기존 `EmbeddingProvider` 포트**를 통한다. 후보 N건을 **배치 1회**로 임베딩하며 후보당 개별 호출을 하지 않는다(NFR-P7 상속). |
| FR-L1-11 | 기존 예문·타 의도 예문의 벡터는 **이미 저장된 `EmbeddingVector`를 읽어 쓴다.** 재임베딩하지 않는다(FR-N1-19의 `textHash` 규약 재사용). |
| FR-L1-12 | **임베딩 서비스가 없거나 `modelId`가 stale이면 의미 검증(①②③)을 수행할 수 없다.** 이때는 **증강을 거부**하고 `503 AUGMENTATION_UNAVAILABLE` + "검증 없이 예문을 늘리지 않습니다"를 안내한다. ⚠ 근거: 검증 없는 증강은 **오학습을 즉시 대화에 주입**하며, 이는 이 기능이 주는 이득보다 위험이 크다. ### 4.2 No.23 — 미응답 요소분해 + 경량 분류기

#### 4.2.1 No.15와의 경계 — 무엇이 새로운가

| 축 | **No.15**(구현 완료) | **No.23**(이번) |
|---|---|---|
| 입력 단위 | 미응답 문장 **통째로 1건** | 문장 **안의 스팬(요소)** |
| 라벨 부여 | 관리자가 **의도명 1개**를 입력 | 스팬별 **역할(의도신호/엔티티후보/불용)** + 대상 지정 |
| 만들어지는 자산 | `Intent.examples` 1건 | `Intent.examples` + **`Keyword.name`/`synonyms`** |
| 추천 근거 | **문자 bigram 자카드**(FR-15-16) | **학습된 의도 분류기 확률**(폴백: bigram) |
| 학습 연산 | **없음**(ADR-0018) | **있음** — 선형 분류기 재학습 |
| 대화 반영 | 저장 즉시(규칙/의미 매칭) | 예문·키워드는 **동일하게 즉시**. 분류기는 **대화에 반영되지 않는다**(J-6) |

> **핵심**: No.23은 No.15를 대체하지 않고 **같은 화면·같은 큐 위에 두 개의 층을 덧붙인다** — (A) 요소분해 층, (B) 추천 품질 층. No.15의 기존 워크플로우(검토 → 의도명 → 반영)는 **그대로 남아 있고 계속 동작한다.**

#### 4.2.2 요소분해 — J-10 결정

**결정: 형태소 분석기를 도입하지 않고, 공백 토큰 + 기존 사전 최장일치 + 조사 절단 휴리스틱으로 시작한다. 관리자가 결과를 직접 수정할 수 있게 하여 정밀도 부족을 흡수한다.**

| ID | 요구사항 |
|---|---|
| FR-L2-1 | 분해 대상은 `UnansweredQuestion.questionText`(**이미 PII·금지어 마스킹된 값** — ADR-0013/0019)다. 원문에 다시 접근하지 않는다. |
| FR-L2-2 | **분해 알고리즘(기본)**: ① 정규화(`normalizeText`) ② 같은 챗봇의 `Keyword.name` + `synonyms` + `HomonymDictionary.word` 로 **최장일치 스팬 추출**(gazetteer) ③ 남은 구간을 공백으로 분할 ④ 각 토큰에서 **조사·어미 접미 절단**(`은/는/이/가/을/를/에/에서/으로/와/과/도/만/까지/부터/의/라도/이나`) ⑤ 불용어 사전(기본 제공, 챗봇별 편집 불가) 적용. |
| FR-L2-3 | **역할 자동 부여 3종**: `ENTITY_CANDIDATE`(gazetteer 일치 또는 명사성 추정 토큰) · `INTENT_SIGNAL`(서술·종결 표현을 포함한 잔여 구간) · `IGNORED`(불용어·1자 조사·숫자 단독). 자동 부여는 **초기값일 뿐**이며 관리자가 바꾼다. |
| FR-L2-4 | 분해 결과는 **저장하지 않고 조회 시점에 계산**한다. 근거: 키워드 사전이 바뀌면 분해 결과가 즉시 달라져야 하며, 저장하면 낡는다(FR-15-16의 추천 비저장 판단과 동일 — ADR-0019). **단 관리자가 수정한 결과는 승인 처리 요청 본문에 실려 오므로 별도 저장이 필요 없다.** |

| FR-L2-6 | `GET /chatbots/:chatbotId/unanswered-questions/:id/decomposition` — 분해 결과 조회. 권한 `dialogue:read`. 응답: `{ spans: [{ start, end, text, role, matchedKeyword?: {id,name,viaSynonym} }], version }`. |
| FR-L2-7 | **엔티티 승인 2경로**: ① 기존 키워드에 **동의어 추가**(`matchedKeyword`가 있거나 관리자가 대상 선택) ② **신규 키워드 생성**(이름 = 스팬 텍스트, 관리자가 수정 가능). 둘 다 `KeywordsService`의 기존 경로를 재사용하며 동의어 상한 200·정규화 유일성 규약을 그대로 따른다(FR-0-51). |

| FR-L2-13 | **기존 `POST .../resolve`(No.15)는 그대로 유지**한다. 요소분해는 **선택 경로**이며, 빠르게 처리하려는 관리자는 기존 단순 반영을 계속 쓸 수 있다. |

#### 4.2.3 경량 의도 분류기 — J-5 결정

**결정: 저장된 문장 임베딩 위의 다항 로지스틱 회귀(선형 분류기). 학습 데이터는 `(Intent.examples 벡터, intentId)` 쌍이며, 학습은 `apps/api` 안에서 CPU로 수행한다.**

| ID | 요구사항 |
|---|---|
| FR-L2-14 | **학습 입력은 이미 저장된 `EmbeddingVector`**(`ownerType`이 `INTENT_EXAMPLE` 또는 `INTENT_NAME`, `status = READY`, 현재 `modelId`)다. **재임베딩을 수행하지 않는다** — 학습 비용의 대부분이 여기서 사라진다. |
| FR-L2-15 | **학습 최소 조건**: 의도 **2개 이상** · 의도당 예문 벡터 **3건 이상**(미달 의도는 학습에서 제외) · 총 샘플 **20건 이상**. 미달 시 `422 CLASSIFIER_INSUFFICIENT_DATA`이며 **추천은 bigram 방식으로 계속 동작**한다(S-8). |
| FR-L2-16 | **알고리즘은 다항 로지스틱 회귀**(softmax) 기본. L2 정규화된 입력에 L2 페널티 + 클래스 불균형 보정(클래스별 가중치). 외부 ML 라이브러리 의존성을 **추가하지 않는다**(수치 연산만으로 구현 가능한 범위). |

| FR-L2-18 | 학습 산출물은 **가중치 행렬 + 절편 + 클래스(의도 id) 목록 + `modelId` + 학습 시점 샘플 수**이며, 벡터와 **같은 직렬화 규약**(base64 Float32Array)으로 저장한다(DD-70 재사용). |
| FR-L2-19 | **산출물 크기 상한 기본 8MB.** 초과 시 학습을 중단하고 `422`를 반환한다(의도 수 × 차원이 비정상적으로 큰 경우의 방어). |

### 4.5 `apps/ml-worker`의 역할 — J-7 결정 (⚠ ADR-0024 충돌 검토)

**ADR-0024가 명시한 것**: "학습·파인튜닝은 포함하지 않는다" · "`TrainingJob`·Redis·BullMQ는 계속 도입하지 않는다" · 재검토 트리거 = "No.16/23 착수 → 학습 기능 추가, Job Queue·`TrainingJob` 도입, **GPU 필요도 5 복귀**".

**이번 그룹은 실제로 학습(분류기)과 생성(증강)을 요구하므로 이 결정을 재검토해야 한다.** 세 가지 대안을 정리하되, **최종 확정은 `system-architect`의 ADR 사안**이다.

| 안 | 내용 | 장점 | 단점 | 요구사항 단계 권고 |
|---|---|---|---|---|
| **A. 전면 확장** | ml-worker에 학습 엔드포인트 신설(`POST /train/*`) + Redis/BullMQ + `TrainingJob` 도입, GPU 5 복귀 | ADR-0024의 트리거를 문자 그대로 따름. 장래 파인튜닝까지 한 번에 수용 | ① **Redis가 새 인프라 의존으로 들어온다**(구축형 설치 절차 증가) ② 분류기 학습 입력이 **`apps/api`의 DB에 있는데 학습을 다른 프로세스로 보내면 벡터를 HTTP로 왕복**시켜야 한다(수 MB) ③ GPU 5 복귀는 **실제 연산 성격과 맞지 않는다**(선형 학습은 CPU 수 초) | **비권장** — 실제 필요보다 과하다 |
| **B. 분리 배치(권고)** | **분류기 학습은 `apps/api` 안 CPU 연산** + **in-process 큐** + **`TrainingJob`만 도입**(Redis 없음). ml-worker는 추론 전용 유지, 역할 정의만 "임베딩" → "ML 추론"으로 확대해 **선택적 `POST /augment`** 수용 | ① ADR-0024의 핵심 주장(**추론 전용 · Redis 미도입 · 모델 파인튜닝 없음**)이 **전부 유지**된다 ② 학습 입력이 이미 있는 프로세스에서 학습한다(데이터 이동 0) ③ 외부 의존성 추가 0 ④ GPU 없이 성립 | ① Node에서 수치 학습을 직접 구현해야 한다(코드량 증가, 다만 선형 모델이라 소규모) ② 다중 인스턴스 전환 시 학습 큐 재설계 필요(교체 지점 1곳으로 국한) | **권고** |
| **C. 오프라인 배치** | 증강·학습을 CLI 스크립트로만 제공하고, 결과를 엑셀 대량 업로드(No.6)로 인입 | 런타임 코드 표면 최소 | ① **관리자 확인 워크플로우가 화면에 없다** — No.23의 "관리자 확인 후"가 요구사항 본문인데 이를 충족하지 못한다 ② 운영자가 서버 셸에 접근해야 한다 | **기각** |

| ID | 요구사항 |
|---|---|
| FR-L2-35 | **모델 파라미터를 갱신하는 파인튜닝은 이번 범위에 포함하지 않는다.** ADR-0024의 이 주장은 유지된다. |

### 4.6 GPU 필요도 재산정 — J-12

| No | 카탈로그 | 재산정 제안 | 근거 |
|---|:---:|:---:|---|
| **16** | 6 | **2**(G1 기본 구성) / **3**(G2 외부 LLM 구성) / **6 유지**(G3 자체 생성모델 구성) | 구간 정의상 1~2 = "CPU 전용 — 규칙매칭", 3~4 = "경량 ML(CPU 가능)". G1은 **규칙·사전 치환**이므로 1~2이고, 검증에 쓰는 임베딩은 **이미 돌고 있는 추론 경로의 재사용**이라 신규 부하가 아니다. G2는 자체 GPU 0(외부 위임 — No.30을 8→1로 재산정한 것과 동일 논리). **G3를 실제로 채택하면 카탈로그 값 6이 그대로 옳다** |
| **23** | 4 | **3** | 학습 입력이 **이미 계산된 벡터**라 재임베딩이 없고, 선형 분류기 학습은 5,000샘플 기준 CPU 수 초다. 기준표의 3~4 구간("경량 ML(CPU 가능) — 소규모 분류/배치학습") 안에서 **하단**에 해당한다 |
| 그룹 종합 | — | **3** | 최댓값 기준(G2 구성 가정) |

> ⚠ **PM 확인(P-2)**: 위 재산정은 **G3(자체 생성모델)를 쓰지 않는다는 전제**다. "엔진까지 사내 설치"라는 구축형 세일즈 포인트를 위해 G3가 필요하다면 GPU 6이 유지되며, **실제 GPU 장비 확보가 개발 착수의 선행 조건**이 된다.

## 7. 수용기준 (AC)

### AC-L1. 예문 증강(No.16)

- **AC-L1-1** Given 예문 1건짜리 의도, When 증강을 요청하면, Then 검증을 통과한 제안이 1건 이상 생성되고 **`Intent.examples`는 변하지 않았다**.
- **AC-L1-2** Given 생성기가 의미가 전혀 다른 문장을 반환(코사인 0.11), When 제안 목록을 조회하면, Then **그 문장이 목록에 없고** 검증 요약의 `SEMANTIC_DRIFT`가 1 증가했다.
- **AC-L1-3** Given 생성기가 기존 예문과 사실상 동일한 문장을 반환(코사인 0.99), When 확인하면, Then **`DUPLICATE_OF_EXISTING`으로 제외**됐다.
- **AC-L1-4** Given 다른 의도의 예문과 코사인이 `τ_accept` 이상인 제안, When 목록을 보면, Then **충돌 배지가 표시**되고 **기본 선택 상태가 아니다**(제외되지는 않는다).
- **AC-L1-5** Given 제안 5건 중 2건 선택, When 승인하면, Then **정확히 2건만** 예문에 추가되고 나머지 3건은 `PENDING`으로 남는다.
- **AC-L1-6** Given 승인 요청 1건(제안 2건), When `DialogueBundleService.invalidate()` 호출을 계측하면, Then **정확히 1회**다(K-2).
- **AC-L1-7** Given 승인 성공, When 응답을 보면, Then `appliedImmediately`가 **`true`** 이고 화면 문구가 "반영 완료 — 다음 대화부터 적용됩니다"다(J-9 — `QUEUED` 분기가 켜지지 않음을 고정).
- **AC-L1-8** Given 승인으로 예문이 늘어난 직후, When 시드와 표현이 다른 문장으로 대화하면, Then **매칭 점수가 승인 전보다 높다**(증강의 존재 이유를 증명하는 테스트 — J-2).
