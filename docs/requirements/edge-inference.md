> **이 그룹 종합 GPU 필요도: 4(카탈로그 유지 권고)** — 이 기능의 대상 장비는 "GPU가 없거나 작은(4~8GB) 고객사 서버"다. 대화 경로의 모델(임베딩)은 이미 CPU로 예산 안에서 돌고, 생성모델은 관리자 배치 작업(예문 늘리기)에만 쓰인다.

## 0. 쉬운 말 요약 — 왜 필요한가, 무엇이 달라지나, 안 해도 되는 경우

### 0.1 한 줄 요약

**"'엣지 추론'은 이 제품에서는 '인터넷이나 큰 GPU 없이도 고객사 서버 한 대에서 AI가 다 돈다'는 뜻으로 보는 것이 맞고, 그 대부분은 이미 된다."** 새로 할 일은 ① 운영 GPU 서버(vLLM)에 붙는 연결 1개, ② 작은 GPU용 구성(Ollama)을 "정식 경량 구성"으로 인정할지와 그 한계 처리, ③ "이 장비면 무엇이 된다"는 설치 안내표 한 장이다. 사용자의 휴대폰·브라우저 안에서 AI를 돌리는 것은 이번에 하지 않는다.

### 0.5 이 기능 없이 충분한 경우 (정직하게)

- **구축형 고객 대부분이 GPU 없는 서버를 쓰고, 예문 늘리기는 규칙 기반으로 만족하는 경우** — 지금 기본값 그대로가 이미 "엣지에서 모든 추론이 도는" 상태다. 할 일은 카탈로그 비고에 그 사실을 적는 것뿐이다(규모 (0)).
- **운영 vLLM 서버가 아직 준비되지 않았고 준비 시점도 모르는 경우** — vLLM 백엔드를 먼저 만들어도 실제로 붙여 볼 곳이 없다(CI의 가짜 서버로만 확인). No.17처럼 대기가 된다.
- **"휴대폰·브라우저 안에서 AI가 돈다"를 기대하는 경우** — 이 문서의 권고 범위(A)는 그것을 하지 않는다. 기대가 다르면 만들어도 실망이 크다(§1.3).

→ 그래서 §11 Q2에 **"지금은 하지 않음(카탈로그 비고만 정리)"** 선택지를 둔다. 반대로 **운영 vLLM 서버 연결이 곧 필요하거나, 작은 GPU를 가진 구축형 고객에게 "사내 AI 예문 늘리기"를 제공해야 한다면** 규모 A의 가치가 분명하다.

### 1.5 "지연시간·유출 최소화"에 대해 정직하게

- **지연시간**: 최종 사용자가 느끼는 응답 지연은 ① 임베딩(이미 사내·예산 안) ② 외부 RAG 생성형 답변(No.30 — **외부 RAG 서버의 vLLM이 결정**, 우리 코드 밖)으로 정해진다. 이 기능(규모 A)은 **둘 다 바꾸지 않는다.** 생성형 답변 지연을 줄이는 일은 외부 RAG 쪽 과제다(§9).
- **유출**: 기본 구성(`rule`)은 이미 외부 전송 0이다. 규모 A는 "사내 생성모델을 쓸 때도 유출 0"을 **ml-worker → 생성 백엔드 구간까지** 넓혀 보장하는 것이 실질 기여다.

### 1.6 No.16·17과의 경계

| 항목 | No.16(완료) | No.17(대기 — L40S 담당자 없음) | **No.37(이 문서)** |
|---|---|---|---|
| 예문 늘리기 기능·검증 5종·승인 흐름 | ✅ 소유 | 재사용 | 재사용(변경 0) |
| 운영 생성모델 **실측·채택 판정** | — | ✅ 소유(합격 기준 P-4) | **하지 않음** — 판정은 No.17 |
| 생성 **백엔드 연결**(transformers · ollama · **vllm**) | transformers | Ollama(개발 검증으로 추가) | ✅ **vLLM 추가 · 3종 설정 정리** |
| 개발용 소형 모델 경로 | — | FR-NG2(흐름 확인) | ✅ **"경량 설치 구성"으로 지위 정리** |
| 장비 등급별 설치 안내 | — | — | ✅ 소유 |

> vLLM 백엔드가 생기면 **No.17 실측도 L40S의 vLLM 서버를 통해 할 수 있게 된다**(지금은 `transformers` 경로 전제 — `nlg-bot-to-bot.md` FR-NG1-3). 다만 L40S 접근 담당자가 없는 대기 상태는 이 문서로 풀리지 않는다.

### 1.7 목적

1. "엣지"의 뜻을 이 제품 기준으로 **하나로 정한다**(E1).
2. 운영 vLLM · 경량 Ollama · 기존 transformers를 **설정만으로** 고르게 하고, `/augment` 계약·API 코드를 바꾸지 않는다.
3. 소형 장비의 구조적 한계(60건 요청)를 **조용한 품질 붕괴 없이** 다룬다.
4. 장비 등급별 "동작 확인" 결과와 "품질 미판정" 경계를 설치 문서에 남긴다.
5. 대화 경로·위젯·엔진·권한·화면을 **바꾸지 않는다.**

### 2.1 역할

| **서버 운영자** | 생성 백엔드 선택(`transformers`/`ollama`/`vllm`) · 주소·모델 ID 설정 · 상태 확인 |
| **ML 담당(ml-engineer)** | vLLM 백엔드 구현 · 경량 구성 상한 기본값 제안 · 등급별 "동작 확인" 기록 |
| **챗봇 편집자** | 변화 없음 — 예문 늘리기 화면에서 "현재 생성기" 표시만 본다 |
| **최종 사용자** | 변화 없음 |

### 2.2 사용자 시나리오

**S-1 (GPU 없는 고객 서버)**: 설치 담당이 등급표 "등급 0"을 따른다 → 임베딩은 CPU, 증강은 규칙 기반(G1), 생성 백엔드 설정 안 함 → 대화·의미 매칭·예문 늘리기(기본 방식)가 모두 돈다. **이것은 지금도 그대로 된다**(이 기능은 문서로 확인만 준다).

**S-2 (소형 GPU 고객 서버 — 경량 구성)**: 설치 담당이 같은 서버에 Ollama를 설치하고 모델을 미리 받아 둔다 → ml-worker 생성 프로세스를 `GENERATION_BACKEND=ollama`로 별도 포트에 띄우고 API에 `AUGMENTATION_PROVIDER=local` 설정 → 편집자가 "예문 늘리기"를 누르면 경량 모델이 **상한(권고 20건)까지만** 후보를 만들고 기존 검증 5종을 통과한 것만 제안으로 뜬다 → 화면의 생성기 표시는 "사내 경량 모델 — 품질 미보증".

**S-3 (운영 L40S — vLLM)**: 운영자가 vLLM 서버 주소·모델 ID를 ml-worker 생성 프로세스에 설정(`GENERATION_BACKEND=vllm`) → 기동 시 vLLM 서버 연결과 모델 존재를 확인하고, 없으면 **기동 실패**(가짜 생성기로 조용히 바뀌지 않음) → API는 기존 `local` Provider로 그대로 부른다. 이 모델을 **운영에 켜도 되는지**는 No.17 실측·합격 판정이 정한다.

**S-4 (폐쇄망 설치)**: 설치 담당이 인터넷 되는 PC에서 Ollama/vLLM 모델 파일을 받아 매체로 반입 → 문서화된 경로에 두고 기동 → 기동 중 외부 내려받기 시도 0.

**S-5 (시연 — 3050 노트북)**: 개발자가 S-2 구성을 노트북에서 돌려 "요청 → 생성 → 검증 → 제안"이 끝까지 도는 것을 보여 준다. 시연 자료·화면에는 "동작 확인용 — 품질 판단 근거 아님"이 붙는다.

**S-6 (장애)**: 생성 백엔드(Ollama/vLLM)가 요청 중 죽거나 느리면 → ml-worker는 빈 후보를 돌려주고 API는 G1로 폴백, "고급 증강을 사용할 수 없어 기본 방식으로 생성했습니다" 표시(현행 ADR-0026 §2). 대화에는 영향이 없다(생성 프로세스는 임베딩과 별도 — 권고 구성).

| FR-ED3-1 | `GENERATION_BACKEND=vllm`이면 ml-worker는 **외부 vLLM 서버에 HTTP로 생성을 맡긴다.** vLLM이 제공하는 OpenAI 호환 API를 쓰는 것을 권고하되 경로(완성형/대화형)·요청 형식은 ml-engineer가 확인해 정한다(**확인 필요**) |
| FR-ED3-2 | 기동 시 vLLM 서버 **연결과 설정한 모델 ID의 제공 여부**를 확인하고, 실패하면 **기동 실패**한다(Ollama의 `_verify_server_and_model` 원칙 동일 — `generator.py` 187~220행) |

### 11.1 AskUserQuestion용 쉬운 문구(핵심 6건)

**Q1. "엣지 추론"을 우리 제품에서 무슨 뜻으로 볼까요?** (원래 목록에는 "가벼운 AI 모델을 단말/엣지에서 돌려 빠르고 유출 없이"라고만 적혀 있습니다. 지금도 대화에 쓰는 AI는 고객사 서버 안에서, 그래픽카드 없이 돕니다)
- ① **고객사 서버 한 대(그래픽카드가 없거나 작아도)에서 AI가 전부 도는 것 (추천)**
- ② 매장·지점마다 작은 장비를 두고 각각 AI를 돌리며, 본사에서 한꺼번에 관리하는 것 — 여러 곳 관리 기능을 새로 만들어야 함
- ③ 사용자 휴대폰·브라우저 안에서 AI가 도는 것 — 챗봇 창을 가볍게 유지하는 원칙과 충돌하고, 챗봇 답변 전체를 사용자 기기로 보내야 해서 오히려 유출 위험이 커짐
- ④ 따로 기능으로 두지 않음 — "설치형"이 곧 엣지이므로 설치 안내 문서만 정리

**Q2. 이번에 어디까지 할까요?**
- ① 지금은 하지 않기 — "대부분 이미 된다"는 사실만 기능 목록에 적어 둠
- ② **작게: 운영 AI 서버(vLLM) 연결 추가 + 작은 그래픽카드용 구성 정리 + "이 장비면 무엇이 된다" 설치 안내표. 새 화면 없음 (추천)**
- ③ ②에 더해 실제 고객 소형 장비에서 직접 시험해 안내표 채우기 — 시험할 장비가 있어야 함
- ④ ③에 더해 휴대폰·브라우저 안 AI, 여러 지점 관리까지 — 비용·위험 가장 큼

**Q3. 개발용 노트북에서 돌려 본 "작은 AI 모델 구성(Ollama)"을 고객 설치에도 쓰게 할까요?** (시험 결과, 한 번에 20개 문장은 약 13초에 잘 만들었지만 60개는 시간 초과이거나 결과가 망가졌습니다)
- ① **"가벼운 구성"으로 쓰게 하되, "동작은 하지만 품질은 보장하지 않음"을 화면과 문서에 표시 (추천)**
- ② 개발·시연용으로만 두고 고객 설치에는 쓰지 않음
- ③ 운영 표준으로 채택 — 품질 근거가 아직 없음

**Q4. 운영에서 연결할 AI 서버(vLLM)는 어떤 서버인가요?**
- ① **예문 늘리기 전용 AI 서버를 따로 둔다(회사 내부 주소) (추천)**
- ② 문서 검색 답변(외부 RAG)이 쓰는 AI 서버를 함께 쓴다 — 서로 느려지거나 같이 멈출 수 있음
- ③ 아직 정해지지 않았다 — 그러면 연결 기능은 가짜 서버로 시험만 해 두고 실제 연결은 서버가 생기면

**Q5. "켜도 된다"는 판단 기준은 어떻게 할까요?**
- ① **개발 노트북·작은 장비 결과는 "돌아간다"는 확인으로만 쓰고, 품질·속도 합격은 운영 서버의 운영 모델로 시험해 정한다(No.17과 같은 기준) (추천)**
- ② 작은 장비용 합격 기준을 따로, 더 느슨하게 정한다
- ③ 기준 없이 결과를 보고 그때 판단

**Q6. 작은 AI 모델이 한 번에 많이(60개) 만들지 못하는 문제는 어떻게 할까요?**
- ① **작은 구성에서는 한 번에 만드는 개수를 줄인다(예: 20개) — 제안 수는 줄지만 제시간에 나옴 (추천)**
- ② 여러 번 나눠 만들어 60개를 채운다 — 전체 시간이 제한(30초)을 넘기 쉬움
- ③ 그대로 둔다 — 대부분 기본 방식(규칙 기반)으로 자동 전환돼 작은 AI 모델을 켠 의미가 거의 없음
