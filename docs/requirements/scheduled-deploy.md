### 1.3 ★ 선결 쟁점 — "무엇을 지정 시각에 반영하는가"

카탈로그 문구 **"학습 완료된 챗봇을 지정 시각에 자동 반영"** 은 원본(ROCHA 매뉴얼 p.4 재학습 절차 — `stats-learning.md` §9 인용)에서 **"운영중 챗봇 복사 → 학습 → 운영 챗봇 교체"** 의 마지막 단계를 예약하는 기능이다. 즉 원본은 **운영본과 학습본이 동시에 존재**하는 모델이다. 우리 시스템에는 그 두 벌이 없다(§1.2 첫 행). 따라서 반영 대상을 먼저 정해야 한다.

#### 1.3.1 후보 비교

| 후보 | 지정 시각에 일어나는 일 | 코드 근거 · 재사용 | "학습 완료된 챗봇을 반영"을 얼마나 충족하나 | 비용 · 위험 |
|---|---|---|---|---|
| **(a) 버전 예약 복원** | 선택한 `ChatbotVersion` 스냅샷으로 **원자적·ID 보존 복원**(`BEFORE_RESTORE` 백업 포함) | `VersionRestoreService.restore()` **그대로**. 미리보기·blockers·해시 재확인·백업·재색인·분류기 삭제·감사가 전부 이미 있다 | **부분 충족.** ① **캠페인 종료 복귀**("10/31 23:59에 이벤트 전 버전으로") ② **야간 반영**("오늘 준비한 버전을 새벽 2시에") 을 지원한다. 단 ②는 준비 과정에서 **편집이 운영에 즉시 보인다** — 준비 → 버전 저장 → 직전 버전으로 즉시 복원(운영 원상태) → 새 버전을 예약. **편집하는 동안(수 분~수 시간) 운영 노출 창이 존재한다**(⚠ P-2) | **낮음.** 신규 쓰기 경로 0(applier 재사용). 대가: ADR-0025/0031의 "복원은 관리자 요청 핸들러 1곳 — 스케줄러 경로 없음" 문구를 **갱신**해야 한다(J-11). 예약~실행 사이 편집이 있으면 **실행하지 않는다**(J-4) |
| **(b) 공개 상태 예약 전환** | ① `DRAFT → ACTIVE`(+ 선택: WEB 채널 동시 활성화) ② WEB 채널 `enabled` 켜기/끄기 | `ChatbotsService.updateStatus()` · `ChannelsService.upsert()` 재사용. `PublicAccessService`가 캐시 없이 매 요청 판정하므로 **즉시 반영** | **"새로 만든(학습 완료된) 챗봇을 지정 시각에 공개"를 완전 충족.** 운영 중 챗봇의 **내용 교체는 못 한다** | **매우 낮음.** 자산 쓰기 0. `ACTIVE→DRAFT` 전이가 없으므로 "내리기"는 **채널 끄기**로만 제공(§4.1.2) |
| **(c) draft/published 분리 신설** | 편집은 draft에, 대화는 published에서. 지정 시각에 draft → published 승격 | 없음 — 새로 만든다 | **완전 충족**(원본 ROCHA 의미 그대로) | **매우 높음 · No.40 선점.** §1.3.2 |
| **조합 (a)+(b)** ★ | 한 예약 = 동작 1개(복원 / 공개 시작 / 채널 열기·닫기). 같은 챗봇에 **순서 있는 예약 여러 개**(예: 08:55 v31 복원 → 09:00 공개 시작) | 위 두 실행부 | 신규 챗봇 공개는 완전, 운영 중 내용 교체는 (a)의 한계 그대로 | 낮음 |

| **No.40과의 관계** | draft = Dev, published = Prod다. **"환경 분리 + 승격"은 No.40의 정의 그 자체**이며(카탈로그 89행 "배포 전 별도 환경에서 테스트, 환경별로 버전을 태깅·트래픽 전환"), ADR-0031 §8은 "No.40 ADR이 명시적으로 대체하기 전까지 경계를 유지한다"고 고정했다 |

> **결론**: (c)는 No.28(GPU 1, "스케줄 트리거")이 아니라 **No.40의 본체**다. No.28에서 만들면 No.40을 **선점**하고 7개 선행 그룹의 설계를 동시에 흔든다. 그래서 **권장하지 않는다.**
> **향후 경로(기록)**: No.40 착수 시 가장 가벼운 형태는 **"published = 특정 `ChatbotVersion`을 가리키는 포인터"** 다(No.25 스냅샷이 이미 `DialogueBundle` 형태이므로). 그때 이 그룹의 예약 엔진은 **"포인터 전환 예약"** 이라는 동작 유형 1개를 추가하는 것으로 원본 의미를 완전히 충족할 수 있다 — 이 그룹은 **동작 유형을 확장 가능한 판별 유니온으로** 설계한다(NFR-DM2).

#### 1.3.3 권장안

**조합 (a)+(b)** — 1차 동작 유형 3종: **`RESTORE_VERSION`** (a) · **`PUBLISH`**(DRAFT→ACTIVE, 선택적으로 WEB 채널 동시 활성화) (b) · **`SET_WEB_CHANNEL`**(열기/닫기) (b). (c)는 No.40으로 보낸다.

**근거 요약**
1. **(b)만으로는 이름값을 못 한다** — 운영 중 챗봇에 "학습 결과"를 반영할 수단이 0이다. **(a)만으로는 가장 흔한 요구(신규 챗봇 오픈 시각 지정)를 못 한다.** 둘은 실행부가 이미 있고 겹치지 않는다.
2. 두 실행부 모두 **이미 검증된 코드 경로**다(복원: AC-H3 전 항목, 상태/채널: AC-1-13·AC-P-3). 예약 엔진은 **"언제 호출하느냐"만** 새로 만든다 — 신규 자산 쓰기 경로 0건.
3. (a)의 핵심 한계(준비 중 운영 노출)는 **정직하게 PM에게 넘긴다**(P-2). 수용 불가라면 올바른 답은 (c)를 No.28에 끼워 넣는 것이 아니라 **No.40을 먼저 하는 것**이다.

### 1.4 목적

1. 관리자가 **지정한 시각에**, 사람이 콘솔 앞에 없어도 **이미 검증된 반영 동작**(버전 복원 · 공개 시작 · 채널 열기/닫기)이 **정확히 한 번** 실행되게 한다.
2. 예약 시점에 관리자가 **확인한 상태 그대로**일 때만 실행하고, 그 사이 누가 무엇을 바꿨다면 **실행하지 않고 알린다**(조용한 덮어쓰기 금지).
3. 서버가 꺼져 있었거나 재시작돼도 예약이 **유실되지 않고**, 늦었으면 **정해진 규칙(misfire 정책)** 대로 처리된다.
4. 다중 인스턴스에서도 **중복 실행이 구조적으로 불가능**하다.
5. 실행 결과(성공·실패·누락)를 **콘솔과 감사로그**에서 확인할 수 있고, 복원 실행은 **백업 버전으로 즉시 되돌릴 수 있다**.
6. **No.25의 경계(한 챗봇·시간축·즉시 복원)와 No.40의 경계(환경·승격·트래픽 전환)를 침범하지 않는다.**

            │                        (같은 챗봇에 선행 PENDING 복원이 있으면 = 그 예약의 대상 해시, J-5)

            └─ SET_WEB_CHANNEL : 열기/닫기
        │  시각 입력(STATS_TIMEZONE 기준, 분 단위) · 메모 · ACTIVE 확인(acknowledgeActive)
        ▼
  검증: 리드타임 ≥ 5분 · ≤ 90일 · 챗봇당 활성 ≤ 5 · 같은 챗봇 예약과 ≥ 1분 간격 · 권한
        ▼
  DeploySchedule 행 { action, params, scheduledAt(UTC), expectedContentHash?, createdBy*, status: PENDING }
  감사: DeploySchedule CREATE

■ 실행 엔진 (API 프로세스 내부, 폴링 30초)
  tick ─▶ due = status=PENDING AND scheduledAt ≤ now  (scheduledAt 오름차순, 챗봇별 첫 건만)
        │
        ├─ now − scheduledAt > 유예 10분 ──▶ MISSED  (+ 같은 챗봇 후속 PENDING → HELD)
        │

        │        영향 행 1 → 내가 실행 / 0 → 다른 인스턴스가 가져감(건너뜀)
        ▼

        ▼
  ┌ RESTORE_VERSION ─▶ VersionRestoreService.restore(chatbotId, versionId,
  │                       { expectedCurrentHash: expectedContentHash, acknowledgeActive }, actorOverride=생성자)

        ▼

            └─ 영구적(STATE_CHANGED·무결성·권한…)  → FAILED(사유) + 같은 챗봇 후속 PENDING → HELD
        ▼

■ 기동 시 정리 (임대 기반 — 단일 인스턴스 가정 없음)
  RUNNING AND claimedAt < now − 임대 5분 ─▶ 실제 상태로 판정(복원: 현재 해시 = 대상 해시? / 공개: status·enabled)

## 2. 사용자 역할 및 시나리오

### 2.1 역할

`security-audit.md` §2.1의 역할 3종을 상속한다. **신규 권한 문자열 0종**(J-8, `Permission` 유니온 15종 불변).

| 역할 | 이 그룹에서의 활동 | 권한(권고안) |
|---|---|---|
| **ADMIN** | EDITOR의 모든 활동 + 감사로그에서 예약 실행 추적 | EDITOR 권한 + `audit:read` |
| **EDITOR** | 예약 생성·시각/메모 수정·취소·보류 해제·결과 확인(이 그룹의 주 사용자) | 동작별(§4.2.3): 복원 = `dialogue:write`+`chatbot:write` · 공개 시작 = `chatbot:write`(+ 채널 동시 활성화 시 `channel:write`) · 채널 열기/닫기 = `channel:write` |

### 2.2 사용자 시나리오

**S-1. 신규 챗봇 오픈 시각 예약 (EDITOR · ★ 핵심 — (b))**
`연말정산 상담봇`을 `DRAFT`로 만들어 의도·FAQ를 채우고 No.19 TC 세트로 검증(통과 412/420)을 끝냈다. 오픈은 1월 15일 09:00이다. `예약 배포` → `공개 시작` → `WEB 채널도 함께 열기` 체크 → 시각 `2027-01-15 09:00 (KST)`를 입력한다. 예약 목록에 `대기 · 공개 시작 · 1/15 09:00 · 편집자A`가 보인다. 1월 15일 09:00:20에 상태가 `ACTIVE`, WEB 채널이 `사용`으로 바뀌고 예약은 `성공 (09:00:20 실행)`이 된다. 감사로그에 `상태변경 DRAFT → ACTIVE [예약 실행]`과 `채널 수정 사용 여부 변경 false → true [예약 실행]`이 편집자A 명의로 남는다.

**S-2. 캠페인 기간 FAQ 교체와 자동 복귀 (EDITOR · (a) + 체인)**
10월 한 달 이벤트 FAQ를 넣어야 한다. 9월 30일 오후, 편집자는 ① 현재 상태를 `v30 "이벤트 전"`으로 저장(고정) ② 이벤트 FAQ 12건 추가 → `v31 "이벤트"` 저장 ③ 곧바로 v30으로 **즉시 복원**(운영은 원상태 — 이 사이 약 20분간 이벤트 FAQ가 운영에 노출됨, ⚠ P-2) ④ `v31 복원 · 10/1 00:00` 예약 ⑤ `v30 복원 · 11/1 00:00` 예약. ⑤의 기준 해시는 **④의 대상(v31) 해시**로 자동 설정된다(J-5). 10월 1일 00:00에 v31로, 11월 1일 00:00에 v30으로 바뀐다. 각 실행은 `BEFORE_RESTORE` 백업을 남긴다.

**S-3. 예약 이후 누가 편집했다 (EDITOR · J-4)**
S-2의 ⑤ 예약(11/1 v30 복귀)이 걸려 있는데, 10월 15일 다른 편집자가 오탈자 FAQ 1건을 고쳤다. 편집 화면 상단에 **"이 챗봇에 예약된 복원이 있습니다(11/1 00:00 v30). 지금 저장하면 예약 시점의 상태와 달라져 예약이 실행되지 않습니다"** 배너가 떠 있었지만 저장했다. 11월 1일 00:00 예약은 **실행되지 않고** `실패 · 예약 이후 자산이 변경됨`이 된다. 챗봇 목록에 `확인 필요` 배지가 뜬다. 편집자는 출근 후 v30 복원 미리보기(오탈자 수정분도 함께 되돌아감이 보임)를 확인하고 **즉시 복원**하거나 다시 예약한다.

**S-4. 서버가 꺼져 있었다 (운영자 · misfire J-6)**
02:00 예약이 있었는데 서버가 01:30~02:05에 점검으로 내려가 있었다. 02:05 기동 시 예약은 5분 늦었으므로(유예 10분 이내) **즉시 실행**되고 결과에 `지연 5분`이 기록된다. 점검이 03:00까지 이어졌다면 예약은 `누락(MISSED)`이 되고 실행되지 않는다. 관리자는 아침에 `확인 필요`를 보고 `지금 실행`을 누른다(새 미리보기 → 새 예약 생성 흐름).

**S-5. 새벽에 TC 실행이 돌고 있다 (J-7)**
02:00 복원 예약 시각에 누군가 퇴근 전 걸어 둔 대량 TC 실행이 진행 중이다. 예약은 `대기(재시도 중 — 진행 중인 작업: TC 실행 72%)`로 30초마다 재시도하다 02:03에 TC가 끝나자 실행된다. TC가 02:15를 넘겨도 끝나지 않으면 `실패 · 진행 중인 작업으로 15분간 실행하지 못함`이 된다.

**S-6. 예약한 편집자가 퇴사했다 (J-8)**
편집자B가 걸어 둔 예약이 있는데, 그 사이 관리자가 편집자B 계정을 `DISABLED`로 바꿨다. 실행 시각에 예약은 **실행되지 않고** `실패 · 예약자의 권한이 없음`이 된다. 예약 목록에서 다른 편집자가 같은 동작을 **자신의 이름으로 다시 예약**한다.

**S-7. 선행 예약 실패 시 후속 보류 (J-5)**
08:55 `v31 복원` → 09:00 `공개 시작` 순서로 예약했다. 08:55 복원이 무결성 문제로 실패했다. 09:00 공개 시작은 **보류(HELD)** 로 바뀌어 실행되지 않는다 — 옛 내용으로 공개되는 사고를 막는다. 관리자가 원인을 고친 뒤 `보류 해제`(새 시각 지정) 또는 `취소`한다.

**S-8. 지정 시각에 대화 중인 사용자 (최종 사용자 · RESTORE)**
00:00 복원 순간 커피 주문 폼 2단계에 있던 사용자는, 대상 버전에도 같은 컨텍스트(같은 ID)가 있으면 **그대로 이어 간다**. 없으면 다음 턴에 일반 매칭으로 자연스럽게 복귀한다(ADR-0009, No.25 S-7과 동일 — 이 그룹은 새 동작을 만들지 않는다).

**S-9. 채널 닫기 순간 대화 중인 사용자 (최종 사용자 · SET_WEB_CHANNEL)**
이벤트봇을 18:00에 닫도록 예약했다. 17:59:50에 질문을 보낸 사용자는 정상 답변을 받는다. 18:00:20 이후의 다음 메시지는 `403 CHANNEL_DISABLED`이고 위젯은 **"현재 상담을 이용할 수 없습니다"** 를 표시한다(기존 공개 접근 규약 — 오류 화면 아님). 대기 중이던 비동기 RAG 답변 폴링도 같은 판정을 받는다.

**S-10. VIEWER가 예약을 본다**
운영 모니터가 예약 목록에서 `11/1 00:00 v30 복원 · 대기`를 확인한다. 생성·수정·취소 버튼은 보이지 않는다.

**S-11. 접근성 (EDITOR)**
시각 입력은 **달력 위젯만이 아니라 날짜·시·분 텍스트 입력**을 함께 제공하고, 시간대 라벨 `(KST, UTC+9)`을 입력 필드의 접근 가능한 이름에 포함한다. 상태 배지는 **색상 + 텍스트**(`대기`/`실행 중`/`성공`/`실패`/`누락`/`보류`/`취소`)로 구분한다. 예약 취소 확인 대화상자의 기본 포커스는 **"예약 유지"**(파괴적 동작의 기본값 = 취소하지 않음).

## 4. 기능별 요구사항

### 4.1 반영 대상(동작 유형) — J-1 결정

#### 4.1.1 동작 유형 3종

| `action` | 파라미터 | 실행 내용 | 재사용 경로 | 필요 권한(생성·수정·취소) |
|---|---|---|---|---|
| **`RESTORE_VERSION`** | `versionId` · `expectedContentHash`(생성 시 서버가 결정, J-5) · `acknowledgeActive` | 대상 버전으로 원자적·ID 보존 복원(`BEFORE_RESTORE` 백업 포함) | `VersionRestoreService.restore()` | `dialogue:write` + `chatbot:write`(즉시 복원과 동일, ADR-0031 §7) |
| **`PUBLISH`** | `enableWebChannel: boolean` | `DRAFT → ACTIVE`. `enableWebChannel=true`면 WEB 채널 `enabled=true`(행 없으면 기본 config로 생성)를 **같은 트랜잭션에서** | 상태 전이 판정(`evaluateStatusTransition`) · 채널 활성화 규칙(IMPLEMENTED만) | `chatbot:write`(+ `enableWebChannel=true`면 `channel:write`) |
| **`SET_WEB_CHANNEL`** | `enabled: boolean` | WEB 채널 `enabled` 변경(행 없고 `enabled=true`면 기본 config로 생성) | `ChannelsService.upsert()` 규칙 | `channel:write` |

#### 4.1.2 제외한 동작과 근거

| 제외 동작 | 근거 | 대안 |
|---|---|---|
| `ACTIVE → DRAFT`(운영 내리기) | **허용 전이에 없다**(`CHATBOT_STATUS_TRANSITIONS`). 전이 규칙 변경은 No.1(FR-1-17)의 결정을 뒤집는 일이다 | `SET_WEB_CHANNEL(enabled=false)` — 공개 접근 조건(ADR-0011)상 동일하게 비공개가 되며 **가역**이다 |
| `ACTIVE → ARCHIVED`(보관) 예약 | 되돌리려면 `DRAFT` 경유 재검수가 강제되는 **무거운 전이**다. 무인 실행에 두기엔 복구 비용이 크다 | 채널 닫기 예약 + 사람이 확인 후 보관 |
| 다른 채널(카카오 등) 활성화 | `CHANNEL_IMPLEMENTATION`상 WEB만 `IMPLEMENTED`다(ADR-0011) | 채널 연동 착수 시 `SET_WEB_CHANNEL`을 `SET_CHANNEL(type)`로 일반화(NFR-DM2) |
| 답변설정만·표시설정만 예약 변경 | 버전 스냅샷에 이미 포함된다(ADR-0031 §1) — 부분 적용은 No.25의 "부분 복원 없음" 결정과 충돌 | `RESTORE_VERSION` |
| 금지어·보안 정책 예약 변경 | 전역 설정이다(챗봇 스코프 아님) | 범위 밖 |
| 분류기 재학습·재색인·TC 실행 예약 | 반영이 아니라 **작업**이다. 자동 재학습은 ADR-0027이 기각했다 | 범위 밖(§9). 단 **실행 직후 TC**는 선택 기능(§4.5) |
| **draft → published 승격** | §1.3.2 — No.40 본체 | No.40에서 "포인터 전환" 동작 유형 추가 |

| ID | 요구사항 |
|---|---|
| FR-D1-1 | 동작 유형은 **판별 유니온**(`action` + 동작별 `params`)으로 정의한다. 1차 값은 §4.1.1의 3종이며, 유형 추가는 유니온 확장 + 실행기 분기 1개로 끝나야 한다(NFR-DM2). |
| FR-D1-2 | 예약 1건은 **동작 1개**다. 복합 동작(예: 복원 + 공개)은 **같은 챗봇의 순서 있는 예약 여러 건**으로 표현한다(J-5 체인·보류 규칙 적용). 단 `PUBLISH`의 `enableWebChannel`은 "공개"의 정의(ADR-0011: 상태 AND 채널)상 하나의 동작으로 본다. |
| FR-D1-3 | `PUBLISH`의 상태 변경과 채널 활성화는 **원자적**이다 — 둘 다 적용되거나 둘 다 적용되지 않는다. 구현 방식(기존 서비스에 트랜잭션 인자 추가 등)은 architect 확정. |

### 4.2 예약 생성 · 미리보기 바인딩

#### 4.2.1 생성 절차

| ID | 요구사항 |
|---|---|
| FR-D2-1 | **`RESTORE_VERSION` 생성은 미리보기를 거쳐야 한다.** 콘솔은 기존 `POST …/versions/:versionId/restore/preview`를 호출해 차이·blockers·warnings를 보여 주고, 생성 요청은 그 응답의 `currentContentHash`를 `previewedContentHash`로 싣는다. |
| FR-D2-2 | 서버는 생성 시 **기준 해시(`expectedContentHash`)** 를 결정한다: ① 같은 챗봇에 이 예약보다 **이른 `PENDING`/`HELD` `RESTORE_VERSION`** 이 있으면 → 그중 가장 늦은 것의 **대상 버전 해시**(J-5 체인) ② 없으면 → **현재 해시를 다시 계산**해 `previewedContentHash`와 비교, 다르면 `409 RESTORE_PREVIEW_STALE`(미리보기 이후 변경 — No.25 FR-H3-6과 동일 규약) ③ 같으면 그 값을 저장. |
| FR-D2-3 | 생성 시 미리보기 **blockers가 있으면 생성을 거부**한다(`DEPLOY_SCHEDULE_PRECONDITION_FAILED` + blockers). 단 **"진행 중 작업(`ACTIVE_JOB`)"과 "복원 진행 중(`RESTORE_IN_PROGRESS`)"은 예외** — 실행 시점에는 끝나 있을 것이므로 **경고로 격하**한다. `NO_CHANGES`(현재와 동일)도 체인 예약(①)에서는 판정 기준이 "선행 대상 상태"이므로 서버가 그 기준으로 다시 판정한다. |
| FR-D2-4 | 챗봇이 `ACTIVE`이거나 **예약 시각에 `ACTIVE`일 예정**(같은 챗봇에 더 이른 `PUBLISH` 예약 존재)이면 `acknowledgeActive: true`를 요구한다(No.25 FR-H3-20과 같은 확인). |
| FR-D2-5 | `PUBLISH` 생성 조건: 현재 상태가 `DRAFT`. `ACTIVE`면 `DEPLOY_SCHEDULE_PRECONDITION_FAILED`("이미 공개 중"), `ARCHIVED`면 같은 코드("보관된 챗봇은 먼저 DRAFT로 되돌려야 합니다" — `ARCHIVED→ACTIVE` 금지 규약). |
| FR-D2-6 | `SET_WEB_CHANNEL` 생성 조건: 챗봇이 `ARCHIVED`가 아님. 현재 값과 같은 값을 예약하는 것은 **허용**한다(그 사이 다른 예약·수동 변경으로 바뀔 수 있다) — 실행 시 같으면 NOOP 성공. |
| FR-D2-7 | 생성 시 **준비도 경고**(§4.5 soft)를 응답·화면에 표시한다. 경고는 생성을 막지 않는다. |
| FR-D2-8 | 모든 예약은 생성자 스냅샷(`createdById`·`createdByEmail`·`createdByRole`, FK 없음 — AuditLog 규약)과 선택 메모(최대 200자)를 저장한다. |

#### 4.2.2 시각 규칙 (J-12, J-13)

### 4.3 예약 관리 · 실행 엔진

#### 4.3.1 상태 모델

| 상태 | 의미 | 다음 상태 |
|---|---|---|
| `PENDING` | 실행 대기(재시도 대기 포함 — `lastAttemptAt`·`attemptCount`·`lastTransientReason`으로 표시) | `RUNNING` · `CANCELLED` · `MISSED` · `HELD` |
| `RUNNING` | 한 인스턴스가 선점해 실행 중(`claimedAt`·`claimToken`) | `SUCCEEDED` · `FAILED` · `PENDING`(일시적 원인 재시도) |
| `SUCCEEDED` | 실행 완료. `outcome`: `APPLIED` \| `NOOP`(이미 그 상태) \| `RECOVERED`(기동 정리에서 적용 확인) | 종단 |
| `FAILED` | 영구적 원인으로 실행 안 됨 / 실행 실패. `failureReason` 코드 | 종단 |
| `MISSED` | 유예 초과로 실행하지 않음 | 종단 |
| `HELD` | 같은 챗봇의 선행 예약 실패/누락으로 **보류** | `PENDING`(보류 해제 + 새 시각) · `CANCELLED` |
| `CANCELLED` | 사용자 취소 | 종단 |

`failureReason`(제안): `STATE_CHANGED` · `TARGET_VERSION_MISSING` · `INTEGRITY_FAILED` · `SCHEMA_UNSUPPORTED` · `CHATBOT_ARCHIVED` · `CHATBOT_NOT_FOUND` · `INVALID_TRANSITION` · `CREATOR_NOT_AUTHORIZED` · `BLOCKED_TOO_LONG`(재시도 창 소진) · `INTERRUPTED`(실행 중 중단, 상태 판정 불가) · `INTERNAL_ERROR`.

#### 4.3.2 관리 요구사항

| ID | 요구사항 |
|---|---|
| FR-D3-1 | 예약 목록: 챗봇별(`/chatbots/:chatbotId/deploy-schedules`)과 **전체 챗봇 통합**(콘솔 운영 화면용 — 권한 범위 내 챗봇만) 두 가지. 필터: 상태·동작·기간. 정렬: `scheduledAt`. 페이지네이션 필수(기본 50). |
| FR-D3-2 | 수정 가능 필드는 **`scheduledAt`·`memo`뿐**이며 `PENDING`/`HELD`에서만 가능하다(`DEPLOY_SCHEDULE_NOT_MODIFIABLE`). 시각 변경 시 FR-D2-11~13을 다시 검사한다. 시각 변경으로 **체인 순서가 바뀌면**(다른 복원 예약을 앞지르면) 기준 해시가 달라지므로 **거부**하고 "취소 후 다시 예약"을 안내한다. |
| FR-D3-3 | 취소는 `PENDING`/`HELD`에서만 가능하다. `RUNNING`은 취소할 수 없다(실행은 수 초 — No.25 NFR-HP3). 취소된 `RESTORE_VERSION`이 체인 중간이면 **후속 복원 예약을 `HELD`로** 바꾼다(기준 해시 전제가 깨졌으므로). |
| FR-D3-4 | **보류 해제**: `HELD` → `PENDING`은 **새 `scheduledAt` 입력을 요구**하고, `RESTORE_VERSION`이면 **미리보기 재확인**(FR-D2-1~3 재적용 — 기준 해시 재결정)을 요구한다. |

#### 4.3.3 실행 엔진 — J-3 결정

| 방식 | 재시작 내성 | 다중 인스턴스 | 신규 의존·표면 | 판정 |
|---|---|---|---|---|
| 예약별 `setTimeout` | ✕(메모리 소실 → 기동 시 재적재 필요) | ✕ | 없음 | **기각** — 지연이 2³¹−1ms(약 24.8일)를 넘으면 Node가 1ms로 취급해 **즉시 실행**된다(90일 예약에서 실제로 발생) |
| `@nestjs/schedule` | 선언형 cron은 정적, 동적 1회 예약은 `SchedulerRegistry` + 결국 타이머 | ✕(인스턴스마다 동작) | 신규 의존성 | **기각** — DB 폴링 이상을 제공하지 않으면서 의존성만 는다. 반복(cron) 예약을 도입할 때 재검토 |
| 외부 cron(OS cron · k8s CronJob) → 내부 엔드포인트 | ○ | 호출 측 설정에 의존 | **내부 호출 인증 경로(공개 표면)** + 구축형 설치 절차 추가 | **기각** — FR-0-85, 배포형태 중립(개발명세서 §5) |
| ★ **인프로세스 폴링 + DB 선점** | ○(DB가 원천) | ○(CAS 선점) | 없음(`pending-answer.store.ts`의 `setInterval` 선례) | **채택** |

| ID | 요구사항 |
|---|---|
| FR-D3-5 | 실행 엔진은 API 프로세스 안의 **주기 폴링**(기본 30초, `DEPLOY_SCHEDULE_POLL_INTERVAL_MS`)이다. 각 tick은 `status=PENDING AND scheduledAt ≤ now`를 `scheduledAt` 오름차순으로 조회하고 **챗봇별로 가장 이른 1건만** 처리한다(같은 챗봇 예약의 순서 보장). |
| FR-D3-6 | **선점**: `UPDATE … SET status='RUNNING', claimedAt=now, claimToken=<uuid> WHERE id=? AND status='PENDING'`의 영향 행 수가 1일 때만 실행한다. 0이면 다른 인스턴스가 가져간 것이므로 건너뛴다. **프로세스 로컬 잠금은 정합성 근거가 아니다**(FR-0-81). |
| FR-D3-7 | tick은 **겹쳐 실행되지 않는다**(이전 tick이 끝나지 않았으면 건너뜀). tick 한 번의 처리 시간 상한을 두고(예: 20초), 남은 예약은 다음 tick으로 넘긴다. tick의 예외는 **흡수**하고 경고 로그만 남긴다(타이머가 죽지 않는다). |
| FR-D3-8 | 실행 엔진은 `DEPLOY_SCHEDULE_ENABLED=false`로 끌 수 있다(다중 인스턴스에서 실행 전담 인스턴스를 지정하거나 테스트 환경용). 꺼져 있어도 **예약 CRUD는 동작**하며, 콘솔에 "이 서버에서는 예약 실행이 비활성화되어 있습니다" 경고를 표시한다(관리자가 모르고 기다리지 않게). |
| FR-D3-9 | 실행 결과를 **일시적/영구적으로 분류**한다(J-7). 일시적: DB 경합(`BUSY`) · 진행 중 `TrainingJob`/`TestRun`(`RESTORE_BLOCKED_BY_ACTIVE_JOB`) · 복원 잠금(`RESTORE_IN_PROGRESS`). ⚠ 현재 `restore()`는 `BUSY`와 해시 불일치를 **같은 `RESTORE_PREVIEW_STALE`로 반환**하므로, 분류를 위해 **원인 구분**(`RESTORE_BUSY` 신설 또는 details 필드)이 필요하다 — architect 확정. 그 외는 영구적. |
| FR-D3-10 | 일시적 원인이면 `PENDING`으로 되돌리고 `attemptCount`·`lastTransientReason`을 갱신한다. **`scheduledAt + 재시도 창(15분)`을 넘으면 `FAILED: BLOCKED_TOO_LONG`**. 재시도 창은 misfire 유예(J-6)와 별개로 "**시각에 맞춰 시작은 했으나 막힌**" 경우에만 적용한다. |
| FR-D3-11 | `RESTORE_VERSION` 실행은 `VersionRestoreService.restore()`를 호출하며, 호출 인자에 **감사 주체(`actorOverride` = 생성자)** 와 `acknowledgeActive`를 전달할 수 있어야 한다. 기존 컨트롤러 호출 경로는 **동작이 바뀌지 않는다**(선택 인자). |
| FR-D3-12 | 실행 직전 **생성자 재검증**(FR-0-80): 사용자 행이 존재하고 `status=ACTIVE`이며 현재 역할(`ROLE_PERMISSIONS`)이 그 동작의 권한을 전부 보유. 불충족 → `FAILED: CREATOR_NOT_AUTHORIZED`(재시도 없음). |
| FR-D3-13 | `RESTORE_VERSION`에서 현재 해시가 이미 대상 해시와 같으면(`RESTORE_NO_CHANGES`) **`SUCCEEDED(NOOP)`** 로 처리한다 — 원하는 결과가 이미 달성됐다. `PUBLISH`에서 이미 `ACTIVE`(+채널 이미 활성)면 NOOP, `SET_WEB_CHANNEL`에서 이미 그 값이면 NOOP. NOOP은 감사를 남기지 않는다(쓰기 0건). |
| FR-D3-14 | 한 예약이 `FAILED`/`MISSED`가 되면 **같은 챗봇의 그보다 늦은 `PENDING` 예약 전부를 `HELD`(사유: `PREDECESSOR_FAILED`, 선행 예약 id)** 로 바꾼다(J-5, ⚠ P-8). `CANCELLED`는 FR-D3-3 규칙만 적용한다. |
| FR-D3-15 | **기동 시 정리**(임대 기반): ① `RUNNING AND claimedAt < now − 임대(5분)` → **실제 상태로 판정**: `RESTORE_VERSION`은 현재 해시 = 대상 해시이고 그 사이 이 예약을 원인으로 한 `BEFORE_RESTORE` 백업이 있으면 `SUCCEEDED(RECOVERED)`, 아니면 `FAILED: INTERRUPTED`. `PUBLISH`/`SET_WEB_CHANNEL`은 현재 상태·`enabled`가 목표와 같으면 `RECOVERED`, 아니면 `INTERRUPTED` ② `PENDING`이고 유예 초과 → `MISSED`. 이 정리는 **기동 시 1회 + 매 tick**(임대 만료 검사) 수행한다 — `TrainingJobService.onModuleInit`처럼 "잔존 = 전부 고아"로 가정하지 않는다(다른 인스턴스가 실행 중일 수 있다). 임대 시간은 복원 트랜잭션 타임아웃보다 길어야 한다(architect 확정). |

### 4.4 misfire — J-6 결정

| 상황 | 처리 |
|---|---|
| 서버가 예정 시각에 떠 있음 | 폴링 주기 안에 실행(NFR-DP1) |
| 예정 시각에 다운 → **유예(10분) 이내** 기동 | **지연 실행**. `delaySeconds` 기록, 결과 화면에 "n분 지연 실행" 표시 |
| 예정 시각에 다운 → **유예 초과** 기동 | **`MISSED`**. 실행하지 않는다. 후속 예약 `HELD`(FR-D3-14) |
| `DEPLOY_SCHEDULE_ENABLED=false` 인스턴스만 떠 있음 | 유예 초과 시 다른 인스턴스(또는 활성화 후 기동)가 `MISSED` 처리 |
| 서버 시계가 뒤로 조정됨(NTP) | `scheduledAt ≤ now` 판정만 하므로 **늦게 실행**될 뿐 중복되지 않는다(선점이 상태 기반) |

| ID | 요구사항 |
|---|---|
| FR-D4-0 | 유예는 `DEPLOY_SCHEDULE_MISFIRE_GRACE_MINUTES`(기본 10, 범위 0~1440)로 조정 가능하다. `0`이면 "시각을 놓치면 절대 실행하지 않음". |
| FR-D4-0a | `MISSED`·`FAILED` 예약 상세에 **"지금 다시 예약"** 동작을 둔다 — 같은 동작·파라미터로 **새 예약 생성 흐름**(미리보기 재확인 포함, 최소 리드타임 5분 적용)을 연다. **즉시 실행을 원하면 No.25의 즉시 복원 / 기존 상태·채널 화면을 쓰도록 링크한다**(예약 기능에 두 번째 즉시 실행 경로를 만들지 않는다). |

### 4.5 실행 게이트("학습 완료") — J-2 결정

#### 4.5.1 게이트 후보와 비용

| 게이트 | 내용 | 가능 여부 · 비용 | 판정 |
|---|---|---|---|
| **G0 정합성 차단** | 복원 blockers(ARCHIVED · 무결성 · 스키마 · 해시 불일치) · 전이 가능 여부 · 권한 | 기존 코드가 이미 판정 — **비용 0** | ★ **필수(hard)** |
| **G0' 준비도 경고** | ① 임베딩 색인 `PENDING`/`FAILED` 건수(기존 `embedding-status`) ② 분류기 stale — **대화 경로와 무관**(ADR-0027)하므로 **표시하지 않음** ③ 최근 TC 실행 결과 요약(세트명·통과율·실행 시각) ④ 복원 warnings(금지어 일치 · 제거되는 승인 증강 예문 · `UNRESOLVED`가 될 TC — No.25 FR-H3-5) ⑤ `PUBLISH` 시 WEB 채널 미설정·비활성 | 기존 조회 재사용 — **비용 낮음** | ★ **생성 시 표시(soft)**. 실행을 막지 않는다 |
| G1 생성 시 대상 버전 TC 결과 요구 | 복원 대상 **버전**에 대해 TC를 돌린 결과가 기준 통과율 이상일 때만 예약 허용 | ✕ **현재 불가** — TC 실행은 현재 DB 번들(또는 오버레이)만 잰다. "스냅샷 번들로 실행" 모드 신설 필요 + 대상 버전 문장의 **임베딩 벡터가 없어**(현재 색인은 현재 문장 기준) 의미 매칭이 저하 모드로 판정된다 → **판정 왜곡**. 비용 **중~상** | 1차 제외 |
| G2 실행 직전 자동 TC → 실패 시 취소 | T−Δ에 TC 실행, 결과가 기준 미달이면 예약 취소 | G1의 문제 + **비동기 오케스트레이션**(Δ가 TC 규모에 의존: 2,000 TC ÷ 500/분 ≈ 4분, 저하 모드 차이) + **합격 임계 정의**(절대 통과율? 회귀 0건?) + 실행 중 편집 시 재판정. 비용 **상**. `PUBLISH`는 자산이 안 바뀌므로 현재 상태 TC로 가능하나 오케스트레이션 비용은 같다 | 1차 제외 |
| **G3 실행 직후 자동 TC(보고만)** | 반영 후 지정 세트를 자동 실행해 결과를 예약 상세에 연결. **자동 롤백 없음** | 기존 `TestRun` `SINGLE` 모드 그대로(반영 후 = 현재 상태). `TrainingJobQueue` 재사용. 비용 **낮음~중**(예약 → 검증 모듈 호출 의존 1개). 새벽 실행 시 ml-worker 점유 | ⚠ **선택 기능, 기본 OFF**(P-3) |
| G4 실행 직후 TC + 미달 시 자동 롤백 | G3 + 기준 미달이면 `BEFORE_RESTORE` 백업으로 자동 복원 | 무인 자동 롤백은 **판정 오류 시 정상 반영을 되돌리고**, 롤백 자체가 다시 TC 대상이 되어 **진동**할 수 있다. ADR-0025의 "관리자 모르게 자산이 바뀌지 않는다" 원칙과 정면 충돌 | **기각**(§9) |

> **"학습 완료된"의 이 그룹 정의**: 관리자가 **미리보기로 확인했고(G0'), 그 상태가 실행 시각까지 그대로이며(J-4), 실행 시점에 정합성 차단이 없는(G0)** 상태. 품질 검증(TC)은 **관리자가 예약 전에 수행하는 절차**이지 시스템 게이트가 아니다 — 화면이 최근 TC 결과를 보여 주어 그 절차를 유도한다.

| ID | 요구사항 |
|---|---|
| FR-D5-1 | G0는 실행 시 **기존 실행부의 판정을 그대로** 쓴다(복원 서비스의 트랜잭션 내 재확인 · `evaluateStatusTransition` · 채널 IMPLEMENTED 규칙). 예약 모듈이 판정 로직을 **복제하지 않는다**. |
| FR-D5-2 | G0' 준비도 경고는 **생성 시점과 예약 상세 조회 시점**에 계산해 보여 준다(저장하지 않음 — 조회 시점 계산, No.25 J-7과 같은 이유). |
| FR-D5-3 | ⚠ (P-3 채택 시) G3: 예약 생성 시 `postRunTestSetId`(선택)를 지정하면 **`SUCCEEDED(APPLIED)` 직후** 그 세트의 `SINGLE` 실행을 시작하고 `testRunId`를 예약에 연결한다. 세트가 삭제됐거나 실행 시작이 거부되면(동시 실행 1건 규약 등) **예약 결과는 성공으로 유지**하고 경고만 남긴다. 자동 롤백은 하지 않는다. |
| FR-D5-4 | 예약 상세의 `RESTORE_VERSION` 성공 결과에는 **백업 버전 번호와 "이 반영 되돌리기"(= 백업 버전 즉시 복원 미리보기) 링크**를 둔다 — No.25 경로 재사용. |

### 4.6 예약 이후 상태 변경 — J-4 · J-5 결정

| 변경 | `RESTORE_VERSION`에 미치는 영향 | `PUBLISH`/`SET_WEB_CHANNEL`에 미치는 영향 |
|---|---|---|
| 대화 자산·답변설정·표시설정 편집(단건·대량·증강 승인·학습 반영) | 해시 불일치 → **`FAILED: STATE_CHANGED`** | 없음(스냅샷 범위 밖) |
| 다른 즉시 복원 실행 | 해시 불일치 → 실패(단 결과가 대상과 같으면 NOOP 성공) | 없음 |
| 대상 버전 삭제 시도 | **`409 VERSION_REFERENCED_BY_SCHEDULE`**(J-9) | — |
| 대상 버전이 보존 정리 대상 | **정리에서 제외**(FR-D4-1) | — |
| 챗봇 상태 수동 변경(`DRAFT→ACTIVE` 등) | 없음(`status`는 스냅샷 밖) — 단 `acknowledgeActive` 미확인 예약이 `ACTIVE` 챗봇에 실행되려 하면 `FAILED: STATE_CHANGED`(ACTIVE 확인 없이 운영 챗봇을 바꾸지 않는다) | `PUBLISH`: 이미 ACTIVE → NOOP / ARCHIVED → `FAILED: CHATBOT_ARCHIVED` |
| 챗봇 보관(`ARCHIVED`) | `FAILED: CHATBOT_ARCHIVED` | 동일 |
| 챗봇 영구삭제 | 예약 **동반 삭제**(사전 검사 409 대상 아님 — `ChatbotVersion`과 같은 규약) | 동일 |
| 생성자 권한 강등·비활성 | `FAILED: CREATOR_NOT_AUTHORIZED` | 동일 |

| ID | 요구사항 |
|---|---|
| FR-D4-1 | `selectVersionsToPrune()`의 보호 집합에 **`PENDING`/`HELD` 예약이 참조하는 버전 id**를 추가한다(순수 함수 입력 확장). 보호 때문에 총량 상한을 넘으면 기존 총량 초과 규약을 따른다. |
| FR-D4-2 | 버전 수동 삭제(`DELETE …/versions/:versionId`)는 그 버전을 참조하는 활성 예약이 있으면 `409 VERSION_REFERENCED_BY_SCHEDULE` + 예약 목록. |
| FR-D4-3 | ★ **예약 충돌 예고**: 활성 `RESTORE_VERSION` 예약이 있는 챗봇의 **대화 자산 편집 화면들**(의도·키워드·동음이의어·컨텍스트·노드·FAQ·답변설정·기본설정)과 **증강 승인·대량 업로드·학습현황 반영 화면**에 배너를 표시한다: "이 챗봇에 예약된 복원이 있습니다(시각·대상). 지금 변경하면 예약이 실행되지 않습니다." 배너는 **저장을 막지 않는다**(편집 우선 — 예약이 편집을 인질로 잡지 않는다). |
| FR-D4-4 | 예약 상세에서 **"지금 기준 상태 점검"**(현재 해시 vs `expectedContentHash`)을 요청 시 계산해 보여 준다(목록에서 매번 계산하지 않음 — 캡처 비용 1초급, NFR-DP3). |
| FR-D4-5 | ⚠ "변경 무시하고 강행(`acceptLaterChanges`)" 옵션은 **1차에 두지 않는다**(J-4, P-4). |

### 4.7 실행 결과 알림 · 감사 — J-10 결정

| ID | 요구사항 |
|---|---|
| FR-D6-1 | 예약 행은 실행 결과를 보관한다: `startedAt` · `finishedAt` · `delaySeconds` · `attemptCount` · `outcome`/`failureReason` · `resultSummary`(JSON, 원문 없음 — 복원이면 `{ fromVersionNo, backupVersionNo, counts }`, 공개면 `{ statusBefore, statusAfter, channelBefore, channelAfter }`) · `testRunId?`(G3). |
| FR-D6-2 | **"확인 필요" 표시**: `FAILED`·`MISSED`·`HELD` 중 **확인(acknowledge)되지 않은** 예약이 있는 챗봇에 챗봇 목록·대시보드 배지 `확인 필요 n`. 예약 상세에서 `확인함`을 누르면 배지에서 빠진다(`acknowledgedAt`·`acknowledgedBy`). |
| FR-D6-3 | 콘솔 상단(전역)에 **"최근 24시간 예약 실행 결과: 성공 n · 실패 n · 누락 n"** 요약 진입점을 둔다(위치는 ui-designer). 실시간 푸시(웹소켓)는 만들지 않는다 — 화면 진입·주기 조회로 충분하다. |
| FR-D6-4 | **감사 — 예약 관리**: `AuditTargetType`에 **`DeploySchedule`** 을 추가하고 생성(`CREATE`) · 시각/메모 수정(`UPDATE`) · 취소(`STATUS_CHANGE`, summary `"예약 취소"`) · 보류 해제(`STATUS_CHANGE`) · 확인(기록 안 함 — 표시 상태일 뿐)을 기록한다. |
| FR-D6-5 | **감사 — 실행**: 실제로 쓰기가 일어난 실행만 **기존 액션**으로 기록한다 — 복원 `RESTORE`(기존 요약 액션) · 상태 `STATUS_CHANGE` · 채널 `UPDATE`. 주체는 **생성자**(`actorOverride`), summary에 **`[예약 실행 #<id 앞 8자>]`** 접두를 붙인다. 신규 `AuditAction`은 만들지 않는다. |
| FR-D6-6 | **NOOP·FAILED·MISSED·HELD 전이는 감사하지 않는다** — 자산·상태 쓰기가 없고, 시스템 동작이다(No.25 FR-H3-18 "자동 스냅샷·정리 비감사"와 같은 판단). 결과는 예약 행과 서버 경고 로그(FR-0-87)에 남는다. ⚠ 규제 고객이 "실행되지 않은 사실"의 감사를 요구하면 No.45에서 재검토. |
| FR-D6-7 | 이메일·SMS·웹훅·메신저 알림은 **만들지 않는다**(FR-0-86, §9). |

## 7. 수용기준 (AC)

### AC-D1. 예약 생성

- **AC-D1-1** Given `DRAFT` 챗봇, When `PUBLISH(enableWebChannel=true)`를 `now+1일`로 생성하면, Then `201`이고 상태 `PENDING`, 감사에 `DeploySchedule CREATE` 1건이 있다.
- **AC-D1-2** Given `ACTIVE` 챗봇, When `PUBLISH`를 생성하면, Then `DEPLOY_SCHEDULE_PRECONDITION_FAILED`다.
- **AC-D1-3** Given 버전 v5 미리보기 후 다른 사용자가 FAQ 1건 수정, When `previewedContentHash`로 `RESTORE_VERSION`을 생성하면, Then `409 RESTORE_PREVIEW_STALE`이고 행이 생기지 않는다.
- **AC-D1-4** Given v31 복원 예약(10/1)이 `PENDING`, When v30 복원 예약(11/1)을 생성하면, Then 새 예약의 `expectedContentHash` = **v31의 대상 해시**다(J-5).
- **AC-D1-5** Given 대상 버전에 무결성 blocker, When 생성하면, Then 거부된다. Given 해당 챗봇에 `RUNNING` TC 실행, When 생성하면, Then **생성은 성공**하고 경고에 진행 중 작업이 표시된다(FR-D2-3).
- **AC-D1-6** Given 오프셋 없는 `scheduledAt: "2027-01-15T09:00:00"`, When 생성하면, Then `400 VALIDATION_FAILED`다. `"…T09:00:30+09:00"`은 `09:00:00+09:00`(= `00:00:00Z`)로 저장된다.
- **AC-D1-7** Given `now+4분` / `now+91일`, When 생성하면, Then 둘 다 `DEPLOY_SCHEDULE_INVALID_TIME`이다.
- **AC-D1-8** Given 같은 챗봇에 09:00 예약, When 09:00:40(같은 분)으로 생성하면, Then `DEPLOY_SCHEDULE_INVALID_TIME`이다. 09:01은 성공한다.
- **AC-D1-9** Given 활성 예약 5건, When 6번째를 생성하면, Then `DEPLOY_SCHEDULE_LIMIT_EXCEEDED`다.
- **AC-D1-10** Given `ACTIVE` 챗봇, When `acknowledgeActive` 없이 `RESTORE_VERSION`을 생성하면, Then `400`이다.

### AC-D2. 실행 · 선점 · 순서

- **AC-D2-1** ★ Given `PENDING` 예약 1건과 **실행 엔진 인스턴스 2개**(같은 DB), When 두 인스턴스가 동시에 tick을 돌리면, Then 동작은 **정확히 1회** 실행되고 `BEFORE_RESTORE` 백업도 1건이다(FR-0-81).
- **AC-D2-2** ★ Given v5 `RESTORE_VERSION` 예약이 실행됨, When 현재 `contentHash`를 계산하면, Then v5의 해시와 같고 상태 `SUCCEEDED(APPLIED)`, `resultSummary.backupVersionNo`가 존재한다.
- **AC-D2-3** Given `PUBLISH(enableWebChannel=true)` 실행, When 공개 대화 API를 호출하면, Then **즉시 `200`**이다(캐시 대기 없음). 실행 전에는 `403 CHATBOT_NOT_PUBLISHED`였다.
- **AC-D2-4** Given `PUBLISH(enableWebChannel=true)` 중 채널 쓰기에서 오류를 주입, When 실행하면, Then 챗봇 상태도 `DRAFT` 그대로다(원자성, FR-D1-3).
- **AC-D2-5** Given `SET_WEB_CHANNEL(false)` 실행, When 다음 공개 요청을 보내면, Then `403 CHANNEL_DISABLED`다.
- **AC-D2-6** Given 같은 챗봇에 08:55 복원 · 09:00 공개 예약이 모두 도래(서버가 08:50~09:02 다운 후 기동), When tick이 돌면, Then **08:55 → 09:00 순서**로 실행된다.
- **AC-D2-7** Given 이미 대상과 같은 상태, When 실행하면, Then `SUCCEEDED(NOOP)`이고 **감사·백업이 생기지 않는다**.
- **AC-D2-8** Given 실행 엔진이 tick 도중 예외, When 다음 tick이 되면, Then 엔진은 계속 동작한다(타이머 생존).
- **AC-D2-9** Given 예약이 없는 상태, When tick 1회의 DB 쿼리를 계측하면, Then 조회 1건(인덱스 사용)이다.

### AC-D3. 상태 변경 · misfire · 재시도 · 보류

- **AC-D3-1** ★ Given `RESTORE_VERSION` 예약 생성 후 FAQ 1건 수정, When 실행 시각이 되면, Then **자산이 변하지 않고** `FAILED: STATE_CHANGED`이며 챗봇에 `확인 필요` 배지가 뜬다(J-4).
- **AC-D3-2** Given 예정 시각 + 7분에 기동(유예 10분), When tick이 돌면, Then 실행되고 `delaySeconds ≈ 420`이다.
- **AC-D3-3** Given 예정 시각 + 11분에 기동, When tick이 돌면, Then **실행되지 않고** `MISSED`다.
- **AC-D3-4** Given `DEPLOY_SCHEDULE_MISFIRE_GRACE_MINUTES=0`, 예정 시각 + 1분 기동, When tick이 돌면, Then `MISSED`다.
- **AC-D3-5** Given 예정 시각에 해당 챗봇 `TestRun` `RUNNING`, When tick이 돌면, Then 예약은 `PENDING`(재시도, `lastTransientReason`)이고, TC가 끝난 뒤 다음 tick에 실행된다.
- **AC-D3-6** Given 진행 중 작업이 재시도 창(15분)을 넘겨 계속됨, When 창이 지나면, Then `FAILED: BLOCKED_TOO_LONG`이다.
- **AC-D3-7** Given DB `BUSY`를 1회 주입, When 실행하면, Then **재시도 대상으로 분류**되어 다음 tick에 성공한다(해시 불일치와 구분 — FR-D3-9).
- **AC-D3-8** ★ Given 08:55 복원(무결성 실패 주입) · 09:00 공개 예약, When 실행 시각이 지나면, Then 복원은 `FAILED`, **공개는 `HELD`(PREDECESSOR_FAILED)** 이고 챗봇은 `DRAFT` 그대로다.
- **AC-D3-9** Given `HELD` 예약, When 새 시각 없이 보류 해제하면, Then `400`이다. 새 시각 + (복원이면) 새 미리보기 해시로 해제하면 `PENDING`이 된다.
- **AC-D3-10** Given 체인 중간 복원 예약을 취소, When 목록을 보면, Then 그 뒤의 복원 예약이 `HELD`다(FR-D3-3).
- **AC-D3-11** Given `RUNNING` 중 프로세스 강제 종료 후 복원이 **커밋된** 상태에서 재기동, When 임대가 만료되면, Then 예약은 `SUCCEEDED(RECOVERED)`다. 커밋 전 종료였다면 `FAILED: INTERRUPTED`이고 자산은 불변이다.
- **AC-D3-12** Given 인스턴스 A가 `RUNNING`(임대 유효) 중 인스턴스 B 기동, When B의 기동 정리가 돌면, Then A의 예약을 **건드리지 않는다**(임대 기반 — 단일 인스턴스 가정 없음).

### AC-D4. 권한 · 감사 · 봉인

- **AC-D4-1** Given VIEWER, When 생성·수정·취소·보류 해제를 호출하면, Then 전부 `403`이고 DB 변경 0건이다. 목록·상세 조회는 `200`이다.
- **AC-D4-2** Given `chatbot:write`만 있는 가상 역할(단위 시험), When `RESTORE_VERSION`을 생성하면, Then `403`이다(`dialogue:write` 필요).
- **AC-D4-3** ★ Given 생성자 계정을 예약 후 `DISABLED`로 변경, When 실행 시각이 되면, Then **실행되지 않고** `FAILED: CREATOR_NOT_AUTHORIZED`다.
- **AC-D4-4** Given 생성자 역할을 EDITOR→VIEWER로 강등, When 실행 시각이 되면, Then AC-D4-3과 같다.
- **AC-D4-5** Given 예약 복원 실행 성공, When 감사로그를 보면, Then `RESTORE` 1건의 주체가 **생성자**이고 summary에 `[예약 실행 #…]`가 있다. `system` 주체 레코드는 없다.
- **AC-D4-6** Given `FAILED`/`MISSED`/`NOOP`, When 감사로그를 보면, Then 해당 실행에 대한 레코드가 **0건**이다(FR-D6-6).
- **AC-D4-7** Given 저장소 전체, When 예약 모듈의 import 그래프·심볼을 검사하면, Then `VersionRestoreApplier`·자산 서비스·`AugmentationModule` 참조 0건, `fetch`/HTTP 클라이언트 0건이다(FR-0-79, NFR-DS2).
- **AC-D4-8** Given 공개 라우트, When `@Public()` 핸들러 수를 세면, Then **정확히 6개**다.
- **AC-D4-9** Given 환경변수 미설정, When 서버를 기동하고 예약을 생성·실행하면, Then 정상 동작한다(FR-0-83).
- **AC-D4-10** Given `packages/dialogue-engine`, When git diff를 확인하면, Then 변경 0건이다.

### AC-D5. No.25 연동

- **AC-D5-1** Given v12를 참조하는 `PENDING` 예약, When 자동 스냅샷이 31건째 생성되어 보존 정리가 돌면, Then **v12는 남아 있다**(FR-D4-1).
- **AC-D5-2** Given v12를 참조하는 활성 예약, When v12 삭제를 요청하면, Then `409 VERSION_REFERENCED_BY_SCHEDULE`이다. 예약 취소 후에는 삭제된다.
- **AC-D5-3** Given 챗봇 영구삭제, When 확인하면, Then 그 챗봇의 `DeploySchedule`이 전부 제거됐고 영구삭제가 예약 때문에 409로 막히지 않는다.
- **AC-D5-4** Given 즉시 복원(기존 컨트롤러 경로), When 이 그룹 적용 전후를 비교하면, Then **동작·응답·감사 주체가 동일**하다(선택 인자 추가의 회귀 없음).
- **AC-D5-5** Given 예약 복원 성공 결과의 "되돌리기" 링크, When 따라가면, Then 백업 버전의 **즉시 복원 미리보기**가 열린다.

### AC-D6. 시간대 · 접근성

- **AC-D6-1** Given `STATS_TIMEZONE=Asia/Seoul`, When 콘솔에서 `2027-01-15 09:00`을 입력하면, Then 저장값은 `2027-01-15T00:00:00Z`이고 목록에 `2027-01-15 09:00 (KST)`로 표시된다.
- **AC-D6-2** Given 서버 OS 시간대가 UTC, When 같은 입력을 하면, Then 저장값이 AC-D6-1과 **같다**.
- **AC-D6-3** Given 키보드만 사용, When 예약을 생성·취소하면, Then 마우스 없이 완료된다. 상태 배지는 텍스트 라벨을 가진다. axe 대비 위반 0건.

## 11. PM 확인이 필요한 항목

| # | 항목 | 왜 PM이 정해야 하는가 | 미확정 시 기본값 |
|---|---|---|---|
| **P-1** | ★ **반영 대상**(쟁점 1) — (a) 예약 복원 · (b) 공개 시작/채널 열기·닫기 · (c) draft/published 분리 중 무엇을 1차로 하는가 | 제품 정의의 핵심. (c)는 No.40과 사실상 같은 일이며 7개 선행 그룹의 설계를 흔든다. (a)+(b)는 실행부가 이미 있어 **신규 자산 쓰기 경로 0**으로 끝난다 | **(a)+(b) 조합**, 동작 3종(`RESTORE_VERSION`·`PUBLISH`·`SET_WEB_CHANNEL`). **(c)는 No.40으로** |
| **P-2** | ★ **준비 편집의 운영 노출 한계를 수용하는가** — (a)로 "운영 중 챗봇의 내용 교체"를 하려면 준비하는 동안(편집 → 버전 저장 → 즉시 원복) 편집이 **운영에 잠시 보인다** | 수용 불가라면 올바른 해법은 No.28 안에 (c)를 넣는 것이 아니라 **No.40을 먼저** 하는 것이다(착수 순서 결정) | **수용**(신규 챗봇 공개·캠페인 복귀·야간 반영은 1차로 충분) + 한계를 콘솔 안내(FR-D7-7)로 명시 |
| **P-3** | **실행 게이트**(쟁점 2) — TC 회귀 검증을 실행 조건으로 걸 것인가 | 실행 전 게이트(G1/G2)는 신규 TC 모드·오케스트레이션·합격 임계가 필요해 범위가 크게 는다. 사후 자동 TC(G3)는 싸지만 새벽 ml-worker 점유가 생긴다 | **G0(정합성 차단) + G0'(준비도 경고)만.** G3는 선택 기능으로 구현하되 **기본 OFF**. G4(자동 롤백) 기각 |
| **P-4** | **예약 이후 상태가 바뀌면**(쟁점 3) — 실행하지 않는가, 강행 옵션을 두는가 | 강행하면 다른 관리자의 편집이 무인 시각에 사라진다(백업은 남음). 엄격하면 장기 예약이 자주 실패한다 | **엄격 — 실행하지 않고 `확인 필요` 표시.** 강행 옵션 없음. 편집 화면에 사전 경고 배너 |
| **P-5** | **misfire 정책**(쟁점 4) | 늦은 실행이 운영 시간대 한가운데서 일어나는 위험 vs 반영 누락 | **유예 10분 이내 지연 실행, 초과 시 `MISSED`**(환경변수로 0~1440분 조정) |
| **P-6** | **재시도**(쟁점 4) | 진행 중 작업·DB 경합을 얼마나 기다릴지 | **일시적 원인만 30초 주기 재시도, 최대 15분.** 영구적 원인은 즉시 실패 |
| **P-7** | **예약 관리 한도**(쟁점 5) | 운영 패턴(캠페인 수·선행 준비 기간)에 따라 달라진다 | 챗봇당 활성 **5건** · 리드타임 **5분** · 최대 **90일** · 같은 챗봇 예약 간 **1분** 간격 · 수정은 시각·메모만 |
| **P-8** | **선행 예약 실패 시 후속 예약 처리** | 보류(fail-stop)는 안전하지만 사람이 풀어야 한다. 독립 실행은 "옛 내용으로 공개" 같은 어긋난 반영을 만든다 | **같은 챗봇의 후속 예약 전부 `HELD`** — 새 시각 입력(복원은 미리보기 재확인) 후 재개 |
| **P-9** | **실행 주체와 권한 재검증** | 퇴사·강등 후에도 예약이 실행되어도 되는가, 감사에 누구 이름이 남는가는 조직 통제 정책이다 | **실행 시 생성자 재검증(불충족 시 실패)** · 감사 주체 = **생성자** + `[예약 실행]` 표기 · 신규 권한 0종 · 취소는 같은 권한의 누구나 |
| **P-10** | **알림 범위**(쟁점 6) | 외부 알림은 새 외부 접촉면(메일 서버·자격증명·폐쇄망)이다 | **콘솔(목록·배지·전역 요약) + 감사로그만.** 외부 알림은 No.41/45 |
| **P-11** | **채널 닫기/열기 예약(`SET_WEB_CHANNEL`) 포함 여부** | `ACTIVE→DRAFT`가 없어 "공개 종료"의 유일한 가역 수단이지만, 카탈로그 문구("반영")보다 넓다 | **포함**(공개 시작과 짝 — 이벤트봇 종료 시나리오) |
| **P-12** | **GPU 필요도 1 확인**(쟁점 7) | 카탈로그 값과 같다 | **1 유지** |

> **쟁점 → P 매핑**: 쟁점 1 = P-1/P-2/P-11 · 쟁점 2 = P-3 · 쟁점 3 = P-4(+J-5 체인·P-8) · 쟁점 4 = P-5/P-6 · 쟁점 5 = P-7 · 쟁점 6 = P-10 · 쟁점 7 = P-12 · 스케줄러 구현(J-3)·시간대(J-12)는 **architect 확정 사항**(PM 확인 불요 — 권고안 제시).
