### 1.2 원본 근거 — "무엇을 요구하는가"

**근거 1 — 카탈로그 원문**(92행): 위 T-1.

**근거 2 — "재인덱싱"의 두 가지 해석**:

| 해석 | 뜻 | 필요한 것 | 우리 GPU |
|---|---|---|---|
| **(가) 외부 RAG가 재인덱싱** | 바뀐 문서를 외부 RAG 적재 API에 다시 넣으면, 외부 RAG가 청킹·임베딩·키워드 추출을 다시 한다 | 수집기 + 변경 감지 + 적재 API 호출 | **0** |
| (나) 우리가 재인덱싱 | 우리가 문서를 잘라(청킹) 임베딩해 우리 색인에 넣는다 | 문서 저장소 + 청킹 + 임베딩(ml-worker) + 벡터 검색 + **답변 생성 LLM** | 임베딩 4 · 생성 7 |

카탈로그 GPU 4는 (나)의 "임베딩만"을 가정한 값으로 보인다. 그런데 우리 2단계 답변은 **외부 RAG가 검색과 답변 생성을 함께** 한다(`rag-http.client.ts` 43~55행 — 질문만 보내고 답을 받는다). 우리가 색인을 따로 만들어도 **외부 RAG는 그 색인을 쓰지 않는다**. 즉 (나)는 "재인덱싱"이 아니라 **RAG 엔진을 새로 만드는 것**이다(No.30 PM 결정 "자체 RAG 엔진을 만들지 않는다" — ADR-0022 12행 — 도 함께 번복).

**근거 3 — 인접 기능과의 경계**:

| 축 | **No.30 외부 RAG 연동**(구현됨) | **No.43 크롤링/동기화**(이 문서) | **No.48 수동 업로드**(종결) | **No.41 업무 자동화**(구현됨) |
|---|---|---|---|---|
| 무엇 | 질문 → 외부 RAG 답변(읽기) | 사내 사이트 → 변경분 → 외부 RAG 적재(쓰기) | 관리자가 파일을 직접 올림 | 이벤트 → 웹훅 발송 |
| 외부 RAG 경로 | 질의·상태·메타데이터 3개 | **+ 적재 · 작업 조회**(권고) | (만들지 않음) | — |

| **(a) 수집·변경 감지 + 외부 RAG 적재 API로 자동 전송** ★ | 사이트 방문 · 바뀐 페이지 골라내기 · **바뀐 것만 적재 API로 보내기** · 작업 상태 추적 · 이력 | 파싱·청킹·임베딩·검색·답변(지금과 같음) | ADR-0022 §5의 **"인입을 만들지 않는다"만** 연다(적재·작업 조회 2경로 추가). **수동 업로드 화면(No.48)은 여전히 만들지 않고**, 삭제·초기화·전역 설정·프롬프트 봉인은 **그대로** | 0 | **권고** — 원문 "자동 최신화·변경분만"을 **가장 작은 변경으로** 충족. 외부 RAG가 이미 가진 적재 기능을 그대로 쓴다(메모: PM이 2026-09-22에 "외부 RAG의 인입 기능을 그대로 쓰는 방향이 유력"이라 언급 — 설계서 652행) |

| (c) 외부 RAG의 크롤링 기능을 예약·실행만 | 예약 시각에 "크롤링 시작" 호출 · 결과 표시 | 수집·변경 감지·적재 전부 | 없음(외부 기능 호출만) | 0 | **현재 불가** — 외부 RAG 명세에 크롤링 기능이 **없다**(§1.3.2 마지막 행). 외부 RAG 쪽에 기능이 생기면 가장 깔끔하다 → 재검토 트리거로 남김 |
| (d) 수집·변경 감지·보고만 | 사이트 방문 · 바뀐 페이지 목록 · "외부 RAG에 다시 올릴 파일" 묶음 내려받기 | 운영자가 외부 RAG에서 **직접** 올림 | **없음**(ADR-0022 완전 불변) | 0 | 대안 — 충돌은 0이지만 **"자동 최신화"가 되지 않는다**(사람이 매번 올려야 함). PM이 봉인을 절대 열지 않겠다면 이 안 |

→ **판단 J-1**: **(a)**. 사용자가 충돌을 안내받고도 도입을 택한 취지를 "외부 RAG 지식베이스를 **사람 손 없이** 최신으로 유지"로 해석한다. 그 최소 구현이 (a)이며, 봉인의 **파괴적 부분(삭제·초기화·전역 설정·프롬프트)은 한 글자도 열지 않는다**.

### 1.7 ★ 선결 쟁점 3 — 사라지거나 짧아진 페이지를 어떻게 하나 (P-3)

외부 RAG는 **문서 1건만 지우는 기능이 없고**(§1.3.2), 재적재로 짧아진 문서는 **옛 조각(청크)이 남는다**. 그래서 이 쟁점은 "봉인을 얼마나 여느냐"와 같다.

| 선택지 | 동작 | 봉인 영향 | 판정 |
|---|---|---|---|
| **(a) 자동 삭제 없음 — "정리 필요" 표시 + 안내** ★ | 두 번 연속 없어진 페이지(404·410·사이트맵에서 빠짐)와 크게 짧아진 페이지를 **"정리 필요"로 표시**. 소스 화면에 "외부 RAG에서 이 서브카테고리를 정리한 뒤 '전체 다시 적재'를 누르세요" 안내 · "전체 다시 적재" = 소스의 모든 페이지를 다시 보냄(삭제는 운영자가 외부 RAG에서) | **불변** — 삭제 경로 금지 검사 그대로 | **권고** — 봉인을 최소로 연다. 옛 내용이 **잠시 남는 위험**은 화면 경고로 드러낸다 |
| (b) 소스 전용 서브카테고리 **재구축**을 우리가 실행 | "정리 필요"가 쌓이면 관리자 확인 후 `DELETE`(회사·카테고리·서브카테고리 **3개 모두 필수** — 회사 단위 삭제 불가하게 강제) → 전체 재적재 | 삭제 경로 1개 허용 — 금지 검사를 "3개 필드 모두 채운 호출 1곳만 허용"으로 바꿈 | 2차 권고 — 재구축 동안(수 시간) **그 소스 답변이 비는 구간**이 생긴다. 삭제 성패를 구분 못 하는 문제(418행)도 풀어야 함 |
| (c) 사라진 페이지를 "빈 문서"로 덮어쓰기 | 같은 이름의 거의 빈 파일로 재적재해 내용을 지움 | 불변 | 비권고 — 옛 청크가 남는 규칙(296~299행) 때문에 **실제로 지워지지 않는다** |

### 1.8 ★ 선결 쟁점 4 — 언제 실제로 반영하나 (P-4)

외부 RAG의 문서는 **버전이 없고**, 적재하는 순간 그 스코프를 쓰는 **모든 챗봇의 답변이 바로 바뀐다**(No.40 환경 분리의 "운영에 보이지 않는 준비"가 적용되지 않는다).

| 선택지 | 동작 | 판정 |
|---|---|---|
| **(a) 첫 동기화만 미리보기(드라이런) 후 확인 → 그다음부터 자동 반영** ★ | 새 소스의 첫 실행은 **수집·변경 감지만** 하고 "적재할 페이지 N개 · 제외 M개 · 개인정보 마스킹 K건" 목록을 보여 준다. 관리자가 "적재 시작"을 누르면 그때 보낸다. 이후 예약 실행은 자동 반영. 소스 설정(범위·스코프)을 바꾸면 다시 미리보기 | **권고** — 범위를 잘못 잡아 **엉뚱한 페이지 수천 개가 들어가는 사고**를 첫 회에 막고, 이후에는 사람 손이 필요 없다 |
| (b) 매번 관리자 승인 후 반영 | 실행마다 변경 목록을 보여 주고 승인해야 전송 | 안전하지만 "자동 최신화"의 취지가 약해짐 — 규제 업종 고객용으로 **소스별 옵션**(2차) |
| (c) 처음부터 완전 자동 | 등록 즉시 수집·적재 | 비권고 — 범위 실수 비용이 크고 되돌릴 방법(삭제)이 봉인돼 있다 |
| (d) 스테이징용 스코프에 먼저 적재 → 확인 후 운영 스코프로 다시 적재 | 같은 문서를 두 번 적재 | 비권고 — 적재가 느려(143초/4쪽) 비용 2배 · 외부 RAG에 "복사·이름 변경" 기능이 없다 |

→ **판단 J-15(No.40과의 관계)**: 지식베이스는 설문·API 연결·상담 설정처럼 **환경 밖 자원**이다(즉시 반영). 환경 모드 챗봇의 답변 설정 화면에 "지식베이스 동기화는 환경과 무관하게 즉시 반영됩니다" 안내를 둔다.

### 1.9 목적

1. 관리자가 사내 사이트를 **한 번 등록**하면, 정해진 주기로 **바뀐 페이지만** 외부 RAG에 반영되어 챗봇 2단계 답변이 최신 내용을 근거로 한다.
2. 새 외부 출구(크롤러)가 **출구 게이트·SSRF 방어·속도 제한·robots.txt**를 기존 출구와 같은 수준으로 지킨다.
3. 외부 RAG의 **파괴적 기능(삭제·초기화·전역 설정·프롬프트)은 계속 호출할 수 없다**.
4. 수집한 문서 **원문을 우리 DB에 저장하지 않는다**(해시·메타데이터만) — 보존·암호화 부담을 늘리지 않는다.
5. 기능을 끄면(`KB_SYNC_ENABLED=false` · 소스 0개) 시스템 동작이 **바이트 단위로 동일**하다.

### 2.2 사용자 시나리오

**S-1. 사내 규정 게시판 등록 (ADMIN · ★)** 인사팀 규정이 자주 바뀌어 챗봇이 옛 규정을 답하는 문제가 있었다. 관리자가 규정 게시판을 소스로 등록하고, 미리보기에서 312쪽이 잡힌 것을 확인한 뒤 적재를 시작한다. 첫 적재는 밤새 진행되고, 다음 날부터는 매일 새벽 **바뀐 규정 몇 건만** 다시 적재된다.

**S-2. 변경 없는 날 (★)** 예약 실행에서 모든 페이지가 304(변경 없음) 또는 해시 동일로 판정되어 **외부 RAG 적재 0건**, 실행 이력에 "변경 없음 312"만 남는다.

**S-3. 페이지 삭제 (★)** 폐지된 규정 페이지가 이틀 연속 404를 반환하자 "정리 필요 1건"으로 표시된다. 화면은 "외부 RAG에 이 문서의 옛 내용이 남아 있어 답변에 쓰일 수 있습니다. 외부 RAG에서 해당 서브카테고리를 정리한 뒤 '전체 다시 적재'를 누르세요"라고 안내한다.

**S-4. 범위 실수 방지 (★)** 관리자가 경로 범위를 비워 두고 사내 포털 첫 화면을 시작 주소로 넣었다. 미리보기가 "최대 500쪽 도달 — 범위를 좁히세요"를 보여 주고, 관리자는 적재 전에 범위를 `/hr/`로 좁힌다.

**S-5. 개인정보 포함 페이지 (★)** 부서 연락처 페이지에 직원 휴대전화 번호가 있다. 추출 텍스트에서 번호가 마스킹되어 적재되고, 미리보기에 "마스킹 9건"이 표시된다. 같은 번호가 들어 있는 PDF 파일은 "원본 파일 전달" 옵션이 꺼져 있어 **적재되지 않고** "원본 파일 전달 꺼짐 — 제외"로 표시된다.

**S-6. 외부 RAG 재시작 (운영)** 적재 도중 외부 RAG 서버가 재시작되어 작업 조회가 `not_found`를 돌려준다. 크롤러는 이를 실패로 세지 않고 **해당 문서를 다시 보낸다**(같은 파일 이름이라 덮어쓰기).

**S-7. vLLM 장애 (운영)** 외부 RAG 상태가 `degraded`(vLLM 끊김)이다. 적재 워커는 전송하지 않고 대기하며, 소스 화면에 "외부 RAG 준비 안 됨 — 대기 중"이 표시된다. 챗봇 질의 경로에는 영향이 없다.

**S-8. 거버넌스 모드 고객 (서버 운영자 · ★)** 규제 업종 고객 서버는 거버넌스 모드 ON이다. 크롤 대상 호스트 `intra.example.local`이 출구 허용 목록에 없어 소스 저장 시 "출구 허용 목록에 없는 호스트입니다"로 거부된다. 운영자가 환경변수에 추가한 뒤 등록한다.

**S-9. SSRF 시도 차단 (★)** 사내 페이지 링크 중 하나가 `http://169.254.169.254/…`(클라우드 메타데이터 주소)로 리다이렉트된다. 크롤러는 리다이렉트 대상 주소를 재검증해 **절대 차단 대역**으로 판정하고 그 링크를 건너뛴다.

**S-10. 기능 미사용 (★)** `KB_SYNC_ENABLED`가 꺼져 있거나 소스가 0개인 서버는 기존 동작·시험·응답이 **바이트 단위로 같다**.

**S-11. 폐쇄망 구축형 (서버 운영자)** 고객사 내부망에 외부 RAG 서버와 챗봇 서버가 함께 설치되어 있다. 운영자가 `KB_INGEST_TRANSPORT_ACK=INTERNAL_NETWORK`로 전송 전제를 확인하면 적재가 켜진다. 이 값이 없으면 소스 등록·미리보기는 되지만 "적재 시작"이 비활성화된다.

**S-12. 거버넌스 모드를 나중에 켠 서버 (ADMIN · ★ — 사용자 결정 2026-09-28)** 거버넌스 모드를 켜기 전에 개인정보 마스킹을 끈 채 저장해 둔 소스가 있다. 운영자가 모드를 켠 뒤 관리자가 "적재 시작"을 누르면 "거버넌스 모드에서는 개인정보 마스킹을 끌 수 없습니다. 소스를 수정해 마스킹을 켜 주세요."가 배너로 표시되고 실행이 만들어지지 않는다. 예약 실행도 이 소스만 건너뛴다. 이미 외부 RAG에 들어간 문서는 그대로 둔다. 관리자가 소스를 수정해 마스킹을 켜면 적재 승인이 해제되므로, 미리보기를 다시 실행해 결과를 확인하고 적재를 승인하면 다시 동작한다(FR-KB6-9).

| FR-KB6-9 | ★ **거버넌스 적재 차단 — 실행 시작·적재 제출 시점 재검사 [사용자 결정 2026-09-28]**: 거버넌스 모드 ON에서 ① 개인정보 마스킹이 꺼진 소스 또는 ② 서버 허용 없이 원본 파일 전달이 켜진 소스(모드를 켜기 전에 저장해 둔 경우 등)는 저장 거부(FR-KB6-2·3)에 더해 아래 시점에도 막는다. 근거: 원문 유출은 되돌릴 수 없고 외부 RAG에는 문서 1건 삭제 API가 없다(C-2). (나) **적재 제출 직전** — 이미 진행 중이던 실행은 외부 RAG로 보내기 전에 실행 전체를 `CANCELLED`로 끝내고 실패 코드(위 2종 중 해당 코드)를 남기며, 대기 중인 적재 작업을 모두 취소하고 감사 `[적재 차단]` 1건을 남긴다. (다) **이미 적재된 문서는 건드리지 않는다**(외부 삭제 호출 0 · 문서 기록의 해시·적재 상태 불변). 소스를 수정해 마스킹을 켜거나 원본 파일 전달을 끄면 다시 동작한다 — **[정합 2026-09-29 — PQ-2] 단 이 두 옵션은 바꾸면 적재 승인이 해제되는 설정(범위·스코프와 같이 `configVersion`을 올리는 필드 — FR-KB5-3 · EX-KB-14)이므로, "다시 동작"은 미리보기부터 다시 실행하고 그 결과로 적재를 승인해야 동기화(적재)가 재개된다는 뜻이다(수정 전에 끝난 미리보기로는 승인할 수 없다 · 승인 전 예약 실행은 미리보기만 · 이번 예약을 건너뛴 소스의 예약은 다음 예약 시각까지 대기하고 수동 미리보기는 즉시 가능). 반면 일시중지→재개와 이름·주기·인증·요청 간격 변경은 승인을 유지한다(AC-KB6-10).** (라) 문구 — 마스킹: "거버넌스 모드에서는 개인정보 마스킹을 끌 수 없습니다. 소스를 수정해 마스킹을 켜 주세요." · 원본 파일: "거버넌스 모드에서는 서버 설정 없이 원본 파일 전달을 쓸 수 없습니다. 소스를 수정해 원본 파일 전달을 꺼 주세요. 꼭 필요하다면 서버 운영자에게 허용을 요청해 주세요." 콘솔은 적재 승인 화면에서 이 오류를 배너로 표시한다. |

### 11.1 AskUserQuestion용 쉬운 문구(핵심 4건)

**Q1. 사내 문서를 외부 RAG에 넣는 일을 누가 할까요?** (지난 9월 22일에 "문서 넣기·지우기는 우리 시스템에서 하지 않는다"로 정했는데, 자동 최신화를 하려면 이 중 일부를 다시 열어야 합니다)
- ① **우리 시스템은 사내 사이트를 돌아보며 바뀐 페이지만 골라서, 외부 RAG의 '문서 넣기' 기능으로 보내기. 파일 직접 올리기 화면과 지우기·초기화는 계속 만들지 않음 (추천)**
- ② 우리 시스템 안에 문서 보관함과 검색용 색인(임베딩)을 따로 만들기 — 사실상 RAG를 새로 만드는 큰 작업이고 GPU가 필요
- ③ 외부 RAG에 자체 수집 기능이 있으면 그걸 정해진 시각에 실행만 시키기 — 현재 명세에는 그런 기능이 없음
- ④ 바뀐 페이지 목록만 보여 주고, 외부 RAG에 넣는 건 지금처럼 담당자가 직접 — 지난 결정은 그대로지만 자동 최신화는 안 됨

**Q2. 무엇을 수집할까요?**
- ① **사내 웹 페이지 + 사이트맵(사이트 전체 주소 목록) + 페이지에 걸린 PDF·워드·엑셀·파워포인트 파일. 로그인 없이 보이거나 고정 인증값으로 열리는 곳만 (추천)**
- ② ①에 더해, 아이디·비밀번호로 로그인해야 보이는 사이트까지
- ③ ①에 더해, 화면을 스크립트로 그리는 최신 웹앱까지(브라우저 프로그램 설치 필요)
- ④ ①에 더해, 파일 서버·공유 드라이브(셰어포인트 등)까지

**Q3. 사이트에서 없어지거나 내용이 줄어든 페이지는 어떻게 할까요?** (외부 RAG에는 문서 1개만 골라 지우는 기능이 없습니다)
- ① **자동으로 지우지 않고 "정리 필요"로 표시해 알려 주기. 정리는 담당자가 외부 RAG에서 (추천)**
- ② 그 사이트용 영역을 통째로 지우고 전부 다시 넣는 기능을 우리 시스템에 만들기 — 다시 넣는 몇 시간 동안 그 내용으로는 답을 못 함
- ③ 빈 문서로 덮어쓰기 — 외부 RAG 특성상 옛 내용이 실제로는 남음

**Q4. 수집한 내용을 언제 실제 챗봇 답변에 반영할까요?** (외부 RAG에 넣는 순간 그 범위를 쓰는 모든 챗봇 답변이 바로 바뀝니다)

- ② 매번 바뀐 목록을 관리자가 확인·승인해야 반영
- ③ 등록하자마자 처음부터 완전 자동 반영
- ④ 시험용 영역에 먼저 넣어 확인한 뒤 운영 영역에 다시 넣기 — 넣는 시간이 두 배
