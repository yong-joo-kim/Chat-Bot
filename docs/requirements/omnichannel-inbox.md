### 1.2 원본 근거 — "무엇을 요구하는가"

**근거 1 — 카탈로그 원문**(`기능요구사항.md` 91행):
> "옴니채널 통합 인박스 | 여러 채널(웹/카카오톡/전화 등)에 걸친 **동일 고객 대화를 하나의 스레드로 통합**, **채널 전환 시에도 컨텍스트 유지** | GPU 2 | ○ | ○ | 11번(다양한 채널 제공)은 '배포'이고 이건 **'상담원 관점 통합 뷰'**"

→ 요구는 셋이다: ① **동일 고객 판별**(무엇으로 같은 사람인지 아는가) ② **하나의 스레드**(상담원이 한 곳에서 본다) ③ **채널 전환 시 컨텍스트 유지**(다음 채널에서 처음부터 다시 묻지 않는다). 비고가 "상담원 관점 통합 뷰"로 **관점을 못 박았다** — 봇이 채널을 넘나들며 기억하는 것(고객 관점 연속성)은 원문의 핵심이 아니다(J-8).

**근거 2 — 채널 현실(코드)**: 8개 채널 중 **WEB 1개만 종단 구현**이고 나머지 7개는 "설정만 저장"이다(§1.3.1). 카카오톡 등을 실제로 붙이려면 ADR-0011 맥락(12행)이 말한 세 전제 — **플랫폼 계정·자격증명, 공개 HTTPS 수신 주소, 플랫폼 심사** — 가 필요하고, 이 중 어느 것도 지금 없다. → **1차에서 "여러 채널"은 WEB + 사람이 기록하는 채널(전화·이메일·방문) + 시험용 가상 채널로 채운다**(J-1).

| (c) (a) + **카카오톡 실연동**(오픈빌더 스킬 서버) | 카카오가 우리 서버로 메시지를 보내고 봇이 답함 | 카카오 비즈 채널·오픈빌더 계정·심사 · **공개 HTTPS 주소** · 자격증명 저장 ADR | **9** | 2차 — 전제 3개가 지금 없다(ADR-0011 12행). ⚠ 규격 미확인(조사 한계) |
| (d) (a) + **범용 서버 간 "API 채널"** | 고객사 앱·키오스크·자체 중계 서버가 API 키로 메시지를 넣는 범용 입구 | 고객사 개발 | **9** | 2차 — 인증 방식(API 키 발급·회전)·레이트리밋 설계가 새로 필요 |

→ **판단 J-1**: 1차 = **(b)**. 외부 채널 실연동은 **"자격증명 저장 ADR + 공개 파이프라인 채널 매개변수화 + 어댑터 1개"** 가 한 묶음이며 **실제 계정이 생기는 시점**에 2차로 착수한다(첫 후보 카카오톡 — 국내 CX 비중).

### 1.5 ★ 선결 쟁점 2 — 같은 고객을 어떻게 알아보나 (P-2)

| 방식 | 내용 | 오병합 위험 | 개인정보 | 판정 |
|---|---|---|---|---|
| **(a) 로그인 연동 서명 토큰** ★ | 고객사 홈페이지가 로그인한 회원에 대해 **서명한 짧은 토큰**(회원 번호 + 만료)을 위젯에 넘긴다. 서버는 서명을 확인하고 회원 번호의 **해시**로 고객을 찾는다 | 낮음(서명 위조 불가 · 호스트 책임) | 해시만 저장(+선택 표시 이름) | **권고** — 로그인 고객에 한해 자동 통합 |
| (b) 서명 없는 외부 ID | 같은 방식이지만 서명 없이 ID만 | **높음**(누구나 남의 ID를 넣어 남의 스레드에 끼어듦) | 동일 | 기각(C-2) |
| (c) 전화번호·이메일 해시 자동 병합 | 폼에 입력된 연락처가 같으면 같은 고객 | 중간(가족 공용 번호·오타·남의 번호 입력) | **폼 원문을 해시 목적으로 처리** — 로그는 마스킹본뿐이라 원문 접근 지점이 새로 생김 | 2차 — "제안만 하고 상담원이 확인" 형태로 |
| **(d) 상담원 수동 연결·분리** ★ | 상담원이 "이 대화는 저 고객"이라고 직접 연결 · 잘못이면 분리 | 사람 판단(감사로 추적) | 추가 없음 | **권고(보조)** — 익명 대화·전화 기록을 고객에 붙이는 유일한 방법 |

→ **판단 J-5**: 1차 = **(a) + (d)**. 토큰이 없는 방문자는 **지금과 똑같이 익명**이다(세션 단위). "연결"은 데이터 복사가 아니라 **연결 행**이므로 분리하면 원상태로 돌아간다(J-13).

### 1.6 ★ 선결 쟁점 3 — 인박스를 어디에, 무엇을 담나 (P-3)

| 축 | (a) 기존 상담 콘솔에 "고객 이력" 패널만 추가 | **(b) 전역 통합 인박스 화면 신설 + 기존 콘솔 연결** ★ | (c) 기존 콘솔을 인박스로 대체 |
|---|---|---|---|
| 여러 챗봇 한 목록 | ❌(챗봇 선택기 유지) | ✅(참여 챗봇 전체) | ✅ |
| 스레드 상태·담당·태그 | ❌ | ✅ | ✅ |
| No.24 화면·시험 영향 | 소폭 | **추가만**(기존 화면 불변 + 고객 카드 링크) | 대규모 재작성 |
| 판정 | 카탈로그 "하나의 스레드" 미충족 | **권고** | 회귀 위험 |

**담는 대상**(같은 P-3의 하위 결정 — 권고):
- **목록에 뜨는 것**: "사람이 볼 일이 생긴" 스레드만 — 상담 시작 · 경고 단계 도달(챗봇 설정으로 선택) · 수동 기록 · 상담원이 직접 연 스레드. **봇이 혼자 잘 처리한 대화는 목록에 띄우지 않는다**(소음 방지 — 모니터링은 No.24).
- **스레드 안에서 보이는 것**: 그 고객에 연결된 **모든 대화**(봇 구간 포함 · 마스킹본) + 상담 + 수동 기록 + 메모.

### 1.7 ★ 선결 쟁점 4 — 채널이 바뀌면 무엇을 이어가나 (P-4)

| 선택지 | 누가 이어받나 | 엔진·봉투 | 새 저장소 | 판정 |
|---|---|---|---|---|
| **(a) 상담원 화면에서 이어가기** ★ | 상담원 — 새 채널 상담에 **이전 대화 이력 · 고객 카드(규칙 기반 요약) · 상담 메모**가 함께 뜬다 | 변경 0 | 고객·연결·메모 | **권고** — 카탈로그 "상담원 관점 통합 뷰" 충족 |
| (b) (a) + **봇이 이전 폼 값을 기억** | 봇 — 식별 고객이 다른 채널에서 오면 이전 슬롯 값을 봉투에 미리 채움 | 봉투·엔진·재검증 변경 | **고객별 슬롯 원문 서버 보관**(새 원문 저장소 — ADR-0013 충돌) | 2차 — No.34와 함께. 챗봇마다 슬롯 id가 달라 **같은 챗봇 안**에서만 의미 |
| (c) (a) + **AI 대화 요약** | 상담원 — 요약문 | 0 | 요약문 | 2차 — 생성형(GPU/외부 LLM · 옵션 AI) |
| (d) 위젯에 **지난 대화 복원** | 최종 사용자 | 위젯·공개 표면 | 이력 반환 | 2차 — 식별이 곧 **이력 열람 권한**이 되어 보안 등급이 바뀜(ADR-0009 트리거 ③) |

→ **판단 J-8**: 1차 = **(a)**. "고객 카드"는 텍스트 생성 없이 **사실만** 모은다: 연결된 대화 수·채널·챗봇 · 최근 대화 시각 · 최근 매칭 의도/FAQ 이름 · 미응답 수 · 상담 이력(결과·종료 사유) · 설문 완료/부정 평가 여부 · 태그 · 최근 메모.

### 1.8 선결 쟁점 5 — 권한 · 감사 · 거버넌스 (P-5 · P-8 · P-10)

- **가시성**: `cs:read` 보유자(AGENT·EDITOR·ADMIN)는 **인박스에 참여한 챗봇 전체**의 스레드를 본다(전역 역할 — 챗봇별 제한은 멀티테넌시 그룹 · T-6). 스레드가 여러 챗봇에 걸치면 **참여하지 않은 챗봇의 대화는 스레드에 표시하지 않는다**(J-11).
- **처리**: 담당 지정·상태 변경·태그·메모·수동 기록·연결/분리 = `cs:write`. 태그 목록 관리·식별 고객끼리의 병합 되돌리기 = ADMIN(서비스 재검증 — 강제 인수 선례). 식별 비밀 참조 지정 = `security:write`(신뢰 경계 — No.26/41 선례).
- **감사**: 연결·분리·병합·담당 변경·상태 변경·태그 목록 변경·설정 변경 = 감사(커밋 후 · ADR-0016). 메모·기록 작성 = 감사 아님(업무 데이터 — 작성자·시각은 행에 남음).
- **열람 감사**: 인박스 목록·스레드 상세·고객 타임라인 = `VIEW` 닫힌 목록 편입(거버넌스 모드 ON에서만 기록 — ADR-0040 규약).
- **거버넌스**: 새 저장소 3종(고객 식별 해시·표시 이름 / 수동 기록·메모 본문 / 연결 이력)을 **데이터 지도에 표시** · 텍스트는 **마스킹 → 암호화(모드 ON) → 보존기간 소거** · 고객 행은 마지막 활동 후 보존기간이 지나면 **식별 정보 소거**(수치·연결 이력 메타는 유지).

### 1.9 선결 쟁점 6 — 하위 호환 · 공개 표면 (J-12 · J-14)

- **인박스를 켜지 않은 챗봇**(기본 꺼짐)과 **식별 토큰을 보내지 않는 위젯**은 공개 대화·상담·통계·설문·평가·업무 자동화 결과가 **바이트 단위로 동일**하다.
- **`@Public()` 8 유지**(1차): 식별 토큰은 기존 `POST …/messages` 요청의 **헤더**로 받는다(상담 토큰 헤더 선례 — ADR-0011 갱신 142행). 새 공개 경로 0.
- **위젯 변경**: 호스트가 토큰을 넘길 **입력 1개**(임베드 속성 또는 JS 호출)와 헤더 전송만. 토큰이 없으면 요청 바이트 불변.
- **엔진·봉투·ml-worker 변경 0** · 봉투 `CONVERSATION_STATE_VERSION` 불변.
- 2차 외부 채널 웹훅은 **채널마다 `@Public()` +1**(서명 검증·전용 버킷·Origin 가드 제외 사유를 ADR로).

### 1.10 목적

1. 로그인한 회원이 여러 챗봇·여러 사이트·여러 번에 걸쳐 나눈 대화를 **상담원이 한 고객 스레드로** 본다.
2. 전화·이메일·방문처럼 시스템 밖에서 일어난 응대도 **같은 스레드에 기록**해, 다음 상담원이 처음부터 다시 묻지 않는다.
3. 상담원은 **한 인박스**에서 여러 챗봇의 "볼 일이 생긴" 고객을 상태·담당·태그로 관리한다.
4. 채널이 바뀌어도 **고객 카드와 이력**이 따라와 상담이 이어진다(봇 동작은 바뀌지 않는다).
5. 새로 저장하는 고객 정보는 **해시·마스킹·암호화·보존 파기·열람 감사**를 처음부터 받고, 기능을 쓰지 않는 설치는 **동작이 바이트 단위로 동일**하다.

### 2.2 사용자 시나리오

**S-1. 로그인 회원 자동 통합 (★)** 쇼핑몰이 "주문 도우미" 챗봇과 "회원 혜택" 챗봇 두 개를 운영하고 둘 다 인박스에 참여시켰다. 회원 A가 오전에 주문 도우미, 오후에 모바일 웹의 회원 혜택 챗봇과 대화한다. 두 페이지 모두 로그인 상태라 서명 토큰이 전달되어, 상담원이 인박스에서 A의 스레드를 열면 두 대화가 시간순으로 함께 보인다.

**S-2. 채널이 바뀐 상담 (AGENT · ★)** 회원 A가 웹에서 환불을 물었다가 연속 미응답으로 상담원 김상담이 개입해 계좌 확인을 안내하고 종료했다. 다음 날 A가 콜센터로 전화한다. 전화를 받은 이상담이 인박스에서 A의 회원 번호를 입력해 스레드를 찾으면 **고객 카드**("대화 2건 · 최근 의도 환불 문의 · 상담 1건(상담원 종료) · 메모: 계좌 확인 안내함")가 보인다. 통화 뒤 이상담은 **수동 기록(전화)**에 "계좌 재확인 완료, 3일 내 환불"을 남기고 상태를 **보류(해제: 3일 뒤)**로 둔다.

**S-3. 익명 방문자를 고객에 붙이기 (AGENT)** 로그인하지 않은 방문자가 웹에서 "어제 전화한 사람인데요, 주문번호 1234"라고 말한다. 상담원은 대화 보기에서 이 세션을 **고객 A에 연결**한다. 몇 분 뒤 다른 사람이었음을 알고 **분리**하자 스레드는 원래대로 돌아가고, 두 동작은 감사로그에 남는다.

**S-4. 오병합 방지 (★)** 상담원이 식별 고객 A의 스레드를 식별 고객 B에 병합하려 하자 "서로 다른 로그인 회원은 합칠 수 없습니다"로 거부된다(서명 식별은 틀릴 수 없으므로 병합이 필요하다면 회원 정보 문제다).

**S-5. 토큰 위조 시도 (★)** 누군가 개발자 도구로 다른 회원 번호가 든 토큰을 만들어 보낸다. 서명이 맞지 않아 대화는 **익명으로 정상 응답**되고, 인박스 설정 화면에 "최근 24시간 서명 불일치 17건" 경고가 뜬다. 공격자에게는 아무 차이도 보이지 않는다.

**S-6. 시뮬레이션 시연 (EDITOR)** 카카오톡 계약 전, 영업 시연을 위해 **시험 고객**을 만들고 가상 채널 "카카오톡"으로 "배송 언제 와요?"를 넣는다. 봇 답이 스레드에 "시뮬레이션 · 카카오톡" 배지와 함께 쌓인다. 이어서 같은 시험 고객에게 웹 시뮬레이션과 전화 기록을 넣어 "채널이 바뀌어도 한 스레드"를 보여 준다. 대시보드 통계·질문 순위·학습현황은 변하지 않는다.

**S-7. 여러 챗봇 인박스 (AGENT)** 상담원은 챗봇마다 콘솔을 바꿔 가며 보던 것을 인박스 한 화면에서 "열림 · 내 담당 · 태그 [환불]"로 거른다. 참여하지 않은 "사내 복지" 챗봇의 대화는 어떤 스레드에도 보이지 않는다.

**S-8. 동시 상담 (★)** 회원 A가 두 챗봇에서 동시에 상담 개입을 받는다(No.24는 챗봇별이라 허용). 스레드에는 "진행 중 상담 2건" 배지가 뜨고 각 항목에서 해당 상담 콘솔로 이동할 수 있다.

**S-9. 기능 미사용 고객 (★)** 인박스 참여를 켠 챗봇이 하나도 없는 설치는 모든 화면·API·통계·대화 응답이 이전과 같다. 위젯이 토큰을 보내도 참여하지 않은 챗봇은 헤더를 읽지 않는다.

**S-10. 보존기간 파기 (운영자)** 거버넌스 모드에서 인박스 텍스트 보존 180일 · 고객 식별 정보 365일로 정했다. 파기 잡이 지난 기록·메모 본문을 소거하고, 1년간 활동이 없는 고객의 표시 이름과 식별 해시를 지운다(스레드 수치·연결 이력 메타데이터는 남는다). 데이터 지도에 "고객 식별 정보 · 해시 · 암호화 · 보존 365일"이 표시된다.

| FR-OC4-6 | **담당**: 스레드당 담당 1명(없을 수 있음). "가져가기"(담당 없음일 때 · CAS) · "지정"(`cs:write` — 대상은 `cs:write` 보유 활성 사용자) · "놓기". 담당 변경 = 감사. 상담원이 인박스에서 상담을 시작하면 담당이 없을 때 그 상담원이 담당이 된다. 스레드 담당과 상담 담당(`HandoffSession.assignedUserId`)은 **별개**다(상담은 상담 잠금 규약 그대로). |
| FR-OC4-7 | **태그**: 전역 태그 목록(이름 ≤20자 · 색 · ≤100개 · ADMIN만 생성·수정·삭제 — 사용 중 삭제는 확인 후 스레드에서 제거) · 스레드당 ≤10개 · 부착/제거 = `cs:write`(감사 아님 — 스레드 이력에 남김). |
| FR-OC4-8 | 목록·요약은 **폴링 갱신**(기본 10초 · 화면 표시 중일 때만) — SSE/WebSocket 미도입(ADR-0036 결정 유지). |

| `InboxEntry` | id · threadId · kind(`NOTE｜RECORD｜SIM_USER｜SIM_BOT｜SYSTEM`) · recordChannel · simulatedChannel · direction · occurredAt · text(마스킹 · 암호화) · authorUserId/Name · textPurgedAt | 원문 | 〃 · 삭제 없음(TEST 고객 삭제 예외) |
| `InboxTag` · 스레드-태그 연결 | name · color | — | 〃 |
| `CustomerMerge` | fromCustomerId · toCustomerId · movedLinkIds · movedEntryIds · mergedBy · revertedAt | 본문 | 〃 |
| `ChatbotInboxSetting`(1:1) | enabled · identitySecretRef · openOnWarning | 비밀 값 | 설정 서비스 1파일 |

**불변**: `ConversationLog` · `HandoffSession` · `HandoffMessage` · `ChatbotHandoffSetting` · 봉투 스키마 · `ChannelType` · `Channel`.

### 5.2 식별 토큰(입력 — 권고)

```
헤더  x-cb-identity: <JWT HS256>
클레임 { sub: string(1~128, 인쇄 가능 ASCII), exp: number(≤ iat+24h), iat: number, name?: string(≤40) }
서명  HMAC-SHA256(OMNI_IDENTITY_SECRET__<REF>, header.payload)
결과  성공 → 고객 키 = HMAC-SHA256(OMNI_CUSTOMER_KEY_SECRET, "<REF>:<sub>") → Customer 조회/생성 → CustomerLink 1회
      실패 → 익명(응답 불변) + 사유 계수(SIGNATURE｜EXPIRED｜MALFORMED｜SECRET_MISSING｜CONFLICT)
```

### 5.3 출력 — 인박스 목록 행(개요)

```
{ threadId, customer: { alias, displayName?, kind }, status, snoozeUntil?, assignee?: { id, name },
  tags: [{ id, name, color }], lastChannel: { family: 'DEPLOY'|'RECORD'|'SIMULATED', type, label },
  lastChatbot?: { id, name }, linkedConversationCount, activeHandoffCount,
  lastActivityAt, lastEntryPreview /* 마스킹 60자 */ }
```
금지: 전체 `sessionId` · 원문 · 회원 번호 · 토큰.

### 5.4 신규 환경변수(전부 선택)

| 이름 | 기본 | 용도 |
|---|---|---|
| `OMNI_INBOX_ENABLED` | `true` | 전역 기능 스위치(`false`면 인박스 API `404`·식별 검증 0 · 기존 동작 바이트 동일) |
| `OMNI_CUSTOMER_KEY_SECRET` | 없음 | 고객 키 해시 비밀(없으면 식별 꺼짐 — 수동 연결·기록·시뮬레이션은 동작) |
| `OMNI_IDENTITY_SECRET__<REF>` | 없음 | 식별 공간별 토큰 서명 비밀 |

## 7. 수용기준 (AC)

### AC-OC1. 범위 · 회귀

- **AC-OC1-1** ★ Given 참여 챗봇 0개, When 전 시험 세트 실행, Then 결과·응답 바이트·공개 경로 DB 조회 수가 도입 전과 같다.
- **AC-OC1-2** ★ Given 비참여 챗봇, When 위젯이 `x-cb-identity`(유효 토큰)를 보내며 대화, Then 응답 바이트 동일 · 고객·연결 행 0 · 헤더 파싱 0.
- **AC-OC1-3** Given 저장소 전체, When 봉인 spec(`omnichannel-sealing.spec.ts` 가칭 · 기존 `governance`·`handoff` 봉인), Then 통과 · `@Public()` 8 · 엔진·ml-worker 변경 0 · `ConversationLog` 쓰기 호출부 불변.

### AC-OC2. 고객 식별

- **AC-OC2-1** ★ Given 참여 챗봇 X·Y가 같은 식별 참조, When 같은 `sub`의 유효 토큰으로 X·Y에서 각각 대화, Then 고객 1명 · 연결 2건 · 스레드 타임라인에 두 대화.
- **AC-OC2-2** Given X는 참조 R1, Y는 R2, When 같은 `sub`, Then 고객 2명(식별 공간 분리).
- **AC-OC2-3** ★ Given 서명이 틀린/만료된/`alg:none` 토큰, Then 응답 바이트가 토큰 없음과 동일 · 연결 0 · 사유 계수 +1 · 로그·DB에 `sub` 없음.
- **AC-OC2-4** Given 같은 세션에 두 번째 턴, Then 추가 DB 조회·쓰기 0(캐시 적중).
- **AC-OC2-5** Given 같은 세션에 다른 `sub`의 유효 토큰, Then 기존 연결 유지 · `CONFLICT` 계수.
- **AC-OC2-6** ★ Given DB 전체 덤프, Then 원 `sub` 문자열 0건(해시만) · 토큰 0건.
- **AC-OC2-7** Given `OMNI_CUSTOMER_KEY_SECRET` 미설정, Then 기동 정상 · 식별 연결 0 · 설정 화면 "식별 꺼짐(서버 설정 필요)" · 수동 연결·기록은 동작.

### AC-OC3. 연결 · 병합 · 분리

- **AC-OC3-1** ★ Given 익명 세션 S, When 고객 A에 수동 연결 후 분리, Then 스레드 A 타임라인에서 S가 나타났다 사라지고 감사 2건 · `ConversationLog`·`HandoffSession` 행 변경 0.
- **AC-OC3-2** ★ Given 식별 고객 A·B, When 병합, Then `409` · 변경 0.
- **AC-OC3-3** Given 익명 고객 C(연결 2 · 메모 1) → A 병합, When 되돌리기, Then 연결·메모가 C로 복귀 · 감사 2건.
- **AC-OC3-4** Given IDENTITY 연결 세션, When 분리 시도, Then `409`.
- **AC-OC3-5** Given 회원 번호 입력 검색, Then 해시 정확 일치 고객만 · 응답에 회원 번호 없음.

### AC-OC4. 인박스 · 스레드

- **AC-OC4-1** ★ Given 참여 챗봇에서 상담 개입 성공, Then 스레드 열림(익명이면 익명 고객 생성) · 목록에 표시 · 개입 응답 지연 증가 없음(적재 실패 주입 시에도 개입 성공).
- **AC-OC4-2** Given `openOnWarning` 켜짐, When 세션이 경고 단계 도달, Then 스레드 1회 열림(같은 세션 재도달 시 추가 0). 꺼짐이면 0.
- **AC-OC4-3** Given 식별 고객의 종료 스레드, When 새 봇 대화만 발생, Then 상태 종료 유지 · 타임라인에 대화 추가.
- **AC-OC4-4** ★ Given 두 상담원이 동시에 "가져가기", Then 1명만 성공(CAS) · 다른 쪽 `409`.
- **AC-OC4-5** Given 보류(해제 1시간 뒤), When 1시간 경과 후 목록 조회, Then 열림으로 표시.
- **AC-OC4-6** Given 참여 챗봇 X와 비참여 Y 대화가 모두 연결된 고객, Then 스레드에 X 대화만.
- **AC-OC4-7** Given AGENT, Then 인박스 조회·처리 가능 · 태그 목록 변경 `403` · 식별 참조 변경 `403`. VIEWER는 인박스 `403`.
- **AC-OC4-8** Given 타임라인 응답, Then 텍스트는 마스킹본 · 전체 `sessionId`·원문 키 없음(키 집합 정적 검사).

### AC-OC5. 수동 기록 · 시뮬레이션

- **AC-OC5-1** ★ Given 전화 기록 "010-1234-5678로 회신 요청", Then 저장 본문이 마스킹 결과 · 암호화 ON이면 DB 원시 값 `enc:v1:` · 스레드 열림.
- **AC-OC5-2** ★ Given 시험 고객 · 가상 채널 카카오톡 · 메시지 3회, Then 스레드 기록 6건(사용자 3 · 봇 3, 시뮬레이션 배지) · `ConversationLog`·통계·학습 큐·업무 자동화 발송함 **증가 0**.
- **AC-OC5-3** Given 시험 고객을 실제 고객에 병합, Then `409`.
- **AC-OC5-4** Given 시험 고객 삭제, Then 시뮬레이션 기록 삭제 · 감사 1건.

### AC-OC6. 거버넌스 · 감사

- **AC-OC6-1** Given 모드 ON, When 인박스 목록·스레드 상세·고객 검색 조회, Then `VIEW` 감사가 (열람자, 대상, 일)당 1건.
- **AC-OC6-2** ★ Given 인박스 텍스트 보존 30일, When 파기 잡, Then 31일 전 메모·기록 본문 `""` · 행·시각 유지 · 진행 중 스레드도 본문 소거 대상(기록은 종단 개념 없음 — architect 확인).
- **AC-OC6-3** Given 고객 식별 보존 365일 · 마지막 활동 366일 전, Then 표시 이름·고객 키 해시 소거 · 스레드 수치 유지 · 같은 `sub`로 다시 오면 **새 고객**.
- **AC-OC6-4** Given 데이터 지도, Then "통합 인박스" 저장소 행 · 외부 출구 6종 불변.
- **AC-OC6-5** Given 연결·병합·상태·담당 변경, Then 감사 요약에 별칭만(이름·회원 번호·본문 0).
