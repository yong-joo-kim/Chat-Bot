## 1. 배경 / 목적

### 1.1 배경 — 데이터는 이미 쌓이고 있는데, 읽는 화면이 없다

No.11(공개 대화 API) Phase에서 `ConversationLog`의 **최초 쓰기 주체**가 생겼고, No.12 Phase에서 `blockedByFilter`·`matchedNodeId`·`matchedFaqId`가 채워지기 시작했다. 즉 **분석에 필요한 원천 데이터는 이미 생산되고 있으나, 그것을 읽는 기능은 No.2 대시보드 카드 3종(접속수/응답률/미응답률) + 인기질문 TOP 5가 전부**다.

| # | 현재 상태 | 결과 |
|---|---|---|
| ① | 기간 지정은 있으나 **시계열이 없다**. "지난주보다 나아졌나"를 알 수 없고, 대시보드는 한 기간의 스냅샷 하나만 보여준다 | 운영 개선의 근거가 되는 **추세**가 보이지 않는다 |
| ② | `matchedNodeId`/`matchedFaqId`/`blockedByFilter`/`channelType`은 **적재되지만 어떤 화면도 읽지 않는다** | "노드가 답했나 FAQ가 답했나 폴백이었나"를 구분할 수 있는 데이터가 있는데도 활용되지 않는다 |
| ③ | **`UnansweredQuestion` 테이블은 Phase 0부터 존재하지만 쓰기 코드가 0줄**이다(`apps/api/src` 전체에서 읽기는 `chatbots.service.ts`의 영구삭제 영향 미리보기 1곳뿐). `packages/shared-types/src/stats.ts`의 `UnansweredQuestionSchema`·`ResolveUnansweredQuestionSchema`도 초안 상태로 소비자가 없다 | 미응답 질문이 **어디에도 축적되지 않는다.** 관리자가 "무엇을 못 답했는지" 알려면 대화 로그를 직접 뒤져야 한다 |
| ④ | 미응답률이 높다는 사실은 대시보드가 알려주지만(`chatbot-operations.md` FR-2-3), **그다음에 할 일이 시스템 안에 없다.** 기존 문서가 "미응답률이 높으면 향후 No.15로 이동해 보완한다"고 예고만 해 두었다 | 진단은 있고 **처방이 없다** |
| ⑤ | 의도에 예문을 추가하는 경로(`PATCH /intents/:id/examples`)는 있으나, **"이 미응답 질문 때문에 추가했다"는 맥락이 끊긴다** | 같은 질문이 반복 유입돼도 처리 여부를 기억할 곳이 없어 매번 처음부터 검토하게 된다 |

이 그룹은 **새 원천 데이터를 만드는 그룹이 아니라, 이미 쌓인 데이터를 ① 읽고(No.14) ② 그 결과를 대화 자산으로 되먹이는(No.15) 폐루프를 완성하는 그룹**이다.

### 1.2 목적

1. 일/주/월 단위 **시계열**로 사용자현황·대화현황·질문순위·이용동향을 조회하게 한다(No.14).
2. 이미 적재 중인 필드(`matchedNodeId`/`matchedFaqId`/`blockedByFilter`/`channelType`)를 **응답 출처·채널 분포 지표로 소비**한다(No.14).
3. 미응답 질문을 **검토 가능한 큐로 축적**한다 — 정규화 병합·발생 횟수·검토 상태를 갖는다(No.15).
4. 관리자가 미응답 질문에 **의도명을 지정해 저장하면 즉시 대화에 반영**되게 한다(No.15).
5. 반영했는데도 **여전히 답하지 못하는 경우(노드 미연결)를 화면이 먼저 알려준다**(No.15).

### 1.4 원본 근거 인용 (`docs/00-source/`)

> ⚠ **조사 한계 명시**: 이 환경에서는 `ROCHA_매뉴얼_23.07.07.pdf`(116p)의 **페이지 범위 추출이 불가능**했다(PDF 페이지 렌더러 미설치, 전체 읽기는 컨텍스트 초과). 따라서 p.59~62의 직접 인용 대신, **같은 내용을 상호참조하는 `로차_간단학습매뉴얼.pdf`(28p) 전문**과 `기능요구사항.md` §5의 교차검증 메모를 근거로 삼았다. 매뉴얼 p.59~62 화면의 세부 필드는 `ui-designer` 단계에서 원본을 직접 확인해 보정할 것을 권고한다.

**근거 1 — 매뉴얼 p.59가 "학습현황" 화면임이 교차 확인된다.**
`로차_간단학습매뉴얼.pdf` p.4 "재학습 절차" 플로차트에 다음 노드가 있다:

> `미응답 리스트 확인` → (N) → **`학습상태 변경 (59p 학습현황 – 학습 완료 상태 변경)`**

즉 ROCHA의 학습현황 화면(매뉴얼 p.59~)은 ① **미응답 리스트**와 ② **학습 상태(완료로 변경)** 두 요소를 갖는다.

**근거 2 — 운영 루프의 형태가 "미응답 → 예문 증강 → 재검증"의 반복이다.**
같은 문서 p.3 "처음 생성 절차" 플로차트의 되먹임 화살표 라벨:

> **`미응답 질문의 반복적인 추가 및 예문 증강`** — `응답 테스트` → `의도 추가 및 예문 증강` → `의도학습` → `노드 생성(대화그래프)` → `응답 테스트`(순환)

p.4는 이 루프를 오답 유형별로 3분기한다:

> `의도/키워드 파악 여부` → **①`의도 미파악/키워드 파악`** → `의도 추가 및 예문 증강` / **②`의도 파악/키워드 미파악`** → `키워드 추가 및 예문 증강` / **③`의도 미파악/키워드 미파악`** → `의도+키워드 추가 및 예문 증강`
> (판단 기준 주석) "의도가 잘못되어 대화상자를 잘못 찾은 것인지? / 대화상자는 찾았지만 키워드가 없어 답이 나가지 않은 것인지? / 의도도 없고, 키워드도 없는 것인지"

→ **FR-15-20(반영 후 노드 미연결 경고)의 직접 근거**다. 의도만 추가하고 그 의도를 쓰는 노드가 없으면 여전히 답하지 못한다는 사실을 원본 매뉴얼이 이미 3분기로 다루고 있다.

**근거 3 — "관리자 개입 필수"는 원본의 명시 권고다.**
p.4 상단 적색 주석:

> **"※ 여러 관계자의 수시적 학습이 아닌 전문 담당자에 의한 일괄 학습 추천"**

→ **FR-15-15(일괄 반영)** 와 §4.2.1의 "반자동" 성격을 뒷받침한다.

**근거 4 — ROCHA의 '의도 학습' 버튼은 DLE 엔진 전제이며, 우리 시스템에는 대응물이 없다.**
p.21 의도관리 설명 4번:

> "의도 등록 완료 후 **'의도 학습'을 하여야 반영됨**. → 의도 파악 시 사용할 데이터 이므로 반드시 실행"

→ ROCHA는 별도 학습 실행 단계가 있으나, 이는 자사 딥러닝 학습엔진(우리 목록의 **No.16 DLE**, GPU 6, 확장기능)을 전제한 것이다. 우리 현행 엔진은 규칙 매칭이므로 이 단계가 **캐시 무효화로 치환**된다 — **J-1의 근거**다.

**근거 5 — "미응답"의 정의가 Fallback과 일치한다.**
p.6 "기본 생성되는 대화상자 설명" 2):

> "**Fallback : 'unknown' 대화 상자로 학습되지 않은 답변이나 의도추천점수가 낮을 경우** 선택되어 메시지를 주게 됨."

→ 우리 시스템의 `judgeAnswered()`(`conversation/lib/conversation-log.ts`)가 `FALLBACK_NODE`/`FALLBACK_FAQ`/`FALLBACK_DEFAULT`/`EMPTY_INPUT` trace를 미응답으로 판정하는 것과 **개념이 일치**한다 → **FR-15-1(수집 조건)의 근거**.

**근거 6 — 통계는 독립 메뉴다.**
p.5 관리 콘솔 좌측 내비게이션 캡처에 `대시보드`와 별개로 **`통계/분석`**(하위 메뉴 있음), `모니터링`, `설문관리`, `이력관리`가 존재한다.

→ **J-4(대시보드와 기본 통계의 분리)** 의 원본 근거다. ROCHA도 두 화면을 분리해 두었다.

### 1.5 No.15 ↔ No.21(딥러닝 군집분석) ↔ No.23 구분 — 혼동 주의

> ⚠ **기준 목록의 번호 오류 발견**: `기능요구사항.md` §2 No.15 행은 *"**19번** '딥러닝 군집분석'과는 별개 기능"* 이라고 쓰여 있으나, **§3 확장기능 표에서 딥러닝 군집분석은 No.21**이고 **No.19는 "대화검증시스템 & TC테스트"** 다. 같은 문서 §5 교차검증 메모도 *"딥러닝 군집분석(21번...)"* 으로 적고 있어 **§2의 "19번"이 오기**다(항목 추가 과정에서 번호가 밀린 것으로 추정). §10에 정정을 제안한다. 본 문서는 **No.21**로 표기한다.

## 2. 사용자 역할 및 시나리오

### 2.1 역할

`security-audit.md` §2.1의 역할 3종을 그대로 상속한다.

| 역할 | 이 그룹에서의 활동 |
|---|---|
| **ADMIN** | EDITOR의 모든 활동 + 전 챗봇 접근 |
| **EDITOR** | 통계 조회, 미응답 질문 검토·의도 반영·무시 처리(**이 그룹의 주 사용자**) |
| **VIEWER** | 통계 조회, 미응답 질문 **목록 조회만**(반영/무시 버튼이 렌더되지 않음, FR-C-6) |
| 최종 사용자 | **직접 사용하지 않는다.** 다만 이 사람의 발화가 미응답 큐의 유일한 입력원이다 |

### 2.2 사용자 시나리오

**S-1. 월말 운영 보고 (EDITOR)**
편집자가 `챗봇 상세 > 통계` 탭을 연다. 기본값은 **일 단위 / 최근 30일**이다. 상단 요약 카드에 세션 수, 총 대화 턴, 응답률, 미응답 건수, 금지어 차단 건수가 보이고, 아래 시계열 그래프가 일별 추세를 그린다. 단위를 `주`로 바꾸면 같은 기간이 4~5개 막대로 합쳐지고, `월`로 바꾸면 기본 기간이 최근 12개월로 자동 확장된다.

**S-2. "우리 봇은 무엇으로 답하고 있나" (EDITOR)**
같은 화면 아래 `응답 출처` 분포를 본다. 노드 62% / FAQ 25% / 폴백 13%로 표시된다. 폴백 13%를 클릭하면 **미응답 질문 목록으로 필터가 걸린 채 이동**한다.

**S-3. 몰리는 시간대 파악 (EDITOR)**
`이용동향` 영역에서 시간대별(0~23시)·요일별 분포를 본다. 평일 10~11시와 14~15시에 집중돼 있어, 상담원 배치 근거로 캡처해 보고서에 넣는다.

**S-4. 채널별 비교 (ADMIN)**
채널 분포에 `WEB 100%`만 표시된다. 아직 웹 채널만 실제 대화를 처리하기 때문이며(ADR-0011), 화면은 "현재 대화가 유입되는 채널은 1종입니다"라는 캡션을 함께 보여준다.

**S-5. 미응답 질문 검토 (EDITOR)**
`챗봇 상세 > 학습현황`을 연다. 목록이 **발생 횟수 많은 순**으로 정렬돼 있다. 1위 `해외배송도 되나요?` (12회, 최근 발생 3시간 전). 행을 펼치면 정규화 병합된 원문 변형 3종과 추천 의도 후보(`배송문의` 0.62 / `주문조회` 0.41)가 보인다.

**S-6. 기존 의도에 반영 (EDITOR)**
편집자가 추천 후보 `배송문의`를 선택하고 `반영`을 누른다. 확인 모달에 "의도 **배송문의**에 예문 1건이 추가되고, 저장 즉시 대화에 반영됩니다"가 표시된다. 저장하면 성공 토스트와 함께 해당 행이 `반영 완료`로 바뀌고 목록에서 접힌다.

**S-7. 새 의도 만들기 (EDITOR)**
다음 질문 `포장 선물 되나요?` 는 추천 후보가 없다. 편집자가 의도명 입력란에 `선물포장문의`를 직접 입력한다. 시스템이 "같은 이름의 의도가 없습니다. **새 의도를 만들고** 이 질문을 첫 예문으로 등록합니다"라고 안내하고, 저장하면 의도가 생성된다.

**S-8. ⚠ 반영했는데도 못 답하는 경우 (EDITOR)**
S-7 저장 직후 화면에 **경고**가 뜬다: "의도 `선물포장문의`를 사용하는 대화 노드가 없습니다. 노드를 연결하기 전까지 이 질문은 여전히 답변되지 않습니다." 옆에 `노드 만들기` 링크가 있다. 편집자가 링크를 따라가 노드를 만든다.

**S-9. 반영 후 재발생 (EDITOR)**
일주일 뒤 목록을 다시 연다. `해외배송도 되나요?` 행에 **`반영 후 재발생 4회`** 배지가 붙어 있다. 예문을 넣었는데도 매칭되지 않는다는 뜻이므로, 편집자는 예문 표현을 늘리거나 키워드 조건을 점검한다.

**S-10. 검토할 가치가 없는 항목 (EDITOR)**
`ㅋㅋㅋ`, `.`, `테스트` 같은 항목은 `무시`를 누른다. 기본 목록에서 사라지고, `무시됨` 필터를 켜면 다시 볼 수 있으며 `되돌리기`로 대기 상태로 복원할 수 있다.

**S-11. 일괄 처리 (EDITOR)**
비슷한 배송 관련 질문 8건을 체크박스로 선택하고 `일괄 반영 > 배송문의`를 실행한다. 8건이 한 번에 처리되고 결과 요약("반영 7건 / 실패 1건 — 예문 상한 초과")이 표시된다.

**S-12. 권한 없는 사용자 (VIEWER)**
모니터 역할 사용자가 같은 화면을 연다. 목록과 추천 후보는 보이지만 `반영`·`무시`·체크박스가 **렌더되지 않는다**. 개발자 도구로 반영 API를 직접 호출하면 `403`이다.

**S-13. 데이터가 없을 때 (EDITOR)**
갓 만든 챗봇의 통계 화면은 오류가 아니라 "선택한 기간에 대화 기록이 없습니다"라는 빈 상태와 기간 확대 안내를 보여준다. 학습현황도 "검토할 미응답 질문이 없습니다 — 좋은 신호입니다"로 표시된다.

**S-14. 너무 긴 기간 요청 (ADMIN)**
관리자가 URL을 직접 고쳐 1년치를 일 단위로 요청한다. `400`(`STATS_RANGE_TOO_WIDE`)과 함께 "일 단위 조회는 최대 92일까지 지정할 수 있습니다. 더 긴 기간은 월 단위로 조회해 주세요"가 안내된다.

**S-15. 개인정보는 보이지 않는다 (ADMIN)**
어떤 사용자가 전화번호를 포함해 질문했다. 미응답 목록에 표시되는 문장은 `010-****-1234 로 연락 주세요`처럼 **이미 마스킹된 값**이다(ADR-0013). 마스킹 전 원문은 어디에도 없다.

**결정: `ConversationLog`에 `dayBucket`(`YYYY-MM-DD`, Asia/Seoul) 컬럼을 추가하고, 적재 시점에 확정한다. 주/월 버킷은 `dayBucket`에서 앱이 파생한다.**

근거:
1. `groupBy(['createdAt'])`은 **의미가 없다** — 타임스탬프는 행마다 유일해서 그룹이 행 수만큼 생긴다. 시계열을 얻으려면 어딘가에서 "날짜"로 뭉쳐야 한다.
2. DB 날짜 함수로 뭉치면 **이식성이 깨진다.** SQLite는 `strftime('%Y-%m-%d', createdAt, '+9 hours')`, Postgres는 `date_trunc('day', createdAt AT TIME ZONE 'Asia/Seoul')`로 문법이 다르다. `개발명세서.md` §5는 DB 이식성 유지를, ADR-0004는 "DB 종속 SQL을 늘리지 않는다"를 이미 정했다.
3. 전량 `findMany` 후 앱 버킷팅은 **NFR-P1을 만족하지 못한다**(ADR-0004가 이미 기각한 대안). 3개 컬럼만 선택하면 메모리는 견딜 수 있으나, 10만 행 직렬화 비용이 목표 예산을 잠식한다.
4. **쓰기 주체가 이미 있다.** `ConversationLogService.record()` 단일 진입점에서 1줄로 채울 수 있으므로 ADR-0004의 "쓰기 주체 없는 컬럼 금지" 기준을 통과한다(DD-20·DD-37과 같은 논리).
5. **타임존이 데이터에 고정된다.** "KST 기준 하루"가 조회 시점 계산이 아니라 적재 시점에 확정되므로, 서버 TZ 설정이 바뀌어도 과거 집계가 흔들리지 않는다.

> **대안(아키텍트 판단 여지)**: `dayBucket` 없이 `$queryRaw` 1회로 DB별 날짜 함수를 쓰는 안. 성능은 동등하나 이식성·테스트 용이성에서 불리하다. 최종 결정은 `system-architect`(DD-50).

### 4.2 No.15 — 학습현황(관리자 보조 재학습)

기준 목록의 기능 설명은 **"미응답 질문 리스트를 검토 → 의도명 입력 → 저장하여 재학습(관리자 개입 필수인 반자동 워크플로우)"** 이다. 아래는 그 3단계를 그대로 따른다.

#### 4.2.1 "재학습"의 범위 — J-1 결정 (⚠ 이 그룹의 최대 쟁점)

**결정: 이번 Phase의 "재학습"은 ① 의도 예문 추가 ② 번들 캐시 무효화 ③ 즉시 반영 확인까지다. 학습 Job·`TrainingJob` 테이블·`apps/ml-worker` 연동·분류기 재학습은 만들지 않는다. 수동 트리거 API도 만들지 않는다.**

근거:

1. **현행 아키텍처에 "학습"이라는 연산이 존재하지 않는다.** 매칭은 `packages/dialogue-engine`의 **정규화 기반 규칙 매칭**(정확일치/부분일치)이며(ADR-0008, `matcher.ts`), 학습된 가중치·모델 파일·인덱스 빌드 단계가 없다. `Intent.examples`에 문자열을 추가하고 `DialogueBundleService.invalidate(chatbotId)`를 호출하면 **다음 턴부터 매칭에 반영된다.** 이것이 이 시스템에서 "재학습"의 전부다.
2. **ROCHA의 '의도 학습' 버튼은 DLE 전제다**(§1.4 근거 4). 그 대응물은 우리 목록의 **No.16 딥러닝 학습엔진(GPU 6, 확장기능)** 이며, No.15가 선점할 항목이 아니다.
3. **GPU 등급이 이를 못 박는다.** 기준표의 GPU 구간 정의상 **1~2 = CPU 전용(CRUD/설정/통계조회/규칙매칭)** 이다. No.15는 **2**이므로 딥러닝은커녕 "3~4 경량 ML"에도 못 미치는 등급으로 이미 분류돼 있다. 경량 분류기 재학습은 **No.23(GPU 4)** 의 정의 그 자체다.
4. **쓰기 주체 없는 스키마를 만들지 않는다**(ADR-0004). `TrainingJob` 테이블은 `개발명세서.md` §3에 No.16/18/21용으로 예고돼 있으며, **그 소비자가 생길 때** 만든다. 지금 만들면 상태가 항상 `SUCCEEDED`인 가짜 Job 행만 쌓인다.
5. **"수동 트리거 API"는 사용자를 속인다.** 내부가 no-op인 `POST /retrain`을 노출하면 관리자는 "아직 학습 중이니 기다려야 한다"고 오해한다. 실제로는 저장 즉시 반영되므로, **화면은 "반영 완료"를 즉시 말해야 정확하다**.

> **대신 남기는 것 — 향후 ml-worker 연동 지점(인터페이스만)**
> 반영 동작의 마지막 단계를 `applyLearning(chatbotId, intentId)` 같은 **단일 지점**으로 모아 둔다. 현재 구현은 `bundleService.invalidate(chatbotId)` 한 줄이지만, No.16/No.23 착수 시 이 지점이 **Job 큐 적재로 교체되는 유일한 장소**가 된다. 인터페이스 이름·위치는 `system-architect`가 확정한다(DD-55).
>
> **역할 분담 결론**: 이 그룹은 **`backend-implementer` 단독 구현**이다. `ml-engineer`는 투입하지 않는다. 장래 No.16/21/23 착수 시 위 인터페이스 1곳에서 인계한다.

#### 4.2.2 미응답 질문 수집 — J-2 결정

**결정: `ConversationLogService.record()` 내부에서 `UnansweredQuestion`을 upsert한다.**

근거:
1. **검토 상태는 로그에서 파생할 수 없다.** `PENDING`/`RESOLVED`/`IGNORED`는 관리자의 판단 결과이며 대화 로그에 존재하지 않는다. 파생 집계로 가면 이미 처리한 질문이 매일 다시 올라온다.
2. **마스킹된 값에 접근할 수 있는 유일한 지점이다.** `record()` 안에서 금지어 마스킹 → PII 마스킹이 끝난 문자열이 만들어진다(ADR-0013). 이 바깥에서 수집하면 **원문을 다시 만지게 되어 마스킹 정책이 무너진다**.
3. **실패 정책을 그대로 상속한다.** `record()`는 이미 전체가 try/catch로 감싸여 실패해도 대화 응답에 영향을 주지 않는다(FR-11-24). 수집을 여기에 두면 같은 안전망 안에 들어간다.
4. **시뮬레이션 오염이 자동으로 방지된다.** 관리자 시뮬레이션(No.10)은 `ConversationLog`를 적재하지 않으므로(FR-10-5, AC-10-10), 수집기도 자동으로 타지 않는다.

| ID | 요구사항 |
|---|---|
| FR-15-1 | **수집 조건(전부 만족해야 적재)**: ① `isAnswered = false` ② `blockedByFilter = false` ③ 마스킹 후 질문 문자열의 `normalizeText()` 결과가 빈 문자열이 아님 ④ **버튼 클릭 턴이 아님**(아래 FR-15-2) ⑤ 정규화 결과 길이가 상한(기본 200자) 이하. |

#### 4.2.4 추천 의도 — J-5 결정

**결정: `apps/api/src/learning/lib/intent-suggest.ts`에 신규 순수 함수를 만든다. 엔진은 수정하지 않는다. 추천은 조회 시점에 계산하며 저장하지 않는다.**

근거:
1. **엔진 재사용이 원리적으로 불가능하다.** `matchIntent()`는 정확일치 또는 **부분 문자열 포함**만 점수화한다(`matcher.ts` 38~44행: `normalizedInput === norm` 또는 `includes`). 미응답 질문은 정의상 이 판정을 통과하지 못한 문장이므로, 같은 함수를 호출하면 **항상 `null`** 이다.
2. **추천은 매칭과 다른 문제다.** 매칭은 "확실히 이 의도다"를 판정하고(오탐 비용 높음), 추천은 "이것일 수도 있다"를 제시한다(오탐 비용 낮음 — 관리자가 거른다). 임계값과 알고리즘이 달라야 한다.
3. **엔진 규약을 지킨다.** `packages/dialogue-engine`은 DB·정책 무의존 순수 함수라는 규약(ADR-0008)이 있고, 관리 보조 기능을 엔진에 넣으면 대화 경로의 성능·안정성 표면이 넓어진다. 추천은 `apps/api` 쪽 `lib/`에 둔다(FR-12-41이 금지어 필터를 엔진에 넣지 않은 것과 같은 판단).
4. **한국어에는 문자 bigram이 실용적이다.** 교착어 특성상 공백 토큰만으로는 `해외배송`/`해외 배송`/`배송문의`가 전부 무관해진다. 문자 bigram 자카드는 사전·모델 없이 이 문제를 상당 부분 흡수한다. **임베딩·의미 유사도는 No.18(GPU 5) 범위이며 도입하지 않는다.**
5. **저장하면 즉시 낡는다.** 의도·예문은 계속 바뀌므로 저장된 `suggestedIntentName`은 다음 날 틀린 값이 된다. 조회 시점 계산이 정확하고, 그 결과 **기존 컬럼은 끝내 쓰기 주체가 없다** → 제거 제안(DD-49).

| ID | 요구사항 |
|---|---|
| FR-15-15 | 추천 후보는 **최대 3건**, 각 후보에 `{ intentId, intentName, score(0~1), matchedExample }`을 포함한다. |
| FR-15-16 | 점수 산출은 **정규화 후 문자 bigram 자카드 유사도**를 기본으로 하며, 의도의 **예문 전체 중 최고 점수**를 그 의도의 점수로 한다. 의도명 자체도 후보 문자열에 포함한다. |
| FR-15-17 | **최소 임계값**(기본 0.25) 미만은 후보로 제시하지 않는다. 후보가 0건이면 화면은 "추천할 의도가 없습니다 — 새 의도를 만들어 주세요"로 안내한다. 잘못된 추천을 억지로 채우지 않는다. |
| FR-15-18 | 추천 산출은 **DB·Nest 무의존 순수 함수**이며 단위 테스트 1차 대상이다(NFR-M1). |
| FR-15-19 | 의도·예문이 많은 챗봇에서도 목록 1페이지(20행)의 추천 계산이 **P95 500ms 이내**여야 한다. 의도 예문 집합은 요청당 1회만 로드해 전 행이 공유한다(NFR-P4). |

#### 4.2.5 반영(저장) — 의도명 입력 → 저장

| ID | 요구사항 |
|---|---|
| FR-15-20 | `POST /chatbots/:chatbotId/unanswered-questions/:id/resolve` — 요청 `{ intentId? , intentName?, exampleText? }`. 권한 `dialogue:write`. 둘 중 하나는 반드시 있어야 한다(`intentId` 우선). |
| FR-15-21 | **기존 의도 매칭 규칙**: `intentName`이 주어지면 `(chatbotId, normalizeText(name))` 로 조회한다. **존재하면 그 의도에 예문을 추가**하고, **없으면 새 의도를 생성**한 뒤 예문 1건으로 시작한다. 어느 쪽인지 **저장 전에 화면이 먼저 알려준다**(S-7) — 의도가 뜻하지 않게 새로 생기는 일을 막는다. |

| FR-15-23 | 예문 추가는 **기존 의도 규약을 그대로 상속**한다: 중복 제거, 예문 상한 500개(초과 시 `400 LIMIT_EXCEEDED`), 예문 길이 1~200자, 다른 의도와의 **예문 충돌 경고**(`conflicts[]`) 반환. 기존 `intents.service.ts`의 경로를 재사용할 것을 권고한다(계산·검증 로직 이중화 금지). |
| FR-15-24 | 저장이 성공하면 ① `UnansweredQuestion.status = RESOLVED`, `resolvedIntentId`, `resolvedAt` 기록 ② **`DialogueBundleService.invalidate(chatbotId)` 호출** ③ 응답에 `appliedImmediately: true` 를 포함한다. 화면은 "학습 중"이 아니라 **"반영 완료 — 다음 대화부터 적용됩니다"** 로 표기한다(J-1). |
| FR-15-25 | ⚠ **노드 미연결 경고**: 반영 응답에 대상 의도를 참조하는 **대화 노드 수(`linkedNodeCount`)** 를 포함한다. `0`이면 화면이 **경고와 함께 노드 생성 링크**를 제시한다(S-8). 근거: 의도만 추가하고 노드를 연결하지 않으면 여전히 폴백이 나간다 — 원본 매뉴얼이 오답 유형을 3분기로 다룬 바로 그 함정이다(§1.4 근거 2). 이 경고가 없으면 관리자는 "반영했는데 왜 안 되지"에서 막힌다. |
| FR-15-26 | **이미 처리된 항목 재반영 금지**: `status`가 `PENDING`이 아니면 `409`(`ALREADY_RESOLVED`). 되돌리려면 `reopen`을 먼저 호출한다(동시 편집 경합 방어 — 판정은 서비스 계층 트랜잭션 내부 재확인). |
| FR-15-27 | `POST .../:id/ignore` — `status = IGNORED`. 목록 기본 필터에서 제외된다. |
| FR-15-28 | `POST .../:id/reopen` — `RESOLVED`/`IGNORED` → `PENDING`. 반영으로 추가된 예문을 **자동으로 되돌리지 않는다**(예문 삭제는 의도 편집 화면에서 명시적으로 수행한다 — 되돌리기가 조용히 대화 자산을 바꾸면 안 된다). 화면에 그 사실을 안내한다. |
| FR-15-29 | **미응답 질문의 물리 삭제는 제공하지 않는다.** `IGNORED`로 대체한다. 근거: 삭제하면 같은 질문이 다시 유입될 때 "이미 판단한 항목"임을 알 수 없어 검토가 반복된다(FR-12-30의 회원 비활성화와 같은 논리). |

### 4.4 관리자 콘솔 횡단 요구사항 (`apps/web`)

> 이 그룹은 **화면이 핵심이다.** 통계는 본질적으로 시각화이고, 학습현황은 검토 UI 없이는 기능이 성립하지 않는다. → **`ui-designer` 단계가 반드시 필요하다**(§11).

## 6. 비기능 요구사항

### 6.1 성능

| ID | 요구사항 |
|---|---|
| NFR-P1 | **통계 조회는 `ConversationLog` 10만 행 / 기간 90일 기준 P95 1초 이내.** 기존 대시보드 기준(P95 500ms, 단일 기간)보다 완화하되, 5초 타임아웃 시 `503`(`AGGREGATION_TIMEOUT`)으로 명확히 실패한다(기존 패턴 재사용). |
| NFR-P2 | **`where`에는 항상 `chatbotId` + 기간이 먼저** 들어가 기존 인덱스(`conversation_logs(chatbotId, createdAt)`) 또는 신규 인덱스(`(chatbotId, dayBucket)`)에 적중해야 한다. **전량 `findMany` 금지**(ADR-0004 기각 대안). |
| NFR-P3 | **미응답 수집이 대화 P95 500ms 예산(NFR-P1, No.11)을 잠식하지 않는다.** 응답 반환 이후 fire-and-forget이며 쿼리는 upsert 1회다. |
| NFR-P4 | **학습현황 목록 조회(20행 + 추천 계산 포함) P95 500ms 이내.** 의도 예문 집합은 요청당 1회 로드해 전 행이 공유한다. 추천을 행마다 DB 조회하는 구현은 금지한다(N+1). |
| NFR-P5 | 일괄 반영 50건은 **P95 5초 이내**이며, 번들 캐시 무효화는 1회만 수행한다. |
| NFR-P6 | `dayBucket` 컬럼 추가로 인한 **대화 응답 시간 증가는 측정 가능한 수준이 아니어야 한다**(문자열 1개 계산). |
| NFR-P7 | 백필 스크립트는 기존 로그 100만 행 기준 **10분 이내**에 완료되고, 배치 단위로 커밋해 중단·재개가 가능해야 한다. |
| NFR-P8 | 통계 API 3종은 **서로 독립적으로 호출 가능**해야 한다(화면이 부분 로딩할 수 있도록). 한 API의 지연이 다른 영역의 표시를 막지 않는다. |
| NFR-P9 | 기존 성능 기준(대시보드 P95 500ms, 목록 300ms, 대화 500ms)이 **이 그룹 적용 후에도 유지**된다(회귀 측정 대상). |

## 7. 수용기준 (Acceptance Criteria)

### AC-14A. 기간·단위·집계

- **AC-14A-1** Given 최근 30일에 걸친 로그 300건, When `GET /stats/summary`를 `granularity=DAY`로 호출하면, Then **30개 버킷**이 반환되고 데이터가 없는 날도 `turnCount: 0`으로 포함된다.
- **AC-14A-2** Given 같은 데이터, When `granularity=WEEK`로 호출하면, Then 버킷의 **일별 합계가 주별 합계와 정확히 일치**한다(합계 보존 검증 — `시험항목.md` TC-14의 기준).
- **AC-14A-3** Given 같은 데이터, When `granularity=MONTH`로 호출하면, Then 월 합계가 일 합계의 총합과 일치한다.
- **AC-14A-4** Given KST 기준 `2026-09-21 23:50`과 `2026-09-22 00:10`에 적재된 로그 2건, When 일 단위로 조회하면, Then **서로 다른 날짜 버킷**에 들어간다(UTC 기준으로 묶이지 않는다).
- **AC-14A-5** Given 주 단위 조회, When 버킷 라벨을 확인하면, Then **월요일 시작**이며 시작·종료일이 함께 표기된다.
- **AC-14A-6** Given `granularity=DAY`로 120일 기간 요청, When 호출하면, Then `400`(`STATS_RANGE_TOO_WIDE`)이며 메시지에 **월 단위 조회 대안**이 포함된다.
- **AC-14A-7** Given `granularity=YEAR`(미지원), When 호출하면, Then `400`(`INVALID_GRANULARITY`)이다.
- **AC-14A-8** Given 기간 미지정, When 호출하면, Then 단위별 기본 기간(일 30 / 주 12 / 월 12)이 적용되고 응답의 `periodStart`/`periodEnd`로 확인된다.
- **AC-14A-9** Given 동일 챗봇·동일 기간, When `GET /stats/dashboard`와 `GET /stats/summary`를 각각 호출하면, Then **접속수·응답률·총 건수가 완전히 일치**한다(FR-14-3).
- **AC-14A-10** Given 로그 0건 챗봇, When 통계 3종을 호출하면, Then **모두 `200`** 이며 모든 수치가 0이다(오류가 아니다).
- **AC-14A-11** Given 존재하지 않는 `chatbotId`, When 호출하면, Then `404`다.
- **AC-14A-12** Given 집계가 5초를 초과하도록 강제, When 호출하면, Then `503`(`AGGREGATION_TIMEOUT`)이고 **오래된 캐시를 반환하지 않는다**.
- **AC-14A-13** Given 기존 대시보드 스펙(AC-2-1~14), When 이 그룹 적용 후 실행하면, Then **전부 수정 없이 통과**한다.

### AC-14B. 지표 정의

- **AC-14B-1** Given 응답 90 / 미응답 10(그중 금지어 차단 4), When `/stats/summary`를 호출하면, Then `turnCount:100`, `answeredCount:90`, `unansweredCount:10`, `blockedCount:4`이고 화면이 "미응답 10건(이 중 금지어 차단 4건)"으로 구분 표기한다.
- **AC-14B-2** Given 노드 응답 50 / FAQ 응답 30 / 미응답 20, When `/stats/distribution`을 호출하면, Then `bySource`가 `NODE 50 / FAQ 30 / FALLBACK 20`으로 나온다.
- **AC-14B-3** Given `sessionId` 40종의 로그 100건, When 세션 지표를 확인하면, Then `sessionCount:40`, 세션당 평균 턴 `2.5`다.
- **AC-14B-4** Given `sessionId`가 전부 `null`인 로그 10건, When 조회하면, Then 접속수 10 + `visitCountBasis: 'LOG_COUNT'`로 기존 ADR-0001 규칙과 동일하게 동작한다.
- **AC-14B-5** Given 시간대가 편중된 로그, When `/stats/distribution`을 호출하면, Then `byHour`가 **정확히 24개**, `byWeekday`가 **정확히 7개** 반환되고 값이 없는 구간은 0이다.
- **AC-14B-6** Given `" 배송  조회 "`와 `"배송 조회"`가 섞인 로그, When `/stats/questions`를 호출하면, Then **하나의 항목으로 병합**되어 집계된다(기존 정규화 규칙 재사용).
- **AC-14B-7** Given 미응답 로그 중 금지어 차단 3건 포함, When `topUnansweredQuestions`를 확인하면, Then **차단 3건은 순위에서 제외**된다.
- **AC-14B-8** Given 전화번호가 포함된 질문, When 순위·목록에 표시되면, Then **마스킹된 형태**이며 원문은 어떤 응답에도 없다.
- **AC-14B-9** Given 응답률 계산, When `responseRate + noResponseRate`를 확인하면, Then **정확히 1**이다(기존 파생 계산 유지).

### AC-15A. 미응답 질문 수집

- **AC-15A-1** Given 챗봇이 답하지 못한 발화 1건, When 공개 대화 API로 전송하면, Then `UnansweredQuestion` 1행이 `PENDING`으로 생성된다.
- **AC-15A-2** Given 같은 질문을 표기만 달리해 3회(`"해외배송 되나요"`, `" 해외배송 되나요 "`, `"해외배송 되나요"`) 전송, When 큐를 조회하면, Then **1행**이고 `occurredCount: 3`이다.
- **AC-15A-3** Given **금지어로 차단된** 발화, When 전송하면, Then `ConversationLog`는 남지만 `UnansweredQuestion`은 **생성되지 않는다**(`blockedByFilter` 제외 규칙).
- **AC-15A-4** Given 봇이 제시한 **버튼(NODE)** 클릭 턴, When 그 턴이 미응답으로 끝나도, Then 큐에 적재되지 않는다.
- **AC-15A-5** Given 빈 문자열/공백만 입력, When 전송하면, Then 적재되지 않는다.
- **AC-15A-6** Given **관리자 시뮬레이션**으로 답하지 못하는 문장을 10회 실행, When 큐를 조회하면, Then **신규 행이 0건**이다(AC-10-10과 동일 보장).
- **AC-15A-7** Given 정상 응답된 발화, When 전송하면, Then 큐에 적재되지 않는다.
- **AC-15A-8** Given 수집이 실패하도록 강제, When 대화를 전송하면, Then **대화 응답은 정상**이고 경고 로그만 남으며 로그 본문이 기록되지 않는다.
- **AC-15A-9** Given PII가 포함된 미응답 발화, When 큐를 조회하면, Then 저장된 문장이 **마스킹된 값**이다.
- **AC-15A-10** Given `RESOLVED` 상태 항목과 동일한 질문이 재유입, When 큐를 조회하면, Then 상태는 `RESOLVED`를 유지하고 `recurredCount`가 증가하며 목록에 **재발생 배지**가 표시된다.
- **AC-15A-11** Given `PENDING`이 상한(테스트용 낮은 값)에 도달, When 새 질문이 유입되면, Then **새 행은 추가되지 않고** 기존 행의 카운트 증가는 계속되며 경고 로그가 남는다.

### AC-15B. 검토 · 반영

- **AC-15B-1** Given `PENDING` 항목 5건, When 목록을 조회하면, Then **발생 횟수 내림차순**이고 동률은 최근 발생 내림차순이다.
- **AC-15B-2** Given 기존 의도 `배송문의`(예문에 `"배송 언제 오나요"` 포함)와 미응답 질문 `"배송 얼마나 걸리나요"`, When 상세를 조회하면, Then 추천 후보에 `배송문의`가 **포함**되고 점수가 반환된다.
- **AC-15B-3** Given 어떤 의도와도 유사하지 않은 질문, When 상세를 조회하면, Then 추천 후보가 **빈 배열**이며 화면이 "새 의도를 만들어 주세요"로 안내한다(억지 후보 없음).
- **AC-15B-4** Given `PENDING` 항목과 기존 의도 ID, When `resolve`를 호출하면, Then ① 그 의도의 예문이 1건 늘고 ② 항목이 `RESOLVED`가 되고 ③ 응답에 `created: false`, `appliedImmediately: true`가 담긴다.
- **AC-15B-5** Given 위 반영 **직후**, When 같은 문장으로 공개 대화 API를 호출하면, Then **캐시 TTL을 기다리지 않고** 해당 의도가 매칭된다(번들 무효화 검증).
- **AC-15B-6** Given 존재하지 않는 의도명으로 `resolve`, When 호출하면, Then **새 의도가 생성**되고 응답에 `created: true`가 담긴다.
- **AC-15B-7** Given 대소문자·공백만 다른 의도명(`"배송 문의"` vs `"배송문의"`), When `resolve`하면, Then **기존 의도에 병합**된다(새 의도가 생기지 않는다 — 정규화 유일성 규약).
- **AC-15B-8** Given 반영 대상 의도를 **참조하는 노드가 없음**, When `resolve` 응답을 확인하면, Then `linkedNodeCount: 0`이며 화면에 **지속 표시 경고 + 노드 생성 링크**가 나타난다.
- **AC-15B-9** Given 예문이 이미 500개인 의도, When `resolve`하면, Then `400`(`LIMIT_EXCEEDED`)이고 항목 상태는 **`PENDING` 그대로**다(부분 반영 없음).
- **AC-15B-10** Given 이미 `RESOLVED`인 항목, When 다시 `resolve`하면, Then `409`(`ALREADY_RESOLVED`)다.
- **AC-15B-11** Given 두 관리자가 같은 항목을 동시에 `resolve`, When 두 요청을 처리하면, Then **한쪽만 성공**하고 다른 쪽은 `409`이며 예문이 **중복 추가되지 않는다**.
- **AC-15B-12** Given 항목 8건 선택, When `bulk-resolve`(그중 1건은 예문 상한 초과)를 호출하면, Then `succeeded: 7`, `failed: 1`이고 실패 사유가 반환되며 **번들 무효화는 1회**만 발생한다.
- **AC-15B-13** Given 51건으로 `bulk-resolve`, When 호출하면, Then `400`(`BULK_SIZE_EXCEEDED`)이다.
- **AC-15B-14** Given 항목을 `ignore`, When 기본 목록을 조회하면, Then 그 항목이 **보이지 않고** `status=IGNORED` 필터로는 조회된다.
- **AC-15B-15** Given `RESOLVED` 항목을 `reopen`, When 의도를 확인하면, Then **예문은 그대로 남아 있고** 항목만 `PENDING`으로 돌아가며 화면이 그 사실을 안내한다.
- **AC-15B-16** Given 미응답 질문 삭제 API, When 경로를 탐색하면, Then **존재하지 않는다**(FR-15-29).
- **AC-15B-17** Given `resolve` 수행, When 이력(No.13)을 조회하면, Then `Intent`에 대한 `UPDATE`(또는 신규 시 `CREATE`) 1건이 있고 `summary`에 "학습현황 반영"이 담긴다.
- **AC-15B-18** Given `ignore`/`reopen` 수행, When 이력을 조회하면, Then **관련 기록이 없다**(J-6).
- **AC-15B-19** Given 어떤 감사 레코드든, When 검사하면, Then **미응답 질문 문자열이 포함되어 있지 않다**.

### AC-UI. 관리자 콘솔

- **AC-UI-1** Given EDITOR 로그인, When 챗봇 상세를 열면, Then `통계`·`학습현황` 진입점이 보이고 학습현황에 **`PENDING` 건수 배지**가 표시된다.
- **AC-UI-2** Given 통계 화면, When 차트를 확인하면, Then **표 보기 토글**이 있고 표에 동일한 수치가 표시된다.
- **AC-UI-3** Given 스크린리더, When 차트에 포커스하면, Then **요약 문장**이 읽힌다.
- **AC-UI-4** Given 키보드만 사용, When 기간·단위 변경 → 목록 필터 → 체크박스 선택 → 일괄 반영까지 수행하면, Then **전 과정이 완료**된다.
- **AC-UI-5** Given VIEWER 로그인, When 학습현황을 열면, Then `반영`·`무시`·체크박스가 **렌더되지 않는다**.
- **AC-UI-6** Given VIEWER 로그인, When 개발자 도구로 `resolve` API를 직접 호출하면, Then `403`이고 **DB가 변경되지 않는다**.
- **AC-UI-7** Given 미응답 질문 0건, When 학습현황을 열면, Then **긍정 표현의 빈 상태**가 표시된다(오류 색상 아님).
- **AC-UI-8** Given 응답 출처 분포의 `폴백` 조각, When 클릭하면, Then **학습현황 화면으로 이동**한다.
- **AC-UI-9** Given 반영 모달, When 새 의도가 생성되는 상황이면, Then **저장 전에** "새 의도를 만듭니다"가 표시된다.
- **AC-UI-10** Given 신규 화면 2종, When axe 스캔을 수행하면, Then 대비 위반 **0건**이다.

### AC-X. 공통 / 회귀

- **AC-X-1** 기존 통합 테스트 3종이 **전부 통과**한다(회귀 0건).
- **AC-X-2** 모든 신규 엔드포인트 응답이 대응 zod 스키마 파싱을 통과한다(계약 테스트).
- **AC-X-3** `@Public()`이 부착된 핸들러는 **여전히 정확히 5개**다(AC-C-4 유지 — 우회 경로 회귀 방지).
- **AC-X-4** 신규 환경변수를 하나도 설정하지 않아도 API가 기동한다.
- **AC-X-5** 공개 대화 API의 기존 AC(AC-P-1~15)가 전부 통과하고, **응답 시간이 유의미하게 늘지 않는다**(NFR-P3).
- **AC-X-6** `dayBucket` 백필 후 기존 로그의 **대시보드 수치가 변하지 않는다**(집계 기준이 바뀐 것이 아니라 버킷 컬럼이 추가된 것뿐임을 증명).
- **AC-X-7** 신규 원시 SQL이 **추가되지 않았다**(NFR-M5 — 코드리뷰 체크 항목).
