## 0. 쉬운 말 요약 — 왜 필요한가, 무엇이 달라지나, 안 해도 되는 경우

### 0.1 한 줄 요약

**"우리 챗봇에서 AI가 스스로 문장을 지어 내보내는 곳은 '문서 검색 답변(외부 RAG)' 한 곳뿐이다. 그 답이 나가기 전에 '위험한 주제·주민번호 같은 개인정보 형식'을 규칙으로 걸러 안전한 문구로 바꾸고, 위험한 질문은 애초에 AI에게 보내지 않게 하며, 운영 챗봇의 답을 바꿀 때는 두 번째 관리자가 확인하게 하는 기능"** 이다. 원본 ROCHA에는 없는 최신 트렌드 제안이고, 핵심은 AI 없이 규칙으로 된다. "AI가 AI를 검사"하는 환각 판정은 운영 GPU 서버가 있어야 제대로 되므로 뒤 단계(선택)로 미룬다.

### 0.5 이 기능 없이 충분한 경우 (정직하게)

- **외부 RAG를 켜지 않는 챗봇만 운영하는 경우** — 모든 답이 관리자가 쓴 문장이므로 "AI 위험 응답"이 생길 곳이 없다. 금지어(No.12)·운영 전환 게이트(No.40)·검토 큐(No.15/44)로 충분하다. (단 입구 규칙 "위기 질문 → 안전 안내"는 RAG와 무관하게 쓸모가 있다.)
- **금융·공공처럼 내부통제 요구가 강한 고객이 당장 없는 경우** — 2인 승인은 조직 통제 기능이라 요구가 없으면 불편만 늘린다.
- **"AI가 틀린 답을 자동으로 잡아 준다"를 기대하는 경우** — 규모 A는 그것을 하지 않는다(R-1).

→ 그래서 §11 Q1에 **"지금은 하지 않음(카탈로그 비고만 정리)"** 선택지를 둔다. 반대로 **외부 RAG를 켜서 금융·공공 고객에게 시연·납품하려면** 규모 A는 "AI 답이 위험 주제를 말하면 어떻게 되나?"라는 질문에 답할 최소 장치다.

**결론**: 최종 사용자에게 AI 자유 문장이 나가는 경로는 **P3 하나**다. 따라서 "환각 탐지"는 **"외부 RAG 답이 근거 문서와 다른 말을 했는가"** 로 재정의한다(J-2). 규칙 기반 답(P1)의 "틀린 답"은 환각이 아니라 **오매칭**이며 기존 기능이 이미 다룬다.

### 1.8 목적

1. 외부 RAG 경로(유일한 AI 자유 생성 경로)에 **입구·출구 규칙 검사**를 두어 위험 주제 답과 고위험 개인정보 형식 노출을 막는다.
2. 운영 챗봇의 답변 교체에 **요청자와 다른 두 번째 승인자**를 둘 수 있게 해 HITL 승인 공백을 메운다.
3. 모두 **LLM 없이** 성립시키고, 모델 판정(환각·편향)은 운영 모델이 준비된 뒤의 선택 단계로 분리한다.
4. 대화 엔진·위젯·동기 턴 지연 예산·외부 RAG 봉인·저장 마스킹 결과를 **바꾸지 않는다.**

| **서버 운영자** | (규모 B·C) LLM 판정자 백엔드 설정 |

### 2.2 사용자 시나리오

**S-1 (규칙 등록 — 관찰부터)**: ADMIN이 금융 챗봇 "가드레일" 메뉴에서 규칙 "투자 권유"를 만든다 — 분류 "투자·재무 조언", 표현 "수익 보장·원금 보장·꼭 사세요·매수 추천" 등, 적용 위치 "AI 답(출구)", 동작 **"기록만"**(기본값). "문장으로 시험하기"에 예시 답을 넣어 걸리는지 본다. 저장하면 즉시(캐시 무효화) 적용된다. 감사 기록이 남는다.

**S-2 (관찰 → 강화)**: 1주일 뒤 현황 화면에서 "투자 권유: AI 답 적중 12건"을 확인하고, 적중한 대화 기록(마스킹본 · 기존 대화 기록 열람 권한·감사 규약)을 몇 건 열어 본다. 오탐이 없다고 판단해 동작을 **"안전 문구로 대체"** 로 바꾸고 대체 문구("투자 판단은 고객님께서 직접 하셔야 하며, 자세한 상담은 영업점으로 문의해 주세요.")를 적는다.

**S-3 (최종 사용자 — 출구 대체)**: 사용자가 "지금 이 펀드 사면 돈 벌어요?"라고 묻는다. 대화 엔진이 답하지 못해 외부 RAG로 넘어가고, 위젯은 평소처럼 대기 문구를 보여 준다. RAG 답에 "수익 보장" 표현이 있어 **답이 대체 문구로 바뀌어** 전달된다. 이 턴은 "RAG 실패"와 같은 경로로 끝나므로, 상담이 켜진 챗봇이면 기존 관찰 창(상담 연결 안내)이 열린다. 대화 기록에는 "가드레일 대체" 표식이 남는다.

**S-4 (입구 — 위기 질문)**: ADMIN이 규칙 "위기 표현"을 적용 위치 "사용자 질문(입구)", 동작 "안전 문구로 대체"로 등록하고 문구에 관리자가 확인한 상담 기관 안내를 적는다. 사용자가 해당 표현을 입력하면 **대화 엔진·RAG를 부르지 않고** 대체 문구가 즉시 나간다(금지어 차단과 같은 모양 · 추가 지연 거의 없음).

**S-5 (입구 — RAG로 안 보냄)**: 규칙 "지시 무시 시도"(표현 "이전 지시를 무시", "시스템 프롬프트" 등)를 동작 "AI로 보내지 않음"으로 등록한다. 해당 질문은 대화 엔진은 정상 처리하되, 엔진이 답하지 못해도 **외부 RAG로 넘기지 않고** 기존 폴백 답으로 끝난다.

**S-6 (RAG 답 개인정보)**: 적재 문서 예시에 주민등록번호 형식이 섞여 있었고 RAG 답에 그 형식이 실린다. 출구에서 형식이 `[주민등록번호]`(기존 마스킹 토큰)로 가려져 전달되고 이벤트가 집계된다. 같은 답의 "2026-09-30까지 신청" 날짜는 **기본 설정에서는 그대로** 나간다(계좌 가림이 꺼져 있으므로).

**S-7 (2인 승인)**: ADMIN A가 환경 모드 챗봇의 "운영 전환 2인 승인"을 켠다(활성 ADMIN 2명 이상일 때만 가능 · 감사). 이후 A가 v12로 운영 전환을 **요청**하면 게이트 평가 결과와 함께 "승인 대기"가 된다. ADMIN B가 승인 대기 목록에서 차이·게이트 결과를 보고 **승인**하면 그 시점에 전환이 실행된다. A는 자기 요청을 승인할 수 없다(버튼 비활성 + 서버 거부). 24시간(설정) 안에 승인이 없으면 만료된다.

**S-8 (긴급 롤백)**: 운영 버전에 문제가 생겨 A가 **직전 운영 버전으로 롤백**한다. 롤백은 2인 승인 대상이 아니며 즉시 실행되고, "단독 실행 롤백" 표식과 감사가 남아 B가 사후에 확인한다.

**S-9 (미리보기)**: EDITOR가 시뮬레이션에서 RAG를 켜고 질문하면, 가드레일이 걸린 경우 "운영에서는 이 답이 '투자 권유' 규칙으로 대체됩니다" 표시와 원래 답을 함께 본다(관리자 화면 한정).

**S-10 (세션 만료)**: 규칙 편집 중 관리자 세션이 만료되면 저장이 거부되고 재로그인 후 다시 저장한다(부분 저장 0). 승인 요청은 서버에 남아 만료 시각까지 유효하다.

### 4.2 입구 적용 — 사용자 질문 (FR-AG2)

| ID | 요구사항 |
|---|---|
| FR-AG2-1 | 적용 순서: **① 입구 금지어(기존 — BLOCK이면 끝) → ② 상담 게이트(기존 — 상담 중이면 사람 대화, 가드레일 미적용) → ③ 위험 규칙 입구 판정 → ④ 대화 엔진**. 정확한 삽입 지점은 architect(공개 대화 서비스 1지점) |

|---|---|
| FR-AG3-1 | 외부 RAG 답이 **기존 성공 판정을 통과한 뒤**, 출구 금지어 마스킹 **전에** 다음을 순서대로 적용한다: ① 위험 규칙 출구 판정(적용 위치 "AI 답"·"둘 다") ② **개인정보 형식 가림**(FR-AG3-4). 순서·위치는 architect(`rag-answer.service.ts` 성공 분기 1지점 — 권고) |
| FR-AG3-2 | 출구 규칙은 **외부 RAG 답에만** 적용한다. 관리자가 쓴 규칙 기반 답(P1)·레거시 API 값(P2)·상담원 메시지(P4)에는 적용하지 않는다(사람이 작성·승인한 문장 · 과차단 방지 — J-3) |
| FR-AG3-3 | **대체**: 답을 대체 문구로 바꾸고 이 턴을 **기존 실패 수렴 경로와 같은 상태(FAILED)** 로 완료한다 — 위젯의 기존 "보류 답변 실패 시 관찰 창" 동작이 그대로 작동한다(위젯 변경 0). 출처 목록은 비운다. 대화 기록은 `answeredByRag=false`·미응답 + 가드레일 표식으로 적재한다(통계상 "RAG 성공"에 들어가지 않음 — 표현 architect) |
| FR-AG3-4 | **개인정보 형식 가림**: `packages/pii-mask`의 정규식을 RAG 답에 적용하되 **선택된 종류만** 가린다. 종류 선택은 챗봇별이며 기본은 **주민등록번호·카드번호 켬 · 계좌번호·전화번호·이메일 끔**(J-7 · P-6). 현재 `maskPii()`는 종류 선택이 없으므로 **출구 전용 옵션(종류 목록 · 날짜 형식 제외)** 을 추가한다 — 기존 `maskPii()`의 기본 결과(저장 경로)는 **바이트 불변**(No.45 FR-0-161 · 방식 architect) |
| FR-AG3-5 | 계좌번호 가림을 켤 때 화면에 **"날짜(예: 2026-09-30)·일부 번호가 계좌번호로 오인되어 가려질 수 있습니다"** 를 표시한다. 날짜 형식(연-월-일) 제외 규칙을 출구 옵션에 둘지는 architect(권고: 둔다). 가림 설정 변경은 감사 대상이다 |
| FR-AG3-6 | 출구 판정·가림은 **예외를 사용자에게 전파하지 않는다** — 판정 중 오류가 나면 **안전 쪽으로**(대체 규칙이 하나라도 켜진 챗봇은 폴백, 아니면 원답 + 오류 이벤트) 수렴한다(방식 architect · EX-AG-6) |
| FR-AG3-7 | 관리자 **시뮬레이션**·**TC 실행**에서 RAG를 부른 경우에도 **같은 판정 함수**로 결과를 계산해 "운영이면: 대체됨(규칙명) / 가림 N건 / 통과"를 표시한다. 미리보기에서는 원답도 함께 보여 준다(관리자 화면 한정 · 이벤트 기록 0) |
| FR-AG3-8 | 출구 판정은 같은 메모리 캐시 사전을 쓰며, 백그라운드 경로에서도 **모델·임베딩 호출 0**(규모 A) |

| ID | 요구사항 |

### 4.5 운영 전환 2인 승인 (FR-AG5)

| ID | 요구사항 |
|---|---|
| FR-AG5-1 | 환경 모드(No.40)가 켜진 챗봇에 **"운영 전환 2인 승인"** 설정(기본 **꺼짐**)을 둔다. 켜기는 `chatbot:deploy` 보유 활성 사용자가 **2명 이상**일 때만 허용한다. 켜기·끄기는 감사 대상이다 |
| FR-AG5-2 | 켜진 챗봇에서 **운영 즉시 전환**은 "요청"이 된다: 대상 버전 · 요청 시점 게이트 평가 결과(No.40) · 요청 사유(선택 · ≤200자 · 마스킹) · 만료 시각(권고 24시간 — 설정 1~168시간) |
| FR-AG5-3 | **승인자 ≠ 요청자**(사용자 id 비교 — 서버 강제). 승인자는 `chatbot:deploy` 보유자. 승인 시 **요청 시점 대상 버전과 운영 포인터가 그대로인지 재검증**(그 사이 다른 전환이 있었으면 거부 — No.28 미리보기 바인딩 선례)하고 게이트를 **다시 평가**한 뒤 기존 전환 경로로 실행한다 |
| FR-AG5-4 | 상태: 대기 → 승인됨(실행 성공/실패) · 반려(사유) · 취소(요청자) · 만료. 챗봇당 **대기 요청 최대 1건**(권고) |
| FR-AG5-5 | **예약 전환(No.28 `SWITCH_PROD_VERSION`)**: 2인 승인이 켜진 챗봇에서는 예약 생성이 요청이 되고, 승인되어야 예약이 유효해진다. 승인 전 예약 시각이 오면 실행하지 않고 "승인 없음"으로 종결(misfire 규약과 같은 모양 — architect) |
| FR-AG5-6 | **예외 — 직전 운영 버전 롤백**: 2인 승인 대상이 아니다(긴급 복구). 즉시 실행하고 "단독 실행 롤백" 표식 + 감사 + 가드레일 현황의 알림 목록에 노출한다(P-5) |
| FR-AG5-7 | 대상 밖: 초안 편집·스테이징 승격·버전 복원(환경 모드에서 초안만 변경)·챗봇 켜기/끄기·게이트 설정·거버넌스 설정(J-6). 추가 대상 요구는 재검토 트리거(§9) |
| FR-AG5-8 | 설정을 끄면 대기 중 요청은 **취소**로 정리된다(자동 실행 0). 활성 `chatbot:deploy` 보유자가 1명으로 줄면 설정은 **자동으로 꺼지지 않고**(승인 없는 설정 변경 0) 요청 화면에 "승인할 수 있는 다른 관리자가 없습니다"를 표시하고, 설정 끄기를 안내한다 |
| FR-AG5-9 | 승인 대기 목록(전역 · `chatbot:deploy`): 챗봇 · 요청자 · 대상 버전 · 현재 운영 버전과의 차이 요약(No.25 차이 재사용) · 게이트 결과 · 만료까지 남은 시간. 1차 알림은 콘솔 배지만(메일·메신저 알림은 No.41 2차 운영 이벤트와 함께 — §9) |

## 6. 비기능 요구사항

### 6.1 성능 (NFR-AGP)

| ID | 요구사항 |
|---|---|
| NFR-AGP1 | ★ 입구 판정 추가 지연 P95 **1ms 이하**(규칙 50 · 표현 2,000 · 입력 500자 기준 — 권고 목표, 개발 PC 실측 가능). 공개 대화 API P95 500ms 불변 |
| NFR-AGP2 | 출구 판정(규칙 + 형식 가림) 추가 지연 P95 **5ms 이하**(답 2,000자 기준) — 백그라운드 경로 |
| NFR-AGP3 | 규칙 캐시는 금지어 캐시와 같은 방식(TTL + 쓰기 즉시 무효화). 턴당 DB 조회 추가 0(캐시 적중 시) |
| NFR-AGP4 | 이벤트 기록은 대화 응답을 기다리게 하지 않는다(비동기 적재 — 기존 로그 `void record()` 선례) |
| NFR-AGP5 | (C) 판정자 호출은 RAG 시간 제한(`ragTimeoutMs`) 안에서 끝나거나 포기한다 · 보류 답변 TTL을 늘리지 않는다 |

### 6.2 보안 (NFR-AGS)

| ID | 요구사항 |
|---|---|
| NFR-AGS1 | 표현 매칭은 리터럴/토큰만(정규식·ReDoS 0 — 금지어 NFR-S12 상속) |
| NFR-AGS2 | 대체 문구는 텍스트만 · 출구 금지어 마스킹 통과 · HTML/링크 불가 |
| NFR-AGS3 | 2인 승인은 **서버에서** 요청자 ≠ 승인자를 강제한다(화면 비활성만으로 막지 않음) · 승인 요청은 대상 버전·운영 포인터 바인딩 |
| NFR-AGS4 | 이벤트·요청 테이블에 사용자 발화·AI 답 문장 0 |
| NFR-AGS5 | 교차 챗봇 접근 404 · 모든 변경 감사 |
| NFR-AGS6 | 출구 가림은 **적재 문서 정리의 대체물이 아니다** — 화면에 "형식이 정해진 번호만 가립니다. 이름·주소 등은 가리지 못합니다" 안내(No.21 FR-DC2-3 선례) |

### 6.3 신뢰성 (NFR-AGR)

| ID | 요구사항 |
|---|---|
| NFR-AGR1 | 규칙 캐시 적재 실패 시: 입구 = **통과**(대화 중단 금지) + 오류 로그 · 출구 = FR-AG3-6 안전 쪽 수렴 |
| NFR-AGR2 | 승인 실행 중 전환 실패는 요청을 "승인됨·실행 실패"로 남기고 운영 포인터 불변(기존 전환 원자성) |
| NFR-AGR3 | 서버 재시작 후에도 대기 요청·만료 판정이 유지된다(DB 상태 · 만료는 조회 시 판정 또는 기존 예약 루프 — architect) |

### 6.4 접근성 · UI (NFR-AGA)

| ID | 요구사항 |
|---|---|
| NFR-AGA1 | 동작·상태(기록만/대체/AI로 안 보냄 · 대기/승인/반려/만료)는 **글자로** 표시(색만 금지) |
| NFR-AGA2 | 화면 문구에 "환각 탐지"를 쓰지 않는다(규모 C 실측 전) — "위험 응답 규칙" · "개인정보 형식 가림" · "운영 전환 2인 승인" |
| NFR-AGA3 | 규칙 표·승인 목록은 키보드 조작·스크린리더 읽기 가능(`UIUX_준수기준.md`) |

### 6.5 유지보수성 (NFR-AGM)

| ID | 요구사항 |
|---|---|
| NFR-AGM1 | 규칙 판정은 DB·Nest 무의존 **순수 함수**(입력 = 텍스트 + 규칙 목록 + 위치 → 출력 = 최종 동작 + 적중 목록)로 두고 단위 시험한다. 금지어 `detect()`를 재사용하되 금지어 모듈의 동작은 바꾸지 않는다 |
| NFR-AGM2 | 출구 검사는 교체 지점 1곳(포트)으로 두어 규모 C의 판정자를 같은 자리에 붙인다 |
| NFR-AGM3 | 2인 승인 상태 기계는 대상 동작을 열거형으로 두어 재검토 트리거(복원·예약 외 동작) 때 확장 1곳으로 흡수한다 |
| NFR-AGM4 | `pii-mask`의 출구 전용 옵션은 기존 함수 서명·기본 동작을 바꾸지 않는 **선택 인자**로 추가한다(기존 스냅샷 시험이 그대로 통과) |

### 11.1 AskUserQuestion용 쉬운 문구(핵심 6건)

**Q1. 이번에 어디까지 할까요?** (우리 챗봇에서 AI가 문장을 직접 지어 내보내는 곳은 '문서 검색 답변(외부 RAG)' 한 곳뿐입니다)
- ① 지금은 하지 않기 — 목록에 "이렇게 해석한다"는 메모만 남김
- ② **위험한 주제를 규칙으로 걸러 안전한 문구로 바꾸고, AI 답에서 주민번호·카드번호를 가리고, 운영 챗봇 교체 때 두 번째 관리자가 확인하게 하기. AI 없이 동작 (추천)**
- ③ ②에 더해, 위험 질문 모음·차별 점검 질문 짝을 한꺼번에 돌려 보는 점검 도구까지
- ④ ③에 더해, AI 답이 근거 문서와 다른 말을 하는지 실시간으로 검사까지 — 운영 AI 서버가 있어야 제대로 됨

**Q2. "AI가 지어낸 답(환각)"을 어디에서 찾을까요?**
- ① **문서 검색 AI 답에서만 (추천)** — 관리자가 직접 쓴 답은 지어낼 수가 없고, 엉뚱한 답에 연결되는 문제는 이미 있는 대량 시험·👎 검토로 다룹니다
- ② 모든 답에서
- ③ 관리자 화면의 AI 예문 제안까지 — 이미 사람 승인을 거치고 있어 중복입니다

**Q3. 위험 규칙을 어디에, 어떻게 적용할까요?**
- ① **사용자 질문과 AI 답 모두에 적용. 걸리면 '기록만 / 안전 문구로 바꾸기 / AI에게 안 보내기' 중 선택. 새 규칙은 '기록만'으로 시작해 지켜본 뒤 강화. 관리자가 쓴 답은 건드리지 않음 (추천)**
- ② 사용자 질문에만 적용
- ③ 관리자가 쓴 답까지 모든 답에서 차단 — 정상 답이 막힐 위험이 큼

**Q4. AI로 AI를 검사하는 부분(환각·차별 판정)은 어떻게 할까요?**
- ① **이번 범위는 AI 없이 규칙으로만 하고 지금 개발 PC에서 합격 판정. AI 판정은 운영 AI 서버가 준비되면 그때 (개발 PC 작은 모델 결과는 '동작 확인'만) (추천)**
- ② 모든 판단을 운영 AI 서버에서 잰 뒤로 미룸 — 담당자가 생길 때까지 대기
- ③ 개발 PC의 작은 모델로 판정 — 정확도가 부족해 권하지 않음

**Q5. 사람 승인은 어디까지 넣을까요?** (AI 예문은 승인 후 반영, 👎·못 한 답은 검토 목록, 운영 교체는 관리자 권한, 상담원 연결은 이미 있습니다)
- ① 이미 있는 승인 절차를 정리해 보여 주기만
- ② **①에 더해, 운영 챗봇 교체(예약 교체 포함)에 '두 번째 관리자 승인'을 챗봇별로 켤 수 있게. 기본은 꺼짐, 긴급 되돌리기는 예외 (추천)**
- ③ 복원·설정 변경까지 모두 두 사람 승인 — 운영이 느려짐

**Q6. AI 답에 개인정보 형식이 섞여 있으면 어떻게 할까요?** (문서에 들어 있던 번호가 AI 답에 그대로 실릴 수 있습니다. 다만 지금 쓰는 자동 가림은 '2026-09-30' 같은 날짜를 계좌번호로 착각하는 한계가 있습니다)
- ① **주민번호·카드번호만 기본으로 가림. 계좌·전화·이메일은 챗봇마다 선택 (추천)** — 날짜·기관 대표번호 안내가 망가지지 않음
- ② 다섯 가지 모두 가림 — 날짜와 고객센터 번호까지 가려질 수 있음
- ③ 가리지 않음
