## 1. 배경 / 목적

### 1.1 배경 — "되돌릴 수단이 없다"는 사실이 세 번 기록되어 있다

선행 그룹들이 **같은 구멍**을 각자 다른 자리에서 확인하고, 매번 **"No.25의 몫"** 이라며 비워 두었다.

| 기록 위치 | 원문(요지) | 이 그룹이 메우는 것 |
|---|---|---|
| **ADR-0002** §맥락 | "이 시스템에는 아직 **버전 스냅샷/롤백(No.25)도** … 없어 **되돌릴 수단이 전무하다**." | 복원 수단 자체 |
| **ADR-0016** §감수비용 5 · `security-audit-설계.md` §9.6 | "`beforeValue`가 **부분 스냅샷**이라 이력으로 복원할 수 없다(`examples`→`exampleCount`). 복원은 **No.25의 본체**이며, `beforeValue`로 되돌리기를 제공하면 그 설계를 **선점**하게 된다." | 감사로그가 **의도적으로 담지 않은** 완전한 상태 |
| **ADR-0029** §2 (3) · `개발명세서.md` 미도입 결정 ⑨ | "챗봇 자산 스냅샷 — **기각**. No.25의 본체(스냅샷 저장소·복원·정리 배치·용량 정책)를 **선점**한다." | 스냅샷 저장소·보존 정책 |

여기에 직전 두 그룹이 **실제로 위험을 키웠다**.

| 위험 | 출처 | 지금 할 수 있는 것 | 못 하는 것 |
|---|---|---|---|
| **승인 한 번에 예문 수십 건이 즉시 반영**(`appliedImmediately === true`) | No.16/23 학습 고도화 | 승인 **전에** 영향 확인(No.20 M2) | 승인 **후** 되돌리기 — 어떤 예문이 증강분인지 `Intent.examples`에 표시가 없다 |
| **엑셀 5,000행 임포트·일괄 삭제** | No.6/9(ADR-0007) | 감사로그에 `"대량등록 (N건)"` 요약 1건 | 임포트 직전 상태로 되돌리기 |
| **"어제는 통과, 오늘은 실패"를 발견** | No.19/20 M1 | 회귀 N건과 환경 지문 차이 확인 | **어제 상태로 돌아가기** — 원인을 찾아도 복구는 수작업이다 |

> **요약**: No.19/20은 **회귀를 발견**하는 도구이고 No.25는 **회귀에서 복구**하는 도구다. 앞의 것만 있으면 운영자는 "무엇이 깨졌는지 알지만 고칠 수단이 없는" 상태에 놓인다.

### 1.2 이미 있는 것과 없는 것 (코드 확인)

| 자산 | 실제 구현 | 이 그룹에서의 취급 |
|---|---|---|
| **`ChatbotsService.copy()`** (`chatbots.service.ts` 223~263행) | `Chatbot` 행 **1개만** 새로 만든다(`name`/`slug`/`avatarUrl`/`description`/`skin`, `status: 'DRAFT'`). **의도·키워드·동음이의어·노드·조인·컨텍스트·FAQ·답변설정을 전혀 복사하지 않는 얕은 복사**다 | **재사용할 수 없다**(깊은 부분이 없다). 반대로 **이 그룹의 직렬화기가 향후 깊은 복사의 기반**이 된다(J-12). `copy()`는 **이번에 수정하지 않는다** |
| **`DialogueBundleService.build(chatbotId)`** (`dialogue-bundle.service.ts` 65~146행) | 대화 자산 **6종**(Intent·Keyword·HomonymDictionary·DialogNode(+`intentIds`/`keywordIds` 조인 평탄화)·ContextVariable·FaqEntry)을 **JSON 파싱까지 끝낸 `DialogueBundle`** 로 조립한다. 캐시를 거치지 않는 **DB 직조회** 경로다 | ★ **스냅샷 직렬화의 1차 재사용 후보**(J-2). 단 현재 `Promise.all` 6회 조회라 **트랜잭션 일관 읽기가 아니다** — 스냅샷용으로는 일관 읽기 보장이 필요하다(FR-H1-6) |
| **`DialogueBundleService.invalidate(chatbotId)`** (49~53행) | ① 번들+인덱스 캐시 ② 벡터 캐시(`VectorCacheService`) 무효화 ③ **재색인 예약**(`ReindexQueueService.schedule`)을 **한 지점**에서 수행한다 | 복원 직후 **1회 호출**로 캐시·색인 정합을 맞춘다(FR-H3-12) |
| **`IndexerService.reindexChatbot()`** | `(ownerType, ownerId, slotIndex)` 키로 기존 벡터를 찾고 **`textHash`가 같고 `READY`면 재임베딩하지 않는다**(FR-N1-19) | ★ **ID를 보존하면 복원 뒤 재임베딩이 "바뀐 문장"으로 한정된다**(J-5의 핵심 근거 2) |
| **`judgeClassifierStale()`** (`classifier/lib/stale-judge.ts`) | stale 조건 ③ `EXAMPLES_DRIFTED`는 **`current − atTrain > 50`** — **예문이 늘어난 경우만** 감지한다. ② `INTENTS_DRIFTED`는 의도 수 **10% 이상 변동** | ⚠ **증강 롤백(예문 감소)은 stale로 감지되지 않는다.** 복원이 분류기를 명시적으로 무효화해야 한다(J-8) |
| **`AuditLog`** | 전 도메인 쓰기의 **화이트리스트 부분 스냅샷**(8KB 상한, `examples`→`exampleCount`). 대량 작업은 **배치 1건 요약**. `audit_logs(chatbotId, createdAt)` 인덱스 있음 | **복원 원천으로 쓰지 않는다**(ADR-0016). "두 버전 사이에 누가 무엇을 바꿨나"는 **기존 인덱스로 시간 범위 조회**해 링크한다(J-10) |
| **`TestRun.envFingerprint`** | 자산 건수 6종·`embeddingModelId`·임계값 3종·저하 여부 | ADR-0029 §9 재검토 트리거: "**No.25 착수 시 `envFingerprint`를 스냅샷 id로 승격할 수 있다**" → FR-H2-9(⚠ 선택) |
| **`개발명세서.md` §3** | `ChatbotVersion` — "버전 스냅샷(복원용) · 25" **이름만 예약**된 행 | 이 그룹이 **실체화**한다 |

**없다**: 챗봇 자산의 **완전한 시점 상태** 저장소, 복원 경로, 버전 간 차이 계산, 보존 정책.

### 1.3 목적

1. 챗봇의 **대화 동작을 결정하는 자산 전체**를 한 시점 단위로 **완전하게** 저장한다(감사로그의 부분 스냅샷과 다르다).
2. **대량 변경 직전에 자동으로** 저장해, 관리자가 미리 챙기지 않아도 **롤백 지점이 항상 존재**하게 한다.
3. 버전 목록(업데이트 히스토리)과 **버전 간 / 버전↔현재 차이**를 보여 준다.
4. 선택한 버전으로 **즉시·원자적으로** 되돌리며, **복원 자체도 되돌릴 수 있게** 한다(복원 직전 자동 백업).
5. 복원이 **다른 기능을 조용히 깨뜨리지 않게** 한다 — 특히 **No.19 TC**(ID 기반 기대값), **1단계 색인**, **분류기**, **진행 중 대화**.
6. **No.40(환경 분리)의 영역을 침범하지 않는다** — 환경·트래픽 전환·승격·태깅을 만들지 않는다.

### 1.4 이 문서의 핵심 판단 14건 (⚠ = PM 확인 필요)

| # | 쟁점 | 결정(제안) | 근거 요약 |
|---|---|---|---|
| **J-1** | **스냅샷에 무엇을 담는가** | **"대화 동작을 결정하는 챗봇 종속 자산"만** 담는다: 대화 자산 6종 + 노드 조인 2종 + `ChatbotAnswerSetting` + `Chatbot` 표시 설정 4필드(`name`/`avatarUrl`/`description`/`skin`). **`slug`·`status`·`groupId`·`Channel`·전역 `BannedWord`·파생/운영/검증 데이터는 제외**한다(§4.1 표) | 기준은 **"되돌렸을 때 응답이 그 시점과 같아지는가"** 와 **"되돌려서는 안 되는 사실·외부 계약인가"** 두 가지다. `slug`는 외부 임베드 URL 계약, `status`/`Channel.enabled`는 **배포 행위**(= No.40/No.28 영역), `BannedWord`는 **전역**이라 한 챗봇의 복원이 다른 챗봇을 바꾸게 된다. ⚠ 표시 설정 포함 여부는 **P-2** |
| **J-2** | **저장 형식** | **전체 스냅샷**(증분 아님) · **정규화 JSON 1개** + `schemaVersion`(정수) + `contentHash`(타임스탬프 제외 정규 직렬화의 sha256) + 항목별 건수. 자산 부분의 형태는 **`DialogueBundle`(shared-types)을 재사용**한다 | 증분(델타 체인)은 중간 1개가 깨지면 이후 전부가 복원 불가가 되고, 정리(보존 정책) 때 **재기저화**가 필요하다. 챗봇 1개 자산은 통상 **수백 KB~수 MB**라 전체 저장이 감당 가능하다(§4.3). `DialogueBundle`은 이미 엔진 입력의 **단일 정의**이므로 두 번째 직렬화 규약을 만들지 않는다 |
| **J-3** | ⚠ **스냅샷 생성 시점** | **수동 + 자동 둘 다.** 자동은 **대량 변경 5종 직전 + 복원 직전**에만 만든다: ① 엑셀 임포트 커밋(의도/키워드/FAQ) ② 일괄 삭제(의도/키워드/FAQ) ③ **증강 제안 승인** ④ 학습현황 **일괄** 반영 ⑤ 복원(= 복원 직전 백업, J-6). **단건 CRUD에는 자동 스냅샷을 만들지 않는다.** 직전 스냅샷과 `contentHash`가 같으면 **생성하지 않는다** | 단건 편집마다 만들면 보존 한도(30건)가 **몇 분 만에 소진**되어 정작 필요한 "임포트 전" 지점이 밀려난다. 단건 변경의 추적은 **감사로그의 역할**이다. ★ **증강 승인 직전 자동 스냅샷이 "승인 후 되돌리기"의 유일한 안전망**이다 — `Intent.examples`에는 어느 예문이 증강분인지 표시가 없어, 승인 직전 상태를 저장해 두지 않으면 **증강분만 골라 빼는 것이 불가능**하다(§4.2.2) |
| **J-4** | ⚠ **복원 방식** — 전체 교체 vs 부분 복원 | **1차는 "스냅샷 범위 전체의 원자적 교체"만** 제공한다. 항목 단위 부분 복원(의도 1개만 되돌리기)은 **범위 밖** | 부분 복원은 **참조 정합 문제**를 만든다 — 노드 1개를 되돌리면 그 노드가 참조하는 의도·키워드·컨텍스트·`targetNodeId`가 현재에 없을 수 있고, 반대로 의도 1개를 되돌리면 현재 노드의 조건이 깨질 수 있다. 이를 해결하려면 **의존성 폐포 계산 + 충돌 해소 UI**가 필요하며 그것만으로 한 그룹 분량이다. 대신 **diff 화면에서 항목별 과거 값을 보고 복사**할 수 있게 한다(FR-H2-6). ⚠ **P-3** |
| **J-5** | ★ **ID를 보존하는가** | **보존한다(필수).** 복원된 모든 행은 **스냅샷에 기록된 원래 `id`** 로 되살아난다 | ① **No.19 TC가 ID로 기대값을 저장한다**(`TestCase.expectedTargetId`, ADR-0029 — 이름 변경 내성 때문에 일부러 ID로 정했다). ID가 바뀌면 복원 직후 **TC 세트 전체가 `UNRESOLVED`** 가 되어 "복원이 잘 됐는가"를 **검증할 수단 자체가 사라진다** ② **재색인 비용**: `EmbeddingVector`는 `ownerId`+`slotIndex`+`textHash`로 재사용된다. ID가 바뀌면 **챗봇 전체를 재임베딩**해야 한다(CPU 배포에서는 수 분 — 메모리 기록된 `EMBEDDING_TIMEOUT_MS` 위험과 직결) ③ `ConversationLog.matched*Id`·`UnansweredQuestion.resolvedIntentId`·`AuditLog.targetId`는 FK 없는 **사실 기록**인데 ID가 바뀌면 통계의 "인기 의도"·이력 추적이 **과거와 끊긴다** ④ 진행 중 대화의 클라이언트 봉투(ADR-0009)가 노드/컨텍스트 ID를 들고 있다 — 보존하면 **대부분의 대화가 끊기지 않는다** |
| **J-6** | **복원 직전 자동 백업**(복원의 복원) | **필수.** 복원은 **현재 상태를 `BEFORE_RESTORE` 스냅샷으로 먼저 저장한 뒤에만** 진행한다. 백업 저장이 실패하면 **복원을 중단**한다(fail-closed) | "되돌릴 수 없는 되돌리기"는 ADR-0002가 경계한 **복구 불가 파괴 동작**이 된다. 백업이 있으므로 복원은 **가역 동작**이 되고, 그래서 권한을 ADMIN 전용으로 올리지 않아도 된다(J-11) |
| **J-7** | **버전 간 차이(diff) 범위** | **① 스냅샷 ↔ 현재 ② 스냅샷 ↔ 스냅샷.** 자산 종류별 `추가/삭제/변경` 건수 → 항목 목록 → **필드 단위 차이**(예문·동의어·대체질문은 **집합 차이**, 노드 아웃풋은 **변경 여부 + 전/후 원문**). 매칭 키는 **ID**. **저장하지 않고 조회 시점에 계산**한다 | ID 보존(J-5) 덕분에 ID가 곧 안정 키다. 삭제 후 같은 이름으로 재생성된 항목은 `삭제 1 + 추가 1`로 보이며, **"이름 동일·ID 상이" 힌트**를 붙인다. 계산 결과 저장은 ADR-0029 §2의 "비교 결과는 저장하면 낡는다"와 같은 이유로 하지 않는다 |
| **J-8** | ★ **파생 데이터를 복원 후 어떻게 맞추는가** | **파생 데이터는 스냅샷에 담지 않고 복원 후 재계산/무효화한다**: 임베딩 → **재색인 예약**(바뀐 문장만) · **분류기 → 모델 삭제**(재학습 권유) · 번들/벡터/답변설정 캐시 → 무효화 · 질의 임베딩 캐시 → **무효화 불필요** · 증강 제안·TC·실행 결과·로그 → **변경하지 않음** | **분류기 삭제의 코드 근거**: `judgeClassifierStale()`의 `EXAMPLES_DRIFTED`는 **증가만** 본다. 증강 50건 승인 → 분류기 재학습 → **증강 롤백**하면 예문이 줄었으므로 stale이 **뜨지 않고**, 증강분으로 학습된 모델이 미응답 큐 추천에 **계속 쓰인다**. 재학습은 수 초이고 대화 경로와 무관하므로(ADR-0027) 삭제가 가장 싸고 확실하다. **질의 임베딩 캐시**는 `(질문 문장, modelId)`만의 함수라 자산과 무관하다 |
| **J-9** | ⚠ **운영 중(ACTIVE) 챗봇 복원과 진행 중 작업** | **ACTIVE 복원을 허용**한다(= "즉시 롤백"의 주 용도). 단 ① 해당 챗봇에 **`QUEUED`/`RUNNING` 상태의 `TrainingJob` 또는 `TestRun`이 있으면 `409`** ② **같은 챗봇 동시 복원 금지** ③ 미리보기 이후 자산이 바뀌었으면 `409`(재확인 요구) ④ 진행 중 대화는 **ADR-0009의 매 턴 재검증에 맡긴다**(별도 차단 없음) ⑤ `ARCHIVED` 챗봇은 복원 불가 | 진행 중 작업을 강제 취소하는 대신 **거부**하는 이유: 분류기 학습은 끝나면서 **복원 전 데이터로 학습한 모델을 upsert**하고, TC 실행은 **복원 전 번들로 판정**한 결과를 남긴다 — 둘 다 복원과 **뒤섞인 결과**를 만든다. 작업은 수 초~수 분이며 사용자가 취소할 수 있다(No.19). 대화는 서버가 매 턴 번들 기준으로 재검증하므로(ADR-0009 §2) 없는 노드/컨텍스트는 **자동으로 폐기**된다 |
| **J-10** | **"업데이트 히스토리"와 감사로그의 관계** | **역할을 나눈다.** 감사로그 = **누가·언제·무엇을**(행위 단위, 부분 스냅샷) / 버전 이력 = **그 시점의 전체 상태**(시점 단위, 완전 스냅샷). 버전 이력은 감사로그를 **복제하지 않고** "두 버전 사이의 감사 레코드"로 **링크**한다. 복원은 감사로그에 **요약 1건**(신규 동작 `RESTORE`)으로 남기며, 복원이 바꾼 개별 항목 수백 건을 감사 레코드로 풀어 쓰지 않는다 | 감사로그에 복원의 개별 변경을 전부 기록하면 복원 1회에 수백~수천 건이 쌓이고, 전부 "복원됨"이라는 같은 사유다(ADR-0016 §7 대량 요약 규약과 같은 판단). 반대로 버전 이력에 행위자별 변경 내역을 다시 저장하면 **감사로그와 두 벌**이 된다 |
| **J-11** | ⚠ **권한** — 복원은 파괴적인가 | **신규 권한 문자열 0종을 권고**한다. 조회 `dialogue:read` · 수동 생성/라벨/고정/삭제 `dialogue:write` · **복원은 `dialogue:write` + `chatbot:write` 둘 다**(EDITOR 이상). 대안: `chatbot:restore` 신설(ADMIN 전용, 15→16종) | 복원은 대화 자산(`dialogue:*`)과 답변설정·표시설정(`chatbot:write` — 현재 `answer-settings.controller.ts`가 쓰는 권한)을 **함께** 바꾼다. **J-6(자동 백업)으로 복원이 가역 동작**이므로 ADR-0002의 "복구 불가 동작" 등급(`chatbot:purge` = ADMIN 전용)에 해당하지 않는다. 또한 "즉시 롤백"은 사고 현장의 EDITOR가 할 수 있어야 의미가 있다. ⚠ 조직 통제상 ADMIN 승인이 필요하면 대안 채택 — **P-5** |
| **J-12** | **`copy()`를 깊은 복사로 확장해 재사용하는가** | **하지 않는다.** 관계가 반대다 — **이 그룹의 캡처(직렬화)가 먼저**이고, 깊은 복사는 나중에 "캡처 + **ID 재매핑** + 다른 챗봇에 적재"로 만들 수 있다. 이번에는 `copy()`를 **수정하지 않는다** | 깊은 복사는 ID를 **새로 발급**해야 하고(두 챗봇이 같은 ID를 가질 수 없다), 복원은 ID를 **보존**해야 한다(J-5) — 적재 규칙이 정반대다. 공통 부분은 **캡처와 참조 그래프 검증**뿐이므로 그 두 함수를 순수 함수로 분리해 두는 것으로 충분하다(NFR-HM2). 깊은 복사 자체는 **No.40(쌍둥이 챗봇) 또는 No.1 고도화**의 몫이다 |
| **J-13** | **GPU 필요도 1이 맞는가** | **맞다(1 유지).** | 자체 연산은 DB 읽기·JSON 직렬화·sha256·집합 차이·트랜잭션 쓰기뿐이다(§1 기준표 "1~2 CPU 전용 — CRUD/설정"). 복원 후 재색인은 **기존 ml-worker에 위임**되며 ID 보존으로 **바뀐 문장만** 임베딩한다(J-5 ②) — ADR-0024가 위임처의 등급을 따로 매긴 것과 같은 논리. §4.10 |
| **J-14** | **No.40과의 경계** | 이 그룹은 **"한 챗봇 안에서 시간축으로 되돌리기"** 만 한다. **환경(Dev/Staging/Prod)·환경 간 승격·트래픽 전환/분할·배포 태깅·복원 예약·타 챗봇으로 복원**을 만들지 않는다. 버전 **라벨**은 자유 메모이며 **의미를 가진 태그가 아니다** | 카탈로그 §4-1 No.40 비고: "25번은 **사후 복원**이고 이건 **배포 전 격리 검증**". 라벨에 `prod` 같은 의미를 부여하는 순간 "prod 라벨 버전을 배포한다"는 요구가 따라오며 그것이 No.40이다. §4.9 |

### 1.5 원본 근거 인용

**근거 1 — 카탈로그 No.25 원문**(`기능요구사항.md` §3 62행):
> "챗봇 복원/버전 이력관리 | **업데이트 히스토리 조회, 이전 버전 즉시 롤백** | GPU 1 | 사유: **버전 스냅샷 저장/복원** | 구축형 ○ 구독형 ○"

→ 요구는 **세 개**다: ① 히스토리 조회(J-10, §4.4) ② **"즉시"** 롤백(동기 처리, J-9, NFR-HP3) ③ 스냅샷 저장/복원(J-2, J-4). "즉시"는 **예약·승인 워크플로우 없이 바로**라는 뜻으로 읽는다 — 예약은 No.28이다.

**근거 2 — No.40 비고**(같은 문서 89행):
> "25번(챗봇 버전 롤백)은 **'사후 복원'** 이고 이건 **'배포 전 격리 검증'**"

→ **J-14**. 환경·트래픽 전환·태깅은 No.40 원문("환경별로 버전을 **태깅·트래픽 전환**")에 속한다.

**근거 3 — ADR-0029 §2 (3)**:
> "챗봇 자산 스냅샷 | 기각 | **No.25의 본체를 선점**한다. 스냅샷 저장소·복원·정리 배치·용량 정책이 통째로 끌려 들어온다"

→ 이 문서가 다뤄야 할 목록이 **정확히 이 4개**다: 저장소(§4.3)·복원(§4.6)·정리(§4.3.3)·용량(§4.3.2).

**근거 4 — ADR-0016 §감수비용 5**:
> "`beforeValue`가 부분 스냅샷이라 이력으로 복원할 수 없다 → 복원은 No.25의 본체이며, `beforeValue`로 되돌리기를 제공하면 그 설계를 선점하게 된다."

→ **J-10**. 감사로그를 복원 원천으로 쓰지 않는다 — 감사로그는 **의도적으로 부분**이다.

**근거 5 — GPU 구간 정의**(`기능요구사항.md` §1):
> "| 1~2 | **CPU 전용** — CRUD/설정/통계조회/규칙매칭 |"

→ **J-13**.

## 2. 사용자 역할 및 시나리오

### 2.1 역할

`security-audit.md` §2.1의 역할 3종을 상속한다. **신규 권한 문자열 0종을 권고**한다(J-11).

| 역할 | 이 그룹에서의 활동 | 권한(권고안) |
|---|---|---|
| **ADMIN** | EDITOR의 모든 활동 + 두 버전 사이 **감사 레코드 링크** 열람 | `dialogue:read/write` + `chatbot:write` + `audit:read` |
| **EDITOR** | 버전 저장·라벨·고정·삭제·차이 조회·**복원**(이 그룹의 주 사용자) | `dialogue:read/write` + `chatbot:write` |
| **VIEWER** | 버전 목록·차이 **조회만**. 저장·고정·삭제·복원 버튼이 **렌더되지 않는다** | `dialogue:read` |
| 최종 사용자 | 이 기능의 존재를 알 수 없다. 복원 순간 **진행 중 대화가 가능한 한 끊기지 않는 것**만 체감한다(S-7) | — |

### 2.2 사용자 시나리오

**S-1. 증강 승인을 되돌린다 (EDITOR · ★ 핵심 시나리오)**
오전에 `환불규정문의` 의도에 증강 예문 18건을 승인했다. 오후에 상담팀이 "반품 질문에 환불 규정이 나간다"고 알려 온다. 편집자가 `버전 이력`을 열자 맨 위에 **`v27 · 자동 · 증강 승인 직전 · 09:42 · 편집자A`** 가 있다. `현재와 비교`를 누르면 **`의도 ~1 : 환불규정문의 예문 +18`** 만 보인다. `이 버전으로 복원`을 누르고, 미리보기에서 되돌아갈 변경 18건을 확인한 뒤 확정한다. 3초 뒤 `v28 · 복원 직전 백업`이 생기고 자산은 v27로 돌아간다. 편집자는 곧바로 No.19의 `전체 회귀` 세트를 실행해 **`통과 468 → 471`** 을 확인한다 — **TC는 ID가 그대로라 전부 유효하다.**

**S-2. 엑셀 임포트를 잘못 올렸다 (EDITOR)**
FAQ 1,200건 엑셀을 올렸는데 답변 열이 한 칸씩 밀려 있었다. 커밋 직전에 **`v31 · 자동 · FAQ 대량등록 직전`** 이 만들어져 있다. 복원하면 임포트 이전으로 돌아간다. 그 사이에 다른 편집자가 의도 1개를 고쳤다면 미리보기의 차이 목록에 **그 변경도 함께 되돌아간다**고 표시되며, 편집자는 그것을 보고 확정하거나 취소한다(S-5).

**S-3. 캠페인 전에 수동으로 저장해 둔다 (EDITOR)**
대규모 시나리오 개편 전에 `버전 저장`을 누르고 라벨 `"5월 개편 전"`, 메모를 남긴다. 이 버전을 **고정(pin)** 해 보존 정책이 지우지 못하게 한다.

**S-4. 무엇이 바뀌었나만 본다 (VIEWER)**
운영 모니터가 `v20`과 `v25`를 비교한다. 노드 `배송조회 응답`의 아웃풋이 바뀌었다는 것과 **전/후 원문**을 볼 수 있다. 복원 버튼은 보이지 않는다. **"그 사이 누가 바꿨나"** 링크도 보이지 않는다(`audit:read`가 없다).

**S-5. 미리보기 후 다른 사람이 편집했다 (EDITOR)**
미리보기를 띄워 둔 사이 동료가 FAQ 1건을 수정했다. 확정하자 **`409 — 미리보기 이후 자산이 변경되었습니다. 차이를 다시 확인해 주세요`** 가 뜨고, 미리보기가 자동 갱신된다. **동료의 수정이 사용자 모르게 덮어써지지 않는다.**

**S-6. 학습이 돌고 있다 (EDITOR)**
분류기 재학습 작업이 실행 중일 때 복원을 시도한다. 미리보기의 차단 사유에 **`진행 중인 작업이 있습니다: 분류기 학습(진행률 60%)`** 이 뜨고 복원 버튼이 비활성이다. 작업이 끝나면 활성화된다.

**S-7. 운영 중 복원과 진행 중 대화 (최종 사용자 · ACTIVE)**
커피 주문 컨텍스트 폼을 2단계까지 채운 사용자가 있다. 그 순간 관리자가 복원했다. 복원 대상 버전에도 같은 컨텍스트(같은 ID)가 있으므로 **사용자는 3단계를 그대로 이어 간다.** 복원 대상 버전에 그 컨텍스트가 없었다면 다음 턴에서 서버 재검증이 봉투를 폐기하고 **일반 매칭으로 자연스럽게 복귀**한다(ADR-0009) — 오류 화면은 뜨지 않는다.

**S-8. 복원을 되돌린다 (EDITOR)**
v27로 복원한 뒤 보니 오전 증강분 중 일부는 좋은 예문이었다. `v28 · 복원 직전 백업`으로 다시 복원하면 **복원 전 상태로 정확히 돌아간다**(이때도 `v29 · 복원 직전 백업`이 생긴다). 원하는 예문만 골라 넣으려면 v27↔v28 차이 화면에서 **해당 예문을 복사**해 의도 편집 화면에 붙여 넣는다(부분 복원은 1차 범위 밖 — J-4).

**S-9. 복원 후 의미 매칭 (운영자)**
복원 직후 `임베딩 색인: 재계산 중 (12/18)` 배지가 잠시 보인다. ID가 보존됐으므로 **내용이 바뀐 18문장만** 다시 임베딩된다. 그동안 해당 문장은 **규칙 매칭으로만** 응답되고, 나머지 수천 문장의 의미 매칭은 영향받지 않는다.

**S-10. 오래된 버전이 복원되지 않는다 (EDITOR)**
1년 전 스냅샷(`schemaVersion: 1`)을 복원하려 한다. 서버가 **업캐스터로 현재 형식(`2`)으로 변환**해 미리보기를 보여 준다. 변환 규칙이 없는 형식이라면 **`이 버전은 현재 시스템에서 복원할 수 없습니다(형식 v0)`** 로 차단되고, **내용 조회는 가능**하다.

**S-11. 금지어가 들어 있는 버전 (EDITOR)**
복원 대상 버전의 FAQ 답변에 현재 금지어로 등록된 단어가 있다. **복원은 막지 않는다** — 금지어는 **전역 사전**이며 스냅샷에 포함되지 않고(J-1), 대화 시점의 필터가 그대로 동작한다. 미리보기가 **"현재 금지어 사전과 일치하는 문구 N건"** 을 경고로 알려 준다(참고 정보).

**S-12. 접근성 (EDITOR)**
차이 화면의 `추가/삭제/변경`은 **색상만이 아니라 `+`/`−`/`~` 기호와 텍스트 라벨**로 구분된다. 복원 확인 대화상자는 포커스가 **취소 버튼**에 먼저 놓이고(파괴적 동작의 기본값), 결과는 `aria-live="polite"`로 안내된다.

## 4. 기능별 요구사항

### 4.1 스냅샷 대상 — J-1 결정

**판단 기준 2가지**: ① **되돌렸을 때 대화 응답이 그 시점과 같아지려면 필요한가** ② **되돌려서는 안 되는 사실 기록·외부 계약·전역 설정·배포 행위인가**.

#### 4.1.1 포함 (스냅샷 범위 = 복원 범위)

| 모델(`schema.prisma`) | 포함 필드 | 근거 |
|---|---|---|
| `Intent` | `id`, `name`, `description`, `examples[]`, `createdAt` | 1단계 매칭 입력. `nameNormalized`는 **저장하지 않고 복원 시 `normalizeText()`로 재계산**(ADR-0006 — 정규화 규칙이 바뀌어도 일관) |
| `Keyword` | `id`, `name`, `description`, `synonyms[]`, `createdAt` | 노드 조건 입력 |
| `HomonymDictionary` | `id`, `word`, `description`, `meanings[]`, `policy`, `clarifyPrompt`, `defaultMeaningIndex`, `createdAt` | 모호성 해소 입력. `meanings[].intentId`는 FK가 아니므로 **스냅샷 내부 참조 검증 대상**(FR-H1-8) |
| `ContextVariable` | `id`, `name`, `description`, `slots[]`, `completionMessage`, `cancelKeywords[]`, `sessionTimeoutMinutes`, `createdAt` | 슬롯필링. `slots[].keywordId` 내부 참조 검증 |
| `DialogNode` | `id`, `name`, `description`, `nodeType`, `matchMode`, `enabled`, `priority`, `contextVariableId`, `outputs[]`, `createdAt` | 응답 결정. `outputs[].payload.targetNodeId`/`contextVariableId` 내부 참조 검증 |
| `DialogNodeIntent` / `DialogNodeKeyword` | 노드별 `intentIds[]` / `keywordIds[]`로 **평탄화**해 노드에 포함 | `DialogueBundle`과 같은 형태(`build()` 115~116행) |
| `FaqEntry` | `id`, `category`, `question`, `answer`, `altQuestions[]`, `enabled`, `createdAt` | 1단계 매칭 입력 |

| `Chatbot`(일부) | `name`, `avatarUrl`, `description`, `skin` | ⚠ **P-2** — 위젯의 **보이는 모습**이 버전의 일부라고 보면 포함, "대화 동작"만 버전이라고 보면 제외. **기본값: 포함**(스킨 변경 실수도 되돌릴 수 있어야 한다는 운영 관점) |

#### 4.1.2 제외 (근거와 함께)

| 대상 | 분류 | 제외 근거 | 복원 후 처리 |
|---|---|---|---|

| `BannedWord` | **전역 설정** | 챗봇 스코프가 아니다(개발명세서 §3). 한 챗봇 복원이 **모든 챗봇의 필터**를 바꾸게 된다 | 변경 없음. 미리보기에서 현재 사전 기준 **일치 경고만**(S-11) |

| `EmbeddingVector` | **파생** | 자산 텍스트 + `modelId`의 함수다. 스냅샷에 넣으면 1024차원 × 수천 벡터로 **크기가 수십 배**가 되고, `modelId`가 바뀐 뒤에는 **쓸모가 없다** | **재색인 예약**(`invalidate()`). ID 보존으로 `textHash` 동일 문장은 **재임베딩 생략**(J-5 ②) |
| `IntentClassifierModel` | **파생** | 예문의 함수이며 재학습이 수 초다(ADR-0027). 모델 버전 이력은 ADR-0027이 이미 기각했다 | ★ **삭제**(J-8 — stale 판정이 감소를 못 잡는다). 화면에 "재학습 필요" 안내 |
| `AugmentationSuggestion` | **제안(자산 아님)** | ADR-0025: "이 테이블의 어떤 행도 대화 동작에 영향을 주지 않는다" | **변경 없음**. ⚠ 복원으로 사라진 승인 예문의 제안 행은 `ACCEPTED`로 남으며 `@@unique([intentId, textNormalized])` 때문에 **같은 문장은 다시 제안되지 않는다** — EX-H-10에서 처리 |
| `TrainingJob` | 운영 로그 | 작업 이력은 사실 기록 | 변경 없음(진행 중이면 복원 거부 — J-9) |
| `TestCaseSet`·`TestCase` | **검증 자산** | TC는 복원 결과를 **재는 자**다. 자가 복원과 함께 되돌아가면 "복원이 잘 됐는가"를 잴 수 없다. TC 변경 추적은 감사로그가 한다(ADR-0029) | 변경 없음. ID 보존으로 **유효성 유지** |
| `TestRun`·`TestRunResult` | 검증 결과(사실) | 과거 판정 사실 | 변경 없음 |
| `ConversationLog`·`UnansweredQuestion`·`RagCallLog` | **사실 기록** | 복원은 과거에 일어난 대화를 바꾸지 않는다. 통계(No.14)가 흔들리면 안 된다 | 변경 없음. `resolvedIntentId`가 사라진 의도를 가리키면 기존 "삭제된 의도" 표시 규약 그대로 |
| `AuditLog` | **사실 기록**(append-only) | ADR-0016 | 복원 요약 1건 **추가만** |

> **판단 요약**: 스냅샷 = **"관리자가 직접 작성하고, 응답을 결정하며, 이 챗봇에만 속하는 것"**. 나머지는 ① 재계산 가능하거나(파생) ② 되돌리면 안 되거나(사실·계약·배포) ③ 다른 챗봇과 공유된다(전역).

| FR-H1-1 | 스냅샷 범위는 §4.1.1 표로 **고정**한다. 범위에 모델을 추가/제거하는 변경은 **`schemaVersion` 증가 + 업캐스터 추가**를 동반해야 한다(FR-H1-12). |
| FR-H1-2 | 스냅샷 자산부의 형태는 **`DialogueBundle`(shared-types)을 재사용**하고, `answerSetting`·`profile`(표시 설정 4필드)을 **형제 필드로 추가**한다. 두 번째 자산 직렬화 규약을 만들지 않는다. |
| FR-H1-3 | 스냅샷은 **정규화 컬럼(`*Normalized`)과 `updatedAt`을 저장하지 않는다.** 정규화 컬럼은 복원 시 재계산하고, `updatedAt`은 복원 시각이 된다. `createdAt`은 **보존**한다(목록 정렬이 복원으로 뒤섞이지 않게). |

#### 4.2.2 증강 승인 흐름과의 연계 (★ 쟁점 1의 답)

| 질문 | 답 |
|---|---|
| **승인 직전 자동 스냅샷이 롤백 안전망이 되는가?** | **된다 — 그리고 유일한 안전망이다.** 승인 후 `Intent.examples`에는 증강분 표시가 없다(ADR-0025 — 승격된 문장은 일반 예문이다). `AugmentationSuggestion.status = ACCEPTED` 행으로 역추적할 수는 있으나 **그 사이 사람이 같은 문장을 손으로 넣었는지 구분할 수 없다.** 승인 직전 상태를 통째로 저장해 두는 것이 가장 단순하고 확실하다 |
| **한계는?** | 복원은 **챗봇 전체**를 그 시점으로 되돌린다. 승인 이후 **다른 편집**이 있었다면 함께 되돌아간다 — 미리보기 차이 목록이 이를 **반드시 보여 준다**(FR-H3-3). 특정 의도의 증강분만 빼는 것은 **부분 복원(범위 밖)** 이며, 차이 화면에서 해당 예문을 확인해 **의도 편집 화면에서 삭제**하는 것이 1차의 우회 경로다 |
| **No.20 M2와의 관계** | **M2 = 예방**(승인 전 영향 확인), **No.25 = 복구**(승인 후 되돌리기). 둘은 대체 관계가 아니며 증강 승인 화면에 **둘 다 연결**된다(FR-H4-6) |
| **승인이 잦으면 보존 한도가 소진되지 않는가?** | ① 해시 동일 시 생략 ② 자동 트리거의 보존 한도를 **수동과 분리**(§4.3.3) — 자동 30건이 소진돼도 **수동·고정 버전은 밀려나지 않는다** |

| ID | 요구사항 |
|---|---|
| FR-H1-4 | 자동 스냅샷은 **§4.2.1의 5개 자동 트리거에서만** 생성한다. **단건 CRUD(의도 1건 수정 등)는 자동 스냅샷을 만들지 않는다.** |
| FR-H1-5 | 모든 스냅샷 생성은 **직전 스냅샷의 `contentHash`와 비교**해 같으면 새 행을 만들지 않는다(`BEFORE_RESTORE` 예외). |
| FR-H1-6 | ⚠ 캡처는 **일관 읽기**여야 한다 — 스냅샷 범위의 모든 테이블을 **하나의 읽기 트랜잭션**(또는 동등한 일관성 보장)에서 읽는다. 현재 `DialogueBundleService.build()`는 `Promise.all` 6회 조회라 동시 쓰기 시 **노드는 새 의도를 참조하는데 의도 목록은 옛것**인 스냅샷이 생길 수 있다. 재사용 방식은 `system-architect` 확정(예: `build(chatbotId, tx?)` 선택 인자). |
| FR-H1-7 | 자동 스냅샷은 **본 동작의 트랜잭션 밖, 직전**에 생성한다. 본 동작이 이후 실패해도 스냅샷은 남는다(해시 동일 규칙으로 다음 번에 흡수된다). |
| FR-H1-8 | 캡처 직후 **스냅샷 내부 참조 그래프를 검증**한다: 노드의 `intentIds`/`keywordIds`/`contextVariableId`/`outputs[].targetNodeId`, 동음이의어 `meanings[].intentId`, 컨텍스트 `slots[].keywordId`가 **스냅샷 안에 존재**하는가. 위반은 **저장을 막지 않고** `integrityWarnings`로 기록한다(현재 DB의 앱 레벨 참조가 이미 깨져 있을 수 있다 — 그것을 스냅샷이 숨기면 안 된다). |
| FR-H1-9 | 자동 스냅샷에는 **트리거 문맥**을 남긴다: `{ trigger, resourceType?(INTENT/KEYWORD/FAQ), targetId?(intentId), itemCount? }` — 목록에서 "무엇 직전"인지 읽힌다. **문장 원문은 담지 않는다.** |

### 4.3 저장 형식 · 크기 · 보존 — J-2 결정

| FR-H1-11 | `contentHash` = **정규 직렬화**(키 정렬 · 배열은 `id` 오름차순 · 타임스탬프 제외 · 예문/동의어 등 **값 배열은 원래 순서 유지**)의 sha256. **같은 자산 상태 → 같은 해시**여야 한다(AC-H1-5). ⚠ 예문 순서는 `slotIndex`(임베딩 키)와 연결되므로 **순서 변경도 변경으로 본다**. |

#### 4.6.1 복원 절차

| ID | 요구사항 |
|---|---|
| FR-H3-1 | 복원은 **2단계**다: **미리보기**(`restore/preview`) → **확정**(`restore`). 미리보기는 DB를 바꾸지 않는다. |
| FR-H3-2 | 미리보기 응답: `{ diffSummary(대상 버전 ↔ 현재, FR-H2-7 ①), currentContentHash, blockers[], warnings[] }`. `blockers`가 있으면 확정 버튼이 비활성이다. |
| FR-H3-3 | ★ 미리보기는 **"되돌아가는 변경" 전체**를 보여 준다 — 특히 대상 버전 **이후의 다른 편집**(S-2)이 함께 되돌아간다는 사실을 요약 상단에 **"대상 버전 이후 변경 N건이 함께 취소됩니다"** 로 명시한다. |

#### 4.6.2 교체 규칙

| ID | 요구사항 |
|---|---|
| FR-H3-8 | 교체 전 **복원 무결성 검사**: ① 업캐스트 후 스냅샷이 **현재 zod 스키마·도메인 상한**(예문 500·동의어 200·대체질문 30·아웃풋 1~10·슬롯 1~20 등)을 만족하는가 — 상한이 그 사이 **낮아졌다면** 위반 목록과 함께 거부 ② 스냅샷 내부 참조 그래프(FR-H1-8)가 닫혀 있는가 — **캡처 당시부터 깨져 있던 참조**는 경고로 통과시키되 **FK 제약 대상(`DialogNode.contextVariableId`, 조인 테이블)** 이 깨져 있으면 거부(DB가 어차피 거부한다) ③ 정규화 이름 유일성(ADR-0006) — 스냅샷 내부 중복 시 거부. 실패는 `VERSION_INTEGRITY_FAILED` + 위반 목록. |
| FR-H3-9 | **의미론은 "스냅샷 범위 전체 교체"** 다: 복원 후 스냅샷 범위 테이블의 해당 챗봇 행 집합은 **스냅샷과 정확히 같다** — 스냅샷에 없는 행은 삭제, 있는 행은 원래 `id`로 존재하며 필드 값이 같다. 복원 직후 현재 `contentHash` == 대상 버전 `contentHash`(AC-H3-2). |
| FR-H3-10 | ⚠ **구현 방식은 `system-architect` 확정 사항**이다: (a) 전체 삭제 후 재생성 또는 (b) 차이 적용(삭제/수정/생성). 요구사항 제약: ① FK `Restrict` 순서 준수(조인 → 노드 → 컨텍스트/의도/키워드 순 삭제, 역순 생성) ② **이름 교환**(A↔B 이름 맞바꿈) 시 `@@unique([chatbotId, nameNormalized])` 중간 충돌이 나지 않을 것 ③ (권고) **변경 없는 행의 `updatedAt`을 건드리지 않을 것** — (b) 방식이 유리하며, "복원이 실제로 무엇을 바꿨나"가 `updatedAt`으로도 드러난다. |
| FR-H3-11 | 스냅샷의 `id`가 **다른 챗봇의 행으로 이미 존재**하면(정상 경로로는 불가능 — 방어) 복원을 거부한다. **다른 챗봇으로의 복원 API는 존재하지 않는다**(J-14). |

| **No.1 챗봇 복사**(`copy()` 얕은 복사) | 변경하지 않는다. 깊은 복사는 **캡처 + ID 재매핑**으로 향후 가능(J-12) |
| **No.18 임베딩**(구현 완료) | 복원 후 재색인을 **위임**한다. 새 모델·새 색인 경로 0건 |

### 4.10 GPU 필요도 재확인 — J-13

| No | 카탈로그 | **재확인** | 근거 |
|---|:---:|:---:|---|
| **25** | 1 | **1 유지** | 캡처(DB 읽기 + JSON 직렬화 + sha256) · 차이(집합 연산) · 복원(트랜잭션 쓰기) · 보존 정리 — 전부 CPU이며 §1 기준표 "1~2 CPU 전용 — CRUD/설정"에 해당한다. **새 모델을 적재하지 않는다.** |

**단 복원은 재색인을 유발한다.** 이는 기존 ml-worker(No.18)의 부하이며 **ID 보존(J-5)으로 "바뀐 문장 수"에 비례**하도록 묶는다. ID를 새로 발급했다면 복원 1회 = **챗봇 전체 재임베딩**이 되어, CPU 전용 배포에서 수 분간 의미 매칭이 저하된다(메모리 기록: CPU 배포의 임베딩 타임아웃 위험, 커밋 25e8f89) — **J-5가 GPU 등급을 1로 유지하는 조건**이기도 하다.

## 7. 수용기준 (AC)

### AC-H1. 스냅샷 생성

- **AC-H1-1** Given 의도 3·키워드 2·동음이의어 1·컨텍스트 1·노드 4(조인 포함)·FAQ 5·답변설정 1행인 챗봇, When 수동 저장하면, Then 스냅샷 `counts`가 각각 일치하고 `payload`에 **§4.1.1의 필드만** 존재한다(`slug`·`status`·`Channel`·`BannedWord`·`EmbeddingVector` 없음).
- **AC-H1-2** Given 직전 버전 이후 변경이 없음, When 수동 저장하면, Then 새 행이 생기지 않고 `unchanged: true`와 직전 `versionNo`가 온다.
- **AC-H1-3** Given 의도 임포트 커밋, When 커밋이 끝나면, Then **커밋 직전 상태의** `BEFORE_IMPORT` 버전이 1건 있고 그 `counts.intents`는 커밋 전 건수다.
- **AC-H1-4** Given 증강 제안 6건 승인, When 승인이 끝나면, Then `BEFORE_AUGMENT_ACCEPT` 버전이 있고 그 버전의 대상 의도 `examples`에는 **승인된 6문장이 없다**.
- **AC-H1-5** Given 같은 자산 상태, When 두 번 캡처하면(타임스탬프만 다름), Then 두 `contentHash`가 **같다**.
- **AC-H1-6** Given 의도 1건의 예문 **순서만** 변경, When 캡처하면, Then `contentHash`가 **다르다**(FR-H1-11).
- **AC-H1-7** Given 의도 1건 단건 수정, When 버전 목록을 보면, Then 자동 버전이 **생기지 않았다**(FR-H1-4).
- **AC-H1-8** Given 자동 스냅샷 31건째 생성, When 목록을 보면, Then 자동 버전은 30건이고 **수동·고정 버전 수는 변하지 않았다**.
- **AC-H1-9** Given 고정 10건 상태, When 11번째 고정을 요청하면, Then `VERSION_PINNED_LIMIT_EXCEEDED`다.
- **AC-H1-10** Given 스냅샷 원본이 상한 초과, When 수동 저장하면, Then `VERSION_SNAPSHOT_TOO_LARGE`이고 행이 생기지 않는다.
- **AC-H1-11** Given 노드 outputs의 `targetNodeId`가 이미 없는 노드를 가리키는 DB 상태, When 캡처하면, Then 저장은 **성공**하고 `integrityWarnings`에 해당 참조가 기록된다(FR-H1-8).
- **AC-H1-12** Given 버전 목록 조회, When 쿼리를 계측하면, Then **`payload` 컬럼을 읽지 않는다**(FR-H1-17).

### AC-H2. 이력 조회와 차이

- **AC-H2-1** Given 버전 v5와 현재 사이에 의도 1개 추가·FAQ 1개 삭제·노드 1개 아웃풋 변경, When `diff?against=current`를 조회하면, Then 요약이 `의도 +1`·`FAQ −1`·`노드 ~1`이다.
- **AC-H2-2** Given 예문 `[a,b,c]` → `[a,c,d]`, When 항목 상세를 보면, Then `+d −b`로 표시된다(집합 차이).
- **AC-H2-3** Given 의도를 삭제 후 같은 이름으로 재생성, When 차이를 보면, Then `삭제 1 + 추가 1`이며 **"같은 이름으로 재생성됨"** 힌트가 붙는다.
- **AC-H2-4** Given VIEWER 계정, When 버전 목록을 조회하면, Then 목록은 보이지만 **감사 건수 필드가 응답에 없다**(FR-H2-3).
- **AC-H2-5** Given ADMIN 계정, When v5 행의 감사 링크를 따라가면, Then 이력관리 화면이 `chatbotId` + v5~v6 기간으로 필터된 채 열린다.
- **AC-H2-6** Given 타 챗봇의 `versionId`, When 이 챗봇 경로로 조회하면, Then `404`다(NFR-HS4).
- **AC-H2-7** Given 차이 조회, When DB 쓰기를 계측하면, Then **0건**이다(저장하지 않는다).

### AC-H3. 복원

- **AC-H3-1** Given v5로 복원 미리보기, When 응답을 보면, Then `diffSummary`·`currentContentHash`가 오고 **DB는 변경되지 않았다**.
- **AC-H3-2** ★ Given v5로 복원 확정 성공, When 현재 `contentHash`를 계산하면, Then **v5의 `contentHash`와 같다**(FR-H3-9).
- **AC-H3-3** ★ Given v5에 존재하는 의도 `I1`(id=X)이 이후 삭제됨, When v5로 복원하면, Then `I1`이 **id=X 그대로** 존재한다(FR-0-71).
- **AC-H3-4** ★ Given `expectedTargetId=X`인 TC가 복원 전 `UNRESOLVED`, When 복원 후 TC 세트를 실행하면, Then 그 TC가 **`PASS` 또는 `FAIL`로 판정**된다(`UNRESOLVED` 아님).
- **AC-H3-5** Given 복원 확정, When 버전 목록을 보면, Then **복원 직전 상태의 `BEFORE_RESTORE` 버전**이 새로 있고 그 `contentHash`는 복원 직전 현재 해시와 같다.
- **AC-H3-6** Given 복원 후 그 `BEFORE_RESTORE` 버전으로 다시 복원, When 해시를 계산하면, Then **첫 복원 전 상태와 같다**(복원의 복원 — S-8).
- **AC-H3-7** Given 예문 1,000건 중 20건만 다른 버전으로 복원, When 재색인 임베딩 호출 대상 문장 수를 계측하면, Then **20건 이하**다(NFR-HP6 — 전체 재임베딩 아님).
- **AC-H3-8** Given 트랜잭션 중간 단계에서 오류를 주입, When 복원을 시도하면, Then **어떤 자산 행도 바뀌지 않았고**(원자성) 오류가 반환된다. `BEFORE_RESTORE` 백업은 남아도 된다.
- **AC-H3-9** Given 백업 생성이 실패하도록 주입(크기 상한 등), When 복원을 시도하면, Then 복원이 **중단**되고 자산이 **변경되지 않는다**(FR-0-72).
- **AC-H3-10** Given 미리보기 후 다른 사용자가 FAQ 1건 수정, When 확정하면, Then `409 RESTORE_PREVIEW_STALE`이고 자산은 그 사용자의 수정 상태 그대로다.
- **AC-H3-11** Given 해당 챗봇에 `RUNNING` 분류기 학습, When 미리보기/확정하면, Then `blockers`에 작업이 표시되고 확정은 `409 RESTORE_BLOCKED_BY_ACTIVE_JOB`이다. `TestRun` `QUEUED`도 동일하다.
- **AC-H3-12** Given `ARCHIVED` 챗봇, When 복원을 시도하면, Then 거부된다.
- **AC-H3-13** Given 복원 성공, When `IntentClassifierModel`을 조회하면, Then 해당 챗봇 행이 **없다**(J-8).
- **AC-H3-14** Given 복원 성공, When 곧바로 공개 대화 API로 대상 버전에만 있는 FAQ 질문을 보내면, Then **그 FAQ로 응답**한다(캐시 무효화 — 60초 TTL을 기다리지 않는다).
- **AC-H3-15** Given 전역 질의 임베딩 캐시에 항목 500건, When 복원하면, Then **500건이 그대로 남아 있다**(무효화하지 않음).
- **AC-H3-16** Given 복원 전후, When `ConversationLog`·`UnansweredQuestion`·`AugmentationSuggestion`·`TestCase`·`TestRun`·`TrainingJob`·`Channel`·`BannedWord` 행과 `Chatbot.slug`/`status`/`groupId`를 비교하면, Then **전부 변하지 않았다**(FR-H3-15, §4.1.2).
- **AC-H3-17** Given 두 의도의 이름을 서로 맞바꾼 상태에서 맞바꾸기 전 버전으로 복원, When 복원하면, Then **유일성 충돌 없이 성공**한다(FR-H3-10 ②).
- **AC-H3-18** Given 컨텍스트 폼 2단계까지 진행된 대화 봉투 + 대상 버전에도 같은 컨텍스트 존재, When 복원 후 다음 턴을 보내면, Then 폼이 **3단계로 이어진다**(S-7). 대상 버전에 없으면 **오류 없이 일반 매칭**으로 처리된다.
- **AC-H3-19** Given 도메인 상한이 스냅샷 이후 낮아져 위반하는 스냅샷, When 복원을 시도하면, Then `VERSION_INTEGRITY_FAILED` + 위반 목록이며 자산은 변경되지 않는다.
- **AC-H3-20** Given `schemaVersion: 1` 픽스처, When 현재 코드로 미리보기·복원하면, Then **성공**한다(NFR-HM4).

### AC-H4. 감사·권한·봉인 (공통)

- **AC-H4-1** Given 복원 1회(자산 수백 건 변경), When 감사로그를 보면, Then 이 복원에 대한 레코드는 **`RESTORE` 1건**이며 summary에 from/백업 버전 번호와 건수가 있다.
- **AC-H4-2** Given 자동 스냅샷 생성·보존 정리, When 감사로그를 보면, Then **`ChatbotVersion` 레코드가 0건**이다. 수동 저장·라벨 수정·고정·삭제는 각 1건씩 있다.
- **AC-H4-3** Given VIEWER, When 저장·수정·삭제·미리보기·복원 API를 호출하면, Then 전부 `403`이고 DB 변경이 0건이다.
- **AC-H4-4** Given `dialogue:write`만 있고 `chatbot:write`가 없는 가상 역할(단위 시험), When 복원을 호출하면, Then `403`이다(J-11).
- **AC-H4-5** Given 저장소 전체, When 버전 모듈의 import 그래프를 검사하면, Then 대화 자산 쓰기는 **복원 서비스에서만** 발생한다(정적 검사 — FR-0-69).
- **AC-H4-6** Given 공개 라우트, When `@Public()` 핸들러 수를 세면, Then **정확히 6개**다.
- **AC-H4-7** Given 챗봇 영구삭제, When 확인하면, Then 그 챗봇의 `ChatbotVersion`이 **전부 제거**됐고 영구삭제가 스냅샷 때문에 409로 막히지 않는다(FR-H1-21).
- **AC-H4-8** Given 환경변수 미설정, When 서버를 기동하고 저장·복원하면, Then 정상 동작한다(FR-0-74).
- **AC-H4-9** Given `packages/dialogue-engine`, When git diff를 확인하면, Then 변경 0건이다.
- **AC-H4-10** Given 스냅샷 생성·복원, When 서버 로그를 검사하면, Then 예문·답변 원문이 **없다**(FR-0-77).

## 11. PM 확인이 필요한 항목

| # | 항목 | 왜 PM이 정해야 하는가 | 미확정 시 기본값 |
|---|---|---|---|
| **P-1** | **스냅샷 생성 시점**(쟁점 1) — 수동만 / 자동만 / 둘 다. 자동 트리거 목록(임포트·일괄삭제·**증강 승인**·학습현황 일괄 반영·복원)이 적절한가 | 자동이 없으면 "증강 승인 되돌리기"가 **불가능**하다(§4.2.2). 트리거를 늘리면 보존 한도가 빨리 소진된다 | **수동 + 자동 5종**, 단건 CRUD 제외, 해시 동일 시 생략 |
| **P-2** | **챗봇 표시 설정(이름·아바타·소개·스킨)을 스냅샷·복원 범위에 넣는가** | "버전"을 **대화 동작**으로만 볼지 **위젯 모습 포함**으로 볼지의 제품 정의다. 넣으면 스킨 실수도 되돌리지만, 대화 자산만 되돌리려던 관리자가 **이름까지 바뀌는** 것에 놀랄 수 있다 | **포함**(미리보기 차이에 명시) |
| **P-3** | **복원 방식**(쟁점 2) — 1차를 **전체 원자 교체만**으로 하고 항목 단위 부분 복원을 미루는가 | 부분 복원은 참조 정합 설계로 범위가 크게 늘어난다. 대신 "승인 후 다른 편집까지 함께 되돌아가는" 불편을 감수한다 | **전체 교체만** + 차이 화면에서 과거 값 복사 |
| **P-4** | **자동 스냅샷 실패 시 본 동작(임포트·증강 승인 등)을 막는가** | 막으면(fail-closed) 안전망이 확실하지만 **스냅샷 문제로 업무가 멈춘다**. 진행하면(fail-open) 드물게 롤백 지점이 없을 수 있다 | **fail-open + 경고**(복원 직전 백업만 fail-closed) |
| **P-5** | **복원 권한**(쟁점 — 파괴적 작업) — EDITOR 허용(`dialogue:write`+`chatbot:write`, 신규 0종) vs ADMIN 전용(`chatbot:restore` 신설, 15→16종) | 자동 백업으로 복원은 가역이지만, **조직 통제**(운영 챗봇을 편집자가 단독으로 되돌려도 되는가)는 제품 정책이다 | **EDITOR 허용, 신규 권한 0종** |
| **P-6** | **보존 정책·용량**(쟁점 4) — 자동 30 · 수동 30 · 고정 10 · 1건 20MB · 챗봇당 300MB | 구축형 고객의 디스크 여건과 감사/규제 보존 요구에 따라 달라진다 | 위 값 그대로(전부 환경변수로 조정 가능) |
| **P-7** | **ACTIVE 챗봇 복원 확인 강도**(쟁점 5) — 이름 입력 vs 체크박스 | 영구삭제는 이름 입력을 요구한다. 복원은 가역이지만 운영 중 즉시 반영된다 | **이름 입력 없이 체크박스 확인 + 대상 명시 버튼**(가역 동작이므로) — `ui-designer`와 확정 |
| **P-8** | 복원으로 제거된 **승인 증강 예문의 재제안을 허용**하는가(EX-H-10) | 허용하려면 제안 상태를 바꿔야 하고(ADR-0025 영역 쓰기), 막으면 롤백한 문장이 **다시는 제안되지 않는다** | **허용하지 않음**(제안 테이블 불변) + 미리보기 경고 |
| **P-9** | **ID 보존 확정**(쟁점 2의 핵심) — 예외 없이 보존하는가 | 이 문서의 가장 중요한 결정이다(J-5). 보존하지 않으면 **No.19 TC 전체 `UNRESOLVED`** · **전체 재임베딩** · 통계/이력 단절이 동시에 발생한다. 기술적 반대 요인은 이름 교환 처리(FR-H3-10) 정도다 | **보존(필수)** |
| **P-10** | **GPU 필요도 1 확인**(쟁점 6) | 카탈로그 값과 같다. 재색인은 위임 부하이며 ID 보존 전제에서만 작다 | **1 유지** |

> **쟁점 → P 매핑**: 쟁점 1 = P-1/P-4 · 쟁점 2 = P-3/P-9(+J-6 자동 백업은 필수로 확정 제안) · 쟁점 3 = J-7(PM 확인 불요, 조회 전용) · 쟁점 4 = P-6(+J-2 JSON+`schemaVersion` 확정 제안) · 쟁점 5 = J-9 + P-7 · 쟁점 6 = P-10.
