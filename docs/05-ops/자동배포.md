# 자동배포

> `docs/02-spec/개발명세서.md` §2 모노레포 구조 기준. 실제 코드가 아직 없으므로 이 문서는 **배포 방식의 설계 지침**이며, `deployment-engineer` 서브에이전트가 구현 단계에서 `infra/**`를 실제로 작성한다.

## 1. 범위 (단계적 확대)

| 단계 | 범위 | 조건 |
|---|---|---|
| 1단계 | 로컬 `docker compose up`으로 전체 스택(api/web/widget/db/redis) 기동·헬스체크 | 기본기능 1차 구현 완료 시 |
| 2단계 | ml-worker 포함 전체 스택 + mock LLM/STT/TTS Provider | 확장기능 구현 시 |
| 3단계 | CI 워크플로(빌드/테스트 자동 실행) | 사용자가 원격 저장소(GitHub 등) 및 CI 플랫폼을 확정한 이후에만 |
| 4단계 | 실 클라우드/사내서버 배포 | 사용자가 대상 플랫폼·자격증명을 명시한 이후에만 |

**3~4단계는 사용자의 명시적 지시 없이는 진행하지 않는다** (Auto QA `deployment-engineer` 원칙과 동일).

## 2. Docker Compose 구성(안)

```yaml
services:
  api:
    build: ./apps/api
    env_file: ./infra/.env
    environment:
      NODE_ENV: production   # 운영 판별 기준(No.32 DD-135) — 아래 설명 참고. 빠뜨리면 안 된다
    depends_on: [db, redis]
  web:
    build: ./apps/web
  widget:
    build: ./apps/widget
  ml-worker:
    build: ./apps/ml-worker
    depends_on: [redis, db]
    environment:
      LLM_PROVIDER: mock   # mock | on-prem | cloud
  ml-worker-speech:        # 음성 인식(No.32) 전용 — 선택. SPEECH_ENABLED를 켜는 설치에서만 띄운다(§5.14)
    build: ./apps/ml-worker   # 이미지에 선택 묶음 [speech] 설치 필요(requirements-speech-lock.txt)
    environment:
      ML_WORKER_ROLE: speech          # 배타 역할 — 임베딩·생성 모델을 적재하지 않는다
      ML_WORKER_PORT: "8102"
      STT_BACKEND: faster-whisper     # mock은 시험·시연 전용
      STT_MODEL_ID: ${STT_MODEL_ID}   # 필수 — 기본 모델 없음
      STT_MODEL_DIR: /models/stt
    volumes: ["./models/stt:/models/stt:ro"]   # 반입한 모델 디렉터리(기동 중 내려받기 0)
  db:
    image: postgres:16
    volumes: ["pgdata:/var/lib/postgresql/data"]
  redis:
    image: redis:7
volumes:
  pgdata:
```

**`api`의 `NODE_ENV=production` (2026-10-02 추가, No.32 음성 AI · DD-135)**: API에는 "운영 환경" 판별 기준이 따로 없어, 음성 AI가 Node 관례인 `NODE_ENV=production`(앞뒤 공백 제거 후 정확히 일치)을 처음으로 읽는다. 이 값이 있어야 "운영 ∧ `SPEECH_ENABLED=true` ∧ `SPEECH_PROVIDER=mock`"이 **API 기동 실패**로 막힌다. **빠뜨리면 같은 조합이 기동 경고만 남기고 통과해 가짜 인식 결과("모의 인식 결과입니다")가 실제 사용자에게 나갈 수 있다(fail-open).** 운영 설치는 Compose가 아닌 서비스 단위 파일·pm2·systemd를 쓰더라도 이 값을 명시하고 설치 점검(§5.14-9)에서 확인한다. `NODE_ENV`는 환경변수 스키마 키가 아니라 원시 값 읽기다.

**`ml-worker-speech`(안)**: 음성 인식은 공개(인증 없는) 경로가 부르는 요청당 추론이라 임베딩 프로세스(포트 8100)·생성 프로세스(8101)와 **별도 서비스·별도 포트 8102**로 둔다(`ML_WORKER_ROLE=speech`는 배타 — 같은 프로세스에 합치지 않는다). 위 `ml-worker` 서비스는 기존대로 임베딩 역할이다. API에는 `SPEECH_ENABLED`·`SPEECH_PROVIDER=local`·`ML_WORKER_SPEECH_URL=http://ml-worker-speech:8102`를 `infra/.env`로 준다(스위치는 기본 꺼짐). **GPU를 임베딩·생성과 공유하면 VRAM 예산을 먼저 정한다**: 합계 = 임베딩 + STT 모델 + (생성을 같은 GPU에 둘 때) 생성 모델이며 수치는 **미실측**이다(합계·임베딩 P95 영향은 No.17 실측 때 함께 잰다 — 설계서 §8.8 · §5.14-4). 4GB급 장비에서는 STT를 CPU(`STT_DEVICE=cpu`)에 두거나 구성을 나눈다(제안). 위 YAML은 기존 안과 같은 초기안이며 실제 파일은 1~2단계 작업 때 만든다(이번에 `infra/` 파일은 만들지 않았다).

`infra/.env.example`에는 플레이스홀더만 작성한다(`DATABASE_URL=`, `REDIS_URL=`, `LLM_PROVIDER=mock`, `LLM_API_KEY=` 등). 실제 키 값은 `.env`(git 미추적)로만 관리한다.

## 5. 배포 시 운영 설정·절차 참고 (2026-09-24 추가)

### 5.1 GPU 없는(CPU 전용) ml-worker 배포의 임베딩 타임아웃

- `EMBEDDING_TIMEOUT_MS`(기본 **300ms**)는 **공개 대화 경로의 단건 질의 임베딩** 예산이다(ADR-0024, `nlu-rag-answering-설계.md` §8.1). GPU급 추론을 전제로 한 값이라 **CPU 전용 ml-worker에서는 단건도 300ms를 넘길 수 있다.** 초과 시 오류가 아니라 **의미 매칭 없이 규칙 매칭으로 응답하는 저하 모드**로 동작하므로 장애로 보이지 않는다 — 구축형 고객 환경에 GPU가 없으면 이 점을 운영자에게 명시적으로 안내한다.
- 선택지: ① 300ms를 유지하고 저하 모드를 감수(응답 지연 예산 우선) ② 실측 P95에 맞춰 올린다(예: 로컬 시연 CPU 환경은 15000ms로 운영했다 — 대화 응답이 그만큼 느려질 수 있음). **설계 문서는 기본값 상향을 금지**하므로 배포별 `.env`에서만 조정한다.
- 재색인·TC 실행·증강·분류기 학습 등 **2건 이상 배치**는 `EMBEDDING_BATCH_TIMEOUT_MS`(기본 30000ms)가 따로 적용된다(25e8f89). 배치 실패는 `embeddings/status`의 `failureReason`에 `ml-worker 호출 시간 초과(Nms)`로 표시된다.
- 배포 전 확인: ml-worker 기동 후 대표 질의 수십 건으로 단건 임베딩 P95를 측정해 위 ①/②를 결정한다.

### 5.2 통합 통계(No.29) 배포 순서

`ConversationLog.groupId`(대화 당시 그룹) 도입 때문에 다음 순서를 **연속으로** 수행한다(`integrated-stats-설계.md`, ADR-0033).

1. DB 마이그레이션 적용(`20260924120000_integrated_stats_schema` — 비파괴 `ADD COLUMN`/`CREATE INDEX`만)
2. API 배포(이후 새 대화로그는 `groupId`가 채워진다)
3. 백필 실행: `apps/api/prisma/scripts/backfill-conversation-group.ts`(멱등 — 재실행 안전)

2~3 사이에 챗봇의 그룹 이동이 있으면 그 챗봇의 과거 로그는 이동 **후** 그룹으로 귀속된다. 백필 완료 전에는 통합 통계 화면에 "과거 데이터 정리 중"(`backfillPending`) 안내가 표시된다.

### 5.3 데이터 거버넌스(No.45) 운영 요구 (2026-09-26 추가)

`data-governance-설계.md` · ADR-0040. 거버넌스 모드(`DATA_GOVERNANCE_MODE=ON`)를 켜는 설치(규제 고객 구축형)의 **운영 책임**이며 애플리케이션이 검출·보증하지 않는다.

1. **디스크·볼륨 암호화(전제)**: DB 파일·저널·WAL·같은 볼륨 백업이 있는 디스크를 암호화한다(BitLocker·LUKS·클라우드 볼륨 암호화). 적용 후 `DATA_AT_REST_ENCRYPTION_DECLARED=true`(데이터 지도는 이 값을 "운영자 신고값"으로만 표시). `secure_delete`는 DB 페이지만 덮으므로 파기의 물리 잔존은 이 전제로만 막힌다.
2. **저장 위치**: `DATABASE_URL`은 **절대 경로**(`file:/secure/chatbot/prod.db`) · `DATA_RESIDENCY_ALLOWED_DIRS`에 그 디렉터리 — 상대 경로·심볼릭 링크로 밖을 가리키면 기동 실패. 원격 DB면 `DATA_RESIDENCY_ALLOWED_DB_HOSTS`.
3. **출구 허용 목록 작성**: `DATA_EGRESS_ALLOWED_HOSTS`에 실제로 쓰는 호스트만(`127.0.0.1:8000`(같은 서버 ml-worker) · `rag.internal` · 레거시 연결 호스트 · 필요 시 `*.bank.internal`). 루프백도 자동 허용되지 않는다. 설정된 임베딩·RAG·증강 기본 URL 호스트가 목록 밖이면 **기동하지 않는다**(로그에 호스트·출구 이름). 임베딩 호스트가 같은 서버가 아니면 "질의 원문 외부 송신" 경고가 뜬다.
4. **ml-worker 모델 사전 배치**: 폐쇄망·거버넌스 설치는 모델을 미리 내려받아 두고 `HF_HUB_OFFLINE=1`로 기동한다(ml-worker 코드 변경 없음). **[2026-09-30 No.37]** 생성 백엔드(Ollama·vLLM) 모델 반입 절차·장비 등급표는 **§5.8**. 거버넌스 설치에서 생성 프로파일을 원격 백엔드로 쓰면 ml-worker `.env`에 `GENERATION_BACKEND_REQUIRE_ALLOWLIST=true`와 `GENERATION_BACKEND_ALLOWED_HOSTS`(생성 백엔드 호스트만)를 넣는다 — ml-worker → 생성 백엔드 구간은 API 출구 허용 목록(`DATA_EGRESS_ALLOWED_HOSTS` — 여기에는 ml-worker 주소만)의 대상이 아니고, 이 구간으로 가는 예문 시드는 마스킹되지 않는다.
5. **키 생성·백업·교체**: `DATA_ENCRYPTION_KEYS="k1:<base64 32바이트>"`(예: `openssl rand -base64 32`), 체인 서명 키 `AUDIT_CHAIN_KEY` 동일 형식. **키 분실 = 암호문 영구 손실** — 키는 DB 백업과 **다른 매체**에 이중 보관한다. 교체: 새 키를 **앞에** 추가(`k2:…,k1:…`) → 재기동 → 데이터 지도 "k1 사용 행 0" 확인 → k1 제거 → 재기동(먼저 지우면 기동이 거부된다). 키 값은 로그·티켓·채팅에 붙이지 않는다.
6. **백업 보존**: 백업도 보존기간 정책을 따라야 한다 — 파기 창 이후에도 오래된 백업에 소거 전 텍스트가 남는다. 백업 보관 기간 ≤ 대화 보존기간 + 운영 여유를 권고하고, 백업 볼륨도 암호화한다.
7. **보존 하한**: `RETENTION_MIN_DAYS_CONVERSATION`(7)·`RETENTION_MIN_DAYS_AUDIT`(365)는 **법무 확인 전 기본값**이다 — 고객사 규정(예: 접속기록 보관 기간)으로 확정해 설정한다. 감사 하한을 365 미만으로 낮추면 기동 경고가 남는다.
8. **파기 창**: `DATA_RETENTION_WINDOW`(기본 KST 02:00-05:00)는 예약 배포·백업 시각과 겹치지 않게 둔다(겹쳐도 배치 양보로 동작하지만 지연된다).
9. **체인 머리 보관**: 부팅·파기 실행 로그의 `info` "체인 머리(seq·해시)" 줄과 감사 CSV의 `#CHAIN_HEAD` 행을 로그 수집 시스템·별도 보관소에 남긴다 — 키 없는 설치에서 전체 재계산 변조를 대조로 찾는 유일한 수단이다.
10. **롤백 금지 조건**: 필드 암호화를 켠 설치는 **API 구버전으로 롤백하지 않는다**(구버전은 봉투를 평문처럼 표시) — 전진 수정만. 다중 인스턴스는 전 인스턴스를 동시에 교체한다(구버전 인스턴스의 감사 행은 체인 밖으로 남는다).
11. **배포 후 확인**: 마이그레이션 `20260926120000_data_governance` 적용 후 부분 유니크 4종 존재 · 신규 테이블 5 · `PRAGMA foreign_key_check` 0행 · 데이터 지도에서 모드·출구 판정·체인 머리 확인.

### 5.4 업무 자동화(No.41) 운영 요구 (2026-09-26 추가)

`workflow-automation-설계.md` · ADR-0041. 발송 대상을 1개 이상 등록하는 설치의 **운영 책임**이다.

1. **비밀 설정**: 대상의 `secretRef`·`signingSecretRef`·`urlSecretRef`마다 `WORKFLOW_SECRET__<REF>=<값>`을 서버 환경변수로 넣고 재기동한다(서명 비밀은 32자 이상 — 예: `openssl rand -hex 32`). 값은 로그·티켓·채팅에 붙이지 않는다. 비밀 교체는 받는 쪽이 새·옛 비밀을 함께 검증하도록 먼저 조정한 뒤 환경변수를 바꾼다(이중 서명 없음).
2. **도달성**: 구축형에서 사내 결재·ITSM·메신저가 사설 대역이면 `WORKFLOW_PRIVATE_ALLOWLIST`에 그 주소·호스트를 명시한다(레거시 목록과 별도 · 루프백·링크로컬·메타데이터 대역은 열 수 없다 — 같은 서버의 수신기는 사내 주소로 노출). 폐쇄망에서 클라우드 도구로 보내려면 외부 출구 또는 사내 중계 서버를 대상으로 둔다. 구독형은 고객 사내망 도구에 고정 송신 IP·방화벽 개방이 필요하다.
3. **거버넌스 모드 설치**: 대상 호스트를 `DATA_EGRESS_ALLOWED_HOSTS`에 먼저 등록해야 대상 저장이 된다(목록 밖 = 저장 400 · 발송 차단).
4. **발송 전담 인스턴스(선택)**: 다중 인스턴스에서 대상 한도를 엄격히 지키려면 1개 인스턴스만 `WORKFLOW_DISPATCH_ENABLED=true`로 둔다. 모든 인스턴스가 `false`면 적재만 되고 발송되지 않는다(콘솔 "발송 지연" 경고).
5. **받는 쪽 연동 확인**: 대상 등록 후 콘솔 "테스트 발송"으로 서명 검증·응답 코드(실패는 4xx/5xx로 응답)를 확인한다. 받는 쪽은 `X-Chatbot-Delivery`로 중복을 제거해야 한다(최소 1회 전달 — 재시도·재발송이 같은 값을 보낸다). 연동 가이드: `docs/05-ops/업무자동화_연동가이드.md`(deployment-engineer 작성 예정).
6. **배포 후 확인**: 마이그레이션 `20260926180000_workflow_automation` 적용 뒤 원시 부분 유니크 인덱스 개수가 4 그대로인지 · 신규 테이블 3 · 외래 키 점검 0행 · 콘솔 업무 자동화 화면·데이터 지도 "업무 자동화 웹훅" 행 확인.

### 5.5 통합 인박스(No.42) 운영 요구 (2026-09-26 추가)

`omnichannel-inbox-설계.md` · ADR-0042. 챗봇을 통합 인박스에 참여시키는 설치의 **운영 책임**이다.

1. **고객 키 비밀**: 로그인 연동 식별을 쓰려면 `OMNI_CUSTOMER_KEY_SECRET`(32바이트 이상 — 예: `openssl rand -hex 32`)을 넣고 재기동한다. **이 값은 교체하지 않는다** — 바꾸면 기존 고객과 새 방문의 통합이 끊긴다(원 회원 번호를 저장하지 않아 재계산 불가). 백업 복원 시 같은 값을 함께 보존한다.
2. **식별 공간 비밀**: 고객사마다 `OMNI_IDENTITY_SECRET__<REF>`(32바이트 이상)를 넣고, ADMIN이 챗봇 설정에서 참조 `<REF>`를 지정한다. 같은 비밀을 고객사 로그인 서버와만 공유한다(메일·메신저 전달 금지). 고객사가 비밀을 교체할 때는 새 값을 `…__<REF>`에, 옛 값을 `…__<REF>__PREV`에 두고 재기동 → 고객사 전환 확인 → `__PREV` 제거.
3. **동의·고지**: 로그인 회원 정보를 챗봇 상담 이력과 연결한다는 사실의 고지·동의는 **고객사 책임**이다(연동 가이드·계약 명시). 토큰 권장 수명은 1시간(최대 24시간).
4. **거버넌스 모드 설치**: 인박스 메모·기록 본문과 고객 표시 이름은 암호화 대상이며, 보존기간 화면의 "인박스 메모·기록"·"고객 식별 정보"를 정책에 맞게 정한다(기본 무기한).
5. **배포 후 확인**: 마이그레이션 `20260926210000_omnichannel_inbox` 적용 뒤 원시 부분 유니크 인덱스 개수가 4 그대로인지 · 신규 테이블 8 · 외래 키 점검 0행 · 챗봇 설정 "통합 인박스" 화면의 비밀 상태(설정됨/없음/약함) 확인. 연동 가이드: `docs/05-ops/통합인박스_연동가이드.md`(deployment-engineer 작성 예정).

### 5.6 채널별 리치 메시지(No.46) 운영 요구 (2026-09-27 추가)

`channel-rich-messages-설계.md` · ADR-0043. 캐러셀·바로연결을 쓰는 설치의 **운영 책임**이다.

1. **마이그레이션**: `20260927120000_channel_rich_messages`(`CREATE TABLE` 1개) 적용 뒤 원시 부분 유니크 인덱스 개수가 4 그대로인지 · 신규 테이블 1(`chatbot_rich_url_policies`) · 외래 키 점검 0행을 확인한다.
2. **위젯 교체와 구버전**: `widget.js` 교체 직후 브라우저 캐시(`max-age=300` — 최대 5분)나 고객사가 복사해 둔 구 스크립트는 기능 선언 `rich-v1`을 보내지 않으므로 캐러셀이 **카드 여러 개(세로)**로 보인다 — 서버 강등으로 정상이며 빈 말풍선은 없다.
3. **호스트 페이지 CSP**: 캐러셀 이미지를 쓰려면 고객사 페이지 CSP `img-src`에 이미지 호스트를 넣어야 한다. 막히면 이미지 자리에 대체 텍스트가 보인다(연동 가이드에 안내).
4. **개인정보 고지**: 캐러셀 이미지는 **최종 사용자 브라우저가 이미지 호스트에 직접 접속**해 받는다(IP·브라우저 정보가 그 호스트에 노출 — Referer는 보내지 않는다). 외부 이미지 호스트를 쓰는 고객사는 처리방침에 고지한다. 폐쇄망·거버넌스 모드 설치는 **사내 이미지 서버 + 챗봇 설정 "리치 메시지 주소 허용 목록"**을 권장한다(목록이 비어 있으면 모든 https 주소 허용).
5. **배포 후 확인**: 위젯 번들 gzip 증가 ≤6KB(빌드 로그) · 신버전 위젯의 메시지 요청 `features` 3개 · 챗봇 설정 "리치 메시지 주소 허용 목록" 화면(목록 밖 주소 노드 수 표시).

### 5.7 지식베이스 동기화(No.43) 운영 요구 (2026-09-27 추가)

`kb-crawling-설계.md` · ADR-0044. 지식베이스 동기화를 켜는 설치의 **운영 책임**이다.

1. **마이그레이션**: `20260927150000_kb_crawling`(`CREATE TABLE` 5개) 적용 뒤 원시 부분 유니크 인덱스 개수가 4 그대로인지 · 신규 테이블 5(`kb_sources`·`kb_documents`·`kb_sync_runs`·`kb_ingest_jobs`·`kb_job_leases`) · 외래 키 점검 0행을 확인한다. **[No.43 pass 6]** 두 번째 마이그레이션 `20260928100000_kb_document_parent`(`kb_documents`에 nullable 컬럼 `discoveredFromId` + 인덱스 1 · 백필 0)도 함께 적용되며, 적용 뒤에도 부분 유니크 인덱스는 4개 그대로여야 한다. `KB_SYNC_LEASE_MS`는 **300000 이상**이어야 한다(미만이면 기동 실패 — 기본 600000). 이 그룹 커밋 전 코드로 크롤한 개발·시연 DB는 검증자를 1회 비우거나(`UPDATE "kb_documents" SET "etag" = NULL, "lastModified" = NULL WHERE "kind" = 'HTML'`) DB를 다시 만든다(`kb-crawling-설계.md` §25.4 · K-16). 경로 접두는 경로 단위로 비교한다(`/docs`는 `/docsecret`을 포함하지 않음). **[No.43 pass 7·8]** 세 번째 마이그레이션 `20260928120000_kb_document_observed_hash`(`kb_documents`에 nullable 컬럼 `observedHash` 1 · 백필 0 · 데이터 초기화 불요)도 함께 적용되며, 적용 뒤에도 부분 유니크 인덱스는 4개 그대로여야 한다. `KB_SYNC_LEASE_MS`는 `KB_CRAWL_TIMEOUT_MS × 4 + 120000` 이상이어야 한다(미만이면 기동 실패 — 기본값은 해당 없음 · 타임아웃을 45초 넘게 올리면 임대도 올린다: 60초 → 360000 이상). 소스 요청 간격·robots `Crawl-delay`는 서버가 300초로 잘라 적용한다. **거버넌스 모드(`DATA_GOVERNANCE_MODE=ON`)를 켜기 전에** 지식베이스 소스의 마스킹·원본 파일 전달 설정을 점검한다 — 모드를 켠 뒤 마스킹 끔(또는 `KB_ALLOW_RAW_FILE_INGEST` 없이 원본 파일 전달)인 소스는 실행(미리보기 포함)이 409로 거부되고, 예약은 건너뛰며(감사 `[예약 실행 건너뜀]`), 진행 중 적재는 제출 직전에 중지된다(실행 이력 사유 코드 · 감사 `[적재 차단]` 1건 — No.43 pass 10 · 이미 외부에 접수된 작업은 계속됨).
2. **켜기 순서**: `KB_SYNC_ENABLED=true` → (사내 사이트면) `KB_CRAWL_PRIVATE_ALLOWLIST`에 사내 대역·호스트 → (거버넌스 모드면) `DATA_EGRESS_ALLOWED_HOSTS`에 크롤 대상 호스트 → 외부 RAG 전송 구간 확인 후 `KB_INGEST_TRANSPORT_ACK`. ACK가 없으면 등록·미리보기만 된다. (No.43 pass 12) 수집 범위는 시작 주소·사이트맵에 적힌 **출처(호스트+포트)** 단위다 — 같은 호스트의 다른 포트 문서를 수집하려면 그 포트 주소를 시작 주소나 사이트맵에 넣는다(링크로만 발견된 다른 포트는 범위 밖). robots.txt는 출처마다 따로 읽는다. (No.43 pass 13) 소스 인증 헤더는 평문 `http://` 요청에는 시작 주소·사이트맵을 `http://`로 등록한 출처(호스트+포트)에만 실린다 — `https://`로 등록한 사이트가 같은 호스트의 `http://` 링크를 내놓으면 그 요청은 헤더 없이 나간다(사이트가 https로 리다이렉트하면 그 뒤 요청에는 실린다). 인증이 필요한 평문 전용 사이트는 시작 주소를 `http://`로 등록해야 하며, 이는 자격증명이 평문으로 나가는 것을 운영자가 받아들인다는 뜻이다(가능하면 사이트에 TLS를 적용한다).
3. **전송 전제 확인 절차**: `INTERNAL_NETWORK` = 챗봇 서버와 외부 RAG가 같은 사내망(공인 IP 경유 없음)임을 네트워크 담당자가 확인 · `AUTHENTICATED` = 외부 RAG 앞단(역프록시·mTLS 등)이 인증을 강제함을 확인 · `TLS` = `RAG_BASE_URL`이 https(서버가 검증). 확인 기록을 설치 문서에 남긴다.
4. **첫 적재 전 형식·처리량 실측**: HTML 10쪽·PDF 5개로 형식(`KB_HTML_INGEST_FORMAT` — 외부 담당자 확인 전 기본 DOCX)·처리 시간을 실측하고 `KB_INGEST_CONCURRENCY`·`KB_INGEST_BULK_WINDOW`(예: `19:00-08:00`)를 정한다. **형식은 첫 적재 뒤 바꾸지 않는다**(바꾸면 외부에 옛 파일이 남는다).
5. **외부 RAG 운영자 합의**: 소스마다 **전용 서브카테고리** 사용 · `kb_`로 시작하는 파일 이름은 직접 업로드하지 않기 · "정리 필요" 표시가 쌓이면 외부에서 그 서브카테고리를 정리한 뒤 콘솔의 "전체 다시 적재(정리 완료 확인)"를 누르기.
6. **UA·권리**: `KB_CRAWL_USER_AGENT`에 관리자 연락처를 덧붙인다(예: `ChatBotKBCrawler/1.0 (+mailto:it@example.co.kr)`). 자사·계약상 이용 권한이 있는 사이트만 등록하고, 개인정보가 게시된 페이지는 제외 패턴으로 뺀다.
7. **배포 후 확인**: 콘솔 "지식베이스 동기화" 메뉴 표시 · 소스 1개 미리보기 성공 · 데이터 지도 "지식베이스 동기화" 절 · 적재 1건 성공 후 외부 RAG 질의로 근거 확인 · 서버 로그에 URL 쿼리·헤더 값이 없는지.

3. **경량 설치 구성(Ollama) — 동작 보장·품질 미보증**: Ollama는 **루프백에만 바인딩**(`OLLAMA_HOST=127.0.0.1:11434`)하고 사내망에 열지 않는다. ml-worker `GENERATION_BACKEND=ollama` · `OLLAMA_MODEL=<태그>` · `OLLAMA_TARGET_CAP=20`(API가 60건을 요청해도 20건까지만 생성 — 제안 수는 줄지만 시간 안에 온다) · `OLLAMA_REQUEST_TIMEOUT_S=25`. 고객·영업 자료에 이 구성의 품질 수치를 쓰지 않는다. 상태 확인: 생성 프로세스 `GET /augment/health`의 `profile`이 `lightweight`. 장비가 느려 20건이 25초를 넘으면(로그 "호출 실패 — 빈 후보로 수렴" 반복 · 콘솔 "기본 방식으로 생성") `OLLAMA_TARGET_CAP`을 낮춘다.
4. **운영 구성(vLLM) — 예문 늘리기 전용 사내 vLLM 서버**: **외부 RAG가 쓰는 vLLM을 ml-worker가 직접 부르지 않는다**(외부 RAG 접촉면 봉인 — ADR-0022 · 답변 지연·장애 전파). ml-worker `GENERATION_BACKEND=vllm` · `VLLM_BASE_URL=http://<사내 주소>:<포트>`(끝에 `/v1`을 붙이지 않는다) · `VLLM_MODEL=<vLLM served-model-name>` · (vLLM에 키를 걸었으면) `VLLM_API_KEY`. 어떤 모델을 운영에 켤지는 **No.17 실측·합격 판정**이 정한다 — 그전 기본값(`VLLM_TARGET_CAP=60` · `VLLM_MAX_NEW_TOKENS=2048`)은 출발값이다.
5. **생성 백엔드 주소 통제** — 이 구간(ml-worker → Ollama/vLLM)으로 **마스킹하지 않은 예문 시드**가 간다. 기본은 루프백·사설 대역(`10/8`·`172.16/12`·`192.168/16`·`fc00::/7`)·`localhost`만 허용하고, 이름은 기동 시 해석한 모든 주소가 사설이어야 한다. 다른 주소가 필요하면 `GENERATION_BACKEND_ALLOWED_HOSTS`에 명시한다. 거버넌스 설치는 `GENERATION_BACKEND_REQUIRE_ALLOWLIST=true`(사설·루프백도 목록 필수). 링크로컬(`169.254.0.0/16` 등 — 클라우드 메타데이터)은 목록에 있어도 거부되고 리다이렉트는 따라가지 않는다. 기동 뒤 DNS 변경으로 검사가 우회될 수 있으므로 **IP 주소 또는 hosts 파일 고정**을 권장한다.
6. **폐쇄망 모델 반입**(기동 중 외부 내려받기 0): **HF(임베딩 · `transformers` 생성)** — 인터넷 PC에서 **리비전을 고정**해 내려받고 캐시 디렉터리를 통째로 반입 → `HF_HOME=<반입 경로>` + `HF_HUB_OFFLINE=1`. **Ollama** — 인터넷 PC(대상과 **같은 Ollama 버전**)에서 `ollama pull <태그>` → 모델 저장소(`OLLAMA_MODELS`로 지정한 경로 또는 설치 기본 경로)의 `manifests/`·`blobs/`를 통째로 반입해 같은 구조로 배치 → `ollama list`로 태그 확인 · 매니페스트 digest를 설치 기록에 남긴다. ml-worker는 모델을 **확인만** 하고 내려받지 않는다(없으면 기동 실패 — "`ollama pull`로 받은 뒤 다시 시작"). **vLLM** — 인터넷 PC에서 모델 저장소를 **리비전 고정**으로 내려받아 반입 → vLLM을 로컬 경로 + `--served-model-name <이름>` + `HF_HUB_OFFLINE=1`로 기동 → ml-worker `VLLM_MODEL=<이름>`. ⚠ 기본 저장 경로·기동 인자 이름은 버전마다 다를 수 있다 — 설치하는 버전의 문서로 확인해 설치 기록에 남긴다.
7. **모델 라이선스 기록**(문서에 올린 모델 — 상업 이용을 막는 모델은 올리지 않는다 · **법무 재확인 필요**):

| 모델 | 쓰는 곳 | 라이선스 | 확인 방법·일자 |
|---|---|---|---|
| `nlpai-lab/KURE-v1` | 임베딩(전 등급) | MIT | HF API — `apps/ml-worker/eval/report/model-comparison.md` |
| `qwen3:4b-instruct-2507-q4_K_M` | 등급 1 경량 생성 | Apache-2.0 | `ollama show` 표기 · 2026-09-29(`ollama-dev-pipeline-validation.md`) |
| 운영 vLLM 모델 | 등급 3 | 미정 — No.17 채택 시 기록(Gemma 계열은 자체 이용약관이라 표준 공개 라이선스가 아님에 주의) | — |

8. **시간 제한 조정 규칙**: ml-worker 원격 요청 시간 제한(`OLLAMA_REQUEST_TIMEOUT_S`·`VLLM_REQUEST_TIMEOUT_S`, 기본 25초)은 API `AUGMENTATION_TIMEOUT_MS`(기본 30000)보다 **5초 이상 짧게** 둔다. API 값을 올리면 함께 올린다(30초를 넘기면 ml-worker 기동 경고). 이전 `.env.example`을 복사한 설치는 `OLLAMA_REQUEST_TIMEOUT_S=90`이 남아 있으니 25로 고친다.
9. **설치 점검**(생성 백엔드를 켠 설치): ① 생성 프로세스 `GET /augment/health` — `status=ok` · `backend`가 의도한 값 · `transformers`면 `modelId`가 `mock-generator@0`이 아님 · 원격이면 `device=external` · `targetCap` 확인 ② 생성 백엔드 주소가 같은 서버 또는 사내 대역(거버넌스 설치는 허용 목록 필수 스위치 켬) ③ `VLLM_BASE_URL`이 외부 RAG의 vLLM이 아님 ④ 모델 라이선스 기록 존재(7번) ⑤ 생성·임베딩 프로세스 분리 · 등급 1은 임베딩 CPU ⑥ 폐쇄망: 네트워크 차단 상태에서 Ollama·vLLM·ml-worker가 모두 기동됨(내려받기 시도 0) ⑦ 로그에 `VLLM_API_KEY` 값이 없음.
10. **업그레이드 시 동작 변화**(이 그룹 반영 전 설치): Ollama 요청 시간 제한 90 → 25초 · 공인 주소 Ollama는 기동 실패(허용 목록 필요) · 알 수 없는 `GENERATION_BACKEND` 값은 생성 프로세스 기동 실패 · Ollama 경로 1회 생성 60 → 20건 · Ollama 최대 토큰 512 → 768(`GENERATION_MAX_NEW_TOKENS`를 명시하지 않았을 때). DB 마이그레이션 없음.

### 5.9 발화 묶음 분석(No.21 딥러닝 군집분석) 운영 요구 (2026-09-30 추가)

`deep-clustering-설계.md` · ADR-0047. 발화 파일(상담 녹취 전사본 등)을 받아 묶는 기능을 쓰는 설치의 **운영 책임**이다. 처리 시간·대화 영향 수치는 운영 장비 실측 전까지 **목표**다.

1. **마이그레이션**: `…_utterance_analysis`(`CREATE TABLE` 3 + 인덱스) 적용 뒤 원시 부분 유니크 인덱스 개수가 **4 그대로**인지 확인한다(생성 SQL에 `DROP INDEX`가 끼었으면 그 줄을 지우고 적용). 데이터 이관·백필 없음.
2. **전제**: `EMBEDDING_BASE_URL`(문장 분석)이 설정돼 있어야 한다(없으면 요청이 503). 분석은 대화와 **같은 ml-worker**를 쓴다 — 등급 0·1 장비(§5.8)는 큰 파일 분석을 대화가 적은 시간에 돌리도록 사용자에게 안내한다.
3. **자동 삭제**: 분석 결과는 생성 후 `UTTERANCE_ANALYSIS_RETENTION_DAYS`(기본 90일)가 지나면 **No.45 파기 잡**(`DATA_RETENTION_JOB_ENABLED` · `DATA_RETENTION_WINDOW`)이 지운다. 파기 잡을 끈 설치는 자동 삭제가 일어나지 않는다(데이터 지도 경고) — 수동 삭제로 관리한다. 일수를 바꾸면 **새 분석부터** 적용된다.
4. **개인정보**: 업로드 전에 이름·주소처럼 **자동으로 가려지지 않는 정보**를 지우도록 사용자에게 안내한다(정규식 마스킹 한계). 원본 파일은 서버에 저장되지 않는다. 디스크 암호화가 거버넌스 설치의 전제인 것은 대화 데이터와 같다(§5.3).
5. **이름 제안(선택)**: `UTTERANCE_ANALYSIS_NAME_SUGGEST_ENABLED=true` + `AUGMENTATION_LOCAL_BASE_URL`(생성 프로파일 ml-worker — §5.8 프로세스 구성). 모델·백엔드는 생성 프로세스 설정을 따른다(§5.8). 경량 구성(3050·Ollama)의 이름 품질은 "동작 확인"뿐이다. 거버넌스 모드에서 켜면 그 호스트가 `DATA_EGRESS_ALLOWED_HOSTS`에 있어야 API가 기동한다. ml-worker가 이 그룹 이전 버전이면 `/cluster-label`이 없어 이름 제안만 실패한다(분석은 정상 완료).
6. **부하 게이트(운영 장비 · 첫 사용 전 1회)**: 5,000행 분석을 돌리는 동안 대화 턴을 반복 호출해 ① 대화 임베딩 P95(예산 300ms) ② 임베딩 회로 개방 여부 ③ 결과 저장 시간 ④ 총 소요 시간을 기록한다. P95 초과·회로 개방이 보이면 `UTTERANCE_ANALYSIS_EMBED_YIELD_RATIO`를 올리고(예: 2.0) 다시 잰다 — 그래도 안 되면 분석 전용 임베딩 프로세스 설계를 요청한다(ADR-0047 재검토 트리거).
7. **배포 후 확인**: 콘솔 "발화 묶음 분석" 메뉴 · 양식 받기 · 합성 파일 1개 분석 완료 · 엑셀 다운로드 시 감사 `EXPORT` 1건 · 데이터 지도 "업로드 발화 분석" 절 · 서버 로그에 발화 문장·파일 이름이 없는지.

### 5.10 AI 거버넌스·가드레일(No.36) 운영 요구 (2026-09-30 추가)

`ai-guardrails-설계.md` · ADR-0048. 위험 응답 규칙·RAG 답 개인정보 가림·운영 전환 2인 승인을 쓰는 설치의 **운영 책임**이다. 모델·GPU·새 외부 출구가 없다.

1. **마이그레이션**: `…_ai_guardrails`(`CREATE TABLE` 4 + 인덱스 + `ADD COLUMN` 5) 적용 전 생성 SQL에 `new_` 테이블·`DROP INDEX`가 없는지 확인하고, 적용 후 원시 부분 유니크 인덱스가 **4개 그대로**인지 `sqlite_master`로 확인한다. 데이터 이관·백필 없음.
2. **배포 즉시 바뀌는 것**: 외부 RAG 답에서 **주민등록번호·카드번호 형식이 기본으로 가려진다**(모든 챗봇 — 챗봇별로 끌 수 있음 · 거버넌스 모드 제외). 카드 형식은 14~16자리 연속 숫자(주문번호 등)도 가릴 수 있으므로, RAG를 쓰는 챗봇 담당자에게 "안전 가드레일 > 개인정보 가림" 설정 확인을 안내한다. 위험 응답 규칙은 0개로 시작한다(제품이 의료·법률 문구를 미리 넣지 않는다).
3. **규칙 운영**: 새 규칙은 "기록만"으로 시작해 현황의 적중 수와 이벤트(대화 마스킹본)를 확인한 뒤 "대체"로 강화한다. 다중 인스턴스에서는 규칙 변경이 다른 인스턴스에 `GUARDRAIL_CACHE_TTL_MS`(기본 60초) 뒤 반영된다. 긴급 시 `GUARDRAILS_ENABLED=false`로 규칙·가림을 전부 끌 수 있다(재기동 필요).
4. **2인 승인**: 환경 모드 챗봇에서 켤 수 있고, 활성 ADMIN(`chatbot:deploy`)이 **2명 이상**이어야 한다. 켜진 동안 운영 전환은 "승인 요청 → 다른 ADMIN 승인"이 되며 직전 운영 버전 롤백만 즉시 가능(기록됨)하다. 켜진 동안에는 환경 모드를 끌 수 없다(정책부터 끈다). 예약 전환은 예약 작성자가 승인 요청을 만들어야 실행된다(없으면 `승인 없음`으로 실패). 승인 정책 끄기를 서버 차원에서 막으려면 `ENV_APPROVAL_OFF_LOCKED=true`. **2026-10-01부터 거버넌스 모드(`DATA_GOVERNANCE_MODE=ON`) 설치는 이 값을 설정하지 않아도 끄기가 잠긴다**(명시값 우선 — §5.11).
5. **알림**: 승인 대기는 콘솔 배지로만 알린다(메일·메신저 알림 없음 — No.41 2차). 승인자가 만료(기본 24시간) 전에 확인하도록 운영 절차에 넣는다.
6. **배포 후 확인**: 콘솔 "안전 가드레일" 탭 · 시험하기로 규칙 1개 판정 · 가짜/실제 RAG 답의 가림 표시(시뮬레이터 RAG 답 미리보기) · 2인 승인 켜기 → 요청 → 다른 계정 승인 → 전환 이력 "2인 승인" 표식 · 감사 로그 대상 "규칙"·"운영 전환 승인 요청" · 서버 로그에 질문·답·표현·사유 문장이 없는지.

### 5.11 PM 결정(2026-10-01) 반영 운영 요구 — 증강 폴백 · 2인 승인 끄기 잠금 · 저장 마스킹 날짜 제외

`pm-decisions-2026-10-01-설계.md` · ADR-0049. 마이그레이션 0 — API(+ 콘솔) 교체만.

1. **빌드**: 폐쇄망 반입 빌드는 `pnpm --filter @chat-bot/pii-mask build` · `pnpm --filter @chat-bot/shared-types build`를 **API 빌드 전에** 실행한다(API는 두 패키지를 `dist`로 싣는다 — 빌드를 빠뜨리면 구 규칙이 조용히 남는다). 배포 후 API 기동 로그에 `pii-mask 규칙 v2(저장 마스킹 날짜 제외 · 생년월일 문맥 예외)` 1줄이 있는지 확인한다.
2. **다중 인스턴스**: 전 인스턴스를 동시에 교체한다(혼재 중에는 인스턴스마다 저장 마스킹 결과·끄기 잠금 판정이 다르다).

### 5.14 음성 AI(No.32) 운영 요구 (2026-10-02 추가)

`voice-ai-설계.md` · `docs/requirements/voice-ai.md`(FR-VO7) · ADR-0052. "눌러서 말하기"(서버 음성 인식 STT)와 "답변 듣기"(사용자 기기 음성)를 쓰는 설치의 **운영 책임**이다. 이 절은 문서이며 실 배포·CI·인프라 파일을 만들지 않는다(§1). 근거 없는 수치는 **제안·미실측**이다.

1. **스위치와 공급자**: API `SPEECH_ENABLED`(기본 `false` — 서버 음성 인식 스위치. **읽기(듣기)에는 영향 없음**) · 운영 설치는 **`SPEECH_PROVIDER=local` 필수**(기본값은 `mock`). 운영(`NODE_ENV=production`) ∧ `SPEECH_ENABLED=true` ∧ `mock`은 API 기동 실패다 — 단 `NODE_ENV=production`이 설정돼 있을 때만(§2). `ML_WORKER_SPEECH_URL`이 없으면 기동은 되지만 입력 사용 불가(마이크 숨김) + 경고 1회다. 운영 API는 ml-worker 상태의 `backend=mock`도 사용 불가로 본다(마이크 숨김 + 경고). `SPEECH_PROVIDER` 오타는 API 기동 실패. 스위치를 켜지 않으면 기존 동작은 도입 전과 같다.
2. **프로세스 분리**: 음성 인식은 `ML_WORKER_ROLE=speech`(배타 — STT 1종 + VAD만 적재, 임베딩·생성 적재 0)로 **별도 프로세스·포트 8102**에 둔다. 실행은 `pnpm --filter ml-worker run start:speech`(`scripts/start-speech.mjs`가 역할·포트를 지정, 포트를 미리 설정했으면 그 값을 따름) 또는 같은 진입점(`ml_worker.app:app`)에 `ML_WORKER_ROLE=speech ML_WORKER_PORT=8102` 지정. `both` 역할에 음성을 합치는 조합은 없다. 이유: 공개 요청이 부르는 GPU 추론이 대화 임베딩(300ms 예산)과 스레드·GPU 메모리를 다투지 않게 하기 위함이다(§5.8-2와 같은 원칙). 음성 프로세스의 설정 오류(역할·`STT_BACKEND` 오타, `faster-whisper`인데 `STT_MODEL_ID` 없음, CUDA 적재 실패)는 **음성 프로세스만** 기동 실패하고 조용히 CPU로 대체하지 않는다(임베딩·대화 무영향).
3. **ml-worker 설정**(`apps/ml-worker/.env.example` 음성 절 — 전부 선택, `speech` 역할에서만 읽힘): `STT_BACKEND=faster-whisper` · `STT_MODEL_ID`(필수, 기본 모델 없음 — 캐시 이름 또는 로컬 경로) · `STT_MODEL_DIR` · `STT_DEVICE=cpu|cuda`(기본 cpu) · `STT_COMPUTE_TYPE=int8|int8_float16|float16|float32`(기본 int8) · `STT_BEAM_SIZE` 5 · `STT_CPU_THREADS` 0 · `STT_MAX_CONCURRENCY` 2 · `STT_MAX_AUDIO_BYTES` 1MB · `STT_MAX_AUDIO_SECONDS` 32 · `STT_DEADLINE_S` 8.0 · `STT_VAD=auto|silero|energy|off`. 기본값은 출발값이며 장비별 조정은 실측 전까지 제안이다. `STT_DEADLINE_S`는 API `SPEECH_STT_TIMEOUT_MS`(기본 10000)보다 짧게 둔다(9초 초과 설정은 기동 경고 — §5.8-8과 같은 규칙).
4. **GPU 공유 시 VRAM 예산**: 임베딩 + STT + (같은 GPU에 둘 때) 생성 모델의 합계가 장비 VRAM 안에 들어야 한다. 합계·임베딩 P95 영향은 **미실측**이며 운영 실측은 L40S에서 No.17과 한 번에 한다(설계서 §8.8). 3050(4GB)는 "동작 확인"만이다. 4GB급은 STT를 CPU에 두는 구성을 먼저 검토한다(제안·미실측).
5. **모델 반입(폐쇄망 — 기동 중 외부 내려받기 0)**: 기동 시 `local_files_only`가 고정이라 설정으로 끌 수 없고 모델이 없으면 기동 실패다. 인터넷 PC에서 `python scripts/fetch_stt_model.py <모델 이름|HF 저장소 ID> --out <디렉터리> [--revision <리비전>]`(`faster-whisper` 필요 — `pip install -e ".[speech]"`)로 받는다(**리비전 고정 권장**) → 그 디렉터리를 폐쇄망 서버로 복사 → ml-worker `STT_MODEL_ID=<디렉터리 경로>` 또는 `STT_MODEL_DIR=<캐시 루트>` + `STT_MODEL_ID=<이름>`. 의존성은 선택 묶음 `[speech]`(faster-whisper·PyAV)이고 기본 설치(임베딩)에는 들어가지 않는다. 설치는 `pip install -c requirements-lock.txt -c requirements-speech-lock.txt -e ".[dev,speech]"`(`requirements-speech-lock.txt`는 CPU 실행 기준 검증 조합 — 2026-10-01 · Python 3.10.11 · Windows. GPU의 CUDA·cuDNN 요구는 ctranslate2 빌드별로 달라 동작 확인 기록에 **실제 버전을 남긴다**). 기동 후 `GET /speech/health`의 `status`·`backend`·`modelId`·`device`·`computeType`(실제 적재값)을 설치 기록에 남긴다. 네트워크를 차단한 상태에서 기동되는지 확인한다.
6. **라이선스 원문 확인(U-4 — 법무 재확인 필요)**: faster-whisper · Whisper 가중치 · CTranslate2 · PyAV · FFmpeg 빌드(PyAV 휠 동봉 빌드의 LGPL 여부는 **확인 필요**) · Silero VAD의 이름·조건·확인일을 `apps/ml-worker/eval/report/` 보고서 부록에 기록한다. 상업 이용을 막는 항목은 올리지 않는다. 아래 표는 확인 전 상태이며 원문 확인 후 채운다.

| 항목 | 쓰는 곳 | 라이선스 | 확인 방법·일자 |
|---|---|---|---|
| STT 모델(가중치) | 등급 0~3 | 미확인 — 모델 선정 후 기록 | — |

| PyAV · FFmpeg 동봉 빌드 | 오디오 디코딩 | 미확인(LGPL 빌드 여부 확인 필요) | — |
| Silero VAD(faster-whisper 동봉) | VAD | 미확인 | — |

7. **동시 처리·시간·크기 한도(세마포어)**: API `SPEECH_MAX_CONCURRENCY` 2(1~32 · 초과 즉시 503) · ml-worker `STT_MAX_CONCURRENCY` 2(비대기 세마포어 — 초과 즉시 503 `BUSY` · `num_workers`와 같은 값). 요청 한도 `PUBLIC_SPEECH_RATE_LIMIT_IP_PER_MIN` 30 · `PUBLIC_SPEECH_RATE_LIMIT_SESSION_PER_MIN` 10. 본문 상한 `SPEECH_MAX_AUDIO_BYTES`·`STT_MAX_AUDIO_BYTES` 1MB는 같은 값을 권장. 위 값은 설계 기본값이며 장비 등급에 맞춘 값은 **미실측**(OC-8). 공개 경로이므로 남용(비용·자원 소진) 위험을 고객에게 고지한다. 음성 원본은 디스크·DB·로그에 남기지 않는다(디스크 0 디코딩) — 서버 로그에는 바이트 수·지속 시간·결과 코드·처리 시간만 남는다.
8. **HTTPS 필수 · 고객사 삽입 안내**(고객사에 전달 — 근거 FR-VO7-5): ① 위젯을 넣는 페이지가 **HTTPS**여야 한다(아니면 마이크 버튼이 숨겨진다) ② 페이지의 `Permissions-Policy`가 마이크를 막지 않아야 한다(`microphone` 허용) ③ 위젯을 **아이프레임** 안에 넣으면 `<iframe allow="microphone">`이 필요하다 ④ 위젯은 아이프레임이 아닌 고객사 페이지 DOM(Shadow DOM)에 붙으므로 마이크 권한 창에는 **고객사 사이트 주소**가 표시된다 ⑤ **답변 듣기는 사용자 기기·브라우저에 한국어 음성(기기 안에서 동작하는 `localService` 음성)이 있어야** 동작하고, 없는 PC(예: 한국어 음성 팩이 없는 Windows — **확인 필요**)에서는 듣기가 비활성으로 보일 수 있다. 서버 설치만으로는 해결되지 않으며 기기·브라우저별 결과는 수동 게이트 문서(`docs/04-test/`)를 따른다.
9. **설치 점검**(음성 입력을 켠 설치): ① API `NODE_ENV=production`이 배포 설정(Compose `api.environment`·서비스 단위 파일·pm2·systemd)에 **명시**돼 있음(§2) ② `SPEECH_ENABLED=true` · `SPEECH_PROVIDER=local` · `ML_WORKER_SPEECH_URL` ③ 음성 프로세스가 `ML_WORKER_ROLE=speech`로 별도 기동(포트 8102 · 임베딩 프로세스와 분리) · `GET /speech/health` `status=ok` · `backend=faster-whisper` · `modelId` · `warmedUp` 확인 ④ 콘솔 챗봇 음성 구역의 서버 상태가 "사용 가능" ⑤ 라이선스 기록 존재(6번) ⑥ `SPEECH_MAX_CONCURRENCY`·`STT_MAX_CONCURRENCY`·요청 한도가 장비 등급에 맞음 ⑦ HTTPS·고객사 삽입 안내 전달 기록(8번) ⑧ 거버넌스 모드 ON이면 `ML_WORKER_SPEECH_URL` 호스트가 `DATA_EGRESS_ALLOWED_HOSTS`에 있고 데이터 지도에 `SPEECH_LOCAL` 행·`speech` 절이 보임(허용 목록 밖이면 API 기동 실패) ⑨ 폐쇄망이면 네트워크 차단 상태에서 기동됨 ⑩ 서버 로그에 음성 데이터·인식 글자가 없음. 이후 아래 **개통 전 체크리스트**를 통과한다.
10. **롤백**: ① 가장 빠른 방법 — API `.env`의 `SPEECH_ENABLED=false`로 바꾸고 재기동(서버 음성 입력이 꺼지고 마이크 버튼이 사라지며, 대화는 도입 전과 같다. 챗봇별 음성 입력 끄기는 콘솔에서도 가능) ② 음성 프로세스(8102)만 중지해도 임베딩·대화는 무영향(음성 입력은 사용 불가로 수렴) ③ 코드 롤백이 필요하면 직전 API 버전으로 되돌린다 — 이 기능의 DB 변경은 신규 2개 테이블 추가이고 기존 테이블 변경·데이터 이관은 없다(되돌릴 때 두 테이블은 남겨 두어도 기존 기능에 영향이 없는 것으로 설계됐으나 제거 절차는 별도 확인 필요).
11. **배포 후 확인**: 콘솔 챗봇 "음성" 구역 · 공개 설정 `voice` 키 · 위젯 마이크 버튼 노출(HTTPS) · 실제 발화 1건이 STT를 거쳐 입력창에 채워짐(mock 문구 "모의 인식 결과입니다"가 아님) · 서버 로그에 오디오·인식 글자가 없는지.
