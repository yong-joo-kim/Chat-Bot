## 0. 전제와 연계 확인

1. **아키텍처 제약 F-1~F-14(설계서 §12)를 그대로 받아들인다.** 이 문서는 그 제약을 뒤집지 않고, 제약이 열어둔 화면 구성만 판단한다. 특히:
   - F-1: 비율·합계·세션당 턴수는 서버 응답값을 표시만 한다. 프런트 재계산 금지(NFR-M2).
   - F-2: 빈 버킷은 서버가 0으로 채워 보낸다. 프런트가 날짜를 보간하지 않는다.
   - F-3: 통계 3종 API(`summary`/`distribution`/`questions`)는 독립 호출·부분 렌더다(NFR-P8).
   - F-5: `sessionCount`는 버킷별 distinct 재계산 값이라 합계 보존이 성립하지 않는다 — 캡션 필수.
   - F-7: 권한 없는 쓰기 액션은 숨김(비활성 아님).
   - F-8: 노드 미연결 경고는 토스트가 아니라 **지속 표시 경고 영역**.
   - F-10: `appliedImmediately` 값에 따라 문구가 갈린다. `"반영 완료"`/`"다음 대화부터 적용됩니다"`를 하드코딩된 `true` 전제가 아니라 **응답값 분기**로 구현한다.
2. **현재 코드 상태 확인 결과**(이 문서의 전제):

## 1. 화면 목록 및 정보구조 결정

### 1.1 정보구조 결정 — 8탭 과밀 문제 (FR-C-1)

**결론: 챗봇 상세 최상위 탭에 `통계` 1개만 추가한다(6탭 → 7탭). `기본 통계`와 `학습현황`은 그 안의 내부 서브내비 2개로 배치한다(`DialogueShell` 선례 재사용).**

architect가 제시한 3안과의 관계:

| 안 | 내용 | 채택 여부 |
|---|---|---|
| ① 그룹 내 탭 추가 | 통계→운영, 학습현황→설계 또는 검증에 **각각** 탭 추가(6→8탭) | **부분 채택 + 변형.** "그룹 내에 탭을 추가"하는 방향은 맞지만, 통계와 학습현황을 **별개의 최상위 탭 2개**로 쪼개지 않고 **최상위 탭 1개 + 내부 서브내비 2개**로 묶는다(아래 근거) |
| ② 대시보드 하위 서브탭 통합 | `대시보드` 탭 안에 통계를 서브탭으로 | **기각.** No.14는 J-4로 대시보드와 목적·시간축이 다르다고 이미 확정됐다("스냅샷" vs "추세"). 같은 탭 안에 넣으면 이 구분이 화면에서 사라지고, 대시보드 탭 하나의 콘텐츠 밀도가 과도해진다(카드+Top5도 이미 있음) |
| ③ 좌측 내비/별도 화면 분리 | 챗봇 상세 탭바 바깥으로 완전히 분리 | **기각.** `security-audit.md`의 이력관리가 이 안을 택한 이유(① ADMIN 전용이라 역할마다 탭 수가 달라짐 ② 드물게 조회 ③ 전역 리소스)가 **이 그룹에는 하나도 해당하지 않는다**(아래 "왜 audit 선례를 따르지 않는가") |

**최종 결정 근거**

1. **`DialogueShell`이 이미 검증된 선례다.** `대화설계` 탭 1개가 5개 서브내비(대화상자/의도·키워드/동음이의어/컨텍스트/FAQ)를 좌측 레일로 감싸는 구조가 이미 구현·운영 중이다. "탭 1개가 여러 화면을 품는다"는 패턴이 이 코드베이스의 기존 관용구이므로, 통계 영역도 같은 패턴을 쓰면 **새 내비게이션 패러다임을 도입하지 않고** 문제를 해결한다.
2. **원본 매뉴얼(ROCHA)의 실제 정보구조와 일치한다.** `로차_간단학습매뉴얼.pdf` p.5의 좌측 내비 캡처를 보면 `대시보드`와 별개로 **`통계/분석`이 독립 메뉴이며 "하위 메뉴 있음"** 표시가 붙어 있다(§1.4 근거 6 — 이 문서 §1.4 원본 인용 재확인). 같은 문서 p.4 재학습 절차 플로차트의 `학습상태 변경(59p 학습현황 – 학습 완료 상태 변경)` 노드도 `미응답 리스트 확인` 바로 다음 단계로, **통계/분석 메뉴의 하위 화면**으로 위치가 자연스럽다(좌측 내비에 `학습현황`이라는 별도 1급 메뉴가 보이지 않는다 — p.5 캡처에는 `대시보드/챗봇설정/챗봇제작/채널설정/통계·분석/모니터링/설문관리/이력관리`만 있고 `챗봇제작` 하위에도 `학습현황`은 없다). 즉 **ROCHA 원본도 "통계/분석"이라는 상위 1개 진입점 아래 학습현황을 두는 구조**였을 가능성이 높다 — PM이 요청한 "p.59~62 원본 확인" 결과, 완전한 페이지 렌더는 이 환경에서 불가능했지만(§9-1의 조사 한계 재확인), 교차 근거만으로도 이 결정을 뒷받침한다.
3. **두 화면이 실제로 서로를 호출한다.** 응답 출처 분포의 `폴백` 조각(FR-14-21)과 미응답 순위 행(FR-14-25)은 **학습현황으로 이동하는 딥링크**를 갖는다(§6). 두 화면이 별개의 최상위 탭이면 "탭 전환"이라는 큰 맥락 전환이 일어나지만, 하나의 `통계` 영역 안의 서브내비 전환이면 **같은 화면 그룹 안에서 뷰만 바뀐다는 느낌**을 준다 — 사용자의 멘탈 모델과 실제 내비게이션 비용이 일치한다.
4. **탭 배지(FR-C-2)의 부착 위치가 명확해진다.** `PENDING` 건수 배지는 서브내비의 `학습현황` 항목에 붙고(§2.2), 상위 `통계` 탭에도 보조로 노출된다(§2.1) — "탭"이라는 요구사항 문구를 두 단계 모두에서 충족한다.

**왜 `security-audit.md`(FR-13-23)의 "탭을 늘리지 않고 전역 링크로 해결" 선례를 그대로 따르지 않는가**

| audit 선례가 성립한 이유 | 통계/학습현황에는 적용되지 않는 이유 |
|---|---|
| 이력 조회는 **ADMIN 전용**(`audit:read`)이라 VIEWER/EDITOR에게는 빈 탭이 된다 | 통계는 `chatbot:read`, 학습현황 조회는 `dialogue:read`로 **VIEWER도 접근**한다(§4). 6개 기존 탭과 동일한 권한 계층이라 탭 수가 역할마다 달라지는 문제가 없다 |
| "누가 지웠지?"처럼 **드물게, 특정 계기로만** 조회한다 | 통계는 **월말 보고 등 정기적으로**(S-1), 학습현황은 **운영 루프의 일상적 검토 대상**(S-5~S-11)이다. 상시 탭이 사용 빈도에 맞다 |
| 이력은 **챗봇 횡단 전역 리소스**(여러 챗봇을 한 화면에서 필터링) | 통계·학습현황은 **철저히 챗봇 스코프**다(전역 통계는 No.29, 이번 범위 아님). 전역 화면으로 뺄 이유가 원천적으로 없다(PM 프롬프트의 핵심 지적과 일치) |

### 1.2 화면 목록 및 라우트

| ID | 화면명 | 라우트 | 성격 | 진입 경로 | 필요 권한 |
|---|---|---|---|---|---|
| T0 | 통계 셸(`StatsShell`) | `/chatbots/:chatbotId/stats` | 서브내비 + 본문(`DialogueShell`과 동일 패턴) | `TabNav`의 `통계` 탭 | `chatbot:read` **또는** `dialogue:read`(아래 접근 규칙) |

**접근 규칙**: `T0`는 `chatbot:read` **또는** `dialogue:read` 둘 중 하나만 있어도 진입 가능(둘 다 있는 EDITOR/ADMIN은 두 서브내비 모두 보임). 어느 한쪽 권한만 있는 극단적 조합은 이번 역할 매핑(§2.1 상속, ADMIN/EDITOR/VIEWER 모두 두 권한을 함께 가짐)에서는 실제로 발생하지 않지만, `RequirePermission`을 개별 서브내비 항목 단위로 걸어 **미래의 권한 조합 변화에도 안전**하게 한다(각 서브내비 링크는 독립적으로 숨김 처리, §4).

### 1.3 서브내비 레이아웃 비교 — 좌측 레일이 아니라 상단 스트립을 쓰는 이유

`DialogueShell`은 서브내비 항목이 5개라 좌측 레일(세로 배치)이 적절했다. `StatsShell`은 항목이 **2개뿐**이라 좌측 레일을 쓰면 레일 폭 대비 항목 밀도가 지나치게 낮아진다. 대신 **탭바 바로 아래에 얇은 가로 스트립(밑줄 탭)**을 둔다 — `TabNav`(굵게+밑줄)와 시각적으로 구분되도록 스트립은 더 얇고 배경색이 옅다.

```
[TabNav]  대시보드 · 통계 · 설정 │ 대화설계 │ 응답 테스트 │ 스킨/임베드 · 채널
──────────────────────────────────────────────────────────
[StatsShell 서브내비]  기본 통계 | 학습현황 (●3)
──────────────────────────────────────────────────────────
  <서브내비가 가리키는 화면 본문>
```

## 2. 공통 UI 요소(신규)

### 2.1 `StatsShell` 컴포넌트

| 컴포넌트 | props | 규칙 |
|---|---|---|
| `StatsShell` | — (컨텍스트로 `chatbotId` 획득) | `DialogueShell`과 동일하게 `Outlet context={ctx}`로 상위 `useChatbotDetailContext()` 값을 전파한다. 진입 시 `/stats`(정확히 일치)면 `/stats/overview`로 리다이렉트 |

`pendingCount`는 `StatsShell` 마운트 시 `GET /chatbots/:chatbotId/unanswered-questions/summary`(FR-15-14, 경량 API)를 **1회** 호출해 얻는다. `학습현황` 화면(L1)에서 반영/무시/재오픈으로 건수가 바뀌면 L1이 콜백으로 `StatsShell`의 값을 갱신한다(리마운트 없이 상위 상태만 갱신 — `DialogueShell`이 `chatbot` reload를 상위로 전달하는 것과 동일한 패턴).

| 컴포넌트 | props | 표시 규칙 |
|---|---|---|
| `NavPendingBadge` | `{ count: number }` | `count === 0`이면 렌더하지 않는다(처리할 것이 없을 때는 배지 자체를 숨겨 시각적 소음을 줄인다). `count > 0`이면 숫자 + 원형 배경. **999건 초과 시 화면 표시는 "999+"** 로 자르되 `aria-label`에는 정확한 값을 담는다(`aria-label="대기 중인 미응답 질문 1234건"`). 색상은 중립(파랑 계열, 오류 아님) — 배지가 있다고 "나쁜 상태"가 아니라 "할 일이 있다"는 뜻이므로 위험색(빨강)을 쓰지 않는다(UIUX §1 색상 의미 체계 고정 원칙) |

부착 위치 2곳:
1. **필수**: `StatsSubNav`의 `학습현황` 항목 — `학습현황 (●3)` 형태, FR-C-2가 명시한 지점(AC-UI-1).
2. **보조(이 문서의 추가 제안)**: `TabNav`의 최상위 `통계` 탭에도 같은 값을 작게 노출 — 서브내비까지 들어가지 않아도 검토할 것이 있음을 알 수 있게 한다. `TabNav`는 현재 어떤 API도 호출하지 않는 순수 내비게이션 컴포넌트이므로, 이 값은 `ChatbotDetailLayout`(상위 컨텍스트)이 `summary` API를 1회 호출해 `TabNav`와 `StatsShell` 양쪽에 내려주는 방식을 권고한다(§10 구현 순서 메모).

### 2.3 `MetricCard` 5종 재사용

기존 `MetricCard`(`label`/`value`/`caption` 3-prop, No.2에서 3종에 이미 재사용된 실적, FR-C-10)를 **변경 없이** 그대로 5장 배치한다. 새 props를 추가하지 않는다.

### 2.4 기간·단위 컨트롤 — `GranularityPeriodControl`(신규, `PeriodSelector`와 별개)

기존 `PeriodSelector`(`TODAY`/`7D`/`30D`/`CUSTOM`)는 대시보드 전용으로 유지하고 **재사용하지 않는다** — No.14는 프리셋이 아니라 `granularity`(일/주/월) 축과 `from`/`to` 축이 별개로 움직이기 때문이다(단위를 바꾸면 서버 기본 기간이 자동 전환된다, FR-4·F-4).

| 컴포넌트 | props | 규칙 |
|---|---|---|
| `GranularityPeriodControl` | `{ granularity: 'DAY'\|'WEEK'\|'MONTH', onGranularityChange, from, to, onRangeChange, periodStart, periodEnd, rangeDefaulted }` | ① 라디오그룹 3개: "일" / "주" / "월"(기존 `PeriodSelector`의 `fieldset`+`radiogroup` 패턴 재사용, UIUX §6 단일선택=라디오) ② 커스텀 기간 `DateRangeField`(공용 컴포넌트 재사용) — 단위 변경 시 **입력값을 지우지 않고 유지**하되, 서버가 반환한 `periodStart`/`periodEnd`를 결과 요약 텍스트로 병기해 "실제로 무엇을 보고 있는지"를 항상 드러낸다(F-4) ③ `rangeDefaulted`(사용자가 기간을 지정하지 않아 서버 기본값이 적용됐는지)가 true면 "(기간을 지정하지 않아 최근 30일로 조회되었습니다)" 같은 안내를 병기(`security-audit-ui-spec.md`의 `AuditLogFilterBar` 패턴과 동일 철학) |

단위 전환 시 동작: "일" → "주" 전환 시 `from`/`to` 입력을 **즉시 리셋하지 않는다.** 사용자가 명시적으로 커스텀 기간을 입력하지 않은 상태(=처음 진입, 또는 프리셋 유지 중)라면 서버가 그 단위의 기본 기간(일 30/주 12/월 12)을 적용하고 응답의 `periodStart`/`periodEnd`로 화면이 갱신된다. 사용자가 커스텀 `from`/`to`를 입력해 둔 상태에서 단위만 바꾸면 그 값 그대로 재조회하고, 상한 초과 시 `STATS_RANGE_TOO_WIDE` 오류를 인라인으로 보여준다(§3.5).

### 2.5 차트 접근성 공용 패턴 — `ChartFrame`

`NFR-A1`/`NFR-A2`/`FR-C-3`/`FR-C-4`를 모든 차트가 동일하게 충족하도록 **차트를 감싸는 공용 셸**을 만든다. 개별 차트(§3.3~3.6)는 이 셸 안에 시각화 본문만 꽂는다.

| 컴포넌트 | props | 규칙 |
|---|---|---|
| `ChartFrame` | `{ title, summary: string, view: 'chart'\|'table', onViewChange, chart: ReactNode, table: ReactNode }` | ① 제목(`<h3>`) ② **표 보기 토글 버튼**("표로 보기"/"차트로 보기", `aria-pressed`) — 클릭 시 `chart` 대신 `table`을 렌더(둘 다 마운트해두고 `hidden` 속성으로 토글하는 방식은 스크린리더가 숨겨진 콘텐츠까지 읽을 위험이 있어 **조건부 렌더링**을 쓴다) ③ `summary` 한 줄 요약 문장을 **항상 시각적으로도 노출**(캡션 텍스트, `aria-live` 아님 — 최초 렌더 시 1회성 정보이므로 `polite` 라이브領域 불필요)하고, 차트 컨테이너 자체에도 `role="img" aria-label={summary}`를 부여해 스크린리더가 차트 요소 진입 시 같은 문장을 듣게 한다(NFR-A2) ④ 차트 SVG 내부의 개별 도형에는 `aria-hidden="true"`(중복 낭독 방지 — 요약 문장과 표가 이미 상세 정보를 제공) |

`summary` 생성 규칙(프런트 전용 텍스트 조립, 새 지표 계산 아님 — F-1 위반 아님): 서버가 내려준 배열의 **첫 유효 버킷값과 마지막 유효 버킷값을 비교**해 "최근 {N}일간 {지표명}은 {A}에서 {B}로 {상승/하락/유지}했습니다" 형태로 조립한다. 버킷이 1개뿐이면 "선택한 기간의 {지표명}은 {A}입니다"로 대체한다. 이 조립 로직은 **표시 문구 생성**이며 새로운 집계값을 만들지 않으므로 NFR-M2("서버 값을 표시만 한다")를 위반하지 않는다.

미응답 질문을 검토해 의도 예문으로 반영하거나 무시한다(S-5~S-12). ROCHA 원본의 "재학습 절차"(`로차_간단학습매뉴얼.pdf` p.4)가 요구하는 **① 미응답 리스트 확인 ② 학습상태 변경**(반영/무시) 두 요소를 그대로 구현한다.

### 4.2 원본 매뉴얼 대조 메모 (PM 요청 항목 7)

이 환경에서는 `ROCHA_매뉴얼_23.07.07.pdf`의 p.59~62(학습현황 화면 자체)를 **여전히 직접 렌더할 수 없었다**(`pdftoppm`/poppler-utils 미설치 — requirements-analyst가 보고한 조사 한계가 이 단계에서도 동일하게 재현됨, §1.4 원본 인용 참고). 대신 같은 PDF의 **다른 화면들(의도관리 p.21, 키워드관리 p.23)을 전문 렌더**해 ROCHA의 "목록형 관리 화면" 공통 관용구를 확인했고, 아래 설계에 반영했다:

- **목록 컬럼 패턴**: `순번 / 이름 / 요약(예문) / 개수 / 관리`(의도관리 p.21) — 학습현황에서는 이를 `질문(마스킹된 원문) / 발생 횟수 / 최초·최근 발생 / 상태 / 추천 의도 / 액션`(FR-15-12)으로 그대로 대응시켰다.
- **일괄 액션 버튼 위치**: 의도관리·키워드관리 모두 목록 **상단 우측**에 `추가/학습/다운로드/업로드` 등 전역 액션을 배치하고, 개별 행 우측에 `수정` 액션을 둔다. 학습현황도 동일하게 **상단에 필터+정렬, 선택 시 나타나는 일괄 액션 바, 행 우측에 개별 액션**을 배치한다(§4.4).
- **검색 상단 고정**: 의도관리 p.21은 검색창을 목록 최상단에 고정한다 — 학습현황의 `q`(질문 부분일치) 필터도 같은 위치(필터바 좌측 첫 항목)에 둔다.
- **"학습" 버튼의 대응물**: ROCHA는 의도 저장 후 별도 `의도 학습` 버튼을 눌러야 반영되지만(p.21 ④, DLE 전제), 우리 시스템은 J-1 결정에 따라 **저장 즉시 반영**이라 이 버튼 자체가 존재하지 않는다 — `반영` 버튼 하나가 "저장+학습"을 겸한다(§4.5).
- 재학습 절차 플로차트(p.4)의 "미응답 리스트 확인 → 학습상태 변경" 두 단계는 이 화면에서 "목록 조회 → 반영/무시(상태 변경)"으로 정확히 대응한다. 페이지 59~62의 세부 필드(정확한 컬럼 순서·버튼 라벨 등)는 확인하지 못했으므로, **이 설계는 FR-15-9~38의 요구사항 텍스트와 위 교차 확인만으로 구성**했다는 한계를 명시한다. 실 구현 중 원본과의 세부 차이가 문제 되면 `bug-triage` 단계에서 보정한다.

### 4.6 일괄 처리 (`BulkResolveModal`, FR-C-9, S-11)

1. 체크박스 1건 이상 선택 → `BulkActionBar` 노출.
2. `[일괄 반영]` 클릭 → `BulkResolveModal` 오픈: 선택된 질문 미리보기(최대 5개 텍스트 + "외 {N}건"), **단일 의도 대상 선택 필드**(`IntentTargetField` 재사용 — 선택된 모든 항목에 **동일한 의도**를 적용, 매뉴얼 원문의 "일괄 학습" 용례(S-11)와 일치). 항목별로 다른 의도를 지정하는 세분화 UI는 이번 phase 범위 밖으로 명시(§9) — 다른 의도로 보내고 싶은 항목은 선택에서 제외하고 개별 반영한다.
3. 확인 → `POST .../bulk-resolve`(모든 선택 항목에 같은 `intentId`/`intentName` 적용) → `BulkResultPanel` 렌더:
   - "성공 {succeeded}건 / 실패 {failed.length}건"
   - 실패 목록은 **사유를 포함해 테이블로** 표시: `질문 요약 | 사유`(예: "예문 상한 초과", "이미 처리됨") — 토스트로 끝내지 않는다(FR-C-9).
   - `linkedNodeCount===0`인 성공 건은 `NodeUnlinkedWarningBanner`에 각각 추가된다.
4. `[일괄 무시]`는 `BulkIgnoreConfirmDialog`(위 표) → `POST .../bulk-ignore` → 동일하게 `BulkResultPanel`(무시는 상태 전이 실패만 있을 수 있음 — 예: 이미 `RESOLVED`인 항목 재무시 시도).
5. 51건 이상 선택 시 `[일괄 반영]`/`[일괄 무시]` 버튼은 **비활성화 + 안내**("한 번에 최대 50건까지 처리할 수 있습니다. {N}건 선택됨") — 서버 `400 BULK_SIZE_EXCEEDED`에 도달하기 전에 프런트가 먼저 막아 불필요한 실패 왕복을 줄인다(사전 유효성 검사, UIUX §7).

### 4.7 노드 미연결 경고 — 배치와 지속성 (FR-C-8, NFR-A8)

- **즉시 알림**: 반영(단건/일괄) 응답에 `linkedNodeCount === 0`이 포함되면, 결과를 `NodeUnlinkedWarningBanner`(페이지 상단, 필터바보다 위)에 **추가**한다. 배너는 이 화면에 머무는 동안 유지되며, 항목별 `[닫기]` 또는 전체 `[모두 닫기]`로만 사라진다(자동 소멸 없음 — 토스트와의 핵심 차이).
- 배너의 각 항목은 "원인 + 해결 방법"을 함께 담는다(UIUX §7): "'{questionText}' → 의도 '{intentName}'에 반영했지만, 이 의도를 사용하는 대화 노드가 없어 여전히 답변되지 않습니다. [노드 만들기 →]".
- `[노드 만들기 →]` 링크는 `/chatbots/:id/dialogue/nodes?focusIntentId=<intentId>` 로 이동한다. **주의**: `focusIntentId` 쿼리를 받아 입력조건에 해당 의도를 사전 채우는 기능은 `대화설계` 그룹(No.5~9, 이미 구현됨)의 `NodesListPage`/`NodeFormPage` 쪽 지원 여부를 `frontend-implementer`가 먼저 확인해야 한다. 지원하지 않으면 **이번 Phase는 단순 이동만** 제공하고(사전 채움 없음), 배너 문구에서 "[노드 만들기 →]" 대신 "노드 만들기 화면으로 이동 →"로 톤을 낮춘다 — 과도한 기대를 주지 않기 위함이다.
- **영속성 한계(설계상 알려진 갭, §9)**: 이 경고는 반영 API 응답에서만 얻을 수 있는 정보다. 목록/상세 조회 API(`UnansweredQuestionListItemSchema`/`DetailSchema`)에는 `linkedNodeCount`가 없으므로, **페이지를 새로고침하거나 다시 방문하면 경고가 사라진다.** 이는 이번 설계의 알려진 한계이며 §9에서 backend-implementer에게 개선을 권고(필수 아님)로 남긴다.

### 4.8 반영 완료 문구 — `appliedImmediately` 분기 (F-10, J-1)

**"학습 중"이라는 표현을 어디에도 쓰지 않는다.** 문구는 하드코딩된 `true` 전제가 아니라 응답값을 그대로 분기한다:

```
if (response.appliedImmediately === true) {
  toast("반영 완료 — 다음 대화부터 적용됩니다.")
} else {
  // 현재 API 계약상 도달하지 않는 분기(DD-55 현재 구현은 항상 true)이지만,
  // No.16/23 도입 시 LearningApplyService.applyLearning()의 반환값만 바뀌고
  // 이 분기가 자동으로 활성화되도록 지금부터 조건부로 작성한다(K-4).
  toast("학습 대기열에 추가되었습니다. 처리가 완료되면 자동으로 적용됩니다.")
}
```

이 두 문자열 모두 `MESSAGES.learning.resolveSuccessImmediate` / `MESSAGES.learning.resolveSuccessQueued` 상수로 등록하고, **어떤 컴포넌트도 `"반영 완료"`를 리터럴로 쓰지 않는다**(코드리뷰 포인트로 §10에 재기재).

### 4.9 상태별 UI 총괄

| 상태 | UI |
|---|---|
| 로딩 | `SkeletonRow` × pageSize |
| 성공(데이터 있음) | 표 + "총 {total}건" |
| **빈 상태 ②** — 역대 미응답 질문 자체가 0건(진짜 무기록) | `EmptyState`: **"검토할 미응답 질문이 없습니다 — 좋은 신호입니다."**(중립/긍정 색, 오류 아님 — FR-C-12) + 설명 "챗봇이 모든 질문에 답하고 있거나, 아직 충분한 대화가 쌓이지 않았습니다." |
| **빈 상태 ③** — 기본 필터(`PENDING`)만 0건이고 과거 처리 이력은 있음("전부 처리 완료") | `EmptyState`: "대기 중인 미응답 질문이 없습니다. 모두 처리되었습니다." + 액션 "처리된 항목 보기"(필터를 `RESOLVED`+`IGNORED`로 전환) |
| 필터 결과 0건(위 두 경우가 아닌 일반 빈 결과, 예: 검색어와 일치하는 것이 없음) | `EmptyState`: "조건에 맞는 미응답 질문이 없습니다." + "필터 초기화" |
| 오류 | `ErrorState` + 다시 시도 |

**②/③ 판별 방법**: 기본 조회(`status=PENDING`)가 `total: 0`을 반환하면, 프런트가 **1회 추가로** `GET .../unanswered-questions?status=PENDING,RESOLVED,IGNORED&page=1&pageSize=1`을 호출해 전체 `total`을 확인한다(새 API 아님 — 기존 목록 엔드포인트의 필터 파라미터 조합). 전체 `total === 0`이면 ②, `> 0`이면 ③. 이 추가 호출은 **빈 상태일 때만** 발생하므로 정상 트래픽 비용에 영향이 없다.

## 9. 다음 단계(backend-implementer) 참고사항 — API 계약 갭 1건

이 문서는 API를 재설계하지 않지만, 화면을 설계하는 과정에서 **UI 요구사항과 현재 스키마 사이의 갭 1건**을 발견했다. 필수 변경이 아니라 **권고**로만 남긴다(최종 판단은 `backend-implementer`/`system-architect`).

| 갭 | 현재 상태 | 영향 | 권고(선택) |
|---|---|---|---|
| `linkedNodeCount`(노드 미연결 여부)의 비영속성 | `ResolveResultSchema`에만 존재하고 `UnansweredQuestionListItemSchema`/`DetailSchema`에는 없다 | §4.7의 경고 배너가 **페이지 새로고침·재방문 시 사라진다.** 사용자가 이 화면을 벗어났다가 나중에 돌아오면 "아직 처리 안 된 문제"를 잊을 수 있다 | `DetailSchema` 조회 시 `resolvedIntentId`가 있으면 그 의도의 `linkedNodeCount`를 **함께 재계산해 반환**하는 방안을 검토해달라. `IntentsService.applyLearningExample()`이 이미 `dialogNodeIntent`를 조회하므로(DD-62 규약 4, ADR-0005 역참조 재사용) 상세 조회 시에도 같은 카운트 쿼리 1회 추가로 해결 가능해 보인다(추가 N+1 아님 — 상세는 단건 조회이므로). 도입하지 않아도 §4.7의 세션 스코프 배너로 기능은 성립한다 |

이 항목은 **필수 차단 사항이 아니다** — `frontend-implementer`는 이 갭이 해결되지 않은 채로도 §4.7의 세션 스코프 배너 설계로 구현을 진행할 수 있다.

## 11. `frontend-implementer` 인계 메모

1. **구현 순서 권고**:
   ① `TabNav`에 `통계` 링크 추가 + `App.tsx`에 `/stats` 라우트·`StatsShell` 골격(리다이렉트만, 화면 내용 없이) — 이것부터 해야 나머지가 라우팅될 수 있다.
   ② `ChartFrame`(§2.5) — 이후 모든 차트가 이 위에서 만들어지므로 가장 먼저 완성한다.
   ③ S1(`StatsOverviewPage`) — 읽기 전용이라 L1보다 단순하다.
   ④ L1 목록·필터·펼침 상세(쓰기 액션 제외) → ⑤ `ResolveModal`(단건 반영) → ⑥ 일괄 처리 → ⑦ `NodeUnlinkedWarningBanner`/빈 상태 3종/배지.
2. **의존 스키마**: `stats.ts`의 `StatsSummarySchema`/`StatsDistributionSchema`/`StatsQuestionsSchema`/`StatsGranularity`/`RESPONSE_SOURCE_LABELS`/`STATS_LIMITS`, `learning.ts`의 `UnansweredQuestionListItemSchema`/`DetailSchema`/`SummarySchema`/`IntentSuggestionSchema`/`ResolveUnansweredQuestionSchema`/`ResolveResultSchema`/`BulkResolveSchema`/`BulkResultSchema`/`UNANSWERED_STATUS_LABELS`/`LEARNING_LIMITS` — 이 문서의 데이터 바인딩은 전부 이 스키마들이 `backend-implementer` 산출물로 존재한다는 전제다.
3. **차트 라이브러리 권고(FR-C-11) — 최종 결정은 `system-architect` 재확인 사항**:
   - **권고: 신규 의존성 없이 SVG 직접 구현.** 근거: ① 이 그룹이 필요로 하는 차트는 형태가 단순하다(막대/누적막대 6종, 파이·도넛·복잡한 인터랙션 없음) ② 데이터 카디널리티가 작다(버킷 최대 24개월/92일, 시간대 24개, 요일 7개, 분포 4개 — 대규모 렌더링 최적화가 불필요) ③ `apps/web`은 현재 런타임 의존성이 `react`/`react-dom`/`react-router-dom` 3개뿐이라(§0-2), 이 그룹만을 위해 recharts/chart.js급 라이브러리(gzip 수십 KB)를 들이는 것은 설계서 §1의 "신규 런타임 의존성 0건" 기본 원칙과 어긋난다 ④ `ChartFrame`이 요구하는 접근성 계약(`role="img"`, 세그먼트 `aria-hidden`, 표 폴백)은 SVG를 직접 그릴 때 **완전히 통제 가능**하지만, 서드파티 차트 라이브러리는 캔버스 렌더링(스크린리더가 원천적으로 접근 불가) 또는 라이브러리 자체 접근성 지원 수준에 의존해야 해 NFR-A1/A2 충족을 검증하기 더 어렵다.
   - **대안(권고하지 않음, 기록만)**: 차트 종류가 늘거나(예: No.29 통합 통계에서 다축 비교) SVG 직접 구현 공수가 예상보다 커지면, 경량 라이브러리(예: 번들 수 KB대의 캔버스리스 SVG 기반 옵션) 재검토를 후속 Phase로 미룬다.
   - **이 문서가 확정하지 않는 것**: 실제 도입 여부는 설계서 §12 F-C-11이 명시한 대로 `system-architect` 확인이 필요한 사항이다. `frontend-implementer`는 SVG 직접 구현으로 우선 착수하되, 착수 전 이 권고를 `system-architect`에게 1회 재확인받는 것을 권장한다.
4. **상수 파일**: 이 문서의 모든 한국어 문구는 `MESSAGES.detail.tabStats`/`MESSAGES.statsShell`/`MESSAGES.stats`/`MESSAGES.learning` 네임스페이스로 옮긴다(FR-C-13). **"반영 완료"/"학습 대기열에 추가됨" 두 문구는 `appliedImmediately` 분기 전용 상수이며, 어떤 컴포넌트도 이 문자열을 조건 없이 하드코딩하지 않도록 코드리뷰 포인트로 남긴다**(§4.8, F-10, K-4).
5. **미결정/후속 확인 필요**
   - §4.7의 `focusIntentId` 쿼리 파라미터가 기존 `NodesListPage`에 이미 지원되는지 확인 필요(지원 안 되면 단순 이동으로 축소, 문구도 함께 조정).
   - §9의 `linkedNodeCount` 영속화는 선택 사항이며, 이번 Phase는 세션 스코프 배너로 완결된다.
   - `StatsTrendChart`의 metric 탭 개수(총 턴/응답/미응답/차단/응답률 5개)가 좁은 화면에서 과밀하면 셀렉트 드롭다운으로 축소하는 것을 허용한다(반응형 세부는 §10 원칙 안에서 `frontend-implementer` 재량).
   - `BulkResolveModal`의 "동일 의도만 지원" 제약(§4.6)은 PM 확인 후 필요 시 항목별 의도 지정 UI로 확장 가능(현재 API 스키마는 이미 항목별 `intentId`/`intentName`을 허용하므로 백엔드 변경 없이 프런트 UI만 확장하면 된다).
