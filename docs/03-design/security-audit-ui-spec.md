## 0. 전제와 연계 확인

1. **아키텍처 제약 F-1~F-12(설계서 §12)를 그대로 받아들인다.** 이 문서는 그 제약을 뒤집지 않고, 제약이 열어둔 화면 구성만 판단한다. 특히:
   - F-1: `/login`은 `TopBar`·`UnsavedGuardProvider` **바깥**의 독립 레이아웃.
   - F-2: 부팅 시 `GET /auth/me` 1회, 응답 전에는 라우트를 렌더하지 않는다(깜빡임 방지).
   - F-4: 쓰기 액션은 권한이 없으면 **숨김**(비활성 아님). 페이지 단위 거부는 **403 안내 화면**.
   - F-6: 401 발생 시 **화면 전환 없이** 재로그인 모달, 재인증 성공 시 원 요청 재시도.
   - F-8: `mustChangePassword=true`면 다른 라우트로 이동 불가.
2. **현재 코드 상태 확인 결과**(이 문서의 전제):
   - `apps/web/src/App.tsx`: 라우트 8개 그룹, `/login` **없음**. 챗봇 상세는 `dashboard/settings/skin/simulator/channels/dialogue` **6개 탭**이 이미 존재하고, `TabNav.tsx`가 이를 "운영/설계/검증/배포" **4개 시각적 그룹**으로 묶어 표시 중이다(`quality-channel-ui-spec.md` §2 결정 계승).
   - `apps/web/src/components/TopBar.tsx`: 브랜드 링크 + "챗봇 목록" 링크 **2개뿐**. 사용자 메뉴·역할 표시·로그아웃 진입점 **없음**.
   - `apps/web/src/api/client.ts`: `handleResponse()`의 401 분기가 **주석만 있는 빈 블록**(F-6 대상).
   - 공용 컴포넌트 `Modal`/`ConfirmDialog`(`Modal.tsx`)/`Toast`/`Pagination`/`EmptyState`/`ErrorState`/`SeverityBadge`/`StatusBadge`/`InlineFieldError`/`CopyButton`/`ResourcePickerField`/`FileUploadField` 전부 **이미 존재**하며 이번 화면들이 재사용한다(FR-U-11).
3. **이 문서가 다루지 않는 것**
   - `apps/widget`: 수정 0줄(F-12). 언급하지 않는다.
   - `SIM1`(응답 테스트) 화면 자체의 재설계: **캡션 1줄 추가만** 지시한다(§6.1). 화면 구조는 `quality-channel-ui-spec.md` §4.1을 그대로 따른다.
   - 관리자 콘솔 입력(FAQ·의도 예문 등)에 대한 금지어 검열 UI: J-3 결정에 따라 **존재하지 않는다**.
4. **문구 상수**: 신규 네임스페이스 `MESSAGES.auth.*`, `MESSAGES.users.*`, `MESSAGES.bannedWords.*`, `MESSAGES.auditLogs.*`를 `apps/web/src/constants/messages.ts`에 추가한다(FR-U-12). 이 문서의 모든 따옴표 문구는 그 값의 초안이다. 서버가 내려주는 오류 `message`는 원칙대로 그대로 표시하되, **로그인 실패 문구만 예외**로 서버 값을 쓰지 않고 클라이언트 고정 문구를 쓴다(§3.2.3 근거 — 계정 열거 방지가 표시 계층에서도 이중으로 지켜지게 한다).
5. **판단 요약(선반영)**: 챗봇 상세에 **7번째 탭을 추가하지 않는다**(§4.3). 이력 접근은 ① TopBar "시스템 설정" 전역 메뉴 ② 챗봇 상세 헤더의 소형 링크, 두 경로로 충분하다. 근거는 §4.3에 상술한다.

## 2. 공통 UI 요소(신규)

기존 `chatbot-operations`/`dialogue-design`/`quality-channel` 3개 그룹이 만든 공용 컴포넌트(`Modal`, `ConfirmDialog`, `Toast`, `Pagination`, `EmptyState`, `ErrorState`, `SeverityBadge`, `StatusBadge`, `InlineFieldError`, `CopyButton`, `Skeleton*`, `ResourcePickerField`)는 **변경 없이 재사용**한다(FR-U-11). 아래는 이번 그룹이 새로 정의하는 컴포넌트다.

### 2.1 배지류 (색상+텍스트 병기, UIUX §1)

| 컴포넌트 | props | 표시 규칙 |
|---|---|---|
| `RoleBadge` | `{ role: RoleName }` | `ROLE_LABELS`(shared-types) 값을 그대로 표시 — **문자열을 컴포넌트가 재정의하지 않는다**(F-3). ADMIN "시스템 관리자"(보라 계열, 대비 4.5:1↑) / EDITOR "챗봇 편집자"(파랑) / VIEWER "운영 모니터"(회색) + 각각 아이콘 |

## 3. 화면별 설계

## 3.1 L0 — 인증 부팅 게이트(`AuthGate`)

### 목적
앱이 열릴 때 인증 상태를 **한 번** 확인하고, 그 결과에 따라 로그인/강제 비밀번호변경/정상 화면 중 정확히 하나만 렌더한다. 라우트가 아니라 `App.tsx` 최상단 로직이다.

### 상태 전이

```
[앱 로드]
   │
   ▼
GET /auth/me  ── (진행 중) ──▶  전체 화면 스피너 "불러오는 중…" (F-2, 라우트 렌더 보류)
   │
   ├─ 401 ─────────────────────▶ 미인증: <Routes>는 "/login"만 유효, 그 외 경로는
   │                              /login?returnTo=<현재 경로 encode> 로 리다이렉트(F-2, AC-U-1)
   │
   ├─ 200, mustChangePassword=true ─▶ L2(최초 비밀번호 변경) 전체 화면 렌더.
   │                                  주소창 경로와 무관하게 항상 L2만 보인다(F-8, EX-12-9).
   │                                  예외: `/auth/logout` 트리거(§2.2)만 허용
   │
   └─ 200, mustChangePassword=false ─▶ 정상 앱: TopBar + UnsavedGuardProvider + <Routes>
                                        (returnTo가 있었다면 그 경로로, 없으면 '/')
```

- **재조회 시점**: 로그인 성공 직후, 비밀번호 변경 성공 직후, 로그아웃 직후, 브라우저 새로고침 시. 그 외에는 `AuthContext`가 로그인 응답/`/auth/me` 응답을 메모리에 유지한다(요청마다 재조회하지 않음).
- `AuthContext`가 노출하는 값: `status: 'loading'|'unauthenticated'|'password-change-required'|'ready'`, `user: CurrentUser|null`, `can(permission: Permission): boolean`, `login()`, `logout()`, `refreshMe()`. 컴포넌트는 **역할 문자열을 직접 비교하지 않는다**(F-3) — 전부 `can(permission)`을 통한다.

## 3.2 L1 — 로그인 화면 (`/login`)

### 목적
이메일+비밀번호로 인증하고 세션 쿠키를 발급받는다. `TopBar`·`UnsavedGuardProvider` 바깥의 완전히 독립된 레이아웃이다(F-1).

### 레이아웃 (데스크톱, ASCII)

```
┌───────────────────────────────────────────────────────────────┐
│                                                                 │
│                     Chat Bot 관리자 콘솔                        │
│                                                                 │
│              ┌───────────────────────────────┐                 │
│              │  로그인                          │                │
│              │                                 │                │
│              │  이메일 *                        │                │
│              │  [_____________________________]│                │
│              │                                 │                │
│              │  비밀번호 *          [표시]       │                │
│              │  [_____________________________]│                │
│              │                                 │                │
│              │  ⓘ 이메일 또는 비밀번호가          │  ← 실패 시만    │
│              │     올바르지 않습니다.             │                │
│              │                                 │                │
│              │        [        로그인        ]  │                │
│              └───────────────────────────────┘                 │
│                                                                 │
└───────────────────────────────────────────────────────────────┘
```

### 상태별 UI

| 상태 | UI |
|---|---|
| 초기 | 이메일 필드에 자동 포커스(첫 Tab 대상) |
| 제출 중 | "로그인" 버튼 `disabled` + 스피너, 중복 클릭/중복 제출 방지(UIUX §4) |
| 성공 | 즉시 `returnTo` 또는 `/`로 이동. 화면 전환 자체가 피드백이라 별도 토스트 없음 |
| 실패(`400 VALIDATION_FAILED`) | 필드별 인라인 오류("이메일 형식이 올바르지 않습니다." 등), 첫 오류 필드로 포커스 이동(NFR-A2) |
| 실패(`401 INVALID_CREDENTIALS`) | 폼 상단 `aria-live="assertive"` 배너: **"이메일 또는 비밀번호가 올바르지 않습니다."**(고정 문구 — 서버 `message`를 그대로 쓰지 않고 클라이언트 상수를 쓴다, §0-4) |
| 실패(`401 ACCOUNT_LOCKED`) | 동일 배너 자리, 문구만 교체: **"로그인 시도가 너무 많습니다. {lockedMinutes}분 후 다시 시도해 주세요."**(S-3). `lockedMinutes`는 서버 응답에서 계산(잠금 해제 시각 − 현재 시각) |
| 실패(`429 RATE_LIMITED`) | "요청이 많습니다. 잠시 후 다시 시도해 주세요." + 가능하면 `Retry-After` 반영 |
| 실패(네트워크/5xx) | 공통 오류 배너 + "다시 시도" |

### 컴포넌트 분해

| 컴포넌트 | props / 데이터 바인딩 |
|---|---|
| `LoginPage` | 독립 레이아웃 루트. `returnTo` 쿼리 파싱(없으면 `/`) |
| `LoginForm` | `email`, `password`, `PasswordField` 재사용, `onSubmit` |
| 오류 배너 | `role="alert"`, `aria-live="assertive"`(NFR-A2) |

### 인터랙션 흐름
1. 이메일·비밀번호 입력(Tab 순차 이동, Enter로 제출 가능 — UIUX §3).
2. 제출 → `POST /auth/login` → 로딩 상태.
3. 200 → `AuthContext.user` 갱신 → L0가 `mustChangePassword`를 보고 L2 또는 정상 앱으로 분기.
4. 실패 → 위 표에 따라 인라인/배너 오류, 비밀번호 필드는 **비워지지 않는다**(재시도 편의, 단 값 자체를 다시 채우지는 않고 사용자가 고쳐 입력).

## 3.4 L3 — 세션 만료 재로그인 모달

### 목적
S-6/AC-U-4의 핵심 요구: **작성 중이던 폼 데이터가 사라지지 않는다.** 화면 전환·라우트 이동이 전혀 일어나지 않고, 모달만 뜨고 닫힌다.

### 계약 (구현자 인계용)

- `apps/web/src/api/client.ts`의 `handleResponse()`가 `401`(`SESSION_EXPIRED`/`UNAUTHENTICATED`)을 감지하면(단, 요청 경로가 `/auth/*`가 아닐 때) **요청을 즉시 실패시키지 않고** `AuthContext`가 등록한 전역 핸들러를 호출해 모달을 띄운다.
- 핸들러는 `Promise<boolean>`을 반환한다: 사용자가 재로그인에 성공하면 `true`(원 요청을 **자동으로 1회 재시도**하고 그 결과를 호출자에게 돌려준다), 취소하면 `false`(원 요청은 원래의 `401` `ApiError`로 실패하며 호출한 화면의 기존 오류 처리 경로를 그대로 탄다).
- **화면 컴포넌트는 이 로직을 알 필요가 없다** — `apiClient.patch(...)`를 호출한 곳은 그 호출이 "한 번에 성공"했는지 "재로그인 한 번 거쳐 성공"했는지 구분하지 않아도 된다. 이것이 F-6("화면 전환 없이", "재시도 가능")을 만족하는 유일한 방법이다 — 화면별로 재시도 로직을 각자 구현하면 40여 개 폼마다 빠뜨리는 곳이 생긴다.
- 동시에 여러 요청이 401을 받아도 모달은 **하나만** 뜬다(이미 열려 있으면 새 요청은 같은 모달의 결과를 공유).

### 레이아웃 (모달, 현재 화면 위 오버레이)

```
┌─────────────────────────────────────────────┐
│  로그인이 만료되었습니다                    ✕ │
│  다시 로그인하면 작성 중인 내용을 그대로       │
│  이어서 진행할 수 있습니다.                    │
│                                               │
│  이메일         kim@example.com (읽기 전용)   │
│  비밀번호 *      [_______________] [표시]     │
│                                               │
│  ⓘ 비밀번호가 올바르지 않습니다.  ← 실패 시만  │
│                                               │
│              [ 취소 ]   [ 다시 로그인 ]       │
└─────────────────────────────────────────────┘
```

### 규칙

- 배경의 폼/입력값은 **어떤 경우에도 리렌더·초기화되지 않는다.** 모달은 완전히 독립된 오버레이 레이어다.
- 포커스 트랩 + `Esc`로 "취소"와 동일 동작(NFR-A5). `Esc`/배경 클릭으로 닫아도 **배경 화면은 그대로**이며, 사용자가 나중에 같은 저장 버튼을 다시 누르면 같은 흐름이 반복된다.
- 성공(`200`) → 모달만 닫힘 + 원 요청 자동 재시도(트리거한 화면이 자신의 성공/실패 처리를 그대로 수행 — 예: 저장 성공 토스트).
- 이메일은 **직전 세션의 사용자 이메일**을 읽기 전용으로 표시해, 다른 계정으로 실수로 로그인하는 것을 방지한다(EX-12-*와 무관하게 UX 안전장치).
- 세션이 만료된 것이 아니라 **계정이 비활성화**된 경우(`ACCOUNT_DISABLED`)에도 이 모달이 뜨지만, 재로그인 시도는 다시 `401 INVALID_CREDENTIALS`(C-1 — 로그인 경로는 항상 동일 문구)로 실패한다. 이 경우 문구는 일반 로그인 실패와 **동일**하게 표시한다(계정 열거 방지 원칙을 재로그인 경로에서도 지킨다). 여러 번 실패가 이어지면 모달 하단에 "계정 상태를 관리자에게 문의해 주세요."라는 **부가** 안내를 추가해도 되나(선택), 오류 코드 자체를 노출하지 않는다.

## 3.5 L4 — 403 접근 거부 안내

### 목적
권한이 없는 사용자가 주소창으로 보호 경로에 직접 진입했을 때, **빈 화면이나 무한 로딩이 아니라** 명확한 안내를 준다(FR-U-5, AC-U-6).

### 배치 방식

라우트 자체를 `/403`으로 리다이렉트하지 **않는다** — 주소창은 사용자가 시도한 경로(`/settings/users` 등)를 그대로 유지한 채, 그 라우트의 콘텐츠 자리에 `ForbiddenState`가 대신 렌더된다. 구현은 라우트를 감싸는 가드 요소 패턴을 쓴다:

```
<Route path="/settings/users" element={
  <RequirePermission permission="user:read" fallback={<ForbiddenState />}>
    <UsersPage />
  </RequirePermission>
} />
```

`RequirePermission`은 `can(permission)`이 `false`면 `children` 대신 `fallback`을 렌더한다(F-4의 "페이지 단위 거부는 안내 화면" 조항).

### 레이아웃

```
┌───────────────────────────────────────────────────────────────┐
│                                                                 │
│                      🔒                                        │
│           이 페이지에 접근할 권한이 없습니다                     │
│                                                                 │
│   현재 역할("운영 모니터")로는 회원 관리 메뉴를 사용할 수        │
│   없습니다. 필요하다면 시스템 관리자에게 문의해 주세요.          │
│                                                                 │
│                    [  홈으로 돌아가기  ]                        │
│                                                                 │
└───────────────────────────────────────────────────────────────┘
```

- "다시 시도" 버튼은 넣지 않는다(재시도로 해결되는 상태가 아니다 — `ErrorState`와의 의도적 차이).
- 역할 이름은 `RoleBadge`와 동일한 `ROLE_LABELS`를 사용해 일관성을 유지한다.
- 키보드 포커스는 화면 진입 시 제목(`<h1 tabIndex={-1}>`)으로 이동해 스크린리더가 즉시 상황을 읽게 한다(NFR-A5 취지 확장).

1. "로그아웃" 클릭 → `POST /auth/logout`.
2. 응답과 무관하게(멱등, FR-12-8) `AuthContext.user = null` 설정 → `navigate('/login', { replace: true })`.

### 메뉴 노출 규칙(핵심)
- **"시스템 설정" 메뉴는 숨김 원칙을 따른다**(F-4) — VIEWER/EDITOR는 통째로 보이지 않는다(현재 매핑상 셋 다 ADMIN 전용). 비활성 처리가 아니라 **렌더 자체를 하지 않는다**.
- 역할 배지는 항상 노출(정보 표시이지 권한 게이트가 아니므로 숨김 대상 아님).

- **본인 행에는 액션 메뉴(⋮) 자체가 없다** — 위 예시의 "김관리"(로그인 중인 본인)가 그 경우다. 자기수정은 서버가 `409 SELF_MODIFICATION`으로 최종 차단하지만(NFR-S6), 화면에서 선택지 자체를 없애 혼동을 줄인다(FR-U-4 원칙의 확장 적용 — "사용자가 스스로 해소할 수 없는 조작은 노출하지 않는다"). **역할 변경(마지막 ADMIN 보호, `409 LAST_ADMIN`)은 클라이언트가 미리 계산하지 않고 서버 응답에 맡긴다** — 목록이 페이지네이션되어 있어 "ACTIVE ADMIN이 몇 명인지"를 클라이언트가 항상 정확히 알 수 없기 때문이다(§3.7.3 참고).

### 3.7.1 회원 등록 흐름 (S-7, AC-12C-1)

1. "+ 회원 추가" → `CreateUserModal` 오픈, 이메일에 포커스.
2. 입력 → 제출(`POST /users`).
3. `201` → 모달 내용이 **같은 모달 안에서** `TemporaryPasswordReveal`로 전환("{name}님이 등록되었습니다. 아래 임시 비밀번호를 전달해 주세요.")
4. "확인했습니다" 클릭 → 모달 닫힘 + 목록 갱신(새 행 하이라이트) + `Toast`("회원이 등록되었습니다").
5. 실패(`409 DUPLICATE_EMAIL`) → 이메일 필드 인라인: "이미 사용 중인 이메일입니다."
6. 실패(`400 VALIDATION_FAILED`) → 필드별 인라인.

### 3.7.2 역할 변경 흐름

1. 행 액션 "역할 변경" → `ChangeRoleModal`.
2. 확인 → `PATCH /users/:id { role }`.
3. `200` → `Toast` + 배지 갱신.
4. **`409 LAST_ADMIN`** → 모달 상단 배너: "마지막 시스템 관리자의 역할은 변경할 수 없습니다. 다른 관리자를 먼저 지정해 주세요." — 모달은 닫히지 않고 사용자가 취소로 종료(S-9).
5. `409 SELF_MODIFICATION`은 본인 행 자체가 노출되지 않으므로 **정상 경로에서는 발생하지 않고**, 다중 탭/경합 상황(예: 다른 탭에서 로그인한 자신이 스스로를 대상 목록에서 찾아 조작 시도)의 방어선으로만 존재 — 발생 시 동일한 배너 패턴으로 안내: "본인 계정은 여기서 변경할 수 없습니다."

### 3.7.3 상태 전환(비활성화/활성화) 흐름 (S-8, S-9)

1. "비활성화" → `ToggleStatusConfirmDialog`(danger, 기본 포커스 "취소") → 확인 → `PATCH /users/:id/status { status: 'DISABLED' }`.
2. `200` → 배지 "비활성"로 갱신, `Toast`("계정이 비활성화되었습니다. 해당 사용자는 즉시 로그아웃됩니다.").
3. `409 LAST_ADMIN` → 다이얼로그 내 배너: "마지막 시스템 관리자는 비활성화할 수 없습니다."
4. "활성화"는 확인 없이 즉시 `PATCH ... { status: 'ACTIVE' }` → `Toast`.

### 3.7.4 임시 비밀번호 재발급 흐름 (S-7 연장, FR-12-29)

1. "임시 비밀번호 재발급" → `PasswordResetConfirmDialog`(danger).
2. 확인 → `POST /users/:id/password-reset` → `200` → `TemporaryPasswordReveal`(§2.2 동일 컴포넌트, "확인했습니다"로만 닫힘).
3. 메일 발송이 없으므로(§9.1 Out of scope) **관리자가 이 화면에서 직접 전달**해야 함을 모달 설명에 한 줄 추가: "이 값을 사용자에게 직접 전달해 주세요(메일은 발송되지 않습니다)."

### 필드-오류 매핑

| field/code | 위치 | 메시지 |
|---|---|---|
| `email` | 이메일 필드 하단 | "이메일 형식이 올바르지 않습니다." / "이미 사용 중인 이메일입니다."(409) |
| `name` | 이름 필드 하단 | "이름을 입력해 주세요." |
| `role` | 역할 셀렉트 하단 | (서버 정의 값 외 입력 불가하므로 사실상 발생하지 않음) |

### 3.9.1 필터/조회 흐름
1. 진입 → 기본 최근 30일 조회. `rangeDefaulted=true`면 안내 병기(FR-13-17, AC-13-9).
2. 필터 변경 → 자동 재조회(값 변경만으로 폼 "제출"이 발생하는 형태이나, UIUX §6의 취지는 셀렉트 값 변경이 "페이지 이동/의도치 않은 폼 제출"을 막는 것이지 필터 재조회 자체를 막는 것이 아니다 — `chatbot-operations-ui-spec.md` §3.1 `SortSelect`와 동일 해석).
3. 챗봇 상세에서 "변경 이력" 링크로 진입한 경우 `chatbotId`가 사전 채워진 채 위 흐름을 그대로 탄다.

### 3.9.2 상세 확장 흐름 (S-13, S-14)
1. 행의 `▸`를 클릭(또는 Enter/Space, 키보드 접근) → 아직 상세를 가져오지 않았다면 `GET /audit-logs/:id` 호출(지연 로딩 — 목록 페이로드에 diff까지 담으면 100만 행 스케일에서 과도해진다).
2. 응답 성격에 따라 3분기 렌더: 일반 변경 → `AuditDiffTable`, 대량 작업 → `AuditBulkSummary`, 인증/권한 이력 → `AuditSessionMeta`(또는 `PERMISSION_DENIED`의 경우 `summary` 텍스트 한 줄만).
3. 다시 `▸`(이제 `▾`) 클릭 → 접힘(재요청 없음, 캐시된 상세 유지).

## 4. 권한별 UI 변화 규칙

### 4.1 원칙 (F-4, FR-U-4)

> **쓰기 액션(저장/삭제/추가/역할변경/상태변경 등)은 권한이 없으면 "비활성화"가 아니라 "렌더 자체를 하지 않는다"(숨김).** 페이지 단위 접근 거부만 예외적으로 **안내 화면**(L4)을 명시적으로 보여준다.

이 원칙은 두 가지를 구분한다:

| 구분 | 예시 | 처리 |
|---|---|---|
| **조건이 갖춰지면 스스로 해소 가능한 상태** | 채널의 "준비 중" 토글(자격증명 미설정) | **비활성 + 사유 안내**(NFR-A3, `quality-channel-ui-spec.md` §4.4.2) — 사용자가 설정을 채우면 스스로 해결된다 |
| **사용자가 스스로 해소할 수 없는 상태** | VIEWER의 저장 버튼, EDITOR의 회원 관리 메뉴 | **숨김**(F-4) — 비활성 버튼을 보여줘도 사용자가 할 수 있는 일이 없어 혼란만 준다. 권한 자체가 바뀌어야(관리자의 조치) 해결된다 |

서버가 최종 판정자다(NFR-S6) — 클라이언트의 숨김은 UX일 뿐이며, 개발자 도구로 API를 직접 호출해도 서버가 `403`으로 막는다(AC-12B-5). 프런트 구현은 이 사실에 의존해 **판정 로직을 중복 구현하지 않는다** — `can(permission)` 하나로 렌더 여부만 결정한다.

### 4.2 화면별 매트릭스 (발췌 — 전 화면 아님, 대표 지점)

| 화면 | 요소 | VIEWER | EDITOR | ADMIN |

| S3/S4 챗봇 설정/스킨 | "저장" 버튼, 각 입력 필드 | **폼 자체를 읽기 전용 요약으로 대체**(입력 필드 미렌더, `dialogue:read`/`chatbot:read`만으로 조회는 가능) | 표시 | 표시 |
| 대화설계(D1~D5) | 생성/수정/삭제/대량업로드 버튼 | 숨김(목록·상세 조회는 가능) | 표시 | 표시 |

| U1 | 본인 행의 역할변경/상태변경 액션 | — | — | **본인 여부와 무관하게 숨김**(§3.7 자기수정 방지) |

### 4.3 챗봇 상세 7번째 탭 — 추가하지 않는다 (FR-13-23 판단)

**결론: 탭을 추가하지 않는다.** 대신 ① TopBar "시스템 설정 > 이력 관리"(전역, `chatbotId` 필터 없이 진입) ② 챗봇 상세 헤더의 소형 링크(해당 챗봇으로 필터 사전 적용) 두 경로로 충분하다.

근거:
1. **이미 과밀하다.** 현재 6개 라우트가 4개 시각적 그룹(운영/설계/검증/배포)으로 묶여 있는 상태 자체가 `quality-channel-ui-spec.md` §2가 "6탭 평면이 아니라 그룹핑"으로 한 차례 밀도를 낮춘 결과다. 여기에 7번째를 더하면 그 판단을 무의미하게 만든다.
2. **권한 계층이 다르다.** 6개 탭은 전부 `chatbot:read`/`dialogue:read`/`channel:read`/`simulation:read`로 VIEWER도 접근하는 화면이다. 이력(`audit:read`)은 **ADMIN 전용**이라 VIEWER/EDITOR에게는 애초에 빈 탭(숨김 처리된 탭)이 되어 탭바의 항목 수가 역할마다 달라지는 불일치가 생긴다. 링크 방식은 "있는 사람에게만 보이는 부가 진입점"으로 자연스럽게 처리된다.
3. **탐색 빈도가 다르다.** 대시보드·설정·대화설계는 일상적 편집 대상이지만, "이 챗봇에 무슨 일이 있었나"는 **드물게, 특정 계기(S-13처럼 "어제까지 있던 게 사라졌다")로만** 조회한다. 상시 탭보다 헤더의 보조 링크가 그 사용 빈도에 맞다.

### 헤더 링크 배치

```
← 목록으로   [AB] 주문 상담봇   ●운영중   고객지원 그룹   order-bot   [변경 이력 ↗]
```

- "변경 이력" 링크는 `can('audit:read')`일 때만 렌더(숨김 원칙, ADMIN만 봄).
- 클릭 시 `/settings/audit-logs?chatbotId={chatbot.id}&chatbotName={encodeURIComponent(chatbot.name)}`으로 이동(새 탭이 아니라 같은 탭 이동 — `↗` 아이콘은 "설정 화면으로 벗어난다"는 시각적 신호일 뿐).
- 되돌아오는 경로는 `TopBar`의 "챗봇 목록"과 브라우저 뒤로가기로 충분하며, 별도 "챗봇으로 돌아가기" 버튼은 A1 화면에 추가하지 않는다(과잉 설계 방지 — `ChatbotFilterChip`의 `×`가 이미 필터 해제 기능을 겸한다).

## 7. 사용자 인터랙션 흐름 (제출 → 로딩 → 결과, 오류 포함)

### 7.1 최초 기동(부트스트랩) → 최초 로그인 → 비밀번호 변경 (S-1)
```
서버 최초 기동(사용자 0명 또는 seed ADMIN 1명)
  → 관리자가 /login 진입 → 이메일/초기 비밀번호 입력 → 로그인 성공
  → mustChangePassword=true 감지 → L2 강제 렌더(다른 라우트 이동 불가)
  → 새 비밀번호 설정 → 204 → mustChangePassword=false → 정상 콘솔(대시보드) 진입
```

### 7.2 일상 로그인과 세션 유지 (S-2)
```
/login → 이메일/비밀번호 → 200 + 쿠키 → returnTo 또는 '/' 이동
(브라우저를 닫았다 유휴만료(기본 120분) 전에 다시 열면 GET /auth/me가 200 → 바로 콘솔)
```

### 7.3 로그인 실패 누적 → 계정 잠금 (S-3)
```
1~4회 실패 → "이메일 또는 비밀번호가 올바르지 않습니다"(매번 동일 문구)
5회째 실패(잠금 발생) → "로그인 시도가 너무 많습니다. 15분 후 다시 시도해 주세요"
15분 경과 후 올바른 비밀번호 → 정상 로그인, 실패 카운터 서버에서 초기화
```

### 7.4 세션 만료 중 저장 시도 (S-6, AC-U-4)
```
편집 화면에서 폼 작성 중(dirty=true) → "저장" 클릭 → PATCH 요청 → 401 SESSION_EXPIRED
  → client.ts가 요청을 가로채 L3 모달 오픈(배경 폼은 그대로)
  → 모달에서 재로그인 성공 → 모달 닫힘 + 원래 PATCH 요청 자동 재시도
  → 재시도 성공 → 화면은 평소의 성공 처리(Toast 등)를 그대로 수행
```

### 7.5 회원 등록 → 임시 비밀번호 1회 전달 (S-7)
```
U1 "+ 회원 추가" → 이메일/이름/역할 입력 → 제출 → 201
  → 모달이 TemporaryPasswordReveal로 전환 → 복사 → "확인했습니다" → 모달 닫힘
  → (재조회 경로 없음 — 이 값은 여기서만 볼 수 있다)
  → 당사자가 최초 로그인 → §7.1과 동일하게 비밀번호 변경 강제
```

### 7.6 권한 즉시 회수 (S-8)
```
관리자가 U1에서 사용자 A를 DISABLED로 전환 → 200
A가 열어둔 다른 탭에서 다음 요청(어떤 API든) → 401 ACCOUNT_DISABLED
  → L3 모달이 뜨지만 재로그인 시도도 401 INVALID_CREDENTIALS(계정 열거 방지 문구 재사용, C-1)
  → A는 결국 "취소"로 모달을 닫을 수밖에 없고, 다음 새로고침 시 L0가 /login으로 보낸다
```

### 7.7 마지막 관리자 보호 (S-9)
```
ADMIN이 유일한 ACTIVE 관리자 자신을 VIEWER로 변경 시도
```

## 10. `frontend-implementer` 인계 메모

1. **구현 순서 권고**: ① `AuthContext` + `AuthGate` + `/login` + `ForcedPasswordChangeScreen`(L0~L2, 이것 없이는 다른 무엇도 인증된 화면에 도달할 수 없다) ② `client.ts` 401 훅(L3) + `credentials` 적용 ③ `TopBar` 확장(N1) ④ U1/B1/A1 3화면 ⑤ 챗봇 상세 헤더 링크(§4.3) ⑥ `quality-channel-ui-spec.md` SIM1 캡션 1줄(§6).
2. **의존 스키마**: `security.ts`의 `Permission`/`ROLE_PERMISSIONS`/`ROLE_LABELS`/`UserSchema`/`CreateUserResponseSchema`/`PasswordResetResponseSchema`/`RoleListItemSchema`/`BannedWord*Schema`/`validatePasswordPolicy()`, `audit.ts`의 `AuditAction`/`AUDIT_ACTION_LABELS`/`DESTRUCTIVE_AUDIT_ACTIONS`/`AuditTargetType`/`AUDIT_TARGET_LABELS`/`AUDIT_TARGET_ROUTE`/`AuditLogListItemSchema`/`AuditLogDetailSchema`/`AUDIT_LIMITS` — 이 문서의 데이터 바인딩은 전부 이 스키마들이 `backend-implementer` 산출물로 존재한다는 전제다.
3. **`AuditRetentionNotice`의 `startDate`**: 이 문서 작성 시점에는 실제 배포일을 알 수 없다. `backend-implementer`가 환경변수(예: 배포 시 1회 설정하는 상수) 또는 `AuditLogListResponseSchema` 부가 필드로 내려주는 방식을 확정해야 하며, 프런트는 하드코딩하지 않는다.
4. **상수 파일**: 이 문서의 모든 한국어 문구는 `MESSAGES.auth`/`MESSAGES.users`/`MESSAGES.bannedWords`/`MESSAGES.auditLogs` 네임스페이스로 옮긴다(FR-U-12). 로그인 실패 고정 문구(§0-4)는 특히 **서버 `message`로 대체되지 않도록** 상수 사용을 강제하는 코드리뷰 포인트로 남긴다.
5. **`postForm` 누락 점검**(F-5, AC-U-9): 대량 업로드(`BulkImportModal`, `dialogue-design-ui-spec.md` §4.4)가 이 그룹 배포 이후에도 정상 동작하는지 — `client.ts`의 `postForm`이 `credentials: 'include'`를 별도로 추가해야 하는 지점이라 회귀가 나기 쉽다.
6. **미결정/후속 확인 필요**
   - `UserFilterBar`의 역할/상태 기본 선택값(§3.7 "상태 ☑활성 ☐비활성")은 이 문서의 제안이며, PM 확인 후 조정 가능.
   - CSV 내보내기(A1)는 P2로 설계에 포함했으나 일정 압박 시 버튼 자체를 숨기는 것으로 후퇴 가능(FR-13-19, 컨트롤러 1개 메서드로 격리되어 있어 회귀 없이 뺄 수 있다).
   - `AuditLogFilterBar`의 `actorId` 선택기가 사용자 수가 많아질 경우 셀렉트에서 검색 가능한 `ResourcePickerField` 스타일로 바뀔 수 있다(현재는 seed 기준 3명이라 단순 셀렉트로 충분).
