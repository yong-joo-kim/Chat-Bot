# ADR-0025 — No.16 증강의 산출물 정의와 "제안 ≠ 자산" 구조적 봉인

- **상태**: 채택 (Accepted)
- **일자**: 2026-09-22
- **결정자**: system-architect (PM 확정사항 1·5 반영)
- **관련**: `docs/requirements/learning-augmentation.md` **J-1 / J-2 / J-4 / J-11**, FR-0-50/51, FR-L1-1~26, AC-L1-1~16, AC-L4-3 / ADR-0018(예문 반영 공용 경로·인계 지점) / ADR-0022(allowlist 봉인 — "약속하지 않고 할 수 없게 만든다"의 선례) / ADR-0004(쓰기 주체 없는 스키마 금지) / ADR-0020(사전 계산 결과 주입)
- **영향 범위**: `apps/api/src/augmentation/**`(신설), `apps/api/prisma/schema.prisma`(`AugmentationSuggestion` 신설), `packages/shared-types/src/learning.ts`, 개발명세서 §2.2·§3·§4·§6
- **세부 설계**: `docs/02-spec/learning-augmentation-설계.md` §4·§10·§13

## 맥락

카탈로그 No.16 "딥러닝 학습엔진(DLE)"은 "최소 데이터로 문장·의도 데이터를 유사 의미로 증강학습(GPU 6)"이다. 이 문장은 두 가지로 읽힌다.

- **(a)** 데이터 증강 파이프라인 — 산출물이 **예문 문장**이며 기존 `Intent.examples`에 편입된다.
- **(b)** 모델 파인튜닝 — 산출물이 **가중치 파일**이며 보관·버전·롤백·배포 설계가 새로 필요하다.

동시에 카탈로그 No.23은 "**관리자 확인 후** … **전면 자동 아님**"을 요구사항 본문에 못 박았다. 그런데 "자동으로 하지 않기로 한다"는 **약속은 회귀에 약하다** — 반년 뒤 누군가 "제안을 자동 승인하는 배치"를 한 줄 추가하면 아무 테스트도 실패하지 않는다.

## 결정

### 1. No.16의 1차 산출물은 **모델이 아니라 데이터**다 (a안 채택)

증강 파이프라인의 최종 산출물은 `Intent.examples`에 편입될 **후보 문장**이다. 임베딩·분류기의 **파인튜닝은 이번 범위에 포함하지 않는다**(§9 Out of scope, ADR-0024 §1의 주장 유지).

| 얻는 것 | 설명 |
|---|---|
| 색인·매칭·감사·권한·롤백을 **새로 설계하지 않는다** | 산출물이 기존 자산이므로 FR-N1-18(색인)·ADR-0016(감사)·ADR-0015(권한)·예문 삭제(롤백)가 전부 이미 있다 |
| **새로 만드는 것이 제안 저장소 1개**뿐이다 | `AugmentationSuggestion`. 모델 산출물 보관·버전·배포 설계가 이번 범위로 끌려 들어오지 않는다 |
| `modelId` **전역 1개** 규약이 유지된다 | 챗봇별 파인튜닝은 이 규약을 깨고 임계값 기본값 매핑(ADR-0021 §5)까지 챗봇별로 갈라놓는다 |
| 자체 GPU 없이 **1차 구현이 성립**한다 | 기본 구성(G1 규칙 기반)은 GPU 0·외부 호출 0이다(ADR-0026) |

> **세일즈 메시지와의 정합성(요구사항 P-3)**: (a)만 구현하면 "우리 엔진을 고객 데이터로 학습시킨다"는 주장은 하지 못하고, "고객 데이터로 예문을 자동 확장한다"는 주장만 가능하다. 기술적으로 **(a) → (b)는 선행 관계**다 — (a)가 만든 데이터가 (b)의 학습 데이터가 되므로 순서상 손해가 없다. PM은 (a)로 확정했다.

### 2. 증강은 임베딩 매칭의 중복이 아니다 — **비교 대상 집합**을 넓힌다

1단계 의미 점수는 `s = max_i cos(q, eᵢ)` 다. 예문이 1건이면 **모델을 아무리 좋게 바꿔도 `max` 자체가 낮게 형성**된다. 증강이 바꾸는 것은 점수 계산식이 아니라 `eᵢ`의 집합이다.

- 임베딩(No.18, 완료) = **질의 쪽** 표현 다양성을 흡수한다(추론 시점).
- 증강(No.16, 이번) = **등록 쪽** 표현 빈약을 메운다(편집 시점, 오프라인).

따라서 **예문이 이미 충분한 의도(기본 10건 이상)에는 증강을 권하지 않는다**(FR-L1-2 — 요청은 막지 않고 화면이 안내한다). 수확 체감이 크고 오염 위험만 남기 때문이다.

### 3. 생성 문장은 **이미 운영 중인 임베딩으로 자기 검증**한다. 신규 추론 인프라를 만들지 않는다

| # | 검사 | 규칙 | 기본값 | 실패 시 |
|---|---|---|---|---|
| ① | 의미 보존 | `τ_keep_low ≤ cos(후보, 시드) ≤ τ_keep_high` | 0.75 / 0.97 | 제외 `SEMANTIC_DRIFT` / `NEAR_DUPLICATE` |
| ② | 신규성 | `max cos(후보, 기존 예문) < τ_novel` | 0.95 | 제외 `DUPLICATE_OF_EXISTING` |
| ③ | 타 의도 충돌 | `max cos(후보, 타 의도 예문) ≥ τ_accept` | 챗봇 설정값 | **경고만**(차단 아님) |
| ④ | 금지어 | `BannedWord` 리터럴 매칭 | — | 제외 `BANNED_WORD` |
| ⑤ | 형식 | 길이 1~200자 · 제어문자 없음 · 한국어 판별 | — | 제외 `INVALID_FORMAT` |
| ⑥ | 자기 중복 | 같은 요청 내 정규화 동일 또는 `cos ≥ 0.97` | — | 1건만 유지 |

- 검증 임계값은 **`modelId` 종속 잠정값**이며 코드 상수 1곳의 `modelId → 기본값` 매핑이다(ADR-0021 §5와 동일 규약). **챗봇별 설정으로 노출하지 않는다** — 관리자가 조정할 이유가 없고, 조정하면 검증이 무력화된다.
- 임베딩 배치 호출은 **요청당 1회**(후보 전체)이며, 기존 예문·타 의도 예문 벡터는 **저장된 `EmbeddingVector`를 읽는다**(재임베딩 0).

### 4. **검증할 수 없으면 증강을 거부한다. 저하 모드를 만들지 않는다**

임베딩 서비스가 없거나 `modelId`가 stale이면 ①②③을 수행할 수 없다. 이때 **④⑤만 통과시키고 제안하는 "저하 모드"를 만들지 않으며**, `503 AUGMENTATION_UNAVAILABLE`로 거부한다.

> 대화 경로의 저하 모드와 성격이 다르다. **대화는 멈추면 안 되지만, 증강은 안 해도 되는 일**이다. 검증 없는 증강은 오학습을 **즉시** 대화에 주입하며(반영이 즉시니까 — ADR-0018이 자동 반영을 기각한 바로 그 이유), 이 기능이 주는 이득보다 위험이 크다.

### 5. **제안과 자산을 서로 다른 저장소에 두고, 승격 경로를 1곳으로 봉인한다** (J-11)

```
[생성 Job]  ──쓰기──▶  AugmentationSuggestion   (제안 — 대화에 아무 영향 없음)
                              │
                              │ ★ 관리자 요청 핸들러 1곳(POST .../augmentations/accept)
                              ▼
[승격 서비스] ──호출──▶  IntentsService.applyLearningExample()  ──▶  Intent.examples (자산)
```

**봉인 4계층** — ADR-0022가 파괴적 RAG 경로를 "호출하지 않기로 약속"하지 않고 **호출할 수 없게** 만든 것과 같은 방식이다.

| 층 | 수단 |
|---|---|
| L1 모듈 그래프 | 비동기 작업 실행 모듈(`TrainingJobsModule`·`AugmentationJobRunner`)은 `IntentsModule`·`KeywordsModule`을 **import하지 않는다.** NestJS DI 그래프에 없으므로 Job 완료 콜백이 자산을 쓰는 코드는 **컴파일되지 않는다** |
| L2 서비스 경계 | `Intent.examples`·`Keyword.synonyms`를 쓰는 Prisma 호출은 `intents.service.ts`·`keywords.service.ts` **2개 파일뿐**이다 |
| L3 호출부 allowlist | `applyLearningExample()`/`KeywordsService`의 학습용 공용 메서드를 호출하는 파일은 **명시된 3곳뿐**(미응답 단순 반영 · 증강 승인 · 요소분해 반영) |
| L4 정적 검사 | 위 3항목을 `augmentation/lib/asset-write-sealing.spec.ts`가 매 실행 단언한다(AC-L4-3). 스캔 대상이 조용히 0건이 되는 것을 막는 가드 단언을 포함한다(`rag-allowlist.spec.ts` 선례) |

추가 규약:

- **"전체 승인" 전용 API를 만들지 않는다.** 화면의 전체 선택은 id 배열을 채워 보낸다 — 서버에 "무조건 전부"라는 의미의 경로를 두지 않는다(FR-L1-19).
- **충돌 경고가 붙은 제안은 전체 선택에서도 제외**된다(FR-L3-3).
- 제안의 상태 변경(승인/거절)은 **감사 대상이 아니다.** 실제 통제가 필요한 변경(예문 추가)은 `Intent` UPDATE 1건으로 이미 남는다(FR-15-35와 동일 판단).
- 물리 삭제 API를 제공하지 않는다(`REJECTED`로 대체). `@@unique([intentId, textNormalized])`가 같은 문장의 재제안을 흡수한다.

### 6. stale 판정은 "**대상 의도의 예문 변경**"을 쓰지 않고 **승인 시점 재검증**으로 대체한다 (FR-L1-23의 정밀화)

요구사항 FR-L1-23은 stale 조건에 "대상 의도의 예문이 변경되면"을 포함했다. 이를 문자 그대로 구현하면 **제안 2건을 승인하는 순간 `Intent.updatedAt`이 바뀌어 남은 제안 전부가 즉시 승인 불가**가 된다 — AC-L1-5("나머지 3건은 `PENDING`으로 남는다")가 실질적으로 무의미해진다.

| 항목 | 확정 |
|---|---|
| stale 조건 | ① 검증에 쓴 `modelId` ≠ 현재 `modelId` ② 생성 후 `AUGMENTATION_SUGGESTION_TTL_DAYS`(기본 7일) 경과 ③ 대상 의도가 존재하지 않음 |
| 예문 변경 대응 | stale이 아니라 **승인 핸들러가 건별로 재검증**한다 — 정규화 중복 확인 + 신규성 코사인 재계산(`≥ τ_novel`이면 그 건만 `DUPLICATE_OF_EXISTING` 실패, 나머지는 성공 = 부분 성공) |
| 근거 | 비교 벡터는 이미 캐시에 있어 재검증 비용이 무시할 만하고, **"지금 이 순간의 사실"로 판정**하므로 낡은 점수로 승인하는 위험이 stale 플래그보다 더 정확하게 제거된다 |

### 7. 증강 편입도 **기존 즉시 반영 경로**를 그대로 탄다

- 편입은 제안 건당 `IntentsService.applyLearningExample()` 호출이며(dedupe·상한 500·충돌·감사·색인 예약을 복제하지 않는다 — FR-0-51),
- `LearningApplyService.applyLearning()`은 **요청당 정확히 1회**(`reason: 'AUGMENTATION_ACCEPT'`, K-2),
- 반환값은 여전히 `{ mode:'IMMEDIATE', appliedImmediately:true, jobId:null }`이다(ADR-0018 보론 §7 참조).

## 근거

- **산출물을 데이터로 두면 재사용 표면이 최대가 된다.** 카탈로그 원문 스스로 "문장·의도 **데이터**를 증강"이라고 적었고, 데이터로 두는 순간 이 프로젝트가 이미 검증한 통제(상한·충돌·감사·권한·색인)를 한 줄도 다시 쓰지 않는다.
- **생성 모델은 반드시 쓰레기를 만든다.** 그런데 우리는 "두 문장이 의미가 같은가"를 수치로 판정할 도구를 **이미 갖고 있다**(`EmbeddingVector` + 코사인). 안 쓸 이유가 없다. 상한 0.97은 "사실상 같은 문장"을 걸러 예문 상한 500을 낭비하지 않기 위함이다.
- **약속이 아니라 구조로 막는다.** ADR-0022가 확립한 패턴의 두 번째 적용이다. 모듈 그래프에서 의존을 끊으면 "자동 승인 배치"는 작성 의도가 있어도 **컴파일 단계에서 막힌다**.
- **거부가 저하보다 안전한 유일한 경로다.** 이 프로젝트의 다른 모든 저하 모드(엔진·RAG·임베딩)는 "사용자 대화가 멈추면 안 된다"는 이유로 정당화됐다. 증강에는 그 이유가 없다.

## 대안과 트레이드오프

| 대안 | 기각 사유 |
|---|---|
| **(b) 파인튜닝을 1차에 구현** | `modelId` 전역 규약·임계값 매핑을 챗봇별로 갈라놓고, 모델 산출물 버전·롤백·배포 설계가 통째로 필요하며, 챗봇당 수백~수천 문장으로는 과적합이 지배적이다. 실제 GPU가 **필수**가 된다(현재는 선택) |
| **검증 없이 제안하고 관리자에게 전부 맡긴다** | 관리자는 "이 문장이 다른 의도와 충돌하는가"를 눈으로 판정할 수 없다. 화면이 20건을 무검증으로 쏟아내면 승인 절차가 형식화된다(J-11의 취지 붕괴) |
| **임베딩 없을 때 ④⑤만으로 저하 제안** | 의미 이탈 문장이 예문에 들어가 **즉시** 매칭 품질을 떨어뜨린다. 저하의 대가를 사용자가 치른다 |
| **제안을 `Intent.examples`에 `pending` 플래그로 함께 저장** | 대화 자산 테이블에 "대화에 쓰이면 안 되는 행"이 섞인다. 엔진·색인·상한 계산·감사 스냅샷 전부가 그 플래그를 알아야 하며, 한 곳이라도 빠지면 **승인 안 된 문장이 대화에 반영**된다 |
| **`Intent`에 FK를 걸어 제안을 참조 무결성으로 보호** | `onDelete: Restrict` 규약 때문에 **제안이 있는 의도를 영원히 삭제할 수 없게** 된다. `EmbeddingVector.ownerId`와 동일한 판단으로 FK를 걸지 않고 `chatbotId`에만 건다 |
| **챗봇 전체 일괄 증강 제공** | 수백 개 제안을 한 화면에서 검토하면 승인 절차가 형식화된다. 의도 단위 요청으로 제한한다(FR-L1-3) |
| **FAQ 질문·대체질문까지 증강 대상에 포함** | 승인 화면·감사·상한 규칙이 두 벌이 된다. 의도 예문에서 검증된 후 확장한다(§9) |

**감수하는 비용**

1. **제안 테이블이 비대해질 수 있다** → 챗봇당 `PENDING` 상한 500(기본)에서 신규 생성을 거부하고 정리를 안내한다(큐 상한 규약과 동일). 챗봇 영구삭제 시 동반 삭제된다.
2. **거절한 문장은 영원히 다시 제안되지 않는다**(`@@unique`) → 의도된 동작이다. 되살리려면 관리자가 의도 편집에서 직접 예문을 추가한다.
3. **임베딩이 꺼진 환경에서는 증강 기능 전체가 쓸 수 없다** → 화면이 원인과 해결 방법을 명시한다(UIUX §7). `EMBEDDING_BASE_URL`이 이 기능의 실질적 전제조건임을 문서에 남긴다.

## 갱신 (2026-09-23 — 자산 쓰기 봉인 L2/S-1의 세 번째 허용 파일: 복원 applier)

챗봇 복원/버전 이력관리(No.25, ADR-0031)의 **`apps/api/src/versions/restore/version-restore.applier.ts`** 가 `Intent`·`Keyword`(및 나머지 대화 자산)를 트랜잭션 안에서 쓴다. 따라서 §5 봉인 **L2**("`Intent.examples`·`Keyword.synonyms`를 쓰는 Prisma 호출은 2개 파일뿐")와 `asset-write-sealing.spec.ts` **S-1**의 허용 파일이 **2 → 3**이 된다(가드 단언 "정확히 2개" → 3개).

**이 예외가 "승인 없는 자산 변경 금지"를 약화하지 않는 이유**
- 복원은 **관리자의 명시적 요청 핸들러 1곳**(`POST …/versions/:versionId/restore`, `dialogue:write` + `chatbot:write`)에서만 실행된다. 스케줄러·Job·콜백 경로가 없다.
- 복원이 쓰는 내용은 **과거에 실제로 존재했던 자산 상태**다 — 스냅샷 본문을 만드는 경로는 **실제 DB 자산의 캡처뿐**이며 **내보내기·가져오기가 존재하지 않는다**(NFR-HS5). 따라서 제안(`AugmentationSuggestion`)이나 외부 문장이 승인 없이 예문으로 들어가는 경로가 되지 않는다.
- 복원은 `AugmentationSuggestion`에 **쓰기 0건**이며 `applyLearningExample()`을 호출하지 않는다 — **L3(호출부 allowlist 3곳)·S-2는 불변**이다.
- 버전 모듈 쪽에도 대화 자산 쓰기가 applier **1파일**뿐임을 `version-sealing.spec.ts`가 단언한다(L4와 같은 형식).

**영향 기록**: 롤백으로 제거된 **승인 증강 예문은 다시 제안되지 않는다**(`@@unique([intentId, textNormalized])` — 감수비용 2와 같은 성질, PM 확정 P-8). 복원 미리보기가 그 건수를 경고로 보여 준다. 반대로 **증강 승인 직전 자동 스냅샷**(`BEFORE_AUGMENT_ACCEPT`)이 "승인 후 되돌리기"의 유일한 안전망이 된다 — 승격된 문장은 일반 예문이라(§5) 증강분만 골라낼 표시가 없기 때문이다.

## 갱신 (2026-09-23 — 봉인 문구 개정: 복원 호출부에 "관리자가 승인한 예약의 실행기" 추가)

운영 예약 배포(No.28, **ADR-0032 §6**)에 따라 위 갱신(2026-09-23)의 문장 "복원은 **관리자의 명시적 요청 핸들러 1곳**에서만 실행된다. 스케줄러·Job·콜백 경로가 없다."를 **다음으로 대체**한다.

> 복원(대화 자산을 쓰는 `version-restore.applier.ts`)은 `VersionRestoreService.restore()` 안에서만 호출되며, `restore()`의 호출부는 **① 관리자 요청 핸들러(`POST …/versions/:versionId/restore`, `dialogue:write` + `chatbot:write`) ② 관리자가 미리보기로 확인하고 해시에 묶어 생성한 예약의 실행기(`deploy-schedules/executors/restore-version.executor.ts`)** 2곳뿐이다. 그 밖의 스케줄러·Job·콜백 경로는 없다.

**이 개정이 §본뜻("승인 없는 자산 변경 금지")을 약화하지 않는 이유**
- 예약 복원은 **관리자의 명시적 승인**이다 — 생성 시 복원 미리보기(차이·blockers·warnings)를 확인하고, 그 기준 상태를 **해시로 묶는다**. 실행 시 상태가 달라졌으면 **실행하지 않는다**(엄격 바인딩).
- 실행 직전 **예약자의 계정 상태와 권한을 재검증**한다(`dialogue:write` + `chatbot:write`) — 권한을 잃은 사람의 승인은 실행되지 않는다. 감사 주체도 예약자다.
- 반영 내용은 여전히 **과거에 실제로 존재한 자산 상태**다 — 스냅샷 본문을 만드는 경로는 실제 DB 자산의 캡처뿐이고 내보내기·가져오기가 없다. 제안(`AugmentationSuggestion`)이나 외부 문장이 승인 없이 예문이 되는 경로가 아니다.
- **L1~L4 봉인은 전부 불변**이다: 예약 모듈은 `IntentsModule`·`KeywordsModule`·`AugmentationModule`을 import하지 않고(L1), 자산 테이블 쓰기 호출이 0건이며(L2 — **`asset-write-sealing.spec.ts` S-1 허용 파일은 3개 그대로**), `applyLearningExample()`을 호출하지 않는다(L3 — S-2 불변). 개발명세서 §5의 "스케줄러·백그라운드 작업·Job 완료 콜백이 자산을 **직접** 쓰는 코드 0건"도 그대로 참이다 — 예약 실행기는 applier가 아니라 `restore()`를 호출한다.
- 구조 보장은 약속이 아니라 **주입 불가**다: `VersionsModule`이 applier를 export하지 않는다. `restore(` 호출 파일이 정확히 2개임을 `deploy-schedule-sealing.spec.ts`가 단언한다.
