# ADR-0032 — 운영 예약 배포 = 기존 반영 동작의 1회성 시각 예약 + 인프로세스 폴링 · DB CAS 선점 · 임대

- **상태**: 채택 (2026-09-23)
- **결정자**: system-architect (PM 확정사항 P-1~P-12 반영)
- **관련**: 요구사항 `docs/requirements/scheduled-deploy.md` **J-1 / J-3 / J-4 / J-5 / J-6 / J-7 / J-8 / J-11 / J-12 / J-15**, FR-0-78~87, FR-D1~D7, AC-D1~D6 · 설계 `scheduled-deploy-설계.md` §4~§9·§13
- **연관 ADR**: ADR-0031(버전 스냅샷·ID 보존 복원 — §8이 "예약 복원(No.28)"을 **일부러 비워 둔** 결정) · ADR-0025(승인 없는 자산 변경 금지 · 자산 쓰기 봉인) · ADR-0011(공개 = 상태 ACTIVE AND 채널 enabled) · ADR-0016(감사 · `actorOverride`) · ADR-0015(권한) · ADR-0027/0029(in-process 큐 · 기동 시 고아 정리) · ADR-0017(`STATS_TIMEZONE`)
- **Supersedes**: 없음. ADR-0025 갱신 각주·ADR-0031 갱신 각주가 이 ADR을 참조해 **봉인 문구를 개정**한다(결정 자체는 불변).

## 맥락

카탈로그 No.28 원문은 "학습 완료된 챗봇을 지정 시각에 자동 반영 예약"이다. 원본(ROCHA)은 **운영본과 학습본이 동시에 존재**하는 모델에서 "교체"를 예약한다. 우리 시스템에는 그 두 벌이 없다 — 대화 자산 편집은 저장 즉시 운영에 반영되고, `Chatbot.status`는 생명주기일 뿐 두 벌의 자산이 아니다.

동시에 선행 7개 그룹이 "스케줄러 인프라 부재"를 이유로 기능을 미뤘다. 이 그룹이 처음으로 **시각 트리거 실행 엔진**을 만든다. 결정해야 할 것은 여섯 가지다: ① 지정 시각에 **무엇을** 반영하는가 ② **어떤 엔진**으로 실행하는가(재시작·다중 인스턴스) ③ 예약 이후 **상태가 바뀌면** 어떻게 하는가 ④ 늦었거나(misfire) 막혔으면(재시도) 어떻게 하는가 ⑤ **누구의 권한·이름**으로 실행되는가 ⑥ "스케줄러는 자산을 쓰지 않는다"는 기존 봉인(ADR-0025·0031)과 어떻게 양립하는가.

## 결정

### 1. 반영 대상 = **이미 검증된 반영 동작 3종의 1회성 예약** — draft/published는 만들지 않는다 (J-1, P-1)

| 동작 | 실행부(재사용) |
|---|---|
| `RESTORE_VERSION` | `VersionRestoreService.restore()` — 잠금·해시 재확인·백업·ID 보존 차이 적용·사후 검증·캐시 무효화를 **한 줄도 바꾸지 않고** 호출 |
| `PUBLISH`(DRAFT→ACTIVE, 선택: WEB 채널 동시 활성화) | 신규 `ChatbotPublicationService.publish()` — 상태 전이 판정(`evaluateStatusTransition`)·채널 활성화 규칙(`IMPLEMENTED`만)을 **호출만** 하고 상태+채널을 **한 트랜잭션**으로 |
| `SET_WEB_CHANNEL`(열기/닫기) | 같은 서비스 `setWebChannel()` — `ACTIVE→DRAFT` 전이가 없으므로 "공개 종료"의 유일한 가역 수단 |

예약 1건 = 동작 1개이며 복합 반영은 **같은 챗봇의 순서 있는 예약 여러 건**이다. 동작 유형은 **판별 유니온 + 매핑 타입 레지스트리**(`{ [A in Action]: Executor<A> }`)로 둬 **추가가 파일 1개 + 레지스트리 1줄**이고 누락은 컴파일 오류다.

**draft/published 분리(요구사항 후보 (c))는 기각한다.** 그것은 No.40("환경 분리 + 승격")의 정의 그 자체이며, 자산 서비스 6종·대화 경로·임베딩 색인(버전 차원 부재)·학습 반영(`appliedImmediately`)·TC·버전 복원을 **동시에** 재설계하게 만든다. No.40 착수 시 가장 가벼운 형태("published = 특정 `ChatbotVersion` 포인터")가 되면 이 엔진에 **"포인터 전환" 동작 1개**를 더하는 것으로 원본 의미를 완전히 충족한다.

### 2. 엔진 = **인프로세스 폴링(30초) + DB 조건부 갱신 선점(CAS) + 임대(lease)** (J-3)

- **DB가 예약의 유일한 원천**이다. 각 tick은 `status IN (PENDING, RUNNING) AND scheduledAt ≤ now`를 `(status, scheduledAt)` 인덱스로 1회 조회하고(유휴 시 0행), **챗봇당 가장 이른 1건만** 처리한다(순서 보장).
- **선점**은 `updateMany({ where: { id, status:'PENDING', attemptCount }, data: { status:'RUNNING', claimToken, claimedAt } })`의 영향 행 수가 1일 때만 실행한다. 인스턴스가 몇 개든 같은 행의 선점은 DB에서 1회만 성공한다 — **프로세스 로컬 상태를 정합성의 근거로 쓰지 않는다**(at-most-once). 원시 SQL은 0건이다.
- **부분 유니크 인덱스 2개**(마이그레이션 원시 DDL, `test_runs` 선례): ① 같은 챗봇 활성 예약의 같은 분 금지 — 분 정규화와 합쳐 "최소 1분 간격"의 DB 차원 보장 ② 챗봇당 RUNNING 최대 1건 — 다중 인스턴스에서도 챗봇 단위 직렬 실행.
- **임대**: RUNNING이 `claimedAt + lease`(기본 5분)를 넘기면 주인이 죽었다고 보고 **실제 상태로 판정**한다(복원 = 이 예약이 남긴 `BEFORE_RESTORE` 백업 흔적 존재 여부 — 백업은 복원과 같은 트랜잭션이므로 커밋의 증명이다 / 공개·채널 = 목표 상태 도달 여부). **재실행하지 않는다.** 기동 시 정리는 "첫 tick"이며, `TrainingJobService.onModuleInit`처럼 "잔존 = 전부 고아"로 가정하지 않는다. 임대는 실행 최장 시간(복원 트랜잭션 `maxWait + timeout`)보다 길어야 하며 기동 시 검사·상향 보정한다.
- **루프 부품(`common/polling/PollingLoop`)은 도메인과 분리**한다 — `setTimeout` 체인(겹침이 구조적으로 불가능) · 예외 흡수 · `stop()`이 진행 중 tick을 기다림. 시계는 `CLOCK` 토큰으로 주입해 모든 판정을 순수 함수(`now` 인자)로 만든다.

### 3. **엄격 바인딩** — 예약 시 확인한 상태가 아니면 실행하지 않는다 (J-4, J-5, P-4)

- `RESTORE_VERSION`은 생성 시 **기준 해시**를 저장하고 실행 시 `restore()`의 `expectedCurrentHash`로 넘긴다. 불일치면 자산을 바꾸지 않고 `FAILED(STATE_CHANGED)` + "확인 필요". "변경 무시하고 강행" 옵션은 두지 않는다 — 강행은 **무인 시각의 조용한 덮어쓰기**다.
- **체인**: 같은 챗봇에 이른 활성 복원 예약이 있으면 기준 해시 = 그 예약의 **대상 해시**. 복원 체인은 **뒤에만 붙는다**(앞에 끼워 넣으면 뒤 예약의 기준이 조용히 틀어진다) · 시각 수정은 **활성 예약의 상대 순서를 바꾸지 않는** 범위에서만.
- **fail-stop**: 한 예약이 `FAILED`/`MISSED`가 되면 같은 챗봇의 후속 `PENDING` 전부를 **같은 트랜잭션에서** `HELD`로 바꾼다. 해제는 사람이 새 시각(복원이면 새 미리보기)으로 한다.
- 생성 시 기준 해시는 **쓰기 트랜잭션 안에서** 재계산한다(SQLite 직렬화 — 재계산과 INSERT 사이에 끼어든 편집이 없다).

### 4. misfire = **유예 + 폴링 1주기 허용오차**, 재시도 = **일시적 원인만 · 15분 창** (J-6, J-7)

- 시도 0회인 예약이 `예정 + 유예(10분) + 폴링 주기 + 5초`를 넘기면 `MISSED`(실행 안 함). 허용오차가 없으면 "유예 0"에서 정상 가동 중에도 전부 누락된다.
- 결과 분류는 `ApiException.code` 기반 순수 함수 1곳이다. **일시적** = DB 경합(`RESTORE_BUSY`·`P2034`·`SQLITE_BUSY`) · 진행 중 `TrainingJob`/`TestRun` · in-process 복원 잠금 → PENDING 복귀, 폴링마다 재시도, `예정 + 15분` 초과 시 `FAILED(BLOCKED_TOO_LONG)`. **그 외 전부 영구적**(분류 불가 예외 포함 — 모르는 오류를 반복하지 않는다).
- 이를 위해 `restore()`가 **BUSY 경합을 `RESTORE_BUSY`로 분리**한다. 해시 불일치는 계속 `RESTORE_PREVIEW_STALE`이다. "같은 코드, 다른 의미"를 details 필드로 구분하는 안은 기각했다. BUSY 후 재시도는 트랜잭션 안 해시 재확인이 실제 변경을 다시 판정하므로 항상 안전하다.

### 5. 권한은 **즉시 실행과 동일**, 실행 시 **예약자를 재검증**, 감사 주체는 **예약자** (J-8, P-9)

- 동작 → 권한 목록을 **순수 함수 1개**(`requiredPermissions`)로 두고 생성·수정·취소·재개·확인 판정과 **실행 직전 재검증**이 모두 이것을 호출한다. 신규 권한 0종.
- 실행 직전 예약자 사용자 행이 `ACTIVE`이고 현재 역할이 권한을 전부 보유해야 한다. 아니면 `FAILED(CREATOR_NOT_AUTHORIZED)` — **예약은 권한 우회 수단이 아니다**(퇴사·강등 후 과거 예약이 실행되지 않는다).
- 실행의 감사는 **기존 액션**(`RESTORE`·`STATUS_CHANGE`·`UPDATE`)으로, **주체 = 예약자**(`actorOverride`), summary 접두 `[예약 실행 #<id 앞 8자>]`. 복원 직전 백업 스냅샷의 `createdBy`도 예약자다. NOOP·실패·누락·보류는 감사하지 않는다(쓰기 없음). `RequestContextService.get()` 호출 지점은 여전히 `AuditLogService` 1곳이다 — 요청 컨텍스트가 없는 경로는 주체를 **인자로** 넘긴다.
- 변경 API의 권한은 **가드 기준선(`chatbot:read`) + 서비스 판정**으로 통일한다. 생성만 동작별 경로로 나누면 PATCH·취소·재개(행을 읽어야 동작을 안다)와 판정 방식이 두 벌이 된다. 관리 권한이 전혀 없는 사용자는 행 조회 전에 403이다("권한 판정 후 존재 판정" 규약 유지).

### 6. ★ 봉인 문구 개정 — "복원은 관리자 요청 핸들러 1곳"에서 **"관리자 요청 핸들러 또는 관리자가 승인한 예약의 실행기, 둘 다 `restore()` 경유"**로 (J-11)

ADR-0025(§갱신 2026-09-23)와 ADR-0031(§8)은 "복원은 관리자 요청 핸들러 1곳에서만, 스케줄러 경로 없음"이라고 적었다. 이 ADR은 **그 문구를 다음으로 개정**한다(결정의 본뜻은 불변):

> 대화 자산을 쓰는 유일 경로(`VersionRestoreApplier`)는 **`VersionRestoreService.restore()`를 통해서만** 호출되며, `restore()`의 호출부는 **① 관리자 요청 핸들러 ② 관리자가 미리보기로 확인하고 해시에 묶어 생성한 예약의 실행기** 2곳뿐이다. 그 밖의 스케줄러·Job·콜백 경로는 없다.

본뜻("**승인 없는** 자산 변경 금지")이 유지되는 이유: 예약 복원은 ① 관리자가 차이를 미리 보고 ② 그 기준을 해시로 묶고 ③ 달라지면 실행하지 않으며 ④ 실행 시 권한을 재검증하고 ⑤ 반영 내용이 **과거에 실제 존재한 상태**(캡처 본문뿐 — 가져오기 경로 없음)다. "관리자 모르게 바뀌는 자산"이 아니라 "관리자가 승인한 변경의 시각 지연"이다.

**약속이 아니라 구조로 보장한다**(ADR-0022 이래 다섯 번째 적용): `VersionsModule`이 applier를 **export하지 않는다**(주입 불가) · 예약 모듈에 applier·자산 서비스·자산 모듈 심볼 0건 · `restore(` 호출 파일 정확히 2개 · 예약 모듈의 Prisma 쓰기 대상은 `deploySchedule`뿐 · `asset-write-sealing.spec.ts` S-1 허용 파일 **3개 그대로** — 전부 정적 검사가 단언한다.

### 7. 시간 = **UTC 순간 저장 · 오프셋 필수 입력 · `STATS_TIMEZONE` 표시** (J-12)

API는 오프셋 포함 ISO 8601만 받는다(오프셋 없는 로컬 시각은 서버 시간대에 따라 9시간 틀린다). 분 단위로 정규화한다. 표시·입력 변환은 `Intl` 기반 순수 함수 1곳(DST의 존재하지 않는/중복 시각을 판별). 신규 시간대 변수를 만들지 않는다.

### 8. 알림 = **콘솔 + 감사로그만**, 공개 표면·아웃바운드 0건 (J-10, FR-0-85/86)

외부 cron용 내부 트리거 엔드포인트를 만들지 않으며(`@Public()` 6개 불변), 메일·웹훅·메신저 호출을 만들지 않는다. "확인 필요"는 예약 행의 상태 + 확인 표시로 계산하고, 엔진이 어디서도 돌지 않는 상황은 "기한 넘긴 PENDING 건수"로 드러낸다(heartbeat 테이블 없음).

## 근거

- **"언제"만 새로 만들고 "무엇을"은 재사용한다.** 복원·상태 전이·채널 활성화는 이미 수용기준을 통과한 경로다. 예약 엔진이 새로 쓰는 테이블은 `DeploySchedule` 하나뿐이고, 신규 자산 쓰기 경로는 **0건**이다.
- **DB가 원천이면 재시작과 다중 인스턴스 문제가 한 번에 풀린다.** 타이머를 메모리에 두는 모든 안은 재시작 시 재적재와 중복 실행 방지를 따로 풀어야 한다. 조건부 갱신 1줄이 두 문제의 공통 해법이다.
- **엄격 바인딩은 No.25의 409 규약과 같은 판단이다.** 사람이 보고 있는 즉시 복원에서도 미리보기 이후 변경은 거부한다. 아무도 보지 않는 새벽에는 더더욱 그렇다. 백업이 있으니 가역이라는 반론은 "사라진 사실을 아는 사람이 없다"는 문제를 해결하지 못한다.
- **fail-stop이 어긋난 반영보다 싸다.** "복원 실패 후 공개 성공" = 옛 내용으로 공개된 챗봇이다. 보류는 사람 한 명의 클릭으로 풀리지만, 잘못 공개된 챗봇의 대화는 되돌릴 수 없다.
- **책임 소재는 예약한 사람이다.** `system` 주체는 "누가 반영했는가"를 지운다. 그러려면 실행 시점에도 그 사람이 여전히 그 권한을 가져야 한다.

## 대안과 트레이드오프

| 대안 | 기각 사유 |
|---|---|
| **draft/published 분리를 No.28에서 신설** | No.40의 본체 선점 · 7개 선행 그룹 설계 동시 변경 · 임베딩 색인에 버전 차원이 없어 이중화 필요(CPU 배포 재색인 2배) |

## 감수하는 비용

1. **(a) 경로의 준비 편집이 운영에 잠시 보인다**(P-2 수용) — 편집 → 버전 저장 → 즉시 원복. 불가하다면 올바른 답은 No.40 선행이다.
2. **장기 예약은 그 사이 편집이 있으면 실패한다** — 편집 화면 충돌 배너·상태 점검·장기 예약 경고로 사전에 알린다.
3. **폴링 지연(최대 30초 + tick 대기)** — 분 단위 예약에 충분하다. 초 단위 정확도는 요구되지 않는다.
4. **크래시 후 RUNNING 판정이 임대 만료(기본 5분)까지 미뤄진다** — 그동안 같은 챗봇 후속 예약도 기다린다(유예 10분 안).
5. **커밋 직후~감사 기록 전 크래시 시 감사 누락** — 기존 모든 쓰기와 같은 성질(ADR-0016 §4). 예약 행·백업 스냅샷에는 사실이 남는다.
6. **즉시 복원의 BUSY 경합 응답 코드가 `RESTORE_BUSY`로 세분화된다** — 정상 경로 불변, 프런트 분기 1줄, UX 동일.

## 갱신 (2026-09-25 — No.24: `PollingLoop` 두 번째 소비자 = 상담 정리 루프)

하이브리드 CS(No.24, **ADR-0036 §5·§6**)가 도메인 무관 부품 `common/polling/PollingLoop`·`Clock`을 재사용한다. 이 ADR의 결정은 불변이다.

- **60초 상담 정리 루프**: 시간 기반 상담 종료 판정(조회 시점 판정과 같은 순수 함수)·만료 원문 필드 소거·`draining` 해제. 기동 즉시 `runOnce()` 1회.
- **선점(claim)을 쓰지 않는다** — 예약 실행과 달리 모든 연산이 조건부 갱신이라 멱등이다. 모든 인스턴스가 실행하며 같은 상담을 두 인스턴스가 동시에 종료해도 CAS가 1회만 통과시킨다. 임대·RUNNING 부분 유니크는 필요 없다.
- `CLOCK` 포트를 `HandoffModule`에서도 제공한다(같은 토큰 — 통합 시험의 `overrideProvider(CLOCK)`가 두 모듈에 함께 적용된다). tick 예외는 코드만 남긴 새 오류로 넘긴다(원문·메시지 인자를 `PollingLoop` 경고 로그에 흘리지 않는다).
