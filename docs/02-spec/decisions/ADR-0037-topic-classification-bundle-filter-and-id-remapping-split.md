# ADR-0037 — 토픽 = 챗봇 안 평면 분류 · 번들 조립 필터(엔진 0) · 경계 참조 허용 · ID 재매핑 적재기로 분리(복사)

- **상태**: 채택 (Accepted)
- **일자**: 2026-09-25
- **결정자**: system-architect (PM 결정 P-1~P-16 — 전부 권고안)
- **관련**: `docs/requirements/topic-system.md` J-1~J-18, FR-0-129~137, FR-TP1-\*~FR-TP8-\*, AC-TP1~TP7 / ADR-0002(삭제 참조 무결성) · ADR-0005(참조 조인·JSON 참조) · ADR-0006(정규화 유일성) · ADR-0008(해석 파이프라인) · ADR-0016(감사) · ADR-0024(`textHash` 재임베딩 회피) · ADR-0025(자산 쓰기 봉인) · ADR-0030(검증 도구 격리) · ADR-0031(스냅샷·ID 보존 복원 — §8 "깊은 복사는 ID 재매핑") · ADR-0032(예약 해시 바인딩) · ADR-0033(대화 당시 스냅샷 컬럼)

- **세부 설계**: `docs/02-spec/topic-system-설계.md`

## 맥락

원문 "부서·주제별 토픽 분리 구축 후 개별 챗봇화 또는 병합/확장"(기능요구사항 No.22)을 우리 모델 위에 올려야 한다. 대화 자산 6종은 전부 `chatbotId`로 스코프되고, 이름 유일성·교차 챗봇 404·번들 캐시·스냅샷·임베딩·통계가 모두 "챗봇 = 단위"를 전제한다. 풀어야 할 질문은 다섯이다.

1. 토픽은 챗봇 **안**인가 **밖**(여러 챗봇이 공유)인가.
2. 비활성 토픽을 **어디서** 거르는가 — 엔진·인덱스·자산 플래그·번들 조립.
3. 토픽 경계를 넘는 참조를 막는가.
4. 스냅샷(버전)에 소속을 넣는가, 넣으면 기존 해시가 깨지지 않는가.
5. "떼어 내 챗봇으로 만든다"를 어떻게 구현하며, No.40(환경 분리)·병합(2차)과 무엇을 공유하는가.

## 결정

### 1. 토픽은 챗봇 스코프의 **평면 분류**다

`Topic(chatbotId, name, nameNormalized, description?, sortOrder, enabled)` · 챗봇당 50 · 계층 없음. 자산 6종에 **nullable `topicId`**(FK `Restrict` · `@@index([topicId])`) — null = **공통**(가상 토픽, 항상 활성, 삭제·비활성화 불가). 자산당 토픽 0~1개(다대다 아님). START·FALLBACK 노드는 항상 공통. 설문·자주 쓰는 문장·채널은 토픽 비소속. **이름 유일성은 챗봇 단위 그대로**(ADR-0006 불변). 교차 챗봇 토픽 지정은 서비스 1곳(`TopicLookupService`)이 `404 INVALID_REFERENCE`로 막는다.

### 2. 비활성 토픽은 **`getCached()` 번들 조립 1곳**에서 **응답 진입점 3종만** 뺀다 — 엔진 수정 0

- `DialogueBundleService.build(chatbotId, db?, { excludeInactiveTopics? })` — 기본 = 전체 자산. `getCached()`만 필터를 켜고, 필터는 비트랜잭션 경로에서만 허용된다(런타임 가드 + 정적 검사).
- 빼는 것: **노드·의도·FAQ**(사용자 발화가 답에 도달하는 진입점). 남기는 것: 키워드·컨텍스트·동음이의어(사전형 — 스스로 답하지 않고, 빼면 활성 토픽 노드가 공용 키워드를 잃는다).
- 엔진은 "없는 노드·의도"를 이미 예외 없이 처리한다(`BROKEN_REFERENCE` trace · 조건 불일치). 공개 대화·시뮬레이터·비교·TC·상담 힌트·답변 설정 미리보기 6곳이 `getCached()`를 공유하므로 한꺼번에 일관되고, 의미 매칭은 번들 기준으로 후보를 거르므로 **재색인 없이** 따라온다.
- 버전 캡처·설계 점검·흐름·삭제 사전검사·분리 캡처는 **필터 없는** `build()`를 쓴다.
- 시뮬레이터의 "비활성 토픽 포함"은 **별도 캐시 인스턴스**(`getCachedUnfiltered`, LRU 10)로 운영 캐시와 섞이지 않는다. `invalidate()`는 두 캐시를 함께 비운다(무효화 지점 1곳 유지).

### 3. 경계 참조는 **허용하고 보이게** 한다

저장 검증(같은 챗봇이면 통과)은 불변이다. 설계 점검에 API 계층 순수 함수 `validateTopicBoundaries()`가 규칙 4종(`INACTIVE_TOPIC_REFERENCE` 경고 · `CROSS_TOPIC_REFERENCE` 정보 · `CROSS_TOPIC_DUPLICATE_EXAMPLE` 정보 · `NO_LIVE_ENTRY_POINT` 경고)을 **엔진 결과 뒤에** 합친다. 토픽이 0개면 규칙을 실행하지 않는다(점검 결과 바이트 동일). 비활성화 전 **영향 미리보기**(빠지는 진입점 수 · 끊기는 참조 · 예문 중복)를 화면 흐름으로 강제한다. 참조 열거는 `dialogue-common/lib/asset-ref-graph.ts` **1벌**이며, 노드→노드는 `getOutgoingNodeRefs()`를 호출만 하고 나머지 JSON 참조는 **번들 자산 id와 정확히 같은 UUID 문자열 잎**으로 찾는다.

### 4. 스냅샷에는 자산 `topicId`를 **선택 필드**로 넣는다 — 해시 불변 · 복원은 대상 정규화

- `build()`가 `topicId: row.topicId ?? undefined`로 매핑하고, 정규 직렬화(`sortKeysDeep`)는 `undefined` 키를 생략한다 → 모든 자산이 공통인 챗봇의 `contentHash`는 도입 전과 **바이트 단위로 같다**. `SNAPSHOT_SCHEMA_VERSION = 1` 유지 · 업캐스터 불필요.
- `Topic` 정의·활성 상태는 스냅샷 밖(설문·API 연결 선례). 토글은 해시를 바꾸지 않고, 소속 변경은 바꾼다(예약 해시 바인딩이 보류 — 설계상 올바름).
- 복원은 **트랜잭션 안에서 현재 토픽 id 집합으로 대상 스냅샷을 정규화**(없는 토픽 → 공통 · 시스템 노드 → 공통)한 뒤 그 정규화본의 해시를 기대 해시로 삼아 계획·사후 검증을 한다. 정규화 없이 공통으로만 적재하면 사후 해시 검증이 실패해 모든 그런 복원이 롤백되기 때문이다. 미리보기 경고 `TOPIC_MISSING`·`TOPIC_EXPOSURE_CHANGE`(blocker 아님).

### 5. 분리 = **복사** — ID 재매핑 적재기 3단계 (No.40·병합이 재사용)

```
① 캡처(서비스, tx 안 순차)   captureTransferSource(tx, chatbotId) → { bundle(전체·설문 포함), topics, capturedAt }
② 선택·계획(순수)            selectTransferSubset(source, selection) → 씨앗 + 의존 폐포 + 시스템 노드 처리 + 건수
                             planTransfer(source, subset, policy)     → 순서 보존 새 ID · 참조 재작성 · 적재 행
                             verifyTransferPlan(plan, sourceIdSet)    → 원본 ID 잔존 0 · 참조 폐쇄성
③ 적재(서비스, 생성 전용)     AssetTransferLoader.load(tx, targetChatbotId, plan) — create/createMany만
```

- 원본 불변 · 새 챗봇 `DRAFT` · **모든 ID 새로 발급**. 선택 토픽 자산 + 그것이 가리키는 토픽 밖 자산의 **전이 폐포**(새 챗봇에서 공통) + START·FALLBACK. 참조 설문은 정의만 복제(DRAFT·key 재발급) · `connectionId`(전역)는 그대로. 토픽 정의 복사. 채널·설정·TC·로그·버전·임베딩 등 비복사(재색인으로 색인 생성).
- **폐포와 재작성은 같은 "UUID 잎" 판정**을 쓴다 — 참조 종류 목록(E-1~E-8)에 없던 참조(API 슬롯 바인딩 → 컨텍스트)도 빠지지 않고, "폐포에 없는데 재작성해야 하는 id"가 구조적으로 생기지 않는다. 재작성 후 원본 id가 1건이라도 남으면 적재하지 않는다.
- **순서 보존 ID 발급**(종류별로 정렬된 원본 id ↔ 정렬된 새 UUID) + **타임스탬프 보존** → 동점 규칙(`createdAt, id` 번들 순서 · `rankNodes`의 `updatedAt desc → id asc`)이 분리본에서도 같은 승자를 낸다.
- 시작 노드는 거의 항상 모든 토픽으로 가는 허브라 폐포를 챗봇 전체로 키운다 → **공통을 선택하지 않은 분리에서는 시스템 노드의 이동·버튼 연결 중 폐포 밖을 가리키는 것을 잘라낸다(TRIM, 기본)**. 잘린 항목은 미리보기·결과에 전수 표시하고, `FOLLOW`(원안 — 전부 따라가기)를 선택할 수 있다.
- 한 인터랙티브 트랜잭션(캡처 → 계획 → 검증 → 챗봇 행 → 적재) · 동기 상한 초과 `422 TOPIC_SPLIT_TOO_LARGE` · 경합 `409 TOPIC_SPLIT_BUSY` · 실패 시 새 챗봇 행까지 롤백. **전체 토픽 + 공통 = 챗봇 깊은 복사**(기존 `POST …/copy`는 프로필만 — 불변).
- **복원 적재기(ID 보존)와 코드를 공유하지 않는다** — 공유하는 것은 캡처(`build(chatbotId, tx)`)와 `normalizeText`뿐이다. 병합(2차)의 "합치기"는 적재기가 아니라 별도 적용기가 한다(적재기에 `update`를 넣지 않는다).

### 6. 소속 변경은 **분류 전용 경로**이며 `updatedAt`을 보존한다

일괄 지정은 자산 서비스를 거치지 않고 `topic-assignment.service.ts` 1파일이 `topicId`만 쓴다(`updatedAt` 값별로 묶은 `updateMany` · 부분 성공 없음 · 감사 요약 1건). 단건 수정도 `topicId`만 바뀌면 `updatedAt`을 보존한다. `rankNodes`가 `updatedAt`으로 동점을 가르므로 분류가 답을 바꾸면 안 된다.

### 7. 권한·감사·로그

신규 권한 0(편집 `dialogue:write` · 분리 `dialogue:read` AND `chatbot:write`) · 신규 역할 0 · `AuditTargetType` + `Topic`(20 → 21) · `AuditAction` 추가 0(분리 = 기존 `COPY`, 일괄 지정 = `UPDATE` summary 1건) · `ConversationLog.topicId`(답한 자산의 **당시** 토픽, FK·인덱스 없음, `record()` 1곳, 불변 — ADR-0033 `groupId` 선례) · 영구삭제 사전검사 13 → 14(`토픽`) · `@Public()` 7 유지.

### 8. 이번에 하지 않는 것

공유 토픽 패키지(여러 챗봇이 한 토픽을 참조) · 토픽 우선 라우팅(엔진 단계 추가) · 토픽 계층 · 다대다 소속 · 토픽 단위 권한 · 토픽 활성화 예약 · 토픽 스냅샷 · 병합 구현(충돌 규칙만 설계서 §10에 고정) · 분리 비동기화.

## 근거

- **"챗봇 = 버전·배포·검증·권한 스코프 단위"는 선행 13개 그룹의 전제다.** 토픽을 챗봇 밖에 두면(공유 패키지) 한 토픽 편집이 여러 운영 챗봇을 동시에 바꾸고, 스냅샷 복원이 다른 챗봇을 바꾸며, 자산 소유·유일성·임베딩·통계·감사 스코프가 전부 바뀐다. 챗봇 안 분류는 컬럼 1개 + 테이블 1개로 원문 요소 ①(분리 구축)을 충족하고, 나머지 요소(개별 챗봇화·병합)의 **단위**를 먼저 만든다.
- **필터 위치는 "모든 소비자가 지나는 1곳"이어야 한다.** 엔진 인자는 엔진 불가침을 깨고, 인덱스 제외는 번들 원본과 어긋나며(색인 미주입 경로), 자산별 `enabled` 일괄 끄기는 의도·키워드에 컬럼이 없고 사용자 설정값을 덮어써 되켤 때 원래 값을 잃는다. 번들 조립 필터는 엔진 입력 모양을 바꾸지 않고 6개 소비자와 의미 매칭을 한꺼번에 맞춘다.
- **막는 것보다 보이게 하는 편이 운영에 맞다.** 공용 의도("인사")·공용 키워드를 토픽마다 복제할 수 없고, ROCHA 도식의 "본 그래프 → 토픽 상자 위임"도 경계를 넘는 이동이다. 기존 자산을 토픽으로 나누는 순간 저장이 막힌 노드가 대량으로 생기는 설계는 도입 자체를 막는다.
- **해시 불변은 "기존 직렬화 규칙에 선택 필드를 태우는 것"으로 얻는다.** `undefined` 키 생략은 No.27이 이미 쓴 규칙이라 새 코드가 필요 없다. 스키마 버전을 올리면 업캐스터·픽스처·예약 해시 전부에 파급이 있다.
- **"분리 = 복사"는 운영 사고를 막는다.** 옮기기는 원본 운영 챗봇에서 자산을 즉시 없앤다. 복사 후 원본 토픽 비활성화는 관리자가 별도 동작(각각 감사)으로 한다.
- **깊은 복사·환경 승격·병합은 같은 부품이 다른 선택·정책을 받는 문제다.** ADR-0031 §8이 예고한 "캡처 + ID 재매핑"을 이번에 3단계 인터페이스로 고정하면 No.40은 "기존 대상과의 차이 적용"만, 병합은 "이름 충돌 정책 + 합치기 적용기"만 더하면 된다.
- **UUID 잎 규칙은 K-2(참조 목록 두 벌)의 원인을 새 코드에서 제거한다.** 재작성은 어차피 "모든 참조 위치"를 알아야 하는데, 타입 목록으로 만들면 세 번째 목록이 된다. 잎 규칙은 새 참조 종류가 생겨도 갱신이 필요 없다.

## 대안과 트레이드오프

| 대안 | 기각 사유 |
|---|---|
| 챗봇 밖 공유 토픽(해석 b) | 자산 소유·유일성·스냅샷·임베딩·통계·감사 스코프 전면 변경 · 한 편집이 여러 운영 챗봇을 바꿈 — 3차 이후 재검토 |
| 토픽 우선 라우팅(토픽 먼저 고르고 그 안에서 매칭) | 엔진 해석 파이프라인 단계 추가 · 기존 매칭 결과·TC 기준 전면 변경 |
| 엔진 `resolveTurn`에 비활성 토픽 인자 | 엔진 수정 · 의미 매칭을 엔진이 따로 챙겨야 한다 |
| 인덱스(`buildDialogueIndex`)에서만 제외 | 엔진 패키지 수정 · 색인 미주입 경로와 불일치 |
| 토픽 비활성 = 소속 노드·FAQ `enabled=false` 일괄 | 의도·키워드에 `enabled` 없음 · 되켤 때 사용자 설정값 소실 |
| 키워드·컨텍스트·동음이의어까지 제외 | 활성 토픽 노드가 공용 사전을 잃는 교차 파손 |
| 경계 참조 차단 | 공용 자산 복제 강제 · 기존 자산 분류 순간 저장 불가 노드 대량 발생 |
| 참조 대상 비활성 시 출발 자산 자동 비활성 | 연쇄 비활성화 예측 불가 |
| 유일성을 `(chatbotId, topicId, nameNormalized)`로 | 엔진·편집기·가져오기·동음이의어의 "이름 → 자산" 해석 전면 수정 |
| 자산↔토픽 다대다 | "비활성 A와 활성 B에 동시 소속" 판정 모호 |
| 스냅샷에 소속 미포함 | 복원이 행을 재생성하면 비활성 토픽 자산이 공통(=운영)으로 몰래 노출 |
| `SNAPSHOT_SCHEMA_VERSION` 2 + 업캐스터 | 선택 필드라 불필요 · 예약 해시·픽스처 파급 |
| 복원 시 없는 토픽을 이름 없는 자리표시 토픽으로 재생성(해시 보존) | PM 결정(공통 + 경고)과 다름 · 이름 없는 토픽이 쌓임 |
| 복원 시 없는 토픽 → 공통, 사후 검증은 원래 해시 | 그런 복원이 전부 롤백 |
| 분리 = 옮기기 | 원본 운영 챗봇 자산 즉시 소실 |
| 복원 적재기(ID 보존)를 분리에 재사용 | 적재 규칙 정반대(ADR-0031 §8) |
| `copy()`를 깊은 복사로 확장 | 기존 계약(프로필만) 파괴 · 선택·폐포·상한이 필요한 경로를 단순 복사 경로에 섞음 |
| 타입별 재매핑 경로 목록 | K-2와 같은 "목록 누락" 위험의 세 번째 사본 · 실제로 API 슬롯 바인딩이 누락돼 있었다 |
| 폐포 밖 참조를 끊어서 복사(아웃풋 조용히 삭제) | 저장 검증 위반 노드 또는 몰래 사라진 아웃풋 · 시스템 노드 TRIM만 예외로 두고 전수 표시 |
| 시작·폴백 노드 연결을 항상 따라감 | 시작 노드 허브가 거의 모든 분리를 전체 복사로 만든다(선택지로만 남김) |
| 새 ID 무작위 발급 · 타임스탬프 `now` | 분리본의 동점 승자가 원본과 달라질 수 있다 |
| 분리 비동기 Job | 상한 이하 규모는 수 초 · Job 테이블·폴링·부분 실패 상태가 생긴다(트리거로 남김) |
| 토픽 활성 전환에 `BEFORE_*` 스냅샷 | 자산 내용 불변 · 토글이 가역 |
| 분리·일괄 지정에 새 `AuditAction` | 기존 `COPY`·`UPDATE` summary로 충분 |
| 영향 미리보기 서버 증빙(해시 바인딩) | 오류 코드·계약 증가 · 토글은 가역 |

## 감수하는 비용

1. **자산 6테이블 재정의 마이그레이션** — SQLite에서 FK 컬럼 추가는 테이블 재생성이다. API 중지 상태에서 실행하고 소요 시간을 실측·기록한다(대화 로그 테이블은 `ADD COLUMN`만).
2. **이름 유일성이 챗봇 단위로 남는다** — 부서 간 같은 이름 불가. 오류 문구에 상대 토픽을 표시하고 접두어 운영 지침으로 완화한다.
3. **다중 인스턴스 60초 수렴** — 기존 자산 편집과 같은 한계.
4. **분리 동안 SQLite 전체 쓰기 대기** — 상한·청크 적재·실측. Postgres 전환 시 완화.
5. **자산 쓰기 봉인(ADR-0025 S-1) 허용 파일 3 → 5** — 일괄 지정(`topicId`만 · 정적 검사로 키 제한)과 분리 적재기(생성 전용 · 새 챗봇에만). 둘 다 "승인 없는 예문 주입" 경로가 아니다.
6. **시스템 노드 TRIM이 새 챗봇의 시작 노드 내용을 줄인다** — 전수 표시 · FOLLOW 선택 가능 · 원본 불변.
7. **토픽 도입 전 스냅샷 복원은 모든 자산을 공통으로 되돌린다** — P-7의 귀결. `TOPIC_EXPOSURE_CHANGE` 경고로 알린다.
8. **UUID 잎 규칙의 이론적 오탐** — 자유 텍스트 잎 전체가 우연히 원본 자산 UUID와 같을 때만. 무시할 수 있다.

## 재검토 트리거

- **같은 토픽을 3개 이상 챗봇이 지속 동기화해야 하는 요구 확정** → 공유 토픽 패키지(해석 b)를 새 ADR로(No.40 이후).

- **분리 상한 초과 요청 반복** → 분리 비동기 Job(적재기 인터페이스 그대로, 실행만 큐로).
- **병합(2차) 착수** → 설계서 §10 규칙 + 이 ADR §5 ①②③ + 합치기 적용기를 새 ADR로. `BEFORE_MERGE` 트리거 추가.

- **엔진을 닫힌 목록으로 수정하는 다음 그룹이 `getOutgoingNodeRefs()`에 위치 정보를 더할 때** → 저장 검증의 노드 참조 수집을 그 함수로 단일화(K-2 해소, 동등성 시험을 단위 시험으로 대체).
- **토픽 단위 권한 요구 확정**(No.45) → 권한 경계 후보로서의 토픽 재검토.
- **`ConversationLog.topicId` 적재 후 한 분기 이상 데이터 축적 + 토픽별 통계 요구 확정** → 통계 화면·인덱스.
