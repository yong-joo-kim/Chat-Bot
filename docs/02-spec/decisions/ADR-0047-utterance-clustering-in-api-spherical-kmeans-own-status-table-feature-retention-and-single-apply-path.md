## 맥락

카탈로그 No.21은 "STT/TA 비정형 발화 데이터를 딥러닝 기반 토픽 클러스터링(재학습 데이터 정제용) · GPU 7"이다. 사용자는 2026-09-30에 **입력 = 이미 글자로 된 발화 파일(엑셀/CSV)**, **규모 A = 업로드 → 마스킹 → 임베딩(기존 `/embed`) → 군집 → 대표 키워드 → 챗봇 대조 → 조회·다운로드 + 관리자가 고른 발화만 확인 화면을 거쳐 의도 예문 반영(자동 반영 없음)**, **LLM = 묶음 이름 제안 보조만(기본 꺼짐)**, **보존 = 마스킹본만 · 원본 파일 0 · 90일 자동 삭제(설정) · 수동 삭제**, **합격 = 묶음 품질은 개발 PC에서 기존 의도 예문을 정답표로 판정 · 속도·LLM은 운영 실측**을 확정했다.

ADR-0024와 ADR-0027은 No.21 착수 시 "학습 기능·Job Queue·GPU 복귀"와 "학습 위치(`apps/api` CPU vs ml-worker)"를 **다시 판정**하라고 남겼다. 결정할 것은 여덟 가지다.

1. 군집 계산을 어디서 하나(API vs ml-worker).
2. 어떤 알고리즘인가(HDBSCAN 가능 여부 포함).
3. 작업 상태를 어디에 두나(`TrainingJob` kind 추가 vs 자체 테이블).
4. 동시 실행을 어떻게 1건으로 막나(큐는 직렬화하지 않는다).
5. "기본 90일 자동 삭제"를 No.45 보존 체계와 어떻게 맞추나.
6. 결과 → 자산(의도 예문) 경로를 어떻게 봉인하나.
7. LLM 이름 제안을 어디에 붙이나.
8. 두 번째 LLM 소비자가 생긴 것으로 `packages/llm-provider` 승격 트리거가 발동하나.

## 결정

### 1. 벡터화는 ml-worker `/embed`, 군집·키워드·대조는 `apps/api` 비동기 작업 안에서 CPU로 한다

- **모델 학습(파인튜닝)은 0이다.** 군집은 이번 요청의 벡터 위에서 끝나는 일시 수치 계산이고 중심점도 저장하지 않는다. ml-worker의 역할("ML 추론 서비스 — 임베딩 + 선택적 생성")과 `/embed`·`/health` 계약은 불변이다.
- 벡터는 챗봇 대조(의미 매칭 점수)에 **어차피 API 메모리에 있어야 한다**(5,000 × 1,024 float32 ≈ 20MB). ml-worker로 군집을 보내면 같은 20MB를 한 번 더 왕복시키고(base64 ≈ 27MB), 대화 `/embed`와 같은 프로세스의 스레드 풀·BLAS 스레드를 수 초씩 점유해 대화 임베딩 예산(300ms)을 직접 위협한다. 얻는 것은 속도뿐인데 이 기능의 병목은 임베딩이다.
- API에서는 이벤트 루프를 **조각(256점)마다 양보**한다(로지스틱 회귀·TC 실행 선례). 알고리즘은 순수 TS 함수 1곳(교체 지점)이며 **품질 측정 도구가 같은 함수를 호출**한다 — 측정한 것 = 배포되는 것.
- 개발명세서 §1이 "군집분석"을 ml-worker 예시에 적은 문장은 카탈로그 GPU 7 전제였다 — **GPU 등급인 부분(임베딩 추론)만 ml-worker**라는 원칙과 일치하도록 정정한다.

### 2. 알고리즘 = 구면 k-평균(코사인 · k-means++ · 시드 고정 · 3회 시도) + 작은 묶음 → 미분류

- 원본 조건 "토픽수"가 곧 k다. 계산량 선형·메모리 O(n·d)·쌍 거리 행렬 없음·완전 결정론(시드·입력 정렬·동점 규칙·누산 순서 고정). 결과 행에 `algorithmVersion='skmeans-1'`을 남긴다.
- **HDBSCAN**: ml-worker venv에 `scikit-learn` 1.7.2가 **이미 있다**(`sentence-transformers`의 간접 의존성 · `sklearn.cluster.HDBSCAN` 존재 확인 · `pyproject.toml` 미선언). 그러나 1,024차원 원공간에서 밀도 추정은 약한 경향이 알려져 있어 보통 UMAP 차원 축소가 필요하고, UMAP은 `umap-learn`·`numba`·`llvmlite`·`pynndescent` 새 의존성(폐쇄망 반입 증가)과 ml-worker 배치를 강제한다. "목표 묶음 수"를 맞추려면 병합 단계도 필요하다 → **제품에 넣지 않고** 품질 측정의 선택 기준선(파이썬 스크립트)으로만 비교한다.
- 병합형 계층 군집은 5,000² 거리 행렬(≈100MB)과 O(n² log n) 시간 때문에 기각.

### 3. 작업 상태는 `UtteranceAnalysis`가 스스로 소유한다 — `TrainingJob` kind를 추가하지 않는다

`TrainingJobQueue`는 재사용하되 상태 기록은 `AsyncJobStatusSink`의 **세 번째 구현**이다(ADR-0027 갱신① "Training이 아닌 작업은 `TrainingJob`에 넣지 않는다" 선례 · `TestRun`과 같은 구조). 결과와 상태가 한 행에 있어야 **"성공 전이 = 결과 쓰기"를 한 트랜잭션**으로 묶을 수 있다 — 결과가 반쯤 저장된 성공이 구조적으로 없다(부분 결과 저장 0). 저장은 3테이블(분석·묶음·발화)이며 문장은 금지어·PII 마스킹본만(브랜드 타입으로 강제).

### 4. 동시 실행 = 서버 전체 1건, nullable 유일 컬럼 `activeLock`으로 막는다

큐는 직렬화하지 않는다(fire-and-forget). QUEUED·RUNNING 동안 `activeLock='ACTIVE'`, 종결 시 `null` — `@unique`는 NULL을 여러 개 허용하므로 **Prisma 스키마로 표현되는 전역 1건 제약**이 된다. 원시 부분 유니크 인덱스(`test_runs` 선례)는 `migrate dev` diff가 지울 위험이 있어 쓰지 않는다(No.41 `dedupeKey` 선례 · 원시 부분 인덱스 4개 불변). 상한을 설정값으로 두지 않는다 — 두 번째 동시 분석은 대화 임베딩 경합만 두 배로 만든다.

### 5. 보존 = 기능 설정 일수(기본 90) + 생성 시 `expiresAt` 고정 + No.45 파기 잡에 단계 1개

No.45 보존 종류의 전역 값 규약은 "키 없음 = 무기한"이다. "기본 90일"을 그 틀에 넣으면 한 종류만 기본값 의미가 달라져 정책 화면·미리보기·단축 유예·지도가 종류마다 다른 규칙을 갖게 된다. 그래서 **보존 종류를 늘리지 않고**, 일수는 `UTTERANCE_ANALYSIS_RETENTION_DAYS`(생성 시 고정 — 일수를 줄여도 기존 분석이 예고 없이 사라지지 않는다)로 두되 **실행은 기존 파기 잡**(같은 KST 창·임대·요약 이력·`PURGE` 감사·secure_delete)에 태운다. 분석이 없는 설치의 파기 결과·감사는 바이트 동일하다(삭제 0이면 키를 만들지 않는다). 수동 삭제·챗봇 영구삭제 동반 삭제(27 → 30테이블)도 같은 순서(발화 → 묶음 → 분석)다. 반영된 의도 예문은 자산이라 삭제되지 않는다.

### 6. 결과 → 자산은 `apply/utterance-apply.service.ts` 1파일 — 미리보기 → 확정, `applyLearning()` 요청당 1회

- 관리자가 고른 발화(≤50)만. 미리보기(DB 변경 0)로 들어갈 것·빠질 것(이미 반영·금지어·200자 초과·대상 의도 중복·**다른 의도에 이미 있음**·의도당 500 초과)을 보여 주고, 확정 때 계획을 다시 계산한다.
- 자동 스냅샷(`BEFORE_UTTERANCE_APPLY` — fail-open) → 발화마다 `IntentsService.applyLearningExample()`(번들 무효화 연기) → 성공 1건 이상이면 `LearningApplyService.applyLearning({ reason: 'UTTERANCE_ANALYSIS_APPLY' })` **1회**(ADR-0018 K-1~K-6). 원자성은 증강 승인과 같이 **건별 부분 성공 + 명시**다.
- 봉인: `IntentsService` 주입·호출 = 이 파일만 · 러너(`*job.runner.ts`)에 `IntentsService` 심볼 0 · 모듈이 키워드·FAQ·노드·토픽·미응답 큐를 쓰는 경로 0 · 스케줄러 0(자동 반영 코드가 작성돼도 봉인 검사가 잡는다).
- 환경 모드 챗봇은 **초안에만** 들어간다(운영은 기존 승격 절차). 새 의도는 공통(토픽 없음)으로 만든다.

### 7. 이름 제안은 ml-worker 생성 프로파일의 선택 경로 `POST /cluster-label` — API는 `AUGMENT_LOCAL` 출구로 부른다

- 기본 꺼짐(`UTTERANCE_ANALYSIS_NAME_SUGGEST_ENABLED=false`). 켜도 실패·지연·잘림·영문·개인정보 모양은 전부 "이름 없음(키워드만)"으로 수렴하고 분석은 완료다.
- 생성 백엔드(transformers·ollama·vllm)·주소 통제·시간 제한은 **No.37 그대로 재사용**한다(ADR-0046). 모델·백엔드는 ml-worker 생성 프로세스 설정이며 API·코드에 모델 이름 0. `/augment` 계약·`build_prompt`는 불변이고 이름 전용 프롬프트·파서를 별도로 둔다(입력은 JSON 데이터 블록으로만).
- 보내는 것 = 묶음별 대표 키워드 + 마스킹 대표 발화 ≤5. 새 출구 클래스 0 — 호출 파일을 `AUGMENT_LOCAL` 레지스트리에 추가하고 `fetch` 전 가드. 거버넌스 모드에서 이름 제안을 켜면 그 호스트가 허용 목록에 있어야 기동한다. 외부 LLM API(cloud)로 발화를 보내는 구현은 두지 않는다.

### 8. `packages/llm-provider` 승격 트리거는 발동했으나 승격하지 않는다

ADR-0026 §6·ADR-0046의 트리거 "LLM 호출 소비자 2곳"은 문자 그대로 충족된다(증강 + 이름 제안). 그러나 두 소비자는 **입출력 계약이 다르고**(예문 N개 생성 vs 이름 1개) **배포 형태 요구도 다르다**(증강 = rule·gemini·local / 이름 = local만 · cloud 금지). 공통으로 올릴 수 있는 것이 "ml-worker 생성 프로세스로 HTTP를 보낸다"뿐이라 패키지는 빈 추상화가 된다(`packages/pii-mask`는 **같은 함수**를 두 곳이 써서 승격했다). → 이름 제안 포트(`ClusterNameSuggester` — local·mock)를 **Nest·Prisma 무의존 파일**로 두어 나중에 파일 이동만으로 승격되게 하고, 트리거를 **"같은 생성 연산(같은 계약)을 쓰는 두 번째 소비자, 또는 cloud 구현이 필요한 두 번째 소비자"** 로 정밀화한다.

## 근거

- **입력이 있는 곳에서 계산한다**(ADR-0027 근거 1의 재적용). ADR-0024가 임베딩을 분리한 이유는 모델 런타임이 Python이어야 해서였지 분리 자체가 목적이 아니었다. 군집의 입력은 이미 API에 있고, 필요한 런타임(수치 연산)은 TS로 충분하다.
- **대화 경로 보호는 구조로.** 대화 임베딩 프로세스에 무거운 계산을 넣지 않는 것이 가장 싼 보호다. 남는 경합(분석 임베딩 호출)은 서버 1건·배치 16·적응형 양보(ml-worker 시간 최대 절반)로 줄이고, 운영 장비 부하 게이트로 확인한다.
- **"제안 ≠ 자산"은 이 제품의 확립된 봉인이다**(ADR-0025). 묶음은 의도 정의가 아니다 — 자산 경로는 관리자 확인 1곳뿐이다.
- **보존은 사람이 예측할 수 있어야 한다.** 행마다 만료일이 고정돼 있으면 화면이 정확히 말하고, 설정 변경이 과거 분석을 한꺼번에 지우지 않는다. 실행 인프라는 새로 만들지 않는다.
- **트리거는 "다시 생각하라"는 뜻이다**(ADR-0024·0027의 해석). 항목별로 판정한 결과: 학습 위치 = API(군집) / ml-worker(임베딩) · `TrainingJob` 확장 없음 · GPU 7 → 5 · llm-provider 미승격.

## 대안과 트레이드오프

| 대안 | 기각 사유 |
|---|---|
| **ml-worker 임베딩 프로세스에 `/cluster`**(scikit-learn) | 대화 `/embed`와 같은 프로세스·스레드 풀·BLAS 스레드 경합(대화 300ms 예산 직접 위협) · 20MB 벡터 재왕복 · 선언되지 않은 의존성의 버전 통제 필요 · API 통합 시험에 실제 알고리즘이 안 들어온다 |
| **ml-worker 별도 분석 프로세스(새 역할)** | 운영 프로세스·포트·설치 문서가 늘고, 같은 장비면 CPU는 여전히 공유다. 이득(속도)이 병목이 아니다 |
| **HDBSCAN + UMAP** | 새 의존성 4종(폐쇄망 반입) · ml-worker 배치 강제 · "목표 묶음 수"와 어긋남. 측정 기준선으로만 비교 |
| **병합형 계층 군집** | 거리 행렬 ≈100MB · O(n² log n) |
| **`TrainingJob`에 kind 추가** | ADR-0027 갱신① 선례 위반 · 결과와 상태가 두 테이블로 갈라져 "성공 = 결과 있음" 원자성이 깨진다 |
| **원시 부분 유니크 인덱스로 동시 실행 제한** | `migrate dev` diff가 지울 수 있다(기존 4개가 이미 주의 대상) · nullable 유일로 충분 |
| **`RetentionTargetKind`에 종류 추가** | "키 없음 = 무기한" 규약에 한 종류만 기본 90일 예외를 만든다 · 보존 정책 화면·미리보기·유예·지도 전부 분기 |
| **기능 전용 정리 루프(`PollingLoop` 신설)** | 백그라운드 루프가 하나 더 늘고(시험 격리 설정 추가) 파기 이력·감사가 No.45와 따로 논다 |
| **`TestRunExecutor` 클래스 재사용** | `TestCase`·`TestRun`·다중 턴·오버레이·목·RAG에 결합 · `runSide()` 비공개 — 검증 모듈 수정(회귀 표면). 규약·부품 재사용으로 충분 |
| **반영 전체 롤백(트랜잭션)** | `applyLearningExample()`에 트랜잭션 인자를 뚫어야 하고 감사 체인 트랜잭션과 중첩된다 · 자동 스냅샷이 되돌리기 안전망 |
| **"다른 의도에 이미 있음"을 경고로만**(기존 의도 서비스 동작) | 외부 대량 문장이 의도 경계를 흐린다 — 이 경로는 제외로 강화 |
| **이름 제안을 `/augment`로** | 계약이 "예문 N개 생성"이라 의미가 다르고 ADR-0046 봉인(`build_prompt` 불변) 위반 |
| **이름 제안을 API가 Ollama/vLLM에 직접** | ADR-0046 §2(생성 백엔드는 ml-worker 안에서만) 위반 · 출구·주소 통제 두 벌 |
| **`packages/llm-provider` 지금 승격** | 공유 계약이 없는 두 소비자 — 빈 추상화 |
| **분석 전용 임베딩 주소(두 번째 ml-worker)를 지금 지원** | 출구 호스트·거버넌스 기동 검사·데이터 지도가 늘어난다 · 필요성은 부하 게이트가 판단 — 교체 지점 1곳만 둔다 |

**감수하는 비용**

1. **JS 수치 계산은 느리다** — 최악 수십 초(추정). 10분 목표의 지배 요인은 아니다.
2. **밀도 기반 외톨이 탐지가 없다** — 미분류는 "작은 묶음"으로만 생긴다(원본 "토픽 −1"보다 적을 수 있다).
3. **보존 일수를 콘솔 보존 정책 화면에서 바꿀 수 없다**(환경변수).
4. **분석 임베딩은 대화와 같은 ml-worker를 쓴다** — 양보 규칙의 효과는 운영 부하 게이트 전까지 미확인.
5. **정규식 마스킹은 사람 이름·주소를 놓친다** — 화면 안내 · 보존 기한 · secure_delete로 줄인다.

## 재검토 트리거

- **품질 측정에서 밀도 기반이 k-평균보다 뚜렷이 우수** → ml-worker 두 번째 군집 구현 + 의존성 선언(이 ADR §1·§2를 대체하는 새 ADR).
- **부하 게이트에서 대화 임베딩 P95 초과·회로 개방** → 양보 강화 → 분석 전용 임베딩 프로세스.
- **보존 일수의 콘솔 편집 요구** → No.45 보존 정책 편입(기본값 의미 확장).
- **동시 분석 2건 이상 요구 · 다중 인스턴스 전환** → 잠금 슬롯화 · 임대 방식 고아 정리.
- **같은 계약의 두 번째 생성 소비자 또는 cloud 구현이 필요한 소비자** → `packages/llm-provider` 승격.
- **규모 B(내부 대화 기록 입력) 요청** → 보존 연동·원천 참조 방식 설계(원본 "통계 > 군집분석" 대체).
