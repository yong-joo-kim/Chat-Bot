# ADR-0021 — 매칭 임계값 3구간 체계와 챗봇별 설정 저장 방식

- **상태**: 채택 (Accepted)
- **일자**: 2026-09-22
- **결정자**: system-architect
- **관련**: `docs/requirements/nlu-rag-answering.md` **J-4**, FR-N1-12/13/25~30, FR-N3-2/5, NFR-M2, AC-N1-4/7/12/18/19, EX-N1-6/10/11 / ADR-0004(쓰기 주체·파생 불가 기준) / ADR-0016(감사 스냅샷)
- **영향 범위**: `apps/api/prisma/schema.prisma`(`ChatbotAnswerSetting` 신설), `apps/api/src/answer-settings/*`, `packages/dialogue-engine/src/semantic.ts`, `packages/shared-types/src/answering.ts`
- **세부 설계**: `docs/02-spec/nlu-rag-answering-설계.md` §6.2·§8.8

## 맥락

의미 유사도는 0~1 사이의 연속값이다. "얼마 이상이면 답하고, 얼마 미만이면 포기하는가"를 정해야 한다.

단일 임계값(예: 0.75 이상이면 확정)에는 구조적 문제가 있다.

- **애매한 구간을 강제로 한쪽에 몰아넣는다.** 0.74는 폴백, 0.76은 확정인데 두 값의 실제 차이는 없다.
- **잘못 확정하는 비용이 되묻는 비용보다 크다.** 오답은 신뢰를 깨고 관리자가 원인을 추적하기 어렵다. 되묻기는 1턴을 더 쓸 뿐이다.
- **1·2위가 붙어 있을 때를 다루지 못한다.** `0.86 / 0.84`는 top1이 높지만 "둘 중 뭘 물은 건지" 시스템이 모르는 상태다.

또한 **임계값의 절대값은 임베딩 모델에 종속**된다. 모델이 바뀌면 0.80의 의미가 달라진다.

## 결정

### 1. 3구간 + 격차 조건

| 구간 | 조건(`s₁`=top1, `s₂`=top2) | 동작 | 기본값 |
|---|---|---|---|
| **확정** | `s₁ ≥ accept` **그리고** `s₁ − s₂ ≥ margin` | 그 FAQ/의도로 확정 | `accept = 0.80` |
| **모호** | `low ≤ s₁ < accept`, **또는** `s₁ ≥ accept`인데 격차 미달 | **후보 되묻기**(최대 3건) | `margin = 0.05` |
| **실패** | `s₁ < low`(후보 0건 포함) | 2단계 이관, 없으면 기존 폴백 | `low = 0.60` |

- 후보가 **1건뿐이면 되묻지 않고 확정**한다 — 선택지가 하나인 질문은 되묻는 비용이 이득보다 크다(FR-N1-13).
- 후보는 **최대 3건**이며 동점·근소 차이여도 4건 이상 제시하지 않는다(EX-N1-11).
- 정규화 길이 2자 미만은 **의미 매칭을 시도하지 않는다**(정확일치만) — 단문은 임베딩 품질이 낮다(EX-N1-6).

### 2. 판정 함수는 **엔진 패키지에 1개**

`packages/dialogue-engine/src/semantic.ts`의 `judgeBand(ranked, thresholds)` 순수 함수를 **엔진 · 설정 미리보기(FR-N3-5) · 시뮬레이터**가 공유한다(NFR-M2, AC-N3-9).

복제하면 "미리보기에서는 확정이라고 했는데 실제 대화에서는 되묻는" 불일치가 생긴다. 이 불일치는 관리자가 임계값을 조정할 근거 자체를 무너뜨린다.

### 3. 코드 상수가 아니라 **챗봇별 설정값**이다

- 저장소는 **`ChatbotAnswerSetting` 1:1 테이블**이다.
- 서버 검증: `0.0 ≤ low < accept ≤ 1.0`, `0 ≤ margin ≤ 0.5`. 위반 시 `400 INVALID_THRESHOLD`(AC-N1-18).
- 변경은 **저장 즉시 다음 턴부터** 적용된다(설정 캐시 무효화). "적용 중" 상태를 만들지 않는다.
- 변경은 **감사 대상**이다 — `Chatbot` `UPDATE` 1건, 전/후 값을 화이트리스트 스냅샷에 담되 **대화 문장은 담지 않는다**(AC-N1-19).
- 변경은 **해당 챗봇에만** 영향을 준다. **외부 RAG 서버의 전역 설정(`POST /api/rag/settings`)은 호출하지 않는다** — 그것은 서버 전역이라 다른 이용자의 답변까지 바꾼다(`API_RAG.md` §7).

### 4. 저장 형태는 JSON 컬럼이 아니라 **1:1 테이블**

| 기준 | JSON 컬럼(`Chatbot.skin` 방식) | 1:1 테이블(채택) |
|---|---|---|
| 필드 수 | 12개 | — |
| 필드별 검증 규칙 | 상호 제약 5종(`low<accept`, `subcategory⇒category`, `ragEnabled⇒company`, 타임아웃 하한, 임계값 범위) | 스키마 + 서비스 검증으로 자연히 표현 |
| 감사 스냅샷 | JSON 문자열 통째 비교 → 무엇이 바뀌었는지 불명확 | 필드 단위 화이트리스트 스냅샷 |
| 부분 수정 | 파싱 실패 시 전 설정 유실 위험 | 컬럼 단위 |

`Chatbot.skin`은 **표시용 값 묶음**이라 JSON이 맞았다. 이 설정은 **동작을 바꾸는 규칙**이며 성격이 다르다.

### 5. 기본값은 **모델 종속 잠정값**이며 보정 절차를 산출물로 남긴다

- `modelId → 기본 임계값` 매핑을 **코드 상수 1곳**(`shared-types/answering.ts`)에 둔다(FR-N1-26). 모델이 바뀌면 기본값도 함께 바뀐다.
- 골든셋 **100문항**(매칭 60 / 되묻기 20 / 미매칭 20)으로 `τ` 스윕을 돌려 **정밀도·재현율·오탐률 표**를 만들고 최종 기본값을 그 표로 정당화한다(AC-N1-12). **이 보고서가 나오기 전의 0.80/0.60/0.05는 잠정값임을 문서·화면 양쪽에 명시**한다.
- **행이 없는 챗봇은 전부 기본값이며 두 단계가 비활성**이다. 즉 보정이 끝나기 전에 잘못된 임계값이 운영에 적용될 경로가 없다.

## 결과

**좋아지는 것**
- 애매한 구간이 **오답이 아니라 질문**으로 표현된다. 되묻기 턴은 `isAnswered=true`이므로 응답률 통계도 사실과 맞는다(FR-N1-14).
- `margin` 조건이 "둘 다 그럴듯한" 상황을 잡아낸다 — 단일 임계값으로는 불가능했던 판정이다(AC-N1-7).
- 임계값이 챗봇별이라 **도메인마다 다른 문장 분포**에 맞출 수 있다.

**나빠지는 것 / 감수하는 것**
- 조정할 손잡이가 3개로 늘어난다. 관리자가 직관적으로 이해하기 어려우므로 **3구간 시각화 + 미리보기**를 UI 요구사항으로 못 박았다(FR-N3-5, ui-designer 인계).
- 되묻기가 잦으면 사용자 경험이 나빠진다. `accept`를 낮추면 오답이, 높이면 되묻기가 늘어나는 **교환 관계를 관리자가 직접 지게 된다** — 그래서 골든셋 보정표가 필수 산출물이다.
- 테이블이 하나 늘어난다. 다만 백필이 없고 행이 없어도 동작하므로 마이그레이션 비용은 사실상 0이다.

## 재검토 트리거

- 골든셋 보정에서 3구간으로도 정밀도가 목표에 못 미칠 때 → 리랭킹 도입(구간 체계 재설계 필요).
- 되묻기 수락률이 낮게 관측될 때(사용자가 후보 버튼을 거의 안 누름) → `margin` 조건 또는 되묻기 표현 방식 재검토.
- 챗봇 수가 많아져 임계값을 개별 관리하기 어려워질 때 → 그룹 단위 상속 도입 검토.
