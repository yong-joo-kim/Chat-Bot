개발명세서 §6-2는 "ml-worker/Provider 추상화가 필요해지는 확장기능(16번~) 착수 시점에 결정"이라고 유보했고, §6-4는 Postgres+pgvector/Redis/ml-worker/docker-compose를 같은 시점으로 미뤘다. **이번 그룹이 그 시점**이다.

## 결정

### 1. `apps/ml-worker`를 **추론 전용 임베딩 서비스**로 신설한다

- **학습·파인튜닝은 포함하지 않는다.** 그것은 No.16(DLE 증강학습)·No.18의 학습 부분이며, ADR-0018이 정한 인계 지점(`LearningApplyService.applyLearning()`)을 이번에도 **교체하지 않는다**.
- 제공하는 것은 HTTP 2개뿐이다.

| 메서드 | 경로 | 계약 |
|---|---|---|
| `POST` | `/embed` | `{ texts: string[], kind: 'QUERY'\|'PASSAGE' }` → `{ modelId, dimension, vectors }` (**L2 정규화 완료**) |
| `GET` | `/health` | `{ status, modelId, dimension, device, warmedUp }` |

- **`kind`는 비대칭 인코딩 대비**다. 프리픽스 규칙(`query:`/`passage:` 등)이 필요한 모델이든 아니든 **`apps/api`는 그 규칙을 알지 않는다** — 모델 교체가 API 코드를 건드리지 않게 하는 경계다.
- **L2 정규화는 ml-worker의 책임**이다. `apps/api`는 내적 = 코사인이라고 가정하고 다시 판단하지 않는다.

> ⚠ **2026-09-22b**: "추론 전용"의 의미가 **§갱신 1**에서 정밀화됐고, HTTP 계약에 **선택적 생성 엔드포인트가 추가**됐다(`/embed`·`/health` 계약 자체는 무변경). 아래 §갱신을 함께 읽을 것.

### 2. `TrainingJob`·Redis·BullMQ는 **계속 도입하지 않는다**(§6-4 유지)

- 재색인은 `apps/api` 안의 **단일 인스턴스 in-process 큐**(`ReindexQueueService`)로 처리한다. 챗봇당 동시 1건, 배치 64건, 배치 간 양보.
- 근거는 ADR-0018과 같다 — **쓰기 주체가 없는 인프라를 미리 만들지 않는다.** 추론 호출은 300ms 예산의 동기 요청이라 큐에 넣을 이유가 없고, 재색인은 하루에 몇 번 일어나는 배치다.
- 다중 인스턴스 전환 시 교체 지점은 `ReindexQueueService` 1곳이다.
- **`TrainingJob` 테이블은 이번에도 만들지 않는다.**

> ⚠ **2026-09-22b 갱신**: `TrainingJob`은 **학습 고도화 그룹에서 도입됐다**(쓰기 주체가 생겼다 — ADR-0027 §4). **Redis/BullMQ는 여전히 도입하지 않는다.** 아래 §갱신 2.

### 3. 런타임은 **Python 3.11 + FastAPI**다. Node ONNX 단독 구성은 기각

| 안 | 판단 |
|---|---|
| **Python + FastAPI + sentence-transformers/FlagEmbedding** (채택) | 한국어 임베딩 모델의 1차 배포 형태가 거의 전부 PyTorch/HF다. **"최고 성능"을 목표로 두는 순간 모델 교체 자유도가 런타임 선택을 지배한다** |
| Node + onnxruntime-node 단독 | 후보군이 "ONNX 변환본이 이미 있고 품질이 검증된 모델"로 좁아진다 — **P-1과 정면 충돌**한다. (ONNX는 채택 후보 모델을 고정한 뒤 **최적화 수단**으로 다시 쓴다) |
| 외부 임베딩 API(클라우드) | 구축형에서 쓸 수 없다. 단 **`EmbeddingProvider` 포트로 구독형 교체 경로는 열어 둔다** |

**모노레포에 Python 프로세스가 하나 생기는 비용**은 3가지로 격리한다(ADR-0012가 위젯에 React를 쓰지 않으면서 도구·스크립트 이름을 통일한 것과 같은 방식).

1. **접촉면은 HTTP 2개뿐**이다. 언어가 바뀌어도 `apps/api`는 모른다.
2. `apps/api`는 **`EmbeddingProvider` 포트만** 안다. `MockEmbeddingProvider`(결정론적 벡터)로 **Python 없이 전 테스트가 통과**한다 — 다른 개발자·CI가 Python에 묶이지 않는다.
3. 기동은 `apps/ml-worker/package.json`의 pnpm 스크립트가 venv를 감싼다 — 팀의 명령 체계가 하나로 유지된다.

### 4. 모델은 **한국어 검색 성능 1순위**로 고르고, 골든셋 실측으로 확정한다

후보 3종(한국어 파인튜닝 BGE-M3 계열 1024차원 / 범용 다국어 BGE-M3 / 경량 대조군)을 **5지표**(골든셋 top1 정확도 · 오탐률 · **CPU 1문장 P95** · 재색인 처리량 · 라이선스·크기)로 비교한 표를 남기고 `ml-engineer`가 확정한다. **이 표가 이 그룹에서 가장 먼저 나와야 하는 산출물**이다(임계값 기본값이 여기서 파생되기 때문 — ADR-0021 §5).

**`modelId` 규약**: `<model-name>@<rev>|<prefix-rule>|<norm-rule>`. 임계값은 모델뿐 아니라 **프리픽스 규약·정규화 규약에 종속**되므로 이 셋이 하나라도 바뀌면 `modelId`가 바뀌고 **기존 벡터는 자동 무효**가 된다(AC-N1-11).

### 5. GPU는 **권장이지 필수가 아니다** — No.18 GPU 필요도를 5 → 4로 재산정

카탈로그의 5는 "임베딩 **학습·추론**"을 함께 가정한 값이다. 이번 범위는 ① 학습 없음 ② 추론 전용 ③ 소형 문장 인코더 ④ 챗봇당 수백~수천 문장 ⑤ 벡터 인덱스 없이 메모리 내적이다 — **"경량 ML(CPU 가능)" 구간의 정의에 부합**한다.

**단, 최고 성능 모델은 크다.** CPU 단문 인코딩이 `EMBEDDING_TIMEOUT_MS=300`을 넘기면 저하 모드가 흡수하지만 **그 상태는 의미 매칭이 사실상 꺼진 것**이다. 대응 순서를 고정한다.

1. 워밍업 + 단문 경로 `max_length` 절단(기본 128토큰)
2. ONNX Runtime + int8 동적 양자화(정확도 손실을 골든셋으로 재측정)
3. GPU 할당(`EMBEDDING_DEVICE=cuda`) — 구축형 고객사가 GPU를 가진 경우의 기본 구성
4. 경량 모델로 교체

> **금지**: 예산을 못 지킨다고 `EMBEDDING_TIMEOUT_MS`를 조용히 올려 **공개 대화 500ms(P95) 예산을 깨지 않는다.** 예산 변경은 설계 문서 갱신을 거친다.

### 6. 벡터 저장·탐색은 **DB 직렬화 + 메모리 내적**이다

- `EmbeddingVector.vector`는 **base64(Float32Array little-endian)**. JSON 배열은 1024차원 기준 크기가 2배 이상이고 파싱 비용이 재색인·캐시 워밍에 그대로 붙는다.
- **벡터 인덱스(HNSW/pgvector)를 도입하지 않는다.** 챗봇당 수백~수천 벡터에는 과설계이고, dev DB가 SQLite인 현실과도 맞지 않는다. 재검토 트리거는 **챗봇당 2만 벡터 초과**다.
- 벡터는 **번들 캐시와 같은 수명주기**의 메모리 캐시에 동거하며 무효화 지점을 공유한다 — "FAQ는 최신인데 벡터는 옛것"인 상태가 구조적으로 생기지 않는다.
- 메모리 상한은 항목 수가 아니라 **바이트 기준**(기본 256MB)이며 초과 시 LRU 축출한다.

### 7. `packages/llm-provider`는 **이번에도 만들지 않는다**

2단계의 LLM 추론은 전부 외부 서버가 수행하므로 우리 쪽에 LLM Provider 추상화가 들어갈 자리가 없다. 임베딩 추상화는 `packages/`가 아니라 **`apps/api/src/embedding/`의 포트**로 충분하다(소비자가 `apps/api` 1곳). `infra/`(docker-compose)도 계속 만들지 않는다.

> ⚠ **2026-09-22b**: 학습 고도화 그룹이 LLM(Gemini) 호출을 도입했으나 **소비자가 여전히 1곳**이라 `packages/llm-provider`는 **계속 미생성**이다. 추상화 자체는 `AugmentationProvider` 포트로 제공된다(ADR-0026 §6). 승격 트리거는 **소비자 2곳**이다.

## 결과

**좋아지는 것**
- 1단계가 외부 서버 가용성·레이트리밋·LLM 게이트와 **완전히 분리**된다. RAG 서버가 죽어도 FAQ 응답은 정상이다.
- 모델 교체가 **DI 바인딩 1곳 + `modelId` 문자열**로 끝난다. 구독형에서 외부 임베딩 API로 바꾸는 경로도 같은 지점이다.
- 학습 부하와 대화 처리가 프로세스 분리돼 개발명세서 §5의 가용성 원칙이 실제로 지켜진다.
- ml-worker가 없어도(환경변수 미설정) 시스템은 정상 기동하고 현행 규칙 매칭으로 동작한다.

**나빠지는 것 / 감수하는 것**
- **모노레포에 Python이 들어온다.** 개발 환경 준비 절차가 하나 늘어난다(README + pnpm 스크립트로 완화).
- **모델 파일이 크다**(수백 MB~1GB). 온프레미스 설치 패키지 크기와 초기 기동 시간(모델 로드 + 워밍업)이 늘어난다.
- **CPU 지연이 예산과 충돌할 수 있다**(설계서 R-2). 실측 전까지는 확정할 수 없는 리스크다.
- ml-worker 장애 = 저하 모드 = **부분일치 오탐 복귀**(ADR-0020의 감수 사항과 연결).

## 재검토 트리거

- **No.16(DLE 증강학습)·No.21(군집분석)·No.23(경량 재학습) 착수** → 학습 기능 추가, Job Queue·`TrainingJob` 도입, GPU 필요도 5 복귀. → ⚠ **2026-09-22b: No.16/23에 대해 항목별로 판정 완료. §갱신 3 참조**(No.21은 미판정 — 착수 시 다시 판정한다).
- **챗봇당 2만 벡터 초과** → 벡터 인덱스(pgvector/HNSW) 도입.
- **다중 인스턴스 전환** → `ReindexQueueService`와 벡터 캐시 전략 재검토.
- **음성(STT/TTS)·비전 기능 착수** → ml-worker의 역할이 "임베딩 서비스"를 넘어서므로 내부 구조(단일 프로세스 vs 워커 분리)를 다시 정한다. → ⚠ **2026-09-22b: 생성모델(G3) 수용으로 이 트리거가 조기 발동됐다. §갱신 1-② 참조.**
- **골든셋 실측 결과 CPU P95가 예산을 크게 초과** → §5의 완화 단계를 넘어 모델 등급 자체를 재결정.

## 갱신 (2026-09-22b) — 학습 고도화 그룹(No.16/23)의 항목별 판정 결과

> **성격**: 이 절은 위 §1~§7의 결정을 **전면 개정하지 않는다.** ml-worker 역할 정의의 **범위를 넓히고**, 보류했던 항목 1건(`TrainingJob`)을 **해소하며**, 재검토 트리거 1건(GPU 5 복귀)을 **철회**한다. 근거: `docs/requirements/learning-augmentation.md` **J-7**, FR-L2-35~38 / **ADR-0026**(3-포트 증강 Provider) · **ADR-0027**(분류기·`TrainingJob`).

### 1. "추론 전용"의 의미를 정밀화한다 — **"모델 파인튜닝 없음"**

| 항목 | 갱신 전 | 갱신 후 |
|---|---|---|
| 역할 정의 | **임베딩 추론 서비스** | **ML 추론 서비스** — 임베딩 추론 + **선택적 생성 추론** |
| "추론 전용"의 의미 | 학습 엔드포인트 없음(암묵적으로 "임베딩만") | **모델 파라미터를 갱신하는 파인튜닝을 수행하지 않는다.** 순전파(추론)는 임베딩이든 생성이든 수용한다 |
| HTTP 계약 | `/embed`, `/health` 2개 | 위 2개 **계약 무변경** + **선택적** `POST /augment`, `GET /augment/health`(생성 프로파일이 켜진 경우에만 존재) |
| 부재 시 동작 | ml-worker 없어도 API 정상 기동(의미 매칭만 비활성) | **불변.** 생성 프로파일이 없으면 증강은 G1(규칙)으로 동작한다 |

**① 왜 역할을 넓히는가** — 생성은 **추론이지 학습이 아니다.** 증강 후보 문장 생성은 순전파 1회이며, 이 ADR이 금지한 것("모델 가중치를 바꾸는 일")에 해당하지 않는다. 반대로 역할을 "임베딩"으로 못 박아 두면 **로컬 생성모델을 쓸 수 있는 유일한 자리가 없어진다** — 구축형 고객사가 외부 전송 없이 고품질 증강을 쓸 경로가 사라진다.

**② 실행 프로파일을 도입한다(`ML_WORKER_ROLE=embed|augment|both`, 기본 `embed`)** — 생성모델과 임베딩 모델이 **같은 프로세스·같은 GPU·같은 요청 큐를 공유하면 대화 경로의 `EMBEDDING_TIMEOUT_MS=300` 예산이 관리자 편의 기능에 밀린다.** 운영 기본 구성은 **프로세스 분리**(별도 포트)를 권고하고, `both`는 개발 편의용이며 **대화 성능 예산을 보장하지 않는다**고 명시한다. 위 재검토 트리거 *"ml-worker의 역할이 임베딩 서비스를 넘어서면 내부 구조를 다시 정한다"* 의 조기 발동이다.

**③ 여전히 하지 않는 것** — 모델 파인튜닝 · 학습 엔드포인트(`POST /train/*`) · ml-worker에서의 DB 접근 · `apps/api`가 모델·프롬프트 규칙을 아는 것.

### 2. `TrainingJob`은 **도입한다**. Redis/BullMQ는 **여전히 도입하지 않는다**

§2의 보류 근거는 "쓰기 주체가 없다 / 항상 `SUCCEEDED`인 가짜 행만 쌓인다"였다. 학습 고도화 그룹에서 **쓰기 주체 2종(`AUGMENT`·`CLASSIFIER_TRAIN`)이 실재**하고 **`FAILED`·`PARTIAL`이 실제로 발생**한다(외부 LLM 타임아웃, 생성 0건, 학습 데이터 부족, 서버 재시작 중 중단) → **ADR-0004 기준을 통과했다.** 상세와 스키마는 ADR-0027 §4.

- **큐는 여전히 단일 인스턴스 in-process**다(`TrainingJobQueue` — `ReindexQueueService`와 같은 패턴·같은 교체 규약).
- **분류기 학습은 ml-worker가 아니라 `apps/api` 안에서 CPU로 수행**한다. 학습 입력(저장된 float32 벡터 수 MB)이 이미 그 프로세스의 DB에 있어, 다른 프로세스로 보내면 HTTP로 왕복시켜야 한다(ADR-0027 §3).
- **`TrainingJob`은 `applyLearning()`과 무관**하다 — 대화 자산 반영은 여전히 승인 요청 핸들러 안에서 즉시 일어난다(ADR-0018 보론).

### 3. **"GPU 필요도 5 복귀" 트리거는 철회한다** — 항목별 재산정으로 대체

실제로 착수해 보니 트리거의 전제가 성립하지 않았다. 증강 검증은 **이미 돌고 있는 추론 경로의 재사용**이고, 분류기 학습은 **CPU 선형 연산 수 초**다. 트리거는 "이때 다시 생각하라"는 뜻이지 "이때 자동으로 5로 올려라"가 아니다.

| No | 카탈로그 | 재산정 확정 | 근거 |
|---|:---:|:---:|---|
| **16** | 6 | **구성 의존 — G1 `2` / G2(Gemini) `3` / G3(로컬 생성모델) `6`**. 카탈로그 값 **6 유지** + 구성별 값 각주 병기 | PM이 G3를 승인하고 24GB+ GPU를 확보해 **6을 하향할 근거가 사라졌다.** 다만 기본 구성(G1)은 GPU 0이므로 "GPU 없이도 기능이 성립한다"가 함께 사실이다 |
| **23** | 4 | **3** | 재임베딩 없음 + 선형 학습 CPU 수 초. 기준표 3~4 구간의 하단 |
| **18** | 5 → **4**(이 ADR §5) | **4 유지** | 변동 없음 |
| **30** | 8 → **1**(이 ADR) | **1 유지** | 변동 없음 |

### 4. 이 갱신이 **건드리지 않는 것**

- `/embed`·`/health`의 요청·응답 스키마(**바이트 단위 무변경** — FR-L2-37).
- ml-worker 부재 시 `apps/api` 정상 기동 규약.
- `EmbeddingProvider` 포트·`MockEmbeddingProvider`로 **Python 없이 전 테스트 통과**.
- 벡터 저장·탐색 전략(base64 + 메모리 내적, 벡터 인덱스 미도입).
- `packages/llm-provider` 미생성(§7 각주 참조) · `infra/` 미생성.
- ml-worker는 **DB에 접근하지 않는다**(모든 영속화는 `apps/api`).

## 갱신 (2026-09-25 — No.40: 버전 문장 벡터 보존 저장소 · ml-worker 무변경)

환경 분리/버전관리(No.40, **ADR-0039 §4**). §4 "이 갱신이 건드리지 않는 것" 전부와 `/embed`·`/health` 계약은 **불변**이다.

1. **슬롯 색인(`EmbeddingVector`)과 색인기는 바꾸지 않는다** — 유일 키·재사용 키 `textHash`·고아 정리·재색인 비용이 모드 꺼진 챗봇에서 같다.
2. **`EmbeddingTextVector`(신규)**: `(chatbotId, modelId, textHash)` 유일 · 원문 없음 · 같은 코덱. 운영·스테이징·운영 이력·전환 예약 대상 버전의 질문 측 문장 벡터를 **슬롯 색인에서 복사**해 보존한다(재사용 키의 "같은 정규화 문장 = 같은 벡터" 등식). 모드 꺼진 챗봇은 0행.
3. **버전 대상 점수**: 버전 슬롯마다 "보존 저장소 → 같은 `textHash`의 초안 벡터" 순으로 벡터를 모아 기존 `assembleSemanticInput()`에 넣는다 — 랭킹·타이브레이크 규칙 1벌 유지.
4. **추가 임베딩 호출**: 정상 경로 0. 경합(캡처 직전 편집의 재색인 전 재편집)·모델 교체로 벡터가 없는 문장만 기존 Provider 경로(유일 출구)로 임베딩한다 — 외부 HTTP 출구 수 불변 · ml-worker는 여전히 DB에 접근하지 않는다.
