## 맥락

카탈로그 No.36은 "환각 탐지, 편향 테스트, 위험응답 필터링, Human-in-the-loop 승인 · GPU 5"다. 요구사항 분석은 이 제품에서 **AI가 자유 문장을 만들어 사용자에게 내보내는 곳이 외부 RAG 답 1곳뿐**이고(규칙 기반 답은 관리자가 쓴 문장), 그 답을 만드는 프롬프트는 **우리가 바꿀 수 없으며**(ADR-0022), 사람 승인(HITL)은 **2인 승인 하나만 빠져 있다**는 것을 코드로 확인했다. 사용자는 2026-09-30에 **규모 A**(위험 응답 규칙 + RAG 답 개인정보 가림 + 운영 전환 2인 승인)를 확정했고, 편향·환각 점검 도구(B)·런타임 근거 점검(C)은 **하지 않는다**.

결정할 것은 일곱 가지다.

1. 위험 응답 규칙을 어떤 모델·매칭으로 두고, 매 턴 비용을 어떻게 0에 가깝게 하나(금지어 `detect()` 재사용 여부 · 캐시).
2. 입구(사용자 질문)·출구(RAG 답) 검사를 **정확히 어디에** 넣나 — 동기 대화 예산·위젯 무변경·ADR-0023 경로와 충돌 없이.
3. 대체된 턴을 어떻게 기록하나(대화 기록 표식 · 통계 분류 · 이벤트).
4. `pii-mask`에 "종류 선택·날짜 제외"를 넣으면서 **저장 마스킹 결과를 바이트 불변**으로 지키는 방법.
5. 2인 승인을 **우회 불가능하게** 거는 지점(즉시 전환·롤백·예약 전환·환경 끄기).
6. 승인과 실제 전환을 어떻게 원자적으로 묶나(동시 승인·취소·만료).
7. 권한·감사를 새로 만들어야 하나.

## 결정

### 1. 규칙 = 챗봇별 "안전 설정"(대화 자산 아님) · 리터럴/토큰 매칭은 금지어 `detect()`를 **무수정 재사용** · 2층 캐시(전역 색인 + 챗봇 프로필)

- 새 테이블 `GuardrailRule`(챗봇 소속 · 이름 정규화 유일 · 분류 8 · 표현 1~100 · 포함/단어 일치 · 적용 위치 입구/출구/둘 다 · 동작 기록만/대체/AI로 안 보냄 · 대체 문구 · 켜짐 · 표시 순서). **버전 스냅샷·토픽 분리·환경 승격·챗봇 복사 대상이 아니며**(설문·API 연결과 같은 "환경 밖" 규약) 저장 즉시 운영에 적용된다. 새 규칙 기본 동작 = **기록만**(zod 기본값).
- 매칭은 금지어 모듈의 순수 함수 `detect(text, dict)`를 **파일 수정 없이** 그대로 호출한다. 규칙 표현을 `BannedWordEntry` 모양의 항목으로 컴파일하고(정책 필드는 쓰이지 않는 상수), `detect()`가 **입력 항목 객체를 그대로 돌려주는 성질**을 이용해 `Map<항목, 규칙 id[]>`로 역참조한다. 같은 정규화 표현은 1항목으로 합친다(규칙 50 × 표현 2,000이라도 `includes` 2,000회 이하). 정규식은 여전히 0(NFR-S12 상속).
- 캐시: **① 전역 색인**(켜진 규칙이 1개라도 있는 챗봇 id 집합 — 쿼리 1개 · 단일 슬롯 · TTL 60초 · 규칙 쓰기 시 즉시 무효화) **② 챗봇별 컴파일 프로필**(색인에 있는 챗봇만 적재 — 쿼리 1개) **③ 챗봇별 출구 개인정보 설정**(출구 경로에서만 적재). 규칙이 없는 챗봇의 공개 턴은 **추가 쿼리 0 · 정규화 0**이다(금지어 FR-12-46 선례를 챗봇 단위로 확장). 재적재 실패 시 직전 값을 계속 쓰고(stale-on-error), 한 번도 적재하지 못했으면 입구 = 통과 · 출구 = 폴백(아래 §2).

### 2. 입구 = 공개 대화 서비스 1지점(설문 예측 직후 · 의미 점수 계산 전) · 출구 = `RagAnswerService` 성공 분기 1지점(2,000자 절단 직후 · 출구 금지어 마스킹 전) · 대체는 기존 실패 수렴(`FAILED`)으로

- **입구 순서**: 입구 금지어(BLOCK이면 끝) → 상담 게이트(개입 중이면 사람 대화) → 번들 로드 → 설문 소비 예측 → **③.6 가드레일 입구 판정**(설문이 소비할 턴·`NODE` 버튼 턴은 건너뜀) → 의미 점수 → 엔진. 위치를 번들 로드 뒤에 둔 이유는 FR-AG2-7(설문 턴 제외)의 판정 함수 `willSurveyConsumeInput()`에 번들이 필요하기 때문이다. **대체**는 엔진·의미 점수·RAG를 부르지 않고 대체 문구 TEXT 1개(출구 금지어 마스킹 통과)를 돌려준다 — 상태는 요청에 실려 온 값 보존(금지어 BLOCK 모양), 대화 기록은 미응답 + 표식, 상담 켜진 챗봇이면 기존 관찰 창 힌트. **AI로 보내지 않음**은 엔진은 그대로 돌리고 RAG 진입 판정만 거짓으로 만든다(유량 슬롯 소비 0 · `shouldRunRag()` 순수 함수 무수정 — 호출부에서 결합).
- **출구 순서**: 외부 응답 → 기존 성공 판정 4조건 → 출처 정제 → **2,000자 절단** → **가드레일 출구 판정(규칙 → 개인정보 형식 가림)** → 출구 금지어 마스킹 → `complete()` → 로그. 판정은 절단된 텍스트에 한다(EX-AG-5 — 사용자가 보는 글자에 판정). **대체·폴백**은 기존 `finishAsFallback()`에 선택 인자(문구·표식)를 더해 **같은 `FAILED` 수렴**으로 끝낸다 → 위젯의 "보류 실패 시 관찰 창"이 그대로 작동한다(위젯 변경 0 · 폴링 스키마 불변 · ADR-0023 경로 불가침).
- **판정 함수는 예외를 던지지 않는다**(내부 try/catch). 오류·프로필 미확보 시 **안전 쪽 수렴**: 그 챗봇에 출구 대체 규칙이 있거나 **개인정보 가림이 켜져 있으면**(기본 켜짐) 폴백, 아니면 원답 + 오류 이벤트. 요구사항(FR-AG3-6)은 "대체 규칙이 있으면 폴백"이었으나, 가림이 기본으로 켜진 이상 가림을 확인하지 못한 답을 내보내는 것도 같은 위험이라 조건을 넓혔다.
- **출구 규칙은 외부 RAG 답에만 적용한다** — 관리자가 쓴 답·레거시 API 값·상담원 메시지는 사람이 작성·승인한 문장이라 적용하지 않는다(과차단 방지 · 사용자 확정).
- 관리자 **시뮬레이터**는 같은 판정 함수를 호출해 "운영이면: 대체됨/가림 N건/통과"와 함께 **RAG 답 미리보기**(대체·폴백이면 원답은 저장 마스킹본으로)를 돌려준다 — 이벤트 기록 0. **TC 실행기 표시는 하지 않는다**(규모 B의 안전 점검 세트와 함께 — 검증 실행기·결과 테이블 변경을 이번에 만들지 않는다).

### 3. 기록 = 이벤트 테이블(문장 0 · FK 0) + 대화 기록 선택 컬럼 `guardrailStage` 1개 · 통계 정의는 불변

- `GuardrailEvent`: 챗봇 · 메시지 id(대화 기록 id — FK 없음, 보존 소거 후에도 수치로 남는다) · 단계 · 종류(규칙/개인정보/오류) · 규칙 id·이름·분류 스냅샷 · 규칙 동작·적용 동작 · 효과(바뀜/없음) · 개인정보 종류·건수 · 일 버킷. **사용자 발화·AI 답 문장 컬럼이 없다**(정적 검사). 적재는 응답 뒤 fire-and-forget이며 쓰기 파일 1개.
- `ConversationLog.guardrailStage`(nullable `INBOUND｜OUTBOUND`)는 "가드레일이 이 턴의 답을 막았다"는 표식이다(대체·개인정보만 남은 답의 폴백·오류 폴백). 쓰기 주체 `record()` 1곳 · 적재 후 불변 · 인덱스 없음 · 백필 없음. `blockedByFilter`와 섞지 않는다(금지어 BLOCK은 미응답 수집 제외 등 다른 의미를 이미 갖는다).
- 가로막힌 턴은 `isAnswered=false`·`answeredByRag=false`로 적재된다 → 응답출처 판정(`classifyResponseSource`)이 `FALLBACK`으로 분류하고 기존 불변식(`bySource.FALLBACK === unansweredCount`)이 유지된다. No.14·29 통계 코드는 한 줄도 바뀌지 않는다. 미응답 수집기도 불변(가로막힌 질문은 미응답 큐에 들어간다 — 관리자가 FAQ로 안전한 답을 만들면 그 답은 사람이 쓴 문장이라 출구 규칙이 적용되지 않는 것이 해결 경로다).

### 4. `pii-mask`는 **선택 인자 2개**(`kinds` · `preserveDates`)를 더하되, 두 인자가 모두 없으면 **기존 본문을 한 글자도 거치지 않고** 그대로 실행한다

- `maskPii(text, { mode?, kinds?, preserveDates? })`. 두 선택 인자가 없으면 함수 첫 줄의 분기로 **기존 본문 그대로** 실행한다(저장 경로 7곳 · 송신 경로 모두 인자를 넘기지 않는다 — 결과 바이트 불변, No.45 FR-0-161).
- 인자가 있으면 별도 내부 함수가 **같은 순서**(주민번호 → 카드 → 전화 → 계좌 → 이메일)로 처리하되, 선택되지 않은 종류의 일치 구간은 **자리표시(숫자·하이픈이 없는 사설 영역 문자)로 보호**했다가 끝에 되돌린다 — 기존 "앞 종류가 먼저 가져간다"(전화 → 계좌 순서로 전화번호가 계좌로 오분류되지 않음) 우선순위를 선택과 무관하게 보존하기 위해서다. `preserveDates`는 계좌 단계 직전에 `YYYY-MM-DD`(1900~2099 · 월 01~12 · 일 01~31 · 앞뒤가 숫자·하이픈이 아님) 구간을 보호한다. 입력에 자리표시 영역 문자가 이미 있으면 **5종 전부 가림**으로 떨어진다(과탐 쪽 — 기존 fail-closed 원칙).
- 불변 증명: ① 도입 **전** 커밋에서 생성한 골든 말뭉치(PARTIAL·FULL) 시험 ② `kinds = 5종 전부`의 선택 경로 결과 = 기존 경로 결과(동등성 시험) ③ 기존 `pii-mask` 시험 무수정 통과 ④ 선택 인자를 넘기는 운영 코드 파일 = 가드레일 출구 1파일(정적 검사).
- 출구 가림의 **종류는 챗봇별**(기본 주민등록번호·카드번호 · 계좌·전화·이메일은 선택 · 날짜 보호 기본 켬), **강도는 서버 설정 `PII_MASK_MODE`를 따른다**(FULL 서버면 전화·이메일도 전량 토큰). 거버넌스 모드 ON에서는 주민번호·카드를 끌 수 없다(No.45 "마스킹 약화는 환경변수만"의 적용).

### 5. 2인 승인 = **전환 서비스(`ProdSwitchService.switch()`) 1곳에서 강제** · 정책은 `ChatbotEnvironment`(게이트 설정 옆) · 요청은 새 상태 테이블 · 환경 끄기·비직전 롤백·예약 전환까지 같은 관문

- 정책(`approvalRequired` 기본 false · `approvalTtlHours` 기본 24, 1~168)은 운영 전환 게이트와 같은 성격이라 `ChatbotEnvironment`에 두고 **쓰기 유일 파일 `environment-pointer.writer.ts`**에 메서드 1개를 더한다(E-1 봉인 유지). 켜기는 환경 모드 ON ∧ 활성 `chatbot:deploy` 보유자 ≥ 2일 때만. 끄기는 1인 동작이며(감사) 서버 환경변수 `ENV_APPROVAL_OFF_LOCKED=true`면 거부한다.
- **강제 지점은 포인터를 쓰는 유일한 서비스 `ProdSwitchService.switch()`** 이다. 정책이 켜진 챗봇에서 `SWITCH`(즉시·예약 공용)와 **직전 운영 버전이 아닌 대상으로의 `ROLLBACK`**은 ① 승인 호출(요청 id + 승인자 + 트랜잭션 안 선점 콜백)이거나 ② 승인된 요청이 묶인 예약 실행일 때만 진행하고, 아니면 `409 ENV_APPROVAL_REQUIRED`다. 컨트롤러·예약 실행기·콘솔이 무엇을 하든 이 1곳을 지나지 않고는 운영 포인터가 바뀌지 않는다(ADR-0022 이래 "약속이 아니라 구조" 원칙).
- **예외 = 직전 운영 버전 롤백**(`pickRollbackTarget()` 결과와 같은 대상): 즉시 실행 · 전환 이력 `approvalMode='SOLO_ROLLBACK'` · 감사 요약 접두 · 가드레일 현황 알림. 게이트 BLOCK이 ROLLBACK에서 WARN으로 낮아지는 기존 규칙(ADR-0039)과 합쳐, 정책이 켜진 챗봇에서 "롤백"이 임의 과거 버전으로 가는 1인 우회로가 되지 않게 범위를 직전 1개로 좁힌다(핑퐁만 가능 — 이미 서비스했던 두 버전 사이).
- **환경 모드 끄기는 정책이 켜진 동안 거부**한다(`ENV_APPROVAL_REQUIRED` · 사유 `POLICY_ACTIVE`) — 모드가 꺼지면 초안이 곧 라이브라서(`PROMOTE_DRAFT`는 즉시, `KEEP_PROD`도 이후 편집부터) 승인 관문 전체가 사라지기 때문이다. 끄려면 정책을 먼저 끈다(감사·잠금 대상).
- 복원·스테이징 승격·게이트·거버넌스 설정·챗봇 켜기/끄기는 대상이 아니다(사용자 확정 — 운영에 닿는 관문은 전환 1곳).

### 6. 요청 = `ProdSwitchApprovalRequest`(상태 기계 · 챗봇당 대기 1건 = nullable 유일 `pendingLock`) · 즉시 전환 승인은 **포인터 CAS와 요청 선점이 같은 트랜잭션** · 예약 전환은 요청이 예약을 **참조**만

- 상태 `PENDING → APPROVED(결과 APPLIED｜NOOP｜FAILED｜SCHEDULED) | REJECTED | CANCELLED(요청자·정책 끔·기준 변경·예약 비활성) | EXPIRED`. 모든 전이는 `status='PENDING'` 조건부 갱신(CAS)이라 승인·취소·만료·두 번째 승인자가 겹쳐도 먼저 커밋된 하나만 유효하다. 대기 1건 제약은 원시 부분 인덱스가 아니라 **nullable `@unique pendingLock`**(대기일 때만 `chatbotId`)이다 — No.21 `activeLock` 선례, `db push`로도 생성되고 원시 부분 유니크 4개가 불변이다.
- **요청자 ≠ 승인자는 서버가 강제**한다(사용자 id 비교 · 반려도 같음 · 요청자는 취소만). 만료는 루프 없이 **지연 판정**(조회·변경 시 CAS로 종결 + 감사 — 서버 재시작과 무관). 예약 전환 요청의 만료는 `min(요청 + TTL, 예약 시각)`.
- **즉시 전환 승인**: 요청 기준(요청 시점 운영 버전)과 현재 운영 포인터가 같은지 확인(다르면 요청 종결 `BASE_CHANGED`) → `ProdSwitchService.switch()`가 대상 허용·게이트 **재평가**·경고 재계산(승인자가 경고 확인)을 한 뒤 **한 트랜잭션에서 ① 포인터 CAS ② 전환 이력(`approvalRequestId`·`approvalMode='APPROVED'`) ③ 요청 선점 CAS(`PENDING → APPROVED/APPLIED`)** 를 한다. ③이 0행이면 예외로 전체 롤백 — "승인됐는데 전환 안 됨"·"전환됐는데 요청이 대기"가 생기지 않는다. 게이트 차단·대상 소실 같은 확정 실패는 요청을 `APPROVED/FAILED(코드)`로 종결하고, 경고 미확인·DB 바쁨은 요청을 대기로 남겨 승인자가 다시 시도한다(자동 재시도 0).
- **예약 전환**: 예약 생성 경로(`deploy-schedules`)는 바꾸지 않는다. 예약 작성자가 그 예약을 가리키는 승인 요청을 만든다(콘솔이 예약 생성 직후 이어서 호출 — 요청자는 예약 작성자여야 한다). 승인은 선점만 하고(`APPROVED/SCHEDULED`) 전환은 예약 시각에 기존 실행기가 한다. 실행 시 전환 서비스가 "이 예약 id + 같은 대상 + 같은 기준 + 미사용"의 승인 요청을 확인하고, 없으면 `ENV_APPROVAL_REQUIRED` → 예약 오류 분류표가 영구 실패 `APPROVAL_MISSING`으로 종결한다(misfire와 같은 모양 — 실행 0). 요청을 만들지 못한 예약도 같은 경로로 실행되지 않는다(fail-closed).

### 7. 신규 권한 0 · 감사 대상 +2 · 액션 추가 0

- 규칙·설정·현황·시험 = 기존 `security:read`/`security:write`(금지어와 같은 등급 — ADMIN). 정책·요청·승인·반려·취소·전역 대기 목록 = 기존 `chatbot:deploy`. 요청 상세·챗봇 승인 현황 조회 = 환경 현황과 같은 `chatbot:read`+`dialogue:read`. `Permission` 18종·역할 4종 불변.
- `AuditTargetType` +2(`GuardrailRule`·`ProdSwitchApprovalRequest` — 36 → 38) · `AuditAction` 16 불변. 출구 가림 설정은 `Chatbot` 대상(선제 안내 스위치 선례), 승인 정책·단독 롤백은 기존 `ChatbotEnvironment` 대상. 요청 사유·반려 메모 본문은 감사·서버 로그에 남기지 않는다(ADR-0039 §8 규약).
- 새 외부 출구 0(`EgressExitId` 7) · 모델·임베딩·LLM 호출 0 · 동기 대화 턴 추가 쿼리 0(규칙 없는 챗봇) · `@Public()` 9 불변.

## 근거

- **AI 자유 생성의 출구가 1곳이면 검사도 1곳이면 된다.** 프롬프트를 못 바꾸는 이상(ADR-0022) 할 수 있는 것은 "보내기 전"과 "내보내기 전" 두 관문이고, 둘 다 우리 코드의 단일 지점이다. 관리자가 쓴 답까지 검사하면 오탐 비용만 늘고 이득이 없다.
- **이미 있는 부품을 무수정 재사용한다.** 탐지(`detect()`) · 입구 조기 반환 모양(금지어 BLOCK) · 실패 수렴(`finishAsFallback`·`FAILED`·관찰 창) · 응답출처 분류(`isAnswered=false` → `FALLBACK`) · 정규식(`pii-mask`)이 전부 있다. 새로 만드는 것은 규칙 저장소·이벤트·승인 상태 기계뿐이다.
- **저장 마스킹 결과를 바꾸는 순간 과거 행과 새 행이 어긋난다**(No.45). 그래서 날짜 오인 수정은 저장 경로가 아니라 출구 전용 인자로 한다 — 기존 호출부가 인자를 넘기지 않는 한 기존 본문만 실행된다.
- **승인은 "누가 버튼을 눌렀나"가 아니라 "포인터를 누가 바꿀 수 있나"로 강제해야 우회가 없다.** 포인터를 쓰는 서비스가 1개(ADR-0039 E-1)라서 그 1곳에 조건을 거는 것이 가장 작고 완전하다. 환경 끄기·임의 롤백이 같은 효과를 내는 옆문이라 함께 닫았다.
- **승인과 실행의 원자성은 같은 트랜잭션의 두 CAS로 충분하다.** 별도 "실행 중" 상태·임대·복구 루프가 필요 없다(요청 선점이 실패하면 포인터 갱신도 롤백).

## 대안과 트레이드오프

| 대안 | 기각 사유 |
|---|---|
| **외부 RAG 프롬프트에 안전 지침 주입** | ADR-0022 봉인 · 전역 설정(다른 이용자 답까지 바뀐다) · 사용자 확정 "하지 않음" |
| **LLM/임베딩 기반 위험 판정(규모 B·C)** | 사용자 확정 "하지 않음" · 운영 모델 실측 전(ADR-0046) · 동기 턴 예산 |
| **금지어 사전을 확장(챗봇별·동작 선택 컬럼 추가)** | 금지어는 전역·BLOCK/WARN·출구 마스킹만이라는 기존 의미가 흔들리고 금지어 봉인·시험이 전부 바뀐다 · 요구사항 "금지어 동작 불변" |
| **금지어 `detect()`를 제네릭으로 고쳐 재사용** | 타입만의 변경이라도 금지어 파일을 건드린다 — 입력 객체를 그대로 돌려주는 기존 성질로 역참조가 가능해 수정이 필요 없다 |
| **규칙 적재를 챗봇별 캐시 1층으로만** | 규칙이 없는 챗봇도 첫 턴마다 쿼리 +1 → 공개 턴 쿼리 수 고정 시험(No.40·45) 기대값이 바뀐다. 전역 색인 1층을 두면 규칙 없는 챗봇은 0이다 |
| **출구 검사를 모든 답(관리자 답 포함)에** | 사용자 확정으로 기각(과차단 · 사람이 승인한 문장) |
| **출구 대체를 `READY` + 대체 문구로** | 통계상 RAG 성공으로 섞이고, 위젯 관찰 창이 열리지 않는다(상담 연결 기회 상실) |
| **`maskPii()`에 종류 선택을 넣고 기본값을 5종으로** | 기존 본문을 리팩터링하게 된다 — "기존 본문 미경유" 분기가 바이트 불변을 가장 싸게 증명한다 |
| **계좌 정규식 자체를 고쳐 날짜 오인 제거** | 저장 마스킹 결과가 바뀐다(No.45 FR-0-161 · 과거 행과 불일치) |
| **대화 기록 표식 없이 이벤트 조인만** | 이벤트는 fire-and-forget이라 누락 가능 · 로그 행만 보고 판정하는 기존 규약(No.44 `inputKind` 승격 선례)과 어긋남 |
| **`blockedByFilter=true` 재사용** | 금지어 차단의 의미(미응답 큐 제외·평가 제외·통계 해석)를 오염시킨다 |
| **2인 승인을 컨트롤러·콘솔에서만 검사** | 예약 실행기·롤백·다른 경로가 우회한다 — 강제 지점은 포인터 쓰기 서비스여야 한다 |
| **승인 정책을 가드레일 설정 테이블에** | 쓰기 소유가 두 모듈로 갈라지고, 전환 서비스(`environment/core`)가 가드레일 모듈을 읽어야 한다 — 게이트 설정과 같은 테이블이 자연스럽다 |
| **승인 = 별도 "실행 중" 상태 + 복구 루프** | 같은 트랜잭션 두 CAS로 원자성이 확보되므로 불필요 |
| **대기 요청 제약을 원시 부분 유니크 인덱스로** | `db push` 미생성 · 원시 부분 유니크 개수 불변 봉인과 충돌 — nullable 유일로 충분(No.21 선례) |
| **예약 생성 트랜잭션 안에서 승인 요청 생성(포트 주입)** | `deploy-schedules`가 환경 모듈을 알아야 하고(순환 — `EnvironmentModule`이 `DeploySchedulesModule`을 import) 예약 모듈 쓰기 봉인(D-1)에 새 테이블이 끼어든다. 실행 시 강제(fail-closed)로 안전성은 같다 |
| **승인 대기 중 예약을 `HELD`로 두기** | 예약 모듈 밖에서 예약 행을 써야 한다(D-1 위반) |
| **롤백 전부를 승인 대상에서 제외** | ROLLBACK은 게이트 BLOCK이 WARN으로 낮아지고 대상이 운영 이력 전체라 1인 우회로가 된다 |
| **정책이 켜진 동안에도 환경 끄기 허용** | 끄는 순간 초안이 라이브 — 승인 관문 전체가 사라진다 |
| **만료를 주기 루프로 종결** | 새 루프 · 다중 인스턴스 경합 — 지연 판정 + CAS로 충분(조회 시 판정 허용 — NFR-AGR3) |
| **신규 권한 `chatbot:approve`** | 사용자 확정 "신규 권한 0" · ADMIN 2명 이상이면 기존 `chatbot:deploy`로 역할 분리가 성립 |
| **TC 실행 결과에 가드레일 판정 컬럼 추가(FR-AG3-7 전부)** | 검증 실행기·결과 테이블·봉인 변경 — 안전 점검 세트(규모 B)와 함께 하는 편이 의미가 맞다(이번 범위 밖으로 조정) |

## 감수하는 비용

1. **규칙은 표현 목록이라 우회 표현(띄어쓰기·은어·다른 언어)을 막지 못한다** — 화면에 한계를 적고, 새 규칙을 "기록만"으로 시작해 관찰 후 강화한다.
2. **"환각 탐지"는 하지 않는다** — 답이 근거와 다른 말을 해도 규칙에 없는 표현이면 그대로 나간다. 화면·영업 문구에 "환각" 표현 금지.
3. **출구 가림 기본값(주민번호·카드)이 배포 즉시 모든 챗봇 RAG 답에 적용된다** — 카드 정규식은 14~16자리 연속 숫자(주문번호 등)도 `[카드번호]`로 가린다(기존 정규식의 과탐 성질).
4. **다중 인스턴스에서는 규칙 변경이 다른 인스턴스에 TTL(기본 60초) 뒤 반영된다** — 금지어 캐시와 같은 수준.
5. **출구 대체 턴에 위젯 상태 문구 "지금은 답변을 준비하지 못했어요."가 함께 보인다** — 위젯 변경 0 원칙의 결과.
6. **승인 정책을 끄는 것은 1인 동작이다** — 악의적 관리자에 대한 방어가 아니라 절차 통제다. 끄기는 감사되고, 필요하면 서버 운영자가 `ENV_APPROVAL_OFF_LOCKED`로 잠근다.
7. **정책이 켜진 동안 환경 모드를 끌 수 없다** — 끄려면 정책부터 끈다(2단계).
8. **예약 전환은 "예약 생성 + 승인 요청" 두 호출이다** — 두 번째가 실패하면 예약은 실행 시 `APPROVAL_MISSING`으로 끝난다(안전 쪽).
9. **대기 요청은 챗봇당 1건** — 예약 전환 여러 개를 동시에 승인 대기에 올릴 수 없다(하나 승인 후 다음 요청).
10. **이벤트 테이블에 자동 삭제가 없다** — 문장이 없어 보존 대상이 아니다. 행 수가 문제가 되면 재검토.

## 알려진 한계 (구현 후 확인 — 2026-09-30)

1. **M-1 승인 정책 끄기 우회**: 끄기가 1인 동작이라 `chatbot:deploy` 보유자가 끄고 → 직접 전환 → 켜기로 우회할 수 있다. 절차 통제이며 악의적 관리자 방어가 아니다(감사·현황 표시는 남음). 거버넌스 모드 ON에서 `ENV_APPROVAL_OFF_LOCKED` 기본 잠금 또는 끄기 감사 알림 강화는 후속.
2. **M-2 우회 표현 방어 약함**: `normalizeText`는 NFKC·소문자·공백 축약만이라 제로폭 문자(U+200B~200D, U+FEFF)·삽입 문자로 CONTAINS 매칭을 회피할 수 있다(띄어쓰기 삽입은 설계 K-1·EX-AG-2 한계). 금지어와 정규화를 공유하는 원칙이라 금지어 정규화 개선과 함께 후속.
3. **L-1** GET 조회(`summary`·`getStatus`·`listGlobal`)가 만료 sweep으로 쓰기를 일으키고 `ApprovalNavLink`가 60초마다 전역 목록을 읽는다(챗봇 수가 크게 늘면 부하).
4. **L-2** 직전 버전 단독 롤백은 A↔B 반복 토글이 가능하다(`SOLO_ROLLBACK` 감사·경고는 남음, 설계 U-3 수용).
5. **L-3** 시뮬레이터 미리보기의 2,000자 절단이 `rag-answer.service`의 비공개 `truncateAnswer`와 중복된다.
6. **L-4** `Modal` 두 번째 이펙트가 `initialFocusSelector`가 있는 대화상자에서 포커스가 밖(중첩 포털)으로 나간 상태로 재렌더되면 되돌린다.
7. **L-5** 챗봇 영구삭제 시 가드레일 캐시가 TTL(60초)까지 남는다(영향 없음). 이벤트·대화 기록이 독립적 fire-and-forget이라 한쪽만 실패하면 이벤트 목록의 `conversation`이 null이다(화면은 null 처리).
8. H9(지식베이스 첫 적재) 바로가기는 기능 꺼짐 여부를 확인하지 않고 `security:read`만으로 링크한다. TC 실행·회귀 화면의 가드레일 표시는 규모 B로 이월.
9. 예약 항목의 `approvalState`(권고 A-7)는 봉인 AG-15와 충돌해 미적용 — 프런트가 승인 조회 응답과 요청 상세로 합성한다.

성능 실측(개발 PC, 2026-09-30, 규칙 50·표현 2,000): 입구 P95 0.46ms(목표 ≤ 1ms) · 출구 P95 1.12ms(목표 ≤ 5ms) — 합격.

## 재검토 트리거

- **규칙 우회가 실제 사고로 확인됨** → 의미 기반 탐지(임베딩 유사도 · 운영 모델 판정자)를 새 ADR로(ml-worker 선택 경로 · `AUGMENT_LOCAL` 출구 — ADR-0047 §7 선례).
- **규모 B(안전 점검 세트·편향 짝) 착수** → TC 실행 결과의 가드레일 판정 표시 · RAG 답 마스킹본 기록(새 보존 대상).
- **외부 RAG 담당자가 `highlight_text` = 청크 전문을 확인** → 규모 C 숫자 대조(기록만) 검토.
- **생성 결과가 사용자에게 직접 나가는 기능(No.17·38) 착수** → 이 ADR의 출구 판정 포트를 그 경로에 같은 방식으로 적용.
- **금융·공공 고객이 복원·게이트·거버넌스 설정의 2인 승인을 명시 요구** → 승인 대상 동작 열거형 확장(요청 테이블 `action` 1곳).
- **법무 확인 결과 생성형 AI 고지 의무 확인(P-11)** → 서버 문구 옵션(FR-AG8) 또는 위젯 표식(위젯 개정).
- **다중 인스턴스 전환** → 규칙 캐시 무효화 전파(금지어 캐시와 함께) 재검토.
- **승인 알림(메일·메신저) 요구** → No.41 2차 운영 이벤트와 함께.
- **M-1 우회가 실제로 문제가 됨** → 거버넌스 모드 ON에서 `ENV_APPROVAL_OFF_LOCKED` 기본 잠금 또는 끄기 감사 알림 강화.
- **제로폭·삽입 문자 우회가 확인됨** → 금지어와 공유하는 `normalizeText` 개선(금지어 그룹과 함께).
- **챗봇 수 증가로 승인 배지 폴링·GET 만료 sweep 부하가 문제** → 배지 전용 경량 조회 · 만료 sweep을 쓰기 경로/스케줄러로 분리.
