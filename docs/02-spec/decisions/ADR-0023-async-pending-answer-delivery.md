# ADR-0023 — 느린 RAG 답변의 비동기 전달(`PENDING` 즉시 반환 + 폴링)

- **상태**: 채택 (Accepted)
- **일자**: 2026-09-22
- **결정자**: system-architect (PM 확정사항 P-5 반영)
- **관련**: `docs/requirements/nlu-rag-answering.md` **J-7**, FR-N2-26~40, NFR-P3/P4/P6, NFR-S16/S17, AC-N2-15~20/27, AC-N4-3, EX-N2-10~13 / **`API_RAG.md` §6-6**(수 초~수십 초, 서버 타임아웃 600초, 스트리밍 미지원) / ADR-0011(공개 API 규약) / ADR-0009(상태 봉투)
- **영향 범위**: `apps/api/src/conversation/{public-conversation.controller.ts, public-conversation.service.ts}`, `apps/api/src/rag/{rag-answer.service.ts, pending-answer.store.ts}`, `apps/widget/src/*`, `packages/shared-types/src/conversation.ts`
- **세부 설계**: `docs/02-spec/nlu-rag-answering-설계.md` §9.8~§9.9·§12

## 맥락

외부 RAG 질의는 **검색 + LLM 생성**이라 한 번에 **수 초~수십 초**가 걸리고, 서버 타임아웃이 **600초**이며, **스트리밍을 지원하지 않는다**(§6-6). 클라이언트 타임아웃은 최소 120초를 권고한다.

반면 공개 대화 API의 성능 예산은 **500ms(P95)** 이다(개발명세서 §5). 두 숫자는 양립하지 않는다.

**PM이 확정한 성능 목표는 "RAG 응답 5초"** 다(P-5). 5초는 500ms 예산보다 10배 크므로, 5초를 목표로 삼더라도 **동기 응답은 여전히 불가능**하다. 즉 "5초를 목표로 한다"와 "공개 대화 API가 5초를 기다린다"는 다른 이야기이며, 이 ADR은 후자를 기각한다.

## 검토한 대안

| 안 | 기각 사유 |
|---|---|
| **A. 동기 대기(요청을 물고 있는다)** | 위젯 요청이 수 초~수십 초 열려 있으면 ① 500ms 예산 붕괴 ② 레이트리밋 창(세션 30/분) 안에서 커넥션이 쌓임 ③ 모바일 네트워크·리버스 프록시가 먼저 끊어 **사용자는 오류만 본다** ④ 브라우저 탭 전환·백그라운드 전환 시 요청이 유실된다 |
| **B. WebSocket / SSE 푸시** | 위젯은 **런타임 의존성 0의 순수 TS + gzip 100KB 예산**이다(ADR-0012). 재연결·하트비트·프록시 호환까지 넣으면 예산과 복잡도를 동시에 깬다. 서버도 연결 상태를 들고 있어야 해 단일 인스턴스 전제가 더 강해진다. **한 턴에 한 번 오는 응답에 상시 연결은 과설계** |
| **C. `PENDING` 즉시 반환 + 폴링**(채택) | — |
| **D. 2단계를 아예 동기 3초로 제한** | 외부 서버를 우리가 못 바꾼다. 3초 안에 안 오면 항상 실패이므로 **2단계가 사실상 동작하지 않는다** |

## 결정

### 1. 공개 대화 API는 **기다리지 않는다**

1단계 실패 + 2단계 조건 충족 시:

```jsonc
{ "messageId": "<uuid v4>",
  "outputs": [{ "type":"TEXT", "payload":{ "text":"문서에서 찾아보고 있어요. 잠시만요" } }],
  "state": <요청에 실려온 상태 그대로>,
  "stateReset": false,
  "pendingAnswer": { "id":"<messageId와 동일>", "pollAfterMs":1200, "expiresAt":"..." } }
```

- **`PENDING` 응답은 200ms(P95)** 안에 나간다(NFR-P3). 외부 호출을 기다리지 않기 때문이다.
- `state`는 **요청 상태를 그대로 보존**한다(금지어 BLOCK 턴과 같은 처리 — EX-12-26 패턴). 폴백 턴은 세션을 바꾸지 않는다.
- **2단계를 타지 않는 턴의 응답은 바이트 단위로 현행과 동일**하다(`pendingAnswer` 키 자체가 없다 — AC-N2-16). 하위호환을 깨지 않는 것이 이 설계의 제약 조건이다.
- `pendingAnswer.id`는 **`messageId`와 같은 값**이다. 별도 식별자를 만들지 않아 로그 1건 규약과 자연히 맞물린다.

### 2. 신규 공개 엔드포인트 1개 — `@Public()`이 **5개 → 6개**가 된다

```
GET /api/v1/public/chatbots/:slug/messages/:messageId
→ { status: 'PENDING' | 'READY' | 'FAILED', outputs?, sources? }
```

**개수 고정 테스트(AC-C-4/AC-X-3)를 무력화하지 않고 6으로 갱신한다.** 그 테스트의 목적은 "몰래 늘어나는 것"을 막는 것이며, 설계 문서에 근거를 남기고 갱신하는 것은 장치의 정상 사용이다.

근거: 폴링은 **방금 자신이 보낸 질문의 답을 받는 동작**이며 공개 대화 API와 같은 신뢰 경계에 있다. 인증을 요구하면 위젯이 답을 받을 수 없다.

**보상 통제 4가지**

| # | 통제 |
|---|---|
| ① | `messageId`는 **추측 불가능한 UUID v4** |
| ② | **다른 슬러그의 id로 조회하면 `404`**(AC-N2-18) |
| ③ | **TTL 5분** 경과 후 `404 PENDING_ANSWER_NOT_FOUND` + 메모리에서 제거(AC-N2-19) |
| ④ | `READY` **최초 조회 후 30초 유예**를 두고 제거 — 네트워크 재시도는 허용하되 무한 재조회는 차단 |

공개 API 규약(ADR-0011)을 전부 상속한다 — 레이트리밋(세션 30/분·IP 120/분), Origin 가드, 내부 식별자·`trace`·점수 미노출.

### 3. 보류 답변 저장소는 **인터페이스 뒤의 TTL 메모리 상태**다

```ts
interface PendingAnswerStore {
  create(id, meta): void;
  complete(id, result): void;
  get(id, slug): PendingAnswerEntry | null;   // 슬러그 불일치는 null(= 404)
}
```

1차 구현은 `InMemoryPendingAnswerStore`(Map + TTL 스위퍼)다. **단일 인스턴스 전제**이며 다중 인스턴스 전환 시 교체 지점은 1곳이다(개발명세서 §5 확장성 규약 — ADR-0007의 업로드 스테이징과 같은 패턴).

서버 재시작으로 보류 답변이 사라지면 폴링이 `404` → 위젯이 정리 문구로 마감한다. **사용자에게 오류를 보이지 않는다**(EX-N2-12).

### 4. 대화 로그는 **최종 결과로 1건만** 남긴다

```
PENDING 반환 시점   : 적재 없음. messageId만 선발급
백그라운드 완료 시점 : record({ id: messageId, ... }) 1회
  ├ 성공 → isAnswered=true,  answeredByRag=true
  └ 실패 → isAnswered=false, answeredByRag=false → 미응답 큐 수집 조건이 자동 성립(ADR-0019)
```

2건을 남기면 **No.14 응답률·No.2 접속수·No.15 큐가 전부 두 번 센다.** 기존 코드가 이미 `record({ id: messageId })`(로그 PK = `messageId`) 규약을 쓰고 있어 선발급이 자연스럽다.

### 5. 성능 목표는 **5초(SLO)** 이고, 120초는 **타임아웃(안전장치)** 이다

| 지표 | 값 | 성격 |
|---|---|---|
| RAG 경유 답변 생성 | **5초(P95)** | **목표.** 초과가 상시화되면 스코프 축소·임계값 조정·외부 증설을 검토한다 |
| HTTP 클라이언트 타임아웃 | 120초(하한 강제) | 안전장치. §6-6 권고 준수. **목표가 아니다** |
| 위젯 하드 상한 | 90초 | 초과 시 정리 문구로 마감하고 입력 재활성화(S-15). 백그라운드 작업은 계속되어 로그에만 남는다 |
| 폴링 | 최초 1.2초 대기 → 1.5초 간격 | 5초 목표 달성 시 **대개 3회 이내 폴링**에서 최종 답변 도착 |

**두 숫자를 혼동하지 않는다.** 5초는 "이 정도면 사용자가 기다릴 만하다"는 약속이고, 120초는 "이보다 오래 붙잡고 있지 않겠다"는 방어선이다.

### 6. 위젯 폴링 규격

- 폴링 중 **입력을 잠그지 않는다.** 사용자가 새 질문을 보내면 **이전 폴링을 중단**하고 이전 결과는 버린다(EX-N2-11).
- 대기는 **시각·보조기술 양쪽**에 알린다 — 진행 표시 + `aria-live="polite"`. 애니메이션만으로 상태를 전달하지 않는다(UIUX 준수기준).
- 사용자 화면에 **"RAG"·"LLM"·"벡터" 같은 내부 용어를 쓰지 않는다.** 대기 문구는 `"문서에서 찾아보고 있어요"` 수준의 평서문이다.

## 결과

**좋아지는 것**
- 공개 대화 API의 **500ms 예산이 그대로 유지**된다. 2단계가 대화 처리 예산에 침입하지 않는다.
- 외부 서버가 느려지거나 죽어도 **사용자 요청은 이미 끝나 있다** — 체감 지연이 회로차단기·폴링 상한으로 흡수된다.
- 위젯이 **상시 연결 없이** 동작한다. 번들 예산(gzip 100KB)과 의존성 0 원칙이 유지된다.
- 하위호환이 **선택 필드 1개 추가**로 끝난다.

**나빠지는 것 / 감수하는 것**
- **왕복이 늘어난다.** 최소 2회 요청(전송 + 폴링 1회)이며 5초 응답이면 3~4회다. 레이트리밋 창(세션 30/분)을 폴링이 소비하므로 **간격 1.5초·상한 90초**로 최대 60회를 넘지 않게 묶었다.
- **보류 답변이 프로세스 로컬 상태**다. 재시작 시 유실되고 다중 인스턴스에서 동작하지 않는다 — 인터페이스 추상화로 교체 지점만 남겼다.
- **프로세스가 죽으면 그 턴의 `ConversationLog`가 유실**된다(통계 1턴 결손). 대화 응답은 이미 전달됐으므로 사용자 영향은 없다. 수용 가능한 손실로 판단하며 설계서 §14에 R-4로 등재했다.
- `@Public()` 표면이 1개 늘어난다 — 보상 통제 4가지로 상쇄한다.

## 재검토 트리거

- 외부 API가 **스트리밍을 지원**하게 될 때 → 토큰 단위 표시로 전환 검토(이 ADR 대체).
- **다중 인스턴스**로 전환할 때 → `PendingAnswerStore`를 Redis 구현으로 교체.
- No.24(상담원 인계)·No.42(옴니채널)가 **서버 보관 대화 세션**을 요구할 때 → 보류 답변을 그 저장소로 흡수할지 재검토(ADR-0009의 재검토 트리거와 동일 시점).
- 폴링 트래픽이 공개 API 레이트리밋을 실제로 압박할 때 → 폴링 전용 상한 분리 검토.
