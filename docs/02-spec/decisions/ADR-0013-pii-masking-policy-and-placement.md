# ADR-0013 — 대화로그 PII 마스킹의 구현 위치와 종류별 차등 정책

- **상태**: 채택 (Accepted)
- **일자**: 2026-09-20
- **결정자**: system-architect
- **관련**: `docs/requirements/quality-channel.md` DD-21, FR-11-20 ~ FR-11-24, NFR-S4, NFR-S6, AC-P-8, AC-P-9, EX-P-8 / `docs/requirements/chatbot-operations.md` NFR-S4("대화 처리 Phase의 책임"으로 지정)
- **영향 범위**: `apps/api/src/conversation/{conversation-log.service.ts, lib/pii-mask.ts, lib/conversation-log.ts}`, `apps/api/prisma/schema.prisma`, seed
- **참고**: 형제 프로젝트 `Auto QA`의 `packages/pii-mask`(한국형 PII 마스킹 — RRN/전화/카드/계좌/이메일, 2단계 탐지 구조)

## 맥락

이번 Phase에 `ConversationLog`의 **최초 쓰기 주체**(공개 대화 API)가 생긴다. 즉 **최종 사용자가 입력한 원문이 DB에 저장되기 시작하는 첫 시점**이다. `chatbot-operations.md` NFR-S4가 "PII 마스킹은 대화 처리 Phase의 책임"으로 유보해 둔 항목이 여기서 만기된다.

결정해야 할 것이 세 가지다.

1. **어디에 구현하나** — `apps/api`의 순수 함수인가, `packages/pii-mask` 신규 패키지인가(DD-21).
2. **어떻게 치환하나** — FR-11-23은 `010-****-5678`, `a***@example.com` 같은 **부분 마스킹** 예시를 들지만, Auto QA의 검증된 구현은 `[전화번호]` 같은 **전량 placeholder**를 쓴다. 둘은 보안 강도와 운영 가독성이 정반대다.
3. **무엇에 적용하나** — `userMessage`만인가, `botResponse`도인가.

세 번째가 특히 중요하다. 얼핏 봇 응답은 "관리자가 작성한 문구"라 PII가 없어 보인다.

## 결정

### 1. 구현 위치 — `apps/api/src/conversation/lib/pii-mask.ts` 순수 함수 (DD-21 ①안)

- 신규 패키지를 만들지 않는다. **현재 소비자가 1곳**(`ConversationLogService`)이기 때문이다.
- **승격 조건을 명시한다**: 소비자가 2곳 이상이 되면 `packages/pii-mask`로 올린다. 예상 트리거 — ml-worker의 학습 데이터 전처리(No.16), 옴니채널 통합 인박스(No.42), 통계 화면의 실시간 마스킹.
- **Auto QA의 코드를 복제하지 않는다.** 별도 저장소이므로 복제본은 즉시 드리프트한다. 대신 **탐지 구조를 설계로 이식**한다(§3).

### 2. 적용 위치 — `ConversationLogService.record()` **내부 단 1곳**

```ts
record(input: { chatbotId, channelType, sessionId, rawUserMessage, rawBotResponse, ... }): Promise<void>
```

- 인자를 `raw*`로 명명하고, 마스킹은 이 메서드 안에서만 수행한다. **마스킹되지 않은 값이 Prisma에 도달할 경로가 구조적으로 1개뿐**이다.
- **이 서비스 밖에서 `prisma.conversationLog.create`를 호출하지 않는다**는 규약을 둔다(code-reviewer 점검 항목). 호출부가 마스킹을 "기억해야 하는" 설계는 반드시 잊힌다.
- `record()`는 전체를 `try/catch`로 감싸 **모든 예외를 삼키고** `logger.warn`만 남긴다(FR-11-24, AC-P-10). **경고 로그에도 메시지 본문을 넣지 않는다** — `chatbotId`/`sessionId`/오류코드만(NFR-S4).

### 3. 종류별 차등 마스킹

| 종류 | 치환 결과 | 근거 |
|---|---|---|
| 주민등록번호 | `[주민등록번호]` **전량** | 뒤 7자리 자체가 고유식별정보다. 어떤 부분 노출도 허용되지 않는다 |
| 카드번호 | `[카드번호]` **전량** | 부분도 금융정보. 운영상 재사용 가치가 없다 |
| 계좌번호 | `[계좌번호]` **전량** | 동일 |
| 전화번호 | `010-****-5678` **부분** | FR-11-23 예시. "같은 사람의 재문의인가"를 판별하는 상담 맥락에 필요하고, 중간 4자리 제거로 역추적 가치가 크게 떨어진다 |
| 이메일 | `a***@example.com` **부분** | FR-11-23 예시. 도메인은 B2B 문의 분석에 쓰인다 |

**탐지 구조(Auto QA에서 이식)**

1. **1단계 — 구조적으로 명확한 패턴**: 구분자(하이픈/점/공백/괄호/국가번호)가 있어 형태만으로 종류가 특정되는 패턴을 규칙별 정규식으로 치환.
2. **2단계 — 구분자 없는 연속 숫자열 분류**: 1단계 후 남은 숫자열을 **전체 길이 + 직전 문맥 키워드 + 검증 로직**(주민번호 월/일/성별코드, 카드 Luhn)으로 분류.

이 구조가 주는 불변식: ① placeholder에는 숫자·`@`가 없으므로 **이미 치환된 결과가 다시 매칭되지 않는다** ② 숫자열 전체를 하나의 토큰으로 보므로 **16자리 카드번호가 13자리 규칙에 의해 쪼개지지 않는다**.

**fail-closed 원칙 상속**: 과탐(정상 숫자를 가림)보다 **미탐(실제 PII가 평문으로 남음)** 이 훨씬 심각하다. 판단이 갈리면 마스킹하는 쪽을 택한다.

### 4. `botResponse`도 **반드시** 마스킹한다

봇 응답은 관리자가 작성한 문구이지만, **`completionMessage`의 `{슬롯명}` 치환**(`packages/dialogue-engine/src/context-session.ts:137`)을 통해 **사용자가 입력한 전화번호·이메일이 그대로 봇 응답에 들어간다.**

```
"010-1234-5678 번호로 안내드릴게요."   ← completionMessage: "{연락처} 번호로 안내드릴게요."
```

이 경로가 존재하는 한 `botResponse` 마스킹 생략은 곧 유출이다. 슬롯 타입에 `PHONE`/`EMAIL`이 있고(`context-session.ts:81-88`) 관리자가 이를 완료 문구에 넣는 것은 **권장되는 사용법**이므로, 드문 경우가 아니라 **일반적인 경우**다.

- 부작용: `PHONE_CALL` 아웃풋의 회사 대표번호도 마스킹된다. **수용**한다 — 운영자는 노드 편집 화면에서 원문을 보며, 로그에서 자사 대표번호를 읽어야 할 이유가 없다.

### 5. 마스킹하지 않는 것

| 대상 | 이유 |
|---|---|
| 관리자 시뮬레이션 응답(`DialogueResolution.input`, 세션 `filledValues`) | 관리자 **본인이 방금 입력한 값**이며 디버깅에 필수다(NFR-S6, FR-10-11). 또한 시뮬레이션은 로그를 남기지 않는다(FR-10-5) |
| 공개 대화 API 응답 본문 | 사용자가 방금 보낸 값을 사용자에게 돌려주는 것이므로 새 노출이 아니다. 마스킹은 **저장·집계 경계**의 책임이다 |
| 요청 본문 자체 | 마스킹 전 원문은 **로그·trace·예외 메시지에 남기지 않는다**(NFR-S4). 저장하지 않으므로 마스킹 대상이 아니다 |

### 6. 알려진 한계를 문서화한다

규칙 기반이므로 **사람 이름·주소·생년월일·문맥 의존 PII는 탐지하지 못한다.** 100% 탐지를 보장하지 않는다. 이 한계를 `pii-mask.ts` 헤더 주석과 `docs/04-test/`에 기록하고, 강화가 필요해지면 승격(§1) 시점에 함께 검토한다.

**구현 확인(2026-09-20)**: `apps/api/src/conversation/lib/pii-mask.ts`는 위 §3이 서술한 2단계 탐지 구조(① 구분자 패턴 ② 구분자 없는 숫자열의 길이/문맥/체크섬 분류) 중 **①만 구현**됐다 — 종류별 정규식을 순서대로 적용하는 **정규식 1패스**이며, ②(Luhn 카드 체크섬, 주민등록번호 월/일 유효성 체크섬 등)는 미구현이다. 그 결과 카드번호와 계좌번호처럼 구조적으로 유사한 자릿수·구분자 패턴은 완벽히 구분되지 않고, 정규식 등록 순서(카드 → 전화 → 계좌)로 우선순위가 결정된다. 이는 §1이 명시한 "설계로만 이식, 코드는 복제하지 않음" 범위 내의 단순화이며 fail-closed 원칙(과탐 허용)과 일치하므로 별도 수정 없이 현재 구현을 유지한다. 체크섬 기반 2단계 분류가 필요해지면 승격(§1) 시점에 함께 재검토한다.

## 근거

- **"서비스 내부 단 1곳"이 규약보다 강하다.** 마스킹을 호출부 책임으로 두면 채널이 늘 때마다(어댑터 추가 시) 누락 후보가 생긴다. 인자 이름을 `raw*`로 두고 서비스 안에서만 변환하면, 마스킹을 우회하려면 **의도적으로 Prisma를 직접 호출해야** 한다 — 리뷰에서 즉시 보인다.
- **차등 정책이 요구사항과 위험도를 동시에 만족시킨다.** FR-11-23이 든 예시(`010-****-5678`, `a***@example.com`)는 **정확히 전화번호와 이메일**이다. 즉 요구사항 작성자도 "모든 종류를 똑같이 다루라"고 말한 것이 아니다. 주민번호·카드·계좌에 부분 마스킹을 적용하는 것은 어떤 해석으로도 정당화되지 않는다.
- **부분 마스킹이 집계를 해치지 않는다.** 인기질문 집계(ADR-0004)는 정규화된 문장을 묶는데, 전화번호가 포함된 문장은 애초에 상위 질문이 되지 않는다. 반면 미응답 분석에서는 "어떤 번호대의 사용자가 무엇을 물었나"가 아니라 "무엇을 물었나"가 중요하므로, 부분 마스킹으로 남는 4자리가 분석을 방해하지도 돕지도 않는다. **AC-P-9("인기질문에 원본 PII 미노출")는 양쪽 정책 모두 통과**한다.
- **Auto QA 코드를 복제하지 않는 이유**: 두 프로젝트는 별도 저장소이며(Chat Bot은 git 저장소도 아니다), 복제된 정규식은 한쪽에서 버그가 수정돼도 다른 쪽에 반영되지 않는다. **구조와 원칙을 이식하고 구현은 이 저장소의 테스트로 보증**하는 편이 정직하다.
- **`botResponse` 마스킹은 선택이 아니다.** `completionMessage` 치환 경로는 가정이 아니라 현재 코드에 존재하는 동작이다.

## 대안과 트레이드오프

| 대안 | 기각 사유 |
|---|---|
| `packages/pii-mask` 신규 패키지를 지금 만든다 | 소비자 1곳. 설정 5벌(package/tsconfig/vitest/lint/CI)이 늘어난다. 승격 조건을 명시해 두면 나중 이동 비용은 파일 이동 + import 경로 변경뿐이다 |
| Auto QA의 `packages/pii-mask`를 복사해 온다 | 드리프트가 확정적이다. 수정이 한쪽에만 반영된다 |
| 전 종류를 전량 placeholder로 통일 | 가장 안전하지만 FR-11-23의 명시 예시와 어긋나고, 상담 맥락 식별(재문의 판별)을 잃는다 |
| 전 종류를 부분 마스킹으로 통일 | **주민등록번호 뒷자리·카드 뒷자리가 남는다.** 법적·실무적으로 수용 불가 |
| 마스킹을 컨트롤러/인터셉터에서 수행 | 로그 적재는 응답 반환 **후** best-effort로 일어난다(§FR-11-24). 인터셉터는 요청/응답 경계에 있어 적재 시점을 덮지 못한다 |
| Prisma 미들웨어(`$extends`)로 자동 마스킹 | 암묵적 동작이라 디버깅이 어렵고, "어떤 필드가 PII인가"를 미들웨어가 알 수 없다. 서비스 1곳 규약이 더 명시적이다 |
| `userMessage`만 마스킹 | `completionMessage` 치환 경로로 유출된다(§4) |
| 마스킹을 비동기 후처리(배치)로 분리 | 원문이 **일단 DB에 저장된다**. NFR-S4("원문은 어디에도 저장하지 않는다")와 정면 충돌 |
| 마스킹 실패 시 대화를 실패시킨다 | FR-11-24/AC-P-10 위반. 다만 마스킹 실패는 "치환 결과를 못 만든 것"이 아니라 예외이며, 이 경우 **로그를 저장하지 않고 버린다**(평문 저장보다 로그 유실이 낫다 — fail-closed) |

**감수하는 비용**
① 전화번호 뒤 4자리가 로그에 남는다 — 단독으로는 개인을 특정할 수 없고, 요구사항이 명시한 수준이다. 더 강한 정책이 필요해지면 `PII_MASK_MODE` 환경변수로 전량 placeholder 전환을 열 수 있게 함수 시그니처를 남겨 둔다.
② 회사 대표번호·주문번호 등이 과탐으로 가려질 수 있다 — fail-closed 원칙의 의도된 귀결이다.
③ 규칙 기반의 미탐이 남는다(이름·주소) — §6에 한계로 기록하고, 강화는 승격 시점 과제다.

## 결과

- `apps/api/src/conversation/lib/pii-mask.ts`: `maskPii(text): { maskedText, counts }` — DB·Nest 무의존 순수 함수. `counts`는 감사·디버깅용 종류별 건수이며 **원문 조각을 포함하지 않는다**.
- `apps/api/src/conversation/conversation-log.service.ts`: 적재 단일 진입점. 마스킹 + `judgeAnswered` + `buildBotResponseText`(2,000자 절단) 적용 후 저장. 실패는 삼키고 경고만.
- Prisma `ConversationLog`: `userMessage`/`botResponse`에 "마스킹 후 값만 저장" JSDoc 주석 명시.
- seed: **마스킹된 값만** 넣는다. seed에 원문 PII가 있으면 AC-P-8 검증이 seed 때문에 흔들린다.
- `test-automation` 인계(우선순위 3위): AC-P-8을 `maskPii` 단위 테스트 + 통합 테스트 양쪽으로 커버. **`completionMessage` 치환 경로**(슬롯에 전화번호를 넣고 완료 문구에 반영 → 로그의 `botResponse` 확인)를 별도 케이스로 반드시 포함한다.
- `code-reviewer` 인계: ① `ConversationLogService` 밖의 `conversationLog.create` 호출 0건 ② 마스킹 전 원문이 `logger`·예외 메시지·`trace`에 등장하지 않는지.

## 갱신 (2026-09-24 — No.26: 네 번째 적용 지점 = 레거시 송신, 연결 단위 원문 예외)

레거시 API 연동(No.26, **ADR-0034 §9**)의 외부 송신이 **네 번째 적용 지점**이 된다(저장 · RAG 송신 · 증강 송신 · **레거시 송신**). 정책·구현은 불변이며 **함수는 여전히 1벌**(`packages/pii-mask`)이다.

- **대상**: 요청 바인딩 중 **폼 슬롯(사용자 입력) 값**만. 관리자가 작성한 상수 바인딩은 비적용(TC 문장 비적용 선례와 같은 판단).
