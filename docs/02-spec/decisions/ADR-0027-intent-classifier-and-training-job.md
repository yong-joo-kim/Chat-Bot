# ADR-0027 — 경량 의도 분류기의 정의·학습 위치·소비자 한정과 `TrainingJob` 도입

- **상태**: 채택 (Accepted)
- **일자**: 2026-09-22
- **결정자**: system-architect (요구사항 P-5를 이 ADR에서 최종 판정)
- **관련**: `docs/requirements/learning-augmentation.md` **J-5 / J-6 / J-7 / J-8**, FR-0-49, FR-L2-14~37, NFR-LP1/LP5/LP6, NFR-LS4/LS6, AC-L2-9~18, AC-L4-2/5 / ADR-0004(쓰기 주체 없는 스키마 금지) / ADR-0018(학습 인계 지점) / ADR-0024(ml-worker 추론 전용 · `TrainingJob` 유보) / ADR-0008·ADR-0020(엔진 순수성) / ADR-0019(추천은 매칭과 다른 문제)
- **영향 범위**: `apps/api/src/classifier/**`(신설), `apps/api/src/training-jobs/**`(신설), `apps/api/src/learning/**`(추천 출처 분기), `apps/api/prisma/schema.prisma`(`IntentClassifierModel`·`TrainingJob` 신설), 개발명세서 §3·§4·§5·§6
- **세부 설계**: `docs/02-spec/learning-augmentation-설계.md` §7·§9·§12

## 맥락

`TrainingJob` 테이블은 개발명세서 §3에 **2년 가까이 예고만 된 채** ADR-0018·ADR-0024가 연속으로 보류했다. 보류 근거는 한결같이 **"쓰기 주체가 없다 — 상태가 항상 `SUCCEEDED`인 가짜 Job 행만 쌓인다"**(ADR-0004)였고, ADR-0024는 재검토 트리거를 **"No.16·No.21·No.23 착수 → 학습 기능 추가, Job Queue·`TrainingJob` 도입, GPU 필요도 5 복귀"** 로 남겼다.

**이번 그룹이 그 착수 시점이다.** 다만 트리거를 기계적으로 전부 발동시킬 것인지, 항목별로 판정할 것인지가 남아 있었다. 요구사항 문서는 세 대안(A 전면 확장 / B 분리 배치 / C 오프라인 배치)을 정리하고 **B를 권고**하되 최종 판정을 이 ADR로 인계했다.

## 결정

### 1. 분류기는 **저장된 임베딩 위의 다항 로지스틱 회귀**다

| 항목 | 확정 |
|---|---|
| 입력 | 이미 저장된 `EmbeddingVector`(`ownerType ∈ {INTENT_EXAMPLE, INTENT_NAME}`, `status='READY'`, 현재 `modelId`). **재임베딩 0** |
| 라벨 | `EmbeddingVector.ownerId` = `Intent.id` |
| 출력 | `의도 id → 확률`(softmax) |
| 알고리즘 | 다항 로지스틱 회귀 + L2 페널티 + 클래스 불균형 가중치. **외부 ML 라이브러리 의존성 0**(입력이 L2 정규화 벡터라 선형 모델로 충분하다) |
| 학습 규모 | 클래스 수십~수백 · 샘플 수백~수천 → **CPU 수 초** |
| 결정론 | **같은 입력 → 같은 모델.** 샘플 정렬 순서 고정 + 시드 고정 + 고정 epoch 상한 + 수렴 판정 임계값 고정. 테스트 가능성의 전제다 |
| 엔티티 추출 | **학습 모델을 만들지 않는다.** 스팬 라벨 데이터가 0건이라 애초에 학습이 불가능하다 — 사전(gazetteer) + 형태소 분석(ADR-0028)으로 한다 |

학습 데이터는 **이미 라벨링돼 있다** — `(예문, 의도)` 쌍이 곧 지도학습 데이터셋이다. 이것이 이 기능이 "경량"인 근본 이유다.

### 2. **분류기의 소비자는 "미응답 큐의 추천 의도" 1곳뿐이다. 대화 경로는 조회하지 않는다**

| 경로 | 분류기 사용 |
|---|---|
| `resolveTurn()` · `packages/dialogue-engine` · 공개 대화 API · 시뮬레이션 | **사용하지 않는다.** 엔진 패키지에 `classifier`·`augmentation` 심볼이 **0건**임을 정적 검사가 단언한다(AC-L4-2) |
| `GET /chatbots/:id/unanswered-questions`(+상세)의 `suggestedIntents` | **유일한 소비자.** 우선순위 ① 분류기 `READY` & not stale → 확률 ② 아니면 기존 bigram 자카드. **둘을 섞지 않는다** |

- 응답에 **출처(`source: 'CLASSIFIER' | 'LEXICAL'`)를 포함**한다. 이 값이 없으면 관리자는 추천이 왜 갑자기 좋아졌는지/나빠졌는지 알 수 없다.
- 후보 최대 3건 · 최소 확률 0.15 미만 제외(기존 FR-15-15/17 규약 유지).
- 질의 임베딩은 **목록 요청당 배치 1회**(20행 = 1회). 실패 시 자동으로 bigram 폴백.

> **매칭과 추천은 다른 문제다**(ADR-0019 §4가 이미 확립한 원칙). 매칭은 오탐 비용이 높고, 추천은 관리자가 거르므로 낮다. 분류기를 대화 경로에 넣으면 ADR-0020(점수 주입)·ADR-0021(3구간 임계값)·저하 모드·되묻기를 **전부 재설계**해야 하고, 그 회귀 표면은 이 그룹이 주는 가치보다 크다. 또한 1단계 의미 매칭은 사실상 **1-NN 분류기**라 선형 분류기와 기능이 겹친다 — **겹치는 쪽을 대화에서 떼고 겹치지 않는 쪽(확률 캘리브레이션된 라벨 제안)만** 쓴다.

**대화 경로 편입의 재검토 조건**: 골든셋 100문항(AC-N1-12 자산 재사용)에서 분류기 top-1이 1단계 의미 매칭 대비 **+5%p 이상** 높을 때. 그 전에는 편입하지 않으며, 편입은 별도 ADR 사안이다.

### 3. **학습은 `apps/api` 안에서 CPU로 수행한다** — ml-worker로 보내지 않는다 (요구사항 B안 채택)

| 근거 | 내용 |
|---|---|
| **데이터 이동 0** | 학습 입력(수천 개 float32 벡터, 수 MB)이 **이미 `apps/api`의 DB에 있다.** 다른 프로세스로 학습을 보내면 그 벡터를 HTTP로 왕복시켜야 한다 |
| **의존성 0** | 선형 학습은 수치 연산만으로 구현된다. Python·GPU·새 서비스가 필요 없다 |
| **ADR-0024의 핵심 주장이 전부 유지된다** | ml-worker는 여전히 **추론 전용**이고, **모델 파인튜닝은 여전히 없으며**, **Redis/BullMQ도 여전히 없다** |
| **GPU 5 복귀는 근거가 없다** | 실제로 착수해 보니 증강 생성은 *추론*이고(학습이 아니다), 분류기 학습은 *CPU 수 초*다. 트리거를 **기계적으로 전부 발동시키는 것이 아니라 항목별로 판정**하는 것이 옳다(§5 GPU 재산정) |

**감수하는 비용**: Node에서 수치 학습을 직접 구현한다(코드량 증가 — 선형 모델이라 소규모). 다중 인스턴스 전환 시 학습 큐 재설계가 필요하지만 **교체 지점을 1곳으로 국한**한다(§4).

### 4. **`TrainingJob`을 드디어 만든다** — 단, Redis/BullMQ는 여전히 도입하지 않는다 (P-5 최종 판정)

**ADR-0004의 "쓰기 주체가 있는가" 기준을 이번에 통과한다.**

| 보류 근거(ADR-0018/0024) | 이번 상태 |
|---|---|
| 쓰기 주체가 없다 | 생성 작업(`AUGMENT`)·학습 작업(`CLASSIFIER_TRAIN`) **둘 다 실재한다** |
| 상태가 항상 `SUCCEEDED`인 가짜 행만 쌓인다 | **`FAILED`가 실제로 발생한다** — 외부 LLM 타임아웃, 생성 0건, 학습 데이터 부족, **서버 재시작 중 중단**(기동 시 `RUNNING|QUEUED → FAILED(SERVER_RESTART)` 정리). `PARTIAL`도 발생한다(후보 일부만 검증 통과) |
| 진행률이 변하지 않는다 | 생성·검증·학습 단계별로 실제로 변한다 |
| 관리자가 기다릴 이유가 없다 | **화면을 떠났다 돌아와도 결과를 봐야 한다**(AC-L3-10). 상태가 서버에 없으면 이 수용기준을 만족할 수 없다 |

**확정 사항 3건**

1. **Job 적재는 Provider 특성으로 분기하지 않는다 — 항상 적재한다.** 근거: 분기하면 프런트가 "동기 결과"와 "jobId 폴링" 두 응답 형태를 다뤄야 하고, **어느 쪽이 오는지가 서버 환경변수에 달려** 화면 코드가 배포 환경에 종속된다. G1이 수백 ms여도 Job 1행 쓰기 비용은 무시할 만하고, AC-L3-10은 Provider와 무관하게 요구된다. **응답은 항상 `202 Accepted { jobId, status }`, 조회는 폴링 1경로**다.
2. **큐는 단일 인스턴스 in-process**(`ReindexQueueService` 선례). Redis/BullMQ 없음. 챗봇당 동시 1건(증강은 의도당 1건). 다중 인스턴스 전환 시 교체 지점은 `TrainingJobQueue` **1곳**이다.
3. **`resultSummary`에 문장 원문을 담지 않는다**(건수·사유 분포·소요시간만 — NFR-LS4). 로그도 동일하다.

> **`TrainingJob`은 "학습이 대화 반영을 지연시킨다"는 뜻이 아니다.** 이 테이블은 **관리자 화면의 비동기 작업 상태**를 담을 뿐이며, 대화 자산 반영은 여전히 승인 요청 핸들러 안에서 **동기·즉시**로 일어난다(ADR-0025 §5, ADR-0018 보론 §7). 두 개념을 혼동하면 화면이 거짓말을 한다.

### 5. GPU 필요도 항목별 재산정 — **"GPU 5 복귀" 트리거는 발동하지 않는다**

| No | 카탈로그 | 확정 | 근거 |
|---|:---:|:---:|---|
| **16** | 6 | **구성 의존 — G1 `2` / G2 `3` / G3 `6`**. 카탈로그 값 **6은 유지**하고 구성별 값을 각주로 병기 | G1은 규칙·사전 치환(구간 1~2), 검증 임베딩은 **이미 돌고 있는 추론의 재사용**이라 신규 부하가 아니다. G2는 자체 GPU 0(외부 위임 — No.30을 8→1로 재산정한 것과 같은 논리). **PM이 G3를 승인하고 24GB+ GPU를 확보했으므로 6을 하향할 근거가 사라졌다** — 요구사항의 "2~3 재산정" 제안은 *GPU 미보유 전제*였고 그 전제가 바뀌었다 |
| **23** | 4 | **3** (확정) | 학습 입력이 이미 계산된 벡터라 재임베딩이 없고, 선형 학습은 5,000샘플 CPU 수 초다. 기준표 3~4 구간("경량 ML(CPU 가능)")의 **하단** |
| 그룹 종합 | — | **기본 구성 `2` / G2 구성 `3` / G3 구성 `6`** | 최댓값 기준 |

### 6. 모델 산출물 규약

| 항목 | 확정 |
|---|---|
| 보관 | `IntentClassifierModel` **챗봇당 1행**(`chatbotId`가 PK). 버전 이력·A/B·롤백은 **범위 밖** — 대화에 관여하지 않아 롤백 필요성이 낮고 재학습이 수 초다 |
| 직렬화 | 가중치 `[classCount × dimension]` row-major + 절편 `[classCount]`, 둘 다 **base64(Float32Array little-endian)** — `EmbeddingVector.vector`와 **같은 코덱 1벌**(`embedding/lib/vector-codec.ts`)을 재사용한다 |
| 쓰기 | **원자적 1회 쓰기**(upsert). 학습 중 서버가 죽어도 모델 파일이 반쯤 쓰이지 않는다(EX-L2-7) |
| 크기 상한 | 기본 8MB 초과 시 `422`(의도 수 × 차원이 비정상적으로 큰 경우의 방어). 의도 300 × 1024차원 ≈ 1.2MB로 여유가 크다 |
| stale 3조건 | ① 학습 `modelId` ≠ 현재 → **즉시 사용 중지**(정확도 문제가 아니라 **입력 공간이 다르다**) ② 의도 집합 10% 이상 변경 ③ 학습 후 예문 50건 초과 추가 → ②③은 **경고만**(계속 사용) |
| 프라이버시 | 가중치는 임베딩의 선형 결합이며 대화 원문을 담지 않는다. 단 **`chatbotId` 스코프를 넘어 공유하지 않는다** |
| 감사 | 학습·삭제는 **감사 대상이 아니다**(대화 자산을 바꾸지 않으며, 기록하면 `AuditTargetType`을 확장해야 한다 — FR-15-35와 동일 판단) |
| 자동 재학습 | **스케줄을 만들지 않는다.** 관리자 트리거이거나, 화면이 "재학습 권장" 배지를 띄우는 것까지다(스케줄러 인프라 부재 + 관리자가 모르는 사이 추천 품질이 바뀌는 것을 막는다) |

### 7. `POST .../intent-classifier/train`은 ADR-0018의 K-6에 저촉되지 않는다

K-6("수동 트리거 API를 만들지 않는다")의 금지 취지는 **"학습 중이니 기다려야 한다는 잘못된 모델을 관리자에게 심지 마라"** 였다. 이 엔드포인트는 **대화 반영 트리거가 아니라 추천 품질 도구**이며, 실제로 시간이 걸리고 실제로 결과가 바뀐다 — 내부가 no-op인 가짜 API가 아니다.

**단 화면이 이것이 대화 반영과 무관함을 명시해야 한다**(FR-L3-8) — "재학습은 추천 의도 품질에만 영향을 주며, 예문·키워드 반영은 저장 즉시 대화에 적용됩니다".

## 근거

- **학습 입력이 있는 곳에서 학습한다.** 수 MB의 벡터를 HTTP로 왕복시키는 아키텍처는 프로세스 분리의 이득(격리)보다 비용(직렬화·지연·실패 모드 추가)이 크다. ADR-0024가 임베딩을 분리한 이유는 *모델 런타임이 Python이어야 해서*였지, 분리 자체가 목적이 아니었다.
- **ADR-0024의 트리거를 항목별로 판정하는 것이 트리거의 취지다.** 트리거는 "이때 다시 생각하라"는 뜻이지 "이때 자동으로 이렇게 하라"가 아니다. 다시 생각한 결과 3개 항목 중 **`TrainingJob`만 발동**하고 학습 위치·GPU 등급은 발동하지 않았다.
- **`TrainingJob` 도입 판정 기준은 ADR-0004 하나뿐이다.** "쓰기 주체가 있는가"에 이번에 처음으로 **예**가 나왔다. 기준을 바꾼 것이 아니라 현실이 기준을 충족했다.
- **분류기를 대화에서 떼는 것이 이 그룹의 회귀 표면을 0으로 만든다.** `packages/dialogue-engine` 파일 변경 0건 · 공개 대화 API 성능 영향 0 · 기존 테스트 전체 무수정 통과가 그 결과다.
- **항상 Job으로 통일하는 것이 프런트 복잡도를 줄인다.** "서버 설정에 따라 응답 형태가 달라진다"는 계약은 테스트 조합을 2배로 만들고, 환경별로만 재현되는 버그를 만든다.

## 대안과 트레이드오프

| 대안 | 기각 사유 |
|---|---|
| **A. 전면 확장**(ml-worker 학습 엔드포인트 + Redis/BullMQ + GPU 5 복귀) | ① Redis가 **새 인프라 의존**으로 들어와 구축형 설치 절차가 늘어난다 ② 학습 입력이 `apps/api` DB에 있는데 벡터를 HTTP로 왕복시켜야 한다 ③ GPU 5 복귀는 **실제 연산 성격과 맞지 않는다**(선형 학습은 CPU 수 초) |
| **C. 오프라인 CLI 배치** | "**관리자 확인 후**"가 요구사항 본문인데 워크플로우가 화면에 없다. 운영자가 서버 셸에 접근해야 한다 |
| **분류기를 대화 매칭에 사용** | ADR-0020/0021을 재설계해야 하고, 1단계 의미 매칭(1-NN)과 기능이 겹치며, 저하 모드·되묻기가 전부 흔들린다. 재검토 조건(+5%p)을 명시해 두는 것으로 충분하다 |
| **분류기 확률과 bigram을 가중 결합** | 또 하나의 보정 과제(가중치는 얼마인가, 모델이 바뀌면 어떻게 되는가)를 만든다. 우선순위 선택 + 출처 표시가 관리자에게 더 정직하다 |
| **`TrainingJob` 없이 동기 처리** | AC-L3-10(화면 이탈 후 재진입 시 상태 조회)을 만족할 수 없고, 외부 LLM 구성에서 HTTP 요청이 30초 열려 있게 된다 |
| **Job 적재를 Provider 특성으로 분기** | 응답 형태가 서버 환경변수에 종속돼 프런트가 두 경로를 유지해야 한다. G1의 Job 1행 쓰기는 무시할 만한 비용이다 |
| **모델 버전 이력 테이블 도입** | 대화에 관여하지 않아 롤백 필요성이 낮고 재학습이 수 초다. 대화 경로 편입 시 **자동으로 필요해지므로** 그때 만든다 |
| **자동 재학습 스케줄** | 스케줄러 인프라가 없고(선행 그룹과 동일 판단), 관리자가 인지하지 못한 채 추천 품질이 바뀐다 |
| **외부 ML 라이브러리(tfjs 등) 도입** | 네이티브 빌드·모델 포맷·번들 크기를 끌고 들어온다. L2 정규화 입력 위의 선형 모델에는 과하다 |

**감수하는 비용**

1. **Node에서 수치 학습을 직접 구현한다** → 순수 함수로 분리해 단위 테스트 1차 대상으로 삼고, 결정론을 규약으로 못 박아 검증 가능하게 한다.
2. **학습이 API 프로세스의 CPU를 쓴다** → 배치 간 양보(재색인 큐와 같은 규약)로 다른 API P95 지연 증가를 20% 미만으로 유지한다(AC-L2-17). 상한 5,000샘플 30초.
3. **`TrainingJob`이 단일 인스턴스 전제다** → 교체 지점 1곳(`TrainingJobQueue`)과 기동 시 고아 Job 정리로 관리한다.
4. **추천 품질이 재학습 시점에 의존한다** → stale 배지 + "학습 시점: N일 전" 병기로 **낡음을 화면이 먼저 말한다**.

## 재검토 트리거

- **골든셋에서 분류기 top-1이 1단계 의미 매칭 대비 +5%p 이상** → 대화 경로 편입을 별도 ADR로 재검토(그 순간 버전 이력·롤백·A/B가 자동으로 필요해진다).
- **다중 인스턴스 전환** → `TrainingJobQueue`를 분산 큐(Redis/BullMQ)로 교체. **그때가 ADR-0024 §2를 실제로 뒤집는 시점**이다.

- **`TrainingJob` 행이 정리 없이 누적** → 보존기간 정책·정리 배치 도입(스케줄러 인프라와 함께, No.45).

## 갱신 (2026-09-23 — 큐가 학습 외 첫 소비자를 얻었다)

검증/품질 고도화의 **대량 TC 실행**이 `TrainingJobQueue`의 **세 번째이자 학습이 아닌 첫 소비자**가 된다. **이 ADR의 결정(단일 인스턴스 in-process 큐 · Redis/BullMQ 미도입 · 교체 지점 1곳)은 불변**이며, 다음 두 가지만 기록한다.

**① `TrainingJob`에 `TC_RUN` kind를 추가하지 않는다.** `TestRun`은 **영속 비교 자산**(보존 정책이 다르다)이고, `resultSummary`의 **"문장 원문 미포함" 규약(NFR-LS4)** 과 충돌하며, `TestRun`이 이미 상태·진행률·시각을 가져야 해 **값이 두 벌**이 된다. "Training"이 아닌 작업이 `TrainingJob`에 들어가지 않는다.

**② ⚠ 코드 재확인 — 큐는 완전한 kind-agnostic이 아니었다.** `TrainingJobQueue.run()`은 `task` 콜백만 받지만 내부에서 `TrainingJobService.markRunning/updateProgress/markFinished(jobId)`를 호출하므로 **`jobId`가 `TrainingJob` 행일 것을 전제**한다. 따라서 상태 기록을 **`AsyncJobStatusSink` 포트로 분리**하고 `enqueue(jobId, task, sink = this.jobs)`로 **기본 인자를 둬 기존 호출부 2곳(augmentation·classifier)을 변경 0건**으로 유지한다. `TrainingJobService`가 그 포트의 첫 구현, `TestRunStatusSink`가 두 번째다. **교체 지점은 여전히 1곳**이며, 다중 인스턴스 전환 시에도 이 파일 하나만 바뀐다.

**큐 클래스는 개명하지 않는다** — 순수 리네임이 `training-jobs` 모듈·테이블·컨트롤러·`TrainingJobService`로 번지는 데 비해 의미 불일치는 이미 싱크 분리로 해소됐다. `markFinished`는 **현재 상태가 `CANCELLED`인 행을 덮어쓰지 않는다**(취소 CAS). 기동 시 고아 작업 정리(`SERVER_RESTART`) 규약은 `TestRun`에도 **같은 시점·같은 방식**으로 적용한다.

## 갱신 (2026-09-23 — stale 조건 ③은 예문 **감소**를 감지하지 않는다 · 복원 시 모델 삭제)

**코드 확인 사실**: `classifier/lib/stale-judge.ts`의 `EXAMPLES_DRIFTED`는 `currentExampleCount − exampleCountAtTrain > 50` — **증가만** 판정한다(`INTENTS_DRIFTED`는 절대값 10%라 양방향이다). 따라서 "증강 50건 승인 → 재학습 → 증강을 되돌림(예문 감소)" 경로에서 **stale이 뜨지 않고, 증강분으로 학습된 모델이 미응답 큐 추천에 계속 쓰인다.**

**결정(ADR-0031 §5)**: 챗봇 복원/버전 이력관리의 **복원은 같은 트랜잭션에서 `IntentClassifierModel` 행을 삭제**한다. 추천은 즉시 LEXICAL(bigram)로 복귀하고 상태 API는 `NOT_TRAINED`를 보고하며, 화면은 "복원 후 재학습이 필요합니다"를 안내한다. 재학습은 수 초이고 대화 경로와 무관하므로(이 ADR §1) 삭제가 가장 싸고 확실하다. 모델 버전 이력을 만들지 않는다는 §6의 결정은 **불변**이다.

**조건 ③을 절대값(`|Δ| > 50`)으로 바꿀지는 별도 판단**으로 남긴다 — 복원 경로는 삭제로 우회하므로 이번에 필수가 아니다. 단 복원이 아닌 경로(관리자가 예문을 대량 수동 삭제)에서도 같은 틈이 있으므로, **재검토 트리거**: "예문 대량 삭제 후 추천 품질 저하"가 보고될 때 조건 ③을 절대값으로 정밀화한다(순수 함수 1곳 수정).

**진행 중 작업과의 관계**: 복원은 이 챗봇의 `TrainingJob`이 `QUEUED`/`RUNNING`이면 `409 RESTORE_BLOCKED_BY_ACTIVE_JOB`으로 거부한다 — 학습은 끝나면서 **복원 전 데이터로 학습한 모델을 upsert**하므로 복원과 뒤섞인 결과를 만든다. 이 판정은 복원 쓰기 트랜잭션 안에서 이뤄져 **DB 직렬화로 TOCTOU가 없다**. 큐·`TrainingJobService`는 **변경 0건**이다.

## 갱신 (2026-09-23 — 예약 실행 엔진은 임대(lease) 기반 정리를 쓴다 · 진행 중 작업은 예약 복원의 일시적 원인)

운영 예약 배포(No.28, ADR-0032)가 두 번째 백그라운드 실행 주체(인프로세스 폴링 엔진)를 도입한다. **이 ADR의 결정(단일 인스턴스 in-process 큐 · Redis/BullMQ 미도입 · 기동 시 고아 Job 정리 `SERVER_RESTART`)은 불변**이며, 다음을 기록한다.

1. **예약 엔진은 "기동 시 잔존 = 전부 고아" 가정을 반복하지 않는다.** 선점 시각(`claimedAt`) + 임대(기본 5분)를 넘긴 `RUNNING`만 회수하고, 재실행이 아니라 **실제 상태로 판정**한다. 다른 인스턴스가 정상 실행 중일 수 있기 때문이다.
2. **재검토 트리거 보강**: "다중 인스턴스 전환" 시 `TrainingJob`·`TestRun`의 기동 시 고아 정리도 **같은 임대 방식**(선점 시각 컬럼 + 만료 판정)으로 교체한다 — 현재 방식은 다른 인스턴스의 실행 중 작업을 `SERVER_RESTART`로 잘못 종결한다. 교체 지점은 각 서비스의 `onModuleInit` 1곳씩이며, 판정 순수 함수는 `common/polling/lease.ts`를 재사용할 수 있다.
3. **진행 중 작업과 예약 복원**: 예약 복원 시각에 이 챗봇의 `TrainingJob`/`TestRun`이 `QUEUED`/`RUNNING`이면 `restore()`가 `409 RESTORE_BLOCKED_BY_ACTIVE_JOB`을 반환하고, 예약 엔진은 이를 **일시적 원인**으로 분류해 폴링 주기마다 최대 15분 재시도한다(초과 시 `FAILED(BLOCKED_TOO_LONG)`). 큐·`TrainingJobService`·`TestRunService`는 **변경 0건**이다(예약 엔진은 큐를 쓰지 않는다 — 시각 트리거이지 작업 큐가 아니다).
4. **자동 재학습 스케줄 기각(§대안)은 불변**이다 — 스케줄러 인프라가 생겼어도 "관리자가 인지하지 못한 채 추천 품질이 바뀐다"는 기각 사유는 그대로다. 예약 엔진은 관리자가 미리보기로 승인한 반영 동작만 실행한다.
