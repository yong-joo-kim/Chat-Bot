- **결정자**: system-architect (엣지 의미·규모·Ollama 지위·상한 20은 사용자 확정 — 2026-09-30, 요구사항 §11 P-1~P-3 · P-4~P-11은 권고안 채택)

## 맥락

카탈로그 No.37은 "경량화(양자화) 모델을 단말/엣지에서 구동, 지연시간·유출 최소화 · 구축형 ○ · 구독형 ✕"다. 코드를 보면 이 제품에서 그 말이 가리킬 수 있는 것의 대부분이 이미 있다 — 대화 경로의 유일한 모델(임베딩)은 CPU 기본값으로 예산 안(P95 126~159ms)이고, 우리 쪽 생성모델은 관리자 배치(예문 늘리기 G3) 1곳뿐이며 규칙 기반(G1)이 바닥이고, 4GB GPU에서 양자화 모델을 부르는 Ollama 백엔드가 `adf536e`로 커밋돼 있다. 사용자는 2026-09-30에 **엣지 = 고객사 사내 소형 서버(E1)**, **규모 (A) — ml-worker에 vLLM 백엔드 + 경량 구성 정리 + 상한·표시·주소 통제 + 등급표/설치 문서, API·위젯·엔진·화면 변경 0**, **Ollama = 경량 설치 구성(동작 보장·품질 미보증) · 1회 상한 20건 · 초과는 400이 아니라 상한까지만**을 확정했다. 결정할 것은 여섯 가지다.

1. "엣지"의 뜻과 하지 않을 것.
2. 운영 vLLM을 **어디에** 붙이나 — API의 새 Provider인가, ml-worker의 새 백엔드인가.
3. 경량 상한 20을 **어디서** 적용하나.
4. "품질 미보증"을 API·화면 변경 없이 어떻게 드러내나.
5. API 30초 뒤에도 ml-worker가 90초까지 백엔드를 붙잡는 **헛일**을 어떻게 줄이나.
6. 마스킹 없는 시드가 나가는 **ml-worker → 생성 백엔드** 구간(API 출구 게이트 밖)을 어떻게 통제하나.

## 결정

### 1. 엣지 = 고객사 사내 소형 서버(E1). 브라우저·휴대폰 안 추론과 다지점 원격관리는 하지 않는다

"엣지"는 **구축형 설치 구성의 문제**로 다룬다. 새 기능을 만드는 것이 아니라 "GPU가 없거나 작은 서버 한 대에서 무엇이 어떻게 도는가"를 **설정·등급표·설치 절차**로 확정하는 것이다. 브라우저 안 추론(E3)은 위젯 gzip 100KB·런타임 의존성 0(ADR-0012)과 정면 충돌하고, 챗봇 자산 전체를 단말로 내려야 해 오히려 유출이 커진다. 다지점(E2)은 서버 1대·SQLite·in-process 큐 전제(ADR-0024 §2)와 맞지 않는다. 대화 경로에 우리 쪽 LLM을 넣는 일도 하지 않는다(생성형 답변은 외부 RAG 소관 — No.30).

### 2. 생성 백엔드 3종(`transformers`·`ollama`·`vllm`)은 **ml-worker 안에서만** 고른다. API 포트·팩토리·출구 클래스는 불변

- 교체 지점은 `_load_generator()` **1곳**, 선택은 환경변수 `GENERATION_BACKEND` 1개. **알 수 없는 값은 생성 프로세스 기동 실패**(지금은 조용히 `transformers`로 떨어진다). 검사는 생성 프로세스에서만 — 임베딩 전용 프로세스는 영향 없음.
- 모든 백엔드가 `Generator` 계약(`model_id`·`generate()` 실패 시 빈 배열·`healthy()`)과 **같은 프롬프트 문자열(`build_prompt`)** 을 쓴다. 다른 것은 전송 형식뿐이다.
- **vLLM = OpenAI 호환 대화형 API(`/v1/chat/completions`) · 단일 `user` 메시지.** 완성형(`/v1/completions`)은 지시 튜닝 모델의 대화 템플릿을 적용하지 않아 품질이 급락하고, Ollama `/api/generate`(비`raw`)가 서버 쪽 템플릿을 적용하는 것과도 어긋난다. `system` 역할을 나누지 않는 것은 일부 모델 템플릿이 그 역할을 지원하지 않기 때문이다. 기동 시 `/v1/models`로 서버·모델을 확인하고 실패하면 **기동 실패**(조용한 mock 대체 없음 — Ollama와 같은 원칙).
- 공개 `modelId`는 `<backend>:<모델>`(`ollama:` 현행 · `vllm:` 신규). `transformers`는 현행 `<모델>@<rev>` 그대로.
- 설정 이름 규칙: **백엔드 전용 = `<백엔드>_` 접두**(`OLLAMA_*` 현행 그대로 · `VLLM_*` 신규), **공통·계약 = `GENERATION_*`**. 옛 이름을 바꾸지 않으므로 병행 읽기가 필요 없다.
- **SDK·새 의존성 0** — 기존 `httpx`로 직접 호출한다(ADR-0026 §4와 같은 이유: 전송·재시도 정책이 통제 밖으로 나가지 않게).

### 3. 경량 상한은 **ml-worker `/augment` 안에서 절삭**한다(400 아님 · API 요청 수 조정 아님)

`/augment` 처리 순서: ① 시드 상한·계약 상한(`targetCount` ≤ 60) 초과는 **현행대로 400** → ② `effective = min(targetCount, generator.target_cap)` → ③ 생성 → ④ **결과도 `effective`건으로 자름**. `OLLAMA_TARGET_CAP` 기본 20(P-3), `VLLM_TARGET_CAP` 기본 60(= 계약 상한 — No.17 실측 전까지 절삭 효과 없음), `transformers`는 계약 상한 그대로(기본 구성·mock 경로 응답 바이트 동일). 상한은 **백엔드를 아는 쪽**에 있어야 하고(API는 백엔드를 모른다), 응답 계약상 후보 수 보장이 원래 없으며, API를 바꾸지 않는다.

### 4. "품질 미보증"은 **ml-worker 상태 보고·기동 로그·운영 문서**로 드러낸다 — 콘솔 문구는 이번에 없다

- `Generator`에 선택 속성 `backend`·`profile`(`standard`|`lightweight`)·`target_cap`을 두고, **`OllamaGenerator`만 `profile="lightweight"`**. `/augment/health`에 선택 필드 `backend`·`profile`·`targetCap`을 더한다. API의 zod 스키마는 모르는 키를 버리므로(strip) **API 동작은 바이트 동일**하다.
- 원격 백엔드면 `device="external"` — 연산 위치(CPU/GPU 분산)를 ml-worker가 모르므로 설정값 `cuda`를 사실처럼 보고하지 않는다. `transformers`는 현행 그대로.
- `profile="standard"`는 **품질 보증이 아니다** — 운영 구성의 모델을 켜도 되는지는 No.17 실측·합격 판정이 정한다(P-5). 3050·경량 구성 결과는 "동작 확인"으로만 기록한다.
- 요구사항 FR-ED6-2(콘솔·capability의 "사내 경량 모델 — 품질 미보증" 글자 표시)는 capability 스키마와 콘솔을 바꿔야 해 **P-2(API·화면 변경 0)와 충돌** → 이번에 하지 않고 No.17 운영 채택 때 함께 설계한다(재검토 트리거).

### 5. 원격 요청 시간 제한 기본값을 **25초**로 — API(30초)보다 먼저 포기한다

FastAPI 동기 핸들러는 API가 연결을 끊어도 계속 돈다. 그래서 API 쪽 30초 포기만으로는 ml-worker가 `OLLAMA_REQUEST_TIMEOUT_S=90`까지 백엔드를 붙잡았다. ml-worker 자신이 25초에 연결을 닫으면 스레드가 풀리고, 백엔드는 연결 종료를 감지해 생성을 멈출 수 있다(엔진 버전 의존 — 확인 사항). `OLLAMA_REQUEST_TIMEOUT_S` 90 → 25, `VLLM_REQUEST_TIMEOUT_S` 25, 워밍업만 별도 `GENERATION_WARMUP_TIMEOUT_S` 120(첫 호출은 모델 적재). 30초를 넘게 설정하면 **기동 경고**(ml-worker는 API 값을 모른다). 취소 전달(계약 확장)은 하지 않는다(P-9).

### 6. 생성 백엔드 주소는 **루프백·사설 대역 또는 명시 허용 목록**만 — ml-worker 자체 검사

- API 출구 게이트(ADR-0040)는 API → ml-worker까지만 보고, G3 시드는 사내 전송 전제로 **마스킹하지 않는다**(ADR-0026 171행). 그 전제를 ml-worker → 백엔드 구간에서 보장하는 장치가 없었다.
- ml-worker는 DB·API 설정을 읽지 않으므로(ADR-0024 §갱신 1-③) **ml-worker 안의 순수 함수**(`backend_guard`)로 판정한다: 스킴 http/https · URL 사용자 정보 금지 · 링크로컬(메타데이터)·미지정·멀티캐스트 **항상 금지** · 허용 목록(`GENERATION_BACKEND_ALLOWED_HOSTS` — API의 `DATA_EGRESS_ALLOWED_HOSTS`와 같은 형식) 우선 · 그 외 루프백(`127/8`·`::1`)·사설(`10/8`·`172.16/12`·`192.168/16`·`fc00::/7`)·`localhost`만 허용 · 이름은 기동 시 해석한 **모든** 주소가 조건을 만족해야 허용. `GENERATION_BACKEND_REQUIRE_ALLOWLIST=true`면 사설·루프백도 목록 필수(거버넌스 설치용).
- 검사는 **생성기 생성 전**(실패 시 연결 0) · 원격 HTTP 클라이언트는 **리다이렉트를 따라가지 않는다**(허용 주소가 다른 곳으로 넘기는 우회 차단).
- API 출구 클래스 **7종 불변** · 데이터 지도 변경 없음(운영 문서로 구간 명시).
- 생성 전용 vLLM만 지원(P-4). **외부 RAG의 vLLM을 ml-worker가 직접 부르는 구성은 지원하지 않는다** — ADR-0022의 외부 RAG 접촉면 봉인을 우회하고 RAG 답변 지연·장애가 섞인다. ml-worker는 RAG 주소를 모르므로 설치 점검 항목으로 둔다.
- 비밀값 `VLLM_API_KEY`는 `SecretStr` · `Authorization: Bearer` 헤더로만 · 로그·상태·오류에 0건(오류에는 호스트만).

### 7. 잘린 출력은 원격 백엔드에서만 **닫힌 원소만 복구**한다

잘림 신호(`done_reason`/`finish_reason == "length"`)가 있으면 JSON 배열에서 **완결된 문자열 원소만** 순서대로 꺼내고 미완 원소는 버린다(3050 실측의 "잘린 190자 문자열 통째 = 후보 1개 → 우연히 검증 통과" 경로 차단). 파싱 전 `<think>` 블록을 제거한다. 공용 `parse_candidate_array()`는 바꾸지 않는다(`transformers` 경로·기존 시험 불변).

## 근거

- **경계는 이미 그어져 있다.** ADR-0026 §5는 "API는 모델·서빙 엔진·프롬프트 규칙을 모른다"고 정했고, Ollama가 그 자리에 API 변경 0으로 들어가 동작함이 실증됐다(`adf536e` · 보고서 §5). vLLM은 같은 틀의 세 번째 구현일 뿐이다 — ADR-0026 재검토 트리거가 예상한 "API 유니온 확장"은 **필요하지 않았다.**
- **상한은 백엔드를 아는 쪽에.** 3050 실측에서 20건은 ≈13초에 정상, 60건은 "53초(초과)" 또는 "28초지만 붕괴"였다. API가 60건을 요청하는 것은 모든 백엔드에 같은 규칙이고(`MAX_RAW_TARGET`), 무엇이 한계인지는 백엔드가 안다.
- **표시는 되돌리기 쉬운 곳부터.** API·콘솔 변경은 스키마·화면·시험·접근성 검토를 끌고 온다. 선택 필드는 API가 버리므로 위험 0이고, No.17 채택 판정 때 한 번에 올리면 된다.
- **헛일은 가장 싼 방법으로.** 취소 전달은 계약 확장이 필요하다. 시간 제한 정렬은 기본값 한 줄이다.
- **주소 통제는 "사내 전송 전제"의 증명이다.** 마스킹을 하지 않는 근거가 "사내"라면, 그 "사내"를 기계가 확인해야 한다. 기본 허용 범위를 루프백·사설로 두면 권장 구성(같은 서버 Ollama · 사내 vLLM)은 설정 없이 통과한다.

## 대안과 트레이드오프

| 대안 | 기각 사유 |
|---|---|
| **API에 `vllm` Provider(G4)를 새로 둔다** | 포트 유니온·팩토리·capability·출구 클래스(7 → 8)·데이터 지도·설정 검증·시험이 전부 바뀌고, 프롬프트·파싱 규약이 Python/TS 두 벌이 된다. P-2(API 변경 0) 위반 |
| **OpenAI 공식 SDK 사용** | 재시도·로깅·리다이렉트 정책이 통제 밖. 접촉면이 경로 2개라 직접 호출 비용이 작다 |
| **vLLM 완성형 API(`/v1/completions`)** | 대화 템플릿 미적용 → 지시 튜닝 모델 품질 급락 · Ollama 경로와 입력이 달라진다 |
| **상한 초과를 400으로 거부** | API가 매번 G1로 폴백 — 경량 구성을 켜도 사실상 G1만 쓴다 |
| **API가 capability로 상한을 받아 요청 수를 줄임** | API·스키마 변경. 이득은 요청 바이트뿐 |
| **여러 번 나눠 60건 채우기** | 3050에서 합계 ≈39초 > 30초 |
| **콘솔에 경량 표식 추가(capability 선택 키)** | 이번 PM 결정(화면·API 변경 0)과 충돌 — No.17 채택 때 |
| **취소 전달(요청 ID + 취소 경로 또는 비동기 핸들러의 연결 끊김 감지)** | `/augment` 계약 확장 · API 변경. 정렬 권고값으로 먼저 상한을 둔다 |
| **주소 통제를 문서 안내만으로** | 마스킹 없는 시드가 나가는 구간을 약속으로만 막게 된다(P-8 기각) |
| **ml-worker가 API의 거버넌스 모드·허용 목록을 읽는다** | ml-worker DB·API 설정 무접근 원칙 위반. 같은 형식의 별도 키 + 선택 스위치로 정렬만 한다 |
| **공용 파서에 잘림 복구를 넣는다** | `transformers` 경로와 기존 시험 결과가 바뀐다 — 원격 백엔드 + 잘림 신호일 때만 쓴다 |
| **구조화 출력(JSON 스키마 강제 디코딩) 도입** | 엔진 버전별 인자가 다르고 실측 근거가 없다 — No.17에서 형식 오류율이 높으면 재검토 |

**감수하는 비용**

1. **경량 구성에서는 요청 1회의 제안 수가 줄어든다**(최대 20건 생성 → 검증 통과분). 대신 시간 안에 온다.
2. **기존 설치 동작이 조금 바뀐다** — Ollama 시간 제한 90 → 25초 · 공인 주소 Ollama는 기동 실패 · 알 수 없는 백엔드 값은 기동 실패 · Ollama 최대 토큰 512 → 768(명시 설정 없을 때). 전부 의도된 변경이며 설계서 §17에 목록으로 둔다.
3. **콘솔은 여전히 "로컬 생성모델"만 안다** — 경량 여부는 상태 보고·로그·문서로만 보인다.
4. **데이터 지도에 ml-worker → 백엔드 구간이 없다** — 운영 문서로 대체.
5. **이름 해석은 기동 시 1회**(DNS 재바인딩 잔여 위험) — IP 리터럴·hosts 고정 권장.

## 알려진 한계

- 생성 백엔드 주소의 이름 해석은 기동 시 1회만 검사하므로 이후 DNS가 바뀌면(재바인딩) 주소 통제가 우회될 수 있다. 통제가 필요한 설치는 IP 리터럴 또는 hosts 파일 고정으로 지정하고, 요청 시점 재해석 검사는 재검토 트리거로 남긴다.
- 허용목록(`GENERATION_BACKEND_ALLOWED_HOSTS`)에 든 호스트는 해석된 IP가 공인 대역이어도 통과한다. 링크로컬·미지정·멀티캐스트 주소만 목록과 무관하게 항상 거부된다.

## 재검토 트리거

- **요청 시점 이름 재해석 검사** → 위 "알려진 한계"의 DNS 재바인딩 우회를 막아야 하는 설치가 생기면 도입.

- **No.17 운영 채택 판정** → `VLLM_TARGET_CAP`·`VLLM_MAX_NEW_TOKENS` 기본값 확정 + capability·콘솔에 생성기 구성 표식(`backend`·`profile`)을 올리는 API 변경을 함께 설계.
- **운영 실측에서 형식 오류·잘림률이 높음** → 구조화 출력 강제 디코딩.
- **느린 장비에서 25초 정렬로도 헛일이 다음 요청을 막음** → 취소 전달(`/augment` 계약 확장).
- **두 번째 LLM 소비자 착수** → `packages/llm-provider` 승격(ADR-0026 §6 — 백엔드 수는 소비자 수가 아니다). → **2026-09-30 발동·미승격(No.21 묶음 이름 제안 — ADR-0047 §8)**. 트리거는 ADR-0026 갱신(2026-09-30b)의 정밀화 문구를 따른다.

## 갱신 (2026-09-30 — No.21: 생성 프로파일의 두 번째 선택 경로 `/cluster-label`)

발화 묶음 분석(No.21, **ADR-0047 §7**). §2~§6의 결정(백엔드 3종은 ml-worker 안에서만 · 경량 상한 · 주소 통제 · 시간 제한 25초 · 리다이렉트 비추적 · 비밀값 규약)은 **불변**이다.

1. 생성 프로파일(`ML_WORKER_ROLE=augment｜both`)에 **`POST /cluster-label`**(묶음 이름 제안)을 더한다 — 임베딩 프로파일에는 없다(404). 같은 생성기(`_load_generator()`가 만든 1개)·같은 백엔드·같은 주소 통제·같은 원격 시간 제한을 쓴다. 모델·백엔드는 생성 프로세스 설정(`GENERATION_BACKEND`·`OLLAMA_MODEL`·`VLLM_MODEL`·`GENERATION_MODEL_ID`)을 따르며 API·코드에 모델 이름 0.
2. **봉인 갱신**: ED-2(`/augment` 모델)·ED-4(`build_prompt`·`SYSTEM_INSTRUCTION`·`parse_candidate_array` 불변)·ED-7·ED-8·ED-9·ED-11은 **그대로**다 — 이름 전용 `build_label_prompt()`·`parse_label()`을 별도로 둔다(입력은 JSON 데이터 블록으로만). **ED-10 "생성 백엔드 호출은 `/augment` 처리와 기동 워밍업 외 0"은 "… 와 `/cluster-label` 처리 외 0"으로 넓힌다**(대화 경로 호출 0은 불변). ED-5(HF·Mock 본문 불변)의 취지는 유지하되, 각 생성기에 **선택 메서드 `label()`을 추가**한다(기존 메서드 본문 불변 · 실패 = `None` · 예외 금지).
3. 이름 제안의 최대 토큰은 `CLUSTER_LABEL_MAX_NEW_TOKENS`(기본 64) · 계약 상한(키워드 ≤20 · 표본 ≤5)을 넘으면 400.
4. 3050·경량 구성의 이름 제안 결과는 **"동작 확인"만** — 이름 품질·지연 판정은 운영 모델 채택(No.17) 뒤.
