# ADR-0028 — 한국어 형태소 분석기 도입(프로젝트 최초의 선택적 네이티브 의존성)과 구축형 설치 영향

- **상태**: 채택 (Accepted)
- **일자**: 2026-09-22
- **결정자**: system-architect (PM 확정사항 2 — 요구사항 P-4를 **"도입"으로 승인**. 요구사항 J-10의 "1차 미도입" 권고를 뒤집는다)
- **관련**: `docs/requirements/learning-augmentation.md` **J-10**(권고 번복), FR-L2-1~13, NFR-LP4, NFR-LM1, AC-L2-1~4, EX-L2-1/2/3 / 개발명세서 §5 "배포형태 중립"(네이티브 의존성 금지 원칙의 **정밀화**) / ADR-0020(사전 계산 결과 주입 패턴) / ADR-0024(런타임 선택의 판단 틀) / ADR-0006(정규화 단일 소스)
- **영향 범위**: `apps/api/src/learning/morph/**`(신설), `apps/api/src/learning/lib/decompose.ts`(순수 함수), 개발명세서 §2·§5·§5.1·§6, 배포·설치 문서(`docs/05-ops/`)
- **세부 설계**: `docs/02-spec/learning-augmentation-설계.md` §6·§11

## 맥락

No.23의 "미응답 질문을 **낱개 요소로 분리**해 인텐트·엔티티 부여"는 문장을 스팬으로 쪼개는 작업이다. 요구사항 문서는 **J-10에서 형태소 분석기 도입을 1차 보류**하고(공백 토큰 + gazetteer 최장일치 + 조사 절단 휴리스틱), PM 확인 항목 P-4로 인계했다. 보류 근거는 셋이었다.

1. 네이티브 빌드·사전 파일 배포가 **구축형 설치 절차를 무겁게** 한다.
2. 모노레포에 프로세스나 네이티브 바인딩 의존성이 늘어난다.
3. 분해 결과의 소비자가 **관리자 화면 1곳**이라 정밀도 요구가 높지 않다(관리자가 칩 경계를 직접 고칠 수 있다).

**PM은 도입으로 확정했다.** 동시에 이 프로젝트에는 정면으로 충돌하는 기존 원칙이 있다 — 개발명세서 §5: *"네이티브 빌드가 필요한 의존성(bcrypt/argon2 등)은 **온프레미스 설치 실패 위험** 때문에 도입하지 않는다."* 이 ADR은 그 원칙을 **폐기하지 않고 정밀화**해 두 요구를 동시에 만족시킨다.

## 결정

### 1. 형태소 분석기를 도입한다. 단 **기동 조건이 아닌 선택적 의존성**으로 둔다

개발명세서 §5의 원칙을 다음과 같이 정밀화한다.

> **(기존)** 네이티브 빌드가 필요한 의존성은 도입하지 않는다.
> **(갱신)** **API 기동의 전제가 되는 네이티브 의존성**은 도입하지 않는다. 설치 실패·미설치가 **해당 기능의 품질 저하로만 귀결되고 기동·대화·기존 기능에 영향이 없는** 선택적 의존성은, 폴백 경로가 **코드에 실재하고 테스트로 검증될 때** 도입할 수 있다.

`bcrypt`/`argon2`가 금지된 이유는 **로그인이 그것 없이는 아예 동작하지 않기 때문**이다(기동 조건). 형태소 분석기는 다르다 — 없으면 요소분해 정밀도만 떨어지고, 그 손실은 **관리자가 칩 경계를 직접 수정**해 흡수한다(FR-L2-8).

### 2. 포트 1개 + 구현체 3종. **폴백이 J-10의 휴리스틱 그 자체**다

```ts
export interface MorphAnalyzerPort {
  readonly analyzerId: string;          // 분해 응답에 실려 화면이 품질 근거를 말할 수 있다
  readonly ready: boolean;              // 로드 실패·미설치 = false
  /** 동기 함수. 로드는 기동 시 1회(비동기), 분석은 메모리 내 연산이다. */
  analyze(text: string): readonly MorphToken[];   // { surface, start, end, pos }
}
```

| 구현체 | 방식 | 네이티브 | 품질 | 역할 |
|---|---|:---:|:---:|---|
| **M0 `HeuristicAnalyzer`** | 공백 분할 + 조사·어미 접미 절단 규칙표 | **없음** | 하 | **폴백 · 기본값 · 의존성 0.** 요구사항 J-10의 알고리즘 그대로다 |
| **M1 (WASM 배포본 우선)** | 사전 기반 형태소 분석기의 **WebAssembly 빌드** | **없음**(WASM) | 상 | **1순위 후보** — 네이티브 툴체인 없이 정밀도를 얻는다 |
| **M2 (네이티브 바인딩)** | mecab-ko + mecab-ko-dic Node 바인딩 | **있음** | 상 | 2순위. WASM 후보가 품질·라이선스에서 미달일 때만 |

- **선택은 `MORPH_ANALYZER` 환경변수**(`auto`(기본) | `heuristic` | 분석기 id). `auto`는 **로드 성공한 최상위 구현을 쓰고 실패하면 M0로 내려간다.**
- **최종 구현체 선정은 `ml-engineer`가 실측으로 확정**한다 — 임베딩 모델(ADR-0024 §4)·증강 생성모델(ADR-0026 §5)과 **동일한 절차**다.

| 지표 | 측정 방법 |
|---|---|
| ① 스팬 경계 정확도 | 실제 미응답 질문 100문장에 대한 수작업 정답 대비 |
| ② 엔티티 후보 재현율 | 등록된 `Keyword`가 스팬으로 정확히 잡히는 비율 |
| ③ 분석 지연 | 문장 1건 P95(**목표 50ms 이내** — NFR-LP4) · 사전 로드 시간 |
| ④ **설치 난이도** | Windows/Linux, 오프라인 환경, 네이티브 툴체인 필요 여부 |
| ⑤ **라이선스 · 배포 크기** | 상업적 이용 가능 여부 · 사전 파일 크기 |

> ④⑤에 실질 가중치를 크게 둔다. 이 기능의 소비자는 관리자 화면 1곳이므로 **정밀도 1~2%p보다 "고객사 서버에 설치되는가"가 중요하다.**

### 3. 분석 결과는 **순수 함수에 주입**한다 — 요소분해 로직은 DB·Nest·분석기 무의존이다

```
MorphAnalyzerPort.analyze(text)   ─┐
Keyword/synonyms/Homonym gazetteer ─┼─▶ decompose(text, { morphTokens, gazetteer, stopwords }) ─▶ 스팬[]
불용어 사전(코드 상수)              ─┘        (DB·Nest·I/O 무의존 순수 함수 — 단위 테스트 1차 대상)
```

- **ADR-0020이 의미 점수를 엔진에 주입한 것과 정확히 같은 패턴**이다. 분석기가 바뀌어도 분해 규칙은 바뀌지 않고, 분석기가 없어도(`morphTokens: []`) 함수는 gazetteer + 공백 휴리스틱으로 동작한다.
- 스팬 산출 우선순위: **① gazetteer 최장일치(결정론적) → ② 형태소 경계 → ③ 공백 → ④ 조사·어미 절단**. gazetteer가 항상 최우선이므로 **등록된 키워드는 분석기 품질과 무관하게 정확히 잡힌다**(AC-L2-1, EX-L2-3).
- 분해 결과는 **저장하지 않고 조회 시점에 계산**한다(사전이 바뀌면 즉시 달라져야 한다 — FR-L2-4). 관리자가 수정한 결과는 **반영 요청 본문에 실려** 오므로 별도 저장이 필요 없다.
- 역할 자동 부여 3종(`ENTITY_CANDIDATE`/`INTENT_SIGNAL`/`IGNORED`)은 **초기값일 뿐**이며 서버는 관리자의 수정본을 재검증(범위 이탈·겹침 → `400`)한 뒤 **그대로 받아들인다**(AC-L2-3/4).

### 4. 분석기는 `apps/api` 프로세스 안에 둔다 — ml-worker로 보내지 않는다

| 근거 | 내용 |
|---|---|
| **지연 예산** | NFR-LP4는 50ms(P95)다. HTTP 왕복은 그 예산의 대부분을 먹는다 |
| **가용성 결합** | 요소분해는 **관리자 기능**인데 ml-worker(대화용 추론 서비스)에 의존시키면, ml-worker가 없는 구성에서 관리자 기능까지 죽는다 |
| **입력 위치** | gazetteer(키워드·동의어·동음이의어)가 `apps/api`의 DB에 있다. 분석만 원격으로 보내면 **스팬 오프셋 정합**을 네트워크 경계 너머로 맞춰야 한다 |

### 5. 구축형(On-Premise) 설치 영향 — **반드시 배포 문서에 반영한다**

| 영향 | 내용 | 완화 |
|---|---|---|
| **설치 절차 +1단계** | 분석기 모듈·사전 파일 설치가 필요하다 | `auto` 기본값 → **설치하지 않아도 기동·동작한다**(M0 폴백). 설치는 "품질 향상 선택 단계"로 문서화 |
| **오프라인 설치** | 폐쇄망 고객사는 레지스트리에서 받을 수 없다 | 설치 패키지에 **사전·바이너리를 동봉**하고 로컬 경로 주입(`MORPH_DICT_PATH`)을 지원 |
| **배포 크기 증가** | 사전 파일 수십 MB | 선택 구성요소로 분리해 기본 패키지 크기를 늘리지 않는다 |
| **플랫폼별 바이너리**(M2 채택 시) | Windows/Linux, Node ABI 버전 종속 | **M1(WASM) 우선 채택으로 회피**하는 것이 이 ADR의 1순위 전략 |
| **기동 시간** | 사전 로드 수백 ms~수 초 | 기동 시 1회 비동기 로드, 로드 완료 전 요청은 M0로 응답(`analyzerId`로 구분되므로 화면이 알 수 있다) |
| **CI** | 러너에 네이티브 툴체인이 없을 수 있다 | **전 테스트가 M0(기본값)로 통과**해야 한다. 분석기 의존 테스트는 있으면 실행·없으면 skip |

## 근거

- **PM이 정밀도를 요구했고, 정밀도는 실제로 부족하다.** 공백 + 조사 절단만으로는 `"해외배송비"`처럼 붙여 쓴 복합어를 쪼갤 수 없고(S-6), 한국어 미응답 질문에서 이런 형태는 흔하다. 관리자가 매번 손으로 고치면 "요소분해"의 가치가 사라진다.
- **원칙을 폐기하지 않고 정밀화하는 것이 옳다.** `bcrypt` 금지의 실질은 "설치 실패가 서비스 기동을 막는 것"에 대한 방어였다. 그 방어를 폴백으로 달성할 수 있으면 원칙의 목적이 유지된다 — **원칙의 문구가 아니라 목적을 지킨다.**
- **폴백이 원래 설계안 그 자체라는 점이 이 결정을 싸게 만든다.** J-10의 휴리스틱을 버리는 것이 아니라 **M0 구현체로 만든다.** 따라서 분석기 도입이 실패하거나 철회되어도 **되돌릴 코드가 없다**.
- **주입 패턴이 분석기 교체 비용을 0에 가깝게 만든다.** 분해 규칙·테스트·API 계약은 분석기를 알지 못한다. 교체 지점은 팩토리 1곳이다.
- **선정을 실측으로 미루는 것이 이 프로젝트의 규약**이다(ADR-0024 §4, ADR-0026 §5). 특정 라이브러리 이름을 설계 문서가 못 박으면, 실측 결과가 나빠도 되돌리기 어려워진다.

## 대안과 트레이드오프

| 대안 | 기각 사유 |
|---|---|
| **도입하지 않는다(요구사항 J-10 원안)** | PM이 정밀도를 요구했다. 붙여 쓴 복합어·어절 내부 경계를 다룰 수 없어 관리자 수정 부담이 상시화된다 |
| **필수 의존성으로 도입** | 설치 실패가 **API 기동을 막는다.** 구축형 온프레미스에서 가장 흔한 사고 유형이며, `bcrypt`를 기각한 바로 그 이유다 |
| **ml-worker(Python)에 두고 `POST /morph`** | ① 50ms 예산을 HTTP 왕복이 잠식한다 ② 관리자 기능이 대화용 추론 서비스 가용성에 묶인다 ③ gazetteer가 `apps/api`에 있어 스팬 오프셋 정합을 네트워크 너머로 맞춰야 한다. **단 G3(로컬 생성모델)를 이미 운영 중이고 지연 실측이 예산 안이면 재검토 가치가 있다**(§재검토 트리거) |
| **학습형 NER(CRF/BERT)로 엔티티 추출** | **스팬 라벨 데이터가 0건**이라 학습이 불가능하다. 이번 그룹이 만드는 엔티티 승인 이력이 **장래 학습 데이터**가 된다 |
| **분해 결과를 DB에 저장** | 키워드 사전이 바뀌면 즉시 낡는다. 조회 시 계산이 정확하고, 관리자 수정본은 요청 본문으로 오므로 저장할 이유가 없다(FR-15-16의 추천 비저장 판단과 동일) |
| **분석기 결과를 순수 함수 밖에서 조합** | 분해 로직이 분석기·DB에 묶여 단위 테스트가 통합 테스트가 된다. NFR-LM1 위반 |

**감수하는 비용**

1. **설치 절차와 배포 크기가 늘어난다** → 선택 구성요소로 분리 + 오프라인 동봉 + 미설치 시 정상 동작.
2. **분석기 품질이 환경마다 다를 수 있다**(설치한 곳/안 한 곳) → 분해 응답에 **`analyzerId`를 실어** 화면이 "정밀 분석 사용 중 / 기본 분해" 를 표시할 수 있게 한다. 조용한 품질 차이를 만들지 않는다.
3. **Windows 개발 환경에서 M2는 고통스럽다** → M1(WASM) 우선. M2 채택 시 개발 기본값은 M0로 두고 문서로 안내한다.
4. **사전에 없는 신조어·도메인 용어는 여전히 못 쪼갠다** → gazetteer 최우선 규칙이 이를 상쇄한다. 관리자가 키워드로 등록하는 순간 다음 분해부터 정확해진다 — **이 기능의 선순환 구조 자체가 보완 장치**다.

## 결과

- `apps/api/src/learning/morph/` 신설 — `morph-analyzer.port.ts` / `morph-analyzer.factory.ts`(★ 교체 지점 1곳) / `heuristic-analyzer.ts`(M0, 기본값) / `<선정 분석기>-analyzer.ts`(M1 또는 M2).
- `apps/api/src/learning/lib/decompose.ts` 신설 — **순수 함수**(사전·형태소 토큰 주입형). `lib/josa-endings.ts`(조사·어미 규칙표)·`lib/stopwords.ts` 동반.
- 환경변수 2종 추가: `MORPH_ANALYZER`(기본 `auto`) · `MORPH_DICT_PATH`(선택, 오프라인 설치용). **둘 다 미설정이면 M0로 정상 동작**한다.
- 개발명세서 §5 "배포형태 중립"의 네이티브 의존성 문구를 §1의 정밀화 문구로 **갱신**한다.
- `docs/05-ops/자동배포.md`·설치 안내에 **"형태소 분석기 = 선택 구성요소"** 절을 추가한다(배포 Phase 착수 시).
- `ml-engineer` 인계: **분석기 후보 3종 × 5지표 비교표**(④⑤ 가중치 상향) + 조사·어미 규칙표 검증 + 불용어 사전 초안.
- `test-automation` 인계: **전 테스트가 `MORPH_ANALYZER=heuristic`(M0)로 통과**해야 한다 · AC-L2-1/2(gazetteer 일치·미등록 토큰) · AC-L2-3/4(관리자 수정본 존중·범위 이탈 400) · EX-L2-3(최장일치 결정론).

## 재검토 트리거

- **실측에서 M1(WASM) 후보가 품질·라이선스 요건을 만족하지 못함** → M2(네이티브)를 조건부 채택하되 **개발 기본값은 M0** 유지.
- **G3(로컬 생성모델)를 상시 운영하게 됨** → ml-worker에 이미 Python 형태소 스택을 둘 수 있으므로 `POST /morph` 대안을 지연 실측과 함께 재검토.
- **엔티티 승인 스팬 라벨이 수천 건 축적** → 학습형 NER 도입 재검토(이 ADR의 전제였던 "라벨 0건"이 해소된다).
- **요소분해 소비자가 관리자 화면 밖으로 확장**(예: 대화 경로의 엔티티 추출) → 정밀도·지연 요구가 완전히 달라지므로 **이 ADR 전체를 다시 쓴다**.
