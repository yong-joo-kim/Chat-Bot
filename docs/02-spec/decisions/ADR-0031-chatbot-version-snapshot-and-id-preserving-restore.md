# ADR-0031 — 챗봇 버전 = 대화 자산 시점 스냅샷, 복원 = ID 보존 차이 적용의 단일 트랜잭션

- **상태**: 채택 (2026-09-23)
- **결정자**: system-architect (PM 확정사항 P-1~P-10 반영)
- **관련**: 요구사항 `docs/requirements/version-history.md` **J-1 / J-2 / J-4 / J-5 / J-6 / J-8 / J-9 / J-11 / J-14**, FR-0-68~77, FR-H1-\*, FR-H3-\*, AC-H1~H4 · 설계 `version-history-설계.md` §4~§9·§11
- **연관 ADR**: ADR-0002(되돌릴 수단 부재 — 이 ADR이 메운다) · ADR-0016(감사로그는 부분 스냅샷 — 복원 원천이 아니다) · ADR-0029(자산 스냅샷을 **No.25 몫으로 비워 둔** 결정) · ADR-0005(노드 조인 테이블) · ADR-0006(정규화 유일성) · ADR-0009(클라이언트 보관 대화 상태 · 매 턴 재검증) · ADR-0015(권한) · ADR-0025(제안/자산 분리 · 자산 쓰기 봉인) · ADR-0027(분류기 stale 판정)
- **Supersedes**: 없음

## 맥락

"되돌릴 수단이 없다"는 사실이 세 곳에 기록돼 있다 — ADR-0002 §근거("되돌릴 수단이 전무하다"), ADR-0016 감수비용 5("`beforeValue`는 부분 스냅샷이라 복원할 수 없다 — 복원은 No.25의 본체"), ADR-0029 §2(3)("자산 스냅샷은 No.25의 본체를 선점한다 — 저장소·복원·정리 배치·용량 정책"). 그 사이 **증강 승인 한 번이 예문 수십 건을 즉시 반영**하게 됐고(ADR-0025 — `appliedImmediately === true`), No.19/20은 회귀를 **발견**하지만 **복구**할 수단은 없다.

결정해야 할 것은 다섯 가지다: ① 무엇을 담는가 ② 어떤 형식으로 저장하는가 ③ 복원 시 행의 **정체성(ID)** 을 어떻게 다루는가 ④ 복원의 원자성·가역성을 어떻게 보장하는가 ⑤ 복원이 다른 기능(TC·색인·분류기·진행 중 대화)을 조용히 깨뜨리지 않게 하려면 무엇을 해야 하는가. 그리고 이 모든 것이 **No.40(Dev/Staging/Prod)의 영역을 선점하지 않아야** 한다.

## 결정

### 1. 스냅샷 = "관리자가 작성하고, 응답을 결정하며, 이 챗봇에만 속하는 것" (J-1, P-2)

| 포함 | 제외 |
|---|---|
| 대화 자산 6종(`Intent`·`Keyword`·`HomonymDictionary`·`ContextVariable`·`DialogNode`·`FaqEntry`) + 노드 조인 2종(노드의 `intentIds`/`keywordIds`로 평탄화) + `ChatbotAnswerSetting`(행 없음 = `null`) + `Chatbot` 표시 설정 4필드(`name`·`avatarUrl`·`description`·`skin`) | **외부 계약** `slug` · **배포 행위** `status`·`Channel` · **조직 정보** `groupId` · **전역 설정** `BannedWord`·`User`·세션 · **파생** `EmbeddingVector`·`IntentClassifierModel` · **제안** `AugmentationSuggestion` · **검증 자산(자)** `TestCaseSet`·`TestCase` · **사실 기록** 로그·실행 결과·`AuditLog` |

판단 기준은 두 가지다: **"되돌렸을 때 응답이 그 시점과 같아지는가"** 와 **"되돌려서는 안 되는 사실·계약·배포·전역 설정인가"**. 정규화 컬럼(`*Normalized`)과 항목별 `updatedAt`은 저장하지 않고(복원 시 재계산 / 복원 시각), `createdAt`은 보존한다.

### 2. 전체 스냅샷 · 정규 JSON 1개 · `contentHash` · `schemaVersion` + 업캐스터 · 메타/본문 분리 (J-2, P-6)

- **증분(델타) 체인을 쓰지 않는다.** 중간 1개가 깨지면 이후 전부가 복원 불가가 되고, 보존 정리 때 재기저화가 필요하다. 챗봇 1개 자산은 통상 1~2MB다.
- 자산부는 **`DialogueBundle`(shared-types)의 형태를 재사용**하되 항목별 `chatbotId`·`updatedAt`만 뺀다. **엄격 검증은 hydrate 후 기존 DTO 스키마(`DialogueBundleSchema` 등)로** 한다 — 두 번째 자산 규약을 만들지 않으며, 도메인 상한의 단일 소스가 그대로 적용된다.
- **`contentHash`** = 타임스탬프를 뺀 정규 직렬화(키 정렬 · 엔터티 `id` 정렬 · **조인 `intentIds`/`keywordIds` 정렬** · 값 배열 순서 유지)의 sha256. 같은 상태 → 같은 해시. "직전과 동일하면 생성 생략", "미리보기 이후 변경 감지", "복원 결과 검증"이 전부 이 해시 하나로 이뤄진다.
- **`schemaVersion`(정수) + 업캐스터 체인(순수 함수)** + **영구 픽스처 `snapshot-v1.json`의 복원 가능성을 CI가 단언**한다. 형식을 바꾸고 업캐스터를 빠뜨리면 CI가 실패한다.
- **메타(`chatbot_versions`)와 본문(`chatbot_version_payloads`)을 분리**한다. 목록이 본문을 읽지 않는 것을 Prisma `select` 규율이 아니라 **구조**로 보장한다. `versionNo`는 별도 시퀀스 테이블이 발급한다(최신 버전 삭제 시 번호 재사용 방지 · `Chatbot.updatedAt` 비오염).
- **무압축 TEXT**로 시작하고 `payloadEncoding` 컬럼으로 압축 전환 여지를 남긴다(마이그레이션 불필요).

### 3. ★ 복원은 **ID를 예외 없이 보존**하는 **차이 적용(diff-apply)** 이다 (J-4, J-5, P-3, P-9)

복원된 모든 행은 **스냅샷의 원래 `id`** 로 존재한다. 스냅샷 범위의 해당 챗봇 행 집합은 복원 후 **스냅샷과 정확히 같다**(없는 행 삭제 · 있는 행 원래 id · 필드 동일 · 복원 후 해시 = 대상 해시). 부분(항목 단위) 복원은 **제공하지 않는다** — 참조 정합(의존성 폐포 + 충돌 해소 UI)이 한 그룹 분량이다.

**ID를 보존해야 하는 이유(하나만 빠져도 기능이 무너진다):**
1. **No.19 TC가 ID로 기대값을 저장한다**(ADR-0029). ID가 바뀌면 복원 직후 TC 세트 전체가 `UNRESOLVED`가 되어 **"복원이 잘 됐는가"를 검증할 수단이 사라진다**.
2. **재색인 비용**: `EmbeddingVector`는 `(ownerId, slotIndex, textHash)`로 재사용된다. ID가 바뀌면 복원 1회 = 챗봇 **전체 재임베딩** — CPU 배포에서 수 분간 의미 매칭 저하. **GPU 필요도 1 유지의 조건**이기도 하다(J-13).
3. `ConversationLog.matched*Id`·`UnansweredQuestion.resolvedIntentId`·`AuditLog.targetId`(FK 없는 사실 기록)와 통계가 과거와 이어진다.
4. 클라이언트 대화 봉투(ADR-0009)의 `contextVariableId`·`homonymId`가 유지되어 **진행 중 대화가 대부분 끊기지 않는다**.

**전체 삭제 후 재생성이 아니라 차이 적용인 이유**: 변경 없는 행의 `updatedAt`을 보존하고(목록 정렬 불변 · "복원이 실제로 바꾼 것"이 드러남), SQLite 쓰기 잠금 시간을 변경 행 수로 한정한다. 대가로 **적용 순서**가 필요하다 — 조인 삭제 → 노드 삭제 → **이름 교환 대비 임시 키 부여 + 바뀌는 `contextVariableId` 해제** → 의도·키워드·동음이의어·컨텍스트·FAQ 삭제 → 생성/갱신 → 노드 생성/갱신 → 조인 생성 → 답변설정 → 프로필. 이 순서로 `Restrict` FK와 `@@unique([chatbotId, nameNormalized])`를 **원시 SQL 없이** 만족한다.

### 4. 복원 = **"해시 재확인 → 복원 직전 백업 → 교체 → 사후 검증"을 하나의 쓰기 트랜잭션**으로 (J-6, FR-0-70/72, P-4)

- **복원 직전 상태를 `BEFORE_RESTORE` 스냅샷으로 저장하지 않고는 복원하지 않는다.** 백업이 교체와 **같은 트랜잭션**에 있으므로 "백업 없는 복원"은 규약이 아니라 **원자성으로 불가능**하다. 백업 = 해시를 확인한 바로 그 상태 = 교체 직전 상태이며, 따라서 **복원의 복원이 정확하다**. 백업 실패(크기 초과 등)는 전체 롤백 = 복원 중단(fail-closed). `BEFORE_RESTORE`는 "직전과 해시 동일 시 생략" 규칙의 **예외**로 항상 새 행이다.
- 백업이 있으므로 복원은 **가역 동작**이다 — ADR-0002의 "복구 불가 파괴 동작" 등급(`chatbot:purge` = ADMIN)에 해당하지 않으며, 사고 현장의 EDITOR가 즉시 롤백할 수 있다(J-11).
- 교체 후 **같은 트랜잭션에서 재캡처해 해시를 대상과 비교**한다. 불일치(구현 결함)면 전체 롤백 — "복원했다고 응답했는데 실제로는 다른 상태"가 존재할 수 없다.
- **자동 스냅샷(대량 변경 직전 5종 중 복원 외 4종)은 fail-open**이다(P-4). 스냅샷 문제로 업무가 멈추지 않으며, 결과는 응답의 선택 필드 `autoSnapshot.status`로 알린다.

### 5. 파생 데이터는 스냅샷에 담지 않고 **복원 후 재계산·무효화**한다 (J-8)

| 대상 | 처리 |
|---|---|
| 번들·인덱스·벡터 캐시 + 임베딩 색인 | `DialogueBundleService.invalidate()` **1회**(기존 단일 지점 — 복제 금지). 색인은 `textHash` 재사용으로 **바뀐 문장만** |
| 답변설정 캐시 | 무효화 |
| **`IntentClassifierModel`** | **삭제**(복원 트랜잭션 안). `judgeClassifierStale()`의 `EXAMPLES_DRIFTED`는 `current − atTrain > 50` — **증가만** 감지한다. 증강 롤백(예문 감소) 후에도 증강분으로 학습된 모델이 stale 없이 추천에 쓰이는 것을 막는다. 재학습은 수 초이고 대화 경로와 무관하다 |
| 질의 임베딩 캐시 | **건드리지 않는다** — `(문장, modelId)`의 함수라 자산 무관. 버전 모듈은 이 서비스를 주입조차 하지 않는다 |
| 제안·TC·실행·로그·채널·금지어 | **쓰기 0건**(정적 검사로 단언) |

부수 결정: `ReindexQueueService.schedule()`이 실행 중 호출을 **버리던 잠재 결함**을 "재실행 예약 플래그"로 보완한다(복원처럼 수백 행이 한 번에 바뀌는 경우 치명적). 동시 실행 1건·수동 재색인 409 계약은 불변이다.

### 6. 동시성의 최종 방어선은 **SQLite 직렬화 트랜잭션 안의 재확인**이다 (J-9)

복원은 동기·단일 요청이라 `test_runs`처럼 "진행 중" 행이 없고, 부분 유니크 인덱스 패턴을 쓸 수 없다. 대신 **판정을 쓰기 트랜잭션 안으로 옮긴다** — 트랜잭션 안에서 ① 챗봇 상태 ② 진행 중 `TrainingJob`/`TestRun` 건수 ③ 현재 해시 = `expectedCurrentHash`를 확인한다. SQLite는 모든 트랜잭션이 직렬화 격리이므로 그 사이 끼어든 커밋은 이 트랜잭션의 쓰기를 실패시키고(`BUSY`), 이를 `409 RESTORE_PREVIEW_STALE`로 돌려준다. 작업 생성은 복원의 쓰기 잠금 뒤로 직렬화되어 **복원 전/후 어느 한쪽에만** 속한다 — 그래서 작업 시작 경로(`validation`·`augmentation`·`classifier`)가 복원 잠금을 참조할 필요가 없다(3모듈 역의존 회피). in-process 복원 잠금은 **UX용 빠른 실패**(`RESTORE_IN_PROGRESS`)일 뿐 정합성의 근거가 아니다. Postgres 전환 시 이 트랜잭션은 `Serializable`로 지정한다(지정 지점 2곳).

일관 읽기(캡처)도 같은 원리다 — `DialogueBundleService.build()`에 **트랜잭션 클라이언트 선택 인자**를 추가해 스냅샷 범위 8회 조회를 한 트랜잭션에서 순차 실행한다(기존 `Promise.all` 6회 독립 조회는 "노드는 새 의도를 참조하는데 의도 목록은 옛것"인 스냅샷을 만들 수 있다). 기존 호출부는 무변경이다.

### 7. 신규 권한 0종 — `@RequirePermission`을 **복수 인자 AND**로 확장한다 (J-11, P-5)

복원은 대화 자산(`dialogue:*`)과 답변설정·표시설정(`chatbot:write`)을 **함께** 바꾸므로 **두 권한을 모두** 요구한다. 현재 가드는 단일 권한만 판정하므로 `RequirePermission(...permissions: [Permission, ...Permission[]])` + 가드의 AND 판정으로 확장한다. 기존 호출(인자 1개)은 한 글자도 바뀌지 않고 `Permission` 유니온은 **15종 그대로**다.

### 8. ★ No.40과의 경계를 여기서 고정한다 (J-14)

이 기능은 **"한 챗봇 · 한 시간축 · 뒤로 가기"** 뿐이다. 다음을 **만들지 않는다**: 환경(Dev/Staging/Prod) 개념 · 환경별 버전 태깅 · 버전 **승격** · **트래픽 전환/분할**(카나리·A/B) · 쌍둥이 챗봇 · **다른 챗봇으로 복원** · 예약 복원(No.28) · `Chatbot.status` 변경. 버전 **라벨은 자유 메모이며 유일성·의미가 없다** — 라벨에 `prod` 같은 의미를 부여하는 순간 "prod 라벨 버전을 배포한다"는 요구가 따라오며 그것이 No.40이다. 향후 No.40·깊은 복사(No.1 고도화)는 이 ADR의 **캡처 + 무결성 검사를 재사용**하되 적재 규칙은 정반대(**ID 재매핑**)다 — 그래서 캡처·검증을 ID 정책과 분리된 순수 함수로 둔다.

## 근거

- **"완전한 상태"와 "행위 기록"은 다른 저장소여야 한다.** 감사로그는 의도적으로 부분 스냅샷(8KB, `examples`→`exampleCount`)이다. 거기서 복원을 만들면 감사 설계가 무너지고(ADR-0016), 감사로그를 복원 수준으로 키우면 모든 쓰기의 비용이 커진다. 역할을 나누고 **링크로만** 잇는다.
- **증강 승인 직전 자동 스냅샷이 "승인 후 되돌리기"의 유일한 안전망이다.** `Intent.examples`에는 증강분 표시가 없고(ADR-0025 — 승격된 문장은 일반 예문이다), `ACCEPTED` 제안으로 역추적해도 그 사이 사람이 같은 문장을 손으로 넣었는지 구분할 수 없다.
- **ID 보존은 선택이 아니라 다른 네 기능(TC·색인·통계·진행 중 대화)의 전제다.** 기술적 반대 요인은 이름 교환 하나뿐이며 임시 키 1단계로 원시 SQL 없이 해결된다.
- **원자성의 단위를 "사용자가 기대하는 결과"에 맞춘다.** 사용자는 "백업이 있는 복원"을 기대한다. 백업과 교체를 다른 트랜잭션에 두면 그 사이의 편집이 두 곳 어디에도 남지 않는 창이 생긴다.
- **약속이 아니라 구조로 막는다**(ADR-0022 이래 네 번째 적용). 대화 자산 쓰기는 applier 1파일, 목록의 본문 미접근은 테이블 분리, 질의 캐시 비오염은 미주입, 자산 모듈의 DI 그래프에서 복원 경로 배제는 캡처 모듈 분리로 — 전부 정적 검사가 단언한다.

## 대안과 트레이드오프

| 대안 | 기각 사유 |
|---|---|
| **증분(델타) 저장** | 체인 1개 손상 = 이후 전부 복원 불가 · 정리 시 재기저화 · 복원 비용이 체인 길이에 비례 |
| **항목별 버전 테이블(`IntentVersion` 류)** | 참조 정합이 테이블 수만큼 쪼개지고, "한 시점의 전체"를 재구성하려면 N개 테이블의 시점 조인이 필요하다 |
| **감사로그 `beforeValue`로 되돌리기** | 부분 스냅샷이라 불가능하며 ADR-0016의 설계를 무너뜨린다 |
| **`ChatbotsService.copy()`를 깊은 복사로 확장해 재사용** | 복사는 ID를 **새로 발급**해야 하고 복원은 **보존**해야 한다 — 적재 규칙이 정반대다. 공통 부분(캡처·검증)만 순수 함수로 공유한다 |
| **복원 시 새 ID 발급** | TC 전체 `UNRESOLVED` · 전체 재임베딩 · 통계 단절 · 진행 중 대화 전부 폐기 |
| **전체 삭제 후 재생성** | 모든 행의 `updatedAt` 변경 · 쓰기량 2배 · 쓰기 잠금 장기화 |
| **백업과 교체를 별도 트랜잭션** | 사이의 편집이 백업에도 없고 교체로 사라지는 창 — 복원의 복원이 불완전 |
| **비동기 복원 Job** | 카탈로그 원문 "**즉시** 롤백". 통상 규모 수 초. Job 테이블·폴링·부분 실패 상태가 새로 생긴다(재검토 트리거로 남긴다) |
| **작업 시작 경로에 복원 잠금 조회 추가** | 3모듈 역의존 + 수정. DB 직렬화로 이미 "복원 전/후 한쪽"이 보장된다 |
| **복원 잠금 테이블(부분 유니크 인덱스 패턴)** | 동기 복원에는 "진행 중" 상태를 담을 행이 없다. 행을 억지로 만들면 재시작 시 고아 잠금 정리가 필요해진다 |
| **`chatbot:restore` 권한 신설(ADMIN 전용)** | PM 확정으로 기각. 백업으로 가역 동작이며 사고 현장의 EDITOR가 즉시 롤백할 수 있어야 한다. 조직 통제가 필요해지면 재검토(No.36/45) |
| **분류기를 스냅샷에 포함** | 파생 데이터(재학습 수 초) · 모델 버전 이력은 ADR-0027이 이미 기각했다 |
| **질의 임베딩 캐시도 무효화("안전하게")** | 자산과 무관한 캐시를 비워 운영 대화의 적중률만 붕괴시킨다(ADR-0030과 같은 위험) |
| **gzip 압축 저장** | 통상 용량이 상한 안이고, 무압축이 장애 분석에 유리하다. `payloadEncoding`으로 나중에 무마이그레이션 전환 |

## 감수하는 비용

1. **SQLite 단일 작성자** — 복원 트랜잭션 동안 전 챗봇의 쓰기가 대기한다. 준비를 트랜잭션 밖으로 빼고 차이 적용으로 쓰기량을 줄이며, 대화 로그 유실 여부를 실측한다(재검토 트리거).
2. **부분 복원이 없다** — 증강분만 빼고 싶어도 그 이후의 다른 편집이 함께 되돌아간다. 미리보기가 "함께 취소되는 변경 N건"을 반드시 보여 주고, 차이·내용 조회로 과거 값을 복사할 수 있게 한다.
3. **자산 쓰기 봉인(ADR-0025 L2/S-1)의 허용 파일이 2 → 3이 된다** — 복원 applier. 본문을 만드는 경로가 실제 DB 자산의 캡처뿐이고(내보내기/가져오기 없음) 관리자 요청 핸들러 1곳이므로 "승인 없는 자산 주입" 경로가 아니다.
4. **`schemaVersion` 관리 부담** — 스냅샷 범위 모델을 바꾸는 모든 변경이 증가 여부를 판단해야 한다. 영구 픽스처 CI 단언과 code-reviewer 점검 항목으로 강제한다.
5. **롤백으로 제거된 승인 증강 예문은 다시 제안되지 않는다**(`@@unique([intentId, textNormalized])`, P-8) — 미리보기 경고로 알린다.
6. **영구삭제는 여전히 불가역**이다 — 스냅샷도 함께 지워진다(오프사이트 백업은 No.45).

## 갱신 (2026-09-23 — No.28 예약 실행기가 `restore()`의 두 번째 호출부가 된다 · `RESTORE_BUSY` 분리)

운영 예약 배포(No.28, **ADR-0032**)가 §8에서 "만들지 않는다"고 적은 **예약 복원(No.28)** 을 도입한다. **이 ADR의 복원 의미론(스냅샷 범위 · ID 보존 차이 적용 · 해시 재확인·백업·교체·사후 검증의 단일 트랜잭션 · 파생 데이터 처리 · No.40 경계)은 한 줄도 바뀌지 않는다** — 예약은 `restore()`를 **지정 시각에 호출**할 뿐이다. `Chatbot.status` 변경은 여전히 복원이 하지 않으며, 공개 전환은 별도 동작(`ChatbotPublicationService`)이다.

1. **봉인 문구 개정**: "복원은 관리자 요청 핸들러 1곳"을 다음으로 바꾼다 — **대화 자산을 쓰는 유일 경로(`VersionRestoreApplier`)는 `VersionRestoreService.restore()` 안에서만 호출되며, `restore()`의 호출부는 ① 관리자 요청 핸들러 ② 관리자가 미리보기로 확인하고 해시에 묶어 생성한 예약의 실행기 2곳뿐이다.** 구조 보장: `VersionsModule`은 `VersionRestoreService`·`VersionDiffService`만 export하고 **applier는 export하지 않는다**(주입 불가) · `restore(` 호출 파일 정확히 2개(`deploy-schedule-sealing.spec.ts`) · `version-sealing.spec.ts` V-1~V-3(applier 1파일) 불변.
2. **§6 BUSY 매핑 변경**: 복원 트랜잭션의 `P2034`·`SQLITE_BUSY` 계열은 **`409 RESTORE_BUSY`**(재시도 가능)로 매핑하고, **`RESTORE_PREVIEW_STALE`은 해시 불일치 전용**이 된다. BUSY 후 재시도는 트랜잭션 안 해시 재확인이 실제 변경을 다시 판정하므로 항상 안전하다. 즉시 복원의 정상 경로 응답은 불변이며, 경합 시에만 코드가 세분화된다(프런트 분기 1줄 — 같은 UX). Postgres 전환 시 `Serializable` 직렬화 실패도 `RESTORE_BUSY`다.
3. **`restore()` 선택 4번째 인자 `ScheduledInvocation { actor, auditSummaryPrefix, triggerContext? }`** — 있으면 `RESTORE` 감사의 주체를 예약자(`actorOverride`)로, summary에 `[예약 실행 #…]` 접두를, `BEFORE_RESTORE` 백업의 `createdBy*`를 예약자로, 백업 `triggerContext.deployScheduleId`를 기록한다(임대 만료 후 "이 예약이 복원을 커밋했는가"의 판정 근거). 없으면 기존과 바이트 단위로 동일하다.
4. **보존 정책 보호 집합 확장**: 활성(`PENDING`/`HELD`/`RUNNING`) 예약이 참조하는 버전은 정리에서 제외하고, 수동 삭제는 `409 VERSION_REFERENCED_BY_SCHEDULE`이다. 알고리즘은 불변이며 순수 함수 입력(보호 id 집합)만 늘어난다. 판정은 정리·삭제 트랜잭션 안에서 한다(예약 생성과의 경합 방어).
5. **재검토 트리거 추가**: No.40 착수 시 예약 엔진에 "포인터 전환" 동작을 추가하는 것이 이 ADR §8 경계와 No.40의 접점이다(ADR-0032 재검토 트리거).

## 갱신 (2026-09-24 — No.26: `ApiConnection`은 스냅샷 밖 · 연결 참조 끊김은 경고 · v1 평문 헤더 처리)

## 갱신 (2026-09-25 — No.22: 자산 `topicId`는 선택 필드 · 복원은 대상 정규화 · 깊은 복사는 ID 재매핑 적재기로 도입)

토픽 시스템(No.22, **ADR-0037 §4·§5**). 스냅샷 범위·ID 보존 복원·단일 트랜잭션·해시 규칙·§8 경계(다른 챗봇으로 **복원** 없음)는 **불변**이다.

## 갱신 (2026-09-25 — No.40: §8 부분 대체 · 해시 밖 보조 필드 · 환경 트리거 2종 · 보존 보호 확장)

환경 분리/버전관리(No.40, **ADR-0039**). 스냅샷 범위·ID 보존 복원·단일 트랜잭션·`contentHash` 규칙·`restore()` 호출부 2곳은 **불변**이다.

1. **§8 부분 대체**: ADR-0039가 환경 개념·환경 포인터(태깅)·승격·트래픽 전환을 도입한다 — 초안 = 자산 테이블, 스테이징·운영 = 이 ADR의 스냅샷을 가리키는 포인터. **유지되는 경계**: 라벨은 자유 메모(환경 배지는 포인터·전환 이력에서 파생) · 다른 챗봇으로 복원 없음 · 트래픽 분할 없음(2차). 재검토 트리거 "No.40 착수 → ID 재매핑 적재와 결합"은 **1차에서 발동하지 않는다** — 같은 챗봇·같은 ID라 재매핑이 필요 없고, 적재기는 2차 서버 간 이관의 부품이다.
2. **해시 밖 최상위 보조 필드 `tiebreak.nodeUpdatedAt`**: §1의 "항목별 `updatedAt`은 저장하지 않는다"를 **해시 범위(자산부)에 한해** 유지하고, 운영 서빙의 동점 일치를 위해 봉투 최상위에 노드 `updatedAt` 맵을 둔다. `contentHash`(자산부·답변설정·프로필만)는 불변이라 기존 해시·영구 픽스처·복원 사후 검증이 그대로다. `SNAPSHOT_SCHEMA_VERSION = 1` 유지(선택 필드) · 봉투 검증 스키마에 선택 필드 선언(strip 소실 방지) · 메타 `tiebreakHash` 추가. 복원·차이는 이 필드를 읽지 않는다.
3. **서빙 역직렬화**: 운영·스테이징 서빙은 `hydrateSnapshot()`을 그대로 부른 뒤 보조 필드를 적용하고 6종 배열을 `(createdAt asc, id asc)`로 재정렬하는 **새 순수 함수**를 쓴다(본문 저장 순서 `id asc`와 라이브 순서가 다르다 — K-1). 복원 경로의 `hydrateSnapshot()`은 무변경.
4. **트리거 2종**: `ENV_INIT`(환경 분리 시작 — 켜기 시 캡처) · `PROMOTE`(스테이징 승격). "같은 상태면 재사용"은 `contentHash` ∧ `tiebreakHash` 동일일 때만(편집 후 되돌리기 대비). 보존 정리에서는 자동 트리거 계열로 센다. 목록 필터 그룹 `ENVIRONMENT`.
5. **보존 보호 집합 확장**: 운영·스테이징 포인터 버전 + 운영 이력 최근 N(기본 5) + 활성 `SWITCH_PROD_VERSION` 예약 대상은 정리에서 제외하고 수동 삭제는 `409 VERSION_REFERENCED_BY_ENVIRONMENT`다. 알고리즘 불변(입력만 늘어난다).
6. **환경 모드에서 복원 = 초안만**: 운영은 포인터라 복원의 영향을 받지 않는다. 미리보기에 `ENV_DRAFT_ONLY` 경고를 더하고 `acknowledgeActive` 요청 계약은 그대로다. 운영 되돌리기는 복원이 아니라 포인터 롤백(ADR-0039 §5)이다.
