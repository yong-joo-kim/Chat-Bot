# ADR-0036 — 하이브리드 CS: 개입 세션 상담 스레드 · API 계층 봇 일시정지 · 상담 전용 짧은 폴링 · 상담 토큰 · 상담 중 한정 원문

- **상태**: 채택 (Accepted)
- **일자**: 2026-09-25
- **결정자**: system-architect (PM 결정 P-1~P-18 반영 — **P-9는 권고안과 다른 PM 결정**)
- **관련**: `docs/requirements/hybrid-cs.md` J-1~J-20 · FR-0-118~128 · FR-CS1~CS11 · AC-CS1~CS7(+AC-CS8 신설) / ADR-0009(봉투 — 트리거 ① 해소) · ADR-0011(공개 표면) · ADR-0013(PII) · ADR-0015(역할·권한) · ADR-0016(감사) · ADR-0023(보류 답변 폴링) · ADR-0031(스냅샷) · ADR-0032(`PollingLoop`·CAS) · ADR-0033(원천 봉인)
- **세부 설계**: `docs/02-spec/hybrid-cs-설계.md`

## 맥락

카탈로그 No.24는 "실시간 대화 모니터링 중 미응답 누적 시 색상 경고 + 상담원 개입, 응답힌트/자주쓰는문장 자동 제시(복사)"다. 현재 구조는 이를 그대로 받아들일 수 없다.

1. **서버가 위젯에게 먼저 말할 경로가 없다** — 공개 대화는 사용자가 말할 때만 오는 HTTP 1턴이다. 유일한 지연 전달 선례(보류 답변 폴링)는 질문 1건 ↔ 답 1건·메모리·90초 상한이라 상담원이 먼저, 여러 번, 오래 보내는 메시지를 표현하지 못한다.
2. **서버는 세션을 모른다** — 대화 상태는 클라이언트 봉투이고(ADR-0009), "상담원이 이 세션을 맡았다"는 상태전이·권한 값이라 봉투에 둘 수 없다(ADR-0009 §3).
3. **`sessionId`는 인증 수단이 아니다** — 세션별 서버 데이터를 공개 경로로 돌려주는 첫 사례가 된다.
4. **원문 저장소가 없다**(ADR-0013) — 그런데 PM은 P-9에서 "**상담 중에는** 담당 상담원이 사용자 원문을 볼 수 있어야 한다, 단 **영구 저장은 마스킹본만**"으로 결정했다.
5. **로그는 적재 후 바꿀 수 없다**(ADR-0033 R-10) · **엔진은 이 기능 때문에 바뀌면 안 된다**(시뮬레이터·TC·버전 결과 불변).

## 결정

### 1. 개입이 일어난 세션에만 서버 상담 스레드를 둔다 — 봇 상태는 봉투 유지

- `HandoffSession`(상담 1건: 상태 `CONNECTING→CONNECTED→ENDED`·담당자·토큰 해시·시각·seq 발급기) + `HandoffMessage`(상담 구간 메시지 순서열 — append-only). ADR-0009 근거 61행이 예고한 "메시지 시퀀스 + 담당자 + 상태" 모델이다.
- 봇 대화 상태는 **계속 봉투**다(ADR-0009 결정 1~3 유지 — **부분 갱신**, 트리거 ① "No.24"는 이 스레드로 **해소**, ②③은 유지).
- 모니터링·경고는 **`ConversationLog` 최근 창 조회 + 순수 판정**으로 얻는다(적재 0).
- **개입 분기는 공개 파이프라인의 입구 금지어 판정 직후·엔진 호출 전(API 계층)**에서 끝난다 — 기존 BLOCK 경로(엔진 미호출·요청 봉투 반환)와 같은 모양. **엔진 수정 0건**.
- 개입 시 진행 폼·설문·되묻기는 API 계층 순수 함수가 **봉투 값을 줄이는 방향으로만** 비운다(새 키·새 값 0 — 봉투 스키마·버전 불변).
- 상담 구간 사용자 메시지는 스레드에 **await 적재**(전달 보장 — 실패 시 재시도 가능한 503)하고, `ConversationLog`에는 기존대로 fire-and-forget + `handoffTurn=true`(적재 시점 확정 — 질문 순위·미응답 수집 제외, 응답출처 `OTHER` 불변).

### 2. 전달 = 상담 전용 짧은 폴링 + 관찰 창 + 편승 격하 — `@Public()` 6 → 7

- `GET /public/chatbots/:slug/handoff`(세션·토큰은 **헤더**, 커서는 쿼리). 상담 중 3초, **미응답 턴 직후 3분 관찰 창**(5초)에서만 폴링한다 — 개입 후보(= 미응답을 겪은 세션)만 폴링하므로 트래픽이 방문자 수가 아니라 경고 대상 수에 비례한다. 보류 답변 턴은 결과를 모르므로 `IF_PENDING_FAILS` 창(위젯이 보류 실패 시 연다 — 보류 폴링 서버 코드 무변경).
- 요청에 기능 선언(`features: ['handoff-v1']`)이 없는 **구버전 위젯**은 상담원 메시지를 다음 발화 응답의 `TEXT`로 받는다(편승 격하).
- **개수 고정 시험을 무력화하지 않고 7로 갱신**한다(ADR-0023 "5→6" 선례). 보상 통제: 토큰 · 슬러그 일치 · 폴링 전용 레이트리밋 버킷 · Origin 가드 상속 · 신원·내부 id·원문 미노출 · `no-store`.
- **폴링 전용 버킷**: `poll-ip:{ip}` 600/분 + 경로 키(상담 = 세션 40/분, 보류 답변 = messageId 60/분). 폴링은 기존 `ip`·`session` 버킷을 **소비하지 않는다** — 같은 NAT 뒤 폴링이 일반 전송을 429로 만들던 K-1 결함도 같은 장치로 고친다(**별도 커밋으로 선행 가능**).

### 3. `sessionId`는 신뢰하지 않는다 — 서버 발급 1회 상담 토큰

- 256비트 난수, DB에는 sha256만, 상담 1건 한정, **CAS로 정확히 1회 발급**(관찰 창 폴링 또는 다음 발화 중 먼저 온 쪽), 봉투 밖 `sessionStorage` 별도 키, 헤더 전송, 상수 시간 비교, 종료 5분 뒤 무효.
- 토큰 없는/틀린 요청은 상담 메시지를 **받지도 보내지도 못한다**(중립 안내 + 미확인 시도 카운트 — 선점 탐지). 토큰 없는 폴링은 활성 상담의 존재조차 드러내지 않는다.
- 관리자 API·콘솔·감사에는 전체 `sessionId`가 없다 — `sessionRef`(챗봇별 해시 16자)와 별칭(앞 6자)만. DTO에 필드 자체가 없다.

### 4. 배정은 DB가 판정한다 — 부분 유니크 + CAS

- `(chatbotId, sessionId) WHERE status IN ('CONNECTING','CONNECTED')` 부분 유니크(마이그레이션 원시 DDL — `test_runs`·`deploy_schedules` 선례) → 동시 개입은 정확히 1건만 성공. 전송·종료·인수·토큰 발급·시간 종료는 전부 조건부 갱신(ADR-0032 형식). 새 프로세스 로컬 상태 0.
- 전송은 담당자만, 종료는 담당자·ADMIN, **강제 인수는 ADMIN만**(사유·감사).

### 5. 시간 종료는 조회 시점 판정 — 같은 판정을 60초 정리 루프도 호출한다

- 사용자·상담원 무응답·미전달·채널 닫힘을 순수 함수 1개로 판정하고, 콘솔·공개 요청 시점과 **`PollingLoop`(ADR-0032 부품의 두 번째 소비자) 60초 루프**가 호출한다. 모든 인스턴스가 실행해도 CAS가 1회만 통과시킨다.
- 루프를 두는 이유는 6절이다 — 아무도 조회하지 않는 상담(사용자 이탈 + 콘솔 닫힘)의 원문을 제때 파기해야 한다.

### 6. ★ 원문은 상담 중에만, 행 단위로 잠시 — 영구 저장은 마스킹본만 (P-9)

- **보관**: `HandoffMessage.rawText` — 사용자 메시지 · `CONNECTED` 중 적재 · 마스킹본과 다를 때만 · 메시지당 최대 60분(`rawExpiresAt`). 서버 메모리 보관은 다중 인스턴스·재시작에서 깨지므로 기각, 별도 원문 테이블 + 행 삭제는 "상담 기록 삭제 경로 0" 봉인과 충돌하므로 기각.
- **파기 3겹(필드 소거 — 행 삭제 아님)**: ① 종료 CAS와 **같은 트랜잭션**의 `rawText = NULL` ② 60초 루프(시간 종료 + 만료 + 종료됐는데 남은 원문) ③ 읽기 경로가 `CONNECTED ∧ rawExpiresAt > now`만 노출(논리 즉시). 소거 트랜잭션마다 **`PRAGMA secure_delete = ON`**으로 SQLite 페이지 잔존을 덮는다(원시 SQL 1줄 격리 파일 — R-7 3 → 4). 저널·백업·파일시스템 잔존은 운영/No.45.
- **열람**: 담당자·ADMIN · `cs:write` · 상담 중 · **명시 요청(`includeRaw`)**. 출구는 실시간 대화 보기 1개. EDITOR·비담당 AGENT·이력·힌트·폴링·통계·스냅샷·감사·로그는 마스킹본만(정적 검사로 봉인).
- **열람 감사**: 신규 `AuditAction` **`RAW_VIEW`** — 원문이 실제로 응답에 실린 **(상담, 열람자)당 1건**. 이 프로젝트 최초의 읽기 감사다(마스킹본 열람은 계속 비감사). P-16 권고안 "열람 미감사"를 이렇게 조정한다.
- **상담원 발신은 계속 마스킹**(출구 금지어 → PII, 전달 원천 = 저장본) + 전송 전 미리보기.

### 7. 역할 `AGENT`와 권한 `cs:read`·`cs:write` 신설 (P-7)

`RoleName` 3 → 4, `Permission` 15 → 17. `AGENT = chatbot:read + cs:read + cs:write` · `EDITOR += cs:read` · `ADMIN += 둘 다` · VIEWER 불변. 원문·전송·종료·인수는 가드 위에 서비스 재검증(담당자·역할).

### 8. 상담 기록은 지우지 않는다 · 설정·문장은 스냅샷 밖

- 상담 스레드 2테이블 **삭제 경로 0**(ADR-0033 확장) · 쓰기 1파일 · FK `Restrict` · 메시지의 유일한 갱신 = 원문 소거 · 챗봇 영구삭제 사전검사 11 → 13(`상담`·`자주 쓰는 문장`).
- 상담 설정은 **신규 1:1 `ChatbotHandoffSetting`**(+ 전용 캐시). `ChatbotAnswerSetting`에 동거시키지 않는다 — 그 행은 스냅샷 대상이고 복원이 `DELETE`/`UPSERT`하므로 복원이 상담을 끄거나 되돌리게 된다. 자주 쓰는 문장(`CannedResponse`)도 스냅샷 밖.

### 9. 응답힌트는 기존 자산 검색이다

의미 매칭 상위 3(기존 `SemanticMatchService` — 질의 임베딩 1회, 운영 LRU 공유) → 불가 시 기존 `suggestIntents()` 입력 확장(함수 1벌) + 자주 쓰는 문장 상위 3. 입력은 마스킹본. 외부 RAG·LLM·요약 0 → **GPU 1 유지**, ADR-0026 포트 승격 트리거 미발동.

## 근거

- **"세션 테이블"이 아니라 "스레드"**: 모든 세션에 행을 만들면 턴마다 쓰기(SQLite 단일 작성자)·만료 배치·엔진 재작성이 따라오는데, 모니터링은 로그 읽기로 이미 얻는다. 상담이 일어난 세션만 행을 가지면 만료 정리가 필요 없고 그 행이 곧 이력이다.
- **분기를 엔진 앞에 두는 이유**: 엔진·시뮬레이터·TC·버전의 결과를 바이트 단위로 지키는 가장 싼 방법은 엔진이 상담을 모르게 하는 것이다. BLOCK 경로가 같은 모양을 이미 증명했다.
- **폴링을 고른 이유**: SSE·WebSocket은 다중 인스턴스 팬아웃에 pub/sub(Redis 유보)가 필요하고 위젯 예산·프록시 설정·재연결 비용이 크다(ADR-0023 23행 논리 그대로). 채팅 상담에서 평균 1.5초·최대 3초 지연은 허용 범위이며 DB 원천이라 다중 인스턴스에 추가 조정이 없다.
- **토큰을 봉투 밖에 두는 이유**: 봉투는 무서명·클라이언트 보관이며 "사용자가 직접 입력해도 같은 결과가 되는 값"만 담는다(ADR-0009 §3). 토큰은 신원 값이다.
- **원문을 DB 컬럼에 두는 이유**: 사용자 발화를 받은 인스턴스와 콘솔 요청을 받은 인스턴스가 다를 수 있다. DB가 원천이면 이 문제가 없고, 파기가 "상태 CAS와 같은 트랜잭션"으로 표현돼 "종료됐는데 원문이 남은 상태"가 커밋될 수 없다. 조회 시점 판정만으로는 조회가 없으면 파기도 없으므로 주기 루프가 필요하다.
- **열람 감사를 (상담, 열람자)당 1건으로 두는 이유**: 2초 폴링마다 기록하면 상담 1건에 수백 행이 쌓여 감사 신호가 사라진다. 물어야 할 질문("누가 어느 상담의 원문을 봤는가")에는 1건으로 충분하다.

## 대안과 트레이드오프

| 대안 | 기각 사유 |
|---|---|
| 봉투에 "상담 중" 플래그 | 상태전이·권한 값 — ADR-0009 §3 위반. 사용자가 지우면 상담원 모르게 봇으로 돌아간다 |
| 전 세션 서버 세션 테이블(ADR-0009 전면 대체) | 턴마다 쓰기·만료 배치·엔진 재작성. 얻는 것(모니터링)은 로그로 이미 얻는다 |
| 보류 답변 폴링 재사용 | 메모리·단발·90초 — 상담원 선발신·연속·장시간·다중 인스턴스 불가 |
| SSE / WebSocket / 롱폴 | 팬아웃 인프라·의존성·프록시·열린 요청 누적(ADR-0023 대안 A·B 사유) |
| 모든 열린 위젯 상시 폴링 | 방문자 수에 비례한 트래픽 — 관찰 창이 개입 후보만 정확히 고른다 |
| `sessionId`만으로 상담 송수신 | 세션별 서버 데이터를 공개로 돌려주는 첫 사례 — 엿보기·가장 가능 |
| 토큰 재발급 허용 | 선점 공격자가 재발급으로 정상 사용자를 밀어낸다. 1회 발급 + 탐지 + 재개입이 더 단순·안전 |
| 원문을 서버 메모리에만 | 다중 인스턴스·재시작에서 깨진다(ADR-0032 원칙) |
| 원문 별도 테이블 + 종료 시 행 삭제 | PM 조건(필드 소거)·삭제 경로 0 봉인과 충돌 |
| 원문 열람을 매 요청 감사 | 감사로그 폭증 — 신호 소실 |
| 원문 열람 미감사(요구사항 권고) | P-9로 원문이 생긴 이상 "누가 봤는가"를 남기지 않으면 사후 확인이 불가능하다 |
| 상담원 발신도 원문 전달 | 상담원 원문 임시 보관이 추가되고 외부(호스트 페이지)로 나가는 PII가 늘어난다 |
| 상담 설정을 `ChatbotAnswerSetting`에 동거 | 버전 복원이 상담 설정을 지우거나 되돌린다 |
| 시간 종료를 조회 시점만으로 | 조회 없는 상담의 원문이 무기한 남는다(P-9와 양립 불가) |

**감수하는 비용**
① `@Public()` 표면 1개와 폴링 트래픽(상담·관찰 세션에 비례) — 보상 통제와 전용 버킷으로 상쇄.
② 구버전 위젯은 토큰 없이 `sessionId` 신뢰 수준으로 동작 — 격하 경로의 본질, 콘솔 배지로 드러낸다.
③ 원문이 상담 중 최대 60분 DB에 존재하고, 저널·백업 수준의 잔존은 애플리케이션이 보증하지 않는다 — 운영(디스크 암호화·백업 보존)과 No.45로 넘긴다.
④ 정리 루프라는 두 번째 상시 타이머가 생긴다 — 도메인 무관 `PollingLoop` 재사용·멱등 CAS라 다중 인스턴스 조정이 없다.
⑤ `AGENT`가 `chatbot:read` 화면 전체를 조회할 수 있다 — PM이 확정한 권한 집합(마스킹본 등급).

## 갱신 (2026-09-26 — No.45: 상담 텍스트 필드 암호화 · 종료 상담 보존 소거 · 원문 표시와 열람 감사의 상호작용 · 물리 잔존 = 디스크 암호화 전제)

데이터 거버넌스(No.45, **ADR-0040 §3·§4·§7**). 결정 1~9, 특히 **원문 정책(상담 중 · 마스킹본과 다를 때 · 최대 60분 · 필드 소거 3겹 · 담당자·ADMIN · `RAW_VIEW`)은 불변**이다.

1. **필드 암호화**: 거버넌스 모드 + `DATA_ENCRYPTION_ENABLED`에서 `HandoffMessage.rawText`·`text`는 `enc:v1:<keyId>:…` AES-256-GCM 봉투로 저장된다(AAD = 테이블:컬럼:행 id — 쓰기 파일이 행 id 선발급). 마스킹·원문 보관 판정은 평문 기준 그대로이고 봉인은 저장 직전 마지막이다.
2. **원문 개봉 = 표시 판정 뒤**: 대화 보기는 `canViewRaw()`·행별 표시 조건을 **먼저** 판정하고 통과한 행만 원문을 개봉한다. 개봉 실패는 원문 키 생략(마스킹본만) — 원문이 실리지 않았으므로 `RAW_VIEW`도 남지 않는다.
3. **열람 감사의 두 층**: `RAW_VIEW`(원문 실제 노출 · (상담, 열람자)당 1건 · 모드 무관)는 불변. 거버넌스 모드에서는 같은 대화 보기가 `VIEW`(마스킹본 열람 · (열람자, 세션, KST 일)당 1건)도 남긴다 — 의미가 달라 둘 다 기록된다. 진행 중 목록·상담 상세도 `VIEW` 대상이다.
4. **원문 소거와 재암호화의 경합**: 재암호화 잡은 기존 값 조건부 갱신(CAS)이라 종료·정리 루프의 `rawText=null`이 항상 이긴다.
5. **보존 소거**: 종료된 상담의 메시지 `text`는 보존기간(`HANDOFF_TEXT`) 경과 시 `""`로 소거된다(행·seq·수치 유지 — 행 삭제 0 봉인 불변). 진행 중 상담은 대상 아님.
6. **감수 비용 ③(물리 잔존)**: `secure_delete`는 DB 페이지만 덮는다 — 저널·WAL·백업 잔존은 **디스크 암호화를 거버넌스 모드의 운영 전제**로 명문화하고, 데이터 지도는 이를 운영자 자기 신고값으로 보여 준다.
7. 재검토 트리거 "원문 60분 상한 부족·원문 열람 권한 위임 → No.45와 함께"는 **미발동** — No.45는 원문 정책을 넓히지 않았다.

## 갱신 (2026-09-26 — No.42: 재검토 트리거 "No.42" 이행 — 상담 1건은 고객 스레드의 항목 · 원문 정책 불변)

통합 인박스(No.42, **ADR-0042 §4·§5**)가 재검토 트리거 "No.42 옴니채널 통합 인박스 → 스레드를 채널·챗봇 축으로 확장"을 이행했다. 결정 1~9(특히 상담 1건 = 한 챗봇·한 세션 · 부분 유니크 잠금 · 1회 토큰 · 원문 60분·`RAW_VIEW` · 삭제 경로 0)는 **불변**이다.

1. **확장 방식 = 상위 개념 추가, 상담 행 변경 0**: 고객(`Customer`)·대화-고객 연결(`CustomerLink`)·고객 스레드(`InboxThread`)를 새로 두고, 상담 1건은 **세션 기준 조인**(`HandoffSession(chatbotId, sessionId)` = 연결)으로 스레드의 항목이 된다. `HandoffSession`·`HandoffMessage` 컬럼 추가 0 · 쓰기 파일 1(H-2) 불변.
2. **상담 시작 → 스레드 열림**: `createHandoff` 트랜잭션 성공 뒤 순수 포트 신호 `HANDOFF_OPENED` 1줄(No.41 `emit` 다음 · await 0). 신호 처리 실패는 개입 결과에 영향이 없다.
3. **담당의 두 층**: 스레드 담당(고객 관리 책임)과 상담 담당(`assignedUserId` — 실시간 대화 잠금)은 별개다. 인박스에서 상담을 시작하면 스레드 담당이 비어 있을 때만 그 상담원이 된다.
4. **원문 정책 불변**: 스레드 타임라인·고객 카드·검색은 `HandoffMessage.text`(마스킹본 — 암호화 시 개봉)만 읽고 `rawText`를 선택하지 않는다. 원문 표시 출구는 기존 대화 보기 1곳 그대로다.
5. **여러 챗봇 동시 모니터링**(FR-CS2-8 이관): 인박스 목록이 "볼 일이 생긴 고객" 단위로 대체한다. 챗봇별 실시간 모니터링(최근 창·경고)은 이 ADR의 화면 그대로다. 두 챗봇에서 같은 고객이 동시에 상담받는 것은 여전히 허용되고 스레드가 "진행 중 상담 N건"으로 드러낸다.
6. **콘솔 연계**: 대화 보기·상담 상세의 기존 응답(H-14·H-17 키 집합)은 바꾸지 않는다 — 고객 카드는 신규 조회 `GET /inbox/session-link`로 얻는다.
7. `live-sessions.service.ts`의 채널 리터럴 분기(`handoffSupported`)는 채널 능력 표 조회로 옮겼다(동작 불변 — ADR-0011 갱신 각주).
