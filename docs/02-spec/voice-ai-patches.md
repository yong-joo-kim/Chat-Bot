> **적용 상태(갱신)**: ✅ 2026-10-01 전부 적용됨(95교체 — 앵커 1회 일치 확인 후 바이트 보존 적용). 아래 옛 문구는 이력. ⏳ **미적용 — 적용 대기(오케스트레이터)**. 2026-10-01 architect 세션(구현 반영 회차)에도 부분 수정 도구·셸이 없어 CRLF 파일을 바이트 보존으로 고칠 수 없었고, LF 문서도 1,000줄 안팎이라 전체 재작성은 원문 훼손 위험이 커서 앵커 패치로 남겼다. 대신 **A-1~A-19 · B-1 · C-1~C-2 22건의 "찾을 원문"이 대상 파일에서 각각 정확히 1회 일치함을 2026-10-01 작업 트리에서 다시 확인**했다(개발명세서 40·45·60·66·82·101·152·321·396·397·422·660·684·719·725·780·847·881·932행 · 기능요구사항 74행 · ADR-0024 117·201행). §D~§F의 LF 문서 패치 앵커(교체 단위 73개)도 같은 날 각각 1회 매칭을 확인했다. 적용한 항목은 아래 **§0 적용 현황표**의 상태 칸을 "✅ 적용됨(일자)"으로 바꾼다.
> **적용 방법**: 각 항목의 "찾을 원문"을 대상 파일에서 **정확히 1회** 찾아 "바꿀 내용"으로 교체한다. "바꿀 내용"이 원문을 그대로 포함하는 항목은 append다.
> **줄바꿈 주의**: §A·§B·§C 대상 파일(개발명세서·기능요구사항·ADR-0024)은 **CRLF**다 — 모든 "찾을 원문"은 **한 줄 안의 부분 문자열이며 그 줄의 끝**이다(줄바꿈 미포함). "바꿀 내용"의 줄바꿈은 CRLF로 정규화하고, 파일 전체는 바이트 단위로 보존한다(예: Python `open(p,'rb')` → `data.count(old) == 1` 단언 → `data.replace(old, new, 1)` → `open(p,'wb')`). §D·§E·§F 대상 파일은 **LF**다(그대로 문자열 교체).
> **순서 독립**: 어떤 "바꿀 내용"도 다른 항목의 "찾을 원문"을 새로 만들지 않는다. 같은 줄에 앵커가 둘인 경우는 **D-32·D-33(설계서 753행)과 F-17의 첫째·둘째 교체(화면 명세 1010행)뿐**이며, 둘 다 서로 겹치지 않는 부분 문자열이라 적용 순서와 무관하다.
> 코드 변경은 이 파일의 범위가 아니다 — 설계서 §17(역할별 체크리스트)을 따른다. **`CLAUDE.md`·`docs/04-test/*`·changelog는 이 패치의 대상이 아니다**(사용자/오케스트레이터·시험 단계 처리).

## 갱신 (2026-10-01 — No.32: 음성 인식 전용 배타 역할 `speech` · 재검토 트리거 "음성 착수" 해소)

1. **재검토 트리거 "음성(STT/TTS)·비전 착수 → 내부 구조 재결정"의 판정**: STT는 인증 없는 공개 경로가 부르는 **요청당 GPU 추론**이라 대화 임베딩(300ms 예산)·증강 생성과 같은 프로세스에 두지 않는다. → **배타 역할 `ML_WORKER_ROLE=speech`** 를 둔다(값 = `embed`·`augment`·`both`·`speech` · `speech`는 다른 역할과 결합 불가 · `both`의 의미 불변 · 알 수 없는 값은 기동 실패). `speech` 역할은 STT 1종 + VAD만 적재하고 `POST /speech/transcribe`(원시 바이트 → `{ modelId, text, durationMs, empty }`)·`GET /speech/health`만 더한다. 다른 역할에서 `/speech/*`는 404, `speech` 역할에서 `/augment`·`/cluster-label`은 404, `/embed`·`/health`는 역할 무관 계약 그대로(이 역할에서는 `loading`/503). 같은 패키지·같은 진입점이다(별도 앱 모듈 기각 · 실행 스크립트 `start:speech`는 Windows에서도 도는 래퍼).
